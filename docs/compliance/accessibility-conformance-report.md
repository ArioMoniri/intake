## 0 · How to read this report

**This report states tested results. It is not a declaration of conformance.** Every status is backed by at least one named automated test or one dated manual check, and the evidence column names them. No row rests on a device screen-reader run, because none has been performed.

**What the automated evidence can and cannot prove.** React Native has no DOM, so no axe-style engine can run: the accessibility tree is built by the OS at runtime, on a device. The tests prove that the source declares what that tree is built from: roles, names, states, languages, announcements, target sizes and the motion policy. A Supports row therefore means the mechanism is present, asserted and read. Nobody has yet heard it through a screen reader. The device audit (§5) confirms or overturns these rows.

**The BK numbers are derived, not transcribed** (HB-L9). WCAG 2.2 Level A has exactly 31 criteria, and the Ministry checklist has 31 Başarı Kriteri mapped 1:1, so the correspondence is forced. The order follows canonical WCAG numbering. Check each number against the Ministry's published checklist before citing it in an İnceleme Komisyonu submission.

**Scope.** Every screen of `apps/mobile`. Kiosk mode is built but cannot activate in the current runtime (`readKioskProvisioning` returns null until the dev-build native layer exists), so it is out of scope except where a row names it. The RED emergency delivery route still has no user interface: on 2026-09-26, `grep -rn lib/livekit apps/mobile/src/app apps/mobile/src/components` returned nothing. Nothing on that route is assessed. `docs/compliance/accessibility-conformance.md` §4 lists the requirements the issue that builds it must carry. `apps/clinician-web` and `apps/admin-web` (EN 301 549 clause 9) are not assessed.

**Relation to INT-144's report.** `docs/compliance/accessibility-conformance.md` (29 August 2026) remains the narrative assessment, and rows here cite its sections. Where the two differ, this report is the status of record. Re-assessment changed these rows: 1.3.4 (unverified, then Does Not Support because the app config locked portrait, and Supports since INT-360 removed the lock); 3.3.1 (supported, then Partially Supports because error lines added since were silent under VoiceOver, and Supports since INT-362 routed every error line through one announcer); 3.3.8 (not assessed before, then Does Not Support, and Supports since INT-361 let a delivered code fill the boxes); 4.1.3 (not assessed before, then Partially Supports because INT-362 closed the three lines INT-226 named and three others stayed silent, and Supports since INT-397 announced those three when they happen); 3.1.2 (unverified, now Partially Supports); 1.3.5 (partial, now Supports, on a recorded field inventory); 1.4.12 and 2.4.5 (supported by inspection, now Not Applicable, with the reason in each row). Two of INT-144's supporting statements did not hold on 26 September: the OTP autofill mitigation named under BK26 (MC-16), which the source carries since INT-361 and DA-07 confirms on a device, and "exactly one timer in the whole app" under BK13, which is true of screens and components only (MC-08).
