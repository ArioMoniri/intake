# ADR-030 · A clinical quantity crosses INTAKE's own wire as a tagged JSON string

Status: Accepted

## Context

CLAUDE.md invariant 22 opens with the rule this document discharges: *numbers never cross a representation boundary unguarded*. files/13 §9.5 names the type that carries them — *"no floats anywhere, `Decimal` with declared scale and exact comparison, because floats are how two machines disagree about the same session"*. INT-303 put `Decimal` into the comparison carrier `clinical_schemas.common.JsonScalar`, because a `Decimal` reaching `canonical_scalar` had been read as Unknown and a red-flag rule gating on it silently never fired — invariant 1's worst failure, the one nothing reports. INT-303 closed the seam in memory and declared the surrounding gap open. INT-309's adversarial review found the same defect on the other side of serialisation: holding `Decimal` in a union says nothing about what happens when the union is written down.

Three boundaries lost or misreported it, and the third is the one that needed a decision rather than a patch. `to_r4._scalar_answer` had branches for bool/int/float/str and fell past all of them to `MappingError("a None answer inside a list is malformed")` — a false diagnosis, since the value is neither None nor malformed. `intake_platform.overlay.store._encrypt` called `json.dumps` with no `default=`, so a learned fact whose value is a measurement — the first thing files/09 §3 names — raised `TypeError` after the fact had already been minted. And the JSON round trip restrung it: `Decimal("38.50")` dumped to the JSON string `"38.50"` and validated back as `str`, which `canonical_scalar` reads as Unknown. That is the INT-303 defect relocated to the wire, and it is a **regression** against the pre-INT-303 `float`, because a float at least still compared.

The ambiguity was already committed as a fact rather than introduced by this change. `packages/clinical-schemas/schemas/openapi.json` carried `JsonScalar` as an `anyOf` with two indistinguishable `string` members — an arbitrary string, and a decimal-shaped string with pattern `^(?!^[-+.]*$)[+-]?0*\d*\.?\d*$`. No consumer can decide which one it is holding, and the generated TypeScript collapsed both to `string`. An undecidable union is the schema-level statement of the same bug, so this ADR repairs a defect rather than choosing an encoding for a green field.

Both obvious encodings were measured before anything was written, on the GPU server at commit `ec40e6c`, pydantic 2.13.4 (`docs/evidence/INT-309.md`):

- A JSON **number** cannot carry the declared scale at all. `TypeAdapter(Decimal).validate_json("38.50")` returns `Decimal("38.5")`. The scale is the one property a `Decimal` is kept for, so "number" is not actually an available option — it discards the reason the type exists, and 2**53 + 1 loses its last digit on top.
- A **bare** JSON string cannot be told apart from a string answer, and a string answer is a real thing this grammar carries. The INT-031 `SessionState` fixture is `slots={"ates": "38.6"}`, and `tests/safety/test_numeric_carrier.py` pins `canonical_scalar("38.5")` as a `str` that must never be coerced into a numeric comparison (files/03 §4.9.6: a separator cannot be resolved without an expected magnitude). Any fix that reads numeric-looking strings back as `Decimal` breaks both, and breaks them in the direction that makes a rule fire on a value the rules never authorised.

## Decision

A clinical quantity crosses INTAKE's own wire as a **JSON string, tagged**, applied by one codec at one place — `encode_json_value` / `decode_json_value` in `clinical_schemas.common`, wired onto the `JsonValue` alias as a `PlainSerializer` and a `BeforeValidator`. `Decimal("38.50")` is the JSON string `"~d38.50"`: the reserved character `~`, the marker `d`, then the exact digits with the declared scale intact. A plain `str` whose first character is `~` is escaped by doubling it. The escape is what makes the encoding **total and bijective** rather than merely unlikely to collide: a patient answer is never refused for the shape of its first character, and never silently reinterpreted as a number. A tagged payload whose digits the `Decimal` constructor refuses raises rather than passing through as a string, because a quantity that arrived corrupt must not become a value the comparison grammar reads as Unknown.

The exported schema is made decidable to match. `JsonScalar` now spells three mutually exclusive string members — `{"type":"string","not":{"pattern":"^~"}}`, `{"pattern":"^~~"}`, `{"pattern":"^~d"}` — plus integer, number, boolean and null, so a consumer of the OpenAPI can decide which member it holds. The generated TypeScript is unchanged in shape: a tagged decimal is still a `string`.

**The alternative we rejected: an object wrapper.** `{"__decimal__": "38.50"}` is unambiguous with no escape scheme at all, and therefore imposes no rule that every plain string in the system pays forever — a real advantage, and the reason it deserves recording rather than omitting. It was rejected on shape, not on taste. `JsonScalar` is a *scalar* position: a wrapper makes a scalar an object, so `list[JsonScalar]` becomes a list of objects, `dict[str, JsonScalar]` a map of maps, and the carrier stops meaning what its name says. It also collides with a legitimate `dict[str, JsonScalar]` value that happens to use the reserved key, which is the same ambiguity relocated rather than removed — closing it needs an encoder that refuses that key, which is an escape scheme wearing different clothes. And it is heavier on every wire for a case that is one character in the chosen form. The tag keeps the carrier's shape; the wrapper keeps every string cheap. We took the shape.

## Consequences

**The FHIR mappers deliberately do not use this.** FHIR R4 requires `decimal` to be a JSON number, so `QrAnswer.value_decimal` widened from `float | None` to `Decimal | float | None` and serialises to a JSON number via a field serializer — the same split `Quantity` already makes. The Python side keeps the `Decimal` and its scale; the documented loss is that trailing zeros normalise when a resource is actually emitted as FHIR JSON, and a foreign format's constraint is not ours to reinterpret. `float` stays in that union because an answer that arrived as a float must come back a float: `Decimal(str(0.1))` is not `0.1`, so promoting one would change the number. Both members are pinned by `tests/schemas/test_fhir_mappers.py` so neither half can quietly disappear.

**`JsonValue` decodes in both validation modes, which makes it a wire type in Python too — and that is this decision's real cost, not a footnote.** The safer-looking choice was to gate the `BeforeValidator` on `info.mode == "json"`, so that only a value that genuinely came off a wire is decoded. It is wrong here, and wrong on the path that matters most: FastAPI parses a request body with its own JSON reader and hands pydantic the resulting **dict**, which validates in *python* mode. A json-only decoder would therefore leave every inbound API quantity a string — the original defect, restored at the front door, and restored silently, which is the property that makes it the worst kind. The same is true of every `json.loads(...)` followed by `model_validate(...)`, including `intake_platform.overlay.store._decrypt`, which is what lets the store encode explicitly and get the read side for free.

The price is a footgun, and it is stated here rather than left to a stack trace: **a model constructed in Python takes wire form.** Handing raw text that begins with the reserved character straight to a constructor decodes it, so a literal `~` must be written `~~`. Every actual wire crossing is safe, because the encoder escapes on the way out and the round trip is bijective; only direct Python construction from unescaped text is exposed, and `services/api` (which receives already-encoded bodies) and `intake_platform.overlay.store` (which encodes on the way in) are the two construction sites today, both correct. The constraint is pinned by `tests/schemas/test_roundtrip.py::TestADecimalCrossesTheWireAsItself::test_a_string_that_looks_like_the_tag_round_trips_as_that_string`, added in commit `d1f3bf1`, whose fixture is spelled `~~d38.50` for exactly this reason and says so in its docstring.

**One module owns the prefix, and a test enforces it.** A reserved prefix is total only while every reader goes through the codec. If one path does not, a patient or a clinician reads the literal `~d38.50` — invariant 22's failure mode wearing a different mask, and worse than the trailing zero the tag protects. `tests/safety/test_numeric_carrier.py::TestTheWireTagNeverReachesAHuman` gates all three render surfaces (the typed numeric rail, which under files/03 §4.6 invariant 30 is the *only* channel a number has in typed; the clinician evidence line of files/04 §5; and a patient answer that begins with the prefix), and sweeps every module under `packages/*/src` and `services/*/src` for a second hand-rolled copy of the tag. The sweep reads string *literals* through `ast` rather than raw file text, because `:class:`~decimal.Decimal`` is a Sphinx cross-reference in three docstrings and a gate that cries wolf gets deleted.

**The overlay envelope shares the codec rather than inventing a `default=`.** `default=str` and `default=float` both make `json.dumps` succeed, which is worse than the crash they replace: the first reads back a string the comparison grammar cannot use, the second reads back a different number. The store encodes explicitly and lets the `LearnedFact` validator decode, so there is one definition of how a quantity crosses JSON and the read side is free.

Enforced by `tests/schemas/test_roundtrip.py`, `tests/schemas/test_fhir_mappers.py`, `tests/learning/test_overlay_provenance.py` and `tests/safety/test_numeric_carrier.py`; the exported OpenAPI, event schemas and generated TS are regenerated and drift-checked; recorded against files/10 §9 row `records`.
