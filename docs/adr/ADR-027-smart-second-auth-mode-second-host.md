# ADR-027 · SMART backend services: a second auth mode, a second host, and one token per push

Status: Accepted

## Context

INT-161 has to push a FHIR R4 document Bundle to a hospital FHIR server, and the acceptance names the authentication: SMART backend services. INT-160 deliberately gave `auth_mode` exactly one member — `mtls` — and recorded in the schema that SMART "arrives with the FHIR adapter (INT-161) as an added member, never as a relaxation of this one", so the question this ADR answers is whether a second member was actually necessary and, if so, what it costs. It is necessary, and the cost is not in the schema: `mtls` authenticates the **channel** with material OpenBao already holds, so a push is one request to one host, whereas SMART authenticates the **client** by minting a JWT assertion, exchanging it at the hospital's *authorization server* for a short-lived access token, and presenting that token on the FHIR request. That is two requests to two hosts, and the second host is the whole security question. ADR-025 named five ways a hostname allow-list is bypassed and the fifth — the right host addressed for the wrong reason — arrived in INT-160 in a form ADR-025 could not express: a host contracted, approved and allow-listed for a **different tenant**, answered with the tenant dimension in the connector registry. A SMART token endpoint is that same bypass in a third form: a host on *this* tenant's own row, genuinely contracted and genuinely approved, for a purpose that is not receiving clinical records. Two further questions had no recorded answer: whether the token endpoint may be discovered rather than registered, and whether an access token may be cached across pushes. Both cheap answers are wrong in ways that are invisible afterwards.

## Decision

`auth_mode` gains `smart_backend_services` as a second member with per-mode requirements enforced by a model validator rather than by optional fields nobody checks together: SMART must declare `token_host`, `token_path` and `smart_scope` and may omit `client_cert_ref` (a hospital that authenticates by assertion has no client certificate to issue, and requiring one would make the row unfillable), while `mtls` still requires `client_cert_ref` and is **refused** if it names a token endpoint — a field a row's own auth mode never reads is an approval nobody reviewed for a host nobody reaches. The token endpoint gets its **own** `AllowlistEntry` from `ConnectorDestination.authorization_egress_entry()`, carrying a new closed-vocabulary purpose `EgressPurpose.CONNECTOR_AUTHORIZATION` and `phi_allowed: false` with no `phi_exception_approval`, because no clinical byte is ever sent there and a token endpoint that inherited `CLINICAL_RECORD_PUSH` would be a destination approved to receive patient records — ADR-025's fifth bypass granted by a shortcut rather than exploited; the two entries refuse each other's traffic, and one host serving both roles still needs both purposes. There is **no discovery**: SMART defines `/.well-known/smart-configuration` and this system never reads it, because discovery lets the receiver nominate the URL our client credential is sent to, which is a redirect to an unchecked host wearing a standard's name — the token URL and the assertion's `aud` are both built from the registry row. There is **no token cache**: one push, one assertion, one token, because a cached access token is a credential that outlives the consent check that authorised it, which is exactly the caching INT-160 already refused for the consent verdict itself. The assertion's `exp` is the **earlier** of a sixty-second ceiling and the share consent's own expiry (files/06 §2.1 `share:{recipient, visit, sections, expiry}`), which is what "scoped by share consent token" can mean at this layer and still be enforceable — the credential is valid only inside the window the patient's consent is, so a stale-consent authorization is refused by the *hospital's* clock as well as ours. The signing algorithm is derived from the key's own type (RS384 for RSA, ES384 for P-384) rather than configured, and a key that is neither fails closed. The token **success** body is read — under an 8 KiB cap, parsed as JSON, accepted only as `{access_token, token_type, scope?}` — because it is a credential we asked for and contains no patient; the token **error** body is not read at all, because the status already separates our assertion (400) from our client identity (401) from their outage (5xx).

## Consequences

`EgressPurpose` gains one member and `tests/security/test_egress_allowlist.py`'s `NON_VENDOR_PURPOSES` gains it too, keeping the "no dead members" rule intact while the companion test asserts the stronger direction — the purpose must be **absent** from the vendor file, never merely optional in it. OpenBao holds a different document for a SMART row: `{client_id, private_key}` plus an optional `key_id` under `credential_ref`, never a long-lived bearer, still under the `connectors/` subtree the connector policy is the only reader of; the public half of that key must already be registered with the hospital, which is a human transaction and not a field. A push now costs one extra round trip, on a path that is not hot. A failed token exchange can never produce an `unresolved` receipt whatever the destination's `receiver_idempotency` declares, because no clinical byte was ever in flight — the ambiguity INT-160 parks for a human exists only on the push itself. `OutboundCall` gains proposed `headers` so a per-hospital adapter can ask for `Accept` and `Prefer: return=minimal`; the framework applies its own last, so an adapter can never set `Authorization`, `Idempotency-Key` or `Content-Type` — respectively the credential, the replay identity and the content contract. `ConnectorAdapter` gains `failure_hint`, which reads a diagnosis from **headers only** and returns one id-shaped token the sender re-checks before it reaches a receipt. The registry still ships with **zero rows**: a SMART destination costs everything HB-A15 already names plus a registered client key, a token endpoint and a granted scope, none of which an engineer may supply.
