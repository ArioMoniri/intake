# ADR-026 · Connector destinations: a second list, one enforcement engine, and a receipt written before the send

Status: Accepted

## Context

INT-160 has to build the outbound path from a system holding patient records to a hospital system, and every invariant this repository holds is on that path at once: invariant 4 (every share checks a consent scope and is audited), invariant 6 (no PHI in a log, a trace or an error report), invariant 14 (secrets only from OpenBao; records are data, never instructions) and files/10 invariant 46 (destinations resolve only against a registered per-tenant allow-list bound to the DPA, with free-text entry absent from the schema). ADR-025 settled the vendor case and named five ways a hostname allow-list is bypassed — literal IPs and private/link-local/metadata ranges, a hostname that *resolves* into one of those ranges, a second resolution between check and connect, a redirect to a host nobody checked, and *the right host addressed for the wrong reason*. A connector is the component most likely to reach all five, and the fifth arrives here in a form ADR-025 could not express: a host that is genuinely contracted, genuinely approved and genuinely on a list — for a **different hospital**. `infra/security/egress-allowlist.yaml` cannot answer that, because a hospital endpoint is not a vendor row: it is per-tenant data registered at onboarding against one executed DPA, and putting it in the global file would make it reachable by every process that loads that file, for every tenant. Two further questions had no recorded answer and no third option: what an idempotency key is derived from and who is trusted to honour it, and whether a receipt is written before a send (and may claim one that failed) or after (and may miss one that succeeded).

## Decision

Connector destinations live in a **second list**, `infra/connectors/destinations.yaml`, addressed only by `endpoint_id` under a `tenant_id` — but they are enforced by **one engine**: `ConnectorDestination.egress_entry()` returns the very `AllowlistEntry` type the vendor file validates, so an IP-literal host, a `phi_allowed` row without a recorded approval, the resolve-once-and-pin, the denied-range refusal, the redirect refusal and the `INTAKE_ALLOW_PHI_EGRESS=explicit-yes` runtime double gate are all the INT-018 code and cannot drift from it; what the second list adds is the tenant dimension, and the vendor file's own test now asserts the stronger direction — `CLINICAL_RECORD_PUSH` must be **absent** from it. The **idempotency key is derived** from `(tenant_id, endpoint_id, resource_ref, sha256(payload))` and the **local ledger is the authority**: a key settled `delivered` is never re-sent whatever the receiver does, the key travels as `Idempotency-Key` so a receiver *can* deduplicate, and because "we sent it twice and the hospital deduplicated" is not a promise this system may make on a hospital's behalf, each row declares `receiver_idempotency` with no default — an ambiguous outcome (timeout, dropped connection, 5xx) is retryable only where the DPA says the key is honoured, and is parked `needs_human` where it does not. The **receipt is written before the send**: an under-recorded delivery is an unauditable disclosure and the failure invariant 4 exists to prevent, while an over-recorded attempt is a reconciliation task — so the write-ahead row says `attempted` and never `delivered`, the outcome is a second state transition and a second hash-chained audit entry, and the response **body is never read**, so a hospital's error text cannot become a log line, a receipt field or an exception message.

## Consequences

The registry ships with **zero rows** and the framework therefore refuses every send today: no DPA is executed, no endpoint is approved, no OpenBao credential path exists, and HB-A5 records that our pilot partner's own interfaces are UNVERIFIED — so the mechanism lands wired and fail-closed rather than with an invented value (invariant 17). A destination costs five recorded human facts (`dpa_ref`, `approval_ref`, `credential_ref`, `client_cert_ref`, `receiver_idempotency`) and a row is still not sufficient on its own, because the egress guard runs afterwards. Write-ahead has a visible price: a process that dies between the attempt and the outcome leaves an open receipt and an `in_flight` key that nothing resolves automatically — surfaced by `connector_receipts_unresolved_total` and `ReceiptStore.open_count()`, and deliberately not guessed. The sender is **synchronous** because the egress guard is a synchronous `httpx` transport and an async connector would need a second implementation of resolve-once-and-pin, which is the two-enforcers-that-disagree failure ADR-025 exists to prevent. `EgressPurpose` gains one member, `CLINICAL_RECORD_PUSH`, and mTLS material is materialised into a `0700` directory and a `0600` file for the length of one `load_cert_chain` — Python's `ssl` has no in-memory API — then zeroed and unlinked in a `finally`. Enforced by `tests/connectors/test_framework.py`, `tests/connectors/test_credentials_and_tls.py` and `tests/security/test_egress_allowlist.py`; signalled by `connector_push_total`, `connector_push_duration_seconds` and `connector_receipts_unresolved_total`; recorded against files/10 §9 row `connectors`.
