# ADR-025 · One egress allow-list, two enforcers, and a purpose on every call

Status: Accepted

## Context

INT-018 has to make CLAUDE.md invariant 19 true rather than asserted: "the `anthropic|openai|google` LLM adapters exist as the mock/dev path only and are blocked on the PHI path by the egress allow-list." A hostname allow-list consulted in one process does not do that. It is bypassed four ways that files/10 §4 names in a single sentence — literal IPs and private/link-local/metadata ranges, a hostname that *resolves* into one of those ranges, a second resolution between the check and the connect (DNS rebinding), and a redirect to a host nobody checked — and a fifth way that is not a network trick at all: the right host addressed for the wrong reason, which is how clinical data reaches a destination that is genuinely contracted, genuinely on the list, and genuinely not approved to receive it. A second, hand-maintained copy of the list inside a proxy config would add a network-tier enforcer and a new failure mode: two lists that disagree, where the disagreement is invisible until an audit. Deciding nothing leaves the invariant a claim, and leaves `infra/security/egress-allowlist.yaml` a document rather than a control.

## Decision

`infra/security/egress-allowlist.yaml` is the single source both enforcers read: `intake_platform.egress` loads it in process, and `scripts/security/render_egress_proxy_conf.py` **generates** the dev forward proxy's `squid.conf` from it, with CI failing on a stale render and a host table decided through both paths so their semantics cannot drift; every row carries a `purpose_id` from a closed vocabulary and a caller must present a matching `EgressPurpose` plus the `DataClass` it is sending, so personal data — pseudonymous included — moves only to a row that is `phi_allowed` and only for the purpose that row exists for; and the in-process guard resolves an authorised host exactly once, refuses any answer inside the ranges enumerated in `DENIED_RANGES`, and connects to the pinned address with `Host` and TLS SNI still naming the hostname, so there is no second lookup for a rebinding attack to win and certificate verification is unchanged.

## Consequences

The PHI tier of the allow-list stays empty (00_STATE D11), and `infra/docker-compose.egress.yml` expresses that as topology rather than as a comment: the `phi` network is `internal: true` and the proxy is not attached to it, so a PHI-path service has no route out at all — which is the honest reading of an empty tier. Adding any row to the PHI tier now requires a `phi_exception_approval`, the runtime `INTAKE_ALLOW_PHI_EGRESS=explicit-yes`, and a deliberate topology change, and `assert_dev_only_vendors` refuses the three vendor LLM families there outright. Enforcement gets more intrusive on purpose: every outbound integration must name its purpose and data class at construction, and a caller that skips it does not get a default, it gets a denial. `infra/security/egress-allowlist.yaml` remains hook-protected (07 §3.8); this ADR is the record that authorises the `purpose_id` schema addition made under INT-018, and the file returns to guard-only change after it. Enforced by `tests/security/test_egress_allowlist.py`, `tests/security/test_egress_policy.py` and `tests/infra/test_egress_proxy.py`; signalled by `sec.egress_denied_total` (files/10 §5: any increase pages); recorded against files/10 §9 row `cloud-boundary`.
