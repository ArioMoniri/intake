## 1. The reading-level check — what it measures, and what it does not

**It is a proxy, not a measurement, and the code says so in those words.** CEFR B1
describes a *reader* — what a person can do with a text — not a property a text carries.
Calibrating a threshold on Turkish text needs a Turkish corpus with reader outcomes and
this repo has none, so inventing a number would be inventing a value (HUMAN_BLOCKERS.md
rule 1). `ReadabilityReport` therefore has exactly two fields, `measures` and `findings`,
and a test walks `dataclasses.fields` and asserts there is no third:

```
test_the_report_carries_no_score_and_no_level
```

A "B1 score of 72" would read as a property of the product, which is what invariant 20
exists to stop.

### Three arms; two of them gate

| arm | what it is | gates? |
|---|---|---|
| PolicyGuard's per-sentence pass, run verbatim | diagnosis · treatment · prognosis · multi-question · register · jargon · the 15-word bound | yes |
| subordinate clauses per sentence (`B1_MAX_SUBORDINATE_CLAUSES = 1`) | the Turkish-specific arm PolicyGuard does not have | yes |
| syllables per word | exact, reported on every `SentenceMeasure` | **no** |

**Arm 1 is PolicyGuard itself, not a copy of it.** Invariant 2 names one guard. The
sentence-length bound and the jargon lexicon already live there, so neither is restated
here — one number, one word list, one owner. Growing a second clinical lexicon in a
readability module would be a clinical review dressed up as an engineering change.

**Arm 2 is the half that is actually about Turkish.** Turkish is verb-final and
subordinates with non-finite verb forms, so every embedded clause has to be held until
the matrix verb arrives. A word count cannot see it: *"Aldığınız belgeleri göstermek için
hazırlayarak getirin."* is six words — comfortably inside the 15-word bound — and three
clauses. Ten named arms (`factive_participle`, `future_participle`, `verbal_noun`,
`converb_arak`, `converb_ince`, `converb_ken`, `converb_madan`, `purpose_infinitive`,
`conjunction_ki`, `conditional`), each **demanding a stem** rather than matching a final
syllable — INT-248's lesson applied before it could bite, so `erken` is not a converb and
`tarak` is not a gerund. A finding names the arm that fired, because a finding a reviewer
cannot trace to a morpheme is a finding they learn to ignore.

**Arm 3 is measured and deliberately not gated, and this is the honest part.** Turkish
syllabification is *exact* rather than heuristic — every syllable has exactly one vowel
nucleus from a closed set of eight and there are no vowel digraphs, so counting vowels
**is** counting syllables, with none of the estimation an English syllable counter needs.
It is still the wrong thing to gate, because Turkish is agglutinative: word length is
morpheme count, not lexical difficulty. `hastalığınız` is five syllables and transparent
to every Turkish speaker; `anamnez` is three syllables and is jargon a B1 reader does not
carry. A Flesch-shaped formula — including the Turkish adaptations that keep Flesch's
syllable term — ranks that pair the wrong way round and penalises precisely the regular
morphology that makes Turkish easy to decode. A test states it as a pair: the long
agglutinated sentence **passes**, and `Anamnez alalım.` **fails**.

### What it does not capture — recorded in the module docstring, not only here

* **Vocabulary frequency.** There is no B1 Turkish word list in this repo and authoring
  one would be authoring content. A short sentence of unfamiliar but non-medical words
  passes every arm. The only vocabulary judgement in the whole gate is PolicyGuard's
  14-entry jargon lexicon.
* **Morphological load.** Four stacked derivational suffixes on one stem is a real reading
  cost and no arm sees it.
* **Information density.** Three short sentences can be harder than one medium one.
* **Whether the sentence should exist.** A perfectly simple sentence can still be a
  prognosis; that is arm 1's job, not arm 2's.
* **Its own precision.** Turkish homography survives the stem requirement: `artıkları`
  reads as a participle and `geleceği` is both *"that he will come"* and *"the future"*.
  Over-firing is **accepted here in a way it is not accepted in PolicyGuard**, and the
  asymmetry is the reason: an over-firing PolicyGuard drops a sentence at the microphone
  and the patient hears the safe bridge instead of the question (INT-248), while an
  over-firing arm here means an author writes a simpler sentence. Under-firing is the
  direction that costs, so the arm is biased that way.

### The gate refuses in two independent places

1. **At bind time.** `summary_copy_from_legal_strings` runs the check over every value and
   a single failure refuses the **whole catalogue** — a summary with a hole where a card
   title belongs is not a shorter summary, it is a different one.
2. **At build time.** Every *authored* segment is checked again as it is assembled,
   because a marker joined to a date is a string nobody authored. The two are tested
   separately, the second by constructing a `PatientSummaryCopy` directly so it cannot be
   caught by the first.

**The patient's own words are never measured and never rewritten.** A `SummaryLine` is
split into `authored` (the product's words, measured) and `quoted` (the patient's or a
document's, never measured). Rewriting what a patient said is its own defect, and failing
a build because somebody spoke a long sentence at the microphone would be that defect with
a deploy attached. A test feeds a 20-word complaint through, asserts it survives verbatim,
and asserts the control really is over the bound. A second test asserts the exclusion is
not vacuous.

## 2. Acceptance clause 1 — the wellbeing exclusion is a partition, not a filter

The obvious shape is a filter at the end of the builder, and the obvious shape is wrong: a
filter names what it *removes*, so a field added to `PreVisitNote` tomorrow is included by
**default** and nobody notices until it is on a patient's screen.

So every `PreVisitNote` field is named exactly once — in `SUMMARY_SECTIONS` or in
`EXCLUSION_REASONS` — and a test asserts the two partition `PreVisitNote.model_fields`
with no overlap. A new note field fails that test until somebody decides, in review,
whether a patient may read it. Every exclusion carries its reason; nine fields are
excluded and five of the reasons are not obvious:

| excluded | why it is not merely "clinician data" |
|---|---|
| `screening` | The acceptance clause. files/02 §5.6 puts wellbeing results on their own consent-gated surface, *"never scores and never labels"* — a PHQ-2 total in a pre-visit summary is a screening output on a surface that did not ask for it. |
| `konusma_ozellikleri` | Observer-lane output. files/03 §4.7.1: an interpretive statement about the patient's state is the device function itself. |
| `ros_pertinent` | The patient said it, and it still cannot be shown back. *Which* absences are pertinent is a clinical judgement (files/13 §9.3); rendered as a list of things the patient does not have, it reads as a finding about them. |
| `data_gaps` | Not just non-actionable — **unsafe**. The `deferred_environment` reason exists because a second voice was audible, so printing it tells the person in the room that sensitive questions were deferred because of them (files/02 §33). |
| `suggested_focus_questions` | Written for the resident who reads the note first (files/02 §5.7). A field whose name reads patient-facing and whose reader is not the patient is exactly how clinician material gets laundered. The patient's questions arrive separately, from their own words. |

The strongest form of the clause is a test, not a filter:
`test_a_scored_note_and_an_unscored_note_produce_the_same_summary` — a note with
`phq2=4, gad2=3, phq9=14, gad7=11`, a screening qualifier and a full `konusma_ozellikleri`
block builds a summary **equal** to one built from a note with none of them. The wellbeing
block is not omitted, it is not an input.

Two supporting absences:

* `test_no_wellbeing_token_appears_anywhere_in_the_summary` searches the whole value —
  joined field by field rather than through `model_dump_json`, because a serializer that
  escaped non-ASCII would make a Turkish token trivially absent and the leak test vacuous.
* `test_no_copy_key_can_name_an_instrument_or_a_lane` — there is no key through which a
  screening result could be *worded* into the summary even if a builder wanted one.

## 3. Attribution, in patient-facing prose

INT-084 enforced attribution **by refusal** — a relative-attributed item raises rather than
being relocated, because moving it silently hides the caller's bug. A friendlier surface is
where that gets flattened. Four things hold the line:

* **Every line carries a marker**, not only the exceptional ones. A marker on the
  exceptions makes the unmarked lines read as endorsed, so the rule is "every line" with no
  card-dependent branch to get wrong. A test asserts `copy.attribution(...)` appears in
  every line's authored half.
* **A relative's condition names the relative and appears exactly once.** The line sits on
  the `family` card, carries `Attribution.RELATIVE` and the localised subject, and a test
  asserts the condition string is on exactly one rendered line and appears in neither the
  `story` nor the `history` card.
* **A carried fact carries the date it was first recorded.** Without it a carried fact
  reads as a current one — the INT-247/INT-256 failure, and worse on the patient's own
  screen than on the clinician's, because the patient has no second source. Deleting the
  date from `_marker` was one of the three mutations in §5 and it failed the suite.
* **Refusal, not relocation, at the one new entry point.** `questions_for_doctor` is the
  only place this issue accepts new patient material; a `RELATIVE`-attributed question
  raises `AttributionRefused` — INT-084's own exception, imported rather than re-declared.

Two structural absences do the rest. `SUMMARY_ATTRIBUTIONS` omits `RULES_ENGINE` and
`LLM_CANDIDATE`, so there is **no marker key** by which a fired rule or a candidate flag
could be worded onto a card — invariant 1's summary face is a missing vocabulary rather
than a filter somebody has to remember to run. And `SUMMARY_SUBJECTS` omits `PATIENT`: a
line about the patient is named by its attribution marker, and "hasta" on the patient's own
screen is the clinician's word for them.

### The stopped medication

`MedicationItem.reconciliation` has four states and there is **no patient-facing copy key
for any of them** — inventing one would be authoring clinical copy. So a `stopped` drug
could only appear *unmarked*, and an unmarked stopped drug in a list headed "İlaçlarınız"
reads as current. It is **dropped from the patient's card rather than worded**; the
clinician note still carries it, with its state, where a reconciliation vocabulary exists.
A test asserts the stopped drug's name is nowhere in the summary and the current one is.

### The card table is the placement, not a description of it

`SUMMARY_CARD_SECTIONS` is inverted once into `_CARD_OF_SECTION` and the builder reads a
line's card **off the fact's own section**. It never names a card. A table that only
documented where a line goes could disagree with the code that puts it there, and every
other test would still pass — a line under the wrong heading is still a line. The first
draft of this module checked the two agreed and raised on a mismatch; deriving is stronger
and left the check with no reachable branch, which is how the defect was noticed.

The fact↔value pairing is positional (the composer files one fact per item), so `_paired`
asserts the lengths match and raises rather than guessing: a line paired with the wrong
fact carries the wrong person's marker.

## 4. A RED note has no summary — and no key to word one

Invariant 21 makes RED three axes: route × register × location, with the script
pre-positioned on the device and triggered over the data channel. **A card set is none of
those three axes**, and a RED sentence whose register is decided by page layout is exactly
the default the invariant forbids. So `SUMMARY_TRIAGE_LEVELS` is `(GREEN, YELLOW)`, there
is no `patient_summary.triage_message.red` key at all, and `build_patient_summary` raises
`SummaryRefused` on a RED note rather than rendering one without a message. The RED patient
still gets the RED script — over the channel that has a register.

**Flagged rather than settled**: this is a product decision taken inside an engineering
issue, and the clinical owner may want a RED patient to keep a card set. Reversing it means
adding the third key and deleting the raise, both visible in one diff.
