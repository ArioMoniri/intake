## 1. Owner decision

> owner chose pgsty/minio (chat, 2026-09-26)

The repo owner made this decision in chat on 2026-09-26. The instruction was to
use the maintained community fork `pgsty/minio`, pinned by sha256 digest. It
answers the question INT-346 §4 raised: which image replaces the withdrawn
upstream MinIO server image (and its `mc` client image) for dev and CI.

The same image carries the `mc` client (§3), so the backup toolbox moves onto
it too. The tree therefore has one digest and one licence record, not two. No
second image (`pgsty/mc`) was introduced.

## 3. What the image is: read from its config blob and layers

The config blob of each platform manifest was fetched from the registry.

- `ENTRYPOINT ["/usr/bin/docker-entrypoint.sh"]`, `CMD ["minio"]`,
  `VOLUME /data`, `EXPOSE 9000`. The base is ubi9-micro. This is the shape the
  upstream image had, so `command: server /data …` still becomes
  `minio server /data …`.
- The layers copy `/usr/bin/minio`, `/usr/bin/mcli`, the symlink
  `/usr/bin/mc -> mcli`, `/licenses/LICENSE` and `/licenses/CREDITS`. So both
  `mc ready local` (every healthcheck) and the backup toolbox's piped
  `mc …` commands have their binary.
- Labels: `maintainer=pgsty <https://github.com/pgsty/minio>`,
  `org.opencontainers.image.version=RELEASE.2026-08-04T00-00-00Z`,
  `org.opencontainers.image.revision=d88f46ccee345a9c2fabe2d221d9a9e56bc11aec`.
- The source at that revision still has the `console-address` flag
  (`cmd/server-main.go`) that the dev tier passes. The `mc` fork it bundles
  (`pgsty/mc`) has `cmd/ready-main.go`.

**Why the digest is not in `host`.** The first green attempt put the full
reference in `host`. That turned
`tests/admin/test_admin_audit.py::TestChainHeadUnreachable::test_no_admin_response_carries_a_chain_hash`
red: the console serves `host` from `GET /admin/models`, and no admin response
may carry a 64-hex string, because the audit chain head is one. That guard is a
security invariant and was not touched. The digest moved to the typed `image`
field instead, and the admin view never projects it. The new test
`test_the_served_host_names_the_release_but_never_carries_the_digest` holds
that line.

**Why the test is not `tests/infra/test_staging_compose.py`.** The issue names
that file, but it belongs to INT-345's open PR #549, and creating it here would
be an add/add conflict. That PR's `infra/staging/compose.yaml` runs no object
store. The new test scans every compose file under `infra/`, including
`infra/staging/compose.yaml` once it lands, so a staging object store would
fall under the same pin without a code change.

## 6. The tests (`tests/infra/test_object_store_image.py`, 16 tests)

- **Schema:** a digest-pinned image with a verified licence loads. A tag with
  no digest, a digest with no tag, a short digest, and an image pin with no
  dated licence verification are each refused.
- **Source of truth:** the `minio` row's `image` matches
  `pgsty/minio:RELEASE.<ts>@sha256:<64 hex>`. The row records `AGPL-3.0-only`,
  a dated verification, a raw blob URL at a 40-hex revision, the blob hash, and
  the owner decision. `host` names the release but carries no 64-hex string.
  The row stays `phi_path`, self-hostable and self-hosted now.
- **Withdrawn images:** no tracked file references the withdrawn upstream
  server or client image, on Docker Hub or quay.io. `docs/evidence/` is
  exempt, because it holds dated history. The guard assembles the forbidden
  names from parts, so it never spells what it forbids, and a self-test proves
  it matches the old shapes but not source URLs such as `github.com/<org>/<repo>`.
- **Agreement:** the compose scan finds exactly the four object-store services,
  and each one runs the approved reference byte for byte. The `mc` toolbox
  runs the same image through `/bin/sh`. Every textual image reference to the
  fork anywhere in the tree (compose, registry, served fixture) equals the
  approved one.
