# INT-592 — the iOS build carries a truthful NSHealthUpdateUsageDescription (ITMS-90683)

GitHub #1000 · Sec-Row: `mobile` · branch `int-592-health-purpose-string` from main `f96e5971`,
with main `4bb5ecae` (INT-585) merged in before the PR.
P0: blocks TestFlight build 7.

## 1. The defect

Apple's processing rejected TestFlight build 6 (0.1.0 (6), EAS `6113647d`, main `f96e5971`) with
ITMS-90683: the bundle's Info.plist has no `NSHealthUpdateUsageDescription`. The HealthKit library
(`@kingstinct/react-native-healthkit` 14.1.0) links the write APIs, so Apple requires the key even
though this app never asks to write. INT-420 had set the plugin option to `false`. The plugin
skips the key when it sees `false`, so the base Info.plist carried no key at all. Builds 3–5 passed
only because the owner's local app.json carried a string.

Acceptance (issues.yaml, from the issue):

- "the HealthKit plugin option NSHealthUpdateUsageDescription is a truthful, B1, siz-register
  Turkish string saying the app does not write to Apple Health; tr is the source and the string is
  localised through expo.locales (app-tr.json / app-en.json) like the other iOS purpose strings"
- "the string never claims a capability the app lacks: the connector requests read types only, and
  the share and update strings agree with it"
- "apps/mobile/e2e/brand.spec.ts requires a non-empty truthful string; near misses: false, an empty
  string and a string that claims writing all fail"
- "PolicyGuard and the claims scan are clean for the new string; the store-label inventory
  classifies the declared key; legal-reviewer reads the string"

## 2. What the app actually does with HealthKit

`apps/mobile/src/lib/health/healthKitConnector.ts` calls `requestAuthorization({ toRead: [...] })`
with exactly three types:

- `HKQuantityTypeIdentifierStepCount`
- `HKQuantityTypeIdentifierRestingHeartRate`
- `HKCategoryTypeIdentifierSleepAnalysis`

It has no `toShare` and calls no `save*` or `delete*` API. iOS shows the update string only when an
app asks for a write type, so no patient sees it. It is still the text App Review reads, and it has
to be true.

## 3. What changed

| file | change |
|---|---|
| `apps/mobile/app.json` | The HealthKit plugin's `NSHealthUpdateUsageDescription` changes from `false` to the Turkish string below. This is the base Info.plist that ITMS-90683 reads. After the legal review (§8), its `NSHealthShareUsageDescription` is the reviewer's variant A. |
| `apps/mobile/src/locales/app-tr.json` | Gains `NSHealthShareUsageDescription` and `NSHealthUpdateUsageDescription`. tr is the source; the plugin options equal it. |

| `packages/intake_platform/src/intake_platform/store/facts.py` | `PERMISSION_CLASSIFICATION` gains `NSHealthUpdateUsageDescription`, with no flow ("writes nothing … no personal data moves"). Declaring the key without a row fails the store-label drift gate. |

The strings as they ship, after the legal review (§8):

| key | tr (source) | en |
|---|---|---|
| `NSHealthUpdateUsageDescription` (new) | Önvizit Sağlık uygulamasına hiçbir veri yazmaz ve oradaki verilerinizi değiştirmez. Yalnızca okuma izni ister. | Önvizit never writes any data to the Health app and does not change your data there. It asks only for permission to read. |
| `NSHealthShareUsageDescription` (rewritten: variant A) | Önvizit adım, dinlenme nabzı ve uyku verilerinizi yalnızca okur. Bu veriler bu telefonda gösterilir. Notunuza ancak siz eklerseniz girer; notunuzu gönderirseniz onunla birlikte gider. | Önvizit only reads your step, resting heart rate and sleep data. It shows them on this phone. They enter your note only if you add them, and they go with the note if you send it. |

"Sağlık" is the name of Apple Health on a Turkish iPhone. Both strings use the siz register
("verilerinizi", "notunuza"), and every sentence is inside the 15-word B1 bound: 10 and 4 words
in the update string; 9, 5 and 10 in the share string. Neither claims more than the connector
does: it requests read types only, so iOS lets it write nothing.

## 4. Tests

| file | what it proves |
|---|---|
| `apps/mobile/e2e/brand.spec.ts` | **The oracle.** A string passes only if it carries the denial (`yazmaz` / `never writes`) and, once the negated verbs are taken out, no write verb is left. **Near misses that fail:** `false` (INT-420's value), `""`, whitespace, the library's default "wants to update your health data", "… Sağlık uygulamasına yazar.", a string that never mentions writing, and a string that denies one write but claims another (`kaydeder` / `saves`). One case must pass: a word that only contains a stem (`bekletmez` holds `ekle`). **The config:** the plugin option is a non-empty string that starts with `Önvizit;` and denies writing; the plugin strings equal app-tr.json's; both health strings are localised and the English update string also denies writing. **Code truth:** the connector's `toRead` is exactly the three types, and both share strings name those three kinds; the connector has no `toShare`, `.save*` or `.delete*`. |
| `tests/legal/test_ios_purpose_strings.py` | Both health strings are in the base Info.plist and equal tr. Every `NS*UsageDescription` exists in both catalogues and is translated. PolicyGuard (tr, `residency_tr`, siz) and the B1 bound run over every purpose string. The new key is declared and classified with no flow. **Near miss:** `false` declares no key (what Apple saw). |
| `tests/legal/test_store_labels.py` (unchanged) | The drift gate: every declared capability has an inventory row. It goes red without the facts.py row (mutation 3). |

**PolicyGuard and B1.** At first the pre-existing share string, one 19-word sentence, was recorded
as a finding rather than rewritten: both the length check and PolicyGuard's length arm (`jargon`)
flag it, and the i18n gate records `welcome.body` the same way. The legal review then replaced it
(§8), so both findings sets are now empty. They may only shrink, so any purpose-string finding is
now new and fails.

## 8. Legal review (30 Oct 2026): approved, with two copy changes

The reviewer approved #1001. The changes below were recommended now, because Info.plist text is
fixed per build. They are applied with the reviewer's exact text:

1. **`NSHealthShareUsageDescription` → variant A**, which is for a build that carries INT-587.
   Build 7 does: a Health line the patient adds to the note now travels with a sent note, so the
   INT-208 wording ("yalnızca bu cihazda görüntülemek …") stopped being the whole truth. The same
   text is in app.json's plugin config and in app-tr.json / app-en.json (strings in §3). This
   clears the recorded length finding, so both findings sets shrink to empty.
2. **`NSHealthUpdateUsageDescription` (tr):** the semicolon after "Önvizit" is dropped. The share
   string has none either, and brand.spec.ts now requires `Önvizit ` and refuses `Önvizit;` on
   both.

Tests first. `brand.spec.ts`:
- The opening-name checks now require no semicolon.
- The share-word check names "dinlenme nabzı" / "resting heart rate".
- A new test pins where an added reading goes: into the note only if the patient adds it, and
  with the note when it is sent.
- **Near miss:** the INT-208 "only shown on this device" wording fails.
