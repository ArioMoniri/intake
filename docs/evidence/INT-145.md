### The shape of the risk, and why the design follows from it

files/10 §3 calls the crash reporter **"the leak nobody mentioned and the one
likeliest to actually happen"**. Three limbs leak by default and each one is a
different failure:

- **stack frames capture local variables** — the `pcm` case §3 names, and on
  the client the same class is a local holding a transcript or an utterance;
- **breadcrumbs capture screen text** — every navigation and UI breadcrumb an
  SDK adds automatically, on screens that render symptoms;
- **a network breadcrumb captures a URL** — with its query string, which on a
  records endpoint is a document title.

So the scrubber is **deny-by-default**, not a regex blocklist. A blocklist
redacts the identifiers somebody thought of and ships everything nobody thought
of; it also cannot help with a Turkish free-text sentence, which matches no
pattern at all. `buildCrashReport` therefore takes the crash event as
`unknown`, reads a **closed, enumerated set of 17 keys** out of it, validates
each against that key's own shape, and assembles a fresh object. A field that
is not enumerated has no code path to the wire.

## The adversarial suite, and the proof it can fail

`apps/mobile/src/lib/telemetry/scrub.test.ts` plants four identifier classes:

| planted | value | why this one |
|---|---|---|
| Turkish symptom sentence | `Üç gündür göğsümde baskı ve nefes darlığı var.` | matches no redaction pattern in any language — the case a blocklist cannot serve |
| TR mobile number | `05321234567` | the form `intake_platform.redaction._TR_MOBILE` matches server-side |
| TC Kimlik (checksum-valid) | `10000000146` | the same synthetic fixture `tests/observability/test_error_scrub.py` uses |
| document title | `Ayşe Yılmaz kan tahlili 2026-03-12.pdf` | a patient name plus a date, exactly what a records URL carries |

Each is planted into **every limb a real crash event has** — the exception
message and `exception.values[].value`; a frame's `vars`, `context_line`,
`pre_context` and `post_context`; a frame's own `module` and `function`; three
breadcrumbs (`message`, `data`, and a network breadcrumb's full `url` with
query string); `tags` on both allow-listed and non-allow-listed keys; `extra`;
`contexts`; `user`; `request` (url, data, headers, cookie); and an
`attachments` array. The assertions run over `JSON.stringify(report)` **and**
over `buildEnvelopeBody(...)` — the actual bytes the transport is handed —
including percent-encoded forms, plus a blanket assertion that **no character
above ASCII 126 appears anywhere in the body**, since every allow-listed value
is an id, a code or a number.

A thirteenth test bounds the work itself: a structurally valid route template
800 characters long is rejected on length **before** any regex runs. The shapes
have nested quantifiers, and a crash reporter that can be made to spin on a long
string is a denial of service triggered by the very condition it exists to
report.

**The near-miss control.** Six legitimate values must survive: `session_id_hash
= 0f1e…e1f0`, `protocol_hash` (64 hex), `prompt_version = v3`, `screen_id =
visit_intake`, `app_version = 0.1.0`, `tenant_id = acibadem-maslak`, plus the
exception type `DialogueStreamError`, one frame
`src/lib/dialogue/stream.ts:openStream:182:11`, and two breadcrumbs. Without
them a scrubber returning `{}` would pass every leak assertion.

Three mutations were applied and reverted to prove the suite bites:

| mutation | result |
|---|---|
| read the breadcrumb `message` (`readString(candidate, "message", /^.{1,200}$/su)`) | vitest **3 failed** — `planted value escaped into the report`, `…into the envelope`, and the breadcrumb equality; pytest **2 failed** — `read set changed. Added keys: ['message']` and `never_reads_message` |
| loosen two tag shapes (`device_model: /^.{1,40}$/`, `session_id_hash: /^[A-Za-z0-9]{1,64}$/`) | vitest **2 failed** — `expected '05321234567' to be undefined`, `expected '10000000146' to be undefined` |
| vacuous scrubber (`breadcrumbs: []`, `tags: {}`) | vitest **3 failed** — the near-miss control: `expected undefined to be '0f1e2d3c4b5a69788796a5b4c3d2e1f0'`, `'eas-1841'`, `'ios'` |

## The allow-list, exactly

**Keys read out of the untrusted crash event (17).** Recorded in
`tests/mobile/test_crash_scrub.py::EXPECTED_READ_KEYS` and held against the
source, so widening the reader is a visible, reviewable change:

```
errorCode  exception  breadcrumbs  tags  timestampMs
values  type  stacktrace  frames
module  function  lineno  colno
category  event  route  status
```

**Never read** (asserted one test per limb): `message`, `value`, `vars`,
`extra`, `contexts`, `user`, `request`, `url`, `data` — and by construction
`context_line`, `pre_context`, `post_context`, `attachments`, `sources`.

**Tag keys (13), split by who may supply each one.** Identity keys are set once
when the client is constructed, from the app's own build metadata; event keys
are the only ones a crash event may set. That split is the fix for the subtle
hole: `05321234567` is a well-formed string, so an allow-listed *key* is not
enough. Every key carries **its own shape**, and `TAG_SHAPES`'s key set is held
equal to the two lists.

| key | supplied by | shape |
|---|---|---|
| `app_version` | identity | `^\d{1,4}\.\d{1,4}\.\d{1,4}(-[A-Za-z0-9.]{1,32})?$` |
| `build_id` | identity | `^[A-Za-z][A-Za-z0-9._-]{0,63}$` |
| `sbom_digest` | identity | `^sha256:[0-9a-f]{64}$` |
| `environment` | identity | `^(dev\|staging\|prod)$` |
| `release_channel` | identity | `^[a-z][a-z0-9-]{0,31}$` |
| `platform` | identity | `^(ios\|android\|web)$` |
| `os_version` | identity | `^\d{1,3}(\.\d{1,4}){0,2}$` |
| `device_model` | identity | `^[A-Za-z][A-Za-z0-9,._-]{0,39}$` |
| `tenant_id` | identity | `^[a-z][a-z0-9-]{0,63}$` |
| `session_id_hash` | crash event | `^[0-9a-f]{16,64}$` |
| `protocol_hash` | crash event | `^[0-9a-f]{64}$` |
| `prompt_version` | crash event | `^v\d{1,4}(\.\d{1,4}){0,2}$` |
| `screen_id` | crash event | `^[a-z][a-z0-9_]{1,39}$` |

The four event keys mirror `intake_platform.otel.ALLOWED_LOG_ATTRIBUTES`
(`session_id_hash`, `tenant_id`, `protocol_hash`, `prompt_version`), with
`tenant_id` moved to the identity side — a tenant is known at construction, and
leaving it event-settable would have accepted a bare digit run under its shape.
The nine identity keys are files/10 §6's *"Mobile and web report app_version,
build_id, sbom_digest in telemetry"* plus the device/OS matrix the same
paragraph asks for.

**Other closed sets.** Breadcrumb categories: `lifecycle`, `navigation`,
`network`, `permission` — an entry outside the set is dropped whole. Breadcrumb
event codes: `^[a-z][a-z0-9_]{1,39}$`. A network breadcrumb carries a **route
template**, `^(/([a-z][a-z0-9-]*|\{Param\}))+/?$`, never a URL: `/records/
10000000146` cannot match, and nor can anything with a host, a query or a
fragment. Frame `module` must contain a letter, which is what stops a bare
digit run passing as a module path. Error codes: `^[a-z][a-z0-9_]{2,63}$`,
falling back to the literal `unclassified_client_error` — never the text.

**The exception message is not sent.** `exception.values[].value` on the wire
carries the error **code**. files/10 §3's `SafeError` boundary says an
exception becomes `{error_code, correlation_id}` before any reporter sees it;
this module assumes that boundary may have been missed and never reads the
message at all. The `installCrashHandler` call site refuses it one layer
earlier still, passing only `error.name`.

**The fingerprint is derived from allow-listed fields only** — error code,
exception type, frame coordinates — and a test proves it: changing only fields
the builder never reads leaves the fingerprint identical. A fingerprint over
the message would be a hash of patient text, and a hash of a ten-digit phone
number is a lookup table, not a de-identification.

## Session replay: unreachable, not unconfigured

No `@sentry/react-native`, no `sentry-expo`, no vendor SDK at all. The envelope
is built by hand (`envelope.ts`), and the reasoning is the control rather than
a preference: **an SDK's value is precisely the behaviour we must not have** —
automatic navigation and network breadcrumbs, `include_local_variables`,
screenshot capture, session replay. Configuring those off leaves the code in
the bundle and one regression away from live. INT-145 asks for replay to be
unreachable; the only way to be sure is for the capture surfaces not to exist.

Proved by `tests/mobile/test_crash_scrub.py`: `replay`, `screenshot`,
`attachment`, `captureScreen`, `viewHierarchy` and `profilesSampleRate` appear
in **no code** in `apps/mobile/src/lib/telemetry/` (comments are stripped
before the scan, so the modules can explain *why* they are absent), and the
envelope carries exactly one item whose type is `event` — asserted by parsing
the body's three lines in `client.test.ts`.

## Inert when unconfigured, and nothing on disk

`app.json` ships `extra.glitchtipDsn: ""` — the same inert-default shape as the
existing `certificatePins: []`. With no DSN the client reports
`{ active: false, reason: "not_configured" }`, `captureCrash` returns `"inert"`
and the transport is never called. A malformed DSN reports `"malformed_dsn"`,
not a fallback host: `test_there_is_no_default_endpoint_anywhere_in_the_client`
asserts no `http://` or `https://` literal exists in any shipped telemetry
module. A DSN carrying a secret half is **refused rather than trimmed** —
Sentry retired the secret in 2016, so a DSN with one is a paste from elsewhere,
and accepting it would put a credential in `app.json`.

**No disk, anywhere.** There is no retry queue and no offline spool: an unsent
crash is dropped and the outcome returned. `test_no_crash_event_can_reach_the_
disk` asserts `expo-file-system`, `expo-secure-store`, `AsyncStorage`,
`localStorage`, `sessionStorage` and `node:fs` are unreachable from these
modules. The reason is invariant 3's posture rather than a size concern: a
spool is a file of crash events on a patient's phone, and it is only
non-sensitive because today's scrubber made it so — a property of the scrubber,
not of a file that would outlive it. A throwing transport is swallowed without
logging the error object, because the premise of this module is that error
objects are untrusted.

## Metrics: all four already catalogued, all four stay `planned`

Nothing was added to `observability/metrics_catalog.yaml` and nothing was
promoted. The four ids this client emits already exist there, `owner: client`:
`client.crash_free_sessions` (target `>= 99.5 %`), `client.cold_start_p95_ms`,
`client.anr_rate`, and `web.core_web_vitals` (labels `[vital]`).

There is precedent both ways in the repo for what `status` should say, and the
honest one is `planned`. `tests/observability/test_metrics_catalog.py` decides
"live" by two mechanisms, **both Python-only**: an AST scan for
`prometheus_client` family constructors under `packages/` and `services/`, and
a real GET of a served `/metrics`. A React Native client registers no
Prometheus family and serves no `/metrics` — it hands readings to an injected
sink. Marking these `live` would be a claim about an exposition that does not
exist, and `dishonest_live` would fail. This is the same reasoning
`apps/mobile/src/lib/livekit/metrics.ts` recorded for the three `net.*` series
(INT-103), and the opposite of promoting a series because the client-side half
landed.

`client.offline_sync_success` is catalogued but **not emitted**: there is no
offline-draft sync feature to measure yet, and a fabricated ratio would be
worse than an absent one.

Invariant 6 is enforced by type: a `ClientMetricSample` is
`{ metricId, value, vital? }`, where `vital` is one of `CLS FCP INP LCP TTFB`.
No free-text field, no attribute bag. Invariant 20's posture holds throughout —
crash-free share before the first session is `null`, not `1.0`; p95 with no
readings is `null`, not `0`; a cold-start reading that is not finite and
non-negative is dropped rather than recorded. p95 is nearest-rank, matching
`median` in `lib/livekit/quality.ts`, so no percentile reports a duration no
launch ever took.

**`client.anr_rate` is named precisely.** A platform ANR is an Android system
determination this app cannot observe from JavaScript. What is measured is a
**main-thread stall** past a watchdog threshold — the closest signal a JS
runtime has, and the one that moves for the same reasons. The module says so;
this paragraph is the record so the series is never read as the platform's own
figure.

## Web RUM

`webVitals.ts` reads Core Web Vitals from the platform's own
`PerformanceObserver`: LCP, CLS, INP, FCP, TTFB, one observer per entry type,
`buffered: true`. No `web-vitals` package, for the same reason as the crash
SDK: the value a RUM library adds is **attribution** — the element, the URL,
the resource that caused the shift — and attribution is the part that carries
text off a clinical page. **Only a number is read off an entry**; `element`,
`url`, `id` and `sources` are never touched, asserted by a test that plants
them. An `event` entry contributes to INP only when the browser assigned it an
`interactionId`. Inert wherever `PerformanceObserver` is absent (every native
build), and an observer that throws on an unknown entry type is skipped rather
than allowed to break the page it is measuring.

The only web target in the repo today is this package's own web build
(`expo start --web`, `react-native-web`, `expo.web.output: "static"`);
`apps/clinician-web` and `apps/admin-web` do not exist yet (INT-150+,
INT-180+). When they land they import this module rather than growing a second
collector.

## Wiring

`apps/mobile/src/app/_layout.tsx` captures `APP_START_MS` at module evaluation
— the earliest clock this app has — and, once the faces resolve and the first
readable frame is about to render, installs the crash handler and records the
cold start. `createTelemetryRuntime` counts the launch as one session, so
crash-free share is live from the first frame.

`installCrashHandler` chains `ErrorUtils.setGlobalHandler`, always calling the
previous handler: swallowing a fatal would replace a red box the developer
needs with silence.

`recordPreviousLaunchCrashed()` exists and is not called by anything yet, and
that is deliberate rather than incomplete. The process that crashes cannot
report its own crash, so the honest way to catch a hard native crash is for the
*next* launch to find the previous session unclosed — which requires a counter
on disk, which this module refuses to have. The seam is typed and tested; the
platform hook that could feed it (a native crash handler) lands with INT-146's
build work. Nothing fabricates the answer in the meantime.

## Deviations and honest scope

1. **The issue's `tests:` field names a Python path for TypeScript code.**
   `tests/mobile/test_crash_scrub.py` exists and is substantive, but it cannot
   execute the scrubber. It is a **source guard**, and it proves the one thing
   no vitest assertion can: that the set of keys read out of an untrusted crash
   event is closed and recorded. The behavioural proof is the colocated vitest
   suite. Both run in `make check`.
2. **The metric sink is the discarding one in the app today.** No service
   ingests client metrics — which is exactly why those four series are
   catalogued `planned`. The readings are computed on device and reachable
   through `runtime.state()`; the sink is the seam an ingest endpoint plugs
   into, and the PR that adds it promotes the catalogue entries. Building a
   fake ingest to make the wiring look finished would have been the dishonest
   move.
3. **`buildId` and `sbomDigest` are empty today.** files/10 §6 requires all
   three of `app_version`, `build_id`, `sbom_digest` in client telemetry.
   `app_version` comes from `expo.version`; the other two are EAS build outputs
   and land with INT-146. The mechanism is complete and **fails closed** — an
   empty value fails its shape and the tag is dropped, rather than a guess
   being reported. This is CLAUDE.md's "build the mechanism, wire the gate,
   make it fail closed, leave the content empty".
4. **No i18n keys were added, and no consent surface.** Crash and performance
   telemetry is invisible to the patient and carries no clinical data. Adding a
   toggle would have meant adding a purpose to
   `apps/mobile/src/lib/consent/purposes.ts`, which is a **view** of the
   server's 06 §2 closed registry and must never fork it. If KVKK-12 review
   concludes diagnostics needs its own purpose, that is a change to the server
   registry first, and a separate issue.
5. **`client.offline_sync_success` is not emitted** — no offline-draft sync
   feature exists to measure.
6. **`device/OS matrix`** is delivered as the `platform`, `os_version` and
   `device_model` tags on crash reports, not as a metric: files/08 §4 defines
   no dotted id for it, and inventing one would break the frozen
   `EXPECTED_SPEC_ID_COUNT = 135` pin.
