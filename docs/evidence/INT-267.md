## The defect, and why Unknown is the harm

`packages/protocols/src/protocols/triage/context.py` declared
`canonical_scalar(value: JsonValue) -> bool | Decimal | str | None` and handled `bool`, then
`(int, float)` → `Decimal(str(value))`, then `str`, then fell through to `return None` — and None
reads Unknown. So a `Decimal` **input**, which is the function's own declared **output** type, read
Unknown: the identity case was the one that failed.

INT-083's extraction emits decimal and quantity slot values as exact `Decimal`
(`packages/intake_platform/src/intake_platform/llm/extraction.py`, `type SlotValue = bool | int |
str | Decimal`, whose comment records this handoff as an open integration defect rather than
papering over it with a float, because a float would breach CLAUDE.md invariant 22 and files/13 §9.5
"no floats anywhere … exact comparison, because floats are how two machines disagree about the same
session"). Every such value therefore reached the gates as Unknown: a threshold rule that cannot
decide, which is not a safe default merely because it is not FALSE.

## A second defect found on the way: a float **already** on the comparison path

`SlotAnswer.values` was typed `tuple[JsonValue, ...]`, and `JsonValue` is
`str | int | float | bool | None` (+ one level of list/dict). Pydantic's smart union has no
`Decimal` member to match, so it **coerced an incoming `Decimal` into a `float`**:

```
SlotAnswer(state=ASKED_PRESENT, values=(Decimal('38.50'),)).values  ->  (38.5,)   # <class 'float'>
```

That is exactly the unguarded representation crossing CLAUDE.md invariant 22 names, and it has two
consequences that matter here:

1. **A float sat on the comparison path** in every triage evaluation whose value arrived as a
   `Decimal` through this carrier — the thing files/13 §9.5 forbids. It also silently discarded the
   authored scale (`38.50` → `38.5`) and would round any magnitude a float cannot represent exactly.
2. **It masked the issue's own defect in the pure-context path.** Because the carrier laundered the
   `Decimal` into a `float` before `canonical_scalar` ever saw it, a golden built only from
   `SlotAnswer` would have passed today for the wrong reason. The defect stayed visible only where
   nothing launders the value: a direct `canonical_scalar` call, and `IntakeEngine._lookup`, which
   reads an unvalidated `dict[str, JsonValue]`. That is why the goldens carry an explicit
   `assert isinstance(context.answers[...].values[0], Decimal)` — a golden that can silently degrade
   into a float test proves nothing.

Fixed inside this issue's own file: `context.py` now declares
`type SlotValue = Decimal | JsonValue` and `SlotAnswer.values` is `tuple[SlotValue, ...]`.
`tests/safety/test_triage_when.py::TestDecimalCarrier::test_admitting_a_decimal_reroutes_no_other_carrier`
pins that widening the union re-routes nothing else: `38` stays `int`, `38.5` stays `float`,
`"38.5"` stays `str`, `True` stays `bool`, `None` stays `None`.

## The scale decision — decided and asserted, not fallen out of

**Decision: the incoming `Decimal` is returned unchanged — the same object — so `Decimal("38.50")`
stays `Decimal("38.50")`. No re-conversion through `str`, no `quantize`, no `normalize`.**

Reasoning:

- files/13 §9.5 types a decimal slot as "`Decimal` with **declared scale** and exact comparison". The
  scale is a property of the slot that was authored and of the value the patient's carrier produced;
  it is not `canonical_scalar`'s to choose. Normalising would be this function overwriting an
  authored fact.
- **It cannot change a verdict, so the choice is free of clinical risk.**
  `packages/protocols/src/protocols/triage/expr.py` compares Decimals with `==`, `!=`, `<`, `<=`,
  `>`, `>=` — Python `Decimal` comparison is by numeric value and ignores trailing zeros
  (`Decimal("38.50") == Decimal("38.5")` is True; `Decimal("38.50") >= Decimal("38.5")` is True;
  `> ` is False). There is no textual comparison anywhere in the grammar: `_equal` routes strings to
  strings and Decimals to Decimals, and a cross-type comparison is Unknown. So "accept unchanged" is
  coherent with how `expr.py` compares, which is what the acceptance asked to be confirmed.
- **It does change every textual render, and there for the better.** The rule's `evidence` line, the
  clinician note and the invariant-22 Turkish orthography expansion all read the carried value's own
  string form. Normalising to `38.5` would make the evidence report a value the patient's carrier
  never produced. Asserted by
  `test_the_evidence_renders_the_decimal_at_its_authored_scale`: `sentetik.olcum=38.50`.
- Asserted directly, not inferred: `canonical_scalar(Decimal("38.5")) is value` (identity, so no
  re-conversion of any kind can be present), `str(carried) == "38.50"`, and
  `carried.as_tuple().exponent == -2`.

**One guard added with the acceptance.** Accepting a `Decimal` newly admits a non-finite one, and an
ordered comparison against a NaN raises `InvalidOperation` — which before this change could not
happen from a `Decimal`, because a `Decimal` read Unknown. A non-finite number is a data defect, not
a magnitude, so `canonical_scalar` reads NaN and ±Infinity as **Unknown** (review), never FALSE
(false reassurance) and never an exception on the triage path. The same guard closes a pre-existing
hole on the float side: `Decimal(str(float("nan")))` was `Decimal("NaN")` and went straight to
`_compare`, where an ordered comparison would have raised. Note that a *signalling* NaN cannot reach
the carrier at all — pydantic's own `Decimal` validation refuses `Decimal("sNaN")` — so it is
reachable only through the unvalidated engine dict, which is precisely why the guard belongs in the
function rather than in the schema.

## What the golden's near-miss proves

`tests/safety/test_triage_engine.py::TestDecimalThresholdGolden`, over a synthetic RED rule
`rf.sentetik_esik` whose `when` is `sentetik.olcum >= 38.5`:

| case | carried value | rule truth | verdict |
|---|---|---|---|
| over / at the threshold | `Decimal("38.5")` | `TRUE` | RED · KIRMIZI_K2 · ALERT · REMOTE, action is the rule's own frozen `remote` object |
| **near-miss negative control** | `Decimal("38.4")` | **`FALSE`** | GREEN, no rules fired, no action |
| scale | `Decimal("38.50")` | `TRUE` | evidence reads `sentetik.olcum=38.50` |

The near-miss is asserted on `rule_truth(...) is Truth.FALSE`, **not only** on the GREEN verdict:
GREEN is also what Unknown produces, so a verdict-only assertion would pass in exactly the broken
state this issue fixes. That is the negative control the CLAUDE.md clinical content rules require —
the gate must *decide* against firing, not fail to decide.

**The threshold, the slot names and the Turkish strings are SYNTHETIC test values invented for this
mechanism test and carry no clinical meaning whatsoever.** They are marked as such the way the
repository already marks them: the `sentetik.` slot prefix (files/04 §7; the same convention as
`tests/protocols/goldens/valid/*.yaml` and `tests/safety/synthetic_triage.py`), a `rf.sentetik_*`
rule id, and a SENTETİK TEST VERİSİ header on the section. **No clinical threshold is invented here**
— HUMAN_BLOCKERS Rule 1. No pack YAML, no life-threat rule and no rule content in
`files/protocols/` or `packages/protocols/base/` was touched: the INT-059 corpus itself records that
"no numeric-threshold comparison exists in merged content yet — those classes are covered at engine
level by the INT-080 synthetic suite and join this corpus when such rules land", and this golden is
written in exactly that place, in that suite's own idiom.

## End to end across all three carriers

`tests/safety/test_triage_engine.py::TestDecimalCarrierThroughIntakeEngine` drives the real
`IntakeEngine.apply_extraction`
(`services/voice-runtime/src/intake_voice_runtime/clinical_agent/fsm.py`, read but **not** edited)
over a three-step synthetic resolved protocol, then projects the engine's own answer state onto the
`TriageContext` the rules evaluate over. For `over = 39` and `under = 38` carried as `Decimal`,
`int` and `float`:

- the triage verdict is the same for all three carriers (RED over, GREEN under), so the extraction
  path (INT-083) and the typed path (INT-096) cannot disagree;
- the engine's **own** protocol gate agrees: the third step, gated on `sentetik.olcum >= 38.5`, is
  offered on the frontier for `over` and absent for `under`, in all three carriers. This is the
  clause that was red for the `Decimal` carrier before the fix (`assert 'sentetik.ek_soru' in []`) —
  `IntakeEngine._lookup` calls the same `canonical_scalar`, so a value invisible to a red-flag rule
  was invisible to the protocol gate too, and an Unknown gate never offers its step;
- `engine.value_of("sentetik.olcum")` is still a `Decimal` at its authored scale, and so is the
  projected `SlotAnswer` value.

## No float on the comparison path

`test_no_float_reaches_the_comparison`: for each of `Decimal("39")`, `39`, `39.0`, the scalar that
reaches `expr.py` is a `Decimal` and is not a `float` — the float carrier converts through its string
form, and the `Decimal` carrier is not converted at all. The one float that *was* on the path (the
`SlotAnswer` coercion above) is removed by this change; `_evidence` no longer needs `json.dumps` for
a Decimal (which cannot serialise one at all, and whose only workaround would have been a float
detour), and renders it from its own exact form instead.
