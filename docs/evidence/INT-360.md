# INT-360 — The app follows the device's orientation, and every screen lays out in landscape

**Epic:** E08-mobile · **Phase:** P1 · **Sec-Row:** mobile · **GitHub:** #586 ·
**Legal:** 5378, EN 301 549 · **Depends on:** INT-226 (merged)
**Criterion:** WCAG 2.2 SC 1.3.4 Orientation (AA), with SC 1.4.10 Reflow alongside

## Acceptance (verbatim)
- "apps/mobile/app.json no longer locks orientation for the whole app; any screen that keeps a lock names the SC 1.3.4 essential exception in the conformance report"
- "every screen lays out in landscape at the largest text size with no clipped control and no horizontal scroll of body text"

## Problem
The INT-226 report recorded SC 1.3.4 as **Does Not Support**. `apps/mobile/app.json`
set `"orientation": "portrait"`, which writes a portrait-only
`UISupportedInterfaceOrientations` on iOS and `android:screenOrientation="portrait"`
on Android. Every screen was locked, and portrait is not essential to an intake
form. Removing the lock needed a landscape layout pass, because no layout had
ever been exercised in landscape.

The pass found a second lock that app.json did not hold. It also found three
landscape defects, one of which affects portrait as well.

1. **A Modal is a portrait lock on an iPhone.** React Native presents a
   `<Modal>` portrait-only on a phone unless it names `supportedOrientations`.
   An empty list is `UIInterfaceOrientationMaskPortrait` in both
   `RCTModalHostView.m` and the Fabric `RCTModalHostViewComponentView.mm`, read
   in `node_modules/react-native` 0.86.3. The dialogue's section sheet is such a
   Modal. Opening it in landscape would have turned the screen under the
   patient.
2. **The dialogue composer sat behind the iOS keyboard.** `DialogueIntake`
   pinned its bottom stack (section strip, turn CTAs, composer) with
   `position: "absolute", bottom: 0` directly inside a `KeyboardAvoidingView`
   with `behavior="padding"`. That view lifts its content with `paddingBottom`,
   and Yoga positions an absolutely positioned child against the parent's
   border box, so the padding is ignored (`yoga/algorithm/AbsoluteLayout.cpp`).
   The offset also left out the stack header's height. This holds in both
   orientations. It is found by reading the code and has not been observed on
   hardware. In landscape, where the keyboard takes about half the window, it
   matters most.
3. **Sizes and chrome decided in portrait.**
   - `PrepGauge` bounded its arc by the window **width**, which in landscape is
     the long side. At the largest step the arc stayed 464 × 232 pt in an
     844 × 390 window.
   - `FloatingTabBar`, the section sheet and the kiosk's own chrome sit outside
     any `Screen`, so they get no left or right safe area. In landscape the
     notch and the rounded corners are at the sides.
   - The kiosk's warning and staff bar could not scroll, so in a short window
     the exit button was pushed off the bottom.
   - Six scrollers that hold a text field did nothing about the iOS keyboard.

## Change

### The lock (`apps/mobile/app.json`)
`"orientation": "default"`. `@expo/config-plugins` writes all four interface
orientations on iOS and `unspecified` on Android, which follows the device and
the user's own rotation lock. `app.config.ts` passes it through unchanged in
every EAS profile.

### Per-screen locks: none
No screen keeps a lock, so `expo-screen-orientation` is **not** added. The one
screen that might have claimed one, the records camera, uses the OS's own
capture screen (`expo-image-picker` `launchCameraAsync`). A photo's upright
travels in its EXIF tag (`lib/records/jpeg.ts`), so no screen's orientation is
essential. The exception register in the conformance source is empty, and the
report says so.

### New pure module (`src/lib/a11y/orientation.ts`)
- `ALL_ORIENTATIONS`: the four orientations app.json now declares, in React
  Native Modal's own terms. It is frozen at run time and typed as the mutable
  array the Modal prop is declared as.
- `shortSide(window)`: the bound a figure may grow to in either orientation.
  In portrait it equals the width, so no portrait layout moves.

### Screens and components (existing primitives only, no new design language)
| File | Change |
|---|---|
| `components/SectionPanel.tsx` | The sheet's `<Modal>` names `supportedOrientations={ALL_ORIENTATIONS}`. A Modal is its own window, so the sheet takes the left, right and bottom safe insets itself. |
| `components/DialogueIntake.tsx` | The avoiding view is offset by `useHeaderHeight()` (`expo-router/react-navigation`). The bottom stack is pinned inside a new frame `View` that ends at the keyboard's top edge. The stack is capped at that frame's measured height (`maxHeight: frameHeight`). The strip and the turn's CTAs sit in a `ScrollView` that gives height back and scrolls when capped, and the composer keeps its full height. |
| `components/GlassBar.tsx` | `flexShrink: 1` on the bar and its inner view, so a host that caps it can take height back. With no cap nothing changes. |
| `components/PrepGauge.tsx` | The arc is capped by `shortSide(window)`, which makes it 350 × 175 pt at the largest step in an 844 × 390 window. Portrait is unchanged. |
| `components/FloatingTabBar.tsx` | The rail's wrap pads by `max(insets.left/right, spacing.md)`. |
| `components/KioskGate.tsx` | The armed chrome (idle warning and staff bar) sits in a `SafeAreaView` with left, right and bottom edges, and scrolls (`flexGrow: 0, flexShrink: 1`) rather than push the exit off-screen. The PIN scroller sets `automaticallyAdjustKeyboardInsets`. |
| `(auth)/phone.tsx`, `(auth)/otp.tsx`, `visits/new.tsx`, `visits/[visitId]/issue-link.tsx`, `visits/[visitId]/intake.tsx` (typed steps) | Each scroller that holds a `TextInput` sets `automaticallyAdjustKeyboardInsets`. On iOS the content is inset by the keyboard and the focused field scrolls into view. Android already resizes the window (Expo's default `softwareKeyboardLayoutMode`). |

No patient-facing string was added or changed.

### The report (`docs/compliance/accessibility-conformance.yaml`, rendered)
- **SC 1.3.4** moves from **Does Not Support** to **Supports**. It cites eight
  tests: seven in `a11y.spec.ts` and one in `orientation.test.ts`. MC-04 stays
  cited as the manual pass that found the app-config lock, and its dated record
  is left as written. The row carries `essential_locks: []`.
- **The renderer** (`scripts/compliance/render_a11y_report.py`) validates the
  register: every entry needs a lock and a reason, only SC 1.3.4 may carry one,
  and SC 1.3.4 must carry it. The renderer also names the register in the row's
  remarks, as *"Essential exception: none. No screen keeps an orientation
  lock."*, or as each lock with its reason. This makes the report the place
  where a kept lock names its essential exception.
- **SC 1.4.10** stays **Not Evaluated** (DA-05 decides). It now cites the
  landscape scan, and its remarks no longer say reflow is exercised only in
  portrait.
- **DA-05** is renamed "Largest text, reflow and landscape" and now confirms
  SC 1.3.4. Its new steps (owner, on hardware) are:
  - walk every screen in landscape with both text settings, on a 6.1-inch phone
    and the smallest phone available, with a screenshot of each;
  - include the dialogue with the keyboard up, the section sheet and, once it
    can be armed, the kiosk chrome;
  - record any screen that stays portrait, any field the keyboard hides and
    anything under the notch.
- The reading note on INT-226's re-assessment now says 1.3.4 is Supports
  since INT-360.
- Counts: Supports 24 → 25, Does Not Support 2 → 1.

## Tests (TDD)

### `e2e/a11y.spec.ts`: new "SC 1.3.4" sections (16 tests)
**The lock scan** reads every script under `src` (tests excluded), `plugins/*.js`,
`app.json` and `app.config.ts`, with comments stripped. It finds:
- an **orientation setting**: the app config's `orientation`, a navigator's
  `orientation`/`screenOrientation`, or a manifest attribute set to a portrait
  or landscape value (a `type` alias that spells the values out is not a
  setting);
- the **orientation API**: `expo-screen-orientation`, statically or lazily
  imported, and `lockAsync` / `lockPlatformAsync`;
- a **native orientation key** (`UISupportedInterfaceOrientations`,
  `requestedOrientation`);
- a **portrait-only modal** (a `<Modal>` with no `supportedOrientations`) or a
  **restricted modal** (one that names anything but `ALL_ORIENTATIONS`).

The lock tests:
- app.json is `default`, and `resolveAppConfig` keeps it `default` for local,
  development, preview and production;
- the scan reads the config, the plugins and more than 50 `src/lib` scripts;
- every lock found is in the SC 1.3.4 `essential_locks` register with a
  reason, read by a small line reader;
- the register holds no stale entry;
- the register reader refuses an entry without a reason, and a row without a
  register;
- every Modal names `ALL_ORIENTATIONS`, imports it from `@/lib/a11y/orientation`
  and reads the side insets.

**Near-miss control:** each of these is caught:
- the pre-INT-360 app.json;
- `ScreenOrientation.lockAsync` (static and lazy);
- a Stack `orientation: "portrait_up"`;
- a plugin writing `android:screenOrientation` or
  `UISupportedInterfaceOrientations`;
- a silent Modal, and a Modal limited to `["portrait"]`.

These pass: the fixed app.json, a Modal with `ALL_ORIENTATIONS`, a commented
lock, the JPEG `orientation: number` parameter and a type alias. A planted lock
clears only once it is registered with a reason.

**The landscape layout scan** is held to 844 × 390 and 568 × 320. It flags:
- a fixed `height`/`maxHeight` over 64 pt (control-sized; the primer badge is 56);
- a `minHeight` over half the shortest landscape window (160 pt);
- any percentage height;
- `Dimensions.get` (stale after a rotation);
- a `useWindowDimensions()` size read without `shortSide`;
- a StyleSheet rule pinned `position: "absolute"` with `left: 0` and `right: 0`
  in a file that does not read `insets.left` and `insets.right`;
- any horizontal `ScrollView`/`FlatList`/`SectionList`.

The allow-list `LANDSCAPE_SAFE` can only shrink, and has three entries, each
with its reason:
- the sheet's `maxHeight: "78%"`: a cap over rows that scroll;
- `GlassBar`'s `floating` rule: every host renders it inside a `Screen` with
  left and right safe edges;
- `DialogueIntake`'s `bottomStack`: the same, plus the cap.

The scan has its own near-miss test for each shape, and a test pins the window
constants.

**Keyboard and chrome tests:**
- every `ScrollView` whose element holds a `TextInput` sets
  `automaticallyAdjustKeyboardInsets`. There are six, found by walking the tree.
  A `useRef<ScrollView>` type argument is not read as an element;
- a `TextInput` outside any scroller sits in a `KeyboardAvoidingView`;
- in the dialogue:
  - the avoiding view is offset by `headerHeight` from `useHeaderHeight()`;
  - the bottom stack is inside the one `View` whose `onLayout` sets the frame
    height;
  - the stack's style carries `maxHeight: frameHeight`;
  - a `ScrollView` sits between the `GlassBar` and the composer row;
- `GlassBar`'s `bar` and `inner` rules carry `flexShrink: 1`;
- the kiosk chrome is one `SafeAreaView` with edges `bottom, left, right`,
  holding a `ScrollView`, the idle warning and the staff bar.

### `src/lib/a11y/orientation.test.ts` (5 tests)
- `ALL_ORIENTATIONS` is the four orientations, uses only values the Modal
  accepts, and is frozen;
- `shortSide` returns the shorter side both ways round, for 390 × 844 and
  320 × 568;
- in portrait, `shortSide` is the width, so portrait is unchanged.

### `tests/legal/test_a11y_report.py` (4 tests)
- the 1.3.4 row carries the register as a list;
- an entry with no reason, or a blank one, is refused;
- only 1.3.4 may carry a register;
- the rendered 1.3.4 line names a registered lock and its reason, and says
  "No screen keeps an orientation lock" when the register is empty.

## Invariants
- **2:** no patient-facing text changed, so PolicyGuard's inputs are unchanged.
- **5:** no catalogue key was added. `make check-i18n` passes.
- **6:** nothing is logged. The new code is layout only.
- **8:** tests were only added. No threshold was lowered.
- **17:** no placeholder was used and nothing was postponed. Both allow-lists
  (`LANDSCAPE_SAFE` and `essential_locks`) hold a reason per entry and fail on
  a stale one, so they can only shrink.
- Expo only: no bare React Native change. `KeyboardAvoidingView`, `ScrollView`
  and `SafeAreaView` are existing primitives, and `useHeaderHeight` is
  re-exported by expo-router. No dependency was added: no
  `expo-screen-orientation`, because no screen needs a lock.
