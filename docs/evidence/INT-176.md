# Fix PR — principal-scoped keys + short in-flight TTL + capped storage

## Acceptance (verbatim from docs/backlog/issues.yaml)

- [x] "Redis key includes subject+tenant; test proves user B cannot replay or pre-claim user A's Idempotency-Key; in-flight marker gets a short TTL distinct from the 24h response TTL; stored bodies size-capped"

## Red run

Tests first, against the merged INT-012 middleware:

```
FAILED tests/platform/test_idempotency.py::test_user_b_cannot_replay_user_a_response
FAILED tests/platform/test_idempotency.py::test_user_b_cannot_preclaim_user_a_key
FAILED tests/platform/test_idempotency.py::test_tenants_are_isolated_like_users
FAILED tests/platform/test_idempotency.py::test_inflight_ttl_is_short_and_response_ttl_is_long

```

(user B literally received user A's stored response body — the #195 HIGH-1

## Green runs

- `tests/platform/test_idempotency.py` — 11 passed: the six original replay
  semantics plus principal scoping (replay + pre-claim + tenant isolation),
  the two-TTL contract (claim ≤300 s, record 24 h), and the oversize-marker
  409 with the handler still executing exactly once.
- 126 py tests green; `mypy --strict` clean; full `make check` on the PR.

## What changed

- `principal_fn(scope) -> (tenant, subject)` is a REQUIRED constructor
  argument — keys are `sha256(tenant ␟ subject ␟ method ␟ path ␟ key)`;
  there is deliberately no safe default.
- In-flight marker TTL 60 s (was: shared 24 h — a crash between claim and
  store poisoned the key for a day).
- Stored bodies base64 (non-UTF-8 responses round-trip; the old
  `decode("utf-8")` could throw after the response was already sent) and
  capped at 256 KiB — an oversize response stores a non-replayable marker
  and a duplicate gets an honest 409 while the handler still never re-runs.
