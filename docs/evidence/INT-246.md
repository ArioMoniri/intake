# INT-246 — the silent voice fallback becomes visible in dev

## The incident

The owner reported, repeatedly, that "the app still asks text questions, the
voice chat UI is not implemented". The voice UI was built, merged and running.
What had actually happened is that the SSH tunnel to the speech server died,
so `reachableAsrBaseUrl()` returned `null`, and `DialogueGate` fell through to
the typed steps **silently by design**. Hours went into a feature that was
already there.

Two things were missing, and neither of them is a change to what a patient
sees:

1. the probe threw away everything it knew. A bare `null` cannot say which
   bases were tried or how each one failed, so nothing downstream could say it
   either — not a banner, not a log, not a person.
2. there was no way to ask the question from the HOST, where the answer lives.
   "Is voice up?" required reading app logs on a phone.

## What was built

| | |
|---|---|
| `probeReachability` (`src/lib/dev/hosts.ts`) | the walk with its detail intact: every candidate in order, each one `timeout` / `refused` / `status <n>` / answered. `reachableBaseUrl` and `probeHealth` keep their exact signatures on top of it — no call site churned. |
| `probeAsrReachability` (`src/lib/voice.ts`) | the same for the ASR lane. `reachableAsrBaseUrl()` still returns `string \| null`. |
| `voiceDiagnostic` (`src/lib/dev/voiceDiagnostic.ts`) | the banner as a pure decision. Returns `null` unless `isDev`; also `null` while the probe is in flight and `null` when a lane answered. |
| `DevVoiceBanner` (`src/components/DevVoiceBanner.tsx`) | renders that decision, or nothing. Reads `__DEV__`; takes no action, holds no state, never probes. |
| `make voice-doctor` (`scripts/dev/voice_doctor.py`) | one line per lane from this machine's sockets, exit 1 when a required lane is down. |

The banner is mounted from the intake screen, not from `DialogueGate`: the
gate unmounts the instant `voice_unavailable` lands, so a notice inside it
would flash for one frame. The gate reports its probe through a new optional
`onProbe` prop, wired to the screen's `setVoiceProbe` — a stable setter, so
the effect does not re-run and the dead host is probed **once**.

## Why the production silence is preserved

`DialogueGate`'s docstring argues that an unreachable lane should fall to the
typed steps without a failure notice: nothing was attempted yet, so there is
nothing to apologise for — the notice belongs to a voice run that actually
broke. That argument is about the patient and it is right. It says nothing
about the engineer holding the phone, for whom the same silence made a dead
tunnel and an unbuilt screen look identical.

So the argument is left standing and the diagnostic is added strictly beside
it:

* **The gate is a pure function, not a style.** `voiceDiagnostic(report,
  false)` returns `null` for every report shape — dead lane, live lane, no
  candidates, probe unfinished. Production is not "the banner hidden"; it is
  the banner having no content to render, and `DevVoiceBanner` returning
  `null` on that.
* **`__DEV__` is passed in, never assumed.** `e2e/voiceFallback.spec.ts`
  pins that `DevVoiceBanner` calls `voiceDiagnostic(report, __DEV__)` and
  rejects a literal `true`/`false` in that position — the debugging flip that
  would ship the banner cannot survive a run of the suite.
* **The patient path is byte-for-byte the same decision.** The gate still
  dispatches `voice_ready` / `voice_unavailable` on exactly the same
  condition (`report.base !== null`), the reducer is untouched, and the typed
  steps still run with no notice. The one added call is `onProbe?.(report)`,
  which in production has no subscriber that renders anything.
* **Belt and braces:** voice entry is already `__DEV__`-gated upstream
  (`voiceEligible` in `intake.tsx`), so in production `DialogueGate` never
  mounts at all. The banner's own gate is the second lock, not the only one.

Nothing here retries. `probeReachability` stops at the first base that
answers and probes each dead candidate exactly once per call; the banner
never probes; there is no timer, interval or retry in the gate (pinned).
Nothing here touches audio: the probe is a `GET /health`, and invariant 3 is
not in contact with this change.

## What the dev banner shows

With the ASR lane down and `__DEV__` on, a compact strip sits above the intake
body while the typed steps run underneath it, untouched:

```
Geliştirici notu: ses hattı yanıt vermedi
Yazılı adımlarla devam ediliyor. Denenen adresler:
http://127.0.0.1:8802 — bağlantı reddedildi
http://172.20.10.3:8802 — zaman aşımı
Ana makinede kontrol edin: make voice-doctor
```

One line per candidate base, in probe order, each with how it failed — the
three failure kinds are distinguishable, which is the whole point. The strings
are catalogued `devVoice.*` keys, tr first with the en mirror (invariant 5),
appended as one commented block at the end of each catalogue.

## `make voice-doctor`

Every configured lane, every configured host, from this machine. Ports are the
app's own constants and its own `app.json`; `tests/mobile/test_voice_doctor.py`
fails if either side drifts, because a doctor probing a port the app no longer
uses is worse than no doctor.

Healthy (this machine, tunnel up):

The incident, reproduced against an unreachable host:

```
voice-doctor · <config> · hosts: 127.0.0.2
asr           DOWN  http://127.0.0.2:8802 timeout
extract       DOWN  http://127.0.0.2:8804 timeout  [degraded, not fatal]
tts:voxcpm2   DOWN  http://127.0.0.2:8805 timeout
tts:freya     DOWN  http://127.0.0.2:8803 timeout
voice: DOWN — asr, tts unreachable; the app falls through to the typed steps
                                                          exit 1
```

A dead tier behind a live one is a healthy ladder — verdict UP, exit 0, tier
still named:

```
tts:voxcpm2   DOWN  http://127.0.0.1:18805 refused · http://172.20.10.3:18805 refused
tts:freya     UP    http://127.0.0.1:8803 (157 ms)
voice: UP — tts:voxcpm2 unreachable                       exit 0
```

Requiredness, and why it is not uniform:

* `asr` — **required**. Down means the dialogue never starts. This is the
  lane whose silence cost the hours.
* `tts:*` — **required as a group**. One tier answering is a healthy ladder;
  the app takes the first that answers (`resolveTtsLane`).
* `extract` — **degraded, not fatal**. `useDialogueSession` keeps the verbatim
  transcript when the extract call fails and simply carries no slot
  suggestions, so the conversation still runs. Exiting non-zero on a lane the
  product tolerates would teach people to ignore the exit code.

`HOST=<addr>` adds the Metro LAN address, which exists only inside a running
Metro and so cannot be read from config. `--json` gives the same content
machine-readably; `--timeout` moves the per-probe cap (default 1.5 s, matching
the app's probe).

Every verdict in the test suite is taken against a real local socket — a live
server, a closed port, a slow handler, a 503, an unresolvable name — because a
mocked `ConnectionRefusedError` would prove only that the mock was written.
