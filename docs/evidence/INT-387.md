## Problem
INT-360's PR (#639) found that `docs/compliance/accessibility-conformance.yaml`
still rated SC 3.3.1, 3.3.8 and 4.1.3 by the defects INT-361 (#597) and INT-362
(#600) had fixed. The 2.2.1 row had been re-rated by INT-363 itself.

Nothing could have caught this. Each stale row named only INT-144 (awaiting-human),
because the fixing issues were filed after the rows were written. So a check
that reads only the INT ids in a row's prose would have stayed silent. The
link that did exist ran the other way: each fix is titled after its criterion
("WCAG 3.3.8: …", "WCAG 3.3.1 / 4.1.3: …").

## Change

### The guard (`scripts/compliance/render_a11y_report.py`)
- `load_backlog()` reads `docs/backlog/issues.yaml` by id.
- `issues_of(row, backlog)` returns the issues a row leans on:
  - every `INT-nnn` its `finding` or `remarks` names;
  - every backlog issue filed against its criterion, meaning a title that
    opens `WCAG <sc>:`, with `/`-separated lists split.
- `validate()` gains a check for a row rated Partially Supports or Does Not
  Support:
  - when one of its issues is `done`, the row must carry a non-blank
    `still_open_because:`. Otherwise it is refused with "re-assess the row, or
    record still_open_because";
  - a cited id the backlog does not carry is refused, so a typo cannot slip
    past the guard.
- `still_open_because` is refused on a row at or above Supports, and on a row
  none of whose issues is done. A reason can only exist where it excuses
  something.
- `validate(..., backlog=)` takes an injected backlog, as `palette=` already
  did, so the tests can close an issue without editing the YAML.
- The rendered row prints the reason as **Still open because:**, between the
  finding and the remarks, so the reader sees why the fix left the row open.
- `--check` runs the same validation, so a stale row fails the render as well
  as pytest.

## Tests (TDD)
`tests/legal/test_a11y_report.py` gains 9 tests, 30 → 39:
- the backlog is read whole (more than 300 rows, each with a status);
- the link convention is pinned by an independent oracle: INT-360 → 1.3.4,
  INT-361 → 3.3.8, INT-362 → 3.3.1 and 4.1.3, INT-363 → 2.2.1;
- a row's own INT ids are linked (a WCAG row and an EN row);
- on the committed source with the real backlog, every row below Supports that
  leans on a done issue carries a reason, and the scanner sees at least one link
  (non-vacuity);
- **the regression itself:** 3.3.8 set back to Does Not Support while INT-361
  is done is refused, and the refusal names INT-361;
- **near-miss control:** 1.4.3 leans on INT-144, which is open, so nothing is
  asked of it. With INT-144 marked done in an injected backlog, the same row is
  refused, and refused again with a blank reason. With a reason it is accepted;
- a reason on a Supports row (2.3.1) is refused, and so is a reason on a
  below-Supports row with no done issue (3.1.2);
- an INT id the backlog does not carry is refused;
- the report prints each recorded reason in the row's own line.

## Not proven here, and for the owner
- **Device behaviour.** Two things need a device run:
  - DA-07: whether iOS offers "From Messages" to a `secureTextEntry` box, and
    whether Android's SMS autofill fires;
  - DA-08: whether each line is spoken once on both platforms.
  The rows point at those items, and INT-359 runs them.
- **The three silent status lines under 4.1.3 have no backlog issue.** INT-362
  recorded them as out of scope, and nothing has picked them up since:
  - `notifications.pending` needs a store flag that tells "in flight" from
    "failed";
  - `review.sentInfo` and `consent.queue.note` need a way to tell "just
    happened" from "already so".
  Filing an issue is the next step. This PR does not mint an id.
- **The statement lags the report** until INT-359, as the acceptance requires.
