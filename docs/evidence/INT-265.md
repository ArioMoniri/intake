# INT-265 — the OTP request budgets were fixed hourly windows

`services/api/src/intake_api/auth_store.py` counted OTP requests in **fixed**
hourly buckets, so every budget reset together on the hour and a caller who
spent its budget just before a boundary was handed a fresh one just after it.
INT-264 found this while fixing the suite's clock, measured the worst case, and
deliberately did not change the limiter: changing how an abuse budget is counted
is a semantics change on the authentication path and did not belong inside
another issue's PR. This is that PR.

## The deviation, stated first

`_window_key` put `int(self._now() // OTP_WINDOW_S)` in the Redis key:

```python
def _window_key(self, dimension: str, identifier: str) -> str:
    window = int(self._now() // OTP_WINDOW_S)
    return self._key("otp", "w", dimension, identifier, str(window))
```

Every budget therefore reset together on the hour rather than sliding with each
caller, and `_window_retry_after()` returned the time to the next boundary
rather than the time until the caller actually had room.

The consequence INT-264 measured: **2 × `PHONE_LIMIT_PER_HOUR` codes to one
phone inside about six minutes** — six codes, floored only by
`RESEND_COOLDOWN_S` at one request per 60 s — against the files/10 §2 wording
*"3 requests/hour/phone"*. The same doubling applied to the per-IP and
per-device budgets, which are counted by the same code.

## The counting scheme

One Redis **sorted set per (dimension, identifier)** — no window number in the
key. Each *admitted* request is one member scored with its timestamp. Every gate
call drops the members scored at or before `now - OTP_WINDOW_S`, so what remains
is exactly the admissions inside the rolling window ending now, and a request is
refused once that count has reached the dimension's limit.

```python
def _window_state(self, key: str, now: float) -> tuple[int, float | None]:
    self._r.zremrangebyscore(key, "-inf", now - OTP_WINDOW_S)
    rows = self._r.zrange(key, 0, 0, withscores=True)
    count = int(self._r.zcard(key))
    if not rows:
        return count, None
    return count, float(rows[0][1])
```

**Error bound versus a true rolling window: none.** This is not a sub-bucket
approximation — the retained scores *are* the admission times, so the enforced
bound is exactly "no more than `limit` admissions in any `OTP_WINDOW_S` span".
A sub-bucket counter of width `B` would have been the usual answer and would
have carried an error of up to `B` seconds in the strict direction (and
`OTP_WINDOW_S / B` keys per identifier); it is not needed here because the
limits are small constants, which is what bounds the set.

**Worst-case key count: one key per (dimension, identifier), holding at most
`limit` members** — 3 for a phone, 10 for an IP, 3 for a device — expiring
`2 × OTP_WINDOW_S` after its last write. The set is bounded because members are
added **only on admission** and the gate refuses at `limit`, so it can never
exceed `limit` entries however much traffic arrives; a refused request writes
nothing at all. That is the specific thing the acceptance forbids: there is no
per-request timestamp list that grows with traffic, and the endpoint an attacker
controls cannot be turned into memory amplification. The number of *keys* still
scales with the number of distinct identifiers presented — unavoidable for any
per-identifier budget — but it is now **half** what the fixed scheme held,
because there is no second bucket alive across a boundary.

`test_the_counter_key_set_is_bounded_and_does_not_grow_with_traffic` asserts all
three parts (key count, `ZCARD ≤ limit`, TTL) after driving one caller for two
whole windows, rather than describing them.

**Work per request: constant, independent of traffic** — one
`ZREMRANGEBYSCORE` + one `ZRANGE 0 0` + one `ZCARD` per dimension (three
dimensions, so nine fixed commands), then one `ZADD` + one `EXPIRE` per
dimension on admission. No `KEYS`, no scan, no iteration over history.

**Clock-injectable, unchanged.** Every score and every comparison comes from
`self._now()`, which is the injected `now_fn`. Nothing sleeps; the tests advance
the harness clock (docs/TDD.md rule 6) and the suite still runs against the
in-process fakeredis. INT-264's window-relative harness clock is kept exactly as
it was — its determinism tests pass unedited — and it is now what lets the
INT-265 tests *choose* a phase of the hour on purpose instead of inheriting one.

## The retry-after

The old answer was the time to the next fixed boundary. That is the failure mode
the acceptance singles out: a caller told to come back at :00 and then refused
again is worse than the bug, because the client has no way to distinguish it
from a broken endpoint and retries into the refusal.

The true answer for a rolling window is the moment the oldest retained admission
leaves it: `oldest + OTP_WINDOW_S - now`. Where more than one dimension is over
its limit, the caller is told the **latest** of them, because every over-budget
dimension has to clear before the request would be admitted:

```python
waits: list[float] = []
for key, limit in budgets:
    count, oldest = self._window_state(key, now)
    if oldest is not None and count >= limit:
        waits.append(oldest + OTP_WINDOW_S - now)
if waits:
    return max(waits)
```

The wait is always strictly positive: `_window_state` has just removed
everything scored at or before `now - OTP_WINDOW_S`, so any surviving `oldest`
satisfies `oldest > now - OTP_WINDOW_S`.

`test_the_retry_after_is_the_true_wait_not_the_time_to_the_next_boundary`
asserts the **value**, not merely that one is present, and then walks it:

- the sequence is placed so the two candidate answers differ — the true wait is
  3417 s and the time to the next boundary is 3540 s — and the test asserts they
  differ before comparing, so it cannot pass by accident on a phase where they
  coincide;
- `retry_after_s` equals the true wait (to 0.5 s, the body being rounded to one
  decimal in `errors.py`) and the `Retry-After` header is `int(wait) + 1`;
- one second **before** the advertised instant the caller is still refused, and
  at exactly the advertised instant it is admitted. Both halves matter: the
  first proves the value is not merely conservative padding, the second proves
  it is not an instruction to come back into another 429.

## Refusals and things deliberately not done

- **A sub-bucket sliding counter.** The usual answer, and the one the issue
  suggests, but it buys an approximation this problem does not need: the limits
  are 3, 10 and 3, so retaining the actual admission times costs at most ten
  sorted-set members and gives an exact bound and an exact retry-after. A
  60-second sub-bucket scheme would have been strict by up to 60 s and would
  have held 61 keys per identifier instead of one.
- **Making the gate atomic.** The check-then-record sequence is not atomic
  against a concurrent burst on the same identifier — the same race the fixed
  scheme had, unchanged in kind and unchanged in width. Closing it needs a Lua
  script or a `WATCH`/`MULTI` retry loop; both are testable, but the fake Redis
  the suite runs against does not execute Lua, so the test that would prove it
  cannot be written here. Reported rather than half-built (invariant 17).
- **Widening the change to `carrier/geo sanity checks against SMS pumping`,**
  which files/10 §2 also names and which no code in `services/api` implements.
  Out of scope for this issue and not this PR's to smuggle in; reported below.
