## Bottom line

- `test_a_replayed_nonce_is_refused_and_a_tampered_replay_does_not_burn_it`
  built its tamper as `signature[:-2] + 'AA'`. The nonce is
  `secrets.token_urlsafe(16)`, so the HMAC is random per run. When the signature
  already ended in `AA`, the "tampered" token was the genuine token. It
  verified, consumed the nonce in `fresh_store`, and the test failed with
  `Failed: DID NOT RAISE CheckinSignatureInvalid`. That is the line seen in the
  INT-583 `make check` on 30 Oct 2026.
- The rate is **1 in 1024, not 1 in 4096**. A 32-byte digest is 43 base64url
  characters. The 43rd character carries only the last 4 bits of data plus 2
  zero padding bits, so it takes only 16 values. That gives
  P(`…AA`) = 1/64 × 1/16 (§1).
- The tamper now flips one bit of the decoded digest and re-encodes it. A
  canonical base64url encoding is one-to-one, so the result always differs and
  is still a well-formed 43-character signature. The test also runs once over a
  fixed nonce whose signature ends in `AA`, so the reproduction is part of the
  suite and does not depend on luck.

## 1. Cause and rate

`mint_checkin` signs `header.payload` with HMAC-SHA256 and encodes the 32-byte
digest as unpadded base64url (`_b64u_encode`). 256 bits fill 42 characters
(252 bits) plus 4 bits in a 43rd character, whose low 2 bits are zero padding.

Measured locally, 30 Oct 2026, over 2^20 HMAC-SHA256 digests (zero key,
counter messages): 43 characters every time, 16 distinct last characters
(`0 4 8 A E I M Q U Y c g k o s w`), and `…AA` about 1 in 994. Over 20,000
tokens from the test module's own `_mint()` (`rate.py`, §4): the old tamper
returned the genuine signature 17 times, about 1 in 1176. Both are consistent
with 1/1024.

The padding bits matter for the choice of fix. Python's `urlsafe_b64decode`
ignores them, so a last-character swap such as `A` → `B` spells the **same**
digest. The current verifier compares strings with `hmac.compare_digest`, so
it would still refuse such a swap. A verifier that compared decoded bytes would
accept it, and the test would then pass for the wrong reason.
`tests/admin/test_staff_second_factor.py::test_near_miss_a_second_spelling_of_the_same_bytes_is_refused`
already pins the same hazard for WebAuthn credential ids.

## 3. The fix

`tests/connectors/test_checkin.py` only:

- `_tamper_signature(signature, bit=0)` decodes the signature, XORs one bit
  (`raw[bit // 8] ^= 1 << (bit % 8)`), and re-encodes it unpadded. This is the
  same idiom `tests/security/test_otp_abuse.py` uses for its DPoP tamper
  (`raw[-1] ^ 0x01`).
- The replay test uses it in place of `signature[:-2] + 'AA'`, and is
  parametrized over a random nonce and `NONCE_SIGNING_TO_AA`. Its body is
  otherwise unchanged. The genuine token verifies, its replay raises
  `CheckinReplayed`, the tampered copy raises `CheckinSignatureInvalid` against
  a fresh store, and the genuine token still verifies against that store
  afterwards. So the tampered copy never reached `consume`.
- Near miss `test_near_miss_the_signature_tamper_differs_in_one_bit_even_when_it_ends_in_aa`,
  over `NONCE_SIGNING_TO_AA`:
  - The old tamper is the identity: `signature[:-2] + "AA" == signature`.
  - A last-character swap is no tamper either: `signature[:-1] + "B"` decodes to
    the same digest.
  - For each of the 256 bit positions, the tamper:
    - differs from the signature;
    - has the same length;
    - decodes to bytes that differ from the digest in exactly one bit;
    - is refused by `verify_checkin` with `CheckinSignatureInvalid`, not
      `CheckinMalformed`.
