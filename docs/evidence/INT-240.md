# INT-240 — VoxCPM2 as the dev-lane TTS (files/03 §4.9.1 rows 10-11)

Two things made this issue: a licence audit dated **2026-08-29** cleared
`openbmb/VoxCPM2`, and a measurement pass showed the dev voice we have been
running is **row 12** — the low-footprint fallback — serving as if it were
the default. Row 12 is telephony-band, so Turkish `ş/s/ç/z/f` fricative
energy is largely absent from it. This iteration stands rows 10-11 up on a
new port, records the licence properly, and measures both.

Freya (row 12) **stays serving on 8803** throughout. Nothing here removes a
fallback; it adds a tier above one.

## Scope boundary with INT-237

INT-237 (`int-237-tts-quality`, unmerged) owns `speechShaping.ts`: how a clip
is chunked into sentences, trimmed, faded and re-joined. This issue owns the
**endpoint and the fallback** and nothing else. The two compose: INT-237's
`synthesizeClip` calls `synthesizeWav` against whatever base was resolved,
and after INT-240 that base may be VoxCPM2 or Freya. No shaping logic is
duplicated or contested here.

## The GPU could not host it, and that is a reported result, not a workaround

files/03 §4.9.1 row 10 puts VoxCPM2 at **~8 GB VRAM**. The slice had **3.38
GiB free**, sampled three times over ten seconds, stable. Per-process
attribution is unavailable (`nvidia-smi --query-compute-apps` returns
`[Insufficient Permissions]` on a MIG slice), so who holds the other 66 GiB
cannot be determined from inside the container — and it is not ours to
reclaim either way.

**VRAM is the binding limit.** Nothing else came close: disk 50 % used with
1.5 TB free, RAM 890 GB available, load 0.02/core.

So the server picks its own device: **CUDA only above a 10 GiB free floor,
otherwise CPU** — the same `_pick_device` shape the Freya server on 8803
already uses. Today it chose CPU. That is a real constraint on what this lane
delivers, and it splits the two rows apart:

- **row 10, the compile-time cached-clip path — SERVED.** Pre-synthesising
  `ask_tr`/`confirm_tr`/`action_tr` at `protocols compile --voice <id>` is a
  batch job with no latency budget. Measured RTF ≈ 4.06 on CPU (bf16, 16
  threads); the whole 16-probe corpus rendered in one pass.
- **row 11, the dynamic runtime path — NOT SERVED.** Its whole claim is a
  0.14 s TTFT, and RTF 4 is three orders of magnitude off that. Row 11 stays
  VRAM-blocked until the slice frees up, at which point the next supervisor
  restart takes the GPU with no change to this code.

The supervisor deliberately does **not** gate its start on free VRAM the way
`serve_tts_supervised.sh` does: with this slice near-full that gate would
mean never starting, and the CPU path costs the other tenants nothing.

## Deliverable 5 — how the normaliser was verified OFF

Invariant 22 and files/03 §4.9.6 require VoxCPM2's built-in normaliser to be
disabled, because it routes Turkish to its **English** branch. Four
independent checks, not one:

**1. Source, read on the installed package.** `voxcpm/utils/text_normalize.py`
builds only `Normalizer(lang="zh")` and `Normalizer(lang="en")` and routes
`lang = "zh" if contains_chinese(text) else "en"`. Confirms §4.9.6 exactly.

**2. Explicit argument, never the default.** `normalize=False` is passed on
every `generate` call. The library default happens to be `False` in 2.0.3,
but a default is not a guarantee — a minor version can flip it.

**3. A live tripwire, not a comment.** The library constructs the normaliser
**lazily, inside `if normalize:`** (`core.py`), so a non-`None`
`tts.text_normalizer` is positive proof that the branch executed. The server
asserts it is `None` at load (refusing to serve otherwise) and again before
and after **every** synthesis, returning `500 normalizer_engaged` if it ever
materialises. Observed `None` throughout: at load, and after all 16 probes.

**4. A positive control — what it would have done.** The normaliser was
instantiated once, off the serving path, purely to show why it is disabled:

| input | what the normaliser produces |
|---|---|
| `15 mg` | `fifteen milligrams` |
| `2,5 mg alin` | `two,five milligrams alin` |
| `Tansiyonunuz 140/90 mi?` | `Tansiyonunuz one hundred forty ninetieths miles?` |
| `gunde 3x1` | `gunde three times one` |

The first row is the failure §4.9.6 predicted. **The third is worse than
recorded and should be added to the hazard list**: a blood-pressure reading
`140/90` is reinterpreted as the *fraction* "one hundred forty ninetieths",
and the Turkish interrogative particle `mi` is read as the unit **"miles"**.
That is a numeral corruption and a unit hallucination in a single four-word
Turkish clinical sentence.

**The digit guard stays, on both sides.** `assertSpeakableTr` throws before
any request leaves the app (`/\p{Nd}/u`, so all Unicode digits); the 8805
daemon independently returns `400 digits_forbidden`. Verified live against
ASCII `15 mg alin`, Arabic-Indic `١٥ mg`, and the Turkish decimal comma
`2,5 mg alin` — all three refused. No numeral reaches any TTS.

### What the numbers say

**The fricative question is answered, and it is not a close call.** Freya's
99 % spectral rolloff sits between **3040 and 3445 Hz on all sixteen
probes** — a 405 Hz spread across utterances ranging from one word to 153
characters. A ceiling that does not move with content is a **band limit**,
not a spectrum. VoxCPM2 ranges **1616–9203 Hz**, a 7587 Hz spread that
tracks the content: the probes that reach highest are the fricative-dense
ones (`b11 "Nasıl başladı?"` 9203 Hz, `b01` 8471 Hz, `b05` 8297 Hz).
Median energy above 4 kHz goes **0.0029 → 0.0283**, roughly 10×.

**Speaking rate is essentially unchanged** — median 12.12 → 12.52 chars/s
excluding whitespace — so this is not a slower voice bought at the price of
bandwidth.

**Lead silence improves markedly**, median 100 → 10 ms; trailing silence
slightly, 110 → 95 ms.

**Two honest caveats, both for the owner's ears rather than the table:**

1. **VoxCPM2's spectrum is variable where Freya's is merely limited.** Five
   probes come in *below* Freya's rolloff (`b12` 1616 Hz, `r02` 1995 Hz,
   `b10` 2308 Hz, `b09` 2571 Hz, `r03` 2651 Hz). Durations rule out
   degenerate or truncated output (ratio to Freya 0.75–1.30 everywhere
   except `r01`), so these are dull renderings, not broken ones — but
   per-utterance variance is a new failure mode that row 12 does not have.
2. **`r01_red_tutun` is a defect worth naming.** The one-word RED imperative
   *"Tutun"* comes back with **410 ms of lead and 780 ms of trailing
   silence** around 570 ms of speech — 2.00× Freya's duration. Under
   invariant 21 the RED script is a pre-positioned clip on the device, so
   this is trimmable at compile time rather than at runtime, but it must be
   trimmed: 1.2 s of silence wrapped around a RED imperative is the wrong
   behaviour in the one place ambiguity is the harm.

## Deliverable 4 — the client seam

`apps/mobile/src/lib/dialogue/ttsLane.ts` (new) turns the single hardcoded
`TTS_PORT = 8803` into an ordered ladder read from config:

```jsonc

  { "id": "voxcpm2", "port": 8805 },
  { "id": "freya",   "port": 8803 }
```

`parseTtsLanes` reads it (absent or empty → the built-in order; malformed

as "down" so the next tier gets its turn. `clips.ts` now probes the ladder.

applies cleanly.

`assertSpeakableTr` verbatim, so the guard throws before any request leaves
the app whichever model is about to answer.

## Deliverable 2 — the registry row

`observability/registry.yaml` had no field for a model pin or a licence
blob — its nine-key schema recorded `license: "Apache-2.0"` as a bare claim,
with pins living as prose inside `host`. Seven **optional** fields were added
to `RegistryEntry` so an auditor can see what was actually read:
`model_id`, `revision`, `weights_sha256`, `licence_verified_at`,
`licence_blob_url`, `licence_blob_sha256`, `licence_note`.

Two conditional validators make the block honest rather than decorative:

- declaring `model_id` **requires** `revision` + `weights_sha256` +
  `licence_verified_at` — a half-pinned row is worse than none, because it
  looks verified;
- declaring `licence_verified_at` **requires** `licence_blob_url` +
  `licence_blob_sha256` — you cannot claim verification without recording
  which bytes you read.

Optional rather than mandatory: the three model rows that predate this
(`qwen3.5-9b`, `whisper-tr-medical`, `freya-tts`) have not all had their
blobs read, and forcing the field now would mean inventing hashes. **Backfilling
them is a follow-up issue, not this one.** The ten service rows are untouched.

The committed row (`voxcpm2-tts`): `self_hostable: true`,
`self_hosted_now: true`, `probe: http_health`, `phi_path: true`,
`fallback: "component:freya-tts"` (the registry's grammar for
`tts.freya_local`), `licence_verified_at: 2026-08-29`,
`model_id: openbmb/VoxCPM2` @ the pinned revision, both weight sha256s, the
blob url and its sha, and a `licence_note` that states in full sentences that
the HF repo carries no LICENSE, where the blob came from, and where it is
vendored.

**One row moved that was not strictly asked for, and it is load-bearing.**
`freya-tts` was `self_hosted_now: false` with host text saying "not deployed
… awaits owner approval". It *is* deployed — `/health` on 8803 answers
`device: cuda` — and it is what `voxcpm2-tts` names as its fallback. A
fallback the release gate believes is not running is a fiction, so the flag
was corrected to `true`. The gate's pinned blocked-set therefore gains
`freya-tts` (it is the bottom of the ladder, fallback `none`) and does **not**
gain `voxcpm2-tts` (its fallback resolves and is healthy). That set did not
shrink; it became honest about a lane that was already running.
