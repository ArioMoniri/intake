## How it works

- **Questions.** The rows are the candidate's own slots. `#` is the slot's place among the chain's pack questions in ask order, so a gap is a cluster question the branch inherits. `Q` is the proposal's question number, assigned exactly as the generator assigns slot ids (`GEN.extract_questions`). The generator's fixed duration slot and the three hand-authored candidates (`gastroenteroloji`, `kardiyoloji`, `noroloji`) show `—`. Proposal items the generator kept out are listed under the table with the generator's own reason. Each `**Q` segment is parsed by `GEN.extract_questions` alone, and the parser keeps no state across segments. There are 25 such items, all `hold=`.
- **Generator identity.** The header records the generator as the git blob id of `scripts/dev/gen_specialty_packs.py` (`git hash-object`), not a commit id. A commit id cannot be derived from the committed tree, changes under a squash merge, and cannot be read in CI's shallow checkout. The blob id is reproducible from the bytes, and `git log --find-object=<id>` names the commits that carry it. The candidate sha256 binds a signature to the exact candidate bytes.
- **The pending-value marker.** Each stub's `when` holds invariant 17's sole-exception form. That form is legal only under `packages/protocols/`, so the renderer escapes the first character of every token of the zero-marker gate as a numeric HTML entity. The page reads the same, and the bytes carry no token. The token pattern is read from `scripts/ci/no_placeholders.sh` itself, so the escape follows the gate.
- **Open items.** An open item is a table row, outside code fences, that names a human decider: an HB-C id, a psychiatrist, a paediatrician, the owner, the clinician, or `awaiting-human`. The trail is every `docs/evidence/verification/*.md` whose title says `awaiting-clinical-review`, plus `docs/evidence/INT-353.md`. `owner-decisions-2026-09-26.md` has no such title: it records decisions already taken.
- **Legend rule.** A table whose first header cell is `code` (or `codes`, `legend`), or whose section heading names codes or a legend, defines terms rather than decisions. Its rows are not open items. This drops the six near-twin §C resolution-code rows (C, B, F, P, S, K).
- **Cross-cutting rule.** A row whose locator cell states a scope over every pack is cross-cutting. The locator cell is the first cell, or a cell under a `where`, `chain`, `proposal`, `branch` or `scope` header. The scopes are "all four" (the clusters that document's title names), "all 91" (all specialties) and "every generated pack" (all generated packs). Such a row is listed once in `_cross-cutting.md`, with its scope, the stated phrase, its source row, its HB ids and deciders, and a decision row in that page's signature block. Every packet the scope covers carries the line "Cross-cutting items that also apply here: see `_cross-cutting.md` (n items)", and none copies the item. So each item is signed once. A scope phrase elsewhere in the row does not count.
- **Filing rule.** Any other row is filed under every packet that it or its section heading names. A packet is named by its slug, its Turkish name (with Turkish case folding), a prefix of either (`kadın`, `iş ve meslek`, `klinik_psikoloji`), its initials (`KBB`) or the cluster id. A prefix that several branches share (`göğüs`) names one only inside a document whose headings name exactly one of them. A one-word prefix that ends another name (`cerrahi`) names nothing. A prefix under three letters (`ic`) names a branch only in front of a question number (`ic Q5`). A row that names no packet falls back to the slot ids it quotes; positional `soru_N` ids and the two fixed slots are not used. A row that names nothing goes to `_unassigned.md`. It is never forced into a packet.
  - The issue says "exactly one packet"; the task brief says an item that names several branches appears in each. The brief wins for named items. The test asserts that every item has exactly one home (filed, cross-cutting or unassigned) and appears in every packet it is filed under and in no other.

## Owner decision: legend rows and cross-cutting items

The coordinator relayed the owner's packaging decision on the 13 unassigned items. It is packaging, not a clinical call:

1. The near-twin §C legend rows define codes, not decisions, so they are excluded by a legend rule (header or section).
2. Items scoped to every pack go into one packet, `_cross-cutting.md`, with its own signature block. That packet is listed first in the README.
3. Each packet carries a one-line pointer with its count, and no item is copied, so each is signed once.

Both rules are in `scripts/dev/signoff_trail.py` (`is_legend`, `Item.scope`, `covered`, and `assign` returning `Filing`).
