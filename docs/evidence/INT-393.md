# Evidence: INT-393 · patient erasure removes Doctor Links, and the retention source text matches the tree

GitHub #649 (P0). **Sec-Row:** `data-at-rest` (files/10 §9; `docs/security/threat-model.md`
§ `data-at-rest`). **Branch:** `int-393-erasure-doctor-links`, based on
`int-392-session-delete-outputs` (PR #648, not yet merged). No migration: the alembic head is
still `0013_previsit_output`.

## 1. The defect

INT-392's evidence §8 found it. INT-150 (migration 0012) added `doctor_links.share_id → shares.id`
as `fk_doctor_links_share_id_shares`, with no ON DELETE rule. Both deletion paths deleted the
subject's `shares` without removing the Doctor Links that hang off them:

| Path | Where | With a Doctor Link present |
|---|---|---|
| DSAR erasure (KVKK m.11, after the 30-day grace) | `services/api/src/intake_api/dsar/shred.py` `_erase_subject` | `ForeignKeyViolation` on postgres. The recipient envelope was never shredded and the link never removed. |
| Retention, class `clinical_record` | `packages/intake_platform/src/intake_platform/retention/executors.py` `destroy_clinical` | `ForeignKeyViolation` on postgres. |

So any patient who ever issued a Doctor Link could not be erased. The unit lane stayed green
because SQLite checks foreign keys only when asked, and no DSAR unit test issued a link.

`git grep` finds no other path that deletes `shares`: the two executors above and the integration
teardowns (`tests/api/test_api_postgres.py`, `tests/data/test_rls.py`, neither of which seeds a
Doctor Link). The `test_api_postgres.py` teardown now deletes `doctor_links` before `shares`
anyway, so a future Doctor Link test there cannot strand its tenant.

## 2. The stop check: must a Doctor Link outlive the patient?

No. Nothing in files/06 keeps it past the record, so nothing here needed a stop.

- **files/06 §3** has one Doctor Link row: "Doctor Link tokens: expiry ≤ 72 h default." That is an
  access expiry, not a reason to keep the row.
- **The row's own inventory annotation** is `RET_SHARE` (`intake_platform/db/inventory.py`):
  "share expiry ≤ 72 h default; grant row retained with the record for audit (06 §3)". Retained
  *with the record* means erased with it.
- **`retention_policy.yaml`**'s `doctor_link_tokens` row says the same in its source text: "the
  Share grant row itself is retained with the record for audit … and follows clinical_record".
- **The audit evidence survives regardless.** Every issue, open and revoke is on the WORM
  hash-chained audit log under `doctor_link:<id>` (10 years, files/06 §3), which this engine
  cannot destroy. The erasure adds its own entry to that chain.
- **files/06 §2.3** keeps a copy a hospital already holds as the hospital's, as controller. A
  Doctor Link is not a copy. It is our grant to reach our record, and the filing of the erasure
  already revoked it (`revoke_live_shares` → `_revoke_links_of_share`).

## 3. The mechanism, and why

This is the INT-392 pattern one level down: **explicit, ordered removal in each deletion path. The
foreign key stays NO ACTION. No `ON DELETE CASCADE` migration.**

- **Crypto-shred first.** files/06 §1 KVKK-7 names crypto-shredding as our destruction method. The
  link's `recipient` label is an envelope (the patient-typed name of whoever they sent it to), so
  its wrapped DEK is destroyed with the note's before the row goes. A cascade would delete the row
  without the shred and without an audit entry.
- **NO ACTION is the fail-closed backstop.** A future path that deletes a share and forgets its
  links raises and rolls back, instead of dropping an unshredded envelope. The contract refuses a
  cascade on `doctor_links.share_id`.
- **Deleted by the ids it audits.** The DSAR path deletes Doctor Links and shares by the ids its
  sweep read, not by parent. A link or share that appeared after the sweep is not in those lists,
  so its NO ACTION key stops the parent's delete and the whole run rolls back. Nothing is removed
  that the audit does not name.

**Order (documented in both module docstrings), children first.** DSAR: previsit outputs, **Doctor
Links, shares**, documents, rectifications, notes, learned facts and their header, slots, then the
telemetry de-link, then the sessions. All of it runs in one transaction. Retention
`clinical_record`: previsit outputs, documents, **Doctor Links, shares**, notes, slots, telemetry
de-link, sessions.

**Audit.** The DSAR erasure writes one entry per removed row:

- `dsar.delete.doctor_link` against `doctor_link:<id>`, the ref the link's issue, opens and revoke
  were audited under;
- `dsar.delete.share` against `share:<id>`, the ref the share was created and cascaded under.

Both are written after the commit and after `dsar.delete.shred`, in removal order, with
`actor=patient:<id>` and `consent_scope=basis:KVKK-11/13`. The `dsar` prefix classifies them as
`DATA_REQUEST` in the patient's access log. The `share` segment does not turn an erasure into
"shared", because the prefix rule runs first; `tests/security/test_access_log_view.py` pins that.
The retention path is audited by the engine's own destruction log (`retention.dsar_destroyed`), as
before.

## 4. The erasure-graph contract

`tests/data/test_session_delete_contract.py` no longer stops at the keys to `sessions.id`. The graph
is every table reachable from `patients` or `sessions` by following foreign keys backwards (17
tables today), and every key between two of them (21 keys). Two declarations are read against
`Base.metadata`:

- `ROWS_ON_ERASURE`, per table: `erased` or `kept`. Each kept table carries its reason in
  `KEPT_BECAUSE`.
  - kept: `patients`, `consents`, `dsar_requests` (INT-037's statutory set), `events`
    (telemetry, de-linked), `guardian_links` (awaiting-human, no 06 §3 row), and
    `notification_preferences` (see §8);
  - erased: everything else.
- `ON_ERASURE`, per key: `removed_first`, `delinked`, `cascade` or `parent_kept`.

`contract_breaches()` checks:

- the key's ON DELETE agrees with the declaration;
- a delinked key can hold NULL;
- a removed-first or cascade key belongs to an erased table, and a delinked key to a kept one;
- removed-first and delinked keys point at an erased parent, and parent-kept keys at a kept one;
- nothing in the graph is undeclared, and nothing declared has left it.

**Near-miss controls:**

- a new key planted on a declared table (`doctor_links.note_id → notes.id`) is named;
- a new table planted below `shares` is named twice, once for the table and once for its key;
- a CASCADE on `previsit_outputs.session_id` or `doctor_links.share_id` is refused;
- a declared cascade that the key does not carry is refused;
- declaring `shares` kept is refused on both keys that would then point at or from it wrongly;
- a `parent_kept` key to an erased parent is refused;
- stale table and key declarations are named.

**Behaviour, with SQLite foreign keys ON.** One seed carries a row in every table of the graph, and
a test proves the seed covers the whole graph. Every payload the erasure shreds is a real
envelope. Then:

- a control proves a bare `DELETE FROM shares` is refused in this lane;
- the retention executor removes every erased table of the session subtree and de-links the event;
- the DSAR executor leaves every table exactly as `ROWS_ON_ERASURE` declares (erased tables empty,
  kept tables intact), shreds the five envelopes, and audits the output, the link and the share by
  id, in that order.

The retention half covers the session subtree only, because that executor is keyed by session.
Subject-keyed rows (learned facts and their header, rectifications) are reached by the DSAR
executor, which the second behaviour test checks against the whole declaration.

## 5. Retention policy text (text only)

`retention_policy.yaml` `clinical_record.source` now lists the tree as it stands: "sessions,
slots, notes, the INT-317 previsit outputs, shares rows and the INT-150 Doctor Link rows that hang
off them, document rows". No `retention`, `action`, `destruction_path` or `status` field changed,
and no period is implied. The Doctor Link row was already on the record clock through `RET_SHARE`
and through the `doctor_link_tokens` row's "follows clinical_record". The text now says what the
executor does.

The issue names "INT-320/150". INT-320 is the embed launch-ticket handshake. It adds no table to
the erasure graph, so the text cites INT-150 (migration 0012), which introduced `doctor_links`.

## 11. Found, not fixed (separate issues)

- **`notification_preferences` is not erased by any path.** `RET_NOTIFICATION_PREFERENCE` puts the
  row on the record clock ("patient-deletable, 30-day grace, then crypto-shred"). Migration 0007
  grants `app_rw` no DELETE on it and says erasure "runs through the retention engine". The DSAR
  executor does not touch it, and the retention `clinical_record` executor is keyed by session, so
  it cannot reach it either. The row holds a flag and two minute counts, no content. The contract
  declares it `kept` with this reason, so closing the gap is a declared change there. Deleting it
  needs a DELETE grant, or the erasure-role decision INT-392 §8 already records, so it is left to
  its owner.
- **The DSAR export does not list Doctor Links.** `intake_api.dsar.store.subject_record` promises
  "one answer" for export and erasure. The erasure now destroys Doctor Link rows that the export
  does not show. The same is true of previsit outputs (INT-392) and learned facts (INT-170). The
  export's shape is INT-037's.
- **INT-392 §8's erasure-role question stands.** The new statements need nothing `app_rw` lacks:
  0001 grants DELETE on `shares` and 0012 grants DELETE on `doctor_links`. The executor still
  cannot finish as `app_rw` because of the telemetry de-link.
