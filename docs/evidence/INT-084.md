## 1. "Every fact carries source span" — a signature, not a validator

The clause is satisfied the way INT-083 satisfied the `YELLOW_REVIEW` ceiling: by removing
the shape that could violate it.

Every parameter of `compose()` that carries patient material takes a `Sourced[T]`, whose
`span` is a keyword-only field with **no default**. `Sourced(item, attribution=…)` is a
`TypeError` at the call site, and a test walks `inspect.signature(compose)` and asserts
that all ten fact-placed parameters are `Sourced`-typed — so a maintainer who wants to
accept a bare `PmhItem` has to change a signature a test pins.

`SourceSpan` has four kinds and four classmethod constructors rather than one flat one,
because a document span with an utterance offset should be unconstructable. Locators are
ids and offsets only — never narrative (invariant 6):

```
utterance:work-1:0-16 · document:doc-0001:p2:0.1,0.2,0.3,0.4
earlier_visit:visit-0000:2026-05-12 · rule:rf.example
```

The fired rules are deliberately **not** facts: files/04 §5 already gives each one an
`evidence` string, and a `RULES_ENGINE` row in the attribution table would open a second,
weaker path for a level to reach the note.

## 2. Attribution — INT-282's rule, generalised and made structural

INT-282 found the concrete case (*the note mapper must not attribute a relative's
condition to the patient*) and INT-256 found the adjacent one (medication-shaped wording
against a penicillin allergy is a **false clinical statement**, not an awkward one). This
issue turns both into one table, `SECTION_ATTRIBUTIONS`, in which **`RELATIVE` appears in
exactly one row** and a test asserts that:

| section | admits |
|---|---|
| chief_complaint · hpi · ros_pertinent · measurements | `patient_self` |
| pmh · medications · allergies | `patient_self`, `record`, `carried` |
| family_social | `patient_self`, **`relative`** |
| imported_objective | `record` |

A relative's condition offered to `pmh` raises `AttributionRefused`. It is **refused, not
moved**: silently relocating it would hide the caller's bug inside the note.

### The three kinds stay apart in every renderer

`compose` is copy-free on purpose. `family_social.family` entries carry the relative
**code** (`mother: …`), never a Turkish label, so the exchange layer keeps codes (files/03
§7) and the human renderers localise them — and a consumer that only ever sees the note
*value* still cannot read a relative's condition as the patient's own.

* **The note value** — `family_social.family == ("mother: Sentetik kalıtsal durum",)`, and
  a test asserts the string is in no `pmh.condition`.
* **SOAP / PDF** — every fact line carries its marker and its `fNN` handle:

  ```
  [f04] hasta beyanı — Sentetik durum A [unconfirmed/patient]
  [f05] belge: doc-0001 — Sentetik durum B [unconfirmed/record]
  [f06] önceki kayıt: 2026-05-12 — Sentetikol · günde bir kez bir tablet [matches]
  [f08] yakın beyanı: anne — Sentetik kalıtsal durum
  ```

  A relative's line names the relative; a carried line names **the date it was first
  recorded**, because a carried fact without its date reads as a current one — which is
  the whole failure INT-247 exists to prevent. A test asserts the condition string appears
  on exactly one SOAP line, that the line carries the relative marker, and that it does
  **not** carry the patient-statement marker.
* **FHIR** — the condition appears **once** in the whole serialised bundle, inside the
  `family_social` section's narrative, and never as a `Condition`, which would assert it of
  the `Patient`. That is not a renderer convention: it follows from the composer refusing
  a `RELATIVE`-attributed `PmhItem` at all, so there is no path by which a relative's
  condition can become a subject-referencing resource.

## 3. What is missing, and *why* — three facts that cannot collapse into one

`NoteGapReason` is a closed four-member enum and `NoteGap` has **no free-text field**. A
reason a caller can spell is a reason two different causes can be spelled the same way.

| reason | the fact it records |
|---|---|
| `deferred_environment` | files/02 §33 — a third party was audible, so the section was not asked. The clinician's marker is that file's verbatim `eksik: ortam uygun değildi`, asserted by a test. |
| `declined` | the patient was asked and chose not to answer — a disclosure decision, not a setting |
| `session_ended` | the session stopped before the section (files/02 §34's "Sıranız geldi" checkpoint) |
| `unresolved_precondition` | the step was obliged and its gate never resolved |

They reach `data_gaps` as language-neutral codes — `screening:deferred_environment:phq2` —
so the localisation happens in each renderer and the four can never be flattened on the
way. Tests assert the four render to four different markers and that all four appear.

## 4. The "missing" disagreement INT-282 left open — decided, and flagged

docs/evidence/INT-282.md: the INT-081 engine counts a `must_ask` step whose gate is TRUE
**or UNKNOWN** as obliged; mobile's `missingQuestions` keeps gate-TRUE only and calls the
rest *"skipped, not missing"*. It was left unresolved there because it *"decides what a
clinician is told is missing from a partial note, and that is a note-semantics decision"*.
That is this issue.

**The note takes the engine's definition**, and takes it structurally rather than by a
flag: `NoteGapReason.UNRESOLVED_PRECONDITION` exists, so an obliged step behind an
unresolved gate has somewhere to be recorded. Mobile's definition is **not representable**
here — it produces no gap at all — so the two cannot be reconciled by configuration; one
of the surfaces has to change.

The reason is asymmetry of harm on the surface this issue owns. A clinician reading a
short `eksik` list on a checkpointed note believes more was covered than was, and acts on
that belief; an over-long list is noise they can dismiss. files/02 §2 calls the checkpoint
the most common way a detailed session ends, so this is the common case, not the edge.

**Flagged, not settled** — HUMAN_BLOCKERS.md **HB-C15** and `docs/backlog/blockers.md`.
It is inert today (mobile drives fixture packs, the engine drives compiled ones) and
becomes live the moment INT-096 puts compiled packs behind both.

## 5. The missing vitals field — added, narrowly, with the reason recorded

files/04 §5's `PreVisitNote` had **no vitals or anthropometry key at all**, while files/02
§2 promises vitals entry in Detaylı. INT-282 refused to invent one and rendered height and
weight into a mobile-only `measurements` section, recording that *"this is a real gap and
it is the note schema's owner's to close … the mapper is INT-084"*.

It is closed, at the schema layer, as **`PreVisitNote.measurements`** — a sibling of
`family_social`, an array of `{code, magnitude, unit}` with `code ∈ {height, weight}`.
files/04 §5 carries the change note with the date, in the form its two 25 Aug 2026 changes
already use. Three limits, each deliberate:

1. **It is not called `vitals`.** files/02 §2 says "vitals entry (manual/HealthKit/Health
   Connect)", but INT-282 asserted **by name** that nabız `174_TC`, KB `173_TC`/`354_TC`
   and solunum `49_TC` are clinician-measured rows a patient is never asked. A field
   called `vitals` invites a patient-typed blood pressure to sit in a clinician note
   beside clinic-measured ones, where it reads as measured. The name describes what the
   intake surface actually collects. **Whether a patient-entered measured vital may appear
   in the note at all is a clinical-safety decision and was not taken here —
   HUMAN_BLOCKERS.md HB-C14.** `MeasureCode` has exactly two members and a test pins them.
2. **The pain score is not here.** `hpi.oldcarts.severity_nrs` already exists and is where
   a 0–10 self-report belongs; INT-282's `pain_score` maps onto a field 04 §5 has had all
   along. A test asserts no `MeasureCode` member mentions pain.
3. **Invariant 22 rides the type.** `magnitude` is an exact `Decimal` (a float would cross
   a representation boundary), `unit` is the unit the patient's control was labelled with
   and is never converted, and every renderer binds number to unit with a non-breaking
   space and no grouping — `1234 kg`, never `1.234 kg`. Tests assert both the atom and the
   absence of a grouping separator, in SOAP and in the FHIR narrative.

Consequence, recorded rather than acted on: `NOTE_SECTION_IDS` is derived from
`PreVisitNote.model_fields`, so the FHIR Composition gained a `measurements` section
automatically and `document.py::_section_lines` was extended to render it — without that
it would have been silently dropped, which is the failure this whole issue is about.
`apps/mobile`'s `NoteSectionId` union does not yet include `measurements`; its `buildNote`
already emits the id as a string, so nothing is broken and widening the union is a mobile
change left to the mobile lane.

## 6. The disclaimer, and INT-284's lesson translated to paper

files/06 §7's footer is required copy on the note **and** the PDF. Invariant 18 says legal
texts render only from `docs/legal/` with hash binding, so `previsit_note.footer` is a key
in `NOTE_COPY_KEYS` and the whole note is refused when it is absent — not rendered with a
hole where the disclaimer belongs. A test strips the footer key from a copy of the fixture
and asserts the *whole note* refuses.

The headings, attribution markers and gap markers ride the same hash-bound file rather
than a second catalogue, so **one version and one SHA-256 bind the whole rendered
document** — the note prints `legal_strings_version` and `legal_strings_sha256` in its
header, exactly as INT-037's DSAR document does. The module docstring names the two
authors behind the one key set (counsel for the footer, the clinical author for the
headings) rather than blurring them.

**INT-284** found the mobile provenance line *"Bu not hasta beyanına dayanır; tanı
içermez."* rendered under the glass bar and unreachable at large text. The paper form of
that requirement is that no length of note may push the footer off a page or draw over it.
So the footer is **not appended to the content**: `render_document_pdf` reserves a band
**below the content box, inside the bottom margin**, and draws the wrapped footer there on
**every** page; the watermark gets the mirror-image band above the top margin. Content
baselines run from `PAGE_HEIGHT − MARGIN` down to `MARGIN + LEADING` and the bands start
outside that range, so overlap is not a layout accident that can be avoided — it is
unrepresentable. Tests read the PDF's own text layer back per page and assert the footer
is on all of them, with and without a watermark, and a footer too long for its band raises
`FooterTooLongError` rather than being truncated: a disclaimer cut to fit is a different
disclaimer.

## 7. The `notes` threat-model row, clause by clause

* **[T] XSS through note rendering (LLM05)** — there is no HTML renderer. SOAP and PDF are
  text; the FHIR face delegates to INT-033's mapper, whose narrative is generated, escaped
  XHTML. A test feeds `<script>alert(1)</script>` through as a chief complaint and asserts
  it survives **verbatim as text** in SOAP (never rewritten — rewriting what a patient said
  is its own defect) and appears **escaped** in the FHIR narrative, and that the SOAP
  render emits no markup of its own.
* **[R] a fact in the note with no provenance** — answered in §1, and made *reachable*:
  every fact line carries `[fNN]`, the document ends with the block resolving each handle
  to its span, and the FHIR document carries one `EXT_FACT_PROVENANCE` extension per fact.
  Tests assert the rendered ref set equals the fact set and that every handle resolves.
* **LLM09 misinformation presented without review** — invariant 1's note face. The note's
  level is the `RulesTriageResult`'s; candidates arrive as a `LlmCandidateTriage`, are
  never placed as facts, render **after** A/P under their own heading with their own
  marker, and still never cross into FHIR. A test asserts `YELLOW_REVIEW` appears nowhere
  in the bundle and that the candidate text is absent from the S block entirely.
