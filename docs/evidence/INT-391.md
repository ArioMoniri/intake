## The rule, and where it comes from

**WebAuthn Level 3**, W3C Recommendation (https://www.w3.org/TR/webauthn-3/; this version
https://www.w3.org/TR/2026/REC-webauthn-3-20260825/), fetched 27 September 2026:

| section | what it says about the id |
|---|---|
| §4 Terminology, "Credential ID" | "At most 1023 bytes long." An authenticator mints it in one of two forms: at least 16 bytes carrying at least 100 bits of entropy, or the credential source encrypted so only that authenticator can read it. |
| §5.1 PublicKeyCredential Interface, `[[identifier]]` | The format is unconstrained except that it must not be longer than 1023 bytes. |
| §7.1 Registering a New Credential, the step that checks `credentialId` against 1023 bytes | A longer id should fail the registration ceremony. |
| §3 Dependencies, "Base64url Encoding" | The RFC 4648 §5 URL- and filename-safe alphabet, with every trailing `=` omitted and no whitespace or other characters. |

**RFC 4648 §3.5, canonical encoding.** A conforming encoder sets the pad bits to zero, and a
decoder may reject data whose pad bits are not zero.

**What the provider writes** (INT-378, PR #643, not yet on `main`):
`WebAuthnSessionNotes.recordAfterAction` sets the `credential_id` note to
`Base64Url.encode(asserted)`, which is unpadded base64url, and the `aaguid` note to the stored
AAGUID text, which is webauthn4j's `AAGUID.toString()`, a UUID in `8-4-4-4-12` hex. INT-378's
recorded Keycloak 26.1.4 login carries a 43-character id (32 bytes) and a lowercase UUID.

**So the rule is:** `credential_id` is a string of 1 to 1364 characters from `[A-Za-z0-9_-]`. It
decodes to 16–1023 bytes, and re-encoding those bytes gives the same string. 1364 is
ceil(1023 × 4 / 3), the length of a 1023-byte id. The alphabet refuses `+`, `/` and `=`, the
decoder refuses a dangling character (4n+1 characters decode to nothing), and the re-encoding
step refuses set pad bits.

**Why one spelling matters.** Four-eyes refuses an approver whose `credential_id` equals the
requester's, and compares the two as strings (`four_eyes.py`, the distinct-credential check).
Python's decoder ignores set pad bits, so a lenient check would accept two strings for one
credential. The canonical check makes string equality mean credential equality.

**Where the id goes.** It reaches the `ActorBlock` (four-eyes) and the approval brief's
`requested_by` block. It never enters the audit chain: every admin row names
`caller.principal.subject`, and `audit.py`'s 128-character ref shape is never applied to it. So
nothing downstream bounds it below 1364 characters. The verifier's 8192-byte token cap leaves
room: INT-378's recorded token re-encodes to 1778 characters, and with a 1023-byte id it is 3539.

## The defect

`principal_from_claims` checked `credential_id` with `_ID_SHAPE`,
`[A-Za-z0-9][A-Za-z0-9._:/@-]{0,127}`, the generic id shape it uses for `sub`, `org`, `sid` and
`aaguid`. Against a credential id that shape was wrong in both directions:

- **Too strict.** It wanted a letter or digit first, so an id whose first byte is 0xF8 or above
  was refused. That byte encodes to `-` or `_`, and it happens for about 2 random ids in 64. It
  also stopped at 128 characters, so every id longer than 96 bytes was refused. A valid staff key
  was refused at random, and the staff member stayed locked out until the key was re-registered.
- **Too loose.** It admitted `.`, `:`, `/` and `@`, none of which is base64url. It admitted
  strings that decode to fewer than 16 bytes (`AA` is one byte) or to nothing at all (21
  characters). It also admitted a second spelling of the same bytes.

## The change

- **`packages/intake_platform/src/intake_platform/admin/principal.py`**
  - `_required_credential_id` replaces `_required_id(claims, "credential_id")`. It refuses a
    missing or non-string claim, then calls `_is_credential_id`.
  - `_is_credential_id` works in four steps:
    1. It refuses more than 1364 characters before decoding anything.
    2. It checks the alphabet, which refuses `+`, `/`, `=` and everything else outside RFC 4648
       §5. This also keeps non-ASCII text away from `urlsafe_b64decode`, which raises
       `ValueError` for it, not `binascii.Error`.
    3. It decodes the string. `binascii.Error` (4n+1 characters) is a refusal.
    4. It re-encodes the bytes, requires the same string back (so set pad bits are refused), and
       requires 16–1023 bytes.
  - A refusal is `MalformedClaims("claim 'credential_id' is absent or not a WebAuthn credential
    id")`. The message names the claim and never the value (invariant 6). The API serves it as
    the same 403 `{"error": "forbidden"}` as every malformed claim, and audits it as
    `admin:unresolved`.
  - `sub`, `org`, `sid`, `tenant` and `aaguid` keep `_ID_SHAPE`.
- **`aaguid` is unchanged, on purpose.** The provider writes UUID text, and `_ID_SHAPE` admits
  every UUID text, since it starts with a hex digit and is 36 characters from `[0-9a-f-]`. The
  shape never refuses a valid AAGUID, so it is not wrong in the direction this issue fixes. A
  property test over `st.uuids()` pins that, so a later change to the shape cannot refuse one
  unnoticed.
- **Fixtures.** Every `credential_id` in `tests/admin/fixtures/keycloak_claims.json` was a
  label, not a credential id. `cred-clinical-lead-1` is 20 characters and decodes to 15 bytes.
  `cred-platform-owner-1` is 21 characters and decodes to nothing. `cred-tenant-clinical-responsible-1`
  has its pad bits set. Each keeps its name and number, and the number is zero-padded until the
  string is a multiple of four characters and at least 24 long (`cred-clinical-lead-00001`, 18
  bytes). The second-tab account still shares `clinical_lead`'s id, and the second account still
  has its own. `tests/admin/test_oidc_verifier.py`'s claim set gets the same id. The unit tests
  that build an `ActorBlock` directly (`test_four_eyes.py`, `test_flag_governance.py`,
  `test_voice_*.py`), and `scripts/dev/record_voice_fixture.py`, never pass through
  `principal_from_claims` and are unchanged.
- **`docs/security/threat-model.md`** `admin-console`: "Controls added by INT-391", and the test
  line.
- **Backlog:** the INT-391 row (`E12-admin`, P1, done, `area:admin`, `risk:security`, sec_row
  `admin-console`). The three pinned counts go from 302 to 303, each with the reason, and
  `files/11_ISSUE_BACKLOG.md` is regenerated.

## Tests

**`tests/admin/test_staff_second_factor.py` §5, `TestCredentialIdShape` (hypothesis, through
`principal_from_claims`):**

- Admitted:
  - every id from `st.binary(16..1023)`, encoded (300 examples);
  - every id whose first byte is 0xF8–0xFF, so it starts with `-` or `_` (200 examples);
  - 16, 17, 18, 95, 96, 97, 98, 1021, 1022 and 1023 bytes, each starting with `A`, `-` and `_`;
    96 bytes was the old ceiling;
  - the id from INT-378's recorded login;
  - every recorded fixture account's id decodes canonically to 16–1023 bytes.
- Refused (near-misses):
  - padding: every id whose length is not a multiple of 3 bytes, with its `=`;
  - one character outside base64url at a random position: `+ / = . : @ ~ %`, space, tab,
    newline, NUL, `ı`, a no-break space, a fullwidth `Ａ` and an Arabic-Indic digit (300
    examples);
  - the same bytes in the standard alphabet, starting with `+` or `/`;
  - 0 to 15 bytes, and 1024 to 1119 bytes;
  - 0, 15 and 1024 bytes by name, each starting with `A` and with `_`;
  - a second spelling of the same bytes, pad bits set; the test first shows a lenient decoder
    reads it as the same credential;
  - a dangling character (4n+1 characters);
  - `None`, `0`, `12345`, `True`, bytes, a list, a mapping, and an absent claim.
- The refusal names `credential_id` and does not contain the value, in its `str`, its `repr` or
  any log record at DEBUG.
- `aaguid`: every UUID text (`st.uuids()`) is still admitted.

**§5b, `TestConsoleCredentialId` (through the API harness):**

- a 1023-byte id starting with `-` (1364 characters) reaches `/admin/whoami` with 200;
- a padded, standard-alphabet, 1024-byte, 15-byte or non-string id each gets the same 403
  `{"error": "forbidden"}`. The audit rows are all `admin:unresolved`, and no value appears in
  the logs, the audit rows or any response body.

**`tests/admin/test_oidc_verifier.py`:** a token carrying a 1023-byte id starting with `_` is
signed, stays under the 8192-byte cap, passes `KeycloakClaimsVerifier`, and is admitted by
`principal_from_claims`.

## Red run

The tests and the fixture were written first and run against `principal.py` as it is on `main`.

```
$ uv run pytest tests/admin/test_staff_second_factor.py tests/admin/test_oidc_verifier.py \
    -q -o addopts="" -k "CredentialId or longest"
34 failed, 26 passed, 166 deselected
```

The 34 failures, by what the old shape did:

- **It refused valid ids (29):**
  - `test_every_webauthn_credential_id_is_admitted`, whose shrunk example is 16 bytes starting
    0xF8, which encodes to `-AAAA…`;
  - `test_an_id_starting_with_dash_or_underscore_is_admitted`, whose shrunk example is
    `first=248`;
  - `test_the_boundaries_are_admitted`: every `-` and `_` case, and every size from 97 bytes up
    (25 cases);
  - the 1023-byte id through the console (§5b) and through the verifier.
- **It admitted what is not a credential id (5):**
  - `/` inside an id (shrunk: `A/AAAAAAAAAAAAAAAAAAAA`);
  - an id of one byte (shrunk: `AA`);
  - an id of 15 bytes starting with `A`;
  - a second spelling of 16 zero bytes;
  - a dangling `A` after 18 bytes.

The 26 that pass on `main` are the controls:

- the near-misses the old shape also refused: padding, the standard alphabet, over 1023 bytes,
  0 and 1024 bytes, non-strings, an absent claim;
- the value kept out of the refusal, the §5b 403, and the `aaguid` pin;
- the valid ids the old shape happened to admit: 16–96 bytes starting with `A`, the INT-378 id,
  and the new fixture ids.

An earlier run, before the fixture was rewritten, also failed
`test_every_recorded_account_carries_a_webauthn_credential_id` with `binascii.Error: … number of
data characters (21) cannot be 1 more than a multiple of 4`. The old fixture ids were labels, not
credential ids.
