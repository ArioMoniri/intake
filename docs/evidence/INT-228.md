# Evidence — INT-228 · Tokenizer pseudonyms exceed the DocumentStore key-segment bound

## Acceptance (verbatim from docs/backlog/issues.yaml)

- "real Tokenizer pseudonyms (kid. + 64 hex, ~68 chars) fit the document-store
  key discipline end to end - either _SEGMENT_SHAPE widens with the audit-ref
  bound re-proven, or a documented derivation maps pseudonym -> segment; the
  INT-197 workaround (patient row UUID hex as the segment) is removed and the
  integration is test-pinned"

Sec-Row: identifiers. Depends on INT-034 (the document store itself).

## The defect

`intake_platform.tokenization.Tokenizer.pseudonym` returns `<key_id>.<64 hex>`.
`intake_platform.documents` accepted `patient_pseudonym` only through
`_SEGMENT_SHAPE = [A-Za-z0-9][A-Za-z0-9._-]{0,39}` — 40 characters. A real
pseudonym is 66+ and was refused outright, so nothing that used the real
tokenizer could store a document at all.

Chasing the bound turned up a second, latent defect in the same arithmetic.
The comment above `_SEGMENT_SHAPE` claimed the 40 was chosen "so the full key
stays inside the audit log's 128-char resource_ref shape", and it does not:
`_document_key` validated three segments at ≤ 40 each, so
`quarantine/` + 40 + 40 + 40 + three separators = **133** > 128. Every key that
long would have been built, used to write an object, and then rejected by
`AuditChain.append` — an object that exists and cannot be audited, which
invariant 4 does not allow.

## The choice: derive, do not widen

The acceptance offers two routes. **Widening `_SEGMENT_SHAPE` is not available**,
and the arithmetic is why rather than taste. The audit `resource_ref` cap is
128 characters, and it is not ours to move (`intake_platform.audit`, and every
audit row already written is bound by it). A key spends:

| part | worst case |
|---|---|
| `quarantine/` — longest of the four prefixes | 10 |
| three separators | 3 |
| tenant id | 40 |
| document id (`uuid4().hex`) | 32 |
| **left for the patient part** | **43** |

A pseudonym needs 66–97. There is no widening that fits, and the only way to
*make* it fit is to cut it — which is the one thing that must not happen. A
prefix of an HMAC is a shorter identifier: truncating to 43 characters would
mean any two patients whose pseudonyms agree on their first 43 characters share
an object prefix and a signed-URL namespace, and the birthday bound drops from
2^128 to roughly 2^71 — with the added property that an attacker who can
enrol identifiers can search for a prefix collision directly.

So the key derives its patient part instead (invariant 22's spirit: nothing
crosses a representation boundary unguarded):

```python
def patient_segment(patient_pseudonym: str) -> str:
    digest = hashlib.sha256(_PATIENT_SEGMENT_DOMAIN + patient_pseudonym.encode("utf-8")).digest()
    return base64.urlsafe_b64encode(digest).decode("ascii").rstrip("=")
```

Why this is collision-safe:

- **No truncation anywhere.** All 256 bits of the SHA-256 are carried into the
  output; base64url of 32 bytes is 43 characters unpadded, and 43 is also the
  floor — 256 bits do not fit in fewer characters of an alphabet this size, so
  nothing shorter was ever on the table.
- **The collision bound is unchanged.** Two patients share a segment only on a
  SHA-256 collision (~2^128). The pseudonym is itself a 256-bit HMAC-SHA-256
  with the same bound, so the derivation adds no collision path — it inherits
  the one the identifier already had.
- **Fixed width by construction.** 43 characters for every input, so the budget
  is satisfied by arithmetic rather than by validation: no future change to the
  pseudonym's shape (a longer key id, a different digest encoding) can push a
  key past the audit bound. The property test asserts exactly this — the
  segment width does not vary with the pseudonym.
- **Domain-separated** (`intake/documents/patient-key-segment/v1\0`), so this
  digest cannot be confused with, or replayed as, some other SHA-256 taken over
  the same pseudonym elsewhere.
- **Deterministic**, so the same pseudonym always addresses the same objects
  across processes and restarts; and **one-way**, so the object key and every
  audit row quoting it now carry an image of the join key instead of the join
  key itself — strictly less identifying material in keys and logs
  (invariant 6). Identifiers stay tokenized (invariant 14): the segment is a
  function of the token, never of the raw identifier, which still exists only
  as Transit ciphertext in the vault.

Rotation is unchanged in kind: a new key generation yields a new pseudonym and
therefore a new segment, exactly as it yielded a new segment before. Objects
already stored keep the keys they were stored under — no path re-derives a key
for an object that already has one (`presigned_get` signs `ref.key` as stored).

Two supporting changes make the budget provable rather than asserted:

- **`tokenization` now publishes and enforces its output shape.**
  `MAX_KEY_ID_LEN`/`KEY_ID_SHAPE` are checked for every key at `Tokenizer`
  construction, which turns `PSEUDONYM_MAX_LEN` (97) into a bound the module
  cannot exceed rather than an observation about today's config. `documents`
  imports that constant to size what it will accept as a pseudonym, so the two
  modules can no longer drift apart at the boundary.
- **`document_id` is pinned to 32 lowercase hex.** The store mints every
  document id as `uuid4().hex`; accepting up to 40 was what made the old worst
  case 133. Pinning the shape to what the store actually issues is what keeps
  the 32 in the table above honest.

The result spends the budget exactly: `10 + 1 + 40 + 1 + 43 + 1 + 32 = 128`.
`MAX_DOCUMENT_KEY_LEN` is computed from its parts in the module and pinned to
`AUDIT_RESOURCE_REF_CAP` by a test, so a fifth prefix or a wider tenant id
fails the build instead of failing in production.

AUDIT_RESOURCE_REF_CAP`, one more character is refused by the chain, the
worst case is reachable (longest prefix + maximal tenant + maximal pseudonym

before anything is looked up or logged.

`tests/security/test_tokenization_roundtrip.py` gains the key-id contract: a
misshapen key id is refused at construction without echoing the value, and a
property over the whole id-shaped space pins every pseudonym inside
`PSEUDONYM_MAX_LEN`.

## Not done here — INT-228 stays open

The acceptance also asks that "the INT-197 workaround (patient row UUID hex as
the segment) is removed". That workaround lives in
`services/api/src/intake_api/documents.py` (`patient_ref` / `patient_pseudonym`
= `patient_id.hex`), and `services/**` was outside this change's territory, so
it is untouched and the issue is not closed by this PR.

Nothing here blocks that follow-up, and the seam is now the right shape for it:
`DocumentStore` accepts any opaque bounded token as `patient_pseudonym`, so the
API can be switched from the patient row's UUID hex to a real tokenizer
pseudonym without the store changing at all. The keys it produces will differ
(a different token derives a different segment), which is a
new-uploads-only change: `presigned_get` signs `DocumentRef.key` as stored, and
the API reconstructs that ref from `row.object_ref`, so documents already in
the store stay downloadable across the switch.

`packages/intake_platform/src/intake_platform/uploads.py` needed no change: the
pipeline forwards `tenant_id` / `patient_pseudonym` / `document_id` straight
through and builds no keys of its own. Its tests changed only where they spell
an object key by hand.
