## What the tests pin

- **Row coverage both ways:** every distinct `sec_row` in issues.yaml has a
  `## `row`` heading in the threat model, and every heading corresponds to a live backlog
  row (drift in either direction fails). Each section must carry all six fields
  (assets, trust boundaries, STRIDE/LINDDUN threats, files/10-cited controls, signals, tests).
- **The linkage gate:** passes a well-formed fixture PR body; fails a missing `Sec-Row:`
  line, a mismatched row, an unfilled template value, an unknown issue, and a row with no
  threat-model heading; an issue without a `sec_row` passes bare or with the `—` marker but
  fails if it claims a row. The real INT-020 → incident-response linkage is exercised
  against the real files. The script's stdlib line-parse of issues.yaml (the `gates` CI job
  has no uv, so plain python3 must suffice) is diffed against `yaml.safe_load` via
  `--dump-rows`, so parser drift is caught in the uv-run test lane.
- **Runbook shape:** the eight required sections (detection sources, severity ladder,
  first 15 minutes, roles, evidence preservation, notification pointers, communications
  rules, post-incident review), the INT-214/2019-10/7545/USOM/DPA pointers, the
  `audit chain (INT-016)` citation, and the ids-only comms rule.
- **Claims scan:** no line of either security document matches performance-claim patterns
  (numeric-percent and the invariant-20 vocabulary) — the spirit of invariant 20 applied to
  docs/security/.
