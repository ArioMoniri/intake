# Evidence — INT-092 · Backend Agent: FIFO Work queue, serialized SessionState, delivery semantics, idempotent

## Acceptance (verbatim from docs/backlog/issues.yaml)

- [x] "one Work in flight per session; results {inline,speech_tr,priority}; duplicates
  impossible (test)"

Test the issue names: `tests/voice/test_work_queue.py` — present, 44 tests.
`depends_on: [INT-081, INT-035]`, both landed.

`sec_row: voice-runtime` — docs/security/threat-model.md "## `voice-runtime` — the agent
worker and its hard boundaries"; files/10 §9 row "Voice intake (runtime)". That row names
**Backend Work queue** as an asset and **Talker ↔ Backend (never awaited)** as a trust
boundary. The threats this issue answers from it: **[D] a stalled Backend blocking
speech** (the queue's whole port is synchronous; the pump is Layer B's own task),
**[E] tool-list growth past the six** (serving a real queue costs the Talker no seventh
tool — asserted), and **[I] transient PCM exposure** (the queue holds no bytes-like
attribute; `retained_frames()` counts rather than claims). Controls built here: FIFO with
one in flight, the double guard, content-addressed idempotency, preempt only from a
rules-engine RED of the session's pinned pack, and refusal — never repair — of a result
that states a number with no `inline` render.

## What was built

`services/voice-runtime/src/intake_voice_runtime/work_queue.py` (new, 181 statements,
100 % statement+branch), plus one enum member on `ports.py` and a docstring correction on
the package `__init__`.

- `WorkQueue` satisfies `WorkSubmitter`, so a `TalkerSession` takes it in place of the
  test double with no change on Layer A. `submit` / `cancel` / `drain_results` are
  ordinary functions; the pump `run_pending()` is **not** on the port.
- `WorkOutcome` is what a handler returns — the *parts* of the result, not a built
  `Presentation`. The queue assembles the `Presentation`, so invariant 22's guard fires
  inside the queue where the refusal can fail the Work, rather than inside the handler
  where it would surface as an ordinary crash.
- `ReadOnlyContext` is what a handler is given: the engine's published snapshot and no
  mutator. Handlers never write `SessionState`; the queue applies the declared effect
  under `_engine_lock` while holding `_queue_lock` — files/03 §4.3's "double guard".
- `WorkRecord` is the delivery receipt of files/03 §4.3. Public fields only, **no
  `session_id` field at all** (files/03 §4.6 invariant 10) and a closed `WorkFailure`
  vocabulary instead of an exception message, because a handler's message can carry a
  transcript fragment (invariant 6).
- `WorkState.COMPLETED_SUPPRESSED` added per files/12 §7.1: a cancel that arrives while
  the Work is running suppresses the **speech**, never the write — "you cannot un-know a
  red flag", so a patient retraction is a supersession, not a deletion.

No metric is emitted. Every emitted metric must exist in
`observability/metrics_catalog.yaml` (invariant 13) and no queue-depth or work-duration
row is catalogued; the module emits none rather than one the catalogue does not know.

- `test_a_missing_handler_fails_the_work_with_a_closed_reason` failed with

  afterwards, so a Work already marked `failed(reason=restart)` would have spoken. The
  emit is now conditional on the record having actually reached `COMPLETED`, which makes
  cancel-while-running and restart-while-running behave the same way by construction:
  the write stands, the speech does not happen.

## What each test proves

**"one Work in flight per session".** `test_only_one_work_is_ever_in_flight` reads
`queue.in_flight_work_ids` from *inside* the handler, on both sides of a yield point, for
three queued Works — six reads, all `1`. `test_two_pumps_racing_never_run_two_works_at_once`
runs three concurrent `run_pending()` calls over eight Works and asserts a peak handler
concurrency of 1 *and* `engine.max_inside == 1`, which is the second half of the double
guard: `SessionState` was never written from two places at once.

**FIFO and no lost or reordered write (files/03 §4.6 invariant 5).**
`test_work_runs_in_submission_order` pins handler order and engine-write order together.
`test_no_slot_update_is_lost_or_reordered_under_interleaved_submission` submits 25 Works
*while the pump is already running*, yielding between each, and asserts all 25 writes
landed in submission order.

**"duplicates impossible".** Four tests, because the sequential case alone is weak:
the same request submitted twice runs once and yields one result; two concurrent
submitters racing two concurrent pumps still run the handler exactly once and drain one
result; a transcript re-submitted after a completion (the restart case files/12 §7.5 is
about) returns the completed ticket and does not run again; and `drain_results` returns
each result exactly once. The mechanism is identity, not locking: `work_id =
sha256(session_id, work_type, step_id, input_hash, protocol_hash)`, so a duplicate is not
a race to win but a record that already exists.

**Results `{inline, speech_tr, priority}`.**
`test_a_completed_work_carries_inline_speech_and_priority` asserts all three fields of
files/03 §4.3's result shape survive the queue, and
`test_a_result_reaches_the_patient_only_at_a_safe_insertion_window` asserts the delivery
rule that goes with them: driven through a **real** `TalkerSession`, the result is not
spoken on a turn where the patient is talking and the Talker is busy, and is spoken on the
first turn where the duplex state opens.

**Only a rules-engine RED may preempt (invariant 9 clause 4; invariant 1).** The
positive control is a RED whose rule id is in the session's pinned pack. Three near-miss
negative controls, same shape, one field different: a rules-engine **YELLOW** claiming
`preempt`, **no determination at all** claiming `preempt`, and an **LLM-originated**
result claiming `preempt` — all three land `FAILED / RESULT_REFUSED` with nothing
delivered. A fourth, `test_a_red_naming_a_rule_outside_the_pinned_pack_is_refused`, is the
copy-a-RED-shape attack: well-formed, correctly typed, refused on provenance
(`PREEMPT_REFUSED`). A fifth asserts an **unpinned** session authorises no preempt at all
— fail closed. And `test_an_llm_originated_result_cannot_even_spell_red` records why the
third of those is structural rather than fortunate: `LlmCandidateTriage.level` is the
literal `"YELLOW_REVIEW"`, so an LLM-derived flag cannot express the level that unlocks
preemption.

**Invariant 22 — numbers never cross a boundary unguarded.**
`test_speech_stating_a_number_with_no_inline_render_is_refused` asserts three things
together, and the third is the one that matters: the Work is `FAILED`, nothing is
delivered, **and `engine.applied == []`** — the result is refused *whole*. Nothing drops
the number, downgrades the speech or stores the slots anyway, because each of those is a
clinical decision wearing an engineering disguise. The paired positive control shows the
identical result accepted once its `inline` render exists, with the slot write landing.
The refusal is ordered ahead of the engine write on purpose: `_produce` builds and
authorises the `BackendResult` before `apply_extraction` is ever reached.

**Invariant 10 — scripts cross the queue verbatim.** Parametrised over a red-flag action
script, an ON_SITE action line and a validated-instrument item, asserting byte equality
between what the handler produced and what `drain_results` returns. The queue is a
conduit: it does not paraphrase, trim, normalise or re-case what it carries. The red-flag
script is written tr-expanded (`"yüz on ikiyi arayın"`, never `"112"`) because by
invariant 22 no numeral reaches a TTS model.

**Invariant 11 — the lanes are nowhere near this.**
`test_the_queue_has_no_observer_lane_surface` asserts the work-type set is exactly
`{extract_slots, plan_follow_ups, parse_document}` and that no public member of
`WorkQueue` names a lane or an observer — there is no seam through which a lane could
write a slot or a triage. `test_a_lane_stalled_thirty_seconds_does_not_delay_the_queue`
is the fake-clock half: a task parked for 30 virtual seconds leaves the queue's completion
time exactly where it was without one. (The full lanes-stalled harness with per-turn
budgets is INT-094; this is the queue's own share of it.)

**Invariants 3 and 6 — nothing leaks.** The public `WorkRecord` is rendered to JSON and
asserted to contain neither the transcript nor the session id, and `WorkRecord` is
asserted to have no `session_id` field at all. A handler that raises with the transcript
in its exception message yields `HANDLER_ERROR` and a receipt that does not contain the
transcript. `retained_frames()` counts bytes-like attributes on the queue — zero.

**Cancellation, restart and the RED seal (files/03 §4.3; files/12 §7.1).** A queued Work
is dequeued synchronously and never runs. A **running** Work is never aborted mid-write:
it completes as `COMPLETED_SUPPRESSED`, its write stands, and its speech never happens. A
late cancel of a completed Work returns the terminal state and does not resurrect it. A
restart marks active Work `failed(reason=restart)` while leaving completed results and
delivery state intact, and the handler finishing afterwards neither walks the record back
to `completed` nor speaks. `seal_for_red()` cancels queued work, leaves the running item
alone (*"it may be the item that produced the RED"*), and refuses further submission.

## Deliberately not built, and why

**The state/background lane split of files/12 §7.4 is not implemented.** It needs six work
types (`confirm_proposed_fact`, `reconcile_meds`, `note_finalize`, `retrieve_records`,
`draft_note_delta`, `score_wellbeing_segment`) and a `ProposedFact` type, and none of the
seven exists anywhere on this branch — a half-built lane would be worse than no lane
(CLAUDE.md invariant 17). What survives of §7.4 here is its load-bearing safety property,
enforced directly and tested: **a `parse_document` result may not carry slot updates**,
because a document's facts reach the record through a confirm step and never through a
write from the work that read the document. The consequence of the missing split is
recorded rather than hidden: **a document parse still occupies the single in-flight slot**,
which is the head-of-line case §7.4's queue arithmetic exists to remove. Not a defect in
this issue's acceptance ("one Work in flight per session" is delivered exactly as
written), but a real follow-up for whoever adds the six work types — it belongs in the
backlog as its own issue, and this file is where it is surfaced.

**The RED preemption path is INT-093.** Only its authorisation gate is called here, and
its queue effect (`seal_for_red`). files/03 §4.6 invariant 4 requires the RED path to
touch no media transport, which is exactly why it is not plumbed through anything here.
The HMAC provenance attestation of files/12 §5 (signing key from OpenBao, nonce,
`inputs_hash`, the seven-way forgery mutation test) is likewise INT-093; nothing in this
module pretends to be it, and nothing here is weakened in its absence — both gates that
can be built today refuse by default.

**No handler ships.** The extraction LLM is files/03 §4.9.1 row 9 behind ADR-006's
gateway (INT-095) and the document parser is INT-12x. The queue takes handlers by
injection, so there is no stand-in on a serving path and every double lives in
`tests/voice/test_work_queue.py` (invariant 17).
