# Evidence — INT-092 · Backend Agent: FIFO Work queue, serialized SessionState, delivery semantics, idempotent

## Acceptance (verbatim from docs/backlog/issues.yaml)

- [x] "one Work in flight per session; results {inline,speech_tr,priority}; duplicates
  impossible (test)"

Tests: `tests/voice/test_work_queue.py`. sec_row: `voice-runtime`
(docs/security/threat-model.md "## `voice-runtime` — the agent worker and its hard
boundaries"). That row already names **"Backend Work queue"** among its assets, the
Talker ↔ Backend boundary ("never awaited") among its trust boundaries, and **"[D] a
stalled Backend blocking speech"** among its threats. This issue is the queue on the
other side of that boundary, and the threat is answered structurally: the queue's
`submit` takes only the bookkeeping lock, so a Backend that never finishes cannot make
the Talker wait.

Module: `services/voice-runtime/src/intake_voice_runtime/clinical_agent/work_queue.py`.

## What this issue is, and what it deliberately is not

**No clinical content was authored.** No threshold, no red-flag level, no Turkish patient
copy. Every id, slot and Turkish string in `tests/voice/test_work_queue.py` is synthetic
(files/04 §7). The authored base pack is INT-043 (`awaiting-human`, HB-C1) and nothing
here needs it, because the acceptance is three mechanisms.

**No production handlers are registered.** The queue is a transport with a typed handler
seam; the `extract_slots` handler is INT-083 and the `parse_document` handler is INT-121.
Submitting a Work type with no handler raises `UnregisteredWorkType` **at submit** rather
than parking an item that could never run — the mechanism is built, the gate fails closed,
the content is left empty (CLAUDE.md invariant 17). Nothing here is a mock: the doubles
live only in `tests/`.

**No triage is computed.** `StateEffect.triage_update` is a `RulesTriageResult` passed
through verbatim from `packages/protocols/triage`; the queue derives delivery class and
priority *from* it and computes no level of its own (CLAUDE.md invariant 1).

## The three acceptance clauses, one at a time

### 1. "one Work in flight per session"

**The serialization mechanism, stated plainly.** files/03 §4.3 names it: *"queue lock +
engine lock — qwen-audio-agent's 'double guard'"*. Two `threading.Lock`s, and which is
which is the whole design:

- `_queue_lock` guards the bookkeeping — the two deques, the record table, the per-lane
  in-flight token, the ready list. It is held for a handful of statements. **`submit`,
  `cancel`, `drain_results` and `depth` take only this one.**
- `_engine_lock` is held across a state handler's entire execution, which is where
  `IntakeEngine` is written.

Collapsing them into a single lock is the tempting simplification and it is the bug: it
would make `submit` block for the whole duration of Backend Work, breaking CLAUDE.md
invariant 9's second clause *in the queue* rather than in the Talker. Mutation F below
records that failure.

Ordering is a single-consumer FIFO per lane. `_claim` pops the head under `_queue_lock`
and takes the lane's in-flight token in the same critical section, so two threads cannot
both claim; a claimed state item then acquires `_engine_lock` **non-blocking**.

**What happens under contention — the question the issue asks to be answered plainly.**

| contending call | behaviour |
|---|---|
| `submit` while a handler runs | returns immediately with a `QUEUED` ticket. It never touches the engine lock, so the running handler cannot delay it. |
| two `submit`s at once | both serialise on the short `_queue_lock`; arrival order under that lock *is* the FIFO order. Nothing is dropped. |
| second `run_pending` while a state Work runs | the lane's in-flight token is taken, so it **claims nothing and returns 0**. |
| `run_pending` re-entered from inside a handler | same — `test_a_pump_re_entered_from_inside_a_handler_runs_nothing`. |
| `run_pending` while `_engine_lock` is held by something else | the item is claimed, the non-blocking acquire fails, and `_unclaim` puts it **back at the head** (`appendleft`) with its state reset to `QUEUED`. `run_pending` returns 0. |

So the loser of a race **refuses**; it never drops an item and never reorders one. That is
the deliberate choice: a queue that silently dropped or reordered clinical Work would be
worse than one that refuses, because the drop is invisible and the refusal is a retry.

**"One Work in flight" means one *slot-writing* Work, and this is the one reading
decision in the issue.** files/03 §4.3 says *"only one Work in flight per session"*.
files/12 §7.4 — written later, in a section headed "Voice-runtime fixes" — splits the
queue into a `state` lane that *"holds the engine lock and is strictly FIFO"* and a
`background` lane that is *"concurrent and structurally cannot write slots"*, and files/12
§7.3 gives the reason: the split exists **to remove the head-of-line case where a RED sat
behind a `parse_document`**. Honouring files/03's sentence literally would reintroduce the
exact defect files/12 fixed.

What the sentence *protects* is files/03 §4.6 invariant 5, *"no lost or reordered slot
updates"*, and that is protected exactly:

- the state lane is strictly FIFO with **one item in flight**, asserted by
  `test_at_most_one_state_work_is_in_flight` (a handler reads `agent.in_flight` from
  inside itself and sees exactly one id, its own, on every turn);
- the background lane cannot write slots because it is never handed anything that could —
  `ReadOnlyContext` has fields `{request, snapshot, is_cancelled}` and no engine, pinned
  by `test_background_work_cannot_reach_the_engine_at_all`. This is files/12 §9
  invariant 21 as a shape rather than as a rule.

`LANE_OF` declares the lane of every `WorkType` and a test asserts the map is total: a
Work type with no lane could not be routed, and a lane inferred at runtime would be a
guess about whether the Work may write slots.

**RT-05, the fast talker.** files/04 §7 asks for *"five answers submitted in 3 s — FIFO
order preserved, one Work in flight, final slot state identical to sequential run"*.
`test_the_final_state_matches_a_sequential_run` submits five answers from five threads
released together on a `threading.Barrier` and compares the engine's final answer states
and values against the same five run one at a time. No test sleeps.

### 2. "results {inline, speech_tr, priority}"

The result is INT-091's `BackendResult{work_id, state, delivery_class, presentation,
priority}` with `Presentation{inline, speech_tr, speech_numerics, triage_update,
candidate_flags}` — reused rather than re-declared, so the Talker's
`accept_result`/insertion scheduler needs no adapter.

**Priority is derived, never requested — this is the invariant 9 clause 4 answer.**
Neither `StateEffect` nor `BackgroundEffect` has a `priority` field, so `preempt` is not
something a handler can *ask for*. `_delivery_of` derives both axes from the
determination:

| determination | delivery class | priority |
|---|---|---|
| `RulesTriageResult` level `RED` | `RED` | `PREEMPT` |
| `RulesTriageResult` level `YELLOW` | `TRIAGE_YELLOW` | `NORMAL` |
| anything else | the handler's `EffectClass` | `NORMAL` |

Four gates stack, and each closes a different door:

1. **The effect types have no `priority`.** A handler cannot spell the word.
2. **`BackgroundEffect` has no `triage_update` field at all.** The lane that runs
   concurrently cannot reach the RED branch. LLM material leaves it as `candidate_flags`
   — clinician-facing text, never a level (CLAUDE.md invariant 1).
3. **`EffectClass` is `{clinical_info, routine}`.** `DeliveryClass` also has `RED` and
   `TRIAGE_YELLOW`; neither is spellable by a handler, so a Work cannot elect itself into
   a protected delivery class either.
4. **Provenance.** A derived preempt goes through INT-091's `authorise_preempt`, so a RED
   naming a rule outside the session's pinned pack is refused, and an unpinned session
   (`rule_ids=frozenset()`) can never preempt.

On a refused preempt the Work **fails**; it is not downgraded to `normal`. Downgrading
would speak a RED as routine, which is the worse error, so the queue emits a `FAILED`
receipt with an empty presentation and counts it in `work_failed_total`. This gate is a
second line: `TalkerSession.accept_result` calls `authorise_preempt` too, and in
production the Talker's copy should now never fire.

**A handler fault is a receipt, not a crashed pump.** files/03 §4.3 makes Work records
delivery receipts and §4.3's delivery paragraph requires that *"one malformed result
cannot block later ones"*. A raising handler, and a `Presentation` that CLAUDE.md
invariant 22 refuses (speech states a numeric slot with no matching `inline` render), both
land as `FAILED` with the exception's class name in `WorkRecord.error` — never the message,
which could quote patient text.

### 3. "duplicates impossible (test)"

Two distinct duplicate classes, both closed:

- **A re-submitted transcript.** `work_id = work_key(request)` is content-addressed
  (files/12 §7.5), so a restart re-submitting the same transcript produces the *same* id.
  `submit` looks the id up first: an existing record returns its **current** ticket and
  the item is not queued again. A completed Work therefore returns `COMPLETED`, is never
  re-executed, and re-runs nothing — `test_a_completed_work_is_never_re_executed` asserts
  the engine's slot value is still `1`, not `2`.
- **A re-drained result.** `drain_results` moves the ready list out under the lock, so a
  result appears exactly once; `_settle` appends exactly once per Work.

`test_no_work_id_ever_executes_or_is_delivered_twice` is the property behind the clause:
Hypothesis generates arbitrary interleavings of `submit` / `run_pending` / `drain_results`
over the five synthetic steps and asserts the executed set and the delivered set each
contain no repeats, and that the two agree.

## Delivery semantics (the title's fourth word)

- **Lifecycle** is files/03 §4.3's `queued → running → completed | failed | cancelled`.
- **`cancelled` is reachable** (files/12 §9 invariant 32). A queued item is dequeued
  synchronously and never runs.
- **A running state Work is never aborted mid-write** (files/12 §7.1): *"if it has
  committed, the write stands (you cannot un-know a red flag) and the effect is
  `COMPLETED_SUPPRESSED`"*. `cancel` on a running item records a suppression rather than
  aborting; the Work completes, the committed engine write stands, `inline` still reaches
  the rail, and only `speech_tr` is dropped. That is a supersession, not a deletion.
- **Suppression never applies to a preempt.** `test_cancelling_cannot_suppress_a_rules_engine_red`
  cancels while a RED is in flight and asserts the RED still arrives with its speech.
- **A running background Work honours a cooperative token** — `ReadOnlyContext.is_cancelled`,
  the only cancellation channel it has.
- **On RED the queue is sealed** (files/12 §7.1): every queued item in both lanes is
  cancelled and further submissions raise `QueueSealed`. files/12's allowed set
  `{note_finalize, clinic_notify, audit_flush}` has **no member in `WorkType` on this
  branch** (see the findings below), so the seal currently admits nothing at all. When
  those Work types exist they are added to the seal, not worked around.

The ladder itself — natural / relaxed / interject / expired, and the transactional
undelivered-note flag — is INT-091's `InsertionScheduler` and is untouched here. This
queue produces the `BackendResult`s that scheduler consumes.

## Invariant 6 — the queue is PHI-free by construction

`WorkRequest` carries `input_hash`, not the transcript. There is no field on a
`WorkRequest`, a `WorkRecord`, a log line or a metric label that patient text could
occupy, so this is structure rather than redaction. Three consequences, all tested:

- `WorkRecord`'s fields are exactly `{request, state, enqueued_ms, started_ms,
  finished_ms, error}` — ids, a closed enumeration, clock readings, an exception class
  name.
- `cancel(work_id, reason)` accepts the tool signature's `reason` and **deliberately does
  not record or log it**: it is free, patient-supplied text. The test passes the synthetic
  transcript as the reason and asserts it appears in no log record.
- The three metrics carry one label, `type`, whose domain is the closed `WorkType`
  enumeration. No session id, no step text.

## Findings — where the blueprints disagree with each other or with what is built

These matter more than the code, so they are written down rather than worked around.

1. **files/03 §4.3 "only one Work in flight per session" contradicts files/12 §7.4's
   concurrent background lane.** Resolved above in favour of files/12, which is the later
   "Voice-runtime fixes" section and carries a numbered invariant (§9 inv. 21) with a
   test. **files/03 §4.3's sentence should be amended in place** the way §4.4 and §4.5
   were, or the next reader will implement a single global FIFO and put a RED back behind
   a `parse_document`.

2. **Five of the eight Work types files/03 §4.3 names have no `WorkType` member.**
   §4.3 lists `extract_slots, evaluate_triage, plan_follow_ups, parse_document,
   retrieve_records, score_wellbeing_segment, draft_note_delta, reconcile_meds`;
   INT-091's enum has three. `evaluate_triage` is correctly gone (files/12 §7.3 deletes
   it), but the other four are simply absent, and files/12 §7.4 assigns lanes to work
   types that do not exist. The visible consequence is that **`_seal`'s allowed set
   `{note_finalize, clinic_notify, audit_flush}` is empty**, so on RED the queue admits
   nothing at all rather than the three things files/12 says it should still accept. That
   is the fail-closed direction, and it is a gap, not a design.

3. **`WorkRequest` has no payload channel, so `extract_slots` cannot reach its
   transcript.** files/03 §4.2 declares `submit_utterance(session_id, step_id,
   transcript, …)` and §4.3 declares `extract_slots(step_id, transcript)`, but INT-091's
   `WorkSubmitter.submit(request)` carries only `input_hash`. Deliberately not fixed here:
   the route by which patient text crosses into extraction is a **data-boundary** decision
   (delimited, schema-constrained — CLAUDE.md invariant 14) and it belongs to **INT-083**,
   whose acceptance is exactly that boundary. It is recorded because it is invisible until
   someone tries to write the first real handler. The side benefit is that this queue is
   PHI-free by construction, and INT-083 should preserve that property rather than adding
   a `transcript` field to `WorkRequest`.

4. **`engine_version` is written and never read.** files/12 §7.2 says *"`submit_utterance`
   carries `engine_version` back"* so Layer B can detect a stale read. `NextStep` carries
   it, `TalkerSession.submit_utterance` copies it into `WorkRequest`, and **nothing
   consumes it**: INT-081's `apply_extraction(step_id, slot_updates,
   clarification_needed)` has no version parameter, and staleness is handled instead by
   the engine's own `invalidated` list. The field is correct and currently inert; the
   staleness check §7.2 describes does not exist. Handlers receive it through
   `StateContext.request`, so INT-083 is where it becomes live — or where it is decided
   that the `invalidated` list subsumes it and the field is removed.

5. **files/03 §5 puts the turn budget inside the engine; INT-081 has no budget.** §5 says
   *"Turn budget: fast ≤ 18, detailed ≤ 45"* and files/13 §9.4 specifies a budget governor
   that filters step classes 6–8 as the budget runs down. `SessionBudget{turns_used,
   turns_remaining}` exists in `clinical_schemas.session` from INT-031 and is wired to
   nothing. INT-081's `must_ask_coverage` reuses the governor's own obligation set
   (`R = must_ask steps unasked whose gate is TRUE or UNKNOWN`) for coverage but does not
   implement the governor. So the harm files/13 §9.4 names —
   *"an 18-turn cap that can silently drop a must-ask"* — currently has no cap to enforce
   and no code to drop anything, which is safe today and becomes unsafe the moment a cap
   is added anywhere but the engine. There is no backlog issue whose acceptance names the
   budget governor.

   Two smaller notes on the same section, both cases where INT-081 is right and files/03
   §5 reads wrong: §5 names a fixed nine-section chain `identity_check → … → wrap_up` as
   though the section order were architectural, while `build_plan` correctly derives
   sections from the resolved pack; and §5's *"Persisted as openEHR `COMPOSITION` … plus
   FHIR `QuestionnaireResponse`"* contradicts files/00_STATE D8, which cut openEHR to a
   P3 export. 00_STATE wins, and §5 has not been updated.

6. **`tests/security/test_otp_abuse.py::test_per_phone_limit_three_per_hour` is a
   wall-clock flake in a security gate — pre-existing, and unrelated to this change.**
   `auth_store._window_key` buckets the rate-limit counter by `int(now // 3600)`, an
   **absolute** hour bucket rather than a sliding window, and the test's `Clock` starts at
   the real `int(time.time())`. The test advances `RESEND_COOLDOWN_S + 1 = 61 s` three
   times, spanning 183 s, so whenever the suite starts within 183 s of an hour boundary —
   183/3600 ≈ **5.1 % of runs** — the three admitted requests straddle two buckets, the
   counter never reaches `PHONE_LIMIT_PER_HOUR = 3`, and the fourth request returns 202
   instead of the asserted 429. Deterministic reproduction:
