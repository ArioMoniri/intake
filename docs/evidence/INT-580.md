## What was built

**One tr source for the copy (rows 29, 30).** `services/api/src/intake_api/sms_copy.tr.json` is
the only place the words live:

> `Önvizit doğrulama kodunuz: {code}. Bu kodu kimseyle paylaşmayınız.`

It keeps INT-329's wording, adds the app's name, uses the siz register with `-iniz` for the
instruction, and has `{code}` as its only slot. `intake_api.sms_copy` loads it and refuses a body
without exactly one slot. Twilio's `SMS_TEMPLATE` is the copy itself; Netgsm's is the copy folded
to ASCII (`Onvizit dogrulama kodunuz: …`), because the OTP product refuses Turkish letters. A
test runs the copy through PolicyGuard on the dynamic path in the siz register: no violation,
nothing dropped. Its near miss, the same words in the sen register, is refused. The template test
removes the app name and the code from every rendered message and asserts that what is left
carries no digit, no link or address, and no unfilled slot. The checker has its own near miss: a
variant with a link and a second number is flagged. Every Netgsm message is ASCII and within one
155-character segment for codes of 4, 6 and 10 digits, with and without a domain line.

**The app name.** The product is Önvizit (the owner's naming, INT-420 and INT-495;
`docs/release/production-checklist.md`), and since INT-420 merged the app's config says so too.
The SMS names the product the owner named.

**The domain-bound line (row 31), built fail-closed.** WebKit's domain-bound code format puts
`@<domain> #<code>` on the message's last line. iOS then offers that code only inside an app
entitled to `<domain>`, never on a look-alike site. `sms_copy.associated_domain` reads the domain
from the app's own entitlement, `expo.ios.associatedDomains` in `apps/mobile/app.json`, and from
nowhere else: `ApiSettings.mobile_app_config_path` has no environment override. It returns a
domain only when:

- there is exactly one `webcredentials:` entry (an `applinks:` entry does not count);
- the entry is a public DNS name: two or more labels, letters, digits and hyphens, no
  developer-mode `?mode=` suffix, no IP literal, no single label;
- the longest message (a ten-digit code, folded) still fits one segment.

Anything else returns None, the reason is logged by name, and no line is sent. A wrong line would
steer the autofill somewhere; no line only forgoes it. Netgsm's adapter takes the domain at wiring
(`otp_delivery_from_settings`) and `seal_otp_request` appends the line. The API image now carries
`apps/mobile/app.json` (`infra/staging/Dockerfile.api.dockerignore`), so the line starts going
out the day the app gains the entitlement, with no other change. **Today the shipped app
declares none, so no line is sent, and a test pins that.**

**The new-device signal (row 32).** On every successful verify, `_note_device` records the
device the verify proved: the App Attest key, or the install id in dev, as a keyed hash under the
OTP pepper (`rate_key("known_device", …)`). It goes into the account's set,
`auth:otp:devices:<patient id>`, which lives for a refresh-token lifetime (30 days). That is the
class of datum INT-344 already keeps for a session (a key and a counter), so no new category of
personal data is persisted. A sign-in is **new** when the account has signed in from at least one
device before and never from this one; an account's first sign-in has nothing to compare
against and is not new. A new one is:

- counted, as `sec_new_device_logins` (the files/08 §4 id, now live);
- written to the hash chain as `auth.login.new_device` under `patient:<id>`, which the patient's
  access log projection already classes as account security;
- handed to the notice channel, `AuthWiring.sign_in_notice`.

That is the event a phished code entered on a thief's phone produces, and the event a SIM swap's
first sign-in produces.

**The notice channel fails closed.** No channel to the patient exists. Netgsm's OTP product is
for codes, not notices, and patients have no push tokens on this path. So the only channel today
is `NoSignInNoticeChannel`: it delivers nothing and logs that it did not. The signal does not
depend on it.

**The passkey step-up (row 33) moved to INT-582 (#981).** Patients have no passkeys. Building
them needs a WebAuthn verifier in the API and a passkey module in the app, each licence-verified;
a decision to persist patient credential public keys (CLAUDE.md, "when to stop and ask"); and the
list of patient actions sensitive enough to step up. A gate built without them could only refuse
those actions for everyone. The orchestrator allocated INT-582 on 28 Oct 2026, and its row is in
this PR. The owner approved it the same day as D36 (files/00_STATE.md, recorded by INT-585,
#984): patient passkey public keys may be stored, and issuing a Doctor Link, changing the phone
number, data export and data delete step up. The row is therefore `todo`, not `awaiting-human`,
and this PR closes #975: the orchestrator recorded on #975 that its passkey clause moved to #981.

## After the security review (28 Oct 2026)

**D34: the domain-bound line is on.** The owner chose the synthetic host for the iOS OTP
autofill domain (D34, files/00_STATE.md, "1Y"; recorded by INT-585, #984). `apps/mobile/app.json`
now declares `"associatedDomains": ["webcredentials:3-211-2-143.sslip.io"]`, so
`sms_copy.associated_domain` finds exactly one valid public name and every OTP SMS ends
`@3-211-2-143.sslip.io #<code>`, still one ASCII segment for codes of 4, 6 and 10 digits. No code
changed for that: the mechanism built fail-closed above reads the app's config.

**The host serves the association file.** iOS honours the line only when the domain names the
app back in `/.well-known/apple-app-site-association`, fetched over HTTPS as JSON, following no
redirect. The Caddyfile gains one route for that path (a `handle` that serves the one file from
`/srv/well-known` as `application/json` with `file_server`; everything else still goes to the API
in a `handle` of its own), and `compose.yaml` mounts the host's `/etc/intake-staging/well-known`
into the edge read-only. `write_aasa` in `infra/staging/lib.sh` renders
`{"webcredentials":{"apps":["<team id>.<bundle id>"]}}` on every deploy, before the edge is
recreated.

**The team id is not in the repository**, and it is not invented. It is the Apple App ID prefix
the operator types into the host's env file (`INTAKE_APP_ATTEST_TEAM_ID`, `app_attest_env.sh`,
INT-528), the same value App Attest verifies against; the bundle id is the env file's
`INTAKE_APP_ATTEST_BUNDLE_ID`, else the app's committed `com.ariomoniri.intakemobile`. Both are
checked against `intake_api.app_attest`'s shapes before they are printed into the JSON. With no
team id, or a malformed one, `write_aasa` writes no file (and removes a stale one), logs why, and
the route answers 404: the SMS line still goes out, and iOS simply offers no autofill. The host
serves the file once the operator has set the App Attest team id there, which App Attest needs
anyway.

**The device set's inventory row.** `auth:otp:devices:<patient id>` is personal data with no
column, so it is an off-schema flow of the data inventory (`intake_platform.store.facts`,
`sign_in_devices`): category `pseudonymised_identity`; purpose, telling a new device from a known
one for account security; basis `BASIS_LEGAL_OBLIGATION` (KVKK m.5/2-ç with m.12, confirmed by the legal review of 30 Oct 2026 unless counsel rules the sign-in number m.6 data; the security
obligation the audit chain already rests on); retention 30 days after the last sign-in (the key's
expiry is `REFRESH_TTL_S`); recipients internal only. The basis is engineering's reading of an
existing constant, for the legal lane to confirm. The store labels are generated from the same
row.

**The stale brand reference** (this file, "The app name") is corrected now that INT-420 has
merged; `tests/release/test_brand_name.py` would otherwise fail on it.

## Legal review fixes (30 Oct 2026)

The legal review returned REVISE with one item on this PR (B1): the SMS that actually ships was
never tested, and run through the tr PolicyGuard whole it fails. The guard splits it into three
sentences against `MAX_SENTENCES_PER_TURN = 2` and drops the WebKit line (`TOO_LONG` on
`@3-211-2-143.sslip.io #<code>`).

The WebKit line is a machine-format token (D34) outside PolicyGuard's prose scope: PolicyGuard
covers the body, and a test pins that the body is the only prose. `_shipped_parts` renders the
message exactly as the Netgsm and Twilio adapters do, with the domain the shipped app config
yields, and splits it at the last blank line: the tail must be exactly the bound line, and the
head must equal the message rendered with no domain, so the line is the only addition.

- `test_the_shipped_sms_is_the_body_plus_the_bound_line_and_nothing_else` (the reviewer's): for
  the Unicode and the ASCII-folded message, the body says the code and the app name and nothing
  else: no other digit, no link shape, no `@`.
- `test_the_shipped_sms_body_passes_policyguard_in_siz` (the reviewer's): the shipped body passes
  the tr guard in siz with no violation and nothing dropped.
- `test_the_guard_would_drop_exactly_the_machine_line` (near miss for the scope): the whole
  message through the guard loses the line and nothing else, which is why the guard runs on the
  body.

These pin a boundary rather than change behaviour, so all three passed on their first run; the
code is unchanged. **"No links" has the D34 exception:** Android linkifies the domain in the
bound line. The owner chose the line, and the domain is the only link-shaped text an SMS may
carry (acceptance table below).

**The device set's basis is confirmed, on condition.** The same review confirmed
`BASIS_LEGAL_OBLIGATION` (KVKK m.5/2-ç with m.12/1) for the device set; it is re-decided if
counsel rules the sign-in number is m.6 data. The question is now in INT-535's
`aydinlatma.app` row (`docs/legal/synthetic/documents.yaml`): the device set, the
`auth.login.new_device` row and the OTP `auth.*` audit rows are what the app's notice must also
describe.

## What this does not stop

- **A SIM swap**, on its own: whoever holds the number receives the code. The new-device signal
  records it and, once a channel exists, tells the patient. The passkey step-up that would make
  the number insufficient is INT-582.
- **A patient who reads the code out to a caller**, while no notice channel exists; the copy says
  not to share it. The domain line keeps iOS from autofilling it into a look-alike page, but a
  code read aloud or typed by hand bypasses autofill altogether.
- **The domain line before the host has its team id.** Until the operator sets
  `INTAKE_APP_ATTEST_TEAM_ID` on the synthetic host, the association file is not served and iOS
  offers no autofill for the line (the code still arrives and can be typed).
