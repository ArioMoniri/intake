# INT-467 — a pool of three ephemeral intake-aws-ci runners, each isolated as runner 1 is

GitHub #799 · Sec-Row `cicd` · phase P1 · 3 Oct 2026 · follow-up to INT-463 (#790, PR #791)

**Why.** One runner, `intake-aws-ci-1`, serializes every PR's 13 jobs. The
host check of 3 Oct 2026, 18:01 UTC, with staging and one job running, showed
about 66 % CPU idle on 8 vCPU and 25 GiB of RAM available. A second runner was
not a config change:
- Every runner would share one user (`ghrunner`) and one rootless daemon, and
  `cycle.sh` cleanup removes every container, volume and network of that
  daemon. One runner's post-job wipe would destroy the other's live job.
- check-integration publishes fixed host-loopback ports (5432, 8200, 9000/9001,
  3310, 8091, 8092) through rootlesskit's builtin port driver. Two concurrent
  runs from two PRs collide.

**What this PR delivers.**
- **One identity per runner.** Every runner N of `POOL_INSTANCES` (1 2 3)
  derives its own identity in `guard.sh instance_env`, and nowhere else:
  - user `ghrunnerN`, with subordinate range `165536 + (N-1) × 65536`;
  - CI root `/opt/dlami/nvme/intake-aws-ci-N`;
  - a rootless daemon under `/run/intake-aws-ci-N`;
  - egress chain `INTAKE-AWS-CI-OUT-N`, matched on that user;
  - network namespace `/run/netns/intake-aws-ci-N`.
- **Templated units.** The units are `intake-aws-ci-{runner,job,dockerd,diskwatch}@.service`
  and `intake-aws-ci-diskwatch@.timer`. All instances share the one
  `intake-aws-ci.slice` ceiling, so the pool never takes more from staging than
  one runner could.
- **Its own network namespace.** Each job runs in its rootless daemon's
  network namespace, as its own uid (see "The design, evaluated on the host"
  below).
  - rootlesskit's port driver is `none`, so a published port exists only in
    that namespace.
  - `guard.sh N netns` attaches the namespace and proves it before every
    registration.
- **Peer denial.** Every runner is ACL-denied every other runner's CI root and
  Docker run directory, and the single-runner tree. The guard proves the
  denial as that runner's user, like the staging paths.
- **The installer.** `install.sh` drains every running supervisor before
  replacing a script: each stops once it holds no `Runner.Worker`, because bash
  reads a running script by offset. It then removes the INT-463 single-runner
  layout before it creates `ghrunner1`, which takes that layout's subordinate
  range.
- **Renovate** (owner patch, see "Green run"). `.github/renovate.json` follows
  the probe image, which is pinned by digest in `runner.conf`.
- **The probe.** `probe.sh` and `scripts/ci/aws_runner.sh probe` measure every
  runner as INT-463 measured runner 1. They run as that runner's user, in a
  transient unit built from every `[Service]` line of the job unit, while every
  runner publishes the same port.

## The design, evaluated on the host (3 Oct 2026, 19:15–19:35 UTC, over SSM)

The design to evaluate proposed running the job inside rootlesskit's child
netns with `nsenter`, as uid 0 in the user namespace, with
`RUNNER_ALLOW_RUNASROOT`. It was measured with the identity runner 2 will use
(`ghrunner2`, uid 994, subordinate range 231072:65536), next to the live
runner 1, which was not touched.

**The host.** Docker 29.8.1, rootlesskit 3.1.0, slirp4netns 1.2.1, systemd 255,
kernel 7.0.0-1013-aws.

**`dockerd-rootless.sh` defaults to detach-netns.**
- The daemon itself stays in the host namespace: `dockerd` is in
  `net:[4026531833]`, which is PID 1's.
- Its containers live in a detached namespace. The rootlesskit child is in
  `net:[4026533574]`, the inode of `$XDG_RUNTIME_DIR/dockerd-rootless/netns`.
- That namespace's only uplink is slirp4netns, a host process of the runner's
  uid. So the owner-match egress chain sees everything that leaves it.

**Port driver `none` works.**
- `docker run -p 127.0.0.1:15432:8080` succeeded, and `docker port` reported
  `127.0.0.1:15432`.
- The host had no listener on `:15432`.
- Inside the detached namespace, `ss` showed `LISTEN 127.0.0.1:15432`.

**A systemd unit can join that namespace without entering the user namespace.**
`ip netns attach` bound the child's namespace at `/run/netns/intake-aws-ci-2`.
A unit with `NetworkNamespacePath=` set to it ran as `ghrunner2`, with the
measurements below.

| from the joined unit, as ghrunner2 (uid 994) | result |
|---|---|
| 127.0.0.1:15432, the container's published port | **reached** (httpd answered) |
| DNS through `nameserver 10.0.2.3` (bound over /etc/resolv.conf) | **reached** (api.github.com → 140.82.113.5) |
| https://api.github.com/zen | **reached**, HTTP 200 in 0.025 s |
| 169.254.169.254:80, the metadata service | blocked |
| 10.0.2.2:22 and :443, the host loopback through slirp4netns | blocked |
| 127.0.0.1:443 and :22 | blocked (the namespace's own loopback; the host's listeners are not in it) |
| staging Postgres 172.18.0.4:5432 and OpenBao 172.18.0.2:8200 | blocked |
| 172.31.0.2:53, the VPC resolver | reached, as for runner 1: the chain allows the upstream resolvers on port 53 |

The same user in the host namespace (runner 1's path today) also could not
reach `127.0.0.1:15432`: nothing on the host listens there.

**The two ways in, compared.**

| | A: `nsenter -U -n --preserve-credentials` (proposed) | B: `NetworkNamespacePath=` (built) |
|---|---|---|
| uid the job sees | 0 (`root`) | 994 (`ghrunner2`) |
| CapEff | `000001ffffffffff`, every capability in the user namespace | `0000000000000000` |
| runner registration | `config.sh` refuses uid 0 without `RUNNER_ALLOW_RUNASROOT` | unchanged |
| file permission checks | capabilities over every file whose owner maps into the user namespace | ordinary DAC and ACLs |
| file view | the job unit's sandbox (no `-m`) | the job unit's sandbox |

B was built. One measurement belongs in both columns. In B, `ip link add`
inside the namespace still succeeded with CapEff 0. The kernel gives the uid
that created a user namespace every capability over the namespaces it owns,
whether or not it has entered them.
- **That is not new.** Runner 1's job has the same power today, through
  `nsenter`. It is inherent to rootless Docker.
- **It does not open a way out.** The namespace's only uplink is
  slirp4netns, and whatever leaves through it is a host socket of the runner's
  uid. `guard.sh net` keeps the full owner-match chain, the host-loopback
  rejects included, because the uid can still act in the host namespace through
  its own daemon. It gives no power over another runner's namespace or over
  the host's.

Everything the experiment started was stopped: the transient daemon, the probe
units and the namespace attachment. No `ghrunner2` process remains. What it
left is listed under "The host install".

## The host install — not run

`scripts/ci/aws_runner.sh install` was refused by this session's permission
classifier, so nothing on the host runs the pool. The acceptance lines that
need the host are therefore open:
- every runner's isolation, measured by the probe;
- jobs picked up by more than one runner;
- two concurrent check-integration jobs on two runners.

The issue stays `awaiting-human` (docs/backlog/blockers.md, HB-I7).

**State of the host now.**
- **Runner 1 (INT-463) is unchanged** and keeps serving every job:
  `intake-aws-ci-1`, online and idle at the last check.
- **The experiment left three inert things,** all of which `install.sh` adopts
  as runner 2's own, since they use the same uid range:
  - user `ghrunner2`: uid 994, subordinate range 231072:65536, locked password,
    `nologin`, no group but its own;
  - its egress chain `INTAKE-AWS-CI-OUT-2`, a copy of runner 1's 15 v4 and
    11 v6 rejects, with its `OUTPUT` jump;
  - `/opt/dlami/nvme/intake-aws-ci-2`, whose image store holds
    `busybox:1.37`.

  No process runs as `ghrunner2`.

**What the install does, in order** (the owner step):
1. Drains every running supervisor.
2. Removes the single-runner layout: its units; its chain, removed by numeric
   uid; its ACL entries; `ghrunner` and its subordinate range; its tree.
3. Creates `ghrunner1` and `ghrunner3`, and adopts `ghrunner2`.
4. Installs the scripts and units, then runs every runner's guards.
5. Starts each daemon, proves each namespace, and starts
   `intake-aws-ci-runner@1..3`.

**What it measures, and how.**
- `scripts/ci/aws_runner.sh probe` writes, per runner, one `ok` or `FAIL` line
  for each property in the acceptance:
  - the staging paths and `openbao-init.json`;
  - the host Docker socket, from the job and from a container;
  - the metadata service, every staging container port and every host
    listener, on the host IP, `10.0.2.2` and `127.0.0.1`;
  - root-disk writes, and bind mounts of the staging paths and of `/`;
  - every other runner's tree, socket and published port;
  - DNS, public HTTPS, rootless Docker, and its own `127.0.0.1:15432`
    answering with its own name while the other runners publish the same port.
- The GitHub API then shows the jobs of a PR spread over `intake-aws-ci-1..3`.
- Two check-integration runs overlapping in time show the fixed ports not
  colliding.

## Limits, stated rather than hidden

- **One ceiling for three runners.**
  - The slice keeps INT-463's numbers: CPUQuota 600 % and MemoryMax 16G, for
    the whole pool.
  - Its `memory.peak` with one runner was 11.8 GiB, read on 3 Oct 2026 just before the experiment.
  - So three memory-heavy jobs at once meet `MemoryHigh` (14G) throttling, and
    at worst an OOM kill inside CI, never in staging.
  - The concurrent run is the measurement. If it fails, `POOL_INSTANCES="1 2"`
    is the one-line answer, and the ceiling is not raised without the owner.
- **Three image stores.** Each daemon keeps its own image store. So the first
  check-integration on each runner pulls its seven images again, within Docker
  Hub's anonymous limit.
- **Run the probe on an idle pool.** It runs beside the live runners, and a
  runner's post-job wipe removes the probe's container and process with the
  job's.
- **The owner's capabilities over a runner's own namespace.** A job holds
  them, as every rootless-Docker user does (see above). Its way out is still
  only slirp4netns and the owner-match chain.
- **Residency.** As for INT-463, this pool is in us-east-1. The TR-DC pool
  stays open under HB-I7 and HB-L11.
