# INT-604: an exclusive "Yok", answers anchored to the answering day, and a visit-mode question that asks one thing

**Date:** 17 November 2026 · **Branch:** `int-604-question-wording` · **Issue:** #1029 ·
**Sec-Row:** files/10 §9 `clinical-content` · **ADR:** ADR-043 · **Source:** design audit 2026-11,
Part B M1–M3 · **Label:** `approval:human-clinical` (kept for the physician's later signature)

## Acceptance (verbatim, GitHub #1029)

1. A multi-select option can be declared `exclusive: true` in the DSL. Selecting it clears the others, and selecting another option clears it. An ADR records the DSL change. Every "Yok"/"Hiçbiri" option in served-candidate packs is marked exclusive. Golden tests include a near-miss negative control.
2. Questions that say "bugün" or other day-relative words are anchored to the time of answering, not the visit date: either the wording is made explicit (e.g. "şu sıralar") or the anchor is stated. The `text_tr` changes follow invariant 10 and are listed for `approval:human-clinical`.
3. The visit-mode question asks one thing. Location (REMOTE / ON_SITE / UNKNOWN) feeds the RED location axis only from an unambiguous answer, and an ambiguous answer resolves to UNKNOWN. A golden test proves a preference answer can never set ON_SITE.
4. `make safety` is green, and red-flag rules stay monotonic (invariant 7).

## 1. M1: the exclusive option

**DSL (ADR-043).**
- `Slot.multiple: bool` declares a code slot multi-select.
- `Slot.options: {<member>: ChoiceOption}` carries per-option attributes, with `ChoiceOption.exclusive: bool`.
- The schema refuses `multiple` or `options` on a non-code slot, `exclusive` on a single-select slot, and two exclusive options on one slot. ADR-043 allows no exception.
- The compiler (`protocols.compile.choice_options`, run by `resolve_protocol` beside `gate_values`) refuses:
  - `OPTION_OUTSIDE_CHOICES`: an option key that is not a member of the value set;
  - `NONE_CHOICE_NOT_EXCLUSIVE`: a multi-select "yok"/"hiçbiri" that is not marked exclusive. The match is on the whole choice: "belli bir saati yok" is a near miss and passes.

**Pack.** base.intake `chest_pain.radiation` is the input of both active chest-pain rules. It is now `multiple: true` with `yok` exclusive. No rule changed.

**Server binding.**
- `protocols.choices.bind_choice_set` refuses a set that holds the exclusive member beside another member. It never trims one. Its production caller is the voice runtime's extraction parser. This was wired in clinical review round 1; the first commit had no caller, and this section claimed a refusal that did not yet exist.
- The triage hop reads a submitted chips answer whole, through `submitted_set_answer`. One member is that member. Several members are the files/12 §7.3 union, so any member that fires, fires. This also fixes a defect: before, a list reached the engine as one value, which reads Unknown, so a symptom chosen among several could never fire. The red run below shows it.

**Lanes.** Both lanes call one rule, `toggleOption`, on every tap:
- the typed lane (`intake.tsx` `toggleChip`);
- the dialogue lane (`DialogueIntake.tsx` chips).

The rule: "Yok" replaces the selection, any other option clears "Yok", and a tap on a selected option removes it. It runs on the on-screen selection, before submit.

A suggested set holding both a symptom and "Yok" is reconciled before it is shown, by `reconcileExclusive`: the symptom is kept and "Yok" is dropped. This covers a voice candidate (`stream.ts`, for both the local read and the extractor) and a typed prefill. A suggestion can therefore show the patient more than "Yok", never less.

All 13 chips "Yok" options in the app packs are marked `exclusive: true`. The app has no chips "Hiçbiri".

**Triage sees only the final submitted set** (`exclusive.test.ts`):
- the taps before submit never reach the note, and the triage request carries exactly the submitted set;
- a set that bypassed the lanes reaches the request whole;
- `tests/safety/test_exclusive_choice_triage.py`, on the served `base.life_threat.yaml`:
  - `["kol"]`, `["omuz","çene"]` and `["sırt","boyun"]` fire the K2 cardiac RED;
  - `["yok"]` alone does not (near miss; the SARI sibling fires instead);
  - `["omuz"]` alone does not (near miss);
  - `["kol","yok"]` in either order still fires the RED;
  - the binder refuses that same set rather than trim it.

## 3. M3: the visit-mode question asks one thing

**The finding.** The old question "Nasıl ilerleyelim?" offered "Hastanedeyim" (a place) beside "Kısa tutalım" (a preference). Its answer feeds `apps/mobile/src/lib/red/location.ts` `deriveRedLocation`, the RED location axis that `RedLayer.tsx` hands the rules-engine hop. Two consequences:
- a patient in the corridor who wanted it short picked the REMOTE-eligible answer;
- a patient at home who wanted detail had no honest answer.

**The change.**
- The question now asks only where the patient is, in files/02 §5.3's own words: "Şu anda hastanede misiniz?".
- The answers are "Evet, hastanedeyim" (Detaylı) and "Hayır, hastanede değilim" (Hızlı). The mode follows from the place, as 02 §2 defines the two modes.
- The answers live in `MODE_CHOICES`, beside the derivation they feed.

| Up-front answer | Location on the device |
|---|---|
| "Hayır, hastanede değilim", visit on a later day | REMOTE |
| "Hayır, hastanede değilim", on the visit day | UNKNOWN (the answer may be stale) |
| "Evet, hastanedeyim" | UNKNOWN |
| no answer, or a kiosk | UNKNOWN |

Why "Evet, hastanedeyim" gives UNKNOWN: the answer can be hours old when a RED fires, and ON_SITE removes the 112 affordance. The RED therefore asks its own question at RED time, and that fresh, explicit "Evet" is the device's only path to ON_SITE (`RedLocationQuestion.onYes`). This is how the owner's "only an explicit 'I am at the hospital now' answer sets ON_SITE" is met.

"No answer" is never read as an answer. The chooser now shows whenever the question is unanswered, also on an edit route (`modeChoiceNeeded`). Before, `?q=extra` from the review skipped it, and the reducer's default `hizli` stood in for an answer.

**Golden** (`location.test.ts`): over every mode, visit date and kiosk state, no answer on the device can make `deriveRedLocation` return ON_SITE. The near miss is the same "Hayır" on the visit day, which gives UNKNOWN. On the server, `derive_location` gives ON_SITE only with a certain check-in (unchanged, `tests/platform/test_visit_lifecycle_machine.py`).

**For the coordinator, not built here.** `RedLayer.tsx` passes `note.mode` and not `note.modeChosen`, and it was out of bounds for this branch. If an answer is ever committed to a note before the location question (no UI path does that now), the hop reads the reducer's default. Two changes would make that unreachable at the hop too:
- a one-line change in `RedLayer.tsx`, passing `modeChosen`;
- a matching field on `RedLocationInput`.

A depth preference separate from the place, that is a real two-question split, needs that same channel.

## Clinical review round 1 (on 4466ad9f): changes

The reviewer found the core exclusive "Yok" path safe and requested eight changes. All are applied in one commit on top.

1. **SAFETY: the voice lane ignored `multiple`.** Before, the extraction schema offered one string and a list was refused as WRONG_TYPE. So for "omzuma ve koluma yayılıyor" the model kept one site, and if that was "omuz", K2 did not fire. Now:
   - `extraction/schema.py` emits an array of the committed members for a `multiple` slot (`minItems: 1`, `uniqueItems`).
   - `extraction/parse.py` binds the set through `bind_choice_set`. A bare member is a set of one, and one member binds as that member, so every existing reading holds. A mixed set is flagged `exclusive_conflict` (a new `FlagReason`) and nothing is bound.
   - `clinical_agent/live_triage.py` `context` reads a bound list whole through `submitted_set_answer`.
   - The change is to the parse and the read only. The Talker still never awaits Backend Work, and the observer lanes stay read-only.
   - Golden: `tests/voice/test_multi_select_voice.py`. "omuz" + "kol" fires K2 in both profiles, through the clinic notification and the data channel. Near miss: "omuz" alone fires nothing.
   - The base.intake radiation comment is corrected to say what each lane does.
2. **`bind_choice_set` had no production caller.** It is now wired into the voice extraction, the server's answer-binding path (see 1), and tested there. ADR-043 and §1 now say exactly which path refuses a mixed set (voice binding) and which path deliberately does not (the hop, where a refusal would leave a site unevaluated).
3. **SAFETY, RED latency.** Each list could hold 64 members, and `itertools.product` ran over every multi-member slot a rule reads; four such lists are about 16.7M worlds.
   - The hop now refuses (422) a list holding a value outside a committed code slot's set, and several members on a single-select slot. A list for a committed slot is therefore never longer than its set.
   - The engine caps the product at `MAX_CONTESTED_WORLDS` = 4096. Past it, the predicate reads TRUE and the rule fires: escalation, never a skip.
   - Tests in `tests/safety/test_contested_world_cap.py`: the cap's both sides with a near miss; 16.7M worlds answered at once; the worst case under the cap over the served chest-pain rules fits the 300 ms budget.
   - A hop test sends the widest set the boundary admits (64 × 64 = 4096 worlds, evaluated in full) and stays inside the budget.
4. **"HİÇBİRİ" escaped the none-word check**, because `.lower()` gives "i̇". The check now uses `protocols.lexicon.turkish_fold`. "YOK" and "HİÇBİRİ" are tested.
5. **The radiation `follow_up_tr`** ("Yayılmıyorsa yok diyebilirsiniz; yayılıyorsa nerelere yayıldığını söyler misiniz?") was not changed by this branch: the diff of base/intake.yaml touches no `follow_up_tr` of that slot. It is therefore not in the text_tr table. Its "nerelere" already asks for several sites, which is consistent with `multiple: true`.
6. **ADR-043** now names D46 instead of saying no 00_STATE row exists.
