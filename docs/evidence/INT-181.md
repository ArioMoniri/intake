### SLO arithmetic (Google SRE workbook, *Alerting on SLOs*, multiwindow multi-burn-rate)

For each SLO, over every window the file declares — `5m, 30m, 1h, 6h, 3d` (the lanes) and `28d`
(the objective window):

- `error_ratio[w]` = the file's SLI with `[5m]` re-ranged to `[w]` — the same expression the
  recording rules use (`intake_platform.slo.prometheus_rule_groups`);
- SLI = `1 − error_ratio[28d]`; budget = `1 − objective`; **budget remaining** =
  `1 − error_ratio[28d] / budget` (negative when overspent, never clamped);
- **burn[w]** = `error_ratio[w] / budget`; a lane's **condition** holds when both its windows
  exceed its factor — exactly the generated alert expression.

One correction over a bare re-range: each `sum(rate(<series>[w]))` term becomes
`(… or vector(0))`. A healthy API that has never answered a 5xx has no error series, so the bare
ratio is *empty* and the tile would read unknown forever. With the fallback it reads 0 errors —
but only beside traffic, because with no traffic the ratio is 0/0 = NaN, which the client drops:
no observation, never a perfect SLI (`test_an_absent_error_series_is_zero_only_beside_traffic`,
`test_a_window_with_no_traffic_is_null_not_zero`). An SLI in any other shape is refused.

**Staleness is derived, not chosen:** `STALE_AFTER_S = 3 × SWEEP_INTERVAL_S` = 180 s — three missed
sweeps of the runner's own interval. At exactly 180 s a result is still fresh; at 181 s it is
stale (`test_a_result_older_than_three_sweeps_is_flagged_stale`). A result with no instant, or
an instant in the future, is stale.

### Refusals the page adds (each with its near-miss)

- `OverviewBurnInconsistent` — a lane whose `condition_met` is not exactly "both windows above the
  factor", or is claimed while a window has no observation. Near-miss: api·latency's ticket lane
  has the long window over the factor and the short one under, and is correctly *not met*.
- `OverviewBudgetInconsistent` — a budget remaining that does not follow from the SLI and objective
  printed beside it. Near-miss: an overspent budget (−150 %) that does follow is rendered.
- `OverviewStaleRenderedFresh` — a probe row past three sweeps, or of unknown age, marked fresh.
- Shared with INT-351: schema, non-id labels (a service, component, vendor or host with a name in
  it), an unknown tile carrying a figure, a `target` key beside a figure.

## No PHI (invariant 6)

Label values must be id-shaped or the tile is `label_not_id_shaped` (`TestPhi`); a label set other
than the query's is `unexpected_label` (an SLI re-sliced by tenant is refused). The runner's
free-text `detail` (which carries addresses and error text) is never read into the payload
(`test_the_probe_detail_never_leaves_the_api`; the spec asserts the rendered page holds neither
`Connection refused` nor `127.0.0.1`). No session, patient or tenant identifier exists on any
tile; readiness check names must be id-shaped.

## No claims (invariant 20)

No accuracy figure anywhere. The SLO objective is an engineering objective declared in
`docs/slo`, shown beside its measurement with its window; the payload carries no `target` key
and the page refuses one. The alert condition is stated as the rule it is ("met / not met"), and
the copy calls no figure good or bad.

## Finding fixed on the way: two SLO files declared a good ratio

`docs/slo/api.yaml` fixes the convention — *every SLI is the ERROR RATIO* — and the schema
docstring and the rule generator depend on it. `docs/slo/langfuse.yaml` and `docs/slo/siem.yaml`
say they follow it but wrote `emitted / (emitted + refused)` and `ingested / (ingested +
refused)`: good ratios. Read as error ratios, a healthy boundary would show ≈ 0.1 % attainment
and burn its budget ~1000× — and the day the generator (pinned to api.yaml today) grows to these
files, both pages would fire permanently. Both now divide the refusal counter by the total
(`TestSloFilesAreErrorRatios`); the objective, window, lanes and referenced series are unchanged
(`tests/infra/test_siem_feed.py` and `tests/observability/test_langfuse_gate.py` still pass).

## Finding reported, not fixed: `/admin/ops` 500s on a malformed sweep file

`intake_api.admin.models_source._results` calls `intake_probes.gate.load_results` unguarded, so
an `INTAKE_PROBE_RESULTS_PATH` holding a truncated or invalid file makes `GET /admin/models` and
`GET /admin/ops` raise instead of rendering "no probe result". The new composite reads the sweep
through its own `load_sweep`, which never raises (`probe_results_unreadable`); the INT-183/351
path is left for its own issue rather than widened into this one.
