# INT-334 — Motion: arbiter and commit windows (pure)

**Epic:** E08-mobile · **Phase:** P2 · **Sec-Row:** mobile · **GitHub:** #533
**Spec:** `docs/design/motion/motion-verification.md` §4 MOTION-5, §2.1 #5–#7 and #20;
`intake-voice-motion-spec.md` §3.3 ARB-1…ARB-5; files/02 §5.2a rules 1 and 8; ADR-033 §2
(PR #571, **Proposed**).

## Acceptance (verbatim, docs/backlog/issues.yaml)
1. "one app-authored animation at any instant; lower or equal priority arrivals render instantly, never queued; RED snaps every running element, stops the ambient loop and bypasses every window"
2. "rail, work-chip and YELLOW commits wait for the commit window (closed while listening or composing) and are applied later, never dropped; arbitration reads no clock"

## ADR-033 status
None of ADR-033's five open questions touches the arbiter. It depends on INT-333 only through
RED's meaning (RED has no motion of its own, so it renders instantly); it imports nothing from
`lib/motion/red.ts` and merges independently of it (#696). A caller keys the RED commit on
`redPresentationMode(register) !== "none"`, so a DEFERRED_CLINICIAN finding never reaches the
arbiter (S-6).

## Problem
02 §5.2a rule 8 allows one animated element at a time in the order RED > work chip > rail
commit, and rule 1 holds commits back while the patient is speaking. Nothing in the app decided
what happens when two of them meet: which one animates, whether the other waits, what the
ambient loop does, and what happens to a commit that arrives while the patient is mid-sentence.
The two motion proposals disagreed on the numbering (0-highest against 5-highest), on the
classes, on "pause at rest" against "hold", and on whether an unsent draft keeps the window shut.

## Change
- New pure module `apps/mobile/src/lib/motion/arbiter.ts`. It imports one type
  (`StreamTurn` from `lib/dialogue/stream`) and nothing from React Native, Reanimated or a clock.
  - `ARBITER_ORDER = ["red", "yellowPill", "workChip", "railCommit", "content", "ambient"]`,
    a named tuple with no priority numbers.
  - `arbitrate(state, commit, window)` → `{ state, render: "animate" | "instant" | "deferred",
    snapped }`:
    - RED renders instantly, snaps the running element, stops the ambient loop and ignores the
      window. Commits already deferred stay deferred: RED does not drop them.
    - A commit-window class (`yellowPill`, `workChip`, `railCommit`) with the window shut is
      deferred. A re-sent id replaces its deferred copy instead of stacking.
    - Otherwise, a strictly higher-priority arrival snaps the running element and animates; an
      equal or lower one renders instantly. The first animation holds the ambient loop.
  - `release(state, id)`: the end of an animation, reported by its consumer. A held loop
    resumes from its current value; a stopped loop stays stopped; a late report for an element
    that was already snapped is ignored.
  - `windowOpen({ turnPhase, composerFocused })`: shut while listening or while the composer has
    focus. A draft that is not being edited does not shut it (ARB-3 as revised).
  - `invalidate(state, slot)`: a deferred commit for an invalidated slot is never rendered.
  - `flush(state, window)`: at a window, the deferred commits in priority order (arrival order
    within a class). One animates, the rest render instantly; a shut window applies nothing.
- No consumer is wired here. INT-337 (dialogue transients) wires the dialogue to it and supplies
  the `release` events; INT-336, INT-338 and INT-342 read it for their own classes.

## Tests (TDD)
`apps/mobile/src/lib/motion/arbiter.test.ts` (15 tests), with the MOTION-5 titles:
"grants one animated element at a time" · "a lower- or equal-priority arrival renders instantly,
never queued" · "a higher-priority arrival snaps the running element to its end state first" ·
"RED snaps every running element, stops the ambient loop and bypasses every window" · "only RED
stops the ambient loop; every other class holds it at its current value" · "rail, work-chip and
YELLOW commits wait for the window; content never does" · "the window is closed while listening
or while the composer has focus" · "a deferred commit is applied at the next window, never
dropped" · "an invalidated slot is never rendered" · "YELLOW never pre-empts and never loops" ·
"arbitration reads no clock"; plus "the order is the named tuple, with no priority numbers",
"a re-sent commit replaces its deferred copy instead of stacking", "a stale release is ignored"
and a property test.

The property test drives 5,000 seeded steps (a constant-seed LCG, so a failure replays exactly)
of arrivals, releases, invalidations and window changes. After every step: nothing runs while
the ambient loop runs free, RED never occupies the animation slot and always stops the loop,
nothing is deferred while the window is open, a flush animates at most one commit, an
invalidated commit never renders, and every commit that renders renders once (more than 1,000
of them per run).

Near-miss controls: an equal-priority arrival does not snap; a draft without focus does not shut
the window; `invalidate` on an unknown slot changes nothing.
