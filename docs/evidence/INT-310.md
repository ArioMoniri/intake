Date: 2026-09-03. Branch `int-310-dep-bump`, off `origin/main` at `11c9fe4`.

## What was wrong

INT-019 built the twelve-step security gate set and **refused to suppress**
what step 6 found. That refusal is why `make security` is honestly red rather
than falsely green, and it is the whole reason this issue exists: the eight
advisories are real, and the fix is a major-version bump across the pnpm
workspace, which is its own change with its own blast radius.

Six packages, eight advisories, one ecosystem (npm). None of them is a
first-party declaration: `vitest` is the only one this repo names directly, and
the other five arrive transitively through it, through `expo-router` and
through the Expo build tooling.

## What changed, and why it took the shape it did

Three manifests and the lockfile. Nothing else in the repository is touched —
no test, no config, no source file.

```diff
 package.json                              vitest ^2.1.9 -> ^3.2.6
                                         + pnpm.overrides:
                                         +   "vite@<6.4.3":                "^6.4.3"
                                         +   "uuid@<11.1.1":               "^11.1.1"
                                         +   "decode-uri-component@<0.5.0": "^0.5.0"
 apps/mobile/package.json                  vitest ^2.1.9 -> ^3.2.6
 packages/clinical-schemas/package.json    @vitest/coverage-v8 ^2.1.9 -> ^3.2.6
```

**Why `vitest` is a declaration and the rest are overrides.** `vitest` is the
only one of the six this repository names. `vite` and `esbuild` arrive under
it; `uuid` and `decode-uri-component` arrive under packages nobody here
controls — `@expo/ngrok@4.1.3`, `xcode@3.0.1` and
`expo-router` → `query-string@7.1.3`. Declaring a transitive as a direct
dependency to move it would put `vite` in `devDependencies` as a thing this
repo does not import; an override says exactly what it is, which is a version
floor imposed on somebody else's tree.

**Why every override carries a version selector.** `"vite": "^6.4.3"` pins
every future resolution; `"vite@<6.4.3": "^6.4.3"` raises only what is below
the fix. The difference matters for `uuid`, whose advisory has three disjoint
affected ranges (`0 → 11.1.1`, `12.0.0 → 12.0.1`, `13.0.0 → 13.0.1`): a
blanket `^11.1.1` would silently drag a future dependency that legitimately
wanted `uuid@14` backwards into a version this repo chose once, for reasons
that had nothing to do with it.

**Why the bump stops at vitest 3 and vite 6 rather than the newest.** The
registry on 3 Sep 2026 carries vitest 5.0.0 and vite 8.2.2. The advisories are
fixed at 3.2.6 and 6.4.3, and the issue's acceptance names those two majors;
going three further majors would be a different change with a different blast
radius, and this one is already a major. `vitest@3` declares
`vite: ^5.0.0 || ^6.0.0`, so `vite@6.4.3` is both the fix and the ceiling of
what vitest 3 accepts.

**One resolution surprise, recorded because it would waste the next person's
hour.** Bumping vitest alone did *not* move vite: pnpm keeps an existing
resolution when the new range still admits it, so `vite@5.4.21` survived
`vitest@2.1.9 → 3.2.7` and `esbuild@0.21.5` survived with it. Four of the eight
advisories were still live at that point. The `vite@<6.4.3` override is what
actually moves them.

## What the new test pins, and why it is about versions rather than exit codes

`tests/ci/test_security_gates.py`, seven cases. The cheap version of this issue
is a row in an ignore file, and that would make the scanner exit 0 too — so the
gate is deliberately not "osv-scanner passes":

- `test_every_advisory_is_cleared_by_a_resolved_version` reads
  `pnpm-lock.yaml` and asserts every resolution of the five packages is at or
  above its fixed version. **Recorded red run of this test**, taken by
  restoring the pre-bump lockfile in place and running it:
  `AssertionError: vitest@2.1.9 is below the fixed version 3.2.6 — the advisory
  is back`, `1 failed, 6 passed`. The lockfile was restored and verified by
  sha256 (`1eb42266f862bbf7…`) before continuing.
- `test_osv_suppressions_do_not_grow` — pin **0**, measured: this repository
  has never carried an osv-scanner config of any kind, on `main` or on
  INT-019's branch.
- `test_trivy_suppressions_do_not_grow` — pin **1**. Measured 0 here (no
  `.trivyignore*` exists on `main`) and 1 once INT-019 lands its
  `.trivyignore.yaml`, whose single row is the workspace-root name collision
  with the unrelated PyData `intake` package. The pin is on *entries*, not raw
  lines, so writing a sentence explaining a row costs nothing and adding a row
  costs the build — the inverse of a raw line count, which would punish the
  explanation and wave through the mute.
- `test_no_suppression_file_names_any_of_the_eight_advisories` — because a pin
  on counts alone can be satisfied by swapping one row for another. All eleven
  ids (7 GHSA + 4 CVE aliases) are checked by name.
- `test_osv_scanner_is_not_invoked_with_an_ignore_flag` — a flag on the command
  line in the Makefile or a workflow mutes as effectively as a config file.
- `test_the_ts_suites_did_not_shrink_for_the_bump` — floor of 88 vitest files,
  measured. Like the invariant-8 coverage floors, it only rises.
- `test_no_ts_test_is_skipped_or_narrowed` — bans the rest of vitest's skip
  vocabulary. `scripts/ci/no_placeholders.sh` already catches the `it` and
  `test` spellings of skip/todo; it does not reach `describe.skip`, the whole
  `.only` family, `skipIf`/`runIf`, or `xit`/`xdescribe`. `.only` belongs in
  the same list because it narrows the run to one case while still reporting
  green.

The suppression allow-lists **did not grow**: no `.trivyignore`,
`.trivyignore.yaml`, `osv-scanner.toml` or `.osv-scanner.yaml` exists on this
branch, and none was created.

### Merging INT-019 and INT-310
