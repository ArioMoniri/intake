## 2. What the code does, and the direction of each fix

### 2.1 Face ID is used, so the key stays and carries a true string

`src/lib/auth/biometrics.ts` calls `LocalAuthentication.authenticateAsync` (INT-131). It runs
from `BiometricGate`, which wraps two places:

- `src/app/(tabs)/_layout.tsx`: opening the app;
- `src/app/(tabs)/visits/[visitId]/review.tsx`: the note review and send screen.

The passkey step-up of D36 (INT-582) is not built yet. `src/lib/shares/stepUp.ts` still uses the
`otp_session` tier. So the string names only the two gates that exist, and it does not mention
passkeys. The operating system does the face match, and the app learns only success or failure.
The string says that the app never sees the face data. It says nothing about where Apple keeps
the data, because that is not this app's claim to make.

Mechanism (INT-592's): the plugin option `faceIDPermission` writes the base Info.plist.
`app-tr.json` holds the same text (tr is the source, invariant 5), and `app-en.json` mirrors it.

| locale | `NSFaceIDUsageDescription` |
|---|---|
| tr (base and `tr.lproj`) | Önvizit uygulamayı açtığınızda ve notunuzu görmeden önce kimliğinizi Face ID ile doğrular. Yüz verilerinizi görmez; yalnızca doğrulamanın başarılı olup olmadığını öğrenir. |
| en | Önvizit uses Face ID to confirm it is you when you open the app and before you view your note. It never sees your face data; it learns only whether the check succeeded. |

The register is siz throughout (`açtığınızda`, `notunuzu`, `kimliğinizi`, `verilerinizi`). The
sentences are 12 and 8 words, under the B1 bound of 15. The string opens with "Önvizit " and has
no semicolon after the name, as INT-592's legal review asked. PolicyGuard (`tr`, `residency_tr`,
`siz`) reports no finding: `tests/legal/test_ios_purpose_strings.py` runs it over every purpose
string, and both findings sets stay empty.

Inventory: `store/facts.py` gets a `NSFaceIDUsageDescription` row with `flow_id=None`, because
no personal data reaches the app. Without that row, `test_every_declared_permission_is_classified_against_the_inventory`
fails once the key is declared.

### 2.2 The photo library is never opened, so the key goes

Production sources call `ImagePicker.launchCameraAsync` (records screen, INT-138) and nothing
else from the picker. There is no `launchImageLibraryAsync`, no
`requestMediaLibraryPermissionsAsync` and no `expo-media-library`. `launchCameraAsync` needs only
the camera key.

Fix: register `["expo-image-picker", { "photosPermission": false }]`. The plugin's own
`applyPermissions` deletes the key when the option is `false`. The camera and microphone options
stay unset on purpose. `microphonePermission: false` would block RECORD_AUDIO app-wide, which is
what the old `records.spec.ts` pin was protecting. That pin used to require that the plugin was
not registered at all. Its premise was false (§1), so it now requires exactly
`{ photosPermission: false }` and neither of the other two options.

### 2.3 Background audio is not intended, so expo-audio is told not to add it

- INT-103's acceptance is "background pauses safely".
- `useDialogueSession.ts` (INT-559) and `VoiceNote.tsx` discard the microphone and zero its buffer
  as soon as the app leaves the foreground.
- No `setAudioModeAsync` call sets `shouldPlayInBackground` or `allowsBackgroundRecording`.
- withVoiceAudio.js already states that the mode must not be declared.

So the intended direction is no `audio` mode. Fix: pass expo-audio
`enableBackgroundPlayback: false` and `enableBackgroundRecording: false`. That is the plugin's
own switch, so the result no longer depends on the order the mods run in. withVoiceAudio's strip
stays as a second fence, and its comment now says why the strip alone was not enough.

The same option also removes, on Android, `FOREGROUND_SERVICE`,
`FOREGROUND_SERVICE_MEDIA_PLAYBACK` and expo-audio's `AudioControlsService`. Those served
background playback and nothing else, and they agree with `releaseConfig.spec.ts`'s existing pin
that the app has no foreground-service permission.

## 3. Tests (written first)

- `apps/mobile/e2e/iosInfoPlist.spec.ts` (new) runs `expo config --type introspect --json`
  offline (`EXPO_OFFLINE=1`; about 1 s here) and asserts on the resolved Info.plist:
  - every `NS*UsageDescription` key names a production call site (comments stripped). A key with
    no entry in the map fails, and so does a key whose call is gone;
  - there is no `NSPhotoLibraryUsageDescription` or `NSPhotoLibraryAddUsageDescription`. Near
    miss: the camera key stays, and no library API appears in the sources;
  - `UIBackgroundModes` holds no `audio` and no `voip`;
  - the base Face ID string equals `app-tr.json`, not Expo's `Allow $(PRODUCT_NAME)` default;
  - the strings say what is gated and that the app never sees the face data. There is no `sen`
    form, and no passkey, server or storage claim.
- `tests/legal/test_ios_purpose_strings.py` (extended): the `faceIDPermission` option equals the
  tr catalogue and an en mirror exists; the key is declared and classified with no flow;
  expo-image-picker is registered with `photosPermission: false` and no camera or microphone
  option; expo-audio has both background options set to `false`. The module's existing
  PolicyGuard, B1 and tr/en parity tests now cover the Face ID string as well.
- `apps/mobile/e2e/records.spec.ts`: the picker pin is rewritten as described in §2.2.

  already installed modules.

  owner's credentials (HB-A3). The resolved config from `expo config --type introspect` is the
  same object that prebuild writes to Info.plist, so it is the closest check this host can make.
