# INT-260 — Görünüm, and the four mechanisms that make its controls do something

Owner directive, verbatim: *"make the chat page and voice page more sleek and minimalistic
maybe get ideas from mobbin and oura like and **alos make text size and other settings
adjustable**"*. This issue is the settings half. The surface redesign is a separate chain
(INT-261 and its siblings); nothing here touches the dialogue surface.

## 1. The thing that was actually hard

Shipping a text-size control is easy. Shipping one where **every** control has a consumer on
the day it lands, and where the app does not fall apart at the size the control can now
reach, is not. Four of five candidate controls had a real consumer; the fifth did not, and
it is absent rather than decorative:

| control | consumer that exists today |
|---|---|
| Yazı boyutu | `useFontScale` (`components/Themed.tsx`) |
| Tema | `useScheme` (`components/Themed.tsx`) |
| Ekran hareketini azaltın | `useReducedMotion` (`lib/a11y/prefs.ts`) |
| Ziyarete başlarken | the intake shell's `voiceEligible` rule (`visits/[visitId]/intake.tsx`) |
| ~~Sesli okuma~~ | **none** — its only consumer is the spoken-dialogue surface, which this
issue does not touch. A switch whose value nothing reads is decoration with a nice pill on
it (invariant 17), so it is not offered. It lands with that surface. |

## 2. Text scales once, never twice — and the test that proves it

`useFontScale()` is redefined **in place** (design plan R4): the chosen step **replaces** the
OS value, it never multiplies it.

```ts
export function effectiveFontScale(textStep: TextStep | null, osFontScale: number): number {
  return textStep === null ? osFontScale : APP_STEPS[textStep];
}
```

`scaledSize`, `lineHeight`, the `[0.5, 2.0]` clamp and `AppText`'s
`allowFontScaling={false}` are **untouched**, and no sibling hook was added — so "scales
once" holds by construction rather than by care.

The discriminating test is `appearance.test.ts::the smallest step at OS 2.0 is 0.9 — a
composing build could not produce this`. A composing implementation returns `0.9 × 2.0 =
1.8`; a composing-and-clamped one also returns 1.8; **only a replacing implementation returns
0.9.** Two more hold the other end: `the control is never inert` asserts that at OS 2.0 all
five steps still render five distinct body sizes (the exact failure a composing design admits
to), and `no step and OS pair can render larger than the OS maximum alone` bounds the top.
`e2e/appearance.spec.ts` then pins it structurally — the hook's body and the pure function it
delegates to must contain **no `*` at all**.

## 3. What the owner reported on the simulator, and what each one turned out to be

> *"navbar and sizes dont mathc"*

Correct, and it was three separate defects wearing one coat.

1. **The rail dropped its captions but did not grow.** Fixed: `scaledControl(base, fontScale)`
   in `lib/theme.ts` shares the clamp with `scaledSize`, so a control's box and a glyph move
   with the text by the same rule. `theme.test.ts` asserts
   `scaledControl(typeScale.body, step) === scaledSize("body", step)` for every step — ratio
   equality is what "sizes match" means.
2. **Content ran underneath the navbar.** `TAB_BAR_CLEARANCE` was the constant `120`, sized
   for a 1.0 pill. Once the rail scaled, the reserved space and the thing it reserved space
   for were two numbers free to drift. Now `useTabBarClearance()` reads `railWellSize()` —
   the same function the rail itself uses — plus the safe-area inset plus one body line at
   the current scale. Thirteen screens rewired; four needed the hook hoisted above an early
   return, which `react-hooks/rules-of-hooks` caught.
3. **The prep gauge's ring was clipped.** A fixed 232 pt arc around a numeral that scaled to
   112 pt. The arc now scales with the numeral it frames and is capped to the screen width,
   so growing it can never clip it against the edge.

> *"the theme control at the top is clipped"* / *"the floating gear overlaps the content"*

**The gear is not ours.** It is Expo Go's own dev-menu overlay: it is present on Expo Go's
splash screen **before any of our JavaScript loads**
(`INT-260-proof-gear-is-expo-go-overlay-not-app-chrome.png`), it is identical in both themes
and at every text scale, and nothing under `apps/mobile/src` renders an absolute-positioned
blue circle. It will not exist in any build of the app, so there is nothing to remove. The
apparent clipping of the theme control was this overlay plus scroll position; the settings
screen's own top inset is correct (`INT-260-dark-step5-en-buyuk-2.0.png`).

The design plan's **H7** (a settings glyph in the intake top bar) is answered by not having
been built: the only entry point is the Profilim row.

## 4. The `00 §2` rulings this touched — recorded, not worked around

### 4a. "The rail collapses at ≥1.6" was about a different rail

`files/00_STATE.md` §2 rules that at `fontScale ≥ 1.6` **the rail** changes form, collapsing
to a count row that opens a full-size sheet. Read in context, that ruling resolves
`02 §5.2a` rule 3 against `§8.2` using `anlattıklarınızdan` — an intake **option label**, 18
characters, needing a 346 pt measure. It is about the **option-chip rail inside the intake**,
not the bottom tab bar, whose five labels are `Bugün`…`Profilim`.

`lib/theme.ts` had carried the comment *"the rail collapses at ≥1.6 — 00 §2"* for four design
passes while `FloatingTabBar.tsx` contained **no `fontScale` reference at all**. When
something finally rendered against that number it was wrong: measured on an iPhone 16 Pro,
the `micro` caption renders at 14 pt at scale 1.3, five Turkish labels stop fitting the pill,
and **`Profilim` clipped mid-word**.

Two named thresholds now live in `lib/prefs/appearance.ts` where a test can reach them —
`LARGE_TEXT_SCALE = 1.6` for content form, `RAIL_LABEL_MAX_SCALE = 1.2` for the tab bar — and
`theme.ts` states no number it does not own. **Both rows are written into `00_STATE.md` §2
with the reasoning and the measurement**, per the rule that where another file disagrees with
00, 00 wins and the disagreement is a defect to fix rather than to ship around. The
option-chip ruling itself is untouched and stays issue-3 scope.

The tab bar does **not** become a count row and a sheet: a sheet listing five tabs is a worse
tab bar, every destination stays one tap away at every scale, and the focused item is marked
with a filled well rather than tint alone once its caption is gone (BK8 / SC 1.4.1).

### 4b. The mid-word no-truncate ruling now has the build gate it asked for

00 §2: *"Never truncate mid-word in Turkish … Scan of current copy found exactly **one** such
token — which is precisely why review will miss it and it must be a build gate."* No such
gate existed. `tests/release/test_i18n_complete.py::test_no_turkish_string_can_be_truncated_mid_word`
scans every shipped module for `numberOfLines`, `ellipsizeMode`, `lineBreakMode`,
`adjustsFontSizeToFit`, `word-break` and `break-all`. The tree holds **none of them**, so no
Turkish word can lose its negation suffix — a stronger guarantee than auditing render sites,
because it cannot drift. A companion test asserts the hazard class is non-empty so the ban
cannot go vacuous.

**Proved to bite** rather than assumed (§6 below).

**What is NOT fixed, honestly:** truncation is closed; mid-word **wrap** is not. React Native
breaks a word longer than the line. Measured at 2.0 on a 402 pt screen, `Hastalıkları` needs
~371 pt and the widest measure a card can offer is ~330, so `İç Hastalıkları` renders as
`Hastalıkla / rı`. **This is the same arithmetic 00 §2 already recorded** for
`anlattıklarınızdan`. Cards now take 16 pt of padding back at large text, which helps every
marginal string and does not reach this one. Swapping the display serif for the sans was
tried, measured, bought nothing at this size, and was **reverted rather than shipped as an
unjustified change to the app's register**. The two remaining levers are both banned —
truncation by the ruling above, shrinking by *"never clamp text harder"* — so what is left is
a copy decision, and it is recorded in `00_STATE.md` for the §2 copy owner rather than
invented here. A separate session is in flight on a hyphenation approach to the same case.

## 5. Persistence — built, annotated, and the ask FILED rather than answered

`{category: device preference, purpose: accessibility, basis: contract, retention: until
uninstall or reset, recipients: none}` — carried in `lib/prefs/appearance.ts` beside the
record it describes (invariant 18).

**`recipients: none` is a fact, not a claim.** The design plan said AsyncStorage; that is
both forbidden by `e2e/auth.spec.ts` (files/10 §2 admits one on-device store, by name) and
wrong on its merits — a record under the app's Documents/Library directory is **included in
iCloud and finder backups**, so the preference would leave the phone. It uses
`expo-secure-store` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, the accessibility class the token
and DPoP slots already use: excluded from backups, never synced, no new dependency.
`e2e/appearance.spec.ts` pins that the provider reaches no network, no session and no note.

Returning every control to its default **deletes** the slot rather than writing a record that
says "nothing chosen", which is what makes *retention: until uninstall or reset* literally
true.

Persisting a new category of patient-controlled state is stop-and-ask under CLAUDE.md. Per
the brief, the mechanism is built and the ask is **filed, not blocking** —
`docs/backlog/blockers.md`, owner **DPO / counsel via HUMAN_BLOCKERS**, one sentence:

> *"May text scale, theme, motion and start-mode persist device-locally under {category:
> device preference, purpose: accessibility, basis: contract, retention: until uninstall or
> reset, recipients: none}?"*

Nothing built here sends a preference off the device; if it had, this would be
`awaiting-human` instead.
