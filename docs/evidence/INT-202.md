## What the tests pin

`tests/infra/test_restore_drill.py`, 72 tests in nine classes:

- **pgBackRest / PITR** — the shipped config parses; `repo1-cipher-type` is
  `aes-256-cbc` so the *repository* (manifests, backups and WAL) is ciphertext,
  which is what files/10 §3 means by "encrypted with separate keys" and is not
  the same thing as an encrypted volume; the passphrase and both S3 keys are
  absent from the file and arrive as `PGBACKREST_REPO1_*` from OpenBao;
  `archive-async=y` is what makes it point-in-time rather than snapshot; the
  restore step really is `--type=time --target=…`.
- **A credential-shaped-literal scan** over the conf, the replication plan,
  the compose tier and the drill script.
- **Replication** — the plan replicates exactly the two buckets the platform
  writes (`intake-docs`, `intake-audit-worm`, from `services/api` defaults and
  `DocumentStore.ensure_buckets`) plus the pgBackRest repository bucket, and
  nothing else; the audit replica is created `--with-lock`, because MinIO
  enables object-lock **only at bucket creation** and a replica made without it
  silently voids the WORM guarantee; deletions and delete-markers are never
  replicated, which is the whole ransomware defence.
- **PHI safety** — `assert_restore_target_outside_workspace` refuses a resolved
  path inside the repo, including `infra/../.cache/restore`; no drill step
  contains `select *`, `pg_dump`, or the words transcript / note_text / tckn /
  phone / full_name; the evidence skeleton has exactly twelve fields, none of
  which an identifier could occupy.
- **Host preflight** — a typed `DrillBlocked` naming HB-I1 and/or HB-I2, and a
  test for each of the four disk × memory combinations.
- **The compose tier** — every service behind the `backup` profile, every image
  tag-pinned (including inline `FROM` lines), every published port on
  `127.0.0.1`, a healthcheck on every long-running service and `restart: "no"`
  on the one-shots, every bind-mount source present, and
  `infra/docker-compose.dev.yml` provably unmentioned by any of it.
- **Entry points** — the script is executable and strict bash; its `--dry-run`
  path is **actually executed by the test** and exits 0; a structural check
  that the pre-`run_drill()` half of the script contains no reference to a
  container runtime, so a dry run cannot become a wet one; and `--run` without
  a retention window exits non-zero naming HB-I8.
- **Negative controls** (near-misses of a valid fixture, so a negative cannot

## Deviations

1. **The dev compose file was not appended to at all.** The brief allowed an
   append; nothing needed one once the backup tier became a standalone overlay
   with its own profile, and zero edits to the hot file is the stronger form of
   the same instruction.
2. **`postgres-pitr` is a separate cluster, not an override of the dev
   `postgres`.** Overriding it would mean either editing the shared file or
   defining a `postgres` key in the overlay — and a `profiles:` key merged onto
   `postgres` would stop the shared dev tier from starting under `-f dev -f
   backup`. In production the same `pgbackrest.conf` mounts on the real primary
   (INT-201); here it is the drill's own primary, and the drill exercises the
   full cycle against it.
3. **`--emit-replication` replaced a `sed` filter.** The first version of
   `run_drill()` piped the human-readable plan through `sed` to recover the
   `mc` commands — which also picked up the `mc ls` verification step and would
   have run it before `mc alias set`. The CLI now emits the commands directly.
4. **A pgBackRest apt version is not pinned** in the two inline builds
   (`apt-get install pgbackrest` on `pgvector/pgvector:pg16`). Pinning a Debian
   package version that can be withdrawn from the archive trades one fragility
   for another; the durable answer is the internal Harbor registry with a signed
   image (INT-201, files/10 §8), and the images here are never built on a host
   that runs the drill anyway.

## How crypto-shredding and backups interact (the question files/06 raises)

Erasure (`intake_api.dsar.shred`) destroys each field's **wrapped DEK in the
database**; the tenant KEK in OpenBao stays (a tenant-KEK shred would erase
every patient in the tenant). Consequences, now measured rather than argued:

- restored to a moment **after** an erasure, the subject stays erased — WAL
  replay carries the shred. The drill's `erased_unreadable` + `erased_same_row`
  checks assert it on every run, host and CI;
- restored to a moment **before** it, the subject is readable again. The CI
  drill's second restore (`--characterise-erasure-window`) measures exactly
  that and prints it; it is a characterisation, not a pass;
- documents behave differently: their bytes are deleted from an unversioned
  bucket, so a restored row points at nothing — which is why `intake-docs`
  must not be versioned or replicated.

So the retention window HB-I8(a) is waiting for is exactly how long an erasure
can be undone, and it has a ceiling files/06 §1 implies (**174 days** = the
shortest six-month span, 181 days, minus the 7-day full-backup interval that
time retention keeps past the window). The runbook's real-restore procedure
re-applies erasures (`execute_due_shreds`) before a restored database serves.
Closing the window for good is INT-037's per-subject-key ask — key-management
design, not decided here. HB-I8's row now carries all three facts.
