The first acceptance clause is therefore met only at ratification.

## INT-332 status: left `todo`, not `done`

Both of this issue's acceptance lines, taken literally, are not met by this commit, so
`docs/backlog/issues.yaml`'s INT-332 row stays `status: todo`:
- **Line 1** — "an ADR in docs/adr ratifies the motion system ..., with the matching 00_STATE row and a
  mobile-ui.md §Motion pointer in the same commit." This commit does not touch `files/00_STATE.md` or
  `docs/design/mobile-ui.md`; the task that produced this ratifying commit scoped it to ADR-033, the ADR
  index and the test file only. The 00_STATE §3 row and the mobile-ui.md pointer remain open.
- **Line 2** — "the five open questions are recorded awaiting-human with their named owners, each failing
  closed meanwhile." Ratification necessarily contradicts this line as written: Q1–Q5 are no longer
  `awaiting-human`, by design — that is what ratifying them means. This acceptance line described the
  pre-ratification (Proposed) state and was never going to survive a ratifying commit; it was not updated
  to describe the ratified state when this ADR was drafted for ratification (`docs/adr/ADR-033-motion-system-v1.md`
  line 3, before this commit, already anticipated a "ratifying commit" that would need to touch files this
  issue's acceptance text doesn't mention).

Both gaps are pre-existing in how INT-332 was scoped, not something this commit introduced or could resolve
without exceeding the task it was given. A follow-up issue (or an update to INT-332's acceptance criteria)
should add the 00_STATE §3 row and the mobile-ui.md §Motion pointer, and reword acceptance line 2 to
describe the ratified state instead of the awaiting-human one.
