# INT-249 — a TTS lane must prove it can SPEAK, not merely answer

The owner's complaint, repeatedly: *"soru hazirlaniyo takes so long"*. It is
one defect with a one-line cause. `apps/mobile/src/lib/dialogue/ttsLane.ts`
selected the session's TTS tier on `/health` alone, and `/health` is the one
thing a CPU-bound VoxCPM2 does well. It answers in milliseconds and then
cannot finish a synthesis inside a turn, so the app chose it, every clip
queued behind it, and the patient watched a spinner.

INT-243 was right not to force VoxCPM2 onto the nearly-full MIG slice — it
recorded RTF ~4.06 on CPU and left the decision alone. What was missing is
that selection never looked at that number.

Corpus for every measurement below: the two dev TTS daemons on this host,
both lanes tunnelled and both `/health`-green, **2026-08-29**. These are
measurements of a dev bridge on one machine on one day, not properties of
either model.

## The measurement

Reported with the issue, on a full clip:

```
POST http://127.0.0.1:8805/synthesize  (VoxCPM2) -> TIMED OUT at 8.0s, 0 bytes
POST http://127.0.0.1:8803/synthesize  (Freya)   -> 200, 276524 bytes, 1.21s
```

Reproduced here at two text lengths, so the effect is the lane and not the
utterance:

| request | VoxCPM2 (8805, CPU) | Freya (8803) |
|---|---|---|
| `GET /health` | 200, 0.14 s | 200, 0.13 s |
| `POST /synthesize` `"Merhaba"` (one word) | 200, 92,204 B, **3.99 s** | 200, 103,724 B, **1.03 s** |
| `POST /synthesize` `"Ağrınız ne zaman başladı?"` | 200, 138,284 B, **6.12 s** | 200, 161,324 B, **0.94 s** |

Both lanes pass every health probe. They separate by ~4× on a single word
and ~6.5× on a real question. Freya's whole-clip time is roughly a fixed
~0.95 s plus a small marginal cost; VoxCPM2 on CPU scales with the text.

## The budget, and which stated number it is

**`TURN_ROUND_TRIP_BUDGET_MS = 1684`**, from **files/03 §4.4**, the
`residency_tr` row — the only production voice profile — under the column
*"expected round-trip p50 (end of speech → first agent audio)"*:

> **p95 ≈ 1684–2364 ms; may BEAT the displaced cloud stack**

and **files/03 §4.5** fixes what round-trip means: *"last patient speech
sample (VAD end) → first agent audio sample played on the device."*

On the dev clip path that round-trip **is** the synthesis. There is no SFU,
no RAN, no jitter buffer — the app POSTs to a daemon over loopback or the LAN
and plays the bytes the moment they land — so the time a lane takes to answer
is the whole of the wait the patient sits through.

The other end of the same stated band, **2364 ms**, is the hard cap on one
live request (`SYNTHESIZE_TIMEOUT_MS`). The asymmetry is deliberate and both
ends are the blueprint's: admission holds a *candidate* lane to the best of
the band on a minimal probe, because a lane chosen for a whole session should
have headroom; a request already in flight on the *chosen* lane is allowed
the worst of the band before it is declared wedged, because failing a lane
having one bad sentence would cost the patient a voice change for nothing.

### Why not §4.5's TTS-stage row

§4.5 also states *"TTS first byte | 0 ms scripted / 140 ms dynamic (§4.9.1
row 11, measured; **520 ms on the row-12 fallback, and that is a hard
architectural floor**)"*. 520 ms was the first candidate for this gate and it
is the **wrong quantity for this seam**, which the measurement settles:

- it is a **TTFT** figure for the *streaming* production path, and row 12's
  own note calls 0.52 s Freya's **TTFT** floor, not its clip time;
- these daemons **do not stream** — one POST returns the whole WAV, so there
  is no first byte to observe separately;
- measured, Freya needs **1.03 s** for a single word. Gating on 520 ms would
  reject the very tier the blueprint designates as the acceptable fallback
  and leave the dev app with **no voice at all** — a worse defect than the
  one being fixed.

Recorded here because the 520 ms reading is the obvious one and the next
person will reach for it too.

## What changed

1. **Selection times a real short synthesis.** `measureLane` does `/health`
   first (cheap, and it distinguishes a refused socket from a slow model),
   then POSTs `LANE_PROBE_TEXT` — `"Merhaba"`, one numeral-free Turkish word
   — under a hard abort at the budget. Verdicts: `ok`, `unhealthy`,
   `over_budget`, `silent`, `error`. The probe bytes are timed and dropped:
   there is no code path from a probe to the filesystem.
2. **The ladder's intent survives.** `selectTtsLane` takes the *first* lane
   in ladder order that is inside budget, and ladder order is quality order
   (files/03 §4.9.1 rows 10-11 before row 12), so VoxCPM2 still wins whenever
   it is actually fast. It is overridden only by measurement, and probing
   stops at the winner — a fast VoxCPM2 costs one health call plus one short
   synthesis, and Freya is never woken.
3. **One probe per session, re-probed on failure.** `createTtsLaneSelector`
   caches the choice (concurrent callers share one in-flight probe, which
   matters because the mount pre-warm fires every question at once) and
   `invalidate()` drops it. A wedged tier demotes itself on the next probe.
4. **Every synthesis is capped and falls through.** `synthesizeWithFallback`
   invalidates the selection on any lane-side failure and retries on the
   re-probed lane, bounded by the candidate count. `tts_numeral_blocked` and
   `tts_empty_text` are excluded by name and rethrown at once — those are
   verdicts on the **text**, and retrying them elsewhere would turn invariant
   22's guard into a lane-shaped loophole.
5. **The clip store binds to the selector, not to a base.** INT-243 bound the
   store to one base for the whole session, so a lane that wedged after
   selection had no way back. `synthesizeClipWith` takes an injected
   per-sentence synthesizer; INT-237's chunking, gaps, trimming and fades are
   untouched — only where each request lands has changed.
6. **The health-only resolvers are deleted, not wrapped.** `resolveTtsLane`,
   `clips.ts::reachableTtsLane` and `clips.ts::reachableTtsBaseUrl` are gone.
   Neither `main` nor `int-246-voice-diagnostic` has any remaining consumer
   (checked with `git grep` on both), and a function that hands out a base
   resolved on health alone is the defect kept within reach. Anything wanting
   a one-shot answer calls `selectTtsLane`, which measures.

## Could a hung lane block a turn? Yes — verified, and worse than a spinner

The default cap was `SYNTHESIZE_TIMEOUT_MS = 30_000` in `tts.ts`, and
`synthesizeClip` synthesizes **one request per sentence, sequentially**. So a
wedged lane held a two-sentence clip for up to 60 s, and there was no fallback
at synthesis time at all — the store was bound to one base. When the cap
finally fired, `useDialogueSession`'s speaking driver caught it and dispatched
`{ type: "failure" }`, which is terminal: `DialogueIntake` returns `null` for
`phase === "failed"` and the patient is routed to the manual steps. The
observed symptom was a long spinner; the actual behaviour was a long spinner
followed by the dialogue tearing itself down.

After: one wedged sentence costs one 2364 ms cap plus a re-probe, then the
words arrive in Freya's voice.

## The patient never waits on synthesis to READ the question

Confirmed **already true** and previously unpinned.

`stream.ts` appends the `agent_question` entry in the *same returned object*
that sets `phase: "speaking"` (`advance()`, and `initialDialogueStreamState`
for the opening turn), so the text is in reducer state before any effect
runs. `DialogueIntake.tsx` renders `{body}` unconditionally in both the
settled and the live bubble; `session.playing` chooses only between a
`PulseDot` and an `ActivityIndicator`, and between `dialogue.speakingHint`
and `dialogue.preparing`. "Soru hazırlanıyor…" is a caption in the status row
*below* the question, never a stand-in for it.

Late audio cannot re-block the turn either: the speaking effect keys on the
turn object, and the reducer preserves that object's **identity** across
`transcript_ready` and `extract_settled`, so a reconcile cannot re-enter the
effect and restart the clip.

Neither fact had a test. There are no React Native render tests in this app —
every `e2e/*.spec.ts` is a static source scanner — so a regression wrapping
`{body}` in a `session.playing` gate would have passed the whole suite. Both
are now pinned: `e2e/askAhead.spec.ts` (5 tests) on the render side, and
three `toBe`-identity tests in `stream.test.ts` on the reducer side.
`toEqual` cannot see the identity defect, which is why those assertions are
identity.

## Selection behaviour, before and after

Against the live daemons, running the real `measureLane` / `selectTtsLane`:

```
measure {"id":"voxcpm2","base":"http://127.0.0.1:8805","ms":1688,"verdict":"over_budget"}
measure {"id":"freya","base":"http://127.0.0.1:8803","ms":1021,"verdict":"ok"}
SELECTED: freya @ 1040 ms
```

| | before (health only) | after (must speak inside budget) |
|---|---|---|
| VoxCPM2 8805 | `/health` 200 → **selected** | probe aborted at 1688 ms → `over_budget`, skipped |
| Freya 8803 | never probed | probe 1021 ms → `ok`, **selected** |
| first clip | 3.99–6.12 s, or a 30 s cap and a dead dialogue | ~1.0 s |
| a lane wedging mid-session | every remaining clip queues, then `failure` | 2364 ms cap, re-probe, Freya |

The ladder is not inverted — it is measured. On a host where VoxCPM2 has real
GPU, its probe lands near §4.9.1 row 11's 0.14 s and it is selected first,
which the `keeps VoxCPM2 when it is actually fast` test pins.

## Invariants

- **22 (no numeral reaches TTS).** `assertSpeakableTr` is unchanged and still
  throws before any request leaves the app. `synthesizeWithFallback` calls it
  once up front *and* excludes `tts_numeral_blocked` / `tts_empty_text` from
  the fallback loop, so a rejected string is never re-offered to a second
  lane. `LANE_PROBE_TEXT` is asserted numeral-free by test.
- **10 (scripted text verbatim).** No shaping, chunking or text handling
  changed; `synthesizeClipWith` is `synthesizeClip`'s body with the base
  swapped for an injected synthesizer, and INT-237's substring/order
  properties are still pinned by `speechShaping.test.ts`.
- **3 (no audio persists).** Probe bytes are measured and dropped — there is
  no path from `measureLane` to `ClipFs`. Agent-clip and patient-recording
  hygiene are untouched.
