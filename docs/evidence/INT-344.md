# INT-344 — real device attestation on OTP and session (audit F02)

GitHub #543 · Sec-Row `onboarding` · branch `int-344-device-attestation`

## Acceptance, verbatim

- iOS release builds attest with App Attest and Android with Play Integrity; the client
  never sends a dev-unattested mode outside `__DEV__`
- the server verifier validates attestation and assertion objects against recorded Apple
  and Google fixtures (certificate chain, app id, counter, nonce binding) and refuses
  everything else; FailClosedAttestationVerifier stays the default when keys are absent
- a TestFlight device smoke test completes OTP login against the staging API with real
  attestation; INTAKE_DEV_ALLOW_UNATTESTED is never set on a public host
- the production keys and team identifiers come from HB-A3; until then the path fails closed

## What is delivered, and what is not

| Clause | State |
|---|---|
| iOS release builds attest with App Attest | **delivered** — client + server, see below |
| Android attests with Play Integrity | **blocked on HB-A3.** The verdict policy is built and tested; no decoder can exist without the Play Console organisation account and its service account (or its local decryption/verification keys). Android release builds refuse with their own copy (`auth.error.attestationPending`) and the server refuses with `play_integrity_not_configured`. Nothing is faked. |
| never dev-unattested outside `__DEV__` | **delivered** — `selectAttestationMode` pinned exhaustively over platform × support |
| validated against recorded Apple fixtures | **delivered** — Apple's own published example attestation verifies against the pinned root; every check refuses on its own against a synthetic chain |
| validated against recorded Google fixtures | **blocked on HB-A3** — no Google verdict can be recorded without the console account; the policy is proven against decoded verdicts |
| FailClosed stays the default when keys are absent | **delivered** — no team id → `app_attest_not_configured`; malformed config → `app_attest_config_invalid` |
| TestFlight device smoke test | **not done** — needs HB-A3 (Apple Developer account, team id), a TestFlight build and a device |
| INTAKE_DEV_ALLOW_UNATTESTED never on a public host | unchanged here; enforced by INT-325 (#521, open), which this issue depends on |

## Design

**Server (`services/api`).**

- `intake_api/app_attest.py` — `AppAttestVerifier`, Apple's algorithm step for step
  (developer.apple.com, *Validating apps that connect to your server*, retrieved 2026-09-26):
  - attestation: CBOR `fmt == "apple-appattest"`; `x5c` chains credCert → intermediate →
    the pinned Apple root, each certificate valid now, CAs above and a non-CA leaf;
    nonce = SHA256(authData ‖ clientDataHash) equals the single OCTET STRING in credCert
    extension 1.2.840.113635.100.8.2 (strict DER walk); SHA256(credCert key, X9.62
    uncompressed) equals the key id, and — beyond Apple's list — the COSE key in authData
    is that same key; rpIdHash = SHA256("<team id>.<bundle id>"); counter 0; aaguid
    `appattest`+7×0x00 (production) or `appattestdevelop` only when development is
    configured; credentialId equals the key id;
  - assertion: ECDSA-P256-SHA256 over SHA256(authenticatorData ‖ SHA256(clientData)) under
    the stored key; rpIdHash; counter strictly greater than stored, then an atomic Lua
    compare-and-set so of two assertions racing on one counter exactly one wins; the
    stored key's environment must match the configured one.
- `intake_api/app_attest_decode.py` — the strict decoders: definite-length CBOR only, no
  duplicate keys, bounded depth, exactly one map where one map is allowed, the WebAuthn
  authenticator-data layout, the COSE P-256 key, and a DER walk that insists on minimal
  lengths. Device objects are data, never instructions.
- `intake_api/trust/apple_app_attestation_root_ca.pem` — the Apple App Attestation Root CA,
  from `https://www.apple.com/certificateauthority/Apple_App_Attestation_Root_CA.pem`,
  retrieved 2026-09-26. DER SHA-256
  `1cb9823ba28ba6ad2d33a006941de2ae4f513ef1d4e831b9f7e0fa7b6242c932` (openssl fingerprint
  `1C:B9:82:3B:…:C9:32`), valid 2020-03-18 → 2045-03-15. Pinned in code
  (`APPLE_APP_ATTEST_ROOT_SHA256`) and again as a literal in the test; the loader refuses
  any other certificate. The test root is reachable only through `AppAttestVerifier(root=…)`.
- `intake_api/app_attest_store.py` — Redis hash per key: public key, counter, environment.
  Registration is `EXISTS`-guarded in one Lua script (a key attests once); the counter
  moves only forward in another. TTL `REFRESH_TTL_S` (30 days), renewed per assertion.
- `intake_api/play_integrity.py` — the verdict policy from Google's *Integrity verdicts*
  page (retrieved 2026-09-26): `requestDetails.requestPackageName` and `requestHash`
  match, `timestampMillis` within `CHALLENGE_TTL_S`, `appIntegrity.appRecognitionVerdict ==
  PLAY_RECOGNIZED` for our package, `deviceIntegrity` carries `MEETS_DEVICE_INTEGRITY`.
  `PlayIntegrityDecoder` is the HB-A3 seam; no production implementation exists.
- `intake_api/attestation.py` — `AttestationReason` (typed, closed set; logged by value
  only), `PlatformAttestationVerifier` routing by mode (a mode claimed from the other
  platform refuses; dev-unattested reaches the dev tier only when it is wired),
  `attestation_client_data(purpose, challenge)` = `intake.attest.v1|<purpose>|<challenge>`.
- `intake_api/otp.py` — the challenge is now **consumed before any verifier runs** (was:
  after), so a challenge is single-use whatever the outcome and the App Attest counter only
  moves under a live challenge. Verifiers run off the event loop (`asyncio.to_thread`).
  New `POST /v1/auth/attest/key` registers a key from an attestation (the attestation
  object is several kB — Apple's example is 7 876 base64 characters — so it travels once
  in a body, never in a header on every call).
- Config: `INTAKE_APP_ATTEST_TEAM_ID` (no default), `INTAKE_APP_ATTEST_BUNDLE_ID`
  (defaults to `com.ariomoniri.intakemobile`), `INTAKE_APP_ATTEST_ENVIRONMENT` (unset =
  production; exactly `development` otherwise).

**Client (`apps/mobile`).**

- `src/lib/auth/attestationPlan.ts` — pure: mode selection, the clientData string, the
  header/registration payloads, the versioned SecureStore slot codec, error mapping to
  copy, and the key lifecycle over injected ports (register once; assert per call; a key
  the Secure Enclave lost after a reinstall is replaced once; a key the server refused is
  forgotten).
- `src/lib/auth/attestation.ts` — native ports: `@expo/app-integrity` behind a lazy
  `import()` (never in the vitest graph; never loaded in `__DEV__`), SecureStore slots.
- `src/lib/auth/api.ts` — `attestedPost` for otp/request and otp/verify; the DPoP proof is
  minted per attempt; a refused App Attest assertion is retried once with a fresh key.
- Copy (tr + en, siz register, no numerals): `auth.error.attestationUnsupported`,
  `auth.error.attestationPending`, `auth.error.attestationService`.

## The recorded Apple fixture

`tests/fixtures/app_attest/apple_validation_guide_example.json` is copied verbatim from
Apple's *Attestation Object Validation Guide* (retrieved 2026-09-26). Two facts established
while verifying it, recorded so nobody re-derives them:

1. The example app passed the **raw challenge bytes** as `clientDataHash`:
   SHA256(authData ‖ `example_server_challenge`) is the nonce in credCert, while
   SHA256(authData ‖ SHA256(challenge)) is not. The test hands the verifier the raw bytes.
   Our app hashes (the Expo module computes SHA256 of the string it is given), and the
   server hashes the clientData it rebuilds the same way.
2. The guide's "expected public key SHA256" line does not equal its own keyId; the keyId,
   the credentialId, the leaf's common name and SHA256 of the X9.62 point all agree, and
   that is what the verifier checks.

## Deliberately not enforced

Apple's 2026 revision adds `apple_validation_category_01` and `apple_bundle_version_01` in
an extensions map after the COSE key. Their accepted iOS values are not published (the
`ValidationCategory.Value` pages give case names, not raw values), and Apple's example
contradicts its text (bundle version `"1"` where the guide expects `"1.0"`). The map is
parsed strictly — anything after the COSE key that is not exactly one CBOR map with text
keys refuses — and its values are not judged. Enforcing a guessed value would lock every
iPhone out.

## Data held

A Redis hash per attested key: the X9.62 public key, the assertion counter and the Apple
environment. No phone, no person identifier, no content — the same class of datum as the
DPoP key thumbprint INT-131 already keeps beside every token — kept 30 days rolling. The
mobile side keeps the key id (an Apple-issued hash of a public key) and a registered flag
in SecureStore. Flagged for the legal reviewer rather than asserted: no new category of
personal data is intended.

## What the owner must do (HB-A3)

1. Set `INTAKE_APP_ATTEST_TEAM_ID` on the staging/production API (the 10-character App ID
   prefix from the Apple Developer account). Without it iOS fails closed.
2. In `apps/mobile/app.json` (`expo.ios`): `bundleIdentifier: "com.ariomoniri.intakemobile"`
   and, to exercise App Attest from development-signed builds against a production server,
   `entitlements: { "com.apple.developer.devicecheck.appattest-environment": "production" }`.
   Store and TestFlight builds use production regardless. Not edited here: the working
   copy carries uncommitted edits to that block.
3. Build with EAS (a development or store build): `@expo/app-integrity` is a native module;
   Expo Go cannot provide App Attest and the client reports `unsupported` there.
4. For Android: the Play Console organisation account, the Google Cloud project number and
   either the decode service account or the Play-managed response keys — then a
   `PlayIntegrityDecoder` and the client's `requestIntegrityCheckAsync` path land.
5. The TestFlight smoke test (acceptance clause three) runs once 1–3 exist.
