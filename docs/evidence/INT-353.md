### The guard gap the cluster queue exposes

`load_registry` refused the review root and a symlink to it. It did not refuse a served
root whose layer directory or pack file resolves into the queue. `cluster/` has no served
tree yet, so the obvious way to try the candidates is to link `cluster/` to
`review/cluster`. Before this change, that served all 8 candidates:

```
$ uv run python probe_layer_link.py .     (base/ -> packages/protocols/base, cluster/ -> review/cluster)
loaded 8 cluster candidates, e.g. ['cluster.allied_and_reports', 'cluster.child_health', 'cluster.dental']
```

`load_registry` now also raises `ReviewQueueRootError` for any pack file whose resolved
path is `review/<layer>/<pack>.yaml`. This covers a linked layer directory and a single
linked file, for both `review/cluster` and `review/specialty`.

`tests/protocols/test_review_queue_not_served.py` gains 8 tests (10 → 18):

- the queue holds exactly one `layer: cluster` candidate per intake cluster in the taxonomy;
- the served registry never holds a cluster candidate (no served cluster pack exists);
- `resolve_branch` never returns a cluster candidate for any branch of an intake cluster;
- the L0 / unsigned / `draft_needs_source` / not-compilable check now covers all 99
  candidates (91 specialty and 8 cluster);
- a cluster candidate registered on purpose raises `L0PackServedError` for every branch of
  its cluster;
- a `cluster/` or `specialty/` layer linked into the queue is refused (parametrised);
- a single candidate file linked into a served `cluster/` directory is refused;
- near-miss control: a `specialty/` layer linked to the served tree still loads, with the
  same ids as the served registry.
