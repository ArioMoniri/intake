# Evidence: INT-392 · deleting a session removes its previsit outputs in every erasure and retention path

GitHub #647 (P0). **Sec-Row:** `data-at-rest` (files/10 §9; `docs/security/threat-model.md`
§ `data-at-rest`). **Branch:** `int-392-session-delete-outputs`. No migration: the alembic head is
still `0013_previsit_output`.

## 1. The defect

INT-317 (#602, migration 0013) added `previsit_outputs.session_id → sessions.id` as
`fk_previsit_outputs_session_id_sessions`, with no ON DELETE rule. No path that deletes a session
removed the output first:

| Path | Where | On main, with an output present |
|---|---|---|
| DSAR erasure (KVKK m.11, after the 30-day grace) | `services/api/src/intake_api/dsar/shred.py` `_erase_subject` | `ForeignKeyViolation` on postgres. The output was never shredded and never deleted. |
| Retention, class `clinical_record` (the engine's DSAR-only path) | `packages/intake_platform/src/intake_platform/retention/executors.py` `destroy_clinical` | `ForeignKeyViolation` on postgres. The same happened for any session with a telemetry event, which this path never de-linked. |
| Integration teardown | `tests/api/test_api_postgres.py` `client` fixture | `ForeignKeyViolation` in the teardown of `test_documents_roundtrip_against_real_minio`: `test_full_visit_and_note_flow_under_rls` sends a note, which writes an output. |

No other path deletes a session. `git grep` finds `delete(IntakeSession)` only in the two executors
above, and `DELETE FROM sessions` only in the two teardowns of `test_api_postgres.py`. There is no
admin deletion endpoint, and crypto-shredding happens inside the DSAR erasure, not as a separate
row-deleting path.

The unit lane stayed green because SQLite enforces foreign keys only when it is asked to. On main,
the DSAR unit tests deleted the session and left the output row behind with no session.
`test_the_erasure_delinks_telemetry_instead_of_orphaning_the_foreign_key` already records this
blind spot for `events`.

`docs/evidence/INT-317.md` and `RET_PREVISIT_OUTPUT` (`intake_platform/db/inventory.py`) both
state that the output is "reached by the same DSAR erasure and the same crypto-shred" as the note.
Before this change the code did neither.

## 2. The mechanism, and why

**Explicit, ordered removal in each deletion path. The foreign key stays NO ACTION. No
`ON DELETE CASCADE` migration.**

- **files/06 §3 decides that the output is erased with the session.** The row is "transcript-derived
  structured data & notes: life of the record, patient-deletable (30-day grace, then
  crypto-shred)". `RET_PREVISIT_OUTPUT` puts the output on that clock because a frozen projection
  of the note cannot outlive the note. No legal reason in files/06 keeps it past its session. The
  hospital's own copy is the hospital's as controller (files/06 §2.3). That is a DPA clause per
  recipient row, not a reason to keep ours. So nothing here needed a stop.
- **files/06 §1 KVKK-7 names crypto-shredding as our destruction method.** A cascade deletes a row.
  It does not destroy the wrapped DEK first, and it writes no audit entry. The existing erasure
  design (`shred.py`: crypto-shred, then delete in dependency order, then audit) is exactly what a
  cascade would skip.
- **NO ACTION is the fail-closed backstop.** With the key left as it is, a future deletion path
  that forgets the output raises `ForeignKeyViolation` and rolls back. A cascade would remove the
  unshredded envelope silently. The contract test below pins the NO ACTION and refuses a cascade
  on this table.
- **The repo already follows this pattern.** `slots`, `notes` and `documents` all reference
  `sessions` with NO ACTION and are removed by name in both executors. The one cascade,
  `csat_texts`, was chosen so that no third sweeper would be needed, and its payload is the one
  envelope that is not shredded before its row goes. The output already has the two sweepers, and
  both now handle it.

**Order (documented in both module docstrings).** The previsit output goes first. It is the one
row a hospital may already have fetched, so removing it first closes the read-back before the
rest of the record goes. Then come shares, documents, rectifications, notes, learned facts and
their header, and slots. Then the telemetry de-link, and the session last. All of this happens in
one transaction.

**Audit.** The DSAR erasure writes one `dsar.delete.previsit_output` entry per output, with
`resource_ref=previsit_output:<id>`. That is the same ref under which `/v1/previsit-output/fetch`
audits a disclosure (`api.previsit_output.shared`), so the chain shows what left and when it was
erased. `actor=patient:<id>` and `consent_scope=basis:KVKK-11/13`, both copied from
`dsar.delete.shred`. The `dsar` prefix classifies as `DATA_REQUEST` in the patient access log. The
retention path is audited by the engine's own destruction log (`retention.dsar_destroyed`, per
class and count). The output is inside the `clinical_record` session tree that entry covers.

## 3. What each path does now

- **DSAR erasure** (`intake_api.dsar.shred`):
  1. Queries the subject's outputs by `tenant_id` + `patient_id`.
  2. Crypto-shreds each payload (counted in `ShredReport.shredded_fields`).
  3. Deletes the outputs first, then the rest of the tree as before.
  4. After the commit, audits each output by id.
- **Retention `clinical_record`** (`intake_platform.retention.executors.destroy_clinical`):
  1. Deletes the sessions' outputs first.
  2. De-links `events.session_id`, the same reasoning `shred.py` gives: telemetry has its own
     clock and carries no PHI. Before this change, a session with an event could not be destroyed
     on this path either. The contract below made that visible, and it is fixed in the same line
     of work.
  3. Deletes the session.

  It does not shred the output payload, just as it does not shred the note. `retention_policy.yaml`
  gives the key-shred to the DSAR flow (`destruction_path: dsar_only`).
- **Integration teardown** (`tests/api/test_api_postgres.py`): `previsit_outputs` is deleted
  first. `test_full_visit_and_note_flow_under_rls` now also asserts that the send wrote the output
  as an envelope, so the teardown's first row is known to exist.

## 4. Tests

- **`tests/data/test_session_delete_contract.py`** (new):
  - `ON_SESSION_DELETE` declares, for every foreign key to `sessions.id`, what a session deletion
    does to it: `removed_first` for slots, notes, documents and previsit_outputs, `delinked` for
    events, `cascade` for csat_texts. `contract_breaches()` reads that from `Base.metadata`.
  - **Near-miss controls:**
    - an undeclared table pointing at sessions is named;
    - a CASCADE on `previsit_outputs` is refused;
    - a declared cascade that the key does not carry is refused;
    - a stale declaration is named.
  - **Behaviour:** the retention executor runs on SQLite **with foreign keys ON** over a session
    that has a row in every declared table. A test proves the seed covers the whole declaration. A
    control proves that a bare session delete is refused in this lane.
- **`tests/legal/test_dsar_flows.py`**
  (`test_the_erasure_shreds_the_previsit_output_and_removes_it_before_its_session`):
  - Foreign keys are enforced on the harness engine.
  - A sent note writes the output, and the erasure runs after the grace.
  - `shredded_fields` equals the envelopes present (note + output + sensitive slots).
  - The output and the session are gone.
  - Exactly one `dsar.delete.previsit_output` entry names `previsit_output:<id>`.
- **`tests/integration/test_session_erasure.py`** (new, `-m integration`, CI only), on the migrated
  postgres:
  - **The backstop:** with every other dependent gone, a bare `DELETE FROM sessions` still raises
    `ForeignKeyViolation` naming `fk_previsit_outputs_session_id_sessions`.
  - **The DSAR erasure** deletes a session that has an output. It shreds two envelopes, de-links
    the event, and audits the output by id.
  - **The retention executor** deletes a session that has an output, and de-links the event.

  Both paths run as the bootstrap superuser. See §6 for why.
- **`tests/api/test_api_postgres.py`**: the teardown order, plus the output-exists assertion.

## 8. Found, not fixed (separate issues)

- **`doctor_links.share_id → shares.id` has no ON DELETE rule, and neither executor removes Doctor
  Links.** Both executors delete the subject's `shares`, so an erasure of a patient who issued a
  Doctor Link (INT-150, migration 0012) raises `ForeignKeyViolation` on postgres, the same class of
  defect one level down. It is not a key to `sessions`, so it is outside this issue's acceptance.
- **The DSAR executor cannot complete as `app_rw`.** Its telemetry de-link needs `UPDATE` on
  `events`, which `app_rw` is deliberately not granted (events are append-only for the app role).
  The executor has no production caller yet (`execute_due_shreds` is called from tests only).
  Choosing the role that runs erasure is a grant and key-management decision: either a column
  grant on `events.session_id` or a dedicated erasure role. CLAUDE.md makes that a human call.
- **`retention_policy.yaml` `clinical_record.source`** lists the session tree as it stood before
  INT-317 ("sessions, slots, notes, shares rows, document rows"). The executor now removes
  previsit outputs as part of that class, as `RET_PREVISIT_OUTPUT` already says it should. The
  retention policy text is left to its owner, not edited here.
