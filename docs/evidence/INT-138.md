## 2. The affordance for confirming a numeric value, and why

**The card offers two verdicts and no text field.** *Evet, doğru* / *Hayır, doğru
değil*, and a third control that is not an edit: *Belgede gösterin*, which opens the
provenance panel.

Three things forced that shape and they agree:

1. **CLAUDE.md invariant 22** — *no free numeric text entry on the clinical critical
   path*. A confirm card with an editable lab value is exactly that, and it is the
   worst instance of it: the patient would be retyping a number they are reading off
   a screen, which is a transcription step nobody asked for and a place a decimal
   separator can move.
2. **`confirm_record_item` has no path that takes a restated value.** INT-121, in its
   own words: *"the observation carries over unchanged: confirming is agreeing with
   what was extracted, never restating it. A patient who disagrees produces a
   correction, not an edited extraction."* An editor on this card would mint
   something the server cannot accept — a UI affordance whose result has nowhere to go.
3. **INT-133 already answered the same question once.** `FactOutcome` is
   `confirmed | changed | stopped`, and its comment records why: *"`changed` records
   disagreement without capturing a replacement value"*. `CardDecision` is
   `confirmed | declined` for the same reason, and a test asserts the type has no
   third member and that `decisionBody` carries exactly `{card_id, decision}` — no
   magnitude, no unit.

**What a disagreeing patient gets instead is the source.** The honest way to settle
"is this 30 or 3.0?" is to look at the page it came from, not to retype it from
memory — which is why the provenance panel is the third control on the card rather
than a detail view somewhere else.

`summary` itself is **carried, never re-rendered**. It arrives from `summarise_item`
already under the invariant-22 display rule (`useGrouping:false`, plain positional
notation, number and unit joined by a NO-BREAK SPACE). `extraction.ts` contains no
`parseFloat`, no `parseInt`, no `toFixed`, no `NumberFormat` and no `toLocaleString`,
and a test greps for all five. The reason is the same one files/03 §4.9.6 gives:
`1.500` reads two ways, the two readings differ by a factor of 1000, and a second
reading on the client is a second answer to a question the server already answered.

## 3. How the unit conflict is surfaced

INT-121's guard flags rather than converts: on disagreement `unit_conflict` is set,
the magnitude stays **unscaled**, the printed unit stays **as printed**, and the flag
rides to FHIR as an extension.

On the card that becomes a distinct amber block under the line, carrying
`records.card.unitConflict` — *"Bu satırdaki birim beklenenden farklı. Değer belgede
yazdığı gibi bırakıldı."* Three properties:

- **The value above it is not touched.** The card renders the same `summary` string
  whether or not the flag is set. A screen that "helpfully" corrected the display
  would undo the guard on the one surface a human could still catch it.
- **The copy says what was NOT done.** *"bırakıldı"* — left as it was. The patient is
  told the app did not convert, which is the fact that matters when the printed unit
  is the wrong one (files/03 §4.9.6's ALT `0 - 55 U/mL`).
- **It is amber, not the emergency pair.** files/02 §5.3 reserves the emergency
  colours for the RED route; a printed unit that disagrees with an expectation is not
  an emergency and must not be dressed as one.

An **unchecked** value is a different state and is not shown as agreement: the server
reports it in `DocumentExtraction.units_unchecked` and the card simply carries no
flag. Nothing on the screen says a unit was verified.

A near-miss control guards the parser in the other direction: `unit_conflict` is a
flag, not a level, and is **accepted** (`invariant 1 — a document is not a rules
engine`, third test). Without it the level-shaped-key refusal would pass for a parser
that rejected every optional key, which would delete the unit guard from the screen.

## 4. What the client refuses, and why each refusal is a mirror

`parseExtraction` is a closed-shape reader, and every refusal restates a server-side
property rather than inventing a client-side one:

| refusal | mirrors | near-miss control |
|---|---|---|
| a level-shaped key refuses the **whole** extraction | `extract_record_items` / `LEVEL_SHAPED_KEYS` (invariant 1) | `unit_conflict` is accepted |
| an item with no `provenance`, no page or no rectangle is refused | `SourceBox` is a defaultless field | a well-formed box parses to `{documentRef, page, bbox}` |
| a bbox outside `[0,1]`, inverted or empty is refused | `SourceBox.__post_init__` | `[0.1, 0.2, 0.5, 0.3]` parses |
| a key the shape does not declare refuses the whole payload | `ITEM_KEYS`, closed | the six declared keys parse |
| an empty `summary` is refused | *"an extracted item renders something for the patient to confirm"* | a real line parses byte-for-byte |
| a `state` outside the closed set is refused | `FEED_STATES` | `read`/`reading`/`unread` parse |

`RECORD_ITEM_KINDS` is asserted against `packages/clinical-schemas/src/generated/
models.ts` member-for-member, by reading the generated file — so the app's vocabulary
is the schema's, not a copy that can drift.

No refusal message names a printed value, a magnitude or a line of a document
(invariant 6): the parser returns a `refused` **state**, and it carries no detail.

## 5. Two things the camera brought with it

### 5a. A photograph of a lab report carries where the patient was standing

On the path this app takes — `quality` at `1.0` — Android's `RawImageExporter` copies
the camera's file byte for byte, so the **entire** original EXIF would reach the upload.
The compressing exporter is no better on the point that matters: it calls
`copyExifData`, and `ImagePickerConstants.EXIF_TAGS` names the GPS family explicitly —
`TAG_GPS_LATITUDE`, `TAG_GPS_LONGITUDE`, `TAG_GPS_TIMESTAMP` and sixteen more. Either
way the camera this issue adds would have put the patient's coordinates into the object
store alongside their medical document.

Location has never been declared as a category of personal data anywhere in this
repository, and invariant 18 requires an inventory annotation
`{category, purpose, basis, retention, recipients}` for every new data field. Adding
one would be a decision to persist a new category of personal data, which CLAUDE.md
makes a stop-and-ask. **Not persisting it needs no decision**, so the bytes are
stripped instead: `stripJpegMetadata` removes every **APP1** segment — the container
EXIF and XMP both live in — before `sha256` sees the bytes, so the digest declared to
the server is the digest of what actually travels.

Three properties, each with a test:

- **APP1 only.** APP0 (JFIF) and APP2 (ICC colour profile) stay; dropping a colour
  profile would change how the document renders for the clinician who reads it.
- **The scan stops at SOS.** Past the start of scan the stream is entropy-coded image
  data, and a `0xFFE1` pair in the pixels is image, not an APP1 header. The near-miss
  control puts exactly that pair in the scan data and asserts it survives — a parser
  that kept walking markers would cut the image apart, and would pass every other
  test in the file.
- **Anything it cannot read whole is returned untouched.** A truncated segment, a
  missing marker byte, a PNG, a PDF, two bytes of nothing. A partially rewritten JPEG
  is a corrupt document the patient believes is their report, which is worse than the
  metadata. ⚠️ **This fails OPEN and the trade is now named in the `records` threat
  row** rather than made silently in code: such a file uploads with its EXIF intact,
  and refusing the upload instead is not obviously worse. Left for a human.
- ⚠️ **PNG is on the allow-list and is not stripped.** It carries its own `eXIf` chunk
  and XMP — a third container beside the two this function names. File-picker path
  only, so lower probability, same exposure. Reported in the threat row, not fixed
  here.

#### The orientation claim was wrong, and the security review caught it

The first version of this file argued that orientation cost nothing, citing Android's
`copyExifData` omitting `TAG_ORIENTATION`. That is true of `copyExifData` — **and
`copyExifData` is on a path this app does not take.** `MediaHandler.kt` picks
`RawImageExporter` whenever `options.quality == MAXIMUM_QUALITY`,
`ImagePickerOptions.kt` defaults `quality` to `1.0`, and nothing set it, so Android
took the raw branch: a straight `copyFile`, no re-encode, no `omittableTags`. iOS has
the same shape from the other side — `imageModified = allowsEditing || quality < 1`
was false, so it tried `tryCopyingOriginalImageFrom`, a raw file copy, and survived
only because `mediaInfo[.imageURL]` happens to be nil for a camera capture. That is an
unwritten UIKit behaviour, one non-nil away from copying the original.

It cut both ways. **The strip is more necessary than the first argument claimed** — a
raw copy preserves the whole original EXIF, including maker notes and an embedded
thumbnail that is a second copy of the patient's document, not just the curated
`EXIF_TAGS` subset. **And the justification was void**, so deleting APP1 deleted a real
orientation tag and would have handed a clinician a sideways lab report.

**What was chosen: carry the tag, do not re-encode the document.** `stripJpegMetadata`
now reads Orientation out of the old APP1 and writes a **34-byte APP1 of its own**
holding that tag and nothing else. `records.tsx` pins `quality: 1` explicitly, so
`RawImageExporter` is a decision rather than an inherited default.

The alternative — passing `quality < 1` to route through `CompressionImageExporter`,
which yields upright pixels and drops orientation itself — was rejected on three
grounds, in order of weight:

1. **It re-encodes a photograph of printed text.** The document image is the input to
   the extraction pipeline; compressing it to avoid writing 34 bytes degrades the one
   thing that pipeline exists to read.
2. **It does not solve the problem it is offered for.** `CompressionImageExporter`
   calls `copyExifData`, and `EXIF_TAGS` names the GPS family — so the strip is still
   required, and the metadata question is unchanged.
3. **It is correct on one path only.** Carrying the tag is correct on every path — raw
   copy or re-encode, iOS or Android, capture or file pick — including the iOS raw-copy
   branch that is one non-nil `imageURL` away, and including a JPEG picked from Files,
   which no exporter ever touches. An assumption about one exporter is what failed here
   the first time.

The replacement is authored rather than salvaged, which makes the minimisation
provable: exactly one tag survives, and it is one this file wrote. Nine tests cover it,
three of them near misses that a plausible implementation fails — a little-endian TIFF
block read in its own byte order (a big-endian-only reader silently loses the tag), an
orientation living in **IFD1** ignored because that is the *thumbnail's* orientation and
a different image's fact, and the right tag in the wrong type refused rather than read
anyway. All three were verified by mutation: each mutation reddens exactly its own test.

### 5b. `withVoiceAudio.js` forbade the camera, and the reason it gave stopped being true

The audio-only config plugin held `android.permission.CAMERA` in
`FORBIDDEN_PERMISSIONS`, on the stated ground that *"this app has no video path at
all"*. That was true until this screen. Two things follow and they point the same way:

1. The premise is gone. The product now uses the camera, for one still capture, on
   one screen, with a declared purpose.
2. **The entry could not have delivered what it claimed anyway.**
   `withAndroidManifest` edits the APP manifest; `expo-image-picker`'s own library
   manifest declares CAMERA and merges it in at Gradle time regardless. A control
   that claims something it does not do is worse than none.

**The guarantee that entry stood for is untouched, and it never lived there:** the
voice session cannot publish video because `room_tokens.py` grants
`"canPublishSources": ["microphone"]` with `canPublishData` pinned false, the SFU
carries one audio codec, and `enableMultitaskingCameraAccess` is false.
`e2e/voice.spec.ts` now asserts those two directly instead of asserting the absence of
a manifest line.

**The list did not become empty**, because a vacuous gate is worse than a retired
one. It holds what the new dependency actually brings: `expo-image-picker`'s library
manifest also declares `READ_EXTERNAL_STORAGE` and `WRITE_EXTERNAL_STORAGE`
(maxSdkVersion 32) for a camera-roll path this app never invokes —
`launchCameraAsync` and the document picker's SAF flow need neither. Those are now
removed with `tools:node="remove"` via `withBlockedPermissions`, which reaches the
merged manifest where the old filter could not.

**The picker's own config plugin is deliberately NOT registered.** Passing it
`microphonePermission: false` calls `withBlockedPermissions` on `RECORD_AUDIO` and
would silence the voice path app-wide; omitting the field writes Apple's English
default over the localised microphone string. `NSCameraUsageDescription` is declared
the way `NSMicrophoneUsageDescription` already is — through `expo.locales`, tr first
(invariant 5).

### 5c. INT-224's store gate caught all of this, which is the system working

The camera did not slip in. `tests/legal/test_store_labels.py` reddened twice:
`every_declared_permission_is_classified_against_the_inventory` (no inventory row for
`android.permission.CAMERA` or `NSCameraUsageDescription`) and
`no_automatable_row_fails_on_the_tree_as_it_stands`
(`apple/no-sensor-the-product-cannot-use`). Both are fixed by stating the truth:

- both permissions are classified into the existing **`document_object`** flow — a
  photograph of the patient's own report is a patient-uploaded document, which that
  flow already annotates. **No new flow, no new category, no new basis.** The
  classification says what **this app** does — it requests no photo-library access,
  stores the capture nowhere but the upload, and strips the metadata — and explicitly
  does **not** claim the frame never reaches the photo library: on Android the OEM
  camera app servicing `ACTION_IMAGE_CAPTURE` commonly writes its own copy to DCIM and
  no application flag prevents it. That sentence feeds a store privacy answer, so it
  had to be a statement about this app's behaviour rather than about the photo.
- `apple/no-sensor-the-product-cannot-use` changed from *no camera* to **no sensor
  without a code path**, in two directions:
  1. every **declared** sensor permission must name the shipped module that uses it —
     the obligation a store reviewer actually applies, and stronger in the direction the
     old form could not see: a permission that outlives its feature now fails;
  2. every sensor **family** must be either declared-with-a-path or **blocked** with
     `tools:node="remove"`. This closes the blind spot the rule itself had:
     `expo.android.permissions` is only what this app *writes*, the installed manifest
     is that merged with every dependency's AAR, and the merged file does not exist
     until a prebuild — which is exactly how `expo-image-picker` brings CAMERA in. A
     library declaring `ACCESS_FINE_LOCATION` would have passed and shipped. It now
     fails unless the family is blocked, and the location family is therefore blocked
     in `withVoiceAudio.js` even though nothing declares it.
  Seven tests, including the near misses: a declared sensor with no path fails, an
  unknown sensor permission fails, a family neither declared nor blocked fails (once
  per family), and a non-sensor permission needs no path — the last stopping the rule
  from flagging everything. Microphone is modelled as a family (`RECORD_AUDIO` *and*
  `MICROPHONE`) because it is one sensor with two spellings, and a rule that split them
  would demand a block for a permission Android does not have.

## 6. Acceptance, line by line

**"camera+file upload" — met.** `launchCameraAsync` beside `getDocumentAsync`, both
through one `ingest`: one pre-check against the server allow-list, one metadata
strip, one digest, one ingest. A capture reporting neither a content type nor a
usable name resolves to no type and is refused rather than guessed. The permission is
requested, a refusal is answered with `records.err.camera` rather than silence,
`quality: 1` is pinned so the exporter choice is a decision rather than an inherited
default, and `exif: false` keeps the metadata dictionary out of JavaScript entirely
(separate from the byte strip, which governs what the file carries).

**"AV/processing states" — the AV half met; the processing half built and shut.**
Scanned-for-malware and read-for-content are different questions with different
answers, so there are two states rather than one overloaded chip, and only a `clean`
document is ever read. The reading state has four values — `cards`, `reading`,
`unread`, `refused` — and `noExtractionFeed` returns `unread` for every document,
always. A refused extraction says so **without alarming** (invariant 2): a quiet line
that also says the document itself is still in the record, no error styling, no
"hata", "başarısız" or "uyarı" (asserted).

**"confirm-before-use" — built, and unreachable.** §2. The cards, the two verdicts,
the no-editor rule and the no-optimistic-write rule are all real and tested; with the
production source, `record()` acknowledges nothing, so `applyDecision` leaves every
card `pending` and no card can ever show as confirmed. That is the correct
fail-closed direction — INT-140's rule, that a state the server has not confirmed is
never shown as done, applied to a server that cannot confirm anything.

**"provenance boxes" — built, and unreachable.** The panel draws the normalised
rectangle on a page-shaped frame (ISO 216 portrait), names the page as one
non-breaking ungrouped atom (`Sayfa␣2`), says in words which third of the page the
box sits in — a rectangle is invisible to a screen reader — and offers the document
itself, which is the full-fidelity provenance. It renders no page image: a PDF
renderer is not shipped, and a schematic that shows position honestly beats a
thumbnail of content the patient can already open.

**It expresses provenance and never confidence.** No accuracy figure exists for this
pipeline and none may be invented (invariant 20, HB-A13), so the answer to *"how do I
know this is right?"* is *here is where it came from*. A test greps the three record
surfaces for `confidence`, `certainty`, `score`, `accuracy` and `probability`, and
every `records.*` string for `%` and `yüzde`.

### Why the issue stayed open (3 Sep 2026) — superseded by §10

Nothing publishes a document extraction. There is no API route that serves
`UnconfirmedRecordItem`s and none that accepts a confirmation, so the three clauses
above cannot be exercised by a patient on a device today. The producer is **INT-124**
(*"Lab-report->JSON via the self-hosted extraction LLM"*, P2). **The transport — a
route that publishes confirm cards and accepts a decision — is owned by no issue in
`docs/backlog/issues.yaml`, and no id was minted for it here.**

The mechanism is built, the gate is wired, and it fails closed with the content
empty. `noExtractionFeed` is the only production `ExtractionSource` and a test asserts
there is exactly one — the same shape `NoLayout` and `NoTerminology` already have on
the server. This is HUMAN_BLOCKERS.md rule 2 applied to an unbuilt dependency rather
than an unanswered question.

## 7b. What the security review changed (3 Sep 2026)

The review confirmed the merge-order reasoning against the installed library manifest
and the room token as a real transport-level control, and found **one blocking defect
plus three weaknesses**. All four are fixed above; recorded here because the shape of
the mistake is the useful part.

**The defect.** The orientation justification was checked against the wrong function.
`copyExifData` does omit `TAG_ORIENTATION` — and this app never reaches it, because
`quality` defaults to `1.0` and that routes Android to the raw copier. The error was not
a missing check; it was checking a function whose name matched the question instead of
following the branch that selects it. The evidence file asserted it twice and the test
file's header asserted it a third time, so a wrong premise had propagated into three
places that all read as corroboration.

**Two tests asserted text where behaviour was available.** The strip-before-digest
assertion compared `indexOf("stripJpegMetadata")` with `indexOf("sha256(bytes)")` in the
module's source — which passes for any arrangement where the identifier merely appears
earlier, a strip moved into a dead branch included. It is now a behavioural test in
`api.test.ts`: an APP1-bearing JPEG goes through `upload`, and the minted `sha256` is
asserted equal to the digest of the **PUT body**, the GPS pointer tag absent from that
body, and exactly one 34-byte APP1 left. Disabling the strip reddens it (verified).
Likewise `voice.spec.ts` grepped `room_tokens.py` for a literal; it now points at
`tests/voice/test_room_tokens.py`, which decodes a minted JWT and asserts the grant
surface.

**A compliance claim overstated what the app controls.** *"the capture never reaches the
photo library"* was true of this app's code and not of the outcome — the OEM camera app
servicing `ACTION_IMAGE_CAPTURE` commonly writes its own copy to DCIM. That sentence
feeds a store privacy answer, so it now states this app's behaviour and names what is
outside its control.

**And the new checklist rule had the blind spot it was written to answer.** §5c.

Two limits are reported rather than fixed, both now named in the `records` threat row:
the stripper **fails open** on a JPEG it cannot walk (file integrity chosen over
invariant 6 — refusing the upload is the other option and is not obviously worse), and
**PNG's `eXIf`/XMP containers are not stripped** at all.

Also noted by the review and **not this issue's to fix**: `make security` does not exist
as a Makefile target on `main` either, while the constitution names a ten-gate version
of it. A standing gap, already tracked.

### 10.2 The route

`GET` answers `{state, items}` with `state ∈ {read, reading, unread, refused}`. Only a
scanned-clean document is passed to the source at all — a quarantined or rejected one is
*unread* and the source is never asked (asserted by counting). Each item is exactly
`{id, kind, summary, unit_conflict, date, provenance: {document_ref, page, bbox}, decision}`
— the OpenAPI schema is asserted to be that closed set, so no level, confidence or value
field can appear. `id` is a digest of the item's position, kind, page, box and character
interval: never of its text, and an extraction re-read differently yields ids a stale
verdict misses rather than lands on.

`POST` takes `{card_id, decision}` with `extra="forbid"`; `by`, `actor`, `source`,
`value_magnitude`, `unit` and `summary` are each a 422 whose body does not echo the value.
A confirmed item goes through `confirm_record_item(item, at=now)` into a per-patient
`ConfirmedRecordStore.admit`; the admitted item's observation equals the extracted one,
its actor is `PATIENT` (read off INT-170's table) and its `source_ref` is the document. A
declined item is recorded and admitted nowhere. The same verdict twice is acknowledged
and admitted once; a contrary verdict on a settled card is `409 already_decided`. The
check, the audit entry and the effect run under one lock, audit first.

Refusals, whole rather than trimmed: an item carrying the data-boundary control token
(`carries_control_token`, the one fence's own check — near miss: the same word without
the marker is served), or a box whose `document_ref` is not `doc:<this document>`.
Both routes declare and enforce `documents`; a refused read appends nothing; every read
and verdict appends `api.document.extraction.{read,confirm,decline}` with `doc:<id>` and
the scope, and the chain verifies. The patient's access log classifies the three as
*record viewed* / *record updated* (`intake_platform.access_log`). No log record carries
the printed name, the magnitude or the unit (asserted with `caplog` at DEBUG).

**The production source reads nothing.** `ApiState.extractions` defaults to
`NoExtractionSource`, which answers *unread* for every document — asserted — because every
producer is shut: `NoLayout`/`NoOcr` behind the parser-sandbox ADR, and row 9 refusing on
the PHI path until a host serves it (INT-381). The fail-closed default moved from the app
(`noExtractionFeed`, deleted) to the server, so there is one gate and not two that could
disagree.

### 10.3 What was not done, and why

- **No new patient copy.** Zero new `tr`/`en` keys; the reading, refused, intro and
  not-saved lines are the 3 Sep strings. The intro (`records.confirm.intro`) is now an
  `AnnouncedText` so the arrival of cards after a wait is heard (SC 4.1.3) — its words are
  unchanged. Nothing to record in `PROSE_REGISTER_FINDINGS`; `make check-i18n` passes.
- **No durable store.** `ConfirmedRecordStore` is INT-121's and lives in process memory.
  Writing confirmed lab values to a table is a decision to persist a structured copy of
  patient health data — a new invariant-18 annotation and an owner's yes (CLAUDE.md,
  *when to stop and ask*). It was not made. The failure is in the safe direction: a
  verdict lost to a restart shows the card *pending*, and a pending item reaches no note.
  Named in the `records` threat row.
- **Guard flags other than `unit_conflict` are not published.** `UnconfirmedRecordItem`
  carries only `unit_conflict`; the INT-124 verdicts (`no_expectation`, `two_number_cell`,
  …) sit on `DocumentExtraction.verdicts` for the clinician side. Showing them to a patient
  would need new copy per flag and a clinical decision about what a patient should be told;
  `unit_conflict` already has both.
- **No edit affordance** — unchanged from §2: the server has no path that takes a restated
  value.
- **INT-313.** Its five acceptance clauses (publish with boxes, consent-scoped and
  audited; a verdict route with no `by=`; `unit_conflict` intact; nothing
  instruction-shaped, through the one fence; no optimistic write end to end) are what
  `tests/records/test_extraction_transport.py` — the path that row names — pins. The row is
  left untouched here, one issue per PR, for the coordinator to close or re-scope.
