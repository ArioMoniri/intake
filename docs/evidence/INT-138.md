## 2. The affordance for confirming a numeric value, and why

**The card offers two verdicts and no text field.** *Evet, doğru* / *Hayır, doğru
değil*, and a third control that is not an edit: *Belgede gösterin*, which opens the
provenance panel.

Three things forced that shape and they agree:

1. **CLAUDE.md invariant 22** — *no free numeric text entry on the clinical critical
   path*. A confirm card with an editable lab value is exactly that, and it is the
   worst instance of it: the patient would be retyping a number they are reading off
   a screen, which is a transcription step nobody asked for and a place a decimal
   separator can move.
2. **`confirm_record_item` has no path that takes a restated value.** INT-121, in its
   own words: *"the observation carries over unchanged: confirming is agreeing with
   what was extracted, never restating it. A patient who disagrees produces a
   correction, not an edited extraction."* An editor on this card would mint
   something the server cannot accept — a UI affordance whose result has nowhere to go.
3. **INT-133 already answered the same question once.** `FactOutcome` is
   `confirmed | changed | stopped`, and its comment records why: *"`changed` records
   disagreement without capturing a replacement value"*. `CardDecision` is
   `confirmed | declined` for the same reason, and a test asserts the type has no
   third member and that `decisionBody` carries exactly `{card_id, decision}` — no
   magnitude, no unit.

**What a disagreeing patient gets instead is the source.** The honest way to settle
"is this 30 or 3.0?" is to look at the page it came from, not to retype it from
memory — which is why the provenance panel is the third control on the card rather
than a detail view somewhere else.

`summary` itself is **carried, never re-rendered**. It arrives from `summarise_item`
already under the invariant-22 display rule (`useGrouping:false`, plain positional
notation, number and unit joined by a NO-BREAK SPACE). `extraction.ts` contains no
`parseFloat`, no `parseInt`, no `toFixed`, no `NumberFormat` and no `toLocaleString`,
and a test greps for all five. The reason is the same one files/03 §4.9.6 gives:
`1.500` reads two ways, the two readings differ by a factor of 1000, and a second
reading on the client is a second answer to a question the server already answered.

## 3. How the unit conflict is surfaced

INT-121's guard flags rather than converts: on disagreement `unit_conflict` is set,
the magnitude stays **unscaled**, the printed unit stays **as printed**, and the flag
rides to FHIR as an extension.

On the card that becomes a distinct amber block under the line, carrying
`records.card.unitConflict` — *"Bu satırdaki birim beklenenden farklı. Değer belgede
yazdığı gibi bırakıldı."* Three properties:

- **The value above it is not touched.** The card renders the same `summary` string
  whether or not the flag is set. A screen that "helpfully" corrected the display
  would undo the guard on the one surface a human could still catch it.
- **The copy says what was NOT done.** *"bırakıldı"* — left as it was. The patient is
  told the app did not convert, which is the fact that matters when the printed unit
  is the wrong one (files/03 §4.9.6's ALT `0 - 55 U/mL`).
- **It is amber, not the emergency pair.** files/02 §5.3 reserves the emergency
  colours for the RED route; a printed unit that disagrees with an expectation is not
  an emergency and must not be dressed as one.

An **unchecked** value is a different state and is not shown as agreement: the server
reports it in `DocumentExtraction.units_unchecked` and the card simply carries no
flag. Nothing on the screen says a unit was verified.

A near-miss control guards the parser in the other direction: `unit_conflict` is a
flag, not a level, and is **accepted** (`invariant 1 — a document is not a rules
engine`, third test). Without it the level-shaped-key refusal would pass for a parser
that rejected every optional key, which would delete the unit guard from the screen.

## 4. What the client refuses, and why each refusal is a mirror

`parseExtraction` is a closed-shape reader, and every refusal restates a server-side
property rather than inventing a client-side one:

| refusal | mirrors | near-miss control |
|---|---|---|
| a level-shaped key refuses the **whole** extraction | `extract_record_items` / `LEVEL_SHAPED_KEYS` (invariant 1) | `unit_conflict` is accepted |
| an item with no `provenance`, no page or no rectangle is refused | `SourceBox` is a defaultless field | a well-formed box parses to `{documentRef, page, bbox}` |
| a bbox outside `[0,1]`, inverted or empty is refused | `SourceBox.__post_init__` | `[0.1, 0.2, 0.5, 0.3]` parses |
| a key the shape does not declare refuses the whole payload | `ITEM_KEYS`, closed | the six declared keys parse |
| an empty `summary` is refused | *"an extracted item renders something for the patient to confirm"* | a real line parses byte-for-byte |
| a `state` outside the closed set is refused | `FEED_STATES` | `read`/`reading`/`unread` parse |

`RECORD_ITEM_KINDS` is asserted against `packages/clinical-schemas/src/generated/
models.ts` member-for-member, by reading the generated file — so the app's vocabulary
is the schema's, not a copy that can drift.

No refusal message names a printed value, a magnitude or a line of a document
(invariant 6): the parser returns a `refused` **state**, and it carries no detail.

## 5. Two things the camera brought with it

### 5a. A photograph of a lab report carries where the patient was standing

`expo-image-picker`'s Android exporter (`CompressionImageExporter`) calls
`copyExifData`, and `ImagePickerConstants.EXIF_TAGS` names the GPS family
explicitly — `TAG_GPS_LATITUDE`, `TAG_GPS_LONGITUDE`, `TAG_GPS_TIMESTAMP` and
sixteen more. Without an answer, the camera this issue adds would have put the
patient's coordinates into the object store alongside their medical document.

Location has never been declared as a category of personal data anywhere in this
repository, and invariant 18 requires an inventory annotation
`{category, purpose, basis, retention, recipients}` for every new data field. Adding
one would be a decision to persist a new category of personal data, which CLAUDE.md
makes a stop-and-ask. **Not persisting it needs no decision**, so the bytes are
stripped instead: `stripJpegMetadata` removes every **APP1** segment — the container
EXIF and XMP both live in — before `sha256` sees the bytes, so the digest declared to
the server is the digest of what actually travels.

Three properties, each with a test:

- **APP1 only.** APP0 (JFIF) and APP2 (ICC colour profile) stay; dropping a colour
  profile would change how the document renders for the clinician who reads it.
- **The scan stops at SOS.** Past the start of scan the stream is entropy-coded image
  data, and a `0xFFE1` pair in the pixels is image, not an APP1 header. The near-miss
  control puts exactly that pair in the scan data and asserts it survives — a parser
  that kept walking markers would cut the image apart, and would pass every other
  test in the file.
- **Anything it cannot read whole is returned untouched.** A truncated segment, a
  missing marker byte, a PNG, a PDF, two bytes of nothing. A partially rewritten JPEG
  is a corrupt document the patient believes is their report, which is worse than the
  metadata.

**Orientation turned out not to be the cost it looks like**, and this was checked in
the two exporters rather than assumed: iOS `ImageUtils.readImageFrom` calls
`fixOrientation()` and re-encodes from the bitmap, and Android's `copyExifData` lists
`TAG_ORIENTATION` among the `omittableTags` it deliberately does **not** copy. Both
hand over an upright image with no orientation tag to lose.

### 5b. `withVoiceAudio.js` forbade the camera, and the reason it gave stopped being true

The audio-only config plugin held `android.permission.CAMERA` in
`FORBIDDEN_PERMISSIONS`, on the stated ground that *"this app has no video path at
all"*. That was true until this screen. Two things follow and they point the same way:

1. The premise is gone. The product now uses the camera, for one still capture, on
   one screen, with a declared purpose.
2. **The entry could not have delivered what it claimed anyway.**
   `withAndroidManifest` edits the APP manifest; `expo-image-picker`'s own library
   manifest declares CAMERA and merges it in at Gradle time regardless. A control
   that claims something it does not do is worse than none.

**The guarantee that entry stood for is untouched, and it never lived there:** the
voice session cannot publish video because `room_tokens.py` grants
`"canPublishSources": ["microphone"]` with `canPublishData` pinned false, the SFU
carries one audio codec, and `enableMultitaskingCameraAccess` is false.
`e2e/voice.spec.ts` now asserts those two directly instead of asserting the absence of
a manifest line.

**The list did not become empty**, because a vacuous gate is worse than a retired
one. It holds what the new dependency actually brings: `expo-image-picker`'s library
manifest also declares `READ_EXTERNAL_STORAGE` and `WRITE_EXTERNAL_STORAGE`
(maxSdkVersion 32) for a camera-roll path this app never invokes —
`launchCameraAsync` and the document picker's SAF flow need neither. Those are now
removed with `tools:node="remove"` via `withBlockedPermissions`, which reaches the
merged manifest where the old filter could not.

**The picker's own config plugin is deliberately NOT registered.** Passing it
`microphonePermission: false` calls `withBlockedPermissions` on `RECORD_AUDIO` and
would silence the voice path app-wide; omitting the field writes Apple's English
default over the localised microphone string. `NSCameraUsageDescription` is declared
the way `NSMicrophoneUsageDescription` already is — through `expo.locales`, tr first
(invariant 5).

### 5c. INT-224's store gate caught all of this, which is the system working

The camera did not slip in. `tests/legal/test_store_labels.py` reddened twice:
`every_declared_permission_is_classified_against_the_inventory` (no inventory row for
`android.permission.CAMERA` or `NSCameraUsageDescription`) and
`no_automatable_row_fails_on_the_tree_as_it_stands`
(`apple/no-sensor-the-product-cannot-use`). Both are fixed by stating the truth:

- both permissions are classified into the existing **`document_object`** flow — a
  photograph of the patient's own report is a patient-uploaded document, which that
  flow already annotates. **No new flow, no new category, no new basis.**
- `apple/no-sensor-the-product-cannot-use` changed from *no camera* to **no sensor
  without a code path**: every declared CAMERA/MICROPHONE/RECORD_AUDIO/LOCATION
  permission must name the shipped module that uses it. That is the obligation a
  store reviewer actually applies, and it is stronger in the direction the old form
  could not see — a permission that outlives the feature it was added for now fails.
  Three tests, including the two near misses (a declared sensor with no path fails; a
  non-sensor permission needs none).

## 6. Acceptance, line by line

**"camera+file upload" — met.** `launchCameraAsync` beside `getDocumentAsync`, both
through one `ingest`: one pre-check against the server allow-list, one metadata
strip, one digest, one ingest. A capture reporting neither a content type nor a
usable name resolves to no type and is refused rather than guessed. The permission is
requested, a refusal is answered with `records.err.camera` rather than silence, and
`exif: false` keeps the metadata dictionary out of JavaScript entirely (separate from
the byte strip, which governs what the file carries).

**"AV/processing states" — the AV half met; the processing half built and shut.**
Scanned-for-malware and read-for-content are different questions with different
answers, so there are two states rather than one overloaded chip, and only a `clean`
document is ever read. The reading state has four values — `cards`, `reading`,
`unread`, `refused` — and `noExtractionFeed` returns `unread` for every document,
always. A refused extraction says so **without alarming** (invariant 2): a quiet line
that also says the document itself is still in the record, no error styling, no
"hata", "başarısız" or "uyarı" (asserted).

**"confirm-before-use" — built, and unreachable.** §2. The cards, the two verdicts,
the no-editor rule and the no-optimistic-write rule are all real and tested; with the
production source, `record()` acknowledges nothing, so `applyDecision` leaves every
card `pending` and no card can ever show as confirmed. That is the correct
fail-closed direction — INT-140's rule, that a state the server has not confirmed is
never shown as done, applied to a server that cannot confirm anything.

**"provenance boxes" — built, and unreachable.** The panel draws the normalised
rectangle on a page-shaped frame (ISO 216 portrait), names the page as one
non-breaking ungrouped atom (`Sayfa␣2`), says in words which third of the page the
box sits in — a rectangle is invisible to a screen reader — and offers the document
itself, which is the full-fidelity provenance. It renders no page image: a PDF
renderer is not shipped, and a schematic that shows position honestly beats a
thumbnail of content the patient can already open.

**It expresses provenance and never confidence.** No accuracy figure exists for this
pipeline and none may be invented (invariant 20, HB-A13), so the answer to *"how do I
know this is right?"* is *here is where it came from*. A test greps the three record
surfaces for `confidence`, `certainty`, `score`, `accuracy` and `probability`, and
every `records.*` string for `%` and `yüzde`.

### Why the issue stays open

Nothing publishes a document extraction. There is no API route that serves
`UnconfirmedRecordItem`s and none that accepts a confirmation, so the three clauses
above cannot be exercised by a patient on a device today. The producer is **INT-124**
(*"Lab-report->JSON via the self-hosted extraction LLM"*, P2). **The transport — a
route that publishes confirm cards and accepts a decision — is owned by no issue in
`docs/backlog/issues.yaml`, and no id was minted for it here.**

The mechanism is built, the gate is wired, and it fails closed with the content
empty. `noExtractionFeed` is the only production `ExtractionSource` and a test asserts
there is exactly one — the same shape `NoLayout` and `NoTerminology` already have on
the server. This is HUMAN_BLOCKERS.md rule 2 applied to an unbuilt dependency rather
than an unanswered question.

## 7. Invariants touched

- **1** — a level-shaped key refuses the whole extraction, client side, mirroring the
  server. The screen renders no level and has no field one could occupy.
- **2** — every new string is ≤ B1, `siz`, no short imperative in prose keys, no
  doubled-polite form in controls; the failed-to-read line is calm. The whole
  catalogue passes `tests/release` including the PolicyGuard sweep.
- **5** — 26 new keys, tr first, en mirrored, same order in both files, every one
  referenced by shipped code.
- **6** — no console, no telemetry, no metrics on any of the four new modules
  (asserted). A source box is a coordinate into a patient's page and stays on the
  device; the filename still never crosses the wire; the JPEG strip removes location.
- **12** — the confirm gate is INT-121's and is not re-implemented: the client carries
  a verdict, never a value, and cannot assert who confirmed.
- **14** — nothing rendered here is fed back to a model. There is no prompt, no
  instruction string and no model call anywhere on this path.
- **17** — no placeholder, no skipped test, no TODO; the extraction seam is a shut
  gate rather than an empty function.
- **18** — the camera permission carries an inventory annotation, through the existing
  `document_object` flow. No new category of personal data is persisted.
- **20** — provenance, never a percentage; asserted by grep over three modules and the
  whole `records.*` catalogue.
- **22** — the number is carried and never re-rendered; the page atom is ungrouped and
  non-breaking; there is no numeric text entry on the card; nothing on this path
  reaches a TTS lane (asserted).

Reachability is asserted across `APP_STEPS = [0.9, 1.0, 1.3, 1.6, 2.0]` rather than at
1.0, because the app's own text control replaces the OS value (INT-295): every new
control label leaves room for a glyph beside the button chrome at every step on both
phone widths, the decision buttons are stacked rather than sharing a row — half a row
at 2.0 cannot hold *"Hayır, doğru değil"*, and a wrap row gives its items no shrink,
which is the INT-295 defect — and nothing on the card or the panel truncates.
