- **The SSM bootstrap:** every value shell-quoted, tracing off, the harness

- **The upload command.**
- **The SigV4 presigner:** AWS's documented GET example reproduces signature

  live stack never named, every tool pinned by version and sha256, the pins

### The gitleaks failure on main, and its fix

- **The six findings.** Reproduced with the pinned binary (8.24.3, checked
  against its published sha256), they are:
  - `deid-tr-ner-v1-d4faec57` (the actions cache key);
  - `admin:$${INDEXER_PASSWORD}` (an env-var reference);
  - `WAF/CrowdSec` twice (prose);
  - a JWT-shaped test fixture twice, in commit 2c6a5dcf.

  The first four are already allowlisted in `.gitleaks.toml`, but in
  `[[allowlists]]` tables, which gitleaks reads only from 8.25. The same scan
  under 8.30.1 reports 2.
- **Red.** `tests/ci/test_gitleaks_pin_compat.py`: `1 failed, 2 passed`.
- **Fix.** The same three rows move into the global `[allowlist]` table.
  Under 8.24.3 the scan then reports 2, and under 8.30.1 it reports 2.
- **The fixture.** The owner approved option (a) on 3 Oct 2026, relayed in
  this session: *"ignore the two old token fingerprints"*. `.gitleaksignore`
  gains exactly
  `2c6a5dcf299b997682602044d14f79d8f9ac35d7:apps/embed-sample-partner/src/partnerBackend.test.ts:jwt:39`
  and `…:jwt:41`. The pinned set in
  `test_gitleaksignore_rows_are_fully_scoped_and_only_shrink` rises by those
  two. The token decodes to `"signature-sample"`, so nothing needs rotating,
  and INT-431 has since removed it from the tree.
- **Green.** Pinned gitleaks over main's history reports `no leaks found`,
  and `tests/ci/test_gitleaks_pin_compat.py` plus `test_security_gates.py`
  pass. The permission system refused my `git add` of the gate files, so the
