# INT-385: Record quantities render with the Turkish decimal comma as one number+unit atom

**Epic:** E07-records · **Phase:** P1 · **Sec-Row:** records · **GitHub:** #635
**Found by:** INT-124 (PR #634), while that PR was queued. It had not merged when this
branch was cut, so the change stays on the render path and does not touch the parse path
that PR rewrites.

## Problem
CLAUDE.md invariant 22: *"Numbers never cross a representation boundary unguarded. …
`useGrouping:false` for every clinical quantity; number + unit is one non-breaking atom."*

INT-121's `render_quantity` returned `f"{magnitude:f}"`, which has a full stop as its decimal
point, and it wrote that for every reader. A Turkish reader takes a full stop as grouping
(files/03 §4.9.6). On a Turkish screen, `12.500` is twelve thousand five hundred. On `main`,
before this change:

```
>>> render_quantity(Decimal('12.5')), render_quantity(Decimal('0.05'))
('12.5', '0.05')
>>> summarise_item('Kreatinin', Decimal('12.5'), 'mg/dL')
'Kreatinin 12.5\xa0mg/dL'
```

That summary is the line the patient's confirm card shows. The clinician note also carries it
verbatim, as `imported_objective`. Both readers read Turkish. Nothing flows yet, because
HB-C24's range table is empty and no route publishes an extraction. The defect was latent,
and it would have broken the invariant as soon as values flowed.

The app had a second form of the same defect. `formatQuantity` in `lib/health/format.ts` is
the app's quantity helper (`useGrouping:false`, the U+00A0 atom), and the intake's measured
answers print through it. It capped every number at one fraction digit, so it wrote 0.05 as
`0,1`.

## Change
Server, `packages/intake_platform/src/intake_platform/records/`:
- `numbers.py`
  - `DECIMAL_SEPARATORS` is a closed, read-only table: `{"tr": ",", "en": "."}`. It records
    the decimal point each locale's reader reads.
  - `render_quantity(magnitude, *, locale)` writes positional notation with the locale's
    point: no grouping, no exponent, and the printed precision kept (`2.50` is `2,50` in
    `tr`). `locale` has no default. A locale missing from the table raises
    `QuantityLocaleUnknown`, whose message does not echo what it was given (invariant 6).
  - `quantity_atom(magnitude, unit, *, locale)` joins the number and the unit with U+00A0
    NO-BREAK SPACE, as before.
- `extraction.py`
  - `SUMMARY_LOCALE = DEFAULT_LOCALE` (`tr`). The stored summary is written once, from a
    Turkish report, for two Turkish readers.
  - `summarise_item(..., *, locale)` passes the locale through. `extract_record_items` passes
    `SUMMARY_LOCALE`.
- `__init__.py` exports `DECIMAL_SEPARATORS` and `QuantityLocaleUnknown`.

Mobile:
- `apps/mobile/src/lib/health/format.ts`: `formatNumber` (behind `formatQuantity` and
  `formatRange`) writes exactly as many fraction digits as the value's shortest round-trip
  decimal has, and no more. `Number.prototype.toString` gives that count, including in its
  exponent forms (`5e-7`, `1e+21`). It is capped at 20, the ES2020 Intl limit.
  `useGrouping:false` and the locale tag are unchanged. Every existing caller already passes
  a whole number or a value rounded to one place, so none of their output changes. The
  existing health and intake tests pin that.
- The confirm card is unchanged, and so is `records/extraction.ts`. INT-138 designed the
  client as a courier for the number and not a second renderer. That test
  (`holds no number formatter and no number parser`) still holds. The card shows the atom
  the server wrote, byte for byte.

**How the two agree.** `tests/fixtures/records/quantity_render.json` is one table of INT-385's
four magnitudes × `tr`/`en`, each row holding the exact atom. The server's `quantity_atom` is
held to it in `tests/records/test_quantity_render.py`. The app's `formatQuantity` is held to
the same file in `apps/mobile/src/lib/records/extraction.test.ts`, and so is the confirm
card's verbatim carriage of each atom. The Python test also checks that the app test reads
that file, so neither side can drop out of the contract quietly.

**The TTS path is not touched.** No file under `packages/protocols`, `packages/voice-clips`
or `services/voice-runtime` changed. A test asserts that none of them imports
`intake_platform.records`, and that the records package imports no speech, voice or clip
module. The compiler still expands every numeral to Turkish orthography before any TTS model
sees it.

## Tests (TDD)
- `tests/records/test_quantity_render.py` (new, 52):
  - **Round trip:** extract → render → re-parse. Printed `12,5`, `12.5`, `12500`, `0,05`,
    `0.05`, `1,5` and `1.5` are each extracted, rendered in `tr` and in `en`, and re-parsed
    twice. The first re-parse is `parse_printed_magnitude`, the per-value resolver the
    ingestion path uses; it refuses a form that reads two ways. The second is a
    locale reader: a test-side model of how a reader of that locale reads the number, which
    is not the renderer. The stored summary round-trips for its Turkish reader, and the
    confirm card carries it unchanged.
  - **Near miss:** `12.500` for 12.5 in `tr` fails (the resolver refuses it as reading two
    ways, and a Turkish reader reads 12500). INT-121's own `12.5` in `tr` fails too. The
    resolver alone would pass it, which is why the reader check exists. The control, `12,5`,
    passes.
  - **`useGrouping:false`:** 12500 is `12500` in both locales, never `12.500` or `12,500`.
    1500000.25 is `1500000,25` / `1500000.25`.
  - **The written form:** the separator per locale, precision kept (`2,50`), sign kept, no
    exponent (`1E+3` is `1000`, `5E-7` is `0,0000005`). The separator table is closed and
    read-only. The joiner is U+00A0 (`unicodedata.name` is `NO-BREAK SPACE`), and a
    plain-space atom fails the round trip.
  - **Refusal:** `de`, `""`, `TR`, `tr-TR` and free text are refused rather than guessed, and
    the refusal does not echo the value it refused.
  - **The shared table:** the server writes every row, every row round-trips for its reader,
    the table covers the four magnitudes in both locales, and the app test reads the same
    file.
  - **Off the speech path:** the two import checks described above.
- `tests/records/test_extraction_eval.py`: INT-121's render assertions call the new
  keyword-only signature, and `2.50` is `2,50` in `tr`.
- `apps/mobile/src/lib/records/extraction.test.ts` (+29): the four magnitudes are covered in
  both locales. For each row, `formatQuantity` writes the server's atom. The card carries the
  atom byte for byte. The atom has the locale's point, no grouping and a single U+00A0.
  12500 is never grouped, the `12.500` near miss fails, and 0.05 is `0,05`.
- `apps/mobile/src/lib/health/format.test.ts` (+1): every digit the value has and no more
  (`0,05`, `1.25`). No exponent at either extreme (`0,0000005`,
  `1000000000000000000000`).

## Acceptance, line by line
1. *"every clinical quantity shown to a patient or clinician renders with the locale's
   decimal separator (tr: comma), `useGrouping:false`, and number + unit as one
   non-breaking atom; the mobile confirm cards (INT-138) and the server renderer agree"*
   - Delivered for record quantities, which is the surface this issue is about. That covers
     the confirm-card summary, the note's `imported_objective` line (it carries the same

     is covered too. The confirm cards and the server agree through one table.
2. *"a round-trip test: extract -> render -> re-parse returns the same value for 12.5, 12500,
   0.05 and 1,5 in tr and en; a near-miss that renders `12.500` for 12.5 fails"*: delivered
   (`TestExtractRenderReparse`, `TestTheNearMissFails`).
3. *"no numeral reaches TTS (the compiler expansion path is untouched)"*: delivered. The
   compiler, the clip path and the runtime are unchanged, and there are two import-boundary
   tests.

## Not in scope, recorded
INT-096 recorded this defect in `services/voice-runtime/src/intake_voice_runtime/typed/render.py`,
and it remains. Four private measure renderers still write `Decimal`'s own `str()`, which has a
full stop:
- `typed.render.render_measure`, the typed profile's numeric rail;
- `note.composer._measure_line`, the clinician note's self-reported measures;
- `summary.builder._measure_text`, the patient summary's measures;
- `clinical_schemas.mappers.document`, the document's measurement and speech-feature lines.

None of them renders a record quantity. The docstring of `render.py` says unifying them "belongs
to whichever issue owns them", and none does. Moving them to `render_quantity` touches the FHIR
document text, the note, the patient summary and a `make safety` test, so it needs its own
issue and its own review. After this PR the note shows a record line with a comma
(`Kreatinin 12,5 mg/dL`) next to a self-reported measure with a full stop. Those measures come
from the stepper, which writes whole centimetres and kilograms today, so no decimal reaches
them yet. That follow-up needs an id from the coordinator, and none was minted here.
