# INT-442 — egress forward proxy for the synthetic AWS host

GitHub #752 · Sec-Row `platform` · ADR-035 · split row 6 of INT-428 · branch `int-442-egress-proxy`, stacked on #751

## Goal

Acceptance, verbatim (GitHub #752):

> - A forward proxy on the synthetic host only, default-deny, admitting just the allow-listed vendor hosts. INTAKE_EGRESS_PROXY_URL is set there and never in the PHI deployment.
> - Tests prove an unlisted host is refused. Deployed and smoked.

INT-428 shipped the hosted lanes, but the synthetic host's API networks are all internal, so a hosted lane had no route out (its split row 6).

## What landed

- **One allow-list, two proxies.** `scripts/security/render_egress_proxy_conf.py` renders two configs from `infra/security/egress-allowlist.yaml`:
  - `build` → `infra/security/squid/squid.conf`, the dev/build proxy. It now skips every `hosted_model_inference` row. Package and weight pulls have no business reaching a model vendor. Today's render is byte-identical to the previous one.
  - `synthetic` → `infra/staging/egress/squid.conf`, the synthetic host's proxy. It renders the `hosted_model_inference` rows and nothing else, exact hosts on 443 only; a glob or a PHI-enabled hosted row stops the render. With no such row it carries no allow rule at all, only `http_access deny all`.
  - Both keep INT-018/INT-203's hardening: `denied_nets` (private, link-local, metadata) before any allow, CONNECT to 443 only, no DNS cache, `host:port`-only CONNECT log, no cache. The synthetic config also sets `pinger_enable off`, because the container holds no `CAP_NET_RAW`.
  - `make egress-conf` / `--check` cover both.
- **The proxy on the synthetic host** (`infra/staging/compose.yaml`, service `egress-proxy`):
  - `ubuntu/squid:6.6-24.04_edge`, pinned by the index digest `sha256:8a3baed4…963c`. It was resolved from Docker Hub's v2 API on 3 Oct 2026.
  - It runs as the image's unprivileged `proxy` user (uid 13) from the start, with `read_only`, `cap_drop: [ALL]`, `no-new-privileges`, uid-13 tmpfs mounts, no published port, and the rendered config mounted read-only.
  - Healthcheck: a TCP connect to 3128. See the finding below.
  - Networks:
    - `outbound` (internal) holds the API and the proxy only.
    - `vendor` (routed) holds the proxy only.
    - The API stays internal-only. Its one way out is the proxy.
  - `INTAKE_EGRESS_PROXY_URL: http://egress-proxy:3128` is set on the api service, the only place in the tree.
- **Never in the PHI deployment.**
  - `intake_platform.model_lanes.guard.egress_proxy_url` is the variable's only reader. It refuses (`EgressProxyRefused`) when the deployment is not synthetic, and when the value is anything but a bare `http://host:port`.
  - `ApiSettings.from_env` calls it at boot, so a PHI process with the variable set does not start.
  - The hosted-lanes plugin reads the proxy through it as well.
- **Proved live on every deploy.** `infra/staging/egress_probe.py proxy` runs as `smoke.sh` step 6, inside the api container. It checks three things:
  - there is no direct route out;
  - `example.com` and the metadata address `169.254.169.254` get the proxy's 403;
  - every hosted row is tunnelled.
  It speaks raw `httpx` on purpose: it tests the network enforcer, not the in-process guard. It sends no credential and reads no body.
- **The vendor rows are the owner's change.** The allow-list file is hook-protected (07 §F rule 2), and an agent edit to it was refused before (INT-428). The change is prepared unstaged in the worktree for the owner to commit:
  - the `openai-api` and `elevenlabs-api` rows;
  - `hosted_model_inference` removed from the egress tests' "awaiting the owner" set;
  - the regenerated `infra/staging/egress/squid.conf`;
  - the INT-001 vendor-gate exception for exactly those two files and those two hosts.
  Until it lands, the synthetic proxy admits nothing, and the code fails closed the same way (`hosted_egress_not_listed`).

## Tests

`tests/infra/test_staging_egress.py` (40 tests):

- **Topology:**
  - the image is digest-pinned;
  - the proxy is unprivileged, read-only, has no capabilities and publishes nothing;
  - the config is mounted read-only;
  - only the proxy sits on the routed network, and the internal leg holds only the API and the proxy;
  - the API names the proxy, and the image bakes `synthetic`.
- **The variable:**
  - nothing in the tree but the staging compose sets it, not even the operator env template;
  - four non-synthetic declarations are refused: empty, `real_phi`, `Synthetic` and `synthetic ` (trailing space);
  - near miss: the exact literal `synthetic` reads it;
  - six malformed URLs are refused;
  - `ApiSettings.from_env` refuses the boot outside synthetic, and the same process declared synthetic boots.
- **The config:**
  - it is generated, its first rule is `deny denied_nets` and its last is `deny all`;
  - it allows `hosted_exact` only when hosted rows exist, and admits exactly the hosted rows;
  - no glob reaches a vendor, and the build config never names a hosted host.
- **Parity.** The synthetic config and the in-process guard (`EgressPolicy.check` with `hosted_model_inference` on `NON_PERSONAL`) agree host for host. The table covers:
  - `example.com` and the metadata IP;
  - every tooling row (on the list for another purpose, so refused by both);
  - lookalikes of every hosted row;
  - the hosted rows themselves.
- **The renderer**, against a fake list with hosted rows (reserved `.example` names, so the INT-001 gate never sees a vendor):
  - hosted rows reach the synthetic proxy and never the build proxy;
  - the allow sits second to last;
  - a glob hosted row is refused.
- **The probe:**
  - it passes when every fact holds;
  - it fails once for each of four broken facts: a direct route, an unlisted host admitted, the metadata IP not refused, a listed host refused;
  - it refuses to run outside synthetic or with no proxy.

## Findings

- **The INT-018 dev proxy's healthcheck cannot pass.** `infra/docker-compose.egress.yml` checks health with `squid -k check`. The rendered config sets `pid_filename none`, and squid then answers `FATAL: no pid_filename configured`. This was observed on the synthetic host on 3 Oct 2026. The dev tier was never booted (HB-I1/HB-I2), so nobody saw it. The synthetic proxy uses a TCP-connect check instead. The dev file is outside this change.
- **The `6.6-24.04_edge` tag ships squid 6.14**, by the running binary's own banner. The licence was re-read at `SQUID_6_14` (commit `a8c54a8f…`): COPYING is byte-identical (sha256 `8177f975…`) and `src/main.cc` keeps the GPLv2+ header. Recorded in `observability/registry.yaml`.
- **Running squid as root and dropping to `proxy` breaks the stdout log.** The worker cannot reopen `/dev/stdout`: `FATAL: Cannot open '/dev/stdout' for writing`, observed on the host. Running as uid 13 from the start fixes it, and it is also the smaller privilege.
