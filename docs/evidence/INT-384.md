# INT-384: Admin console reads the API's flat refusal code, so an IP or unconfigured refusal is named as itself

**Epic:** E12-admin · **Phase:** P1 · **Sec-Row:** admin-console · **GitHub:** #631
**Depends on:** INT-351 (the loader and its `admit()` step, shared by INT-181's `/overview`)

## Problem
`apps/admin-web/src/ops/load.ts` `errorCode()` read the refusal code from
`body.detail.error`. The API does not serve that shape. Its exception handler
(`services/api/src/intake_api/app.py`, `_machine_readable_errors`) returns the
`HTTPException` detail dict as the body itself, so every refusal is a flat
`{"error": <code>}`. The `intake_api.errors` docstring says the same, and
`tests/admin/test_rbac_matrix.py` asserts `response.json()["error"]` for
`forbidden`, `source_ip_refused` and `admin_console_unconfigured`.

So `errorCode()` returned `null` for every real refusal, and `refusal()` fell
back:

| API answer | rendered before | should render |
|---|---|---|
| 403 `{"error":"source_ip_refused"}` (HB-A16 allow-list) | `role_not_permitted` | `source_ip_refused` |
| 503 `{"error":"admin_console_unconfigured"}` (no OIDC verifier) | `unavailable` / `api_unreachable` | `not_admitted` / `console_unconfigured` |

This held on every rendered console page. `/ops` and `/overview` call `admit()`,
and so will INT-182's `/voice` (not yet on `main`; it picks the fix up through
the shared `admit()`). Every outcome was still a refusal and no tile was
painted, so admission never widened. The operator was told the wrong reason,
though. An allow-list miss read as a role problem, and an unconfigured console
read as an outage.

The specs did not catch it because they recorded the gate's refusals as
`{detail: {error: ...}}`, a shape the API never serves. They also used
`role_not_permitted` as the API's 403 code, but the gate raises `forbidden`
(`intake_api.errors.forbidden`).

## Change
- `apps/admin-web/src/ops/load.ts`: `errorCode()` reads the top-level `error`
  key and nothing else. No `detail.error` fallback was kept. The handler is
  installed on every app `create_app` builds, so no deployed API serves the
  wrapper, and a boundary that accepts one shape is easier to reason about
  than one that accepts two. The near-miss below keeps the wrapper from coming
  back unnoticed.
- `apps/admin-web/e2e/ops.spec.ts`, `overview.spec.ts`: the refusal table now
  uses the flat bodies and the codes the gate raises (`unauthorized`,
  `forbidden`, `source_ip_refused`, `admin_console_unconfigured`). The
  `/overview` row now also asserts `data-refusal="<reason>"` on the rendered
  page, as `/ops` already did.

No copy, no i18n key, no API code and no data field changed.

## Tests (TDD)
`apps/admin-web/e2e/ops.spec.ts`, admission block:
- **Positive:** a flat 403 `{"error":"source_ip_refused"}` renders
  `source_ip_refused` (`data-refusal="source_ip_refused"`, and no
  `role_not_permitted`).
- **Near-miss, 403 bodies one step from the flat code:** the FastAPI wrapper
  `{"detail":{"error":"source_ip_refused"}}`, the code under another key
  (`code`), a near code (`source_ip_refused_v2`), and the code in a list. Each
  is still a refusal (`not_admitted`), but with the generic
  `role_not_permitted`. Only `/admin/ops` is dialled.
- **Near-miss, right code at the wrong status:** `source_ip_refused` at 500
  and at 503, `admin_console_unconfigured` at 500, and a 503 carrying the code
  inside the wrapper. Each is `unavailable` / `api_unreachable`, never a named
  refusal, and no tile is painted.
- The refusal table in both specs (4 rows each) now uses the flat bodies.
