the HMAC-SHA-256 key. A 64-character hex value is therefore a 64-byte key, one SHA-256 block.

### Empty means unset, and why deploy.sh now refuses one pairing

Each API reader treats an empty value as absent. main and int-344 use
`os.environ.get(...) or None`, and merge-305 uses `.strip()` and requires all three Twilio keys.
Compose therefore passes each operator key as plain `${KEY}`. An empty key reaches the API empty
and fails closed. `${KEY:?}` would stop compose instead, and `${KEY:-x}` would invent a value.

**The tokenization key changes what the OTP tier does.** The removed test
`test_the_otp_tier_is_left_unconfigured` existed because a tokenization key turns the OTP tier
on. The tier's delivery adapter is then the dev event logger, which answers "sent" and sends
nothing. On main this is unconditional. On merge-305 it is the fallback whenever a Twilio key is
missing. With the key generated, the tier no longer answers 503. What stops a fake send instead
is that every OTP request is attested before delivery (`_require_attested` runs first in
`request_code`, on main and on int-344):

| team id | SMS keys | outcome |
|---|---|---|
| empty | any | every iOS attestation refused (int-344; main refuses all). Android refused until HB-A3. Nothing reaches delivery |
| set | all three | a genuine device reaches the Twilio adapter (merge-305) |
| set | any missing | a genuine device would reach the dev logger: "sent", nothing sent. **`deploy.sh` refuses this**, naming the missing keys and no value |

The replacement tests pin all three rows. They pin the guard's position in deploy.sh (after
`load_env`, before any compose call). They also check that the refusal echoes no value.

### Known gaps, stated rather than built around

- **The API still falls back to the dev logger outside dev.** The complete fix belongs in the
  API: outside dev, no SMS vendor should mean fail-closed delivery (503), not the dev logger. The
  deploy guard covers the staging tier only. It also assumes that the deployed API carries the
  Twilio adapter. If int-344 merges before the adapter does, a team id plus the SMS keys passes
  the guard but reaches the dev logger. So the owner should not set a team id on this host until
  both have landed on main.
- **Setting the SMS keys sends a real phone number through a us-east-1 host to the vendor.** The
  host is synthetic-only (HB-I5, HB-L11), and the vendor needs a signed DPA (invariant 18). The
  runbook says so. Setting the keys is the owner's decision.
- A host initialised before this change has no tokenization key, so `./deploy.sh` stops and
  names it. One re-run of `./init.sh` fills in only what is missing.
- `origin/merge-305` carries its own `docs/evidence/INT-352.md` (the host deploy and k6 run). When
  that lands, the two files merge by section.
