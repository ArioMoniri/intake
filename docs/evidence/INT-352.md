## Part 3: `/version`'s `sbom_digest` (audit F18) and close-out

Date: 2026-09-27 (UTC+3). Branch `int-352-sbom-stamp`, cut from main `d03df3a3` and fast-forwarded to `4bca2ad5` before the backlog edit.

Part 1 left `/version` reporting `sbom_digest: "dev"` on the live host, which is audit finding F18. This part makes the host scripts stamp it and makes the smoke test refuse `dev` in any of the three fields. **Nothing here was deployed.** The laptop has no container runtime (owner ban), and this change does not touch AWS. The live stamp is shown by the coordinator's next run of `deploy.sh` and `smoke.sh`, which run these scripts (see "What the next deploy must show").

### What changed
- `infra/staging/lib.sh`:
  - `build_api_image` is the tier's only build.
  - `stamp_sbom` (init.sh, deploy.sh): has syft write an SPDX JSON SBOM of the built api image to `/etc/intake-staging/releases/<commit>/api-<image id>.spdx.json`, then exports `INTAKE_SBOM_DIGEST=sha256:<hex>` of that file.
    - That path is root-only (0700) and outside the build context, so the SBOM never enters the image it describes.
    - If the same image already has its SBOM, the SBOM is kept. A re-deploy of the same commit therefore keeps its digest and does not recreate the api (deploy.sh stays idempotent).
  - `stamp_sbom_from_disk` (smoke.sh): reads the SBOM and never writes one.
  - `version_verdict`: smoke's `/version` check, moved out of smoke.sh so the tests can run it.
- How syft runs: `docker image save` writes an archive, which is mounted read-only into `anchore/syft` (pinned by digest). The container has `--network none`, `--cap-drop ALL` and `no-new-privileges`, and syft never gets the docker socket.
- Fail closed:
  - If syft exits non-zero, or exits 0 with anything but an SPDX document that lists packages, `stamp_sbom` dies with "refusing to run an image /version cannot name". That happens before any container starts.
  - deploy.sh checks the syft pin before it touches the host, as it does for the object store.
- `infra/staging/compose.yaml`: the api gets `INTAKE_SBOM_DIGEST: ${INTAKE_SBOM_DIGEST:?set by deploy.sh from the release SBOM}`. It is required with no default, so compose starts no api container without a digest.
  - compose interpolates the whole file, so even `compose build` needs a value. `build_api_image` therefore binds `SBOM_DIGEST_DURING_BUILD` to that one call. That value is never exported and is not a digest, so a `/version` carrying it fails smoke (tested).
- `deploy.sh` and `init.sh`: the order is now stamp_revision → build_api_image → stamp_sbom → the first compose call. deploy.sh's final up is `compose up -d --no-build`, so the api runs exactly the image syft described instead of a rebuild.
- `smoke.sh` check 2 now fails in these cases:
  - `dev`, empty or missing in any of `git_sha`, `built_at` and `sbom_digest`;
  - a `git_sha` other than the deployed commit;
  - a `sbom_digest` that is not the sha256 of the SBOM on disk, hashed at check time;
  - an api container whose image is not the one the SBOM describes.
- `docs/runbooks/staging.md`: a new "Release SBOM" section. The deploy/smoke bullets are updated. The "sbom_digest stays dev" gap is replaced by the one that remains: the host SBOM is unsigned, because cosign keyless needs CI's OIDC identity.
