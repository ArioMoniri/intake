## What the console reads (no change here)

| claim | read by | rule |
|---|---|---|
| `aud` | `KeycloakClaimsVerifier._check_claims` | contains `INTAKE_ADMIN_OIDC_AUDIENCE`, as a string or an array |
| `org` | `principal_from_claims` (`_required_id`) | a string matching `[A-Za-z0-9][A-Za-z0-9._:/@-]{0,127}` |
| `tenant` | `principal_from_claims` | absent or null (platform roles), else a string of the same shape |
| `aaguid` | `principal_from_claims` (`_required_id`) → `ActorBlock.authenticator_aaguid` | required, same shape |
| `credential_id` | `principal_from_claims` (`_required_id`) → `ActorBlock.credential_id` | required, same shape |

Four-eyes uses the last two for its "distinct authenticator, distinct credential" rule
(files/08 §2.5).

## What Keycloak 26.1.4 can emit, and what it cannot

Source paths are under https://github.com/keycloak/keycloak/blob/26.1.4/. keycloak.org publishes
no per-patch copy of the docs, so the pinned `.adoc` sources are cited as well.

| fact | source |
|---|---|
| A mapper writes to the access token only when `access.token.claim` is the string `"true"`. | `services/.../protocol/oidc/mappers/AbstractOIDCProtocolMapper.java` (`transformAccessToken`), `OIDCAttributeMapperHelper.includeInAccessToken` |
| `oidc-audience-mapper` adds `included.client.audience`, or else `included.custom.audience`, to `aud`. One audience is serialised as a string and several as an array. | `.../mappers/AudienceProtocolMapper.java` (`setClaim`); `core/.../representations/JsonWebToken.java` (`aud`, `StringOrArraySerializer`); docs "Hardcoded audience": `docs/documentation/server_admin/topics/clients/oidc/con-audience.adoc` |
| The default `roles` scope's *Audience Resolve* mapper also adds every client for which the user holds a client role, so a real `aud` is often `["api","account"]`. | `con-audience.adoc` §"Automatically add audience" |
| `oidc-usermodel-attribute-mapper` reads the user's own attribute values. If there are none, it falls back to the first group that has one (the aggregate flag is off). | `.../mappers/UserAttributeMapper.java` (`setClaim`); `server-spi-private/.../models/utils/KeycloakModelUtils.java` (`resolveAttribute(UserModel, …)`) |
| Value shaping: an empty value produces no claim. With `multivalued` off the first value is used; with it on the value stays a list. `jsonType.label` converts the value. `claim.name` splits on unescaped dots into nested objects. | `OIDCAttributeMapperHelper.java` (`mapAttributeValue`, `convertToType`, `mapClaim`) |
| `oidc-usersessionmodel-note-mapper` emits `userSession.getNote(user.session.note)`. No note means no claim. | `.../mappers/UserSessionNoteMapper.java` (`setClaim`) |
| Notes an authenticator puts on the authentication session with `setUserSessionNote` are copied into the user session when the client session attaches. | `server-spi/.../sessions/AuthenticationSessionModel.java` (`setUserSessionNote` javadoc); `services/.../protocol/oidc/TokenManager.java` (`attachAuthenticationSession`, the `transferredUserSessionNotes` loop) |
| **The stock WebAuthn authenticator records the credential used only as an event detail.** On success it sets `USER_VERIFICATION_CHECKED` and `PUBKEY_CRED_ID_ATTR` (base64url) on the event, then calls `context.success()`. The only note it writes is the challenge (`AUTH_CHALLENGE_NOTE`). | `services/.../authentication/authenticators/browser/WebAuthnAuthenticator.java` (`action`) |
| **Validation writes nothing to the session.** `isValid` matches the stored credential by id, updates the counter and returns `true`. The AAGUID is stored as UUID text and the credential id as **standard** Base64. | `services/.../credential/WebAuthnCredentialProvider.java` (`isValid`, `getCredentialModelFromCredentialInput`) |
| An administrator can *view* a credential's AAGUID ("Show data…"). No mapper or claim is offered for it. | `docs/documentation/server_admin/topics/authentication/webauthn.adoc` §"Managing credentials" |
| User profile: "By default, Keycloak will only recognize the attributes defined in your user profile configuration." Unmanaged attributes are `DISABLED` by default, and then an administrator cannot see or set them either. | `docs/documentation/server_admin/topics/users/user-profile.adoc` §"Understanding Managed and Unmanaged Attributes"; https://www.keycloak.org/docs/latest/server_admin/index.html#user-profile |
| The user profile lives in the realm component `org.keycloak.userprofile.UserProfileProvider` / `declarative-user-profile`, under the config key `kc.user.profile.config`. Realm import imports components. The default profile has four attributes. | `services/.../userprofile/DeclarativeUserProfileProvider.java` (`UP_COMPONENT_CONFIG_KEY`, `getComponentModel`); `model/storage-private/.../DefaultExportImportManager.java` (`importComponents`); `services/src/main/resources/.../keycloak-default-user-profile.json` |
| The `pattern` validator takes `pattern` (and optional `error-message`). `permissions.view`/`edit` take `admin` and `user`. | `user-profile.adoc` §"Built-in Validators", §"Using the JSON configuration" |

**So:**

- `aud`, `org` and `tenant` are stock mappers.
- `aaguid` and `credential_id` cannot come from any stock realm configuration. Keycloak 26.1.4
  computes both at login and then puts them nowhere a mapper can read.

Emitting a plausible constant, such as the all-zero AAGUID or a hard-coded claim, would satisfy
the parser and defeat the four-eyes distinctness it exists for. Nothing like that is done here.

## The mechanism Keycloak lacks (runbook §3), proposed and not built

The smallest mechanism is one provider jar in `/opt/keycloak/providers`. It is an authenticator
that wraps the stock `webauthn-authenticator`, and after a successful assertion it:

- looks up the stored credential the assertion matched;
- calls `setUserSessionNote("intake.webauthn.aaguid", <AAGUID UUID text>)`;
- calls `setUserSessionNote("intake.webauthn.credential_id", <credential id, base64url without
  padding>)`.

`TokenManager` copies both notes to the user session, and the committed note mappers emit them.
Base64url matters here: stored ids are standard Base64, and `+` and `=` fail the console's id
shape.

It is not built here, for three reasons:

- It is Java, and the repository has no Keycloak provider build, signing or deployment path.
- It needs its own issue.
- It waits on an **owner decision**. INT-365 (PR #598) admits the six non-patient-content roles
  with TOTP, which has no AAGUID, while the console requires `aaguid` on every token. The owner
  must either require WebAuthn for every console role or define an actor-block value for a TOTP
  login.

Until the provider exists, a real token lacks both claims and is refused. One test pins that
(`test_without_the_webauthn_notes_the_token_is_refused`).

## Tests (`tests/admin/test_realm_claim_mappers.py`, 49)

- **Mapper → claim, against a recording (16).** Each of the 16 accounts in
  `tests/admin/fixtures/keycloak_claims.json` is reproduced from the realm. The inputs are the
  account's own `org`/`tenant` as user attributes and its `aaguid`/`credential_id` as the two
  notes. The minted `aud`, `org`, `tenant`, `aaguid` and `credential_id` must equal the recorded
  values, which are the claim sets the whole INT-180 suite already drives through the console.
- **Claim → console (3).**
  - A tenant-scoped account (`kc:tenant_admin`) and a platform one (`kc:platform_owner`, no
    tenant) are signed RS256. Each goes through the real `KeycloakClaimsVerifier` with
    audience `api` and through `principal_from_claims`, and each principal field is asserted.
  - A realistic `aud: ["api","account"]` is also admitted.
- **Config shape (2).**
  - All five mappers are on the access token and off the ID token.
  - The audience names the realm's bearer-only `api` client.
- **One-field mutations (13).** Each mutation is applied to a copy of the realm. The same test
  first admits the committed realm, so no mutation can pass vacuously.
  - Two per mapper:
    - `aud` naming `admin-web`, and `aud` off the access token: `ClaimsRejected`.
    - `org` renamed claim, wrong attribute or multivalued, and `tenant` multivalued:
      `MalformedClaims`.
    - `aaguid` wrong note or nested claim name, and `credential_id` wrong note or off the access
      token: `MalformedClaims`.
  - `tenant` renamed claim or wrong attribute are admitted with **no tenant**, because the
    parser treats `tenant` as optional. So these tests pin the value rather than a refusal.
  - With no WebAuthn notes (what stock Keycloak issues) the token is refused.
- **Who writes `org`/`tenant` (8).**
  - The committed profile has no violation, and the default four attributes survive.
  - Six near-misses must each be reported:
    - unmanaged policy `ENABLED`;
    - `tenant` user-editable;
    - `org` user-viewable;
    - `org` multivalued;
    - `tenant` pattern `^.*$`;
    - `org` undeclared.
  - The expected pattern is derived from `intake_platform.admin.principal._ID_SHAPE`, not
    restated.
- **Runbook drift (7).**
  - Every realm mapper has a runbook row with its name, mapper type and source.
  - A renamed note is drift.
  - The runbook names both notes and the id shape.

## For the owner

1. **Apply `docs/runbooks/keycloak-realm.md` §2 and §4 to the deployed realm**, and set
   `INTAKE_ADMIN_OIDC_AUDIENCE=api`. That covers:
   - the five mappers on the console client;
   - `org` and `tenant` declared admin-only in the user profile with the id-shape pattern;
   - the values set on each staff user, never on a group, with `tenant` as the tenant's UUID.
2. **Decide the TOTP question** in runbook §3: WebAuthn for every console role, or an actor-block
   value for a TOTP login. Until the WebAuthn provider exists, **every** staff token is refused,
   including a WebAuthn one, because nothing writes the two notes.
3. **File the provider as its own issue.** The issue should cover the Java authenticator wrapping
   `webauthn-authenticator`, its build and signing, and its deployment to `/opt/keycloak/providers`.
   This PR mints no issue id (ids are allocated by the orchestrator).
