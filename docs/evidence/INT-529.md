# INT-529 — synthetic-scope consent texts, marked "sentetik test metni", loaded only on the synthetic host

GitHub #896 · Sec-Row: `consent` · branch `int-529-synthetic-consent-texts` · legal lane, author
role (D25). An independent legal-reviewer verifies this PR; every claim below cites its source.

## 1. Scope and decision

- **Owner, 16 Oct 2026, relayed:** *"for third do recommended"* — yes to the INT-498 audit's
  proposal P6 (PR #870, `docs/evidence/INT-498.md` §5 P6, not yet on main): the legal lane
  authors consent and notice texts **for synthetic tenants only**, in a separate index, so the
  synthetic host can exercise F04, F06 and F07. The decision is recorded in the issue body
  (GitHub #896); no `00_STATE.md` row was minted for it.
- **Lane:** D25 (owner, 3 Oct 2026; GitHub #800). D25 is on `int-471-legal-lane` (PR #809) and
  is **not on main yet**, so its register `docs/legal/decisions/` does not exist on this branch.
  The reasoning that would go in an LD entry is recorded here instead.
- **What does not change.** `docs/legal/documents.yaml` (the real-tenant index) still declares
  no document and every real id still refuses until a licensed Turkish lawyer countersigns
  (HB-L27, G3). `docs/legal/strings.yaml` does not exist on main; nothing creates it, and no
  files/06 §7 fixed string is quoted in the synthetic texts.

## 6. The mechanism

- `packages/intake_platform/src/intake_platform/legal/synthetic.py`: `DeploymentDataClass`
  (`synthetic` for the exact literal only, else `real_phi` — the reading ADR-035's guard uses in
  PR #751); `SyntheticLegalIndex` (refuses any class but synthetic; the index must declare
  `data_class: synthetic`; ids limited to the sixteen; paths from `REQUIRED_DOCUMENTS`; sha256
  and front-matter version bound to the row; the visible marker on the first body line; the
  invariant-20 scan at render; `awaiting_human` rows refuse as missing);
  `SyntheticConsentTextCatalog` (the consent guard's catalog on a synthetic deployment);
  `refuse_legal_paths_for` (the boot pairing rule).
- `consent/texts.py`: `SYNTHETIC_MARKER`, `carries_synthetic_marker` (Turkish case folding),
  `synthetic_marker_is_visible`; the real-tenant `ConsentTextCatalog` refuses any file that
  carries the marker.
- `services/api`: `ApiSettings.deployment_data_class`; `from_env` refuses the synthetic class
  outside an explicit `dev` or `staging` and defaults the legal root to the synthetic tree for
  it; `__post_init__` refuses a real class on the synthetic tree and a synthetic class off it;
  `state.consent_catalog_for` builds the one catalog both the guard and the embed wiring use.
- `infra/staging/Dockerfile.api` bakes `INTAKE_DEPLOYMENT_DATA_CLASS=synthetic`;
  `infra/staging/compose.yaml` never sets it (test).

## 10. Findings for the coordinator

- **F1 — UI chrome contradicts the bound text on the same screen.** The consent detail screen
  shows `consent.who.*` directly above the legal text. `consent.who.laneAffect` says the doctor
  sees the affect cues ("yalnızca hekiminiz görür"); files/06 §2.1 and `observers/affect.py`
  say they never reach the clinician. `consent.who.voice` says "Veriler Türkiye'deki
  sunucularda kalır", which is false on the us-east-1 synthetic host. `consent.basis.service`
  calls `core` "the service itself, no button", while the registry makes it açık rıza. Under
  2026/347 that is misleading information next to the consent. Not edited here (app copy, not
  legal text).
- **F2 — the app cannot grant `core`.** `purposes.ts` gives it `ui: "info"` and the ledger never
  makes an info row grantable, while visits and notes require `core`. With the synthetic text
  served, `POST /v1/consents/grant {scope: core}` works (tested), but no app control sends it,
  so F04 on the synthetic host still needs an app path.
- **F3 — the render-time claims scanner misses softened Turkish forms.**
  `intake_platform.legal.claims` `accuracy_tr` is `\bdoğruluk`; "doğruluğu yüzde 99" passes it.
  The CI shell gate catches it.
- **F4 — PR #751 (hosted lanes) and these texts.** #751 reads the same
  `INTAKE_DEPLOYMENT_DATA_CLASS` with the same semantics and bakes the same `ENV` line; whichever
  merges second removes the duplicate reader and line. More important: #751 routes the synthetic
  deployment's speech recognition, extraction and speech output to a hosted provider. If it
  merges, "Sesiniz hiçbir dış şirkete gönderilmez" (voice) and "kendi sistemlerimizde" (core)
  become false; the PR that switches a hosted lane on must name the provider (legal name,
  country) in those texts, which re-binds their hashes and re-prompts (files/06 §2.1).
- **F5 — satisfaction annotations disagree with the gate.** The score's `events` columns are
  annotated `BASIS_CONTRACT` and the `satisfaction` retention class says m.5/2-c, but both
  satisfaction routes are gated on the açık rıza purpose and `csat_texts` says m.6 açık rıza.
  The text states the ground the system enforces; the annotations should be reconciled
  (pre-existing, COUNSEL_BRIEF §2.9).
- **F6 — aydınlatma before consent.** 2026/347 wants the aydınlatma given before processing.
  The synthetic açık rıza texts serve while every aydınlatma id is awaiting-human. That is
  acceptable only because the host holds invented patients; it is one more reason the real set
  (HB-L27) must be complete before a real patient.
- **F7 — "accepted" versus "okudum ve anladım".** INT-210 records an aydınlatma as
  `legal_document.accepted`; 2026/347 says an aydınlatma is acknowledged as read and understood,
  never accepted. Worth aligning the UI wording before the aydınlatma texts land.

## 11. What this does not do

It signs nothing for a real patient, fills no counsel field, closes no HB row, edits no UI
string, creates no fixed string, and does not change the real-tenant index or any real-tenant
path. The PR needs the independent legal-reviewer's verdict (D25) before merge.
