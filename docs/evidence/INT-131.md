## Token / DPoP design (services/api: dpop.py, auth_store.py, otp.py)

Access and refresh tokens are opaque random strings stored server-side only
as SHA-256 hashes in Redis, each bound to the RFC 7638 thumbprint (`jkt`) of
the client's P-256 key. Every proof is a compact JWS whose only accepted
header is `{typ: dpop+jwt, alg: ES256, jwk}` (no algorithm negotiation),
verified over `cryptography` with htm/htu matching, a ±300 s iat window, a
single-use jti replay cache, and — on resource requests — the `ath` hash
binding the proof to the presented access token. Refresh rotates on every
use inside a family; presenting an already-rotated token is reuse, which
revokes the whole family and appends a hash-chained audit entry, while a
wrong-key presentation is refused WITHOUT killing the family (a stolen token
must not become a denial-of-service lever). Resource requests use
`Authorization: DPoP <token>` and resolve to a patient principal tagged
`X-Intake-Auth-Tier: otp`; the two INT-197 dev-bearer accounts keep working
unchanged under their honest `dev` tag. The client key lives in SecureStore
(software-held custody; the hardware-backed non-exportable key is the
dev-build native module files/10 §4 budgets separately).
