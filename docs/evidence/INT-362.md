# INT-362 — Error and status lines are announced under VoiceOver as well as TalkBack

**Epic:** E08-mobile · **Phase:** P1 · **Sec-Row:** mobile · **GitHub:** #588 ·
**Legal:** 5378, EN 301 549 · **Depends on:** INT-226 (PR #583, open when this was written)
**Criteria:** WCAG 2.2 SC 3.3.1 Error Identification (A, Ministry BK28) and SC 4.1.3 Status Messages (AA)

## Acceptance (verbatim)
- "every error and status line, including issue-link, ConfirmCard and RecordReading, is announced on iOS (announceForAccessibility) as well as Android (live region)"
- "the a11y test discovers error and status lines from the source tree instead of a hand-written screen list, so a new screen cannot be missed"

## Problem
The INT-226 conformance report (PR #583, `docs/compliance/accessibility-conformance.yaml`)
rates SC 3.3.1 and SC 4.1.3 as Partially Supports. Three lines set only the
Android live region and never posted an iOS announcement, so VoiceOver said
nothing. They were the Doctor Link error (`issue-link.tsx`), the record card's
"not saved" notice (`ConfirmCard.tsx`) and the record-reading line
(`RecordReading.tsx`). The kiosk PIN lines had the same gap. React Native
declares `accessibilityLiveRegion` as `@platform android`, and iOS has no live
regions and no alert trait. The check that should have caught this,
`a11y.spec.ts` "%s announces its error on BOTH platforms", listed four screens
by hand and only asked whether each FILE contained both halves somewhere.

Walking the tree for this issue found more lines than the report named:

- **Android half only:** the new-visit SMS notice, the voice gate's probe row,
  the unavailable-instrument block and the intake integrity warning.
- **Neither half:** the health section's wait and failure lines, the
  voice-failed notice in the typed intake, the share centre's failed revoke and
  unreachable read, and the data-request and learned-fact write failures.
- **Both halves, but doubled on Android:** the four original screens (phone,
  OTP, new visit, records) paired the Android live region with
  `useLiveAnnouncement`, which posts on Android too. TalkBack therefore read
  each error twice.

## Change
- **`apps/mobile/src/lib/a11y/announce.ts`** (pure and node-tested). It adds
  four rules:
  - `politenessOf(tone)`: an error is assertive, a status is polite.
  - `spokenLine(tone, message, errorWord)`: an error is spoken with the
    catalogue's error word first ("Hata: …", joined by `labels.labelled`),
    unless the visible copy already starts with it. The visible copy is never
    changed.
  - `iosAnnouncement(os, speak, politeness)`: iOS posts, with
    `{queue: false, priority: "high"}` for an error and
    `{queue: true, priority: "low"}` for a status. Android and web post
    nothing, because there the live region is the channel.
  - `lineStep(...)`: one render of one line.

  `nextAnnouncement` now treats an empty or blank message as nothing shown.
- **`apps/mobile/src/lib/a11y/prefs.ts`**: new `useLineAnnouncement(message, politeness)`.
  It is `lineStep` plus `AccessibilityInfo.announceForAccessibilityWithOptions`.
  `useLiveAnnouncement` stays as it was for the dialogue's turn state, which
  has no line of its own.
- **`apps/mobile/src/components/Announced.tsx`** (new) is the one place both
  halves are put together:
  - `AnnouncedText` sets `live` on `AppText` for Android and calls
    `useLineAnnouncement` for iOS.
  - `AnnouncedRegion` does the same for a group of lines (a spinner row, a
    title with its body). It can merge the group into one element or leave its
    heading reachable.

  Call sites give only a `tone` and the visible `message`.
- **`apps/mobile/src/components/Themed.tsx`**: `AppText` takes `spokenAs`, which
  becomes the element's `accessibilityLabel`. The live region then reads the
  same words VoiceOver is sent, "Hata" included, and the visible text is
  unchanged.

## Discovery (the second acceptance line)
`e2e/a11y.spec.ts` walks every `.tsx` under `apps/mobile/src`, tests excluded.
The announcer and `Themed.tsx` (the mechanism itself) are skipped. The walk
flags every line that sits outside an `AnnouncedText` or `AnnouncedRegion` and
matches any of these:
1. It declares a live region by hand: `live=`, `accessibilityLiveRegion=` or
   `accessibilityRole="alert"`.
2. It is drawn in the error colour: an `AppText` whose `color` holds `"amber"`,
   or a style naming `theme.amber`.
3. It renders catalogue copy the catalogue marks. Every `t("…")` call counts,
   wherever it is rendered from (a prop, a helper, a line):
   - **failure copy:** a key with an `error`/`err` segment, or a key ending
     `failed`, `notSaved`, `unsaved`, `unsent` or `unreachable`;
   - **wait copy:** a Turkish value that ends in "…".

`ANNOUNCED_ELSEWHERE` lists seven findings, each with its reason:

- DialogueIntake's `dialogue.preparing`, `dialogue.transcribing` and
  `voiceFirst.preparing`. The dialogue's own `useLiveAnnouncement` announces
  these on both platforms, and a live region beside it would say them twice.
- ConfirmCard's `records.card.unitConflict`. It is part of the card from the
  moment the card exists, not a change.
- records' `records.uploading`. It is the busy button's own label, and the
  outcome notice after it is announced.
- VoiceNote's two labels. The component is dev-only (`__DEV__`).

A test fails when an entry no longer matches a finding, so the list can only
shrink.

### Deliberately not routed (outside the discovered set)
- **`notifications.pending`.** `lib/notifications/store.ts` sets `pending: true` at the
  START of every save (optimistic, line 87) and clears it on confirmation. The
  line is therefore also the in-flight state. Announcing it as an error would
  say "Hata: Değişikliğiniz henüz kaydedilmedi" on every toggle. The fix needs
  a store change that separates "in flight" from "failed", so it is left out
  here and reported.
- **`review.sentInfo` and `consent.queue.note`** show persisted state (the note
  was sent; consents are queued) on every visit to the screen, as well as right
  after the action. An announcement on arrival would repeat old news. Separating
  "just happened" from "is so" needs a session flag the screens do not have.

### Known limits carried over (both platforms, unchanged by this issue)
- A repeated identical error is announced once. Two wrong kiosk PINs, or two
  invalid phone submits, produce the same line. This is the INT-144 rule
  ("the same message once, not on every re-render"), and the Android live region
  behaves the same way. OTP and the API paths clear the line before retrying, so
  they re-announce.
- A focus move that follows an iOS announcement can cut it short. Errors are
  posted with `priority: "high"`, which VoiceOver documents as uninterruptible.
  Only a device run confirms it.

  - empty or blank messages;
  - `politenessOf`;

    stays empty;

    INT-226 report cites it, but now runs over the discovered files (15 today)
    instead of four listed ones.
  - Non-vacuity: the walk reaches every file the INT-226 report named.
  - Near-miss control: one sample file is run through the same scanner. The
    fixed line and an ordinary line are silent. The amber line, the
    Android-only `live=`, the hand-made region, the quiet failure copy and the
    wait copy are each caught and named. A region's children count as announced.
  - The exceptions still match findings.
  - No live region is declared outside the announcer.
  - Every announced line states a literal tone (or a conditional of the two),

  - The announcer's source pairs `live={politeness}` and
    `accessibilityLiveRegion={politeness}` with two

## Invariants
- **2:** every announced string is one the screen already shows. An error adds
  only the catalogue's own `a11y.error` word, and no status is spoken as an error.
- **5:** no new copy. The error word comes from `t("a11y.error")`.
- **6:** announcements go to the OS screen reader only. The invariant-6 test
  above pins that the path has no console call and no telemetry, metrics or
  logger import.
