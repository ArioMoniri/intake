# INT-322 — Embed handshake: intake mode bound inside the signed launch ticket (ADR-029)

## 1. What this is, and what it deliberately is not

The embeddable white-label handshake (INT-320, merged) lets a partner backend
mint a signed, single-use launch ticket that a patient device presents to start a
branded intake. INT-322 adds the intake **mode** — the two intake depths the
mobile app already has: `hastanede` (detailed / "Detaylı") and `brief`
(quick / "Hızlı"). A partner requests which depth the launched intake runs in;
the mode is bound **inside the signed ticket** so it cannot be tampered or cross
tenants, and it is gated by what the tenant is allowed to offer.

What it is **not**:

- not a new personal-data field — the mode is a UI-depth flag, not a clinical or
  personal value; invariant 6 holds and no new inventory annotation is needed;
- not a new outbound path, service, migration or consent text;
- not a change to the mobile app — the embed **wire** enum is exactly
  `{hastanede, brief}`; the mobile app's internal reducer values
  (`detayli`/`hizli`) and their mapping to the wire are the coordinator's
  INT-321 and are out of scope here.

## 3. Design, decided rather than assumed

- **Mode rides INSIDE the signature.** The closed ticket claim set grows by
  exactly one — `{tid, nonce, iat, exp, purpose, mode}` — so the mode is covered
  by the HMAC exactly like the tenant id. It is never a query param and never
  re-supplied at launch; `LaunchRequest` stays `{ticket}` with `extra=forbid`, so
  a mode sent at the door is a 422, not an override.
- **Closed enum, single source of truth.** `IntakeMode = Literal["hastanede",
  "brief"]`, `INTAKE_MODES` and `DEFAULT_INTAKE_MODE = "brief"` live in
  `intake_platform.embed.tickets`; the API schema imports the same alias, so the
  wire enum cannot drift between the schema and the ticket core.
- **Defence in depth.** An unknown mode is refused at three layers: the schema
  (pydantic enum → 422), the ticket core at mint (`TicketModeInvalid`), and again
  at verify (a leaked-key forgery carrying an unknown mode is still refused).
- **Tenant gating, fail closed.** A tenant declares `allowed_modes` in
  `infra/tenants/embed_registry.yaml`. Absent → both modes, so every existing row
  keeps working; a present value must be a non-empty list of known modes or it
  fails at load. Minting for a mode the tenant does not allow returns an
  id-shaped `400 embed_mode_not_allowed` — the requested mode is not echoed.
- **No PHI.** The mode is a UI-depth flag; audit and refusals stay id-shaped
  (invariant 6). No new personal-data category (invariant 18 unaffected).

## 5. What the tests pin (tests/embed/test_mode.py)

- **Schema:** `MintRequest.mode` defaults to `brief`; accepts each mode; rejects
  an unknown mode (enum) and still forbids extra fields; `LaunchResponse` carries
  the resolved mode.
- **Ticket core:** each mode binds and round-trips through the signed payload;
  default is `brief`; the mode rides inside the closed 6-key payload; an unknown
  mode is refused at mint and at verify; a non-string mode fails closed.
- **Registry:** `allowed_modes` defaults to both when absent; an explicit subset
  loads; unknown entries, an empty list and a non-list each fail closed.
- **Launch:** `resolve_launch_context` carries the mode.
- **Service/router:** mint→launch round-trips each mode to the launch response;
  the default is `brief` over the app; a disallowed mode is `400
  embed_mode_not_allowed`; the mode cannot be injected at launch (a mode in the
  launch body is 422, and the resolved mode is whatever was SIGNED); an unknown
  mode at mint is 422; a forged mode reaching launch is `400 embed_ticket_refused
  reason=mode`.

Existing ticket-shape tests were updated to include the new `mode` claim (the
closed claim set grew by one) — the intentional, tested change to the ticket
contract, not a placeholder.
