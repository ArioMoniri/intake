# INT-295 — the checkpoint control was drawn where the screen is not

> **Issue.** `docs/backlog/issues.yaml` INT-295 (P1, `E08-mobile`, `sec_row: mobile`).
> **Branch.** `int-295-modebar-reachable`, off `origin/main` @ `c77d4ad`.
> **Filed from.** The INT-293 walkthrough of 2 Sep 2026, defect §3.
> **Worked.** 3 Sep 2026.

## 1 · What was reported, and the one thing in it that was wrong

INT-293 §3, verbatim: the mode bar renders `Hastanedeyim` + `Detaylı mod açık` +
`Sıranız geldi` as one non-wrapping, non-scrolling row; in Detaylı it is clipped mid-word at
"Detaylı mod aç…" and the checkpoint chip is not on the screen at all. A horizontal swipe on
the row does nothing — the walkthrough verified that rather than assuming it.

All of that is true. The size attached to it is not.

The report says "`UICTContentSizeCategoryL` — the **system default**". The OS category was
indeed L. But INT-260's text-size control **replaces** the OS value instead of composing with
it (`effectiveFontScale` in `apps/mobile/src/lib/prefs/appearance.ts`, and the comment there
says so in as many words), so the OS category and the scale the app renders at are two
different numbers and can disagree. Here they did.

The capture settles it. `INT-293-DEFECT-siraniz-geldi-offscreen-modebar-clipped.png`
(1206 × 2622 px, iPhone 16 Pro at 3×, so a 402 × 874 pt space) was scanned for the
`primarySoft` pill behind "Hastanedeyim" — `#EAF5F2`, ±6 per channel:

```
pill rows 354..485  → height 132 px = 44.0 pt
pill x    60..646   → left 20.0 pt, width 195.67 pt
```

- The left edge at **20.0 pt** is `spacing.screen`, which confirms the content box is
  402 − 2 × 20 = **362 pt** and that nothing else was inset.
- A width of **195.67 pt** is the chip at caption size **26 pt**, i.e. `scaledSize("caption", 2.0)`
  — the app's **largest** step. At an OS-following 1.0 the same chip is 108.0 pt.
- The height of **44.0 pt** agrees: `lineHeight("caption", 2.0)` is 36, plus 2 × `spacing.xs`.

So the screenshot is at text scale 2.0, reached through the app's own *Yazı boyutu* control
while iOS still reported the default category. **The defect is real and the report's
description of the layout is exact; only the scale attached to it is wrong**, and it is wrong
in the direction that makes the defect look worse than it is. That correction is written into
the backlog row, because an acceptance line asserting a false measurement would have forced
either a false test or an abandoned issue.

The number that matters is where it *actually* starts, and the red run below prints it: on the
same 402 pt phone the checkpoint control leaves the row at scale **1.20** — the third of the
control's five rungs, and iOS's own XL category — so a patient reaches it without touching an
accessibility setting.

### The corroboration, from a screen that has nothing to do with this issue

The same simulator (`47783B7E-775E-4B01-A8A3-9AA2633C6859`) was screenshotted at 01:33 on
3 Sep 2026, while a sibling agent's session sat on `(auth)/phone`. Its focal CTA pill measures
**80.0 pt** tall and 362.0 pt wide, starting at x = 20.0 pt.

`primaryButton` is `max(CTA_MIN_HEIGHT, spacing.md * 2 + lineHeight("body", scale))`. That is
56 at scale 1.0 and **exactly 80 at scale 2.0** (16 + 16 + 48). So the appearance record stored
in this device's keychain slot is the largest step, it is shared by every branch running under
the same Expo Go bundle id, and it survives reloads — which is precisely how a walkthrough can
read `UICTContentSizeCategoryL` off the OS and photograph a 2.0 layout in the same minute. The
premise was not carelessness; the two numbers really are independent, and nothing on screen
says which one is in force.

## 2 · How the width is known without a device

`apps/mobile/e2e/fontMetrics.ts` reads `Inter_400Regular.ttf`, the file `theme.ts` names as
`fonts.sans` and the root layout loads, and sums the advances the font declares for the exact
code points of a label (`head`/`hhea`/`hmtx` plus a format-12 character map). Kerning lives in
GPOS and is ignored, so the figure is an upper bound on the natural width — the safe direction
for a "does it fit" assertion.

Calibration, on the corpus of one screenshot named above: the model puts the `Hastanedeyim`
chip at **196.0 pt** at scale 2.0 against the **195.67 pt** measured in the PNG — a
disagreement of 0.33 pt, and the test pins it under 1 pt. This is a measurement of a layout on
one device on one day, not a property of the product.

## 4 · The fix

`apps/mobile/src/components/ModeBar.tsx` — three changes, each answering one way the row could
lose a control, none of them touching the design language five merged passes established (the
chips stay caption-register pills, the colours are unchanged, no string changes):

1. **The status caption leaves the row.** `Detaylı mod açık` is prose about the switch, not a
   control; it moves to the line below, where the deferral notice it shares a register with
   already lives. That gives the row back a third of its width.
2. **The row wraps and its chips shrink** (`flexWrap: "wrap"`, `flexShrink: 1`). RN flex
   children do neither by default, which is exactly why the overflow left the screen instead
   of breaking a line. This is the part that carries the guarantee: with it, a label too long
   for the line moves down instead of out. It earns its place in English at scale 1.5 on a
   375 pt phone, where the two chips genuinely do not share a line.
3. **The row changes form at the app's one large-text threshold** (`isLargeText`, 1.6 — the
   third consumer after the tab rail and the segmented control), each chip taking a full-width
   line. 00 §2's rule: a screen that cannot survive 2.0 changes form, it never clamps the text.

The chips also reach the touch floor by **box** (`minHeight: MIN_TAP`) instead of by vertical
`hitSlop`. A row that can now put two chips four points apart *vertically* is the case
`lib/a11y/target.ts` already refuses horizontally — overlapping slop trades one target for a
worse one.

Two things beyond the mode bar, both named in the issue's acceptance:

- **The progress counter** (`intake.tsx`). "N soru yanıtlandı" is the only place the progress
  is stated as a fact; the dots beside it are decoration and are hidden from assistive
  technology. But a Detaylı flow reaches about thirty dots, and at 8 pt plus a 4 pt gap that
  rail is wider than the content box on its own, at any text size — so it pushed the counter
  off the edge. The rail now owns a box that wraps and shrinks; the counter shrinks not at all.
- **The class, swept tree-wide** (`overflow.spec.ts` §6). A row that pins an item to the far
  end — `justifyContent: "space-between"`, or a child with `marginLeft: "auto"` — and cannot
  break a line will push that item off the screen, and this app scrolls nowhere sideways. Five
  such rows exist; one already wrapped (INT-284 fixed it), and the other four take the same
  one-token remedy: `new.tsx::chosenRow`, `HealthSection::row`, `SectionPanel::sheetHeader`,
  `Segmented::optionStacked`. The allow-list ships **empty** and may only shrink.

## 6 · The test was checked against itself

A test that certifies the defect is worse than none, so each part of the fix was reverted in
turn and the suite re-run:

| mutation | result |
|---|---|
| drop `flexWrap: "wrap"` from the row | red — the arrangement check, **and** `en, detayli, 375 pt: intake.queue.called first leaves the 335 pt row at scale 1.5` |
| never stack (`stacked = false`) | red — the form check |
| put `Detaylı mod açık` back into the row | red — `intake.mode.detayliOn on 375 pt at scale 1.15` and up, three lines of chrome where there should be one |
| drop `flexWrap` from `SectionPanel::sheetHeader` | red — the tree-wide gate names it |

Two things the mutations taught, which are recorded rather than smoothed over:

- **Wrapping alone is sufficient for reachability.** With the row wrapping, the caption could
  stay in it and every control would still be on the screen. Moving it out is what keeps the
  row *one line of chrome* at ordinary text sizes instead of three — INT-293 filed the
  "everything is below the fold" complaint about this same screen — and that is what the
  `stays one line of chrome in Turkish` assertion holds. The two claims are kept separate so
  neither borrows the other's evidence.
- **The first version of the tree-wide scanner found two rows where the tree holds five.** Its
  lazy `\n  },` pattern swallowed every single-line style rule following a multi-line one, so
  it passed while three offenders sat in front of it. It counts braces now, and asserts a floor
  on how many rows it can see — a gate that matches nothing passes for the wrong reason.

The negative control the acceptance asks for is a test of its own: the row re-measured
*exactly as photographed*, in the smallest role the type scale has (`micro`, 11 pt at scale
1.0), still puts `intake.queue.called` off the 362 pt row. Shrinking the type was never the
fix, and 00 §2 forbids it anyway.

## 8 · What this does not prove

- **That iOS lays Yoga out the way the model does.** The model is arithmetic over the shipped
  font's advances plus the arrangement read out of the component. It agrees with the two device
  measurements available — the mode chip at 195.67 pt and, independently, the CTA pill at
  80.0 pt — and that is the whole of the empirical claim. **No simulator was driven for this
  branch**, and the reason is on the record rather than glossed: at 01:33 on 3 Sep the one
  booted simulator was mid-session in another agent's run, and loading this branch's bundle
  into it would have destroyed that run to produce a screenshot of three flex properties whose
  semantics are not in doubt. If a visual pass is wanted before merge, it needs a simulator
  nobody else is holding.
- **That the row is beautiful at 2.0.** It is reachable and it changes form the way the rest of
  the app's chrome does. Whether a full-width pill is the right register at that size is a
  design-pass question, not a reachability one.
- **Anything about the other INT-293 defects.** §1 (dialogue answers never reaching the note),
  §2 (the TTS mute latch) and §4 (a reload losing the visit) are INT-293, INT-294 and an
  unfiled defect respectively, and none of them is touched here.
