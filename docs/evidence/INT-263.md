# INT-263 — a scroll container for every screen the appearance work did not reach

Found by driving the app after INT-260 landed, not by a user report. At the 2.0 rung of the
in-app text ladder the welcome screen rendered its title under the status bar and its footer
off the bottom, and swiping did nothing: `apps/mobile/src/components/Themed.tsx` exported
`Screen` as a bare `SafeAreaView` with no scroll container, so the overflow was not merely
awkward — it was **unreachable**, including `t("welcome.body")`, the one line that says what
the screen is. INT-260 rewired thirteen screens; welcome was not among them.

## 1. Acceptance, restated verbatim from docs/backlog/issues.yaml

> - "every route under apps/mobile/src/app renders its content inside a scroll container, or
>   declares in one line at its own definition why it is exempt (a full-bleed media surface, a
>   list that scrolls itself); a test enumerates the routes from the filesystem so a NEW screen
>   added without one fails, rather than a hand-kept list that silently stops covering the app"
> - "the failure is asserted at the largest step of the INT-260 ladder (2.0) and not merely at
>   default: the regression is a function of content height against viewport height, so a test
>   that only runs at 1.0 would have passed on the welcome screen the day the defect shipped"
> - "the fix is a scroll container, never a shrink: no screen closes the overflow by lowering a
>   font size, clamping the scale, or truncating text, because that takes back the size the
>   patient chose (INT-260's own ruling); contentContainerStyle carries the padding so the
>   scroll region reaches the full viewport"
> - "keyboard-bearing screens (phone, otp, any free-text entry) keep their input visible when
>   the keyboard is up — the scroll container does not reintroduce the covered-field defect it
>   is meant to prevent"
> - "the sweep is proved screen by screen rather than asserted: docs/evidence/INT-263.md
>   records, for each route, the state before and after at scale 2.0"

## 2. What this environment can and cannot prove

There is no docker daemon, no simulator and no emulator in this container, and Expo cannot be
started. **Nothing below is a device measurement and none of it is claimed as one.** Two
things are real:

- **Source facts.** `apps/mobile/src/app/scroll-containers.test.ts` walks `src/app`, so the
  route list is the filesystem's, not a list someone maintains. What each route renders is read
  from its own source.
- **A model, stated as a model.** `contentHeight(source, scale)` lays the catalogue strings a
  route declares into a reference phone's measure (iPhone 16 Pro: 402 × 874 pt, insets 62/34,
  so 738 pt of content height inside the screen padding) at the shipped `scaledSize` /
  `lineHeight` tokens, wrapping at an average glyph advance of 0.5 em.

The model is wrong in both directions and deliberately so. It counts **every branch** in a
file, including ones that never render together, so a branchy screen models taller than any
single state of it. And it counts **nothing that is not a catalogue key** — card padding,
control boxes, images, list rows, fixtures, server strings. The first error makes the gate ask
for a scroll container on screens whose shown branch might have fitted, which is the right way
for a gate to be wrong: a scroll container on a screen that fits costs the patient nothing, and
a missing one on a screen that does not costs them the content. The second means "fits" is
never a claim that a screen is safe — only that this model cannot convict it, which is why
rule 1 applies to every route whatever the model says.

## 5. The fix, and the two halves of it

**`ScrollScreen` (`components/Themed.tsx`)** is now the container every route uses:

- the padding rides on `contentContainerStyle`, never on the frame or on the ScrollView's own
  `style`. On either of those the scrollable area and its indicator stop a screen padding short
  of the edge, and content is clipped there instead of running to the physical edge — the exact
  opposite of what `RAIL_EDGES` has promised since INT-130;
- `flexGrow: 1`, not `flex: 1`, so short content still fills the viewport (welcome stays
  centred at sizes where it fits) and tall content is free to exceed it;
- `automaticallyAdjustKeyboardInsets`, so the container added for the overflow cannot bury a
  field behind the keyboard.

**`Screen` lost its own padding.** That padding was the trap: it sat on the *frame*, so every
screen that put a `ScrollView` inside one was scrolling inside a box inset on all four sides.
Two callers remain — the intake and review flows, which host their own scroll region beside a
fixed glass bar — and both already carried the padding on their scroll content, so both simply
dropped the `screenFlush: { padding: 0 }` override they needed to cancel it.

**No screen closes its overflow by taking size back.** Nothing was truncated, no
`numberOfLines` was added, no scale was clamped, no font size was lowered; every string in the
app is byte-identical after this change. The test asserts the absence of `numberOfLines`,
`ellipsizeMode`, `adjustsFontSizeToFit`, `minimumFontScale` and `maxFontSizeMultiplier` across
every route, and that no route clamps `useFontScale`.

One disclosed consequence: `phone.tsx`, `otp.tsx` and `visits/[visitId]/index.tsx` carried
`paddingTop: spacing.md` on their scroll content *in addition to* the frame's 20 pt, so their
top inset was the accidental sum, 36 pt. With the frame padding gone the override would have
made those three screens tighter at the top than every other screen, so it was removed: they
take the uniform 20 pt. This is the only spacing value that changed anywhere.

## 6. The two full-screen surfaces that are not routes

The route walker enumerates routes; these two render a whole screen without being one, and
both were fixed by inspection with the same rule.

| surface | before | after |
|---|---|---|
| `components/DialogueGate.tsx` — the intake route's voice-entry phase | a static `View`; at 2.0 the entry title, body and the quiet "Yazarak devam edin" door at the bottom had nowhere to go | a `ScrollView` whose `contentContainerStyle` carries the padding, `flexGrow` in place of `flex` |
| `components/BiometricGate.tsx` — the locked state, which replaces the whole tree | a padded `Screen` with no scroll container | `ScrollScreen` |

`DialogueIntake.tsx`, the third intake phase, already scrolled. The test names all three
branches so a future rewrite of any one of them cannot quietly drop the container.

## 7. Keyboard-bearing screens

Four routes carry a `TextInput`: `phone.tsx`, `otp.tsx`, `visits/new.tsx` and
`visits/[visitId]/intake.tsx`. All four already declared
`keyboardShouldPersistTaps="handled"`; every one of those declarations was **preserved
verbatim** through the migration, and the test asserts it for whatever set of routes carries a
field, so a new free-text screen inherits the rule. `intake.tsx` additionally keeps its
`keyboardDismissMode="on-drag"`. `ScrollScreen` adds `automaticallyAdjustKeyboardInsets`, which
is the mechanism that lets a covered field be scrolled back into view rather than merely
scrolled past — the container that fixes the overflow is not allowed to create the covered-field
defect it exists to prevent.

## 8. The route enumeration, and one hazard it created

The test walks `src/app` and treats every `.tsx` as a route except `_layout.tsx` and
expo-router's `+`-prefixed framework files. Twenty routes today; a twenty-first added without a
scroll container fails rule 1 on the day it lands.

Living beside the routes has a cost that had to be paid: expo-router's `require.context` matches
`.*\.[tj]sx?$` with no exception for test files, so `scroll-containers.test.ts` would have been
bundled as a screen at `/scroll-containers.test` — importing `node:fs` into the app. A new
`apps/mobile/metro.config.js` blocks `src/app/**/*.test.*` from Metro's file map, which keeps it
out of the route context, the typed-routes output and the bundle alike, while vitest (which does
not go through Metro) still runs it. The test asserts that block exists, so it cannot be dropped
silently. `e2e/nav.spec.ts` — which pins the route tree against the 02 §4 nav map — now filters
test files out of its own walk for the same reason.

## 9. The exemption, and why the set is closed

A route that legitimately should not scroll declares it in one line at its own definition, so
the reason travels with the code:

```ts
// scroll-exempt(redirect): this route renders no content of its own — it hands
// the patient straight to the shell or to welcome, and there is nothing on it
// that a larger text size could push out of reach.
export default function Index() {
```

Three kinds are accepted and **each is checked structurally**, because an exemption nobody can
verify is an exemption anybody can write: `redirect` must render a `<Redirect>` and no
`<AppText>`; `list` must render a virtualized list (which scrolls itself — wrapping one in a
ScrollView is the nested-VirtualizedList bug, separately asserted); `media` must declare no
catalogue copy at all, since a full-bleed surface has no reading text to lose. Exactly one route
is exempt today.

## 11. What remains unverified

- **No device, no simulator, no screenshot.** This container has no docker daemon, no
  emulator, and cannot run Expo. Nothing here was seen rendered. The §4 table is
  test-measured against a model of a phone, not measured on one, and it is offered as such.
  The remaining device-only questions are: whether the removed 16 pt of top inset on three
  screens reads right under a navigation header, and whether
  `automaticallyAdjustKeyboardInsets` behaves as intended on a physical keyboard. Both want a
  simulator pass before release, and neither can lose content — the container is present
  either way.
- **`accessibilityRole` / `accessibilityState` and the MIN_TAP targets INT-260 established
  are untouched.** The migration changed container elements only; no control, label, role,
  state or target size was edited. `e2e/a11y.spec.ts` and `e2e/appearance.spec.ts` both pass
  unchanged, including INT-260's own assertion that at least thirteen rail screens take
  `useTabBarClearance()`.
- **Invariant 5 (`tr` keys):** no user-visible string was added, removed or altered by this
  change, so there is no new key to author. The exemption line and every comment are source
  comments, not rendered copy.
