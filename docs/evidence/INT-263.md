# INT-263 — the OTP request budgets were fixed hourly buckets

`services/api/src/intake_api/auth_store.py` counted every OTP request budget in
a **fixed** window: the counter key carried `floor(now / OTP_WINDOW_S)`, so all
three budgets reset together on the hour. A caller who spent its budget just
before a boundary was handed a fresh one just after it, and never exceeded
either window. The bound that actually enforced was therefore **2 × limit inside
a rolling hour** — for the phone budget, six codes in about six minutes, floored
only by the 60 s resend cooldown — against files/10 §2's "3 requests/hour/phone".

INT-285 found this while fixing the suite's clock, pinned it with a near-miss
control, and deliberately left the limiter alone: changing how an abuse budget
is counted is a semantics change on the authentication path, and CLAUDE.md
forbids making one in passing inside another issue's PR. This is that change.

## The defect, exactly

With `p = t mod OTP_WINDOW_S` the phone budget spent at `p = 3599 - 2 × 61`:

```
t + 0     request -> 202   window W, phone counter 1
t + 61    request -> 202   window W, phone counter 2
t + 122   request -> 202   window W, phone counter 3   (p = 3599)
t + 183   request -> 202   window W+1, phone counter 1  <-- the whole budget back
t + 244   request -> 202   window W+1, phone counter 2
t + 305   request -> 202   window W+1, phone counter 3
t + 366   request -> 429
```

Six codes to one phone in 366 s. Neither window ever admitted more than three,
which is exactly why the deviation was invisible to every test that did not
straddle a boundary. The same arithmetic held for the 10/IP and 3/device
budgets, and there the resend cooldown does not even floor it — those two are
keyed on the IP and the device digest, not on the pseudonym, so a caller with
`n` phones could spend both budgets at a single instant on each side of the
boundary.

## The fix

One sorted set per `(dimension, identifier)` — no window suffix, because a
rolling window has no boundary to roll over. Each **admitted** request is one
member scored with the instant it was admitted; every gate call first drops the
members scored at or before `now - OTP_WINDOW_S`, so what remains is exactly the
admissions in the half-open window `(now - OTP_WINDOW_S, now]`.

```python
    def _budget_wait(self, key: str, limit: int, now: float) -> float | None:
        self._r.zremrangebyscore(key, "-inf", now - OTP_WINDOW_S)
        admissions = list(self._r.zrange(key, 0, -1, withscores=True))
        if len(admissions) < limit:
            return None
        return float(admissions[len(admissions) - limit][1]) + OTP_WINDOW_S - now
```

Four properties this buys, each asserted in
`tests/security/test_otp_abuse.py` rather than described here:

- **No error term.** The retained scores *are* the admission times, so the
  enforced bound is exactly "no more than `limit` admissions in any
  `OTP_WINDOW_S` span". There is no sub-bucket rounding and no instant at which
  anything is handed back.
- **Bounded key set.** One key per `(dimension, identifier)`, holding at most
  that dimension's limit (3 phone, 10 IP, 3 device), expiring `2 ×
  OTP_WINDOW_S` after its last write. A **refused** request writes nothing, so
  traffic cannot grow it. This is *half* the previous key set, which kept the
  old and the new bucket alive across every boundary. There is no per-request
  timestamp list.
- **Constant work per request.** Per dimension: one `ZREMRANGEBYSCORE` and one
  `ZRANGE` over a set of at most `limit` members; then one `ZADD` and one
  `EXPIRE` per dimension on admission. Independent of traffic.
- **A true retry-after.** The slot opens as the admission at index
  `len - limit` leaves the window. Under the fixed scheme the caller was told
  the time to the next boundary, which can be *shorter* than the true wait and
  sends them straight back into a refusal.

The index is written out rather than hard-coded to `0` because it is what keeps
the answer true if a budget is ever **lowered** while windows are live — which
is what tightening a limit under attack does, and the one case where more
admissions sit in a window than the limit now allows.
`test_the_retry_after_stays_true_when_a_budget_is_tightened_under_live_windows`
drives that against `AuthStore` directly (no route can lower a limit).

Everything else is untouched: the clock is still injected (`now_fn`), so no test
sleeps (docs/TDD.md rule 6); the key material is still the Tokenizer pseudonym
and the device digest, never a phone number or a device id (invariants 6, 14);
the refusal is still the one generic `otp_limited` body, so the caller never
learns which dimension tripped (02 §8.2).

### Key migration

The key *names* change (`auth:otp:w:<dim>:<id>:<window>` → `auth:otp:w:<dim>:<id>`),
so the new sorted sets never collide with the old string counters — a `ZADD`
against a live `INCR` counter would raise `WRONGTYPE`, and it cannot happen
because no name is shared. The orphaned fixed-window keys carry the old
`EXPIRE` of `2 × OTP_WINDOW_S` and drain within two hours of the deploy. The
window they leave behind is a caller who had spent a *fixed* budget getting a
*rolling* one at the cut-over, i.e. at worst the behaviour this issue is
removing, for at most two hours, and never worse than it.

## The near-miss control

INT-285's `test_a_fixed_window_hands_the_budget_back_at_the_boundary` is
**inverted, not deleted**: same clock offset, same phone, same cooldown pacing;
the sequence that admitted `2 × PHONE_LIMIT_PER_HOUR` must now stop at
`PHONE_LIMIT_PER_HOUR`. It is `test_a_boundary_crossing_does_not_hand_the_budget_back`.

The control that keeps *it* honest is the third assertion:

```python
assert int(started // OTP_WINDOW_S) != int(harness.clock() // OTP_WINDOW_S), (
    "the sequence has to cross a fixed-window boundary or it proves nothing"
)
```

Without it the test passes against the **old** limiter as soon as the clock
offset drifts off the boundary — a rate-limit test that never straddles a
boundary is a test of the ordinary limit, which four other tests already cover.
The offset is computed by `_boundary_offset_s(limit, spacing)` from the limits
themselves, never written as a number, so it follows if a constant moves; the
same helper places the per-IP and per-device sequences, whose budgets are spent
at a single instant.

The second near-miss is inside
`test_no_rolling_window_span_admits_more_than_the_phone_budget`: it also asserts
`len(admitted) >= 2 * PHONE_LIMIT_PER_HOUR`, so a limiter that simply refused
everything after the first three requests — which satisfies "never more than 3
in any span" perfectly — fails it. The budget has to replenish as well as bind.

## Findings, and what was refused

- **`carrier/geo sanity checks against SMS pumping` is a control no code
  implements.** It sits in the same files/10 §2 sentence as the budgets, so
  acceptance line 5 reaches it. It is now marked in §2 and in the threat-model
  onboarding row as named-but-unbuilt, with the request budgets named as the
  whole of what stands against SMS pumping today. **No issue id was minted for
  it here**: ids are moving under many concurrent branches, `issues.yaml` on
  `main` does not show the ids that open PRs already carry, and minting one
  blind is how INT-285 came to be renumbered twice. It is handed to the
  coordinator to file with an id it can allocate safely.
- **The gate is still not atomic.** `otp_request_gate` reads, decides, then
  writes; two workers racing on the same identifier can both see room and both
  admit, so a concurrent burst can exceed a budget by the number of racing
  workers. This is unchanged from INT-131 — the fixed-window `INCR` had the same
  read-then-decide shape — and it is not narrowed here, because making it atomic
  needs a Lua script and `fakeredis` cannot execute one, so the fix would ship
  with no test that runs in `make check`. Stated rather than papered over.
- **A per-request timestamp list was refused.** The obvious rolling window keeps
  every request time and counts the ones inside the window. Acceptance line 4
  rules it out by name, and rightly: it is an unbounded write primitive on an
  unauthenticated endpoint. Only **admissions** are stored here, which is what
  makes the set bounded by the limit.
- **An approximate rolling window was refused.** The usual cheap scheme
  (weighted count over the current and previous fixed bucket) is one INCR per
  request but carries a sub-bucket error term, so the bound written down would
  have had to be "about 3". The sorted set is exact and its cost is bounded by
  the limit, which is 3 and 10.
- **The dimensions were not changed.** The rolling window is applied to the
  three budgets that already existed — phone (tokenized pseudonym), IP, and
  device (SHA-256 digest of the device id) — and to no new one. Whether an
  abuse budget *should* be per identifier, per device, or both is a product and
  security question; this issue narrows how the existing three are counted and
  answers no part of it. Nothing here needs a human to proceed, so no blocker
  row was opened.
- **`docs/evidence/INT-285.md` was not rewritten.** It names
  `test_a_fixed_window_hands_the_budget_back_at_the_boundary`, which no longer
  exists. It is a dated record of a run that happened; editing it to match
  today's tree would destroy the thing it is for.
