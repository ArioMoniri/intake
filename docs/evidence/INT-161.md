## 1. What this is

INT-160 built the connector framework and no adapter. This issue is the first adapter:
`intake_connectors.fhir.FhirR4PushAdapter`, plus the authentication its acceptance names —
SMART backend services — which turned out to be the larger half of the work, because it
brings a **second host**.

Nothing here relitigates INT-160. The registry still ships with zero rows and every push
still refuses; the receipt is still written before the send; the local ledger is still the
idempotency authority and the receiver is still not trusted to honour the key; the response
body is still never read.

## 3. Did SMART need a second `auth_mode`? Yes — because it needs a second *host*

`mtls` authenticates the **channel** with material OpenBao already holds: one request, one
host. SMART authenticates the **client** — mint a JWT assertion, sign it with a key the
hospital has registered, exchange it at the hospital's *authorization server* for a
short-lived access token, present that token on the FHIR request. Two requests, two hosts.

The schema change is small and is a widening of nothing:

| | `mtls` | `smart_backend_services` |
|---|---|---|
| `client_cert_ref` | **required** (unchanged) | optional — a hospital that authenticates by assertion has no client certificate to issue, and requiring one makes the row unfillable |
| `token_host` / `token_path` / `smart_scope` | **refused** | required |
| OpenBao under `credential_ref` | `{token}` | `{client_id, private_key}` + optional `key_id` |

The negative half matters as much as the positive: an `mtls` row that *names* a token
endpoint is refused, because a field a row's own auth mode never reads is an approval
nobody reviewed for a host nobody reaches.

### 3.1 What that does to the allow-list

**The token endpoint gets its own entry, its own purpose, and `phi_allowed: false`.**

ADR-025 named five bypasses; the fifth is *the right host addressed for the wrong reason*.
INT-160 met it as a host contracted, approved and allow-listed **for a different tenant**,
and answered with the tenant dimension. A SMART token endpoint is the same bypass in a
third form: a host on *this* tenant's own row, genuinely contracted and genuinely
approved, for a purpose that is **not receiving clinical records**.

So `EgressPurpose` gains one member, `CONNECTOR_AUTHORIZATION`, and
`ConnectorDestination.authorization_egress_entry()` builds a second `AllowlistEntry` — the
same type the vendor file validates, so it is still ADR-026's *one engine* — with
`phi_allowed: false` and no `phi_exception_approval`, because none is needed: nothing
personal is ever sent there. Consequences, each a test:

- the push entry and the authorization entry are **different permissions**
  (`test_the_push_entry_and_the_authorization_entry_are_different_permissions`);
- **one host serving both roles still needs both purposes** — sharing a hostname is not
  sharing a permission (`test_one_host_serving_both_roles_still_needs_both_purposes`);
- a token host that resolves into a denied range is refused before any byte leaves, and
  neither transport is entered
  (`test_a_token_host_that_resolves_into_a_denied_range_is_refused`);
- the transfer log records the exchange as `NON_PERSONAL` and the push as `PHI`, from the
  same log, in that order
  (`test_the_authorization_request_is_declared_as_carrying_no_personal_data`).

`tests/security/test_egress_allowlist.py`'s `NON_VENDOR_PURPOSES` gains the new member, so
the "no dead members" rule stays intact, and its companion test already asserts the
stronger direction — the purpose must be **absent** from the vendor file, never merely
optional in it.

### 3.2 What that does to OpenBao

A SMART row reads **one** document instead of two, still under the `connectors/` subtree the
connector policy is the only reader of:

```
connectors/<tenant>/<endpoint>/smart  →  {client_id, private_key, key_id?}
```

Never a long-lived bearer, because under SMART there is none. The **public** half of that
key must already be registered with the hospital, which is a human transaction and not a
field — see §7.

### 3.3 Two cheap answers that are wrong afterwards

**No discovery.** SMART defines `/.well-known/smart-configuration`; this never reads it.
Discovery lets the *receiver* nominate the URL our client credential is sent to, which is a
redirect to an unchecked host wearing a standard's name. The token URL and the assertion's
`aud` are both built from the registry row
(`test_the_token_endpoint_is_registry_data_and_is_never_discovered`).

**No token cache.** One push, one assertion, one token. A cached access token is a
credential that outlives the consent check that authorised it — the caching INT-160 already
refused for the consent verdict itself. The cost is one round trip on a path that is not
hot (`test_the_access_token_is_minted_per_push_and_never_cached`).

## 4. "Scoped by share consent token", made enforceable

SMART **backend services** has no per-patient scope: `system/...` is the only context, so
the acceptance clause cannot be discharged by naming the patient in an OAuth scope. What it
can mean at this layer, and still be enforced rather than asserted, is three things:

1. **The credential is valid only inside the consent window.** `ConsentVerdict` gains
   `expires_at` — files/06 §2.1 gives a share consent `{recipient, visit, sections,
   expiry}`, and the expiry is the half a connector can act on. The assertion's `exp` is the
   **earlier** of a 60-second ceiling and that expiry, so a stale-consent authorization is
   refused by the **hospital's** clock as well as ours
   (`test_the_assertion_expiry_is_clamped_by_the_share_consent_expiry`). A consent that has
   already run out never reaches the token endpoint at all
   (`test_a_consent_that_has_already_expired_never_reaches_the_token_endpoint`).
2. **No token is minted for a share that was refused.** The consent gate runs before the
   exchange, so a withdrawn scope means zero requests to either host
   (`test_no_token_is_requested_for_a_push_the_consent_gate_refused`).
3. **The authorization is never wider than the row's DPA grants.** The request asks for
   exactly `smart_scope`; a grant that does not cover it stops the push
   (`smart_scope_not_granted`, seven parametrised cases covering SMART v1 `.read`/`.write`
   and v2 `.cruds` spellings). An **omitted** `scope` is the scope we asked for, per
   RFC 6749 §5.1 — treating silence as a denial breaks conformant servers and treating it
   as a wildcard is the opposite mistake.

## 5. What a failure tells you without reading the body

INT-160 refuses to read a response body because a FHIR server answers a rejection with an
`OperationOutcome` whose `diagnostics` routinely quotes the resource that was submitted —
a patient's name arriving back inside an error (invariant 6). This issue does not reopen
that. What is left is more than it looks, and it is a **closed set**:

| source | what it separates |
|---|---|
| **the status** | our bundle (`422` — parsed, content wrong) from our request (`400` — did not parse) from our URL (`404`) from our credential (`401`/`403`) from their outage (`5xx`) |
| **`WWW-Authenticate`** | "the token expired" (`invalid_token`) from "the token was never granted this" (`insufficient_scope`) — two faults in the same status family with entirely different fixes |
| **`Content-Type`** | whether a FHIR server answered **at all**: `text/html` on a 4xx is a proxy or a login page, which sends an operator to the network rather than to the bundle they were about to re-read line by line |
| **which stage failed** | a token-exchange failure can never be `unresolved`, because no clinical byte was in flight — the ambiguity INT-160 parks for a human exists only on the push itself |

Delivered as `ConnectorAdapter.failure_hint(status, headers)` returning **one id-shaped
token from the adapter's own closed vocabulary**, folded into the outcome code as
`http_401.invalid_token`. `WWW-Authenticate` is receiver-controlled text, so an
unrecognised error code is not a code
(`test_a_hint_the_receiver_chose_freely_never_reaches_the_receipt`), and the sender
re-checks the shape before it reaches a receipt, because an adapter is the one component
written per hospital
(`test_an_adapter_hint_that_is_not_id_shaped_is_dropped_by_the_sender`).

One thing was **added** rather than merely read: `Prefer: return=minimal` (FHIR R4
§3.1.0.1.7). Not reading the body keeps PHI out of our logs; asking the server not to send
one keeps it off our socket, which is strictly better and costs a header.

## 6. Invariants held, one line each

- **4 — consent + audit.** Unchanged from INT-160 and now load-bearing twice: the gate runs
  before the token exchange, and its expiry bounds the credential (§4).
- **6 — no PHI anywhere it should not be.** The body is still never read; the
  `OperationOutcome` test drives a patient name through a 422 and sweeps the receipt and the
  outcome code for it. `AccessToken` overrides `__repr__` *and* `__str__` together, like
  `TlsMaterial` — overriding only the first leaves `f"{token}"` printing the secret. The
  metric's outcome label is a closed set of **our** codes, never a receiver's status: a
  label a receiver can choose is cardinality a receiver can choose. `SmartAuthorizationFailed`
  carries only an id-shaped code, and a key that fails to load raises it rather than the
  crypto exception, which can quote the material it was handed.
- **13 — metrics.** `connector_token_exchange_total{endpoint,outcome}` added to
  `observability/metrics_catalog.yaml` before it was constructed. No new service, so no
  `docs/slo/` file is due.
- **14 — secrets.** The row holds an OpenBao **path**; the material is read at send time and
  the access token exists for one push. Fixture credentials stay low-entropy and
  unstructured, and the signing keys are **minted in-process per test** rather than
  committed — a committed test key is both a gitleaks finding and a bad habit.
- **17 — no placeholders.** `scripts/ci/no_placeholders.sh` green over the staged tree.
  Nothing is invented: the registry is still empty, and the SMART facts a row would need are
  written into §7 for a human rather than guessed.
- **19 — no new dependency, and no FHIR library.** `packages/clinical-schemas` already emits
  the profiled R4 subset this product exchanges (`Bundle`, `Composition`, `Observation`,
  `RiskAssessment`, `Condition`, …) as pydantic models with `to_wire`, built for exactly this
  under INT-033 and ADR-002. A second FHIR implementation would be a second answer to "what
  shape do we send", and the licence-verification cost of a dependency — raw LICENSE blob,
  `licence_verified_at` in the model registry — would buy something we already have. The
  assertion is signed with `cryptography`, already a declared dependency of `intake-platform`
  (INT-017); no JWT library was added, because RS384/ES384 over a two-segment signing input
  is ~30 lines and a library would be a licence to verify for that.
- **22 — a clinical quantity keeps its declared scale.** Held by **having no boundary**: the
  adapter is handed rendered bytes and puts exactly those bytes on the wire — `call.body is
  payload.body`, asserted at the seam and again end to end through the sender. INT-303 closed
  one `Decimal`→float seam and INT-309 records three still open; a connector that parsed and
  re-serialised the bundle would be a fourth. It does not parse the bundle.
  **Deliberately not fixed here:** `clinical_schemas.mappers.r4.Quantity` still serialises
  `Decimal` to a JSON float, which is INT-309's second and third acceptance clauses, and its
  own text reserves the decision — *"whether a clinical quantity crosses the wire as a JSON
  string or a JSON number is an ADR, not a patch"*. Changing the encoding from inside a
  connector issue would be exactly the patch INT-309 refuses.

### 6.1 The mutation check

The suite passed on the first implementation pass, so five gates were broken one at a time:

| mutation | caught by |
|---|---|
| adapter headers applied **last** (so an adapter could set `Authorization`) | `test_an_adapter_cannot_overwrite_the_framework_headers` |
| the adapter's failure hint trusted without re-checking its shape | `test_an_adapter_hint_that_is_not_id_shaped_is_dropped_by_the_sender` |
| the consent expiry ignored when clamping the assertion | `test_the_assertion_expiry_is_clamped_by_the_share_consent_expiry`, `test_a_consent_that_has_already_expired_never_reaches_the_token_endpoint` |
| any granted scope accepted | `test_a_grant_that_does_not_cover_the_request_stops_the_push` + 3 parametrised cases |
| the token endpoint inheriting `phi_allowed: true` and the push purpose | `test_the_token_exchange_gets_its_own_entry_that_may_not_carry_phi`, `test_the_push_entry_and_the_authorization_entry_are_different_permissions` |

8 failures across the five, then all restored.

**No live call anywhere.** Every transport is a recorder over `httpx.MockTransport`
semantics and every resolver is a table. `scripts/ci/assert_no_vendor_calls.sh` green.

## 7. What is NOT met, and what a human must supply

**Clause 4 — "live smoke against a partner sandbox recorded before close" — is NOT met, and
cannot be met by an agent.** There is no partner sandbox to smoke against:

- **HB-A5** records that Acıbadem Teknoloji A.Ş.'s own interfaces are **UNVERIFIED**, with
  the standing instruction not to size the connector or promise a payload shape before that
  conversation happens. Whether the partner exposes a FHIR endpoint at all is the open
  question.
- **HB-A15** records that no destination exists: no executed DPA, no recorded tier-3
  approval, no OpenBao credential path, and no declaration of whether the receiver honours
  an `Idempotency-Key`. A live smoke needs all of those before it needs a test.

Neither is re-asked here. The issue is marked `awaiting-human` and carries its existing
`live-smoke` and `approval:human-vendor` labels.

Clause-by-clause:

| # | clause | state |
|---|---|---|
| 1 | contract tests vs HAPI | **met, with a named limit** — HAPI's documented behaviours are encoded as recorded fixtures through the adapter seam: `201` + an absolute `Location` naming its own base + `ETag`, a transaction's `200`, a `422` `OperationOutcome`, a `401` with `WWW-Authenticate`, and a `Prefer: return=minimal` create with no body. **No HAPI container is run**, per the standing rule that no live FHIR server is called in tests or CI. The limit is worth stating plainly: a container would prove our client against *a* FHIR server, not against *the partner's*, which is the thing HB-A5 says is unverified |
| 2 | SMART backend client credentials | **met** — §3, RFC 7523 assertion, RS384/ES384 from the key's own type, guarded exchange on a second host with its own purpose |
| 3 | scoped by share consent token | **met** — §4, three enforced bindings, with the honest note that SMART backend services has no per-patient scope so the binding is temporal plus the per-push gate, not a patient named in an OAuth scope |
| 4 | live smoke against a partner sandbox recorded before close | **NOT met** — above |

### 7.1 The SMART facts HB-A15 does not yet name

HB-A15 lists five facts a destination costs, and all five are **mTLS-shaped**. A
`smart_backend_services` row needs four more, and none is an engineer's to supply:

| field | what it asserts | who |
|---|---|---|
| `token_host` + `token_path` | the hospital's SMART authorization server, registered out-of-band — never discovered | owner, from the hospital |
| `client_id` (OpenBao) | the client identifier the hospital issued us at registration | owner, from the hospital |
| the registered **public key** | the public half of the signing key, already registered with the hospital (JWKS or by-value) — the private half goes to OpenBao under `connectors/` | owner (OpenBao) + the hospital |
| `smart_scope` | the `system/...` scope that hospital's DPA actually grants, e.g. `system/Bundle.c` | owner + counsel, from the DPA |

**No blocker id is minted here** — id allocation is the coordinator's, and predicting one is
how two agents in one night collide. The row's content is written out above and in
`docs/backlog/blockers.md` so it can be filed verbatim under whichever id is free.

Nothing is blocked from working in the meantime: the adapter ships wired, tested and
refusing, exactly as the framework does.
