## How it triggers

The staged workflow fires on `schedule`, on a `workflow_run` of `ci` or
`security` completing on main, and on `workflow_dispatch`. Its first step runs
`staging_follow_main.sh --decide`. The config's trigger answers, and only a
`true` mints AWS credentials (`aws-actions/configure-aws-credentials` v6.3.0).
The pin is `e1253824e5c10ff9df46874f81ed3ec929e19cfd`, resolved with
`git ls-remote` and tagged 15 Sep 2026. The licence is MIT, read from the raw
LICENSE blob at that revision. The job then runs `make staging-follow-main`.

- Under `nightly` (the default), only the schedule deploys.
- Under `green_merge`, a push to main deploys once its check runs are all
  green. The workflow fires on each of the two workflow completions. The
  first one waits if the other workflow is still running.
- A pull request's run, or a fork's branch named main, never reaches the job.

The job never edits a workflow. The owner applies
`owner-511-workflow.patch`. It moves the staged file into
`.github/workflows/staging-follow-main.yml`, adds it to
`tests/ci/test_aws_runner.py` (3 workflows, 14 jobs), and points the runbook
at the installed copy.

The INT-206 no-PHI workflow policy (`intake_platform.ci.scan_workflows`) was
run over `ci.yml`, `security.yml` and the staged file installed under its
final name. It reported 0 findings.

## Refusals

| refusal | where | exit |
|---|---|---|
| the event is not the configured trigger | driver, before any network call | 0 (skip) |
| the sha is not on main (GitHub compare `main...sha`) | driver | 3 |
| a check run on the sha failed (its own runs excluded) | driver | 3 |
| checks are still running | driver | 0 (wait) |
| `/version` lacks `X-Intake-Environment: staging-synthetic-only` | driver | 3 |
| the host already runs the sha | driver | 0 (skip) |
| the host is on main and newer than the target, or the two are unordered | driver | 3 |
| GitHub gives no answer on whether the host's commit is on main | driver | 3 |
| the archive's `infra/staging/REVISION` is not the sha | driver, then again on the host | 3 |
| another run holds the lock; `/opt/intake` is not a symlink | host | 3 |
| the release gate refuses, or cannot run, in the running api (INT-187) | host, before the host changes | 3 (status `error`) |
| `deploy.sh`'s own gate refuses in the new image | host; pointer restored | 3 (status `error`) |
| `init.sh` or `deploy.sh` fails | host; pointer restored | 1 (status `failure`) |
| smoke is red | host; the sha is not recorded | 1 (status `failure`) |
| smoke is green but the public `/version` does not name the sha with real stamps | driver | 1 (status `failure`) |

**Found by the live dry run.** The first read-only dry run against the real
GitHub and host refused with `unordered`. The order check asked GitHub to
compare the target with `1785dd58`, and GitHub does not hold that commit. A
commit GitHub never saw cannot be on main, so it cannot be newer than main.
`lineage()` now reads GitHub's body:

- a 404 or 422 means **off main**, and the deploy puts the host back on main;
- an empty body or a 5xx means **no answer**, and is still refused.

Direction is asked only for a host that is on main, and there only `forward`
proceeds.
