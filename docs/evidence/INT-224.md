## The finding: "generated from the data inventory" is false if the inventory means the schema

This is the thing worth having from this issue, so it goes first.

Invariant 18 gives us a data inventory: every column of every table carries
`{category, purpose, basis, retention, recipients}` in `Column.info`, and `tests/data/
test_inventory.py` fails the build on a column without one. That is a real, live, drift-proof
inventory of **111 columns**, and it is the obvious single source for a Data safety or App
Privacy declaration.

**It contains no audio row, and it cannot.** Invariant 3 forbids writing raw audio to disk,
database, object store or logs, and files/06 §3 states it as "Raw audio: never written". A
schema-derived declaration therefore says, with a straight face, that this product does not
process voice — about a product whose central feature is a spoken intake, whose Android
manifest asks for `RECORD_AUDIO`, and whose iOS microphone string tells the patient in
Turkish why we need the microphone. That is false in the one direction a store reviewer
notices, and the derivation would have been *correct* the whole time. Nothing would have
flagged it.

The same hole swallows three more flows, for the same structural reason — the data exists
and no column holds it:

| flow | why it has no column |
|---|---|
| `voice_audio` | invariant 3: never written anywhere |
| `health_platform_reads` | HealthKit / Health Connect steps, resting heart rate and sleep are read **on the device**; nothing is written unless the patient adds a summary to the note |
| `document_object` | the uploaded document's *bytes* live in MinIO; the `documents` row is a reference to them |
| `crash_diagnostics` | read through a closed key allow-list, and the reporter ships with no endpoint at all |

So the fix is a claim about shape rather than about tables: **an inventory row is five
fields, not a column.** `intake_platform.store.facts.OFF_SCHEMA_FLOWS` carries the same five
fields for those four flows, each built with the same `inv()` helper that refuses an empty
field, and each citing a repo file that states the facts rather than a memory of them (a test
asserts every cited path exists). `data_facts()` folds both halves into one sorted,
deterministic set:

```
flow:crash_diagnostics                               persisted=False cols=0   (inactive)
flow:document_object                                 persisted=True  cols=0
flow:health_platform_reads                           persisted=False cols=0
flow:voice_audio                                     persisted=False cols=0
schema:audit_trail:on_lawful_request                 persisted=True  cols=8
schema:consent_record:none                           persisted=True  cols=2
schema:consent_record:on_lawful_request              persisted=True  cols=8
schema:consent_record:on_patient_direction           persisted=True  cols=2
schema:guardianship_link:none                        persisted=True  cols=8
schema:operational_metadata:none                     persisted=True  cols=61
schema:operational_metadata:on_lawful_request        persisted=True  cols=11
schema:pseudonymised_identity:none                   persisted=True  cols=1
schema:special_category_health:none                  persisted=True  cols=1
schema:special_category_health:on_patient_direction  persisted=True  cols=9
```

And because a hand-kept list of flows rots exactly like a hand-kept label, the app's own
manifest is cross-checked against it in **both** directions: every Android permission and
every `NS*UsageDescription` (read from `expo.locales`, where a Turkish-first app keeps them)
must map to a flow or be recorded in writing as carrying no personal data, and a
classification for a permission the manifest no longer declares is equally a failure. Nine
capabilities, all classified.

**What this issue could not decide, and did not.** Whether audio that is transmitted for
transcription and never written counts as *collected* on Google's or Apple's form is **their
definition applied to our fact**. It is the single largest row of the label and it is
`HB-L21(a)`. The mechanism declares the fact; the form's answer is a determination.

## The second thing that had to be true: no vendor policy is written from memory

Apple's App Privacy data types, Google Play's Data safety categories, the Play Health apps
policy and the IARC questionnaire are published artefacts that move. Paraphrasing one is the
same failure as inventing a clinical threshold — authoritative to every later reader, and no
diff makes it look wrong. `files/00 §2` already records what that failure costs in this
project twice over (the `ininia.com` fabrication; "badges are not licence grants").

So `intake_platform.store.taxonomy.load_taxonomy` will not read anything but a file carrying
`source_url`, `retrieved_on`, a **verbatim snapshot committed beside it**, and the sha256 that
binds the two — refusing a taxonomy that has outlived the text it was read from. Nothing is
committed (`docs/legal/store/taxonomy/` is empty), so it raises, and every label path fails
closed behind it. The derivation itself is complete and is exercised end-to-end against
fixture taxonomies in the test file, including the refusal when a fact is unmapped.

That is the whole posture: **the mechanism is finished; the vendors' own words are missing,
and they are missing loudly** (HB-A12).

### Why the claims gate moved rather than being copied

Invariant 20 says "a CI text gate scans the regulatory and legal trees", singular. What
existed was two private copies of the vocabulary — INT-020's tuple over
`docs/security` and INT-240's satisfaction regexes over `docs/legal`/`docs/regulatory`. A
third copy would have made the gate a habit rather than a rule, so the vocabulary moved into
`intake_platform.legal.claims`; both suites now read their groups from there, and a
parametrised test asserts neither has grown a local tuple of regexes back.

Store artefacts are then inside the scan **by where they live**: `docs/legal/store/…`, under
a tree invariant 20 names by name. Nobody has to remember to add them.

**One scope decision, recorded because it looks like an omission.** `bare_percentage`
(INT-020's heuristic that a bare `NN %` in a security document has no innocent reading) is
**not** applied to `docs/legal`. `docs/legal/accessibility-statement.md` legitimately quotes
"200 %" Dynamic Type and "400 %" reflow — those are WCAG requirements, not claims about the
product. Carving conformance exemptions into a claims gate is a worse trade than naming the
metrics, and invariant 20 names metrics. The decision and its reason are in `claims.py`, not
only here.

### The device-claim gate, and the near-miss control that gives it meaning

A listing that describes automated urgency direction or automated interpretation of screening
instruments is claiming a `device_functions` capability that stays off without a recorded CE
certificate or clinical-investigation approval id. Relying on App Review to catch that is the
bad outcome — by then it is published. So `device_claim_hits` scans every listing field
against a phrase lexicon whose every pattern names the function it guards and the file that
defines it.

**It is phrase-shaped and not token-shaped, and the reason is Turkish.** The fixed copy of
files/06 §7 that we are *required* to show contains `tanı` twice — *"tanı niteliği taşımaz"*,
*"tanı değildir"* — and the permitted device-off safety line contains `112`. A token lexicon
would reject exactly the sentences that keep the product on the non-device side of the
boundary. Six near-miss controls pin that, including both disclaimers.

The lexicon also exempts **denials**, in both directions, because Turkish negates after the
phrase (`tıbbi cihaz değildir`) and English before it (`is not a medical device`). Only
**predicate** negation counts — `değil`, `-maz/-mez`, `-m(ı|i|u|ü)yor`, `yok`, and English
`not` **inside an auxiliary**. Two exclusions are load-bearing and both were found by a miss
rather than reasoned in advance (see the red run): `-sız/-siz` is privative and negates the
noun, so "kesintisiz triyaj" is a claim; and a bare `\bnot\b` is unusable in Turkish text,
because *not* means *note*. The exemption is further bounded by sentence end **and by a
contrastive conjunction**, so a denial cannot launder a claim beside it — pinned by
`test_a_denial_earlier_in_the_sentence_does_not_excuse_a_later_claim`, where
*"Triyaj yapmaz ama aciliyet düzeyi belirler"* yields exactly `urgency_tr`.

**And the gate has a live subject.** files/01 §4's promise to clinicians is *"a structured,
specialty-aware pre-visit note + **triage flag**"*, and §3b sells *"realtime triage"*
throughout — while files/06 §0.3 Stage A runs every commercial tenant with
`device_functions=off` and no automated urgency direction at all. **The strategy file's own
pitch is copy this gate refuses**, correctly, until a CE certificate or an approval id
exists. That is not a defect in either file; it is the reason files/01 §3b calls a marketing
claims-control gate a P1 deliverable, and the reason INT-257 is now filed.

the assertion:

1. **`test_every_named_blocker_exists_in_human_blockers` failed on `HB-A12`.** The checklist

   HUMAN_BLOCKERS rows, not to relax the test — which is the whole point of having a test

2. **`test_the_claims_gate_is_green_on_the_declared_trees` failed on my own README.**
   `docs/legal/store/README.md:43` said "health-accuracy claim" while explaining the accuracy
   gate, and the gate caught it. Recorded rather than smoothed over: it is the shortest
   possible proof that the new tree really is inside the scan, and the paragraph now names no
   metric and says why.

3. **`test_the_near_miss_copy…[Vizite is not a medical device.]` failed.** The denial
   exemption looked only *forward*, which is right for Turkish and wrong for English. Fixing
   it forward-only would have left the gate rejecting a sentence that denies the very claim it
   is scanning for. Both directions are now read, both bounded, and the contrastive-conjunction
   barrier was added in the same change so the bidirectional window could not be used to
   launder a claim.

4. **The gate was then run against files/01 §4's own promise to clinicians — and missed
   it.** *"Yapılandırılmış vizit öncesi **not** ve **triyaj** bayrağı"* reported no hit,
   because **`not` is a Turkish word meaning *note*** and the denial set carried a bare
   English `\bnot\b`. The product's own pitch line contains the exact token that silently
   exempted the triage claim standing next to it. English `not` is now recognised only in an
   auxiliary (`is/does/can/… not`, `cannot`, `n't`). The same pass removed `-sız/-siz` from
   the denial set: files/00 §2 lists it, but it is *privative* and negates the noun rather
   than the predicate, so "kesintisiz triyaj" claims uninterrupted triage and would have been
   exempted too. Three regression cases pin all three sentences.

   This one is worth more than the fix. It is the second time in this issue that a
   general-purpose text rule met Turkish and produced a **silent** wrong answer in the unsafe
   direction — the same shape as the `üre`/`BUN` substring rule and the `parseFloat("2,5")`
   finding in files/00 §2.
