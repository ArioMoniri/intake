# INT-329: Twilio SMS delivery adapter (tested, async, fail-closed outside dev)

**Date:** 26 September 2026 · **Branch:** `int-329-twilio-adapter` · **Issue:** #528 · **Sec-Row:** files/10 §9 `onboarding`

Source: production audit 2026-09-26 (`docs/audit/2026-09-26-production-audit.md` on `merge-305`),
finding **F13**, and the INT-325 wiring on main that left the OTP tier at 503 outside dev
because no delivery adapter existed there.

## What was wrong

The only Twilio adapter (commit `1bc0c42f`, never on main) had six problems:

- It made a **blocking** `httpx.post` inside the async OTP route, holding the event loop for up to 8 s.
- It had **no tests** and no evidence document.
- It read the auth token from the **environment** instead of OpenBao (invariant 14).
- It called `api.twilio.com`, which is **not on the egress allow-list**, and it did so outside the
  INT-018 guard.
- Its wiring `twilio_delivery_from_env() or DevLogDeliveryAdapter()` fell back silently, so it
  reported "sent" when nothing was sent. INT-325 has since closed that path on main.
- A 2xx response with no message id was recorded under a random id.

### Outcome mapping (each one logged once, ids only)

| vendor outcome | `OtpDeliveryFailure` | route |
|---|---|---|
| 2xx with a `SM…`/`MM…` sid | (receipt, `delivery_id` = the sid) | 202 |
| 2xx without a valid sid, or a body that is not JSON | `malformed_response` (no receipt is recorded that cannot be tied to a vendor message) | 503 |
| 401 / 403 | `auth_failed` | 503 |
| 429 | `rate_limited` | 503 |
| 5xx | `vendor_unavailable` | 503 |
| any other non-2xx, including an unfollowed 3xx | `rejected` | 503 |
| `httpx.TimeoutException` | `timeout` | 503 |
| any other `httpx.TransportError` | `unreachable` | 503 |
| `EgressDenied` | `egress_denied` (nothing reached the transport) | 503 |

Every 503 is the same `otp_delivery_unavailable`, so a vendor body never reaches the caller. Twilio's
error message echoes the number, and its 201 echoes both the number and the body.

**Log lines:**
- Success logs the vendor message id, the HTTP status and a vendor state drawn from a closed set.
- Failure logs the reason, the HTTP status and the vendor's **numeric** error code (for example
  21211 or 20003).

**Errors:** the error is raised **after** the `except` block closes, so `__cause__` and
`__context__` are both `None`. A chained httpx error would carry the request, and the request
carries the form body.

**Retries:** none. A retry would put a second code in flight. The patient's resend after the 60 s
cooldown is the retry.

## Wiring matrix (outside dev = every `INTAKE_ENV` except `dev`, staging included)

The tier is configured only when **all** of these hold, and then delivery is Twilio:

1. The tokenization key is set (INT-131, unchanged).
2. The egress policy (`phi_path` tier of the allow-list at `egress_allowlist_path`) admits
   `SMS_OTP_DELIVERY` to `api.twilio.com:443`. This is a pure check with no DNS, and it includes
   the runtime `INTAKE_ALLOW_PHI_EGRESS=explicit-yes` gate.
3. OpenBao KV `secret/api/twilio` holds `account_sid`, `auth_token` and `from`, all well-formed.
   This path is inside the `intake-api` policy's `secret/data/api/*` subtree
   (`scripts/security/openbao_dev_setup.sh`).

If any condition fails, `_auth_from_settings` returns `None` and every `/v1/auth` route answers
503 `otp_auth_unconfigured`. It logs one warning line that names the missing piece and never a
value. **`DevLogDeliveryAdapter` is never wired outside dev** (INT-325 / #521 kept). The egress
check runs before the vault read, so a vendor the policy refuses never has its secret pulled into
memory. **Dev is unchanged:** the dev logger is wired, and neither the vault nor the allow-list is
read.

**Credentials (invariant 14).** main already has a vendor-secret pattern: EHRbase credentials
(`intake_platform.ehrbase`, KV `secret/ehrbase`) and embed signing keys (`OpenBaoSigningKeys`) are
read from OpenBao only. This adapter follows that pattern. **The `TWILIO_ACCOUNT_SID` /
`TWILIO_AUTH_TOKEN` / `TWILIO_FROM` environment variables are not read.** A test sets all three and
asserts that the tier stays unconfigured.

**Staging follow-up (#573, not on main).** #573 passes those three variables to the API as env.
Once both PRs land, that passthrough configures nothing. Staging then needs four things, in the
same change that records the owner's decision:
1. a kv-v2 mount at `secret/`. OpenBao server mode has none by default; dev mode does.
2. `path "secret/data/api/twilio" { capabilities = ["read"] }` in
   `infra/staging/openbao/intake-api-policy.hcl`.
3. the runbook step that writes the three values there.
4. deploy.sh's App Attest guard pointed at the vault document instead of the env keys.

Until then staging's OTP tier stays at 503, which is fail closed. This PR does not touch
`infra/staging` because #573 edits the same files.

## Egress: the row is the owner's decision, so the adapter fails closed

**How outbound vendor calls are enforced.** `infra/security/egress-allowlist.yaml` is read by
`intake_platform.egress` in process and rendered into the squid proxy (ADR-025). A caller must
present a purpose and a data class. Personal data (the `PHI` and `PSEUDONYMOUS` classes) moves only
to a row that meets three conditions:
- it is `phi_allowed: true`;
- it carries a `phi_exception_approval` that names a recorded human decision;
- the runtime flag `INTAKE_ALLOW_PHI_EGRESS=explicit-yes` is set.

The API is a PHI-path service, and the `phi_path` tier is empty by design. ADR-025: "a PHI-path
service has no route out at all", and in compose the `phi` network is `internal: true`.

**Why the row was not added.** A phone number is personal data, and here it goes to a US processor.
It cannot go to a `phi_allowed: false` row: the policy refuses personal data there, and declaring
the phone number `NON_PERSONAL` would be lying to the guard. The only honest row shape is on the
`phi_path` tier with `phi_allowed: true` and a `phi_exception_approval` naming a decision. No such
decision exists, and agents never invent an approval id. The file is also hook-protected
(07 §3.8), and the issue's own acceptance line says the row lands "only after the owner records the
DPA and cross-border decision". The row is therefore **awaiting-human**.

**The shipped policy refuses the vendor at three points:**
1. At wiring: the tier stays at 503.
2. At the adapter: `egress_denied`, and the mock transport is never reached.
3. At the allow-list test, which asserts every tier refuses the purpose for every data class.

**The purpose member without a row.** `EgressPurpose.SMS_OTP_DELIVERY` exists because the adapter
must declare why it calls. `tests/security/test_egress_allowlist.py` requires every member to be
used by a shipped row, so the member is listed in a new `PURPOSES_AWAITING_THE_OWNER` set. The set
can only shrink, because a companion test fails the moment any row declares a pending purpose. The
row and the removal from that set therefore have to land together. **This is the one test
exemption this PR adds.** It is bounded, and the stronger direction is asserted beside it. It is
flagged for the security reviewer.

**Data class.** The call is declared `DataClass.PHI`, the strictest class. A phone number is
personal data under KVKK, and the phone of a patient signing up for a clinical intake identifies
them as a patient. The policy gates both personal classes the same way.

**Inventory (invariant 18).** The raw phone number is never persisted: the patient row keeps only
the Tokenizer pseudonym, and the code lives in Redis as a digest. So this PR adds no new stored
field. The acceptance line's "phone-number field carries the data-inventory annotation" means
recording the SMS processor as a **recipient**, which is a legal statement. It lands with the
owner's decision, together with the egress row.

## Awaiting-human

**The owner (product owner, with counsel).** One sentence closes it:

> May the patient's phone number and a one-time code be sent to Twilio, a US processor, for OTP
> delivery, and under which DPA and which KVKK Art. 9 cross-border transfer mechanism? The decision
> id is what the allow-list row records as its `phi_exception_approval`.

No `HUMAN_BLOCKERS.md` row exists for the SMS vendor. `docs/evidence/INT-131.md` lists "SMS vendor
contract (owner)" without an id. The owner allocates the id; agents never mint one.

Once the decision is recorded, one change lands these together:
- the `phi_path` row (`api.twilio.com:443`, `purpose_id: sms_otp_delivery`, `phi_allowed: true`,
  `phi_exception_approval: <decision id>`, the prose purpose and basis), plus the regenerated
  squid config;
- the removal of `SMS_OTP_DELIVERY` from `PURPOSES_AWAITING_THE_OWNER`;
- the recipient annotation;
- the topology change ADR-025 requires, because the `phi` network is internal;
- `INTAKE_ALLOW_PHI_EGRESS=explicit-yes` on the host;
- the staging vault steps above.

**Credentials (owner).** Write `account_sid`, `auth_token` and `from` to OpenBao
`secret/api/twilio` on each host. Never put them in an env file or in chat.

**SMS copy.** The body is `Doğrulama kodunuz: <kod>. Bu kodu kimseyle paylaşmayınız.` It uses the
siz register, with -iniz for instructional prose, and carries no brand name, because which brand
ships is not settled on main. A brand prefix or a domain-bound one-time-code line is a copy
decision for the owner.
