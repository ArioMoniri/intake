### How the two halves were read

- **"report generated from a11y CI results"**: delivered. The source of record is
  `docs/compliance/accessibility-conformance.yaml`, with one row per WCAG 2.2 Level A and AA
  success criterion (all 55) and one per EN 301 549 V3.2.1 clause assessed beyond clause 11.1 to
  11.4 (27). `scripts/compliance/render_a11y_report.py` renders it into
  `docs/compliance/accessibility-conformance-report.md`. "Generated from CI results" is honoured
  in three ways:
  1. Every automated citation is resolved against the vitest source that CI runs (`pnpm -r test`,
     therefore `make check-ts`). It must name exactly one `it`/`test` title in a file that
     `apps/mobile/vitest.config.ts` collects, so a renamed, deleted or skipped test breaks the row.
     A red test fails check-ts itself.
  2. Every contrast figure is computed from `apps/mobile/src/lib/theme.ts` at render time. If the
     palette changes, the report must be re-rendered and its findings re-assessed.
  3. The EN 301 549 clause 11.1 to 11.4 table is derived from the WCAG rows.

  `tests/legal/test_a11y_report.py` (26 tests) pins all of this, and CI's `check-py` collects it.
  A one-off run against a vitest JSON report is recorded below. It shows that all 80 cited tests
  passed.
- **"statement published in-app and web"**: **not delivered, and not claimable.** Publication is
  gated on HB-L9 (posture and BK numbering) and on counsel. The statement's feedback channel
  (owner) and enforcement route (counsel) are undecided. The Turkish statement text belongs to
  counsel and the owner. Every legal text serves only once signed under the HB-L27 regime
  (`docs/legal/documents.yaml` is empty by design). `docs/legal/accessibility-statement.md` is
  not hash-bound and no loader reads it, so its **factual conformance status** was updated to
  match the report. Its "NOT FOR PUBLICATION" posture, its §5 asks and all legal framing are
  unchanged. No Turkish statement copy was drafted: the facts a published statement must carry
  are §4 of that file, and a test keeps them complete.

## What the consistency test enforces

`tests/legal/test_a11y_report.py`:

- The 55 WCAG 2.2 Level A and AA criteria are mapped exactly once, with correct levels and
  new-in-2.2 flags. The canonical list is written in the test, independent of the renderer.
  BK1 to BK31 sit on the Level A rows in canonical order. 4.1.1 Parsing appears only as EN
  11.4.1.1.
- **No Supports row lacks evidence. Every cited test resolves to exactly one test** in a vitest
  file CI runs (`src/**/*.test.ts` or `e2e/**/*.spec.ts`). The title reader handles `it`, `test`,
  `it.each(...)(...)` across lines, and quoted and template titles, and it ignores skipped tests
  and `regex.test(...)` calls.
- Near-miss negatives (all through `validate`):
  - a renamed citation;
  - a Supports row with no evidence;
  - a citation to a non-suite file;
  - an undated manual check;
  - a device-decided row set to Supports;
  - a "fixed" palette, which must force re-assessment of 1.4.3.
- Every manual check is dated no later than the assessment, carries by, method and result, and is
  cited. Every Not Evaluated row is exactly the set the owner's device audit decides.
- Contrast findings agree with the palette they measure. The arithmetic is checked against 21:1,
  1:1 and INT-144's measured 3.43 and 1.25.
- The committed Markdown equals the rendering. The count line matches. The EN clause 11 table is
  derived.
- The statement names every criterion the report marks Partially Supports, Does Not Support or
  Not Evaluated. The matcher does not let "SC 1.4.10" satisfy "SC 1.4.1", and a test proves it.
  The statement reads "partially conformant". Neither document claims blanket conformance.

## Findings from re-assessment (reported, not fixed; each is a row with its evidence)

1. **SC 1.3.4 Orientation: Does Not Support.** `apps/mobile/app.json` sets
   `"orientation": "portrait"`. INT-144 recorded this row as unverified because no screen locks
   orientation in code.
2. **SC 3.3.8 Accessible Authentication (Minimum): Does Not Support.** INT-144 did not assess this
   row. The OTP is six `maxLength={1}` boxes, and `setDigit` keeps only the last character it
   receives, so a pasted or autofilled code cannot fill them. Android declares no SMS-code
   autofill. This also undoes INT-144's BK26 mitigation. The fix is a single code field with
   `oneTimeCode` / `sms-otp`. It is a mobile change for its own issue, and `e2e/auth.spec.ts` pins
   the six-box design today.
3. **SC 3.3.1 / SC 4.1.3: Partially Supports.** `issue-link.tsx` (INT-311) and `ConfirmCard.tsx`
   set only the Android live region and never call `useLiveAnnouncement`, so VoiceOver is
   silent. The same holds for `RecordReading.tsx`'s progress line and, in dormant kiosk mode, for
   `KioskGate.tsx`. The BK28 test lists its four screens by hand, so it could not see them. The
   durable fix derives the list from every `live=` site. 4.1.3 was not assessed by INT-144.
4. **SC 2.2.1 scope.** The BK13 test scans `.tsx` only. `lib/kiosk/nativeKiosk.ts` holds a 60 s
   idle wipe with no warning, and its comment says it was placed there because of that test.
   Kiosk mode cannot activate today, so the row stays Supports for the phone app, with the kiosk
   caveat stated.
5. **Posture corrections, with reasons in each row:**
   - 1.4.12 is Not Applicable, because the criterion is scoped to markup;
   - 2.4.5 is Not Applicable under WCAG2ICT, and INT-144's Kayıtlarım route does not exist;
   - 3.1.2 is Partially Supports (English locale);
   - 1.3.5 is Supports, on a recorded field inventory;
   - EN 11.6 is not user documentation. That obligation is 12.1.1, and it is Does Not Support.
