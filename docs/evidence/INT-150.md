# INT-150 — Doctor Link: 128-bit token + OTP + expiry + view limit + revoke + watermark + access log + no-index

Epic E09-clinician · phase P0 · `sec_row: doctor-link` (docs/security/threat-model.md)
· legal `KVKK-12, HHY-23` · depends on INT-084, INT-016.

Acceptance, verbatim:

> entropy/expiry tests; watermark carries recipient+timestamp; robots/noindex;
> every open audited and visible to patient

## What this issue had to decide first

**INT-137 refused to build the Doctor Link QR and named this issue as the reason:** with no
redemption route, clinical data behind a link would be a share with no consent check and no
audit entry (invariant 4), and a bearer token rendered to a camera is a credential in a
photograph (invariant 6). This issue builds the redemption route with both. **It does not touch
the four negative controls in `apps/mobile/e2e/review_send.spec.ts`** that fail the build if a
link, a scheme, a token or a serialised note appears on the review screen. Whether a QR becomes
legitimate now is a separate decision with its own reasoning — the controls stand.

## Design decisions and why

**1. Expiry is computed on the server, anchored on the visit.** files/02 §2b: *"Doctor Link
expiry is pinned to `visit_datetime + 72 h`, never `issue_time + 72 h` … the single most likely
cause of 'the doctor couldn't see it' at P1."* This repo records a visit **date** and no time of
day (`visit.date`, INT-134), so the exact datetime cannot be computed. `link_expires_at` anchors
to the **start of the visit date in Türkiye** and adds 72 h. The direction is deliberate: the
start of the day is never later than the appointment, so the computed expiry is never later than
the spec's value — it errs strictly towards LESS exposure — while still leaving at least 48 h
after any appointment on that date. An hour of the day is invented nowhere, and a visit with no
recorded date is refused (`visit_date_unknown`) rather than given an issue-time clock.

*Recorded for the coordinator, not fixed here:* the schema has no `visit_datetime`, so the
exact rule in files/02 §2b is not computable by anything in this repo. That is a schema change
(and an OCR/confirm-flow change) with its own acceptance; it is not INT-150's to mint an id for.

**2. The token is 128 bits and the database holds no token.** `secrets.token_urlsafe(16)`;
persisted as SHA-256 (`token_fingerprint`), compared with `hmac.compare_digest`. A digest is
enough precisely because the input is 128 uniform bits — there is no dictionary to run against
it, which is why a *token* needs no keyed construction and a six-digit *code* does (the OTP's
`code_digest` shape is kept for the code). The token appears in exactly one response body, once,
and in one request field. Both redemption routes are POST: **no path or query parameter anywhere
in the package carries it**, asserted over the live OpenAPI document, so it cannot reach an
access log, a Referer header, a browser history entry or a proxy trace.

**3. The OTP is the INT-131 gate, not a second one.** `intake_api.doctor_link.service` drives
the same `AuthStore` (6 digits, 5-minute TTL, 5 attempts, the request budgets, the resend
cooldown) with its own `dlink` key prefix. Two deliberate differences in what the budgets are
counted *against*:

- the five verify attempts are counted per **link**, not per patient: a brute-forcer working on
  one link must not lock out another link to the same person, and two links must not share one
  five-attempt budget;
- the request budgets are counted per **link and per path**: if the patient-side mint and the
  public delivery request shared one budget, anyone holding the token could spend the patient's
  own minting budget and lock them out of the link they issued — a denial of service built out
  of a rate limit.

**The gate's known limitation is inherited knowingly, not re-introduced.** `otp_request_gate` is
read-decide-write; INT-263 records that two workers racing on one identifier can both be
admitted, and that the atomic fix needs a Lua script `fakeredis` cannot execute. INT-150 does not
narrow it and does not write a second, differently-broken limiter. The control that actually
bounds disclosure — the **view budget** — *is* atomic: `spend_one_view` carries "not revoked, not
expired, budget left" and the increment in one guarded UPDATE, so two concurrent redemptions
cannot both be admitted at the limit, on SQLite and on Postgres.

*(Note on the tree: PR #436 had not merged into `origin/main` when this branch was cut, so the
gate this branch reuses is still the fixed-window form whose own comment names INT-263. Reusing
the function rather than copying its numbers is what makes that irrelevant — when #436 lands,
this path inherits the rolling window with no edit here.)*

**4. Delivery is refused rather than faked.** files/10 §2 sends the code *"to the phone/e-mail
the patient chose"*. No such destination is recorded anywhere in this repo — invariant 14 keeps
contact identifiers out of every app table, and no file records a Doctor-Link delivery
preference at all — and no messaging vendor is contracted (INT-131 recorded the same gap). So
`FailClosedDoctorLinkDelivery` is the only wired adapter and it raises; the public route runs the
abuse gate **first** (so the control is real the day a channel lands) and then answers 503
`doctor_link_delivery_unconfigured`. Build the mechanism, wire the gate, make it fail closed,
leave the content empty. The channel that *does* exist is the patient's own authenticated
session: `POST /v1/visits/{id}/note/doctor-links/{link_id}/otp` mints the code and hands it to
the patient, who passes it to the clinician. A delivery attempt cannot invalidate a code the
patient already minted — the public route delivers **before** it remembers.

**5. The consent check does not disappear with the principal.** The redemption routes have no
account, so a route-level guard has nothing to resolve. They carry a sixth, caged
`doctor_link_redemption()` marker (accepted only under `/v1/doctor-link`) and run
`ensure_consent(share:previsit_note)` **record-level** inside the endpoint against the note's own
patient — the same evaluator the clinic-admin branch of `notes.read_note` uses, so a withdrawal
or a stale text refuses here too. It runs **before** the view is spent, so a refused consent
costs the patient no view.

**6. Consent is not bundled, and a withdrawal cannot lock the revoke button.** Issuing and
minting declare `core` enforced with `share:previsit_note` *conditional* and enforced inside the
endpoint (KVKK m.7 / files/06 §2.1: a route that enforced both would be service conditioning —
`tests/legal/test_consent_unbundled.py` caught exactly that on the first draft). Revoke and the
access log are declared under `core` alone: a patient who withdrew consent to share must still be
able to stop the sharing they already started.

**7. The scope is never copied.** A link hangs off a `shares` row and the section list stays on
`shares.scope_sections`. Nothing in this package names a section id, so **INT-304's widening of
`SectionId` needs no change here** and a link can never expose a section the share does not
carry. Revoking a share — which every note save does — revokes its links.

**8. The watermark identifies the GRANT, not the viewer.** `Watermark` carries the recipient the
patient named, the instant of this opening, and the opaque `doctor_link:<id>` ref. Nothing
derived from the request: no IP, no user agent, no device fingerprint. The recipient label is
patient-typed, so it is bounded, single-line, envelope-encrypted at rest and never logged, never
in a filename, never in an audit `resource_ref`. The stamp is fed verbatim to the committed
`render_document_pdf(watermark=...)` (INT-084), and the test asserts the recipient and the
timestamp in the PDF **bytes** — the composer and the renderer cannot drift.

**9. Redis is a routing hint; the database is the authority.** A redemption arrives with no
tenant and every clinical read runs in a tenant-scoped RLS session, so a
fingerprint→(tenant, link) index in Redis is what makes that session openable. The row's own
fingerprint is then re-checked in constant time, so an attacker who could *write* that index
still cannot point a token at a grant that does not carry it — a test forces the index back after
a revocation and the row still refuses. Losing the index makes every live link stop working,
which is the fail-closed direction; the patient can issue another.

**10. The first-open instant is deliberately not persisted as a column.** Every open is written
to the hash-chained audit log — which is what invariant 4 requires and what the patient's access
log renders — and nowhere else. A queryable open instant is the missing half of
`wait.doctor_link_first_open_h`, and landing it without a publisher would put
`intake_platform.wait_times`, the catalogue status and the writer out of step, which is the exact
drift that registry exists to prevent (inv. 13). Publishing that interval needs an **unlabelled**
path through `publish_wait`/`roll_up_wait` that INT-241 built only for the labelled
`records_processing` family. `WAIT_SOURCES` now states this instead of claiming INT-150 would
land it. **Ask for the coordinator: a new issue for the unlabelled wait-publisher plus the
Doctor Link open instant.** No id was minted here.

## Test plan → what landed

`tests/clinician/test_doctor_link.py`, 44 tests. One injected clock throughout
(`DoctorLinkService.utcnow` is what the routes read for expiry, the view budget and the watermark
instant, and it is the same clock `AuthStore` counts OTP windows on): nothing sleeps and nothing
reads the wall clock. The near-miss negative controls a naive implementation passes:

| control | test |
|---|---|
| expired by exactly **one second** (alive at −1 s, dead at +1 s, same code) | `test_expiry_is_exact` |
| the **(limit + 1)th** view — both the refused mint and a caller already holding a valid code | `test_the_view_after_the_last_one_is_refused` |
| a token used **immediately** after revocation, with no clock movement | `test_revocation_is_immediate` |
| the same, with the Redis routing hint **forcibly restored** (the row is authority) | `test_revocation_holds_even_if_the_routing_hint_comes_back` |
| a token differing from a valid one in **one character** (and the valid one still opens) | `test_a_token_one_character_off_opens_nothing` |
| an OTP **one digit** off, refused generically | `test_a_code_one_digit_off_is_refused_generically` |
| the **right** code on the attempt after the five-attempt budget is spent | `test_the_attempt_budget_kills_the_code` |
| a generator that passes every statistical check and is still predictable (`random` vs `secrets`) | `test_the_token_source_is_secrets_and_never_random` |
| a consent withdrawn between minting and opening — refused, and **no view spent** | `test_a_refused_consent_costs_the_patient_no_view` |
| a withdrawal that would lock the revoke button | `test_a_withdrawn_share_consent_cannot_lock_the_revoke_button` |
| a delivery attempt that kills a code the patient already minted | `test_a_failed_delivery_does_not_kill_a_code_the_patient_already_minted` |
| the marker borrowed outside its prefix (`/v1/doctor-linkish`, `/v1/sneaky`) | `test_no_route_is_undeclared_and_the_marker_is_caged` |

Plus the acceptance clauses directly: entropy (`128` bits, 2048 draws distinct, fingerprint-only
at rest, never in a log line), expiry (visit-anchored, not issue-anchored; undated visit refused),
watermark (recipient + timestamp + grant ref, through the real PDF renderer's bytes, and nothing
about the viewer), no-index (every response including refusals), and "every open audited and
visible to patient" (audit entry per open, chain-verified, projected into the patient's access
log as a role and never an identity).

## Invariants touched

- **4** — every redemption checks a consent scope record-level and appends an audit entry before
  it answers; a view that cannot be audited is not served.
- **6** — no token, code or recipient label in any log, URL, filename or audit field; error
  bodies are codes; the metric has no identifying label.
- **13** — `doctor_link_events_total{event}` catalogued `live`; `wait.doctor_link_first_open_h`
  left `planned` with the registry stating why.
- **14** — the recipient label is envelope-encrypted; the token is a fingerprint.
- **16** — the `doctor-link` row in files/10 §9 / docs/security/threat-model.md updated with the
  controls, signals and tests this PR adds.
- **17** — no placeholder anywhere: the one missing dependency (a delivery channel) is a
  fail-closed seam and a recorded ask, not a stub.
- **18** — every column of `doctor_links` carries `{category, purpose, basis, retention,
  recipients}`; retention rides the existing `RET_SHARE` clock and the existing
  `doctor_link_tokens` destroyable class.

## What is NOT delivered, and why

1. **The files/10 §2 delivery channel** ("the phone/e-mail the patient chose"): no recorded
   destination, no contracted vendor. Refused (503) behind a live abuse gate. Recording a
   patient-chosen contact channel would be a new category of personal data, which CLAUDE.md makes
   a stop-and-ask — **for the coordinator to file, with the named human and the one sentence
   they must answer.** No HUMAN_BLOCKERS id was minted here.
2. **`wait.doctor_link_first_open_h`**: the publisher does not exist (see §10 above). Recorded in
   `intake_platform.wait_times` and here; a new issue is the coordinator's to allocate.
3. **The clinician-facing rendering** of the note and its watermarked PDF download: that is
   INT-151's surface. INT-150 composes the stamp and proves it survives into
   `render_document_pdf`'s bytes; it does not add a PDF route, because the note PDF's standing
   footer renders from `docs/legal/strings.yaml` (`previsit_note.footer`), which does not exist
   until INT-210 and would make the route permanently 503 rather than shipping a control.
