## Acceptance (verbatim, GitHub #983)

> Owner decision D38 (28 Oct 2026): move the phone-tokenization key (today INTAKE_TOKENIZATION_KEY in the synthetic host's env file) into OpenBao NOW, carrying the SAME key material across so no pseudonym changes. The API reads it only from OpenBao (invariant 14); deploy.sh migrates it idempotently (read env value → write to OpenBao only if absent → verify equality without printing → remove from env file only after verification); a before/after pseudonym-equality probe on the host for a synthetic number proves no change; the key value is never printed, logged or committed. The backlog row (docs/backlog/issues.yaml, INT-584) restates it in four lines. Each is met below.

## 1. Where the key was, and why it matters

Every keyed pseudonym the API derives is an HMAC-SHA-256 under one key
(`intake_platform.tokenization.Tokenizer`): a phone number in the OTP tier, a hospital patient
number in the previsit read-back, and a device's foreign id on the RED path. Until this change
the synthetic host kept that key as `INTAKE_TOKENIZATION_KEY` in `/etc/intake-staging/.env`
(generated by `init.sh`, INT-352). compose passed it to the API, and `ApiSettings.from_env` read
it. INT-581 recorded that as an open residual against invariant 14. D38 moves it now, with the
same material: a new key would give every patient on the host a new pseudonym.

One detail decides whether "the same material" really means the same pseudonyms. The env path
handed the Tokenizer `key.encode("utf-8")`: the UTF-8 bytes of the 64-character hex **text**,
not the 32 bytes it encodes. The OpenBao path does exactly that. A test pins the near miss:
hex-decoding the key, or one character of drift, gives a different pseudonym.

## 2. The change

**The API (`services/api`).**

- `intake_api.tokenization_key` (new). It resolves the key from OpenBao `secret/api/tokenization`,
  field `key`, through `intake_platform.secrets.SecretsProvider`, the existing secrets path, with
  the API's own token. It tells four states apart: `loaded`, `absent` (404, or no `key`),
  `unreadable` (OpenBao unconfigured, unreachable, sealed, or the token refused) and `malformed`
  (anything but 64 to 256 lower-case hex characters). `with_tokenization_key` puts the key, or
  the typed reason it is missing, into the settings once, at wiring. The log line names the
  path, the state and the exception class, never a value.
- `ApiSettings.from_env` no longer reads `INTAKE_TOKENIZATION_KEY`, in any environment. A value
  left in the environment is named in a warning and ignored, so it is never a fallback. The
  `tokenization_key` field is `repr=False`. A new field, `tokenization_key_refusal`, holds the
  typed reason (`tokenization_key_absent` by default).
- The tiers that need the key answer `503` with that reason:
  `{"error": "otp_auth_unconfigured", "reason": "tokenization_key_unreadable"}`, and the same
  for `previsit_output_unconfigured`. A tier that is down for another reason (no Redis, no SMS
  vendor) carries no key reason.
- Dev reads the OpenBao dev server like every environment.
  `scripts/security/openbao_dev_setup.sh` seeds a random key there (`openssl rand -hex 32`,
  on stdin, check-and-set, kept on re-run), never a literal. The one exception is dev under
  `INTAKE_API_KEK_MODE=file-dev`, the sanctioned no-OpenBao escape that INT-325 refuses at boot
  everywhere else. It takes a process-local random key, as it takes process-local KEKs.
- `tokenization_key_state{state,origin}` (gauge, catalogued as live) is set to 1 at wiring.
  `origin` is `env_file` for a key carried across by D38, `generated` for one made in OpenBao,
  `process_local`, `unrecorded`, or `none`. It holds ids only. This is the migration outcome as
  the API sees it: `state="loaded",origin="env_file"` after the move.
- `intake_api.tokenization_probe` (new): the probe that runs in the api container (section 4).

**The synthetic host (`infra/staging`).**

- `tokenization_key.sh` (new) carries out the move, and `deploy.sh` runs it on every deploy,
  once OpenBao is unsealed and the API's token renewed, before the API starts. It prints
  `changed` or `unchanged`, and the deploy restarts the API on `changed`. `init.sh` runs it with
  `--init`, which alone may make a new host's key, and only in OpenBao.
- `compose.yaml` passes no `INTAKE_TOKENIZATION_KEY`. `staging.env.template` no longer lists it,
  so `init.sh` can never mint one into the env file again.
- `openbao/intake-api-policy.hcl` gains `read` on `secret/data/api/tokenization`. It gains no
  metadata, list, write or delete grant.

**Docs.** The staging runbook gains the section "Phone-tokenization key". It covers the probe
command, what `differ` means, and the rollback hazard. files/10 §9 `onboarding` row; the
threat model's `identifiers` section states the bound and closes INT-581's residual.
`docs/runbooks/red-acknowledgement.md` points at the new location.

## 3. What deploy.sh does on its first run after the merge

On the synthetic host today, the env file holds the key, and OpenBao holds no
`secret/api/tokenization`:

1. It writes the KV engine (create-if-absent) and the committed policy, with the new read grant.
2. It computes a key check value for each copy (HMAC-SHA-256 of a fixed label under the
   key's UTF-8 bytes). Each is computed from stdin and held in a shell variable, never printed.
   OpenBao: `absent`. The env copy: a well-formed key.
3. `record`: the env copy goes on stdin to `python -m intake_api.tokenization_probe record`, in a
   one-off container of this release's api image. That prints a one-way fingerprint of the
   synthetic probe number's pseudonym, which lands in `/etc/intake-staging/tokenization-probe.sha256`
   (root, 0600, written once).
4. It writes `{"key": <env value>, "origin": "env_file"}` to OpenBao with
   `bao kv put -cas=0`, on stdin. Check-and-set means it is written only where nothing is.
5. It reads the document back with the **API's own token**, the read the API makes at boot,
   and requires the same check value. A policy without the grant stops it here.
6. `compare`: the probe resolves the key exactly as the API does at boot and compares the
   pseudonym fingerprint with the record. It must say `equal`.
7. Only then does it remove the `INTAKE_TOKENIZATION_KEY` line from the env file. The rewrite is
   atomic and 0600, using `env_set`'s temp-file discipline. It prints `changed`.
8. compose recreates the API without the variable (its environment changed). The API reads
   the key from OpenBao and sets `tokenization_key_state{state="loaded",origin="env_file"} 1`.

Every later deploy finds the key in OpenBao only. It checks that the API's token still reads it
and that the probe still says `equal`, and prints `unchanged`. If anything fails, the script
stops the deploy before the API restarts, and nothing it has not proven is removed:

| state found | what happens |
|---|---|
| OpenBao holds a **different** key from the env copy | `CONFLICT`: nothing written or removed, both copies kept, exit non-zero |
| either copy malformed | refused, nothing written or removed, exit non-zero (a malformed OpenBao document is never overwritten) |
| the API's token cannot read the written document | exit non-zero; the env copy is kept (the next deploy, after the grant is fixed, finishes) |
| the probe says `differ` | exit non-zero; the env copy is kept |
| both copies equal (a run that stopped after the write) | re-proves both, removes the env copy, prints `unchanged` |
| neither holds a key | a deploy refuses and names `./init.sh`; it never makes a key |

## 4. How equality is proven, and the probe command

Two proofs, neither of which prints a key, a digest of a key, or a pseudonym:

- **The key check value.** HMAC-SHA-256 of the fixed label `intake.int584.key-check.v1`, under
  each copy. The env copy is read from the env file; the OpenBao copy is read with the root
  token to decide, and with the API's token to verify. The values are compared in shell
  variables. Equal check values mean byte-equal key material.
- **The pseudonym.** `intake_api.tokenization_probe` derives the pseudonym of the fixed
  synthetic number `PROBE_NUMBER` (`+90` with no mobile prefix, so no subscriber has it). It
  builds the Tokenizer the way the API does (`intake_api.state._tokenizer_from_settings`).
  `record` fingerprints the pseudonym under the env copy before the move, using SHA-256 over a
  domain-separated pseudonym. `compare` resolves the key through `with_tokenization_key` (OpenBao,
  the API's own token) and prints `equal` or `differ`. It exits 0, 1, or 2 when there is nothing
  to compare, in which case it still prints `differ`.

The owner's (or the queue's) command after the merge-queue deploy, which prints only `equal` or
`differ` and exits 0 only for `equal`:

## 5. Tests

- `tests/api/test_tokenization_key.py` (37). It checks that the environment is never read
  (dev, staging, prod) and that a key in the environment is no fallback, which is the near miss
  for "OpenBao only". The migrated key gives every pseudonym the env path gave, through the
  API's own construction. Near misses: a hex-decoded key and a key one character away both fork
  the pseudonym. Twelve failure inputs are each mapped to their typed reason and the gauge,
  with no value logged. Other cases: the closed origin vocabulary, `repr`, the
  resolution invariant, dev on the dev server, the file-dev escape and its near miss (file-dev
  outside dev still reads OpenBao), and both routes' 503 with each reason. Near miss for the
  routes: a key is present and the OTP tier is down for another reason, so no key reason
  appears.
- `tests/api/test_tokenization_probe.py` (20). `record` prints a domain-separated fingerprint
  only, and refuses a malformed key. `compare` gives `equal` for the same key. Near misses:
  `differ` for a key one character away, and for the same key under another key id. Absent,
  unreadable and malformed give `differ` with the reason on stderr. A missing or ill-shaped
  before-record gives `differ`, and an unknown mode is refused. Every case asserts that the
  key, the pseudonym and the number reach neither stdout nor stderr.
- `tests/infra/test_staging_tokenization_key.py` (28). It runs the real script against stand-ins
  for `bao_as` and `compose`. The compose stand-in runs the **real** probe module over the
  stand-in's document. Covered: the full move; the policy written before the API's token reads;
  a re-run changing nothing; the stopped-after-write completion; the conflict (near miss: one
  character apart); the denied grant; a probe that says `differ` from a stale record; malformed
  env copies and documents; a deploy never making a key; `--init` making two different random
  keys in OpenBao only; init on an old host migrating; later deploys catching a lost grant or
  a drifted key; `--probe` giving `equal`, `differ` and no record. Every case asserts that the
  key never reaches stdout, stderr, the bao argv or the compose argv. Static checks: the order
  in deploy.sh and init.sh, no service or template carrying the variable, the policy grant, the
  dev setup, and the runbook section.
- Updated: `tests/infra/test_staging_compose.py`. The template, compose and init no longer carry
  the key, and load_env admits a migrated host; the negative control moved to `REDIS_PASSWORD`.
  The policy test admits the new grant. Also updated: `tests/infra/test_staging_netgsm.py`
  (policy), `tests/api/test_previsit_output.py` (the typed 503 body),
  `tests/api/api_harness.py` (`tokenization_key_refusal`), and
