# Evidence: INT-559 · The app's voice lane never writes patient audio to a file

**Epic:** E08-mobile · **Phase:** P1 · **Sec-Row:** mobile · **GitHub:** #947 ·
**Depends on:** INT-194, INT-291, INT-446 · **Branch:** `int-559-voice-no-audio-file` from
`origin/main` `78330ff4`

## Problem

From the #946 (INT-536) legal review, 18 Oct 2026. CLAUDE.md invariant 3 — raw audio is never
written to disk, DB, object store or logs; memory buffers ≤ 60 s, mlocked, zeroed on every
trigger — allows no dev exception. The app's voice lane did have one: the DEV dialogue
(`voiceEligible` requires `__DEV__`, `intake.tsx`) and the VoiceNote pill recorded a temporary
file on the phone through expo-audio's recorder (`useAudioRecorder` → `prepareToRecordAsync` →
`recorder.uri`), uploaded it with `FileSystem.uploadAsync` and deleted it afterwards
(`lib/voice.ts`). Between the write and the delete the file was reachable: a backup, a crash
report, another process reading the cache. The synthetic voice text's "Diske … yazılmaz" would
have been false for a dev build pointed at a local API declaring the synthetic class.

## Acceptance (verbatim)

> capture into an in-memory buffer (≤ 60 s, zeroed on every trigger) and stream it; no file
> path is ever created (test that no file API is called; native module behind a lazy import
> for vitest); recorder prepare/abort paths leave nothing on disk; the tripwire/text check
> re-runs when INT-515 deploys voice-runtime. If a native platform constraint makes a file
> unavoidable, stop and record it as an owner/ADR decision rather than ship around invariant 3.

## 2. The options, and the one chosen

Expo SDK pinned in `apps/mobile/package.json`: `expo ~57.0.17`, `expo-audio ~57.0.4` (lockfile
`expo-audio@57.0.4`). expo-audio's *recorder* is file-based on both platforms
(`ios/AudioRecorder.swift` writes under `cachesDirectory`/`documentDirectory`;
`AudioRecorder.kt` the same through MediaRecorder) — there is no file-less option on it.

| option | what it is | verdict |
|---|---|---|
| **expo-audio 57 `AudioStream` / `useAudioStream`** (chosen) | Already in the pinned package: `ios/AudioStream.swift` installs an `AVAudioEngine` input tap (100 ms buffers, `AVAudioConverter` to the asked rate, `NativeArrayBuffer.copy` into the event payload); `AudioStream.kt` runs `AudioRecord` in a coroutine and emits each read as a `NativeArrayBuffer`. Int16 or float32, mono or stereo, any rate the hardware admits. Neither implementation opens a file or names a path — read in full. Licence: expo-audio's raw `LICENSE` blob is MIT (already a dependency; nothing new enters the build). | **Smallest option that meets invariant 3 on both platforms**: no new dependency, no native module, Expo-only (CLAUDE.md: no bare RN), lazy-importable for vitest. One trade-off on iOS, §4. |
| `@siteed/expo-audio-studio` / `expo-audio-stream` | Third-party native modules with their own PCM streaming | Not needed once the pinned expo-audio has `AudioStream`; a new native dependency would need licence verification from its raw LICENSE blob and a review of its own file paths (both ship file-writing recorders beside the stream). Not adopted; the npm registry was not reachable from this session, so no licence claim is made about them. |
| A local Expo module (`modules/`, Swift `AVAudioEngine` tap + Kotlin `AudioRecord`) | ~150 lines of native code that could leave the audio session category to `setAudioModeAsync` and so keep INT-291's voice barge-in on iOS | Not chosen: native code that this session could not compile or run (no iOS/Android build here; the one simulator records silence) would ship unverified, against "prefer boring, typed, testable code". Recorded as the way to restore iOS voice barge-in (§4). |
| LiveKit's local audio track for the dev lane | The INT-515 transport | Not chosen: it replaces the dev ASR bridge (batch `/transcribe` on the team GPU box) with the SFU and the voice-runtime, which is INT-515's scope, not a fix of the dev lane. |

No platform constraint makes a file unavoidable: both native implementations are in-memory
end to end, so the stop condition in the acceptance did not arise.

## 4. The one trade-off: barge-in by voice on iOS

`AudioStream.start()` (iOS) calls `AVAudioSession.setCategory(.record, mode: .measurement)`
unconditionally, and `.record` silences playback. expo-audio's `setAudioModeAsync({
allowsRecording: true })` sets `.playAndRecord`; switching the category back while the engine
runs changes the I/O unit's configuration and stops the engine (no buffers arrive). So on iOS
the clip and the stream cannot be open together. INT-291 opened the microphone when the agent
*started* speaking so the patient could cut in by voice; on iOS that microphone now opens when
the turn becomes the patient's, and the clip plays tap-interruptible — where the product was
before INT-291. Android's `AudioRecord` has no session category, so the barge-in microphone
keeps its place there. `lib/capture/policy.ts` carries the rule and its reason.

Two ways to restore it, both outside this issue: an upstream option on expo-audio's
`AudioStream` for the session category, or the local Expo module in §2. Neither touches
invariant 3; this is a product decision for the owner, not a safety one.

## 5. Residuals, stated plainly

- **mlock.** A JS heap cannot be mlocked. iOS does not page app memory to disk (it compresses);
  Android may swap to zram. What the app controls is the size and the life of the resident
  window: ≤ 60 s, allocated once, zeroed on every trigger. Native-side, the stream's own 100 ms
  buffers are per-callback copies that are released as the event is delivered.
- **The bridge.** React Native's `fetch` carries a typed-array body to the native layer as a
  base64 string (`convertRequestBody.js`); that transient string is not zeroable from JS. It
  lives for the request and is garbage-collected.
- **The dev ASR daemon** on the team GPU box (not in this repository) receives the same
  `application/octet-stream` body it did — a decodable container — and what it does with it is
  its own posture; the `X-Intake-Audio` header lets it take the samples without the container.
- **`inactive` counts as background.** A Control Centre pull or an incoming-call banner zeroes
  the buffer mid-answer; the patient re-speaks. The same choice `lib/kiosk/nativeKiosk.ts` makes.
- **Open PRs.** #939 (INT-551, `drivers.ts`) and #866 (INT-497) both rework
  `useDialogueSession.ts`; this change keeps the capture in its own modules and touches the
  hook only where the recorder was, so the merge is at the recorder call sites.

## Acceptance, clause by clause

1. **"capture into an in-memory buffer (≤ 60 s, zeroed on every trigger) and stream it"** —
   `boundedBuffer.ts` + `session.ts`: `MAX_CAPTURE_SECONDS = 60` is the cap of the allocation
   and the segment size; `fill(0)` on `take`, `clear`, finish, discard, RED (`leave`), unmount,
   a typed answer, app background. Segments stream to the ASR client the moment they exist
   (`turn.ts`); the 70-second node-driven turn in `voiceCapture.spec.ts` shows two segments and
   a zeroed buffer.
2. **"no file path is ever created (test that no file API is called; native module behind a
   lazy import for vitest)"** — `voiceCapture.spec.ts` slices every file on the path for the
   file-system and storage modules, every file API, every recorder API and every audio
   extension; `expoStream.ts` holds the only `await import("expo-audio")` and no other capture
   file names the stream; the turn runs in node under a `localStorage`/`FileReader` trap and
   touches nothing.
3. **"recorder prepare/abort paths leave nothing on disk"** — there is no recorder. The
   prepare that is abandoned is tested as `closed()` flipping before, during and after
   `stream.start()`: the stream is stopped, nothing is subscribed, the buffer is zero, no
   segment is handed (`session.test.ts`, `turn.test.ts`, `voiceCapture.spec.ts`).
4. **"the tripwire/text check re-runs when INT-515 deploys voice-runtime"** — INT-515's step,
   named in the backlog row; this change makes the "Diske … yazılmaz" sentence true for the dev
   build too, which is what that re-run will find.
5. **"If a native platform constraint makes a file unavoidable, stop…"** — it did not arise
   (§2). The iOS constraint that did arise is on simultaneous playback, not on files (§4), and
   is recorded for the owner rather than built around.
