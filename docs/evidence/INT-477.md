# INT-477: solid chrome on capture-protected screens, never Liquid Glass

GitHub #817. Owner decision, in chat, 4 Oct 2026, verbatim: "solid". The designer had found Liquid Glass unreliable on the screens INT-131's capture protection guards. The cause is not known (`docs/evidence/INT-466.md`, `docs/evidence/INT-472.md`), and the designer recommended solid chrome there.

The decision is recorded as a dated amendment to ADR-039, not a rewrite: `## Amendment — solid chrome on capture-protected screens (INT-477, 4 Oct 2026)`. `files/00_STATE.md` §3 row D23 notes it, and `docs/index.md` registers it.

## Stacked on

This branch is `int-477-capture-solid-chrome`. It is stacked on #808 (INT-473), which contains #806, #801, #797 (ADR-039) and #792. Merge order: #792 → #797 → #801 → #806 → #808 → this PR.

## Which screens are capture-protected

Every route that calls `useClinicalScreenPrivacy()`. `captureProtection.test.ts` discovers them from the source, so the list cannot drift.

| Screen | Glass it reached before | What it draws now |
|---|---|---|
| `(tabs)/records` | the tab rail's glass pill | the solid pill (`surface` + hairline) |
| `(tabs)/wellbeing` | the tab rail's glass pill | the solid pill |
| `(tabs)/visits/[visitId]/intake` | the glass or stage nav bar, the `GlassBar` CTA, the stage's `GlassContainer` controls, and the orb's clear lens and glow | a solid nav bar, the `surface` bar, solid stage controls, a flat wash, and the orb with no lens and no glow |
| `(tabs)/visits/[visitId]/review` | the nav bar's system chrome material, and the `GlassBar` (blur, wash and glass) | the page ground behind the nav bar, and the `surface` bar |
| `(tabs)/visits/[visitId]/shares` | the nav bar's system chrome material, and the rail | the page ground, and the solid pill |
| `(tabs)/visits/[visitId]/issue-link` | the rail | the solid pill |
| kiosk PIN screen (`KioskGate`, not a route) | none: the kiosk's screens carry no glass | unchanged. It holds the window store like the others. |

In both themes, a protected screen draws what Reduce Transparency already draws. That is an existing, tested state, so no new colour pair or layout was made.

## What changed

- **The policy (`lib/a11y/glass.ts`).** `glassMode` takes a required `captureProtected` input. Capture protection outranks Liquid Glass availability and Reduce Transparency: it always answers `solid`.
- **Where protection is in force (`lib/auth/captureProtection.ts`, new and pure).** It holds two answers:
  - **The route.** `CAPTURE_PROTECTED_ROUTES` and `captureScope` mean a protected screen is solid from its first frame, before its own guard has run. A scope adds protection and never removes it. `focusedRoutePath` gives the tab rail the route it sits over.
  - **The window.** `captureProtection` is a store of how many screens hold protection. `protectScreen` holds the window before it asks the OS for protection, and lets go only after the release has settled. Glass therefore never returns to a window that is still protected.
- **The one hook (`components/glassMode.tsx`).** `useGlassMode()` passes `routeProtected || windowProtected` to the policy. `CaptureProtectedScope` provides the route's answer.
- **The navigators.** The tabs shell and the visits stack wrap each screen in `CaptureProtectedScope`. They use `screenLayout` and name each route the way the transition policy already names it. The `FloatingTabBar` scopes its pill by the focused route.
- **The guard (`lib/auth/screenPrivacy.ts`).** It runs through `protectScreen` with the same `expo-screen-capture` calls and key. INT-131's protection is unchanged.
- **Docs.** The ADR-039 amendment, the D23 row, `docs/index.md`, and one line under `docs/design/apple-native/spec.md` §1.1.

Every glass consumer already asked `useGlassMode()`, so no host or screen changed: the rail, `GlassBar`, `GlassNavBackground`, the nav helpers, the stage controls, the stage palette and the orb's lens.

## Behaviour to know

- **Protection covers the whole window and can outlive focus.** A tab screen stays mounted after its first visit, and INT-131's guard keeps protection for as long as it is mounted. So after Records or Wellbeing has been opened, every glass surface stays solid until that screen unmounts. This follows "whenever capture protection is active" in the acceptance: the window is still protected, which is the state where the glass was unreliable. Whether protection should follow focus instead is an INT-131 question, and this PR does not change it.
- **Found in passing, not changed: INT-131 can release OS protection early.** `expo-screen-capture` keeps a set of tags, and every protected screen passes the same key, `intake-clinical`. The first protected screen to unmount therefore releases OS protection for all of them. For example, closing the doctor-link issue screen leaves the share centre under it unprotected at the OS level. The window store counts each screen, so the chrome stays solid, which is the safe direction. The OS gap is a security defect in INT-131's control, and it is reported for its own issue.

### Near misses

- `glass.test.ts`: the same OS inputs without protection give `liquid`, or `blur` on an OS without Liquid Glass.
- `captureProtection.test.ts`: the visit screen (`[visitId]/index`) and the new-visit screen ride the same `withGlassNav` chrome without protection, and keep Liquid Glass and the system chrome material. A route matches exactly: a prefix, a bare name or a sibling does not match.
- `captureChrome.spec.ts`: a solid branch that kept a `BlurView` is caught. So are a hook that asked only the OS and a navigator without the scope.
