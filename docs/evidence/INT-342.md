# INT-342 — Motion: content reveal and a static skeleton

**Epic:** E08-mobile · **Phase:** P3 · **Sec-Row:** mobile · **GitHub:** #541 · **Labels:** area:mobile
**Spec:** `docs/design/motion/motion-verification.md` §4 MOTION-13, §1.2 P6 and P7 (both as
revised: one slot, no sequence; a static skeleton; the skeleton unmounts in the commit that mounts
the content, never on an animation callback), §2.2 (`reveal.skeletonDelayMs: 300`, "lands in
MOTION-13 with `revealPlan`") and §2.3 (`src/lib/motion/reveal.ts`, adapters in `native/`).
**Depends on:** INT-331 and INT-335 (merged); INT-334, the arbiter (#697), is still open. Nothing
here imports it: the reveal is the arbiter's `content` class, and wiring classes to the arbiter
belongs to INT-337. No ADR-033 open question (Q1–Q5, PR #571, Proposed) touches this issue.

## Acceptance (verbatim, docs/backlog/issues.yaml)
- "content already available never animates; a load under the skeleton delay shows no skeleton; the skeleton is static (no shimmer, no loop) and unmounts in the commit that mounts the content"
- "reduce motion keeps the delay and drops every fade; busy state is announced with a tr/en label"

## Problem
- Records (`phase === "loading"`) and the share centre (`loaded === false`) drew nothing in
  place of their data while it loaded. Records kept the previous list on screen during a reload
  (after a different visit is chosen), and the share centre printed the log's empty footer
  ("shares.log.empty") before the log had been read.
- Neither screen told a screen reader that it was waiting.
- Nothing held the MOTION-13 rules: no sequence or stagger, no shimmer or loop, a skeleton that
  a fast load never shows, and a skeleton that leaves in the commit that brings the content.

## Change
- `apps/mobile/src/lib/theme.ts`: `motion.reveal = { skeletonDelayMs: 300 }`, with its first
  consumer (§2.2). The comment says what it is: a wait, not a duration. It is not in
  `motion.duration`, so "no motion duration exceeds fadeMs" still covers every duration.
- New pure `apps/mobile/src/lib/motion/reveal.ts` (imports `../theme` and `./fade` only):
  - `revealPlan({ availableAtMount, reduce })` returns `{ skeleton, enter }` for one slot.
  - `skeleton` is `{ delayMs: 300, stepMs: 0, exitMs: 0, loop: false, shimmer: false }`. The
    last four are literal types, so a fading, exiting, looping or shimmering skeleton does not
    compile. It is the same object at every reduce-motion setting.
  - `enter` is `undefined` when the content was there at mount. Otherwise it is `enterFor({
    reduce })` from `fade.ts`: opacity, 120 ms, delay 0, `easing.out`, or `undefined` under
    reduce-motion.
- `apps/mobile/src/lib/motion/native/reanimated.ts`: `useSkeletonOpacity(plan)`. It starts at
  opacity 0 and, in an effect, sets `withDelay(plan.delayMs, withTiming(1, { duration:
  plan.stepMs }), ReduceMotion.Never)`. It returns `useAnimatedStyle(() => ({ opacity:
  shown.get() }))`. It uses `get`/`set` because the React Compiler is on (`app.json`).
  - **Why `ReduceMotion.Never`, on the delay only.** Reanimated 4.5.1 skips a `withDelay`'s wait
    under reduced motion (`src/animation/delay.ts`: `if (now - startTime >= delayMs ||
    animation.reduceMotion)`). With the root's `ReducedMotionConfig` set to `Always`, every
    skeleton would then show on its first frame, and a fast load would flash one for exactly
    the patients who asked for less change on screen. The plan keeps the delay because a wait is
    not movement. The step after it is `motion.duration.instant` (`withTiming` returns the target
    on its first frame when `runtime >= duration`), so nothing moves at any setting.
  - There is no JS timer, and no React render when the skeleton appears. BK13 ("only the resend
    cooldown owns a timer in a screen or component") is unchanged.
- New `apps/mobile/src/components/Skeleton.tsx`: one `Animated.View` with `accessible`,
  `accessibilityLabel={t("a11y.loading")}` and `accessibilityState={{ busy: true }}`, holding two
  static rows in ListGroup's geometry and the raised tone. It has no entrance, exit, transform,
  gradient or loop. Two rows are used whatever the data, because a row count would be a claim
  about the patient's data.
- New i18n key `a11y.loading` in both catalogues, beside `a11y.error`: tr "İçerik yükleniyor",
  en "Loading content". It is a noun phrase with no imperative, so there is no register finding.
  Nothing else in either catalogue changed.
- `apps/mobile/src/app/(tabs)/records.tsx` (`OtpRecords`) and
  `apps/mobile/src/app/(tabs)/visits/[visitId]/shares.tsx`:
  - `const ready = phase !== "loading"` / `loaded || unreachable`;
    `const [availableAtMount] = useState(ready)`;
    `const reveal = revealPlan({ availableAtMount, reduce: useReducedMotion() })`.
  - The data sit in ONE conditional: `{ready ? (<Animated.View
    entering={enteringFor(reveal.enter)}>…</Animated.View>) : (<Skeleton plan={reveal.skeleton}
    />)}`. React removes the skeleton in the commit that mounts the content.
  - Records: the slot holds the empty-state guidance or the document list. When ready, these are
    the same two branches as before: `docs.length === 0` is guidance, anything else is the list.
    The visit row, the reading section, the notice and the upload buttons stay outside the slot,
    unchanged.
  - Share centre: the slot holds the grants and the log together, because `loadShareCentre`
    reads them in one pass ("so the screen never shows a log that describes grants it is not
    showing"). `styles.slot` is `{ gap: spacing.md }`, the gap the two sections had as the
    scroll's children. An unreachable read is "the wait is over", so the announced
    "shares.unreachable" line still shows. A centre already held in the store when the screen
    mounts is `availableAtMount` and does not animate.
  - `git diff -w` on shares.tsx is 24 lines. The rest of that diff is re-indentation.

## Tests (TDD)
`apps/mobile/src/lib/motion/reveal.test.ts` (new). The six MOTION-13 DoD titles, verbatim. The
policy is called directly. A frame model, one frame per millisecond, runs it the way the device
does. As in `transients.test.ts`, the two branches swap in one commit, and only an exit keeps a
removed element on screen. Every test runs all six reduce-motion settings (the app switch × the
OS answer motion/reduced/unanswered, through the real `reducedMotion`) and nine load times
(1, 50, 150, 299, 300, 301, 450, 1000 and 3000 ms).
- **"content that was already available renders without animation".** `enter` is `undefined`,
  and every frame is exactly `[content @ opacity 1]`.
  - Near miss: arriving content's entrance, drawn on content that was already there, starts at
    opacity 0 and is seen moving.
- **"a skeleton never appears for a load under skeletonDelayMs".** The delay is 300. For every
  load from 1 to 300 ms, to the millisecond, the skeleton is never drawn above opacity 0.
  - Near miss: a 301 ms load shows it at t = 300 and swaps to the content at t = 301.
- **"reveal is one element in one slot".** The plan's keys are exactly `enter` and `skeleton`.
  `enter` is one spec, never a list, with delay 0. On every frame the slot holds one element, and
  never two moving.
  - Near miss: a skeleton that fades out puts two elements in the slot on the commit frame.
- **"the skeleton unmounts in the commit that mounts the content, never on an animation
  callback".** `exitMs` is 0. The last frame the skeleton is on is `readyAt − 1`, whether it was
  still hidden or already shown. The plan holds no function, so there is no callback to chain a
  removal to.
  - Near miss: removal at the end of a fade-out keeps it beside the content for 120 ms.
- **"reduce-motion keeps the delay and drops every fade".** Five settings reduce (the app switch
  at any OS answer, the OS alone, and an unanswered OS, which fails closed). Under each: the
  delay is 300, the step is 0, `enter` is undefined, and no frame moves. A 3 s load still shows
  the skeleton only from t = 300. The skeleton plan is identical with and without reduce-motion.
  - Near miss: with motion on, the detector finds exactly the content's 119 in-between frames.
- **"the skeleton has no loop".** `expectTypeOf` pins `loop: false`, `shimmer: false`,
  `stepMs: 0` and `exitMs: 0`. The skeleton plan equals exactly `{ delayMs, stepMs, exitMs,
  loop, shimmer }`. Over a 10 s wait its opacity changes exactly once and is then constant.
  - Near miss: a skeleton breathing on `motion.loop.pulsePeriodMs` changes on more than 5,000
    of 10,000 frames.

`apps/mobile/e2e/motion.spec.ts`: a new "MOTION-13" describe block. Every detector is first run
on samples, and forbidden names are assembled from parts.
- **"no shimmer or translate on skeleton components"** (the DoD title). The detector names a
  shimmer (the word, or a gradient), a translate, any transform, a loop (`loops()` from
  `motionSource.ts`: `Animated.loop`, `withRepeat`, a CSS iteration count), a sequence, and an
  entrance or exit. Eight moving samples are caught. Static blocks, and a comment that names the
  ban, are not. The scan covers every file named for a skeleton, and every function named for
  one (`Skeleton.tsx`, and `useSkeletonOpacity` read on its own).
- **"Records and the share centre render the skeleton and the content as the two branches of
  one conditional, from revealPlan".** `revealFindings` checks five things:
  - the imports come from the app's modules;
  - `revealPlan({ availableAtMount, reduce })` takes `reduce` from `useReducedMotion()`;
  - `availableAtMount` is frozen with `useState(ready)`;
  - `ready` is the screen's load-state expression;
  - exactly one `<Skeleton>` sits as the else-branch of the one conditional whose other branch is
    one `Animated.View entering={enteringFor(plan.enter)}`, with no exit and no animation
    callback.

  It passes on a good sample and catches six near misses: two conditionals; the skeleton removed
  when an animation ends; an exit on the skeleton; content with no entrance from the plan;
  availability re-read every render; reduce-motion not from the app's hook. Then both real
  screens pass, and no other file renders a `<Skeleton>` or calls `revealPlan`.
- **"the skeleton steps in after the delay on the UI thread, and keeps the delay under
  reduce-motion".**
  - `useSkeletonOpacity` starts at `useSharedValue(0)` and sets `withDelay(plan.delayMs,
    withTiming(1, {duration: plan.stepMs}), ReduceMotion.Never)`, with no callback and no timer.
    It drives opacity only, and no duration in the file is a literal.
  - The adapter is the only file besides the root layout that names `ReduceMotion.Never`.
  - The skeleton's single `Animated.View` spreads the hook's style.
- **"the skeleton is announced as busy, with a label from both catalogues".** The skeleton is
  one accessible element with `accessibilityState={{ busy: true }}`. Its `accessibilityLabel` is
  a `t()` key that exists, non-empty, in `tr` and in `en`, and differs between them.

How the busy state reaches a screen reader: the skeleton is on the accessibility tree from the
commit that starts the wait, before it is drawn, as one element with a name and the busy state,
and VoiceOver and TalkBack read both when focus reaches it. It does not post a live
announcement. A load under the delay would then be spoken for a skeleton nobody sees, and the
content that replaces it is what the patient came for.

## What only a device can show: not recorded
- **Felt timing.** No release-build device run is recorded. The owner's two reference devices
  are still unnamed (INT-330). Two things to watch on a device:
  - A load that lands inside a navigator's 120 ms fade (the share centre is pushed; Records is
    a JS tab) fades the content in within a parent that is still fading. That is one nested
    fade, not a second element. It ends at most 120 ms after the load.
  - A skeleton that appears 300 ms after mount and is replaced soon after is a single
    appearance followed by the content, with no fade in between.
- **Screen-reader phrasing.** The label and busy state are exposed on the tree. How VoiceOver
  and TalkBack voice `busy` has not been listened to on a device.

## Found, not fixed (outside this issue's scope)
- **The share centre can show another visit's grants for one frame.** The share store is a
  module singleton that the app never resets. When the patient opens visit B's centre after
  visit A's, the first commit renders A's held centre (`loaded: true`), and only
  `loadShareCentre(B)`'s effect commits the fresh state. This predates this issue. The reveal
  does not make it worse: the fresh state hides the stale centre behind the (hidden, then
  static) skeleton from the next commit. The fix belongs to the store (reset or key by visit on
  mount) and its own issue.
- **An unreachable read still prints the log's empty footer.** When the read fails, the grants
  group correctly prints no reassuring footer and announces "shares.unreachable", but the log
  group still prints "shares.log.empty" ("There is no access record for this note yet"). That
  line is not known to be true. This predates this issue; during a load the skeleton now hides
  it, which is the only part in scope here.
- `records.tsx` is now 514 lines (it was 493). Most of the growth is the list's re-indentation
  inside the slot. Splitting the screen is a refactor outside this issue.
