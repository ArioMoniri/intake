## What this issue is, and what it deliberately is not

`INT-056` ("Patient overlays set (8) + overlay_monotonicity property test") conflates two things:
the **eight authored clinical overlays** of files/04 §2.3 and the **mechanism** that composes any
overlay plus the property test that proves the composition monotone. The first is clinical content
that needs a licensed physician (HB-C1, HB-C5, HB-C6 through INT-043). The second is engineering
and was buildable today. CLAUDE.md: *"An open blocker is not permission to build around it: build
the mechanism, wire the gate, make it fail closed, leave the content empty."*

So INT-258 delivers only the second half. **No clinical threshold, age boundary, dose, red-flag
level or Turkish patient copy was authored.** Every fixture is `SENTETİK TEST VERİSİ` and says so
in its header. INT-056 stays open with the eight overlays and still blocks anything that needs a
real overlay to exist.

Nothing was invented to unblock anything. The one place where inventing was tempting — what an
overlay's `when` predicate may say — was answered by reusing the closed `when` grammar of files/03
§6 that the triage engine already parses, so activation and rule evaluation can never disagree
about what `Unknown` means.

## The defect this uncovered

files/04 §2.3 gives an overlay exactly one power over rules: *"may only add/tighten red flags"*.
**Tightening did not work.** `resolve_red_flags` resolved a `tighten_rule` op's parent over the
pack's own `extends` chain only, and an overlay has no `extends` chain — it is applied *to* a pack
rather than inheriting from one. Every tighten op in an overlay therefore refused with
`TIGHTEN_UNKNOWN_PARENT`.

The only way to make one compile was to give the overlay `extends: <the exact pack>`, which is what
the two INT-041 fixtures do (`tests/fixtures/protocols/compile/tree/overlay/{one,two}.yaml` both
carry `extends: base.derlenebilir`). That pins an overlay to one branch, and it is the opposite of
what the blueprint asks for: files/04 §2.2 attaches `overlay.oncology_patient` to
gastroenterology, while files/04 §5's entire argument is that *"a Dermatoloji patient on
chemotherapy day 8 at 38.1 °C had no neutropenic-fever rule, because it lived inside
`overlay.oncology_patient` attached to gastroenterology"*. A patient overlay follows the patient,
not the booking.

The fix is `resolve_red_flags(..., tighten_parents=...)`: parents may also come from the
chain-composed base. They are **read, never written** — a minted rule still lands only in the
overlay's own resolved set — so a sibling overlay can never become another overlay's tighten
parent, which is what keeps composition order-independent (see P3 below).

## The property test

`tests/protocols/test_overlay_monotonicity.py` generates base packs (one to three rules at any of
the five EK-4 levels, with whatever each level requires — a source block at SARI and above,
register plus a location-resolved action at KIRMIZI) and zero to three overlays of each sanctioned
shape (add, tighten, delivery-only), then asserts four properties. They are not the same property
four times:

| | property | why it is separate |
|---|---|---|
| **P1** | every base rule survives composition byte-identical; composed ⊇ base | the "never removes" half of invariant 7 |
| **P2** | a minted `rf.X.q` never lowers `rf.X`'s acuity, and `rf.X` stays live | the "never relaxes" half, plus the layer-2 sibling rule |
| **P3** | every permutation of one overlay set composes to the same rules **and the same refusals** | files/12 §3.4 claims order independence "by construction, not by convention"; this is what turns the claim into a fact |
| **P4** | a generated overlay that *does* relax is refused | a negative control that fails if the compiler silently accepts |

P4 draws one of seven relaxation vectors and asserts both that refusals are non-empty and that the
expected code is among them:

| vector | refusal |
|---|---|
| tighten downgrades acuity | `MONOTONICITY_VIOLATION` |
| overlay redeclares an inherited rule id with a changed body | `MONOTONICITY_VIOLATION` |
| tighten rewrites the parent predicate instead of disjoining it | `MONOTONICITY_VIOLATION` |
| tighten mints an id outside `rf.X.<qualifier>` | `MONOTONICITY_VIOLATION` |
| overlay suppresses a slot a surviving rule reads | `OVERLAY_REMOVES_RULE_SLOT` |
| overlay claims a `base.life_threat` rule id | `LIFE_THREAT_SET_EXTENDED` |
| a chain pack applied through the overlay door | `OVERLAY_WRONG_LAYER` |

A fifth test (P4b) asserts a refusal is not advisory: whatever a refused overlay tried to
contribute is absent from the composition, so a caller that mishandled the refusals still cannot
serve the relaxed rule.

## Order independence is structural, not incidental

If overlay *B* could tighten a rule overlay *A* had just minted, `(A, B)` would compile and
`(B, A)` would not, and `resolved_protocol_hash` would stop being a function of the session. So
`tighten_parents` carries the **chain-composed base only**; a rule an overlay mints lands in that
overlay's own resolved set and is invisible to its siblings. Combined with the existing rule that
two writers of one pointer with different values are a compile error rather than last-writer-wins,
composition is a set union of independently-validated contributions — commutative by construction.
P3 asserts it over every permutation of every generated set rather than trusting the argument.

## Two gates that are new, not just relocated

**Rule-id collision with `base.life_threat`.** The files/12 §3.2 deny-list stops any *pointer* that
reaches the sibling set, and the schema stops any pack from extending it. Neither stops an overlay
from minting a pack rule under a life-threat rule's id, because that reach never writes a pointer.
`compose_overlay_rules` takes the life-threat rule ids and refuses the collision;
`resolve_protocol` passes them from the loaded set, so the gate is wired, not merely available.

**Suppressing a slot a red flag reads.** The closed op set makes deleting a rule unrepresentable
(files/12 §3.1), but a rule whose slot no longer exists never fires — suppression of that slot
removes the flag without ever naming it. files/04 §2.3 only forbids removing `must_ask` questions,
which is narrower than the harm. The gate is deliberately narrow in the other direction too: an
overlay may still drop a question no surviving rule reads, which is how the low-literacy pacing
case in files/04 §2.3 is supposed to work, and a test pins that it stays allowed. Where a surviving
rule's `when` cannot be parsed, the suppression is refused rather than waved through — an
unreadable predicate is not proof of harmlessness.

This is a *partial*, overlay-shaped face of the CI gate files/04 §8.2 names as
`no_rule_references_an_undeclared_slot`, which is not implemented anywhere in the compiler and
cannot pass until INT-043 authors the six missing `base.intake` slots (HB-C6). Recorded here so
the remaining work is visible rather than assumed done.

## The INT-081 dependency re-point

`INT-081.depends_on` moves from `[INT-080, INT-056]` to `[INT-080, INT-258]`, with the reason
written as a YAML comment above the entry. INT-081's acceptance reads *"no LLM inside;
answered_pending + follow_up_tr semantics; **delta mode driven by PatientOverlay**; must_ask
coverage computed"*. "Driven by PatientOverlay" is activation plus composition — the machinery this
issue delivers — and every clause is testable against synthetic fixtures. Not one clause needs an
authored clinical overlay to exist. `overlay.frequent_attender` (files/04 §2.3, "delta mode by
default") is the *content* that will one day set delta mode; the FSM needs to honour whatever an
active overlay says, which is a mechanism.

INT-056 keeps the eight overlays, stays `todo`, and still blocks anything that needs real overlay
content. No other issue's dependencies were touched.
