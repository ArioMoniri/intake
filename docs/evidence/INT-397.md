# INT-397 — The last three status lines are announced (WCAG 2.2 SC 4.1.3)

**Epic:** E08-mobile · **Phase:** P1 · **Sec-Row:** mobile · **GitHub:** #659 ·
**Legal:** 5378, EN 301 549 · **Depends on:** INT-362 (merged), INT-387 (PR #658, open when this was written; this branch is built on it)
**Criterion:** WCAG 2.2 SC 4.1.3 Status Messages (AA)

## Acceptance (verbatim)
- "the notifications store distinguishes saving from failed, and only a real failure is announced (assertive), once per change"
- "`review.sentInfo` and `consent.queue.note` are announced (polite) only when the state changes in this session (just sent, just queued), never on a revisit"
- "INT-362's source-tree discovery test drops these three from its exception list (the list only shrinks); the 4.1.3 row moves to Supports with the tests cited, and MC-26 is retired"

## Problem
INT-387 kept SC 4.1.3 at Partially Supports because of three lines that
appear after an action and are announced on neither platform (MC-26):

| Key | Where | Shown while |
|---|---|---|
| `notifications.pending` | `me/notifications.tsx` | the store's `pending` flag is set |
| `review.sentInfo` | `visits/[visitId]/review.tsx`, `visits/[visitId]/index.tsx` | the note's status is sent |
| `consent.queue.note` | `me/consents/index.tsx`, `me/consents/[purpose].tsx` | the consent queue holds anything |

INT-362 left them out on purpose, for two reasons:
- The notification store set `pending: true` before every save and kept it
  when the server did not confirm. One flag meant both "in flight" and
  "failed", so announcing the line as an error would have said "Hata" on
  every toggle.
- The other two lines state what already stands, and a patient sees them on
  every visit. Announcing them on arrival would repeat old news.

They were never in `ANNOUNCED_ELSEWHERE`. The discovery did not reach them
at all: none uses failure copy, wait copy, the error colour or a live region.
They sat in INT-362's evidence under "Deliberately not routed (outside the
discovered set)", and in the 4.1.3 row's finding. So "drops these three from
its exception list" is done here by making the discovery reach them. They
then pass because they are announced, with no exception. `ANNOUNCED_ELSEWHERE`
keeps its seven entries, and a new test pins that number as a ceiling.

## Change

### When an outcome line is news (`lib/a11y/announce.ts`, pure and node-tested)
- `arrivedAt(standing)` is a screen's first render: whatever already stands
  is old news.
- `newsStep(memory, standing, inFront)` covers every render after that:
  - the outcome is **news** when the store moves into it while the screen is
    in front (just sent, just queued, just failed);
  - it stays news while the outcome stands, so the line is not re-made after
    it has been announced;
  - it ends with the outcome, so the next move into it is news again (once
    per change);
  - a move made while another screen covers this one is not news here, now
    or when the screen returns. The visit detail sits under the review screen
    when a note is sent, and the review screen is where it is heard;
  - an unchanged memory is returned as the same object, so the hook settles
    in one step.

### The announcer (`components/Announced.tsx`)
- **`useNews(standing)`** stores `newsStep` during render, React's pattern for
  information from earlier renders, so the line is news in the render it
  appears in. `inFront` is `useIsFocused()`, the navigator's own focus.
- **`AnnouncedText`** gains `news` (default `true`), so every line INT-362
  routed behaves exactly as before. While `news` is false:
  - no live region is set;
  - no iOS post is made (`useLineAnnouncement(news ? spoken : null, …)`);
  - the element keeps `spokenAs`, so an error found on arrival is still named
    as an error when the reader reaches it (SC 3.3.1).
- The element is keyed on `news`. A line whose words stay the same while it
  turns into news (a save that was in flight and then failed) is made again,
  and appears with its live region. That is how TalkBack hears it.

### The stores: typed state, with saving itself unchanged
- **`lib/notifications/store.ts`**: `pending: boolean` becomes
  `save: "idle" | "saving" | "failed"`. The switch still moves at once, and a
  refused change still stays shown. The only difference is that the second
  commit after a refusal says `failed`, not the same flag again.
- **`lib/consent/store.ts`**: new `ConsentOutbox`, which is `clear`,
  `sending` or `held`, with `consentOutbox()` and `useConsentOutbox()`:
  - a local grant or withdrawal that starts a flush moves it to `sending`;
  - a push that does not land moves it to `held`;
  - an emptied queue moves it to `clear`, and so do reset and seeding a new
    account.

  A retry that fails again stays `held`, so it is not a new move. A new
  change goes back through `sending`, so it is one. The flush order and the
  queue are unchanged.
- The note's status lives in the session and is persisted in the encrypted
  draft (`NoteState`). A UI flag added there would be stored at rest and
  restored after a restart. So the transition used is the status itself,
  moving from draft to sent while the review screen is in front.

### The five lines
| File | Line | Visible when (unchanged) | Tone | News |
|---|---|---|---|---|
| `me/notifications.tsx` | `notifications.pending` | `save !== "idle"` (was `pending`) | `failed` → error, `saving` → status | `useNews(save === "failed")` |
| `visits/[visitId]/review.tsx` | `review.sentInfo` | the note is sent | status | `useNews(note?.status === "sent")` |
| `visits/[visitId]/index.tsx` | `review.sentInfo` | the status is sent | status | `useNews(status === "sent")` (under the review screen when the note is sent, so never news in practice) |
| `me/consents/index.tsx` | `consent.queue.note` | the queue holds anything | status | `useNews(outbox === "held")` |
| `me/consents/[purpose].tsx` | `consent.queue.note` | the queue holds anything | status | `useNews(outbox === "held")` |

What is heard:
- a failed notification save: "Hata: Değişikliğiniz henüz kaydedilmedi. …",
  assertive, once for each failure;
- a sent note: the review screen's line, polite, once;
- a consent change that could not reach the server: the queue note, polite,
  once, on the screen where the change was made.

A revisit, an in-flight save and an in-flight consent change are shown, not
spoken.

**No copy changed, and nothing visible changed.** No catalogue key was added
or edited. Every line keeps its words, its role, its colour and the
condition it is shown under.

## Discovery (`e2e/a11y.spec.ts`)
- **Outcome copy.** The three keys are named in `OUTCOME_COPY`. Their words
  carry no mark the scan could read, unlike the failure suffixes and the wait
  ellipsis, so they are named by key and never by screen. Every file that
  renders one is still found by walking. The scan reports two new findings:
  - **outcome copy**: the line is outside the announcer;
  - **outcome announced on arrival**: the line is inside it, but its `news`
    is not a `const x = useNews(…)` of the same file. A missing `news`, a
    literal, some other value and an `AnnouncedRegion` all count.
- The five sites are checked against MC-26, as an oracle.
- No outcome line may be excused, and `ANNOUNCED_ELSEWHERE` may not grow
  past seven.
- Every `news=` in the tree must be a `useNews` transition, so no line can be
  muted with `news={false}`.
