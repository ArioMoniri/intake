## Server contract this client was written against

Read from `origin/int-90-livekit-dev` (INT-090 is `status: done` in the
backlog but its branch is **not merged into main**; `services/voice-runtime/`
does not exist on main yet):

- `packages/intake_platform/src/intake_platform/room_tokens.py` —
  `mint_room_token(session_id, identity, now)`; HS256; `TOKEN_TTL_S = 600`;
  room `intake-<session uuid>`; grants exactly
  `roomJoin + canSubscribe + canPublish` with
  `canPublishSources: ["microphone"]` and **`canPublishData` pinned to an
  explicit `false`**.
- `infra/livekit/livekit-dev.yaml` — `audio/opus` is the sole enabled codec;
  rooms ephemeral (`auto_create`, `empty_timeout`, `departure_timeout`); no
  redis/ingress/egress/webhook block, so recording is structurally impossible.
- `docs/runbooks/voice-livekit-dev.md` — embedded TURN UDP/3478 in dev;
  production is a self-hosted SFU + co-located coturn in İstanbul, and
  **TCP/TLS relay selection is degradation trigger T4, not a success**.

Two consequences the client is built around:

1. **`canPublishData: false` makes this client a data-channel RECEIVER only.**
   The adapter therefore exposes `onData` and deliberately has no
   `publishData` counterpart — pinned by a test.
2. **The RED script is pre-positioned on the device** and the data packet
   carries identifiers and axes only (`ruleId`, `register`, `location`,
   `scriptId`), never script text. That is what lets a RED render with the
   media plane fully torn down (invariant 21).

## What still requires a native dev-client build

**No native build was attempted** (host disk headroom is thin and the
simulator was out of scope). Shipped instead: the plugin configuration, the
capability probe and the tests. What a dev-client build is still needed to
exercise:

1. **The native module itself.** `@livekit/react-native-webrtc` is a native
   peer-connection module. Expo Go cannot load it, so nothing below the
   adapter seam has run on a device. `createNativeRoomAdapter` reaches LiveKit
   through a **dynamic import behind an injectable loader** (the `lib/health`
   / INT-208 pattern), so its logic is exercised with a fake and its *real*
   resolution is unverified.
2. **Config-plugin output.** `@livekit/react-native-expo-plugin` (meta-data
   only) and the new `./plugins/withVoiceAudio` (audio-only Android
   permissions; strips CAMERA; strips the iOS `audio`/`voip`
   `UIBackgroundModes`) are asserted as *declarations* by reading `app.json`
   and the plugin source. Their **prebuild output** — the merged
   AndroidManifest and Info.plist — has not been generated.
3. **Real transport numbers.** `parseTransportStats` is tested against
   captured `RTCStats` shapes. Whether `@livekit/react-native-webrtc` 144.1.2
   populates `currentRoundTripTime`, `relayProtocol` and `packetsLost` exactly
   as assumed is a device question.
4. **iOS audio-session and interruption behaviour.** `handleAppState` is
   driven synthetically. Real `AVAudioSession` interruptions (an incoming
   call, Siri) and the OS suspending a backgrounded app were not observed.
5. **The permission prompt.** The localized `NSMicrophoneUsageDescription`
   reaching the real iOS dialog through `expo.locales` is unverified on device.

## Cross-issue dependency (not worked around)

`mint_room_token` exists and is tested but is **not wired to an HTTP route** —
its only importer today is `tests/voice/test_room_tokens.py`. So
`POST /v1/visits/{visitId}/voice-token`, which `lib/livekit/token.ts` is
written against, **does not answer yet**. There is no stub token, no dev
fallback and no locally synthesised JWT anywhere in this change: a missing
endpoint surfaces as `token_unavailable` and the session refuses to start
(invariant 17). The route belongs to the voice-runtime lane.

## The one-line wiring seam for the dialogue UI

This issue does not edit `src/lib/dialogue/stream.ts`,
`components/DialogueIntake.tsx` or `src/lib/dialogue/tts.ts` — other agents own
them. `lib/livekit/events.ts` imports a **type** from `stream.ts` and nothing
else. The coordinator joins the halves with:

```ts
session.subscribe((e) => { const a = toDialogueStreamAction(e); if (a !== null) dispatch(a); });
```

exported as `DIALOGUE_WIRING` and pinned by a test. Only the terminal
transport failure maps today (→ the reducer's `failure`, which lands the
patient in the manual steps with every committed answer intact). Turn-taking
is deliberately **not** mapped: the agent messages that will drive
`utterance` / `transcript_ready` belong to INT-091 and INT-092, and inventing
a mapping for a wire protocol that does not exist yet is exactly the plausible
fiction invariant 17 forbids. RED is not mapped either, and that is
structural: a RED preempts the dialogue rather than advancing it, so it
renders above the reducer.

## Store copy correction

The existing `NSMicrophoneUsageDescription` in `src/locales/app-tr.json` said
the microphone was needed **"anlattıklarınızı kaydetmek için"** ("to record
what you describe"), and the en mirror said "to record". The product never
records: invariant 3 forbids audio reaching disk anywhere, and this client
streams frames that never enter JS. Both strings now state the real purpose
and say the recording is not kept — this is the acceptance's "mic permission
copy per store rules", and an App Review purpose string that promises a
recording the product does not make is the wrong kind of inaccurate. Asserted
by `voice.spec.ts` "never claims a recording is kept".
