# Evidence — INT-303 · One numeric carrier end to end

Date: 2026-09-03. Branch `int-303-decimal-slot`, off `origin/main` at `691f361`.

## What was actually wrong, stated without inflation

Three subsystems each declared their own type for a numeric slot value:

| where | file:line | declared numeric type |
|---|---|---|
| extraction result | `services/voice-runtime/src/intake_voice_runtime/extraction/result.py:46` | `type SlotValue = bool \| int \| Decimal \| str` |
| extraction reader | `services/voice-runtime/src/intake_voice_runtime/extraction/parse.py:78` | `json.loads(raw, parse_float=Decimal)` — a decimal literal becomes `Decimal` on purpose |
| protocol compiler | asserted at `tests/protocols/test_compiler_emitters.py:156` | `ziyaret_sure_dakika: Decimal \| None` |
| the carrier they meet in | `packages/clinical-schemas/src/clinical_schemas/common.py:24` | `type JsonScalar = str \| int \| float \| bool \| None` — **no Decimal** |
| the comparison | `packages/protocols/src/protocols/triage/context.py:89` | handled `bool \| int \| float \| str`, then `return None` |

`canonical_scalar`'s own docstring says *"None reads Unknown"*, so a `Decimal`
reaching it made every gate that compares that slot read Unknown, and a
red-flag rule gating on it would not fire. Nothing reports that (invariant 1).

### Live or latent — the honest answer, and it is not one word

The task brief suggested the whole seam was latent because `SlotAnswer` has no
constructor outside tests. Half of that is right and half is not.

**Latent — the red-flag half.** Confirmed by grep on the branch point:
`SlotAnswer(` and `TriageContext(` appear only in `tests/` and in their own
definition (`packages/protocols/src/protocols/triage/context.py`). No
production code builds a triage context, so no red-flag rule evaluates a real
session's slots today. Two further facts narrow it further, and both are
recorded because they cut against the alarming reading:

- **No merged rule compares a number at all.** `tests/safety/triage_goldens_cases.py`
  says so in its own docstring — *"no numeric-threshold comparison exists in
  merged content yet"* — and the goldens confirm it: every `when:` in
  `tests/protocols/goldens/valid/` and `files/protocols/base.life_threat.yaml`
  is `==` or `in {...}` over strings and booleans. The *"38.5 derece ateşim
  var"* scenario has no gate to miss today because no such gate is authored.
- **Through `SlotAnswer` the failure would not even have been the silent
  Unknown.** Measured on the branch point: pydantic resolves
  `tuple[JsonValue, ...]` against a `Decimal` by coercing it to `float`, so
  `SlotAnswer(state=ASKED_PRESENT, values=(Decimal("38.50"),)).values[0]` came
  back as `38.5`, a float. The silent-Unknown reading is reachable only
  through the **unvalidated** carrier maps — `IntakeEngine._values`
  (`clinical_agent/fsm.py:105`, read at `:292`), the `world` map in
  `protocols/triage/engine.py:171`, and `LearnedFact.value` at
  `protocols/compile/overlay.py:229`.

**Live — the extraction → engine half.** `services/voice-runtime/src/intake_voice_runtime/extraction/handler.py:137`
runs `context.engine.apply_extraction(**outcome.result.as_engine_call())` on
every landed extraction. That path is built and executes. What crossed it was
not a silently-Unknown `Decimal` but a **float**: `as_engine_call()` cast a
fractional `Decimal` to `float` precisely because the engine's carrier
declared none. That is the crossing files/13 §9.5 forbids outright — *"no
floats anywhere ... exact comparison, because floats are how two machines
disagree about the same session"* — and CLAUDE.md invariant 22 calls
unguarded. It also drops the declared scale: `38.50` and `38.5` are the same
float and are not the same `Decimal`.

So: **one seam, two defects — a latent silent-Unknown and a live float.** No
claim is made here that a patient's red flag has been missed. It has not,
because the gate that would miss it does not exist yet.

## The design question: should the uncomparable case raise?

`canonical_scalar` answered two different situations with the same `None`:
*"this slot has no answer"* (a reading the grammar defines) and *"this is a
type I cannot compare"* (a programming error). Conflating them is what made
the defect silent.

**Chosen: make the numeric carrier consistent first, then raise on what is
left.** In that order, because raising inside triage evaluation is a live
session crash and the brief is right to be wary of it. The sequence matters:

1. `JsonScalar` gains `Decimal`, ahead of `float`. This is the "make the bad
   value unrepresentable" half — the type the producers produce is now the
   type the comparison reads, so the question stops arising at the boundary
   rather than being answered late.
2. `canonical_scalar` carries a `Decimal` through unchanged, with its scale.
3. Null and collections still return `None`. They are *inside* the carrier and
   simply do not compare in this grammar; a rule must survive them.
4. Anything outside the carrier raises `UncomparableSlotValue`.

Step 4 is safe **because of** step 1: after admitting `Decimal`, no value any
producer in this repository builds is outside the carrier, so the raise is an
assertion about callers, not a new way for a live session to fail on patient
data. `float` is deliberately kept in the carrier and still converted through
its string form — an observer lane payload legitimately holds one (invariant
11) and that conversion is the guard invariant 22 asks for at a representation
boundary; turning it into a raise would have converted a currently-working
comparison into a live crash for no gain.

The exception names the offending **type** and never the value: an exception
that interpolated a slot value would put what the patient said into a log
(invariant 6). `tests/safety/test_numeric_carrier.py::test_the_refusal_names_the_type_and_never_the_value`
asserts that.

## The two near-miss negative controls

Both sit where a *naive* fix fails, which is why they are the load-bearing
half of this suite.

1. **`miss/float-yuvarlama` — a value that compares equal under float
   arithmetic and not under exact decimal comparison.**
   `Decimal("37.999999999999999999")` is exactly below a `>= 38` gate;
   `float(...)` of it is exactly `38.0`. Any fix that leaves a float anywhere
   in the path reports a **RED the rules never authorised**. This is not a
   hypothetical: in the red run above it *did* report RED, through the
   pydantic float coercion in `SlotAnswer`. Recorded as an observation on this
   branch on this date, not as a property of anything.

2. **`miss/sayisal-metin` — a numeral that must not be silently coerced.** The
   same magnitude written as `"38.5"` stays a string and the gate reads
   Unknown, never True (files/03 §4.9.6: a separator cannot be resolved
   without an expected magnitude, so a numeric string is refused rather than
   parsed). A third control keeps `True` from satisfying a threshold of `1`.

## What changed

- `packages/clinical-schemas/src/clinical_schemas/common.py` — `JsonScalar`
  gains `Decimal`, ahead of `float`, with the reason in the comment.
- `packages/protocols/src/protocols/triage/context.py` — `UncomparableSlotValue`;
  `canonical_scalar` carries a `Decimal` through unchanged and raises on a
  value outside the carrier.
- `packages/protocols/src/protocols/triage/__init__.py` — exports it.
- `packages/protocols/src/protocols/triage/engine.py` — `_render_value`: the
  evidence line renders a `Decimal` in plain positional notation, no exponent
  and no grouping (invariant 22). `json` has no `Decimal`, and rendering it
  through `float` would have put the binary image of a quantity into the
  clinician-facing evidence text.
- `services/voice-runtime/src/intake_voice_runtime/extraction/result.py` —
  `as_engine_call()` hands the `Decimal` over unchanged; the float cast is gone.
- `services/voice-runtime/src/intake_voice_runtime/clinical_agent/fsm.py` —
  `_same_value` compares numbers by magnitude rather than by Python type, so a
  re-stated quantity is not read as a contradiction; a boolean is still never
  the number one.
- `packages/clinical-schemas/src/clinical_schemas/mappers/from_r4.py` — one
  hand-spelled copy of `JsonScalar` replaced by the name, so it cannot go stale
  again.

## Still open

- **No numeric red-flag rule exists to exercise this on real clinical
  content.** The golden corpus covers the numeric threshold synthetically
  (`tests/safety/test_numeric_carrier.py`) because merged content authors no
  numeric comparison. When the first one lands it should get a golden pair at
  its own boundary; that is the existing gap `docs/evidence/INT-059.md`
  already records, not a new one.
- **The triage side still has no production constructor.** The latent half
  stays latent until `SlotAnswer`/`TriageContext` are built from a live
  session. This issue makes the seam correct in advance; it does not build it.
