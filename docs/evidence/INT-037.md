### Known, and deliberately not fixed in this issue

- **The erasure does not route through `DestructionEngine.run_dsar()`.** INT-036's
  `retention_policy.yaml` says the `clinical_record` row's `dsar_only` path is driven by
  this flow, and it is not: no DEST-2017 destruction record (`retention.dsar_destroyed` /
  `retention.dsar_run`) is written, and `retention_destruction_runs_total{kind="dsar"}`
  has no emitter. **My first-cycle evidence claimed INT-036's engine was this executor's
  caller — that was wrong**, and is corrected here. Wiring the two together is a real
  integration with its own policy-plan shape and belongs in its own issue.
- **`execute_due_shreds` has no production caller.** There is no `services/workers` tree,
  so the erasure is reachable from tests only and `admin_dsar_delete_total` is never
  registered in a running process. The scheduler is outside this issue; the consequence
  is recorded rather than papered over.
- Minor: no `FOR UPDATE SKIP LOCKED` on the due-request select (two concurrent executors
  would each append an audit entry for one destruction); `sanitise_cell` does not fold
  U+2028/U+2029.

## What was built

**Export — FHIR + PDF, one obligation, two representations.**
`POST /v1/me/dsar/export` records the request and starts the m.13 clock;
`GET /v1/me/dsar/export/{id}` renders the answer. The FHIR half is a R4 `Bundle`
(`type: collection`) built from INT-033's merged resource models and code systems: a
`Patient`, a `QuestionnaireResponse` per visit, a `Composition` per note under
INT-033's own `SECTION_SYSTEM`/`DOCUMENT_TYPE_CODE`, and a cover `Composition` whose
sections carry the documents, consents, shares, rectifications and request history.
`generated_at` is the request's own `received_at`, so the artefacts are a stable
receipt; `tests/legal/test_dsar_flows.py::test_the_renderers_are_deterministic_for_a_given_view`
pins byte-equality for a fixed view.

**Delete — schedule, cancel shares, then crypto-shred.**
`POST /v1/me/dsar/delete` revokes every live share immediately (files/06 §2.3: a
withdrawal cancels shares rather than orphaning them) and starts the files/06 §3
30-day grace. `DELETE /v1/me/dsar/delete/{id}` withdraws it inside the grace; the
shares stay revoked, because re-publishing to a clinic is the patient's call and not
the server's. `intake_api.dsar.shred.execute_due_shreds` executes after the grace:
crypto-shred first (every envelope-bearing field's wrapped DEK destroyed through
`intake_platform.envelope.shred_field`), then the object store, then the rows — the
same failure-direction bias INT-036's executor takes, so a half-finished run leaves
unreadable rows rather than readable orphans.

What the erasure deliberately does **not** delete: `consents`, `dsar_requests` and the
`patients` pseudonym row. files/06 §3 keeps consent and audit records for 10 years
(WORM), DEST-2017 keeps destruction records for ≥ 3 years, and the request row is that
destruction record — statutory retention outranks erasure, and a tracker that erased its
own evidence of having erased would fail the audit it exists for. All three hold ids,
timestamps and closed enumerations only, so nothing of the subject's content survives.

**Rectify — an addendum, never a rewrite.**
`POST /v1/me/dsar/rectify` writes a `dsar_rectifications` row (envelope-encrypted
correction, id-shaped `target_ref`) and a hash-chained audit entry; the note payload is
untouched, pinned by
`test_rectification_writes_an_addendum_and_never_rewrites_the_note`. files/02 §3 is
explicit that correction "produc[es] an addendum rather than a silent rewrite" — a
rewrite would falsify the record of what the patient actually said.

**SLA tracker.** `dsar_requests` carries `received_at → due_at` (KVKK m.13) and, for an
erasure, `grace_ends_at` (files/06 §3), plus the closed `kind`/`status` enumerations and
a `legal_strings_hash`. Ids, clocks and one public-file hash: no content, no free text
(invariant 6), pinned by `test_tracker_rows_carry_ids_and_clocks_only`.
`intake_api.dsar.sla.overdue_requests` is the query the compliance queue needs;
`GET /v1/me/dsar/requests` is the subject's own view. The **console** over those rows is
INT-189 and is deliberately not built here.

## What fails closed, and why

| gate | behaviour today | why |
|---|---|---|
| `docs/legal/strings.yaml` absent | `GET …/export/{id}` → `503 {"error": "legal_strings_missing"}`, while the request row is still created and its clock still runs | Invariant 18: legal text renders only from `docs/legal/` with hash binding. The obligation exists whether or not we can render the answer, and an unanswerable request that never entered the tracker is an obligation nobody can see. |
| a required fixed string present but empty | same 503, naming the key | An empty legal string is an unanswered ask, not a default. |
| `strings.yaml` malformed or unversionable | same 503 | An unversionable legal text cannot participate in the binding contract at all, so it is refused rather than treated as a quiet absence (the INT-038 `ConsentTextInvalidError` precedent). |
| the strings moved after an export was issued | `409 {"error": "legal_strings_changed"}` | The document we issued is not the document the file would now produce. `dsar_requests.legal_strings_hash` is the binding, exactly as `consents.text_hash` binds a grant. |
| a character outside the export encoding | `UnsupportedGlyphError` from the PDF writer | A legal document that quietly turns "ğ" into "g" misstates what the patient wrote. Refuse, never transliterate. |
| a `target_ref` that is not `<note\|visit\|document>:<uuid>` | `422` | Free text in that column would put PHI where the tracker and the audit both read. |
| a rectification target the subject does not own | `404` | Identity, not consent, is the control on this surface. |
| a clinic-admin principal on any DSAR route | `403` | DSAR is the data subject's own; a non-subject has no surface here at all. |
| a shredded field passed to `decrypt_field` | `CryptoShredError` | A completed erasure is not an integrity failure, and it must not be reported as one. |

## Values refused, with the ask and the named human

Nothing was invented. Two figures were **read off files/** rather than chosen:
`KVKK_RESPONSE_WINDOW = 30 days` (files/06 §1, row KVKK-11/13: "respond **≤ 30 days**")
and `SHRED_GRACE = 30 days` (files/06 §3: "patient-deletable (30-day grace, then
crypto-shred)"). They are separate constants although equal today, because they answer
different questions to different regulators and collapsing them would make a future
divergence a silent behaviour change.

Three things a human must supply. None is a build blocker — every mechanism is built
and every gate fails closed.

1. **The nine fixed strings of the DSAR export document.** *Who:* counsel, through
   INT-210 (`approval:human-legal`), which owns `docs/legal/`. *The one sentence they
   must answer:* "Author these nine Turkish strings into `docs/legal/strings.yaml` in
   the loader contract (`---` / `legal_strings_version: <v>` / `---` / `key: \"value\"`
   lines): `dsar_export.title`, `dsar_export.footer`, and
   `dsar_export.section.{visits,notes,documents,consents,shares,rectifications,requests}`."
   Until then the export refuses (503) and the tracker shows the request as unanswered.
   `dsar_export.footer` is a **separate key** from the files/06 §7 note footer on
   purpose: whether the KVKK m.13 response document carries the 1219 m.8 clinical
   disclaimer verbatim, a variant, or nothing at all is counsel's call, and encoding a
   guess would take that call from them. **No Turkish copy was drafted here and no
   string was hardcoded "temporarily".**
2. **Per-subject crypto-shred versus a per-subject key.** *Who:* the owner plus whoever
   owns key-management design (CLAUDE.md lists key-management design under "when to
   stop and ask"). *The one sentence they must answer:* "Should the KEK hierarchy gain a
   per-subject key so a DSAR erasure is unrecoverable even from a backup taken before
   the run, or is destroying the per-field wrapped DEKs the accepted boundary?" What is
   built today destroys the wrapped DEK of every envelope-bearing field belonging to the
   subject — a true crypto-shred of those fields, since the DEK is the key and the KEK
   only wraps it — and it does **not** reach a wrapped DEK already captured in a backup,
   exactly as a tenant-KEK shred does not reach a backed-up KEK. The tenant-level shred
   `envelope.py` already documents is unusable here: it would erase every other patient
   in the tenant.
3. **Retention of the DSAR tracker rows themselves.** *Who:* counsel, through INT-212
   (the DEST-2017 retention policy document). *The one sentence they must answer:* "Do
   DSAR request rows sit at the consent & audit tier (10 years, files/06 §3), or at the
   DEST-2017 destruction-record floor (≥ 3 years, files/06 §1 KVKK-7)?" The annotation
   shipped takes the **longer, stated** figure and cites both grounds, so no clock was
   invented; if counsel says three years, one constant moves.
4. **The `identity_vault` re-identification gap** (raised by the second-cycle review).
   *Who:* the owner plus counsel. *The one sentence they must answer:* "After a completed
   KVKK m.7 erasure, must the subject's `identity_vault` row go too — and if so, who may
   delete it, given the vault grants only SELECT and INSERT today?" The erasure
   deliberately keeps the `patients` row so the retained consent and destruction records
   still resolve, but `patients.pseudonym` is the **primary key of `identity_vault`**,
   which holds the raw identifier as OpenBao Transit ciphertext — so an erased subject is
   still re-identifiable by anyone holding `tokenization_role`. Closing it needs a schema
   and grant change to a table this issue does not own. My first-cycle evidence said the
   retained rows leave "nothing of the subject's content" behind; that is true of those
   rows and **not** true of what the pseudonym still unlocks, so it is stated plainly here.

## Deviations, and why each was taken

- **`session_state_to_questionnaire_response` is not used.** INT-033's mapper takes a
  `SessionState`, which requires a `protocol_hash` (`Sha256`). The dev-tier visit has no
  resolved protocol hash, so reaching the mapper would mean manufacturing one —
  HUMAN_BLOCKERS.md rule 1 forbids exactly that. The `QuestionnaireResponse` is built
  from the stored slot rows in the shape INT-033 emits (same identifier system, same
  canonical questionnaire URI, same status mapping). Likewise
  `previsit_note_to_document_bundle` takes a full files/04 §5 `PreVisitNote`; the record
  this API holds is a three-section free-text note, so the note `Composition` is built
  directly from INT-033's models and code systems rather than through that builder.
- **A new consent-guard marker, `data_subject_right()`.** KVKK m.11 is a statutory right
  whose basis is legal obligation, not açık rıza. Declaring `require_scopes("core")` on
  these routes would have been a defect, not a safeguard: the request a withdrawal
  provokes is exactly the request a consent-gated route refuses, so a patient who
  withdrew `core` would find their erasure right unreachable
  (`test_rights_survive_the_withdrawal_of_every_consent`). The marker follows the
  existing `pre_auth` / `consent_management` pattern exactly, is caged to
  `/v1/me/dsar` by a segment-boundary check, is listed by
  `data_subject_right_routes()` for a pin test, and leaves `unguarded_data_routes()`
  empty. `ensure_consent` was **not** touched or restructured.
- **A minimal PDF writer instead of a dependency.** No PDF library is in the workspace,
  and adding one means a raw-LICENSE audit plus a font. `intake_platform/pdf.py` is a
  deterministic text-only writer: WinAnsi plus a `/Differences` array parking the six
  Turkish letters (ğĞşŞıİ) in WinAnsi's six unused code points under their Adobe glyph
  names. **Scope is the data-subject export document.** INT-084's clinician-note
  renderer is a different artefact with its own layout and sign-off; it may later reuse
  this module's byte-level plumbing, but nothing here anticipates its design.
- **`admin.dsar_delete_total` flipped from `planned` to `live`** in
  `observability/metrics_catalog.yaml`, because it is now emitted (inv. 13 requires the
  catalogue and the code to agree in both directions). files/08 §4 group O names it and
  the `dsar` threat-model row said its signal lands with INT-037.
- **`tests/data/test_schema_shape.py::_migration_source` now reads the whole migration
  tree**, not just `*int030*.py`. Two tenant-scoped tables arrived in `0003`, and a scan
  that only read `0001` would have reported the strongest possible pass for tables it
  never looked at.
- **`docs/backlog/blockers.md` was not updated**, on the parent task's explicit scope
  instruction ("no docs/backlog"). The three asks above are written here instead and
  reported upward; CLAUDE.md's normal route is a blockers.md row per ask.
