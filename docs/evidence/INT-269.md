## Why this issue exists

INT-091 assigned the files/12 §5 attestor to the Talker. files/12 §5's own import-boundary rule
forbids it there —

> The signing key is fetched from OpenBao **by the rules-engine subsystem alone**, and an
> import-boundary test asserts no module under `extraction/`, `observers/` or `talker/`
> transitively imports the attestor.

— and the reason is not bureaucratic. HMAC is symmetric: whoever holds the key holds the capability.
**A signature verified by the party that could forge it is not a signature.** INT-093 filed this
rather than building it in the wrong place, and corrected
`services/voice-runtime/src/intake_voice_runtime/talker/preemption.py`'s docstring to point here.

## What was built

`packages/protocols/src/protocols/triage/attestation.py` — the attestor, inside the one package that
may produce a level at all (CLAUDE.md invariant 1):

| symbol | what it is |
|---|---|
| `KvSecrets` | structural port — the `get_kv(path)` slice of `intake_platform.secrets.SecretsProvider`, following the `intake_platform.ehrbase.KvSecrets` idiom. `packages/protocols` does not depend on the platform package, and a test must be able to supply a recorded bundle. |
| `keyring_from_secrets` / `AttestationKeyring` | keys read from OpenBao KV v2 at `secret/triage/attestation`, held by id so rotation is additive (the `intake_platform.tokenization` rotation idiom). Fails closed on a missing/blank `active_key_id`, an empty key set, a non-string entry, a non-base64 entry, a key under 32 bytes, or an `active_key_id` outside the set. `__repr__` renders ids only. |
| `TriageClaim` / `TriageAttestation` | the signed statement and its MAC. |
| `attest` | signs a `TriageEvaluation`. **No parameter can set a level** — level, EK-4 acuity, rule ids and RED axes are read off the evaluation `evaluate_triage` produced. |
| `verify` | the verifier the composition root hands the Talker as a port. Returns `None`, raises `AttestationRefused(reason, …)`. |
| `context_inputs_hash` | files/12 §5's `inputs_hash` over the evaluated `TriageContext`. |
| `NonceLedger` | per-session spent nonces, bounded (safely: the 5 s freshness window already refuses anything old enough to be evicted). |
| `RefusalReason` / `ForgedTriageTally` / `FORGED_TRIAGE_TOTAL` | the closed refusal enumeration, the in-process count, and the metric declaration. |

Supporting change, inside the same package: `_render_value` moved from `engine.py` to `context.py`
as the public `render_slot_value`, because `inputs_hash` and the engine's rule-evidence line must
share **one** canonicalisation. Two copies of a canonicalisation is how a hash and the text it
claims to cover drift apart — and it is what keeps INT-267's Decimal scale identical on both.

### What the MAC covers, and the two departures from files/12 §5's literal list

files/12 §5 names `(session_id, ek4, disposition, sorted rule_ids, inputs_hash, protocol_hash,
life_threat_version, engine_version, issued_at, nonce, key_id)`. Both departures are stated in the
module docstring rather than left to be discovered:

1. **`disposition` is carried as `TriageLevel`.** files/12 §2.1's `Disposition` enum
   (`CALL_112`/`GO_TO_ED_NOW`/…) is **not implemented anywhere in the repo** — `grep -rn
   "Disposition" packages/ services/` finds only an HTTP `Content-Disposition` header. Inventing a
   value for it here would be a placeholder in the most expensive possible place (invariant 17).
   When that enum lands it joins the claim as its own field and `_DOMAIN` moves to `v2`.
2. **`register` and `location` are covered in addition.** A RED is three axes, not one
   (invariant 21). An `ALERT` verdict whose register could be flipped to `SILENT` without breaking
   the MAC is a forgeable axis on the path where being wrong is the harm. Adding covered fields
   tightens and never relaxes; two of the refusal tests exercise exactly that swap.

Canonicalisation is **length-prefixed** with a domain constant, not delimiter-joined: with `a|b`
there is always a second pair of field values that concatenates to the same bytes, and a MAC over an
ambiguous encoding authenticates the bytes rather than the claim.
`TestCanonicalisation::test_field_boundaries_cannot_be_slid` slides one character from `session_id`
into `life_threat_version` and asserts the refusal.

### Verification checks far more than MAC validity (files/12 §5)

In order, each with its own closed reason: unknown key id → bad MAC → the claim does not cover the
verdict presented → session mismatch → `inputs_hash` mismatch → `protocol_hash` mismatch → outside
the 5 s window (in **both** directions; a verdict from the future is as wrong as a stale one) →
nonce already spent.

`hmac.compare_digest` is used for the MAC and for every digest/id comparison
(`TestCompareDigest` asserts a `compare_digest` call exists and that **no** `==`/`!=` comparison in
the module mentions `.mac` or `_mac(`). A timing-variable comparison on a security boundary is a
defect even where it is hard to exploit.

## The seven-way mutation table

One control accepted, seven mutations refused. Each mutation is applied **on its own** and the
verifier's other bindings are moved with it where they would otherwise catch it first — so nothing
but the MAC is on trial in any row. All seven are refused as `bad_mac`, which is the point: the
signature covers every one of these fields, and none of them needs a separate binding check to be
caught.

| # | mutation | how it is applied | verifier's other inputs | outcome |
|---|---|---|---|---|
| — | **control** — unaltered | — | live session | **accepted**, tally 0 |
| 1 | `level` RED → GREEN | rewritten in **both** the claim and the verdict presented (a coherent forgery: files/10 §9's named *"set me green"* threat), rule ids and RED axes cleared with it | live session | refused `bad_mac` |
| 2 | rule-id set | claim `rule_ids` and the verdict's `rules` both swapped to a different rule id | live session | refused `bad_mac` |
| 3 | `session_id` | claim rewritten to another session | verifier told the **other** session id, so the session binding would pass | refused `bad_mac` |
| 4 | `inputs_hash` | claim rewritten to the hash of a different context | verifier told the **other** `inputs_hash`, so the inputs binding would pass | refused `bad_mac` |
| 5 | `nonce` | claim given a fresh nonce (ledger untouched, so the replay check would pass) | live session | refused `bad_mac` |
| 6 | key | re-signed under a **second synthetic key under the same key id**; claim byte-identical, every binding still matches | live session | refused `bad_mac` |
| 7 | `issued_at` | moved +3 s, i.e. **inside** the 5 s window | `now` moved with it, so the freshness check would pass | refused `bad_mac` |

`test_all_seven_are_refused_and_the_control_still_passes` runs all seven against one signed verdict,
asserts `tally.total == 7`, then verifies the **unaltered** attestation again and asserts it is still
accepted and the tally has not moved. Seven refusals and one acceptance.

Replay is covered separately, because it is what `inputs_hash` + nonce buy over MAC validity alone —
a *genuine, unaltered* attestation is refused when it is presented to another session
(`session_mismatch`), on a later turn (`stale`, in both time directions), against a different pinned
pack (`protocol_mismatch`), against inputs that are not the context just evaluated
(`inputs_mismatch`), stapled to a different verdict or a swapped register/location
(`verdict_mismatch`), or a second time (`nonce_reuse`). The nonce moves per attestation while
`protocol_hash`, `life_threat_version` and `engine_version` do not — asserted directly.

## The ownership gate, and its negative controls

Two gates, because files/12 §5 states two things:

1. **Syntactic, over every file under `services/voice-runtime/`** (43 files; the test asserts a floor
   of 40 scanned so an empty or truncated scan cannot pass as a clean one): no import of a signing
   primitive (`hmac`, `cryptography`, `nacl`, `Crypto`, `jwt`, `jose`, `joserfc`, `authlib`,
   `ecdsa`, `itsdangerous`), no import of the attestor in either spelling, no **keyed-hash call**
   (`hashlib.blake2b(key=…)`, `blake2s`, `pbkdf2_hmac`, `scrypt` — a keyed BLAKE2 is a MAC hiding
   inside an allowed import), and no key material (a long string/bytes literal bound to a key-ish
   name). `hashlib` itself stays allowed: the runtime hashes content (`work_key`, clip hashes) and
   must keep doing so.
2. **Transitive**, which is what files/12 §5 actually asks for: a first-party import-closure walk
   from every voice-runtime file, following package `__init__` files, asserting
   `protocols.triage.attestation` is never reached — and asserting `protocols.triage.context` **is**,
   so the walk is not vacuous.

The transitive arm is load-bearing rather than decorative:
`services/voice-runtime/src/intake_voice_runtime/typed/render.py` imports
`protocols.triage.context`, which executes `protocols/triage/__init__.py`. **The attestor is
therefore deliberately *not* re-exported from that `__init__`** — a re-export would put the attestor
and `hmac` inside the runtime process, and a test asserts the `__init__` does not mention it.

Negative controls prove every arm can fail: synthetic offender sources for each of
`import hmac` / `from hmac import compare_digest` / `import protocols.triage.attestation` /
`from protocols.triage.attestation import attest` / `from protocols.triage import attestation` /
a keyed BLAKE2 call / two key-material shapes, plus a synthetic three-module package in `tmp_path`
proving the closure walk follows an edge two hops deep. A matching set asserts the gate does **not**
fire on the runtime's legitimate `hashlib.sha256` content hashing.

## Secrets: no live OpenBao was reached

**Stated plainly: no live OpenBao instance was contacted at any point in this work.** There is no
Docker daemon in this environment, so `make dev`'s dev-tier OpenBao cannot run; the eight
`@pytest.mark.integration` tests under `tests/security/` that do need one
(`test_openbao_wiring.py`, `test_envelope_encryption.py`, `test_tokenization_roundtrip.py`,
`test_document_store_integration.py`) fail with `SecretsBootError: OPENBAO_TOKEN missing` when the
integration marker is forced on, and are excluded by the repo's default `-m 'not integration'`.

That is precisely why the key source is an **injected interface** rather than a module-level read:

- production path — `AttestationKeyring` built by `keyring_from_secrets(SecretsProvider…)`,
  reading `secret/triage/attestation` from OpenBao at the composition root;
- test path — `FakeKvSecrets`, a recorded bundle asserted to satisfy the `KvSecrets` protocol,
  which also records the path it was asked for so the test can assert the attestor reads the KV path
  the rules engine owns and no other;
- **no environment-variable path at all** — `test_the_attestor_reads_no_environment_variable`
  asserts neither `os.environ` nor `getenv` appears in the module.

**No key material exists anywhere in this change** — not in a fixture, not in a docstring, not in
this evidence file. Every test key is generated inside the test with
`secrets.token_bytes(MIN_KEY_BYTES)`; the only literal "keys" are runs of a single repeated
character in the negative controls, chosen so they cannot be mistaken for one. A test asserts the
keyring never renders its material in `repr()` or `str()`, and every `KeyringBootError` message says
"the value is not echoed" and does not echo it.

No new key-management **decision** was taken here (that list is on CLAUDE.md's stop-and-ask):
files/12 §5 already rules that the key is an OpenBao secret fetched by the rules engine, and this
change implements that ruling with the repo's existing rotation idiom (a key set keyed by id, as
`intake_platform.tokenization` does). Provisioning the key generation and rotation schedule in the
production vault is ops work with no content this repo must invent.

## The metrics row you must add (invariant 13: the row comes first)

`observability/metrics_catalog.yaml` is outside this change's file ownership, and invariant 13 is
row-first: a series constructed before it is catalogued fails
`tests/observability/test_metrics_catalog.py`'s static gate. So this change **declares** the counter
and emits nothing — `FORGED_TRIAGE_TOTAL` is a `MetricDeclaration`, refusals increment an in-process
`ForgedTriageTally`, and two tests hold that line (`prometheus_client` does not appear in the module,
and no `Counter`/`Gauge`/`Histogram`/`Summary` is constructed anywhere in it). A third test states
the standing prerequisite: *a series may never be emitted before it is catalogued.*

Add this row to `observability/metrics_catalog.yaml` (files/08 §4 does not name this id — it comes
from files/12 §5 — so it is an extra catalogue row, which the catalogue's completeness test allows
in that direction; `status: planned` is honest because nothing emits it yet):

```yaml
  - name: safety_forged_triage_total
    id: safety.forged_triage_total
    type: counter
    labels: [reason]
    owner: safety
    unit: "count"
    target: "0 (any non-zero is an intrusion signal, not hygiene)"
    status: planned
    description: >-
      Triage attestations refused by the rules-engine verifier
      (protocols.triage.attestation.verify), by closed refusal reason:
      unknown_key, bad_mac, verdict_mismatch, session_mismatch,
      inputs_mismatch, protocol_mismatch, stale, nonce_reuse. files/12 §5.
      The label set is a closed enumeration and carries no session, slot or
      patient content (CLAUDE.md invariant 6).
```

Once that row is in, flipping the tally to a `prometheus_client.Counter` is a two-line change and
the catalogue entry moves to `status: live` in the same commit.

**Invariant 6 in the label set:** `reason` is the only label and its values are the eight
`RefusalReason` members. A test asserts the label set intersects an explicit PHI-risk name list
(`session`, `session_id`, `patient`, `transcript`, `evidence`, `slot`, `value`, `rule`, …) at
nothing, that every recorded reason is a `RefusalReason` whose value is a bare identifier, and that
no refusal message carries the session id, the other session id, the slot key or the `inputs_hash`.

## Invariant 1 is not widened

The attestation authenticates a determination; it never becomes a second route to one.

- `attest` takes a `TriageEvaluation` — which only `evaluate_triage` produces — and a test asserts
  its signature has **no** `level`, `ek4`, `rule_ids`, `result`, `register` or `location` parameter.
- `verify` returns `None`, deliberately: not a boolean (a caller who forgets to read a boolean has
  silently disabled the gate) and not the claim (handing back a level is the thing being avoided).
- Nothing in the module reads or writes a triage level except by copying one that already exists.

## The call site in `services/**` that still needs changing (reported, not made)

`services/voice-runtime/**` is outside this change's file ownership, so the third gate is **not**
wired yet; `preemption.py` and `red_path.py` are unchanged and their two existing gates still refuse
by default. The exact change, for whoever owns that tree:

1. `intake_voice_runtime/talker/preemption.py` — add to `Presentation` (or to `BackendResult`,
   whichever the queue populates) an optional field carrying the attestation as **opaque data**:

   ```python
   attestation: TriageAttestation | None = Field(default=None, description=...)
   ```

   imported **from `clinical_schemas`, not from the attestor** — i.e. `TriageClaim` /
   `TriageAttestation` must be re-homed into `packages/clinical-schemas` (types only, no `hmac`, no
   keyring, no `attest`/`verify`) if the runtime is to name the type at all. **Until that is done,
   type the field as a structural `Protocol` or pass it untyped** — importing
   `protocols.triage.attestation` from `services/voice-runtime/**` fails
   `TestOwnershipBoundary::test_voice_runtime_holds_no_signing_capability` and
   `TestTransitiveBoundary::test_no_voice_runtime_module_transitively_imports_the_attestor`, which is
   the whole point of this issue.

2. `intake_voice_runtime/talker/red_path.py` — `RedPreemption` gains an injected port and calls it
   inside `_authorised_determination`, after `authorise_preempt`, before anything is cut off:

   ```python
   @runtime_checkable
   class AttestationVerifier(Protocol):
       """Third gate (files/12 §5). The implementation is
       protocols.triage.attestation.verify, bound at the composition root with
       the keyring, the live session id, the inputs hash, the pinned protocol
       hash, the clock and the nonce ledger. The Talker holds the port, never
       the key: it verifies and can never sign."""

       def __call__(self, attestation: object, result: RulesTriageResult) -> None: ...
   ```

   with `verify_attestation: AttestationVerifier | None = None` on the dataclass; when it is `None`
   the RED path must **refuse** (`RedPreemptRefused`) rather than proceed unverified — fail closed,
   as both existing gates already do. An `AttestationRefused` propagating out of it must be caught
   and re-raised as `RedPreemptRefused` so the caller sees one refusal type on that path.

3. Layer B's queue (`work_queue.py`) must carry the attestation through from the rules engine, the
   same wiring INT-270 already opens for `TriageEvaluation.action`.
