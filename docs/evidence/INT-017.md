## What the tests pin

**Fail-closed boot (unit):** prod with no address/token → refuses to start;
prod with a dev-shaped token (`dev`/`root`/`test` markers) → refuses; prod
with an unreachable backend → refuses at boot (connectivity is checked before
the service exists, not after). Dev boots lazily against the loopback default
with the token from `.env`. `env.example` is pinned by test to carry nothing
beyond the compose bootstrap values and the OpenBao pointer.

**The real thing (integration):** dev OpenBao (`openbao/openbao:2.0.2`,
`bao status` healthcheck) + Postgres from the same compose file; the setup
script enables the database engine against Postgres and writes three roles
with `default_ttl=24h` and three least-privilege policies (each service reads
only its own KV subtree + its own creds path). The test writes/reads KV,
mints dynamic creds, asserts `lease_duration == 86400`, and **connects to
Postgres with the minted credentials** (psycopg `SELECT 1`) — the TTL claim
is exercised against the engine, not read off a config file.

## The integration lane itself (new, per 05 §3)

The docker tier now has its own required CI job: `check-integration` runs the
compose services + setup + `-m integration` tests; the default pytest run
deselects the marker (deselection, not skipping — the tests run on every PR
in their own job). This is the seed the later compose-tier issues
(INT-030/032 roundtrips, INT-024 chaos) extend.

## Fixes caught while proving it

- `docker exec` without `-i` swallowed the policy heredoc — OpenBao accepted
  an empty policy write with a 400 (caught by the failing policy test).
- Listing ACL policies needs the LIST verb (`?list=true`) — plain GET 404s
  (caught by the same test).
