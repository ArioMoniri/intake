## 0. A prior attempt exists, and this issue starts by judging it

`d564237` — *"feat(mobile): INT-136 typed intake — the instrument half,
fail-closed with an empty registry"* — sits on a stranded branch, never
packaged into a PR and never reviewed. It adds four files and touches seven,
+1449/−6. It is not merged and it does not apply: `git merge-tree --write-tree
origin/main d564237` exits 1, and `intake.tsx`, `wellbeing.tsx`, `questions.ts`
and `files/11_ISSUE_BACKLOG.md` all conflict. `questions.ts` alone has moved
+407/−15 since its parent.

So nothing was cherry-picked. What follows is the judgement, item by item.

### Adopted

- **The shape of the licence gate.** A TS mirror of
  `packages/protocols/src/protocols/licences.py`, a fail-closed lookup, and an
  empty item registry as the *delivered* state rather than a gap in one. That
  framing is right and this issue keeps it.
- **Licence before content, and the test that can tell the two orders apart.**
  With an empty registry both orders refuse, so only a *fully authored blocked*
  instrument distinguishes them. `instruments.test.ts` hands `resolveInstrument`
  a complete item set for C-SSRS, WHO-5 and HAQ-DI and asserts
  `reason === "licence_not_go"`. This is the best test in the stranded commit.
- **Byte identity over deep equality, with an NFD near-miss control.** A
  resolver that rebuilt each record — trimming, normalising, re-wrapping —
  passes `toEqual` and fails `toBe`. Invariant 10 is about the bytes, so the
  assertion has to be. The control is shown to discriminate before it is used.
- **Parsing `licences.py` from the spec** so the app's copy cannot drift from
  the compiler's.
- **Lifting `resumeQuestion` out of the screen** so "progress + resume" is held
  by unit tests rather than by a screenshot. The stranded version could return
  `undefined` while typed non-nullable on an empty pack; this one returns
  `IntakeQuestion | null` and the screen's fallback is justified by a pinned
  pack property rather than by hope.

### Refused, with the reason

1. **`affordance.ts` — the invariant-22 gate is unsound against today's `main`,
   and its headline test cannot fail.** `slotFactsFor` projects a question onto
   `slotType: question.slotType ?? (kind === "text" ? "string" : "code")`, and
   **no question in the repo declares `slotType`** — the commit's own comment
   says so. So `isNumericSlot` rejects everything and
   `numericStepsWithoutChoices(pack)` returns `[]` by construction, not by
   measurement. Worse since it was written: INT-282 added `kind: "measure"`, so
   `height` and `weight` — the only genuinely numeric steps in the app — project
   to `"code"` with no choices and the gate misses exactly the steps it names
   itself for. A gate that reads as a strong guarantee and delivers nothing is
   worse than no gate. Its `choicesTr` field is also filled with `MessageKey`s
   rather than Turkish, which happens not to matter only because nothing reads
   past `.length`.
2. **Mounting `<InstrumentItems instrumentId="WHO-5" />` on `wellbeing.tsx`.**
   WHO-5 is licence-BLOCKED (HB-L3), so the component renders `null` and the
   wiring is inert — while leaving a reference that reads as *"the wellbeing
   screen will show WHO-5"*. The screen's own header already states the correct
   position and it is left alone.
3. **Rendering a refusal as `null`.** The stranded component returns `null` when
   the instrument is unavailable. A step that renders nothing looks finished:
   the patient is carried past a section nobody told them was unavailable, and a
   reviewer sees a blank where a blocked licence should be visible. Here the
   refusal is copy, with a catalogue key.
4. **The prototype-key hole.** `registry[id] ?? "UNKNOWN"` on an object literal
   answers `constructor`, `toString` and `valueOf` from `Object.prototype`, so
   the nullish fallback never fires for those names. Not exploitable there —
   the licence check runs first and a function is not `"GO"` — but this
   implementation uses `Object.hasOwn` and `instruments.test.ts` pins all four
   names.
5. **`status: done` in `issues.yaml`.** The stranded commit flips it, and both
   its commit message and its PROGRESS entry claim the backlog now carries a
   comment recording that the registry is empty. **It does not** — the YAML diff
   is exactly the status flip plus the evidence path. The backlog would have
   read `INT-136 … done` with nothing recording that no instrument renders,
   which is the misreading the commit says it prevented. See §5.
6. **A 400-character `slice` window** as the way to assert the text CTA carries
   no `disabled`. It already nearly straddles the `measure` CTA branch that
   INT-282 added, and that branch *is* disabled — a heuristic one merge away
   from asserting the opposite of what it means.

## 1. What was built

**`apps/mobile/src/lib/intake/instruments.ts` — the licence gate and the
verbatim carrier.** No `t()` and no `MessageKey` anywhere in it, deliberately:
the app's catalogue is the app's own copy, an instrument's item text belongs to
the pack, and routing the words through a second store would make the app the
place the wording is decided. `resolveInstrument` returns the authored array
**by reference** — no map, no spread, no trim — which is what lets a byte
identity assertion mean anything. `resolveInstrumentItem` and
`instrumentItemOffer` sit on it; the offer form absorbs `InstrumentUnavailable`
and nothing else, because a malformed registry is a bug and a bare `catch` would
turn every such bug into a blank card that reads as a blocked licence.

`INSTRUMENT_ITEMS` is `{}`, for three independent reasons and none of them
fixable here: HB-C1 leaves every pack unsigned (INT-096's F4 measured the
consequence — all 93 packs are `maturity: L0`, `dist/` holds only `.gitkeep`,
`base.intake` refuses with `PACK_NOT_SERVABLE`); C-SSRS and WHO-5 are
licence-BLOCKED (HB-L2, HB-L3); and `packages/protocols/base/intake.yaml` says
the third itself — *"Instrument ITEM text is not authored here: the verbatim
Turkish items belong to the instrument engine (INT-116)"*.

**`apps/mobile/src/components/InstrumentStep.tsx` — the renderer.** It puts
`item.textTr` on screen as the step's heading and `item.choicesTr` on the
choice cards, applies no transform to either, and has no fallback to the
catalogue. The screen's own catalogue title is **not** rendered beside it: two
askings of one question is how a verbatim item stops being the one that was
validated. A resolved item whose `choicesTr` does not line up with the step's
declared value space is refused too — pairing the *n*th word with the *n*th id
would record an answer to a question that was not asked.

**`apps/mobile/src/lib/intake/lowLiteracy.ts` — `overlay.low_literacy` as pack
gates.** Four rules, every one of them a *delivery* rule, because files/04 §2.3
allows an overlay nothing else: overlays *"may only add/tighten red flags or
change delivery; they never remove questions clinicians marked `must_ask`"*. So
no function drops a step, re-scales one or re-words one; where the pack cannot
satisfy a rule the function **names the step**.

| rule | what it holds | today |
|---|---|---|
| `ordinalAnchorOffenders` | an `ordinal` step's anchor set is 3–4 (files/02 §3, Cowan) | clean |
| `typingOnlySteps` | no critical-path step is answerable only from a keyboard | clean |
| `unspeakableChipLabels` | no digit rides a chip label into a TTS model (invariant 22) | clean |
| `numeralAnchoredSteps` | severity is numeracy-free | **names `pain_score`** |

`ORDINAL_ANCHOR_MAX` is **derived from** `dialogue/speech.ts`'s
`MAX_SPOKEN_OPTION_HINTS` rather than restated. Both are Cowan's ~4 chunks; two
constants for one published finding is how they drift, and INT-096's F2 recorded
what a fourth private copy of a shared rule costs.

`chipSpeechTr` was written and then **deleted before commit**: `speech.ts`
already composes chip labels for the spoken lane, with the same bound, and a
second composition would have been that same defect. What replaced it,
`unspeakableChipLabels`, is a *pre-flight* of `assertSpeakableTr` over the whole
pack — the same rule, failing in CI on a pack change rather than on a patient's
device mid-turn.

**`questions.ts` — `resumeQuestion`, `intakeProgress`, `ordinal`.** The two flow
rules move out of the screen into the pack layer, which is a net **reduction**
in the screen. `ordinal?: true` is declared, never inferred: the only thing that
makes a list ordinal is that its author says so. `severity` — Hafif / Orta /
Şiddetli — declares it, and its wording is unchanged.

**The chip width bound.** `styles.chip` on both option-bearing chip grids
(`intake.tsx`, `DialogueIntake.tsx`) gains `maxWidth: "100%"`. A `flexWrap:
"wrap"` item gets no shrink in React Native, so a label wider than the row made
the **chip** wider than the row, with no horizontal scroll to reach it and
truncation banned (files/00 §2). This is INT-295's warning taken literally —
chips are the component that overflows first, and the app's own text control
*replaces* the OS value, so a device sitting at 1.0 says nothing about what the
control can ask for.

### Second red run — 2026-09-02T23:53:26Z

A module-not-found run proves only that the file is absent, so the modules were
written and the suite re-run to get a behavioural red. It produced one, and it
was a real defect in the test's own instrument:

```
$ pnpm vitest run … e2e/typed_intake.spec.ts
 × no committed pack authors an instrument item > would see one if a pack
   authored it (negative control)
   → expected [ 'FIXTURE-ORNEK', 'ornek' ] to deeply equal [ 'FIXTURE-ORNEK' ]

      Tests  1 failed | 115 passed (116)
```

`definedInstrumentIds` was matching `- id:` at **any** indentation, so an
instrument *item*'s id counted as an instrument definition. Left unfixed, the
scan over the real protocol tree would have kept returning `[]` for the right
reason today and the wrong reason forever after: the first pack to author an
instrument would have been reported as defining its items rather than its
instrument, and the registry cross-check would have compared the app against the
wrong set. The fix pins the sequence to the top of the `instruments:` block and
requires `dsl.py`'s `InstrumentId` shape (leading capital), which an item key
cannot have. **This is what the negative control was for** — the positive
assertion over the real tree passed throughout.

## 5. Acceptance, line by line

The acceptance is one line with three clauses; each is taken separately.

| clause | met | evidence |
|---|---|---|
| **instrument items rendered verbatim** | **mechanism yes, content NO** | There is exactly one route from a pack's `text_tr` to the screen and it copies nothing: `instruments.test.ts` proves byte identity against an injected instrument, with an NFD near-miss control; `typed_intake.spec.ts` proves the renderer applies no transform, never routes item text through `t()`, and is reached from the screen. **But no instrument item renders today, because none exists to render.** The registry is empty, and it is empty because HB-C1 leaves every pack unsigned and HB-L2/HB-L3 block two of the four instruments. The clause asks for items rendered; what ships is the guarantee that if one ever is, it is verbatim. |
| **low-literacy chips** | **partly** | Delivered: chips are the control and are reachable at every step the app's own ladder offers (the `maxWidth` bound, on both option grids); every chip label is selectable and announced by the platform screen reader; the spoken lane enumerates labels within Cowan's bound (`speech.ts`, pre-existing); the four files/02 §3 delivery rules are gates over every shipped pack in both modes, each with a fixture that makes it fail; and no catalogue string asks the patient whether they can read. **Not delivered:** files/02 §3's *"severity is numeracy-free, using 3–4 ordinal spoken anchors"* does not hold in Detaylı. `pain_score` is an eleven-point numeric scale, `baseLayer.ts` records that **no anchor wording is authored for either end of it**, and recoding an eleven-point scale into three or four Turkish anchors is a clinical judgement. `lowLiteracyReadiness` therefore reports the detailed mode as **not ready**, naming `numeral_anchored:pain_score`, rather than inventing a recoding. See §6. |
| **progress + resume** | **yes** | `resumeQuestion` and `intakeProgress` are pure functions in the pack layer with thirteen tests in `questions.test.ts`: resume opens at the first *unanswered* applicable question and not merely the next one in order, honours the review screen's pencil, ignores a request for a question this pack does not ask, lands on the last applicable question when everything is answered, resumes at a step a later answer has just revealed, and returns `null` rather than inventing one for an empty pack. Progress counts only *applicable* answers, so a closed gate cannot inflate it, and prints no denominator — `typed_intake.spec.ts` holds that the screen shows no fixed total and keeps the "may grow" line. |

Because clause one's content is absent and clause two is short of what
files/02 §3 asks, **`status` stays `todo`**, with a comment in `issues.yaml`
recording exactly that. This follows INT-140, which stayed open on the same
grounds three days ago.

## 6. Not done, and who owns it

- **The instrument items themselves.** Nothing is owed by a human that is not
  already owed: **HB-C1** (the physician of record's signature, which unblocks
  any pack at all) and **HB-L2 / HB-L3** (the C-SSRS and WHO-5 licence
  decisions). When a pack authors a GO instrument, `typed_intake.spec.ts`'s
  registry cross-check fails until `INSTRUMENT_ITEMS` carries it verbatim, which
  is the intended way this lands.
- **The ordinal wording for the pain score — a new ask, filed in
  `docs/backlog/blockers.md` for the physician of record.** One sentence:
  *under the low-literacy overlay, which three or four Turkish ordinal anchors
  replace the eleven-point pain score, or is the numeric scale simply not asked
  of a patient running that overlay?* No HB row was minted for it — HB ids move
  under concurrent merges (INT-096 F3 records a live collision), so the
  coordinator should allocate one.
- **Four more wrap-laid chip grids carry no width bound**, and they are out of
  this issue's scope: `visits/new.tsx` (visit-type grid), `me/appearance.tsx`
  (size chips), `visits/[visitId]/review.tsx` (scope chips) and
  `components/CarriedFacts.tsx`. They carry short fixed catalogue labels rather
  than pack option text, so the risk is smaller, but it is the same defect and
  it needs an issue.
- **`intake.tsx` is 900 lines** against CLAUDE.md's 500. This issue moved two
  rules out of it and added one branch, so it is roughly where it was; splitting
  `StepFlow` is a refactor with no acceptance line and it was not smuggled in
  here.
- **The `e2e/` name is a courtesy.** `issues.yaml` names
  `apps/mobile/e2e/typed_intake.spec.ts` as this issue's test and that path is
  honoured, but nothing in it is end-to-end: vitest runs on `node` with no
  renderer. Nothing in this issue was seen rendered and nothing is claimed to
  have been — the file says so in its own header. A renderer for the mobile tree
  is not this issue's to introduce.

## 7. Findings

**F1 — the stranded branch's invariant-22 gate is now unsound, and would have
merged green.** `numericStepsWithoutChoices` returns `[]` for every pack because
nothing declares `slotType`, and INT-282's `measure` kind — the app's only
genuinely numeric steps — projects to `"code"`. Recorded here because the module
is plausible, its test reads as a strong guarantee, and both were true when
written. Refused rather than repaired: a correct mobile mirror of
`typed/affordance.py` wants the union the app actually has, and that is its own
change.

**F2 — `INSTRUMENT_LICENCES` is now the third copy of the same table.**
`licences.py` is the first, `INSTRUMENT_LICENCES` here is the second, and the
`files/04` header table is the third and is prose. The spec parses the Python so
the two code copies cannot drift; nothing checks either against the header.

**F3 — `MAX_SPOKEN_OPTION_HINTS` cites Cowan **2001** and files/02 §3 cites
Cowan **2010**** for what this issue treats as one bound. Both are real papers
by the same author on the same question and the value used is 4 in both places,
so the constants are reconciled and the citation discrepancy is recorded rather
than silently normalised. A blueprint owner should pick one.

**F4 — HB-C15 is still not live, and INT-136 does not make it so.** INT-096's F5
corrected the claim that INT-096 *"puts compiled packs behind both surfaces"*
and named this issue instead. It is not true here either: no pack is servable to
either surface, mobile still drives fixture packs, and this issue's instrument
path resolves through the app registry rather than through a compiled pack. The
note-versus-mobile disagreement about what "missing" means stays not-yet-live.
