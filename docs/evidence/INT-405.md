# INT-405: The backlog sync pages past 500 issues and keeps issue state in step with rows

**Epic:** E00-governance · **Phase:** P1 · **Sec-Row:** — · **GitHub:** #675 · **Depends on:** INT-396 (PR #661)

## Problem
INT-396 (docs/evidence/INT-396.md, "For the coordinator" item 4, and the list of `done` rows
whose owned issue is open) found two defects in `scripts/backlog/sync_issues.py`:

- `fetch_existing` ran `gh issue list --limit 500`, newest first. Past 500 issues the oldest
  ones drop out of the listing, and those are the ones the sync owns
  (`owned_issue_numbers()`: the oldest issue carrying an id). The sync would then edit a
  newer copy, or file a fresh issue for an id that already has one.
- `build_plan` computed a `state` for every row, but `apply_plan` never applied it, so 66
  `done` rows still had their sync-owned issue open.

## Change
- **Paging.** `fetch_existing(listing)` walks GitHub's REST issue list
  (`gh api repos/ArioMoniri/intake/issues?state=all&sort=created&direction=asc&per_page=100&page=N`)
  until a page comes back short. It is oldest first so that an issue filed during the listing
  lands on the last page instead of shifting the earlier ones. Pull requests share that
  listing, and #2 carries the same `INT-001:` title as issue #1, so they are dropped. The
  result is sorted newest first, which is the order `owned_issue_numbers()` reads.
- **Nothing is synced from a partial listing.** GitHub's own issue count (GraphQL
  `repository.issues.totalCount`) is read before and after the listing. `ListingIncomplete`
  is raised, and the CLI exits 1 having changed nothing, when the listed issues differ from
  that count, when the count moved during the listing, or when a full page lists only items
  already seen (a listing stuck on one page would otherwise never end).
- **State follows the row** (`state_change()`, applied by `apply_plan`):
  - a `done` row closes its owned issue, `gh issue close N --reason completed`. That
    includes an issue the same run has just created for the row. The number is read from the
    URL `gh issue create` prints, and a failed create closes nothing;
  - a row that is not done (`todo`, `doing`, `blocked`, `awaiting-human`) reopens a closed
    owned issue, `gh issue reopen N`: the row moved back from `done`;
  - a `withdrawn` row is left as it is in both directions, because the acceptance names
    only `done`. So is an issue whose listing carries no state, as in an old
    `--existing-json` file.
  - Only `owned_issue_numbers()`'s number is ever edited, closed or reopened. Duplicates
    carrying the same id are never passed to `gh`.
- **Dry run.** `--dry-run` prints the plan and changes nothing. It lists every close and
  reopen, then `state: N to close, M to reopen, K to close once created`. Without
  `--existing-json` it reads the listing from GitHub, read-only. With `--existing-json` it
  stays hermetic. `--existing-json` without `--dry-run` is refused, so a live run never
  applies a saved listing. `--issues-file` lets the CLI test plan on its own rows.
- `apply_plan`, `ensure_labels` and `ensure_milestones` take the `gh` runner (and
  `apply_plan` the pause) as parameters. That is how the tests drive them with a fake.
  `mypy --strict` is now clean on `sync_issues.py`: INT-396 recorded the one error at the old
  `fetch_existing`.
- Backlog: the INT-405 row (E00-governance, P1, `area:platform`, `done`, no `sec_row`).
  The three pinned counts go to 309, each with its reason:
  `tests/backlog/test_schema.py`, `tests/backlog/test_sync_dryrun.py` and
  `tests/smoke/test_make_check.py`. `files/11_ISSUE_BACKLOG.md` is regenerated.
- Base: this branch is cut from `origin/int-396-backlog-reconcile` (PR #661, not yet merged)
  and merges `origin/main` at `f0564e93`. Main has 307 rows, INT-396 adds one and INT-405
  one more, so the count is 309.

The live run is the operator's: `make backlog-sync`, which runs
`uv run python scripts/backlog/sync_issues.py`. It was not run for this change, and no issue
state was changed by it.
