# INT-285 — the OTP abuse suite kept time by the wall clock

`tests/security/test_otp_abuse.py::test_per_phone_limit_three_per_hour` failed
in roughly one run in twenty on `main`, on no branch in particular, and reddened
an INT-016 gate run that had nothing to do with authentication. A gate that goes
red without a defect behind it is worse than no gate, because the next red is
read as noise (docs/TDD.md rule 7: fixed or deleted-with-ADR within 48 h — this
is the fix).

## The defect, exactly

Two facts that are individually correct and jointly a coin flip:

1. `services/api/src/intake_api/auth_store.py` counts requests in **fixed**
   windows. `_window_key` puts `int(self._now() // OTP_WINDOW_S)` in the Redis
   key, so every budget resets together on the hour. It is not a sliding window.
2. `Clock.__init__` seeded itself with `float(int(time.time()))` — the real
   wall clock, at whatever phase of the hour the suite happened to start.

`test_per_phone_limit_three_per_hour` spends the phone budget one resend
cooldown at a time and then asserts the next request is refused:

```
t + 0      request  -> 202   (phone counter 1)
t + 61     request  -> 202   (phone counter 2)
t + 122    request  -> 202   (phone counter 3)
t + 183    request  -> 429   ... if and only if t + 183 is still in t's window
```

So the test asserts a property of the counter and gets an answer about the
clock. With `p = t mod 3600`, the fourth request lands in the next window
whenever `p + 183 >= 3600`, i.e. `p >= 3417`: **183 s of every 3600, 5.08 % of
runs**, matching the observed rate.

### Reproduction

A pytest plugin that pins `time.time()` to a chosen phase of the hour and
changes nothing else (the plugin is a reproduction tool and is not committed —
after the fix there is nothing for it to influence, which is the point):

```python
_real = time.time
_phase = float(os.environ["OTP_TEST_PHASE"])
time.time = lambda: (int(_real()) // 3600) * 3600 + _phase
```

| phase (s into the hour) | module result, before the fix |
|---|---|
| 0, 1, 60, 1800, 3300 | 23 passed |
| 3417, 3418, 3500, 3599 | 1 failed, 22 passed |

The boundary is `>= 3417` exactly as the arithmetic predicts, and the failing
test is always the same one.

## The fix

One line of behaviour, in the test harness, not in the limiter:

```python
-        self.now = float(int(time.time()))
+        self.now = float(int(time.time()) // OTP_WINDOW_S * OTP_WINDOW_S) + offset_s
```

`WINDOW_START_OFFSET_S = 60.0` — past the boundary, so the suite is not testing
the boundary instant by accident, and 3540 s clear of the next one.
`LONGEST_WINDOW_SEQUENCE_S = PHONE_LIMIT_PER_HOUR * (RESEND_COOLDOWN_S + 1)` is
derived from the limits rather than written as `183`, so it follows if either
constant moves. Absolute time still tracks the real epoch: the DPoP `iat` skew
check reads this same clock (`dpop.py` takes `now` from `otp.py`'s `_now()`), and
a synthetic epoch would hide a real-clock leak instead of proving there is none.

`_WINDOW_S` in `auth_store.py` became the exported `OTP_WINDOW_S` so the harness
binds to the limiter's own window instead of repeating `3600`; the same rename
turned the bare `otp.clock.advance(3600)` in the per-phone test into
`advance(OTP_WINDOW_S)`, which says what it means.

## The finding this turned up, filed rather than fixed

A fixed window does not enforce "3 requests/hour/phone" (files/10 §2); it
enforces "3 per fixed hour", and a caller who spends the budget just before a
boundary is handed a fresh one just after it. The bound actually enforced is
**2 x limit inside a rolling hour**, floored by the resend cooldown at one
request per 60 s — six codes to one phone in about six minutes.

`test_a_fixed_window_hands_the_budget_back_at_the_boundary` pins that number: it
starts the clock so the third request lands one second before a boundary, walks
six admitted requests and the seventh refusal, and asserts the whole span is
shorter than `OTP_WINDOW_S` and longer than the cooldowns it contains. It is the
near-miss control for the three determinism tests — without it they could be
satisfied by a suite that had quietly stopped exercising the boundary at all —
and it makes the new comment in `auth_store.py` falsifiable rather than
decorative.

**The limiter is not changed here.** Changing how an abuse budget is counted is
a semantics change on the authentication path, and CLAUDE.md forbids making one
in passing inside another issue's PR. Filed as **INT-263** (issue #364) with the
bound, the near-miss control to invert, and the constraint that the replacement
stay clock-injectable and O(1) per request.

## Refusals

- **The limiter's counting scheme.** Left exactly as it was; INT-263 owns it.
  A sliding window in this PR would have been a security change smuggled in
  under a flake fix, and its own near-miss controls would have been missing.
- **A synthetic epoch.** Seeding the clock at a constant like `1_700_000_000`
  would be more deterministic still, and would also mean a code path that
  quietly read `time.time()` instead of the injected clock could no longer be
  told apart from one that did. The seed stays anchored to the real epoch.
- **A repo-wide grep gate against wall-clock seeds.** The sweep found exactly
  one occurrence; a lint rule over test source to protect a single file is more
  machinery than the problem, and it would fire on the legitimate
  `time.monotonic()` uses that a latency harness will eventually need.
- **Quarantining or deleting the test.** docs/TDD.md rule 7 allows deletion with
  an ADR; there was a real defect to fix, so neither applies.
