## How the audited-route list is derived rather than maintained

Three layers, each of which fails independently.

1. **A route cannot be created without an audit action.** `ADMIN_ROUTES`
   (`intake_platform/admin/wiring.py`) is a tuple of descriptors carrying
   method, path, `audit_action`, `permitted_roles` and — for mutating routes —
   `dangerous_action_id`. `intake_api/admin/routes.py` declares no route with a
   decorator; it walks that tuple and registers each descriptor through one
   wrapper. The audit action is therefore structurally attached, not attached
   by an author remembering to.
2. **The list is read off the running app, never written down.**
   `reachable_admin_routes(app)` walks FastAPI's own route tree (descending
   through `_IncludedRouter.original_router`) and cross-checks the result
   against `app.openapi()["paths"]`. Both derivations must agree, and an empty
   result raises. `tests/admin/test_admin_audit.py` then asserts that the
   reachable set equals the descriptor set, that every mutating route resolves
   to a registered `DangerousAction`, and that every route has a drive case.
3. **Every route is driven and the chain is inspected.** For each route, the
   suite makes a real request and asserts exactly two entries appear on the
   chain: `<action>.intent` then `<action>.success|failure`, sharing one
   content-addressed `resource_ref`, in ascending `seq`. Refusals are included:
   a 403 role denial and a 404 both produce the pair, because a refused admin
   request is exactly the one an investigator wants.

What is still forced rather than derived is the *drive fixture* — the body and
role each route needs. That is unavoidable (a machine cannot invent a valid
break-glass justification), but it is forced: a new route appears in the
reachable set, matches no drive case, and the suite fails.

The fix is **not** an entry on an exemption list. `consent_guard.py` gains a
seventh caged marker, `administrative_action`, accepted only under

on every chain entry as `basis:KVKK-12`.

The marker is attached in `routes.py` at the **same choke point** that attaches
the audit action — one `add_api_route` call driven by `ADMIN_ROUTES` — so a
route cannot be added that is undeclared to either scan.

The one route that will reach patient content, §2.5 item 5's redacted
transcript view, does **not** get this marker when it lands: §2.5 item 6 puts
the audit row before the read and invariant 4 puts a consent check with it.

## One audit path, not two

The console appends to the INT-016 hash chain through `AdminAuditSink`, a
Protocol whose entire surface is `record`. `intake_api.audit.AuditWriter`
satisfies it structurally, so the console reaches the one chain without ever
holding one. INT-121 refused to build a second data-boundary fence because a
control implemented twice diverges; the argument is stronger here, because a
private admin log is the log an insider edits.

Write-ahead is the ordering (files/08 §8.1): `AdminActionRecord` is an async
context manager that appends the intent row on entry and the outcome row on
exit, so "audited" is a property of the control flow.

The chain's field set is closed and id-shaped, so the §8.1 detail block cannot
ride in it. What rides is a SHA-256 over the id-shaped part of that block, in
`resource_ref` (`admin_action:<correlation>:<digest>`, 110 chars, inside the
128-char id shape). `test_justification_free_text_never_reaches_the_chain`
asserts the staff free text and its words never appear in any entry field
(invariant 6).

## Can the console reach the audit chain's head? No.

`tests/admin/test_admin_audit.py::TestChainHeadUnreachable` asserts four things:

- an AST walk over every source file in `intake_platform/admin/**` and
  `intake_api/admin/**` finds **no mention** of `AuditChain`, `AuditStore`,
  `build_worm_bundle`, `export_worm`, `verify_entries`, `verify_worm_export`,
  `run_daily_verifier` or the attribute `head`;
- `AdminAuditSink`'s public surface is exactly `{"record"}`;
- no `/admin` response body contains a 64-hex string;
- the head advances with every console action and none of it is echoed back.

This is deliberate and it is the point of **HB-I12** (the blocker's id is
HB-I12, not HB-I8 — HB-I8 is the pgBackRest retention window). HB-I12 asks
where the chain's head is published *outside* the `platform_admin` blast
radius, precisely because a hash chain detects an attacker who edits a row and
stops, but not one who recomputes forward or truncates the tail. The console
sits inside that radius. It can append and it can do nothing else, so it
cannot check its own forgery against the value the anchor would expose.

## What four-eyes covers — and what it does not

`intake_platform/admin/four_eyes.py` is a server-side pending-action protocol.

**Covers**, each with a typed refusal and a test:

| property | refusal |
|---|---|
| a different account | `four_eyes_self_approval` (+ `admin.four_eyes_self_approval_attempt_total`, which **pages**) |
| a different WebAuthn credential | `four_eyes_shared_credential` |
| a different browser session | `four_eyes_shared_session` |
| an eligible approver role | `four_eyes_approver_role` |
| a different organisation **at tier 3 only** | `four_eyes_shared_organisation` |
| a fresh, single-use assertion | `four_eyes_assertion_reused` |
| an approval window that closes | `four_eyes_expired` (+ `admin.pending_action_expired_total`) |
| one decision per action | `four_eyes_already_decided` |

A **shared AAGUID is deliberately not a refusal**: an AAGUID identifies an
authenticator *model*, so two people holding the same brand of key would be
refused by a check on it. Only the credential id distinguishes the key.

**Does not cover: two accounts held by one person.** Nothing in an OIDC claim
set says two subs are two humans. Distinct sub, distinct credential, distinct
session — every check the ceremony can make passes.
`TestWhatFourEyesDoesNotCover::test_two_accounts_held_by_one_person_are_accepted`
asserts the acceptance, so the limit is a passing test rather than a silence.
Closing it needs identity proofing at enrolment or an approver pool the actor
cannot enrol into: an operating control, not another field.

**Does not cover, and should not:** break-glass is registered **tier 2**, not
tier 3. files/08 §2.5 asks for "a distinct human approver, different WebAuthn
authenticator, own session", which is exactly the tier-2 ceremony; §8.2's
tier-3 list does not contain break-glass, and demanding two organisations
would make an all-INTAKE ceremony impossible. So a break-glass approver **may
be a colleague in the same organisation**. The tier-3 different-organisation
rule is implemented and tested, and applies to the tier-3 actions the console
modules will register.

**What the approver sees.** `ApprovalBrief` carries the requester's full
identity block (sub, role, org, AAGUID, credential id, session id), the tier,
the target session, the reason class, the **full justification free text**,
the controller-instruction reference, the evidence, both timestamps, and a
rendered `approver_rule` stating what the server will enforce. An approval
screen showing less than that is theatre.

## The IP allow-list ships empty

`IpAllowList.from_spec("")` yields no networks and `permits()` returns `False`
for everything — the console admits nobody. files/08 §2.3 says "IP allow-list
for the console" and names no addresses; no file in this repository names an
office range, a VPN egress or a bastion. A plausible address would look
configured while being wrong, which is worse than none (invariant 17,
HUMAN_BLOCKERS rule 1). `INTAKE_ADMIN_IP_ALLOWLIST` is documented in
`env.example` with no value.

Only the transport peer is checked. `X-Forwarded-For` is attacker-controlled
without a trusted-proxy hop count, none is configured, so the header is not
read — an allow-list that trusts a spoofable header is not one. A client
address that is not an IP at all is refused rather than coerced.

## The break-glass refusal that is not a gap

`Deployment.CONTROLLER` refuses with `no_lawful_basis`, and this is obedience
to files/08 §2.6 rather than an omission. In the consumer deployment INTAKE is
the controller; post-7499 the health regime aligns to GDPR Art. 9, so
legitimate interest is unavailable, and KVKK m.6/3's care ground runs to
persons under a healthcare obligation of secrecy — which an INTAKE support
engineer is not. files/06 §2 enumerates **no staff-access purpose at all**, so
invariant 4 has no consent scope to check. §2.6's own inference — an unbundled
`support_access` explicit-consent purpose obtained at the point of the support
request — is counsel's call, already recorded as **HB-L6**. Until it is
answered, the controller path refuses and the processor path requires a
`controller_instruction_ref`.

The tenant→deployment map ships **empty** for the same reason: which side of
the controller/processor line a tenant sits on decides the lawful basis, no
file records it per tenant, and a guessed entry would answer a legal question.
Every break-glass request refuses `tenant_deployment_unknown` until a tenant
registry supplies it.

## Keycloak

- **Roles are infrastructure.** All twelve files/08 §2.1 console roles are
  declared in `infra/keycloak/dev-realm.json` with their §2.1 limits as
  descriptions. No user was added and no client secret exists anywhere — the
  existing `TestKeycloakDevRealm` assertions (three synthetic users, dev-only
  passwords) still hold.
- **The registry is held against the spec.**
  `test_registry_is_exactly_the_spec_table` parses the §2.1 table out of
  files/08 itself, so a role added to the spec fails CI until the code
  follows, and vice versa.
- **Token verification is hand-written over `cryptography`**, following the
  `intake_api.dpop` precedent: one algorithm (`RS256`), no negotiation, so the
  alg-confusion family (`none`, HS256 against a public key, a downgraded hash)
  has no code path rather than a guard on one. 24 tests, mostly negatives.
- **The JWKS is a mirrored file, never fetched.** The most privileged surface
  in the system should not answer 503 because an identity provider is briefly
  unreachable, key rotation should be a deploy with a diff, and CI must never
  dial a live service (`INTAKE_ADMIN_OIDC_JWKS_PATH`).
- **ABAC:** tenant scope comes from the claim. `?tenant=` is refused with
  `tenant_scope_refused` for every role except `platform_owner`, asserted over
  **every** route × **every** role (files/08 §8 rule a). A refusal, not a
  silent ignore — an ignored parameter reads as honoured.

## Invariant 18 — no new persisted field

Nothing is written to the database. Pending actions live in
`FourEyesService`'s process-local map, which is the failure direction the
design already assumes: files/08 §2.4 has pending approvals expire, and a
restart that drops them refuses rather than grants. No migration, no column,
so no inventory annotation is due. The `admin_audit.v1` detail record's
persistent home arrives with the console modules that need to read it back;
what exists today is the digest binding in the chain.

### Two failures that are a local artefact, not a code change

`tests/infra/test_restore_drill.py::TestDrillPhiSafety` failed twice on my
machine — `test_a_restore_target_inside_the_workspace_is_refused` and
`test_a_relative_target_that_escapes_upward_is_still_checked`. Neither is
caused by anything on this branch: nothing here touches
`intake_platform.backup.drill`.

The cause is a **symlink I created in the worktree**. A fresh worktree fails
`test_deid_ner` until `.cache/deid-tr-ner-v1` exists, so I symlinked `.cache`
to a sibling checkout. `assert_restore_target_outside_workspace` calls
`Path.resolve()`, which follows that symlink out of the workspace, so
`REPO/.cache/restore` resolves to a path the guard correctly judges to be
outside. Removing the symlink and re-running the class passes 5/5; restoring it
reproduces the failure. It is untracked and gitignored, so CI is unaffected.

Worth recording as a finding rather than fixed here (no id minted): the guard
resolves the target but not the workspace's own symlinked children, so a
symlinked directory **inside** the repo is one `git status` can see while
`resolve()` reports it as outside. That is a small hole in an invariant-3
control, and it is the exact configuration this repo's own fresh-worktree
workflow produces.
