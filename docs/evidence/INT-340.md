# INT-340 — Haptics: one policy, sticky suppression, server-confirmed success

**Epic:** E08-mobile · **Phase:** P2 · **Labels:** area:mobile, risk:legal · **Sec-Row:** mobile · **GitHub:** #539
**Depends on:** INT-332 (ADR-033, PR #571, Proposed) and INT-333 (RED motion contract, PR #696, open). Neither is on `main`, so nothing here imports either.
**Spec:** `docs/design/motion/motion-verification.md` §2.1 #9–#11 and #19, §3 S-3, §1.2 P12/P13/P17, §4 MOTION-11; ADR-033 §6 (Proposed, read from `origin/int-332-motion-adr`); `motion-system-spec.md` §6.1–§6.3 (the event map, which the verification left standing).

## Acceptance (verbatim)
- "no haptic while the voice session is active or the microphone is hot (read at fire time), for any RED register, or for the rest of a session in which a SILENT RED or a third party occurred"
- "no haptic for consent, errors or intake chips; success fires only on a server-confirmed outcome; HapticCall has no error, warning or heavy member"
- "expo-haptics is imported only by the engine adapter via import(); its licence is verified from the raw LICENSE blob; the Android build blocks VIBRATE"

## ADR-033 is Proposed: what ships is its fail-closed default
- **Q2 (ClinicalAuthor, Dr Efe Onganer): "Should an ALERT RED ever fire a warning haptic when the microphone is cold?"** Meanwhile: never. No RED register fires a haptic. The event union has no member a RED could ask with, and `HapticCall` has no warning member to play. If Q2 is answered yes, a new event and a new call member are needed, and the "no RED register fires a haptic" test and the `expectTypeOf` pins say where.
- DEFERRED_CLINICIAN is invisible to the patient, so it is invisible to the gate as well (ADR-033 §5, S-6). This matches `redPresentationMode(...) === "none"` in PR #696's `red.ts`, which this branch does not import. The gate takes the register itself (`presentRed(register)`), and INT-135's RED layer calls it.

## Change
- **`src/lib/motion/haptics.ts`** (new, pure): the whole policy.
  - `hapticFor(event, ctx) → HapticCall | null`.
  - `ctx` is `{ platform, voiceSessionActive, micHot, redPresented, silentOrThirdPartyThisSession, surface, valueChanged?, serverConfirmed? }`.
  - The four live flags block unless each one is exactly `false`, so a missing or unknown answer fails closed. An unknown surface or event fails closed too.
  - `SURFACE_EVENTS` is the closed table:
    - `settings`: select, toggleOn, toggleOff;
    - `visits`: select;
    - `shareIssue`: success;
    - `shareRevoke` and `dsar`: arm, success;
    - `consent`, `legal`, `error`, `intakeChip`: none.
  - `select` needs `valueChanged === true`, and `success` needs `serverConfirmed === true`.
- **The calls.** These follow `motion-system-spec.md` §6.1 exactly, and §6.2 rule 2 ("no heavier impact than Light"):

  | Event | iOS | Android (`performAndroidHapticsAsync`) | AOSP effect (HapticFeedbackVibrationProvider) |
  |---|---|---|---|
  | select | `selectionAsync` | `segment-tick` | EFFECT_TICK |
  | toggleOn / toggleOff | `selectionAsync` | `toggle-on` / `toggle-off` | PRIMITIVE_TICK 0.5 / PRIMITIVE_LOW_TICK 0.2 |
  | arm | `impactAsync(Light)` | `context-click` | EFFECT_TICK |
  | success | `notificationAsync(Success)` | `confirm` | EFFECT_CLICK |

  - `HapticCall` therefore has no `Medium` member. That is stricter than the brief's "light & medium", because the spec's table has no medium.
  - Some Android constants are excluded:
    - `Long_Press` and `Drag_Start` map to **EFFECT_HEAVY_CLICK**;
    - `Reject` maps to EFFECT_DOUBLE_CLICK, the error analogue.

    Source: `frameworks/base/.../vibrator/HapticFeedbackVibrationProvider.java` on AOSP `main`, retrieved 2026-09-27.
- **`src/lib/motion/hapticGate.ts`** (new, pure, takes its dependencies as arguments): `createHapticGate({ loadEngine, afterCommit? })`.
  - Owners register live probes (`voiceSessionActive`, `micHot`). The gate reads them when the handler asks, and again after the adapter loads, just before the native call. A probe that throws counts as hot.
  - `presentRed(register)`:
    - ALERT, CALM and SILENT hold every haptic while they are shown;
    - SILENT also sets the sticky flag;
    - DEFERRED_CLINICIAN changes nothing;
    - an unknown register holds haptics and sets the flag.
  - `markSilentOrThirdParty()` sets the flag, and the gate has no method that clears it (pinned by `expectTypeOf<keyof HapticGate>`).
  - One haptic per commit: the first request a commit lets through holds the rest of that commit, which is released on the next microtask. One per action id: a repeated id is dropped whether or not it played, so a late or doubled confirmation is never felt.
  - The request carries no live state, so a value captured at render cannot be replayed.
  - A load or play failure resolves `null` and never rejects.
- **`src/lib/motion/native/hapticsEngine.ts`** (new): the only file that names the native module. It reaches it through `import()` (with a `typeof import()` type), cached.
  - iOS plays the three UIFeedbackGenerator calls.
  - Android plays `performAndroidHapticsAsync` alone (`playAndroid`). The module's other three calls drive the Vibrator on Android and need VIBRATE.
  - A call built for the other platform is refused.
  - Each Android value is mapped to the module's enum member through a `satisfies Record<AndroidHapticType, …>`, so a rename fails `tsc`.
- **`src/lib/motion/appHaptics.ts`** (new): the app's one gate. It reaches the adapter through `import("./native/hapticsEngine")`, so it is safe to import from anything a node test imports. `haptic(event, request)` is the fire-and-forget one-liner, and it is never awaited before rendering.
- **`app.config.ts`**: `resolveAppConfig` adds `android.blockedPermissions: ["android.permission.VIBRATE"]` for every profile, keeps any block already declared, and drops VIBRATE from `android.permissions` in either spelling. `npx expo config --type introspect` shows the effect on the generated manifest: `<uses-permission android:name="android.permission.VIBRATE" tools:node="remove"/>`, with the `tools` namespace declared.
- **Sticky third party**: `lib/profile/store.ts` `setCompanionDeclaration` calls `appHaptics.markSilentOrThirdParty()` whenever the declaration is anything but the patient alone (`thirdPartyPresent`, or an attribution other than `self_report`). Nothing is persisted. The flag lives in memory, as the declaration does.
- **Microphone owners**: each registers in a mount effect and is released on unmount. `lib/dialogue/useDialogueSession.ts` registers `voiceSessionActive: () => !closedRef.current` and `micHot: () => recorder.isRecording`. `components/VoiceNote.tsx` (the `__DEV__` note mic) registers `micHot`. These are the only two `useAudioRecorder` owners in the app, and the e2e guard pins that list. The dialogue edit is one import and one effect, outside every region the barge-in and MOTION-10 guards slice.
- **Server answers**: `revokeShare`, `fileExport`, `fileErasure` and `withdrawErasure` now resolve `true` only when the server's record came back. Their behaviour is otherwise unchanged.

### Not wired, and why
- **Note sent.** The review screen's send is local: `updateNote(visitId, { type: "send" })`, and the screen reaches no network (its own header says so). There is no server confirmation to wait for, so no `success` is wired, and no `noteSend` surface is added until its first server-confirmed consumer exists (the §2.2 "lands with its first consumer" rule).
- **CSAT** (`CsatPrompt`, which reuses `Segmented`). It is an answer to a question, gated by consent and asked after the note. P17's "selecting an answer must not feel rewarded" applies, and ADR-033 §6's `select` list names only the visits `Segmented`, the calendar and the appearance options. This is why the wiring is at call sites and not inside `Segmented` or `SwitchRow`: those components are unchanged, and the design agent restyling them owns them.
- **Notification opt-out and quiet-hours rows.** These are hand-rolled pills, not `SwitchRow`s, and a reminders opt-out is a communication preference that sits next to consent. Consent-class rows never fire.
- **Consent rows** (`me/consents/*`, `(auth)/consent`) and **legal text**: never. They are refused by surface, and the closed wiring list keeps them out.
- **The calendar's month arrows**: navigation, not a selection. HIG: "Avoid overusing haptics."
- **`arm` on the DSAR erasure** is wired as well as on the share revoke. ADR-033 §6 defines `arm` as "the first tap of a two-step destructive action", and system spec §6.1 names "a DSAR delete". Both use the same INT-140 idiom, and HIG asks for "a clear, causal relationship between each haptic and the action that causes it".

### Grounding (Apple HIG, Playing haptics — https://developer.apple.com/design/human-interface-guidelines/playing-haptics)
- "Use system-provided haptic patterns according to their documented meanings". This grounds the mapping: selection feedback "while the values of a UI element are changing", and notification feedback "about the outcome of a task".
- "Prefer using haptics to complement other feedback": every event pairs with an existing visual, and none is the only feedback.
- "Ensure that haptic vibrations don't disrupt experiences involving device features like the camera, gyroscope, or microphone": the microphone rule.
- "Make haptics optional": the app has no in-app switch. The OS owns it. UIFeedbackGenerator follows System Haptics, and `performHapticFeedback` follows Android's touch-feedback setting.
- The HIG also says switches and pickers "automatically play haptic feedback". `SwitchRow` and `Segmented` are drawn with `Pressable`, not native controls, so the OS plays nothing for them, which is why they are wired.

### The session boundary (a decision, stated)
- The sticky flag lives as long as the gate, which in the app is the process.
- That is also the life of the companion declaration it listens to: `profile/store.ts` says "It resets with the app", and `resetCompanionDeclaration` has no caller in the app.
- No per-visit session-end hook exists to start a narrower session. Over-suppressing is the fail-closed direction.
- "Only a new session starts clean" is proved with a new gate. A per-visit boundary lands with the hook that would reset it.

### What a node test cannot see (not claimed)
- **The recorder's asynchronous stop after unmount.** On `failed` and `leave` the stop is in flight when the dialogue unmounts and its probe is released, so the gate cannot see that tail. The intake has no haptic surface and the review send has none, so none is reachable in that window. As defence in depth, iOS silences haptics while an audio session is recording by default (`AVAudioSession.allowHapticsAndSystemSoundsDuringRecording`, whose default Apple documents as `false`).
- **Device feel, and the OS switches.** Nothing was run on a device. Two things are untested there: the release-build feel on the owner's reference devices (still unnamed, INT-330), and whether System Haptics and touch feedback silence the calls. On Android below API 30 or 34, expo's `HapticType` throws `HapticsNotSupportedException` for Confirm, Toggle_* and Segment_Tick. The gate swallows it, so those devices are silent. `Context_Click` exists at every API level.

## Tests (TDD)
`apps/mobile/src/lib/motion/haptics.test.ts` (new, 17 tests). These are the 12 MOTION-11 DoD titles verbatim, plus five more:
- **"no haptic while the voice audio session is active"**: pure, for every admitted pair on both platforms. Through the gate, a live probe: the session closing is read on the next request, releasing the probe frees the gate, and a probe that throws counts as an open session.
- **"no haptic while the microphone is hot, read at fire time"**: pure, then three near misses:
  - cold when asked and hot by the time the adapter loads, so nothing plays;
  - hot when asked and cold a moment later, so nothing is queued;
  - a caller-supplied stale `micHot: false`, which is ignored. `expectTypeOf` pins that `HapticRequest` carries no live state.
- **"no RED register fires a haptic"**: the event union is the five feedback events (`expectTypeOf`). All four registers are covered:
  - presenting a RED plays nothing;
  - ALERT, CALM and SILENT hold every request;
  - DEFERRED_CLINICIAN changes nothing, because a haptic that stopped would be a side channel;
  - an unknown register fails closed.
- **"no haptic for the rest of a session in which a SILENT RED or a third party occurred"**: SILENT is dismissed and still silent. A marked third party is silent. `keyof HapticGate` has no clearing method. Near misses: a dismissed ALERT or CALM is not sticky, and a new gate starts clean.
- **"no haptic on any intake chip, in either lane"**: voice lane listening, voice lane confirming with the mic closed, and the typed lane, for every event on both platforms.
- **"consent grant and withdraw never fire a haptic"**: consent and legal, for every event including toggleOn (grant) and toggleOff (withdraw).
- **"success fires only on a server-confirmed outcome, never on press"**: `undefined` and `false` are refused on all three success surfaces. Through the gate: the press is refused, the server's refusal is refused, and the confirmation plays `confirm` on Android.
- **"issuing and revoking a link give the same feedback"**: the same answer for all 16 combinations of the live conditions, × confirmed or not, × both platforms.
- **"select fires only when the value changes"**: `false` and `undefined` are refused, and `true` gives the selection tick or segment tick.
- **"HapticCall has no error, warning or heavy member"**: `expectTypeOf` on the method union, the impact style (`"light"` only), the notification type (`"success"` only) and the Android type union. At run time, every call the policy can return, over the whole context space, is scanned for error, warning, heavy, rigid, reject, long-press and drag-start.
- **"Android never uses Vibrator-backed calls"**: `expectTypeOf`, then every Android call through the policy and through the gate. The adapter's `playAndroid` body calls `performAndroidHapticsAsync` and none of the three Vibrator-backed calls, and `play` refuses a call built for the other platform.
- **"one haptic per commit, deduplicated by action id"**:
  - the same action asked twice in one commit plays once;
  - the same action in a later commit plays nothing;
  - two actions in one commit play once;
  - a new commit is free again;
  - minted ids never repeat;
  - a refused request does not hold the commit.
- Also: the positive control (all nine admitted pairs fire when nothing forbids them), "a companion or a third party declared on the phone marks the app's session" (the real store and the real app gate, two scenarios on fresh modules, a near miss for the patient alone, and taking the declaration back keeps the silence), "an error never fires a haptic", "an unknown surface, event or missing flag fails closed", and "a failing engine never reaches the handler".

`apps/mobile/e2e/motion.spec.ts`, a new MOTION-11 block of 4 guards. Every detector is proved on samples first, and the module name, the permission and `Vibration` are assembled from parts:
- **"expo-haptics is imported only by the engine adapter, and only via import()"**:
  - seven static shapes are caught (named, namespace, type-only, side-effect, `require`, re-export, subpath);
  - two lazy shapes are accepted (`await import`, `typeof import`), plus one across lines;
  - a comment is not an import;
  - the dependency is `~57.0.x`;
  - across the tree, exactly one file names the module, with zero static and at least one lazy reference;
  - nothing imports the adapter statically, and `appHaptics.ts` reaches it through `import()`;
  - `haptics.ts` and `hapticGate.ts` import no platform, adapter or loader.
- **"the Android build blocks VIBRATE"**:
  - covers app.json, a config that asks for VIBRATE in both spellings, and a config that already blocks something else, × four profiles;
  - VIBRATE is blocked exactly once and never requested;
  - the other block is kept, and the declared inventory resolves unchanged;
  - the library manifest really does declare VIBRATE, so the block is not vacuous;
  - no app file takes react-native's vibration API, which would throw without the permission.
- **"only the wired handlers ask, never an intake, consent, legal or error surface"**: the files that ask, with their events and surfaces, equal a closed five-file list. Every `success` states `serverConfirmed:`, and none states it as a literal `true`.
- **"every microphone owner reports itself to the haptic gate for as long as it lives"**: the `useAudioRecorder` owners are exactly the two listed. Each registers in a mount effect that returns the release, with `micHot` reading `.isRecording`, and the dialogue also registers `voiceSessionActive`.

`src/lib/shares/store.test.ts` and `src/lib/dsar/store.test.ts` each gain one test: "answers true only when the server's own row / the controller's own record came back (INT-340)".
