`lib.sh` provides the following:
- Every compose call goes through `docker compose -p intake-staging --env-file /etc/intake-staging/.env`.
- Secrets never travel in argv. Tokens reach `bao` through the docker CLI environment (`-e BAO_TOKEN`). Unseal keys and SQL go on stdin.
- Migration-role re-keying. `ROLE_PASSWORD_KEYS` is checked against `migrations/versions`.

The three host scripts do this:
- `init.sh` generates every secret on the host into `/etc/intake-staging/.env` (0600, in a 0700 dir). It initialises OpenBao with 3 shares, threshold 2, and writes the shares and root token to `openbao-init.json` (0600). It unseals, enables Transit, writes the policy and the probe KEK, and mints the API's periodic orphan token (768h). The token id is host-generated, so the env file is complete before OpenBao exists. It then runs alembic and re-keys the roles.
- `deploy.sh` stamps, unseals, renews the token, builds, migrates, re-keys, runs `up -d --build --wait`, and then probes HTTPS.
- `smoke.sh` runs the four endpoints over HTTPS. It checks that `/version` equals the deployed sha and is never `dev`. It checks the staging header, the HTTP→HTTPS redirect, and the API posture. It runs the restart test across an api restart **and** an OpenBao restart plus unseal.

### Decisions worth a reviewer's eye

- **The restart test runs through the API's cipher, not an HTTP route.** A staging API with no
  dev gate has no authentication tier that can write a note. The dev bearers are dev gates.
  The OTP tier needs an SMS vendor and attestation, both awaiting-human. It is also left
  unconfigured on purpose: a tokenization key would wire the dev delivery logger. The probe
  drives `wiring_from_env().cipher` in the api container, with the same OpenBao token. Its
  negative control is unit-tested: a record written with one `FileKekProvider` does not open
  with a fresh one (`TamperError`), which is exactly what the process-local KEK would do
  across a restart.
- **OpenBao's command starts with `bao`.** The image's default CMD is `server -dev`, and its
  entrypoint's `server` branch appends `-dev-*` flags. `["bao", "server", "-config=…"]`
  bypasses both and still runs as the image's non-root user.
- **The "KEK key".** `TransitKekProvider` creates one key per tenant, `tenant-<id>`, on the
  first wrap. init.sh creates the Transit engine and one key, `tenant-staging-restart-probe`,
  for the probe. The API's tenants get their keys from the API under the `tenant-*` policy.
- **Unseal shares on the same host.** This is the staging posture the task specified.
  Production key custody is a key-management design decision for a human (CLAUDE.md
  stop-and-ask). This PR does not make it.
- **Migration roles carry committed dev passwords** (`migrations/versions/0001`, `0009`).
  init.sh and deploy.sh re-key every one of them from host-generated values. The failing
  statement is kept out of the Postgres log.

## Follow-up: INT-325 credentials and the object store (INT-347)

**Why.** PR #521 (INT-325, head `be74a9d1`) makes every non-dev `INTAKE_ENV`, staging
included, refuse to boot on any `INTAKE_DEV_*` flag, a file-dev KEK, the fake-SMS adapter, or
a missing or empty credential variable. Its `settings.NON_DEV_REQUIRED_CREDENTIALS` lists five:
`INTAKE_API_DB_URL`, `INTAKE_API_AUDIT_DB_URL`, `INTAKE_API_BOOTSTRAP_DB_URL`,
`MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`. The artefact passed the three DB URLs but not the
object-store pair, so the staging API would have refused to boot.

**What changed.**
- `staging.env.template` gains `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD` (ten keys, no
  values).
- `init.sh` generates secrets through `lib.sh`'s `generate_missing_secrets`. Every template
  key except `STAGING_HOSTNAME` gets a 256-bit hex value in the root-only 0600 `.env`, once.
  A re-run keeps every existing value.
- `compose.yaml` passes the pair to the api as `${NAME:?run init.sh}`, with no default.
- **Object store.** The upstream `minio/minio` image is withdrawn, and no replacement image
  is approved in this repository. `lib.sh` carries `OBJECT_STORE_IMAGE=""`, and deploy.sh's
  first statement is `require_object_store_image "$OBJECT_STORE_IMAGE"`. That check runs before
  the root check and before any docker call. It refuses an empty or non-digest-pinned
  reference and names INT-347 (#550). The runbook and PR body say "depends on INT-347".
  During this follow-up the owner's choice of a replacement image was relayed by the
  coordinating agent. The session's permission classifier refused integrating that
  third-party image on a relayed decision ("untrusted code integration"). This PR therefore
  keeps the fail-closed gate. The swap belongs to INT-347 once the owner approves it
  directly.

The test reads the required list from `api_settings.NON_DEV_REQUIRED_CREDENTIALS` when the base
carries #521. Until then it uses the same five names, and a test proves that each one is a
string literal the API reads (`settings.py`/`app.py`).
