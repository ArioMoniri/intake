# Evidence: INT-446 · RED end to end in the app

**Epic:** E08-mobile · **Phase:** P0 · **Sec-Row:** triage · **GitHub:** #756 ·
**Depends on:** INT-080 (the triage engine), INT-103 (`livekit/red.ts`), INT-333 (the RED motion contract)

## Problem

The INT-440 voice end-to-end test, run on 3 Oct 2026, found that a RED could not fire anywhere in the app:

- `apps/mobile/src/lib/livekit/red.ts` decoded and resolved a RED, but no screen mounted it.
- No lane sent the patient's bound answers to the rules engine. The dialogue lane went to the
  extract daemon and nowhere else, and the typed StepFlow went nowhere at all.

## Change

**The rules-engine hop (invariant 1).** There is no rule on the device.

- `services/api/src/intake_api/triage_hop.py` adds `POST /v1/triage/evaluate`. It runs
  `protocols.triage.evaluate_triage` (packages/protocols) over the served set.
- A RED comes back as the data-channel packet itself (`kind`, `ruleId`, `register`, `location`,
  `scriptId`), which is `red_path.RedTriggerMessage`'s shape. The device therefore decodes it with
  the one decoder the LiveKit lane already uses, `decodeRedTrigger`.
- The winning rule id is taken from the engine's own outputs: the fired rule whose register and
  resolved action the engine returned. `result.rules[0]` is not used, because it is ordered by
  severity and then id, while the engine breaks severity ties on register. A test pins this.
- Both routes declare the `core` consent scope. Nothing is stored or logged.

**The served set (fail closed, content empty).**

- `intake_api/triage_rules.py` loads `ApiSettings.triage_rules_path` (env `INTAKE_API_TRIAGE_RULES`)
  through `load_life_threat_set`. A set is served only when all of these hold:
  - it declares `served: true`;
  - its HB-C1 sign-off is complete;
  - it holds no `draft_needs_source` rule;
  - every RED rule resolves to verbatim `tr` for REMOTE, ON_SITE and UNKNOWN.
- Anything else, including no path at all, makes both routes answer 503 `triage_unconfigured`.
  That is never a GREEN and never an empty catalog.
- Today every `base.life_threat` rule is `draft_needs_source` (HB-C1). **The shipped state is
  therefore 503 and no RED.** The mechanism is proved over the committed signed SENTETİK fixtures.

**The pre-positioned catalog (invariant 21).**

- `GET /v1/triage/red-scripts` serves each RED rule's REMOTE and ON_SITE scripts and its UNKNOWN
  question. All of it is verbatim `tr` (invariant 10).
- The device fetches the catalog **before** it sends any answers. With no catalog on the device,
  no answers are sent (`createRedHop`), so a RED can never arrive that this device cannot render.

**The device.**

- `lib/red/hop.ts` maps the note's `Answer[]` to slots. It sends `values` only, never `words`.
- `lib/red/location.ts` derives the location axis from files/02 §5.3 Axis 3:
  - Hızlı mode on a visit planned for a later day is REMOTE.
  - Everything else is UNKNOWN.
  - ON_SITE is never derived, because the client has no check-in event.
- `lib/red/store.ts` holds the one RED, escalation only:
  - nothing clears it;
  - a later RED replaces it only when the first changed nothing on the patient's screen;
  - the one location question is answered once.

  `redScreen` is the pure screen model and spreads `lib/motion/red.ts`: `RED_MOTION` (now
  exported), `redPresentationMode` and `redAffordances`.
- `components/RedLayer.tsx` is mounted by `app/_layout.tsx` as a sibling **after** the navigator
  container (`</KioskGate>`). It runs the hop on every change to a visit's bound answers, so the
  typed StepFlow, the dialogue composer and spoken turns all pass through it: each lands in the
  note through `updateNote({type:"answer"})`.
  - ALERT and CALM paint as the root layer. ALERT uses the reserved `emergency` colour; CALM is
    amber-neutral.
  - SILENT renders in the flow of both lanes (`RedInFlow`, with no headline).
  - DEFERRED_CLINICIAN changes nothing on the patient's screen.
  - There is no `Modal`, no Animated, no haptic, and no audio or media module.
- `DialogueIntake` calls `session.leave()` the moment a RED the patient sees is presented. The agent
  stops and the microphone closes, for SILENT as well.
- The `tr` chrome is `red.call112` ("112'yi arayın"), `red.location.yes` and `.no`, and
  `red.doNots` ("Lütfen yapmayın", the files/02 §5.3 CALM wording). The RED's own words are never in
  the catalogue.

**Haptics (ADR-033 Q2).** No RED fires a haptic, for any register. The motion contract's
`haptic: false` holds, and no haptic engine exists on `main`. When INT-340 (#710) merges, its
`appHaptics.presentRed(register)` belongs in `RedLayer` while a RED shows. It holds every other
haptic, which is stricter, never looser.

## Open, and not built around

- **No served rule set exists (HB-C1).** Until a physician signs `base.life_threat`, `/v1/triage`
  answers 503 and no RED fires in a real session. That is the intended fail-closed state.
- **The app's dev question packs have no dated slot.** A real rule's tense anchor (files/12 §2.4)
  cannot be satisfied by any dev question today. Projecting a live SessionState onto rule slots is
  INT-081's job. The simulator set anchors on the free-note slot itself.
- **Generic copy for an unrenderable RED is a clinical and legal string.** This is a RED whose script
  is not on the device, which is possible only on the LiveKit lane under version skew. No such
  string exists, so `redScreen` returns `unrenderable` and invents nothing.
- **`services/voice-runtime/.../red_path.py` picks the script from `rule_ids[0]`.** That has the same
  ordering issue this route avoids. It is outside this issue's scope and reported in the PR.
