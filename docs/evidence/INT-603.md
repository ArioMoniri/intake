## 1. Acceptance (verbatim)

1. The first-run screen and its copy agree. Either no purpose that needs consent shows "Açık"
   before the patient acts, or the rows that show "Açık" are labelled as the service itself (no
   switch) rather than as a consent. A test asserts that no consent-scope row defaults on.
2. The consent state uses a platform switch/toggle with accessibilityRole "switch", not a
   badge-like pill. Withdrawing asks for one confirmation that says what stops and that it takes

4. Every string comes from the tr catalogue, with no new legal text outside docs/legal/

## 2. What changed and why

**K1 (item 1).** Every açık rıza purpose already defaults off in the registry and the ledger, and a
real (otp) account starts with every session consent off. The only rows on before the patient acts
are `learning:personal` and `learning:service_improvement`, which the registry puts on non-consent
bases (service performance, de-identified opt-out) with an opt-out. So the first branch of item 1
holds, and it is now pinned. The second branch does not fit: these rows are not the service itself,
and removing their switch would remove the opt-out (files/06 §2). Labelling them "the service
itself" would also bring back the deleted `consent.basis.service` claim, which brand.spec.ts and
consent.spec.ts keep out of the catalogue (INT-537).

What the patient saw as a contradiction was the order: the explanation was a footer under the two
"Açık" switches. The existing line, `consent.group.learning.hint` ("Bu iki seçenek hizmetin
çalışması içindir ve açık gelir; dilediğiniz an kapatabilirsiniz."), now sits **above** the rows,
and its wording is unchanged. No new legal characterisation is made: a first draft said "izin
değildir", and it was withdrawn before commit. Whether those two grounds carry health data at all is
the open HB-L27 question (docs/backlog/blockers.md, INT-529 learning row), and a UI line must not
answer it. The opt-out rows' switch gets its own screen-reader hint, so it is not called a consent.

**K2 (item 2).** The pill (`StatePill`) is gone. `ConsentSwitch` is a `Pressable` with
`accessibilityRole="switch"`, `accessibilityState={{ checked, disabled }}`, the state word kept
beside it, and the drawn track and knob from `SwitchRow` (now exported as `SwitchTrack`, so the
knob still moves as well as recolours). The audit's alternative, the RN `Switch`, cannot scale with
text or stack; SwitchRow's header explains why the app draws its own. The tap rules live in the pure
module `lib/consent/switchIntent.ts`:

- an unchecked switch (off, pending or stale) opens layer 2, where the grant is made against the
  text. No extra confirmation is added;
- a checked switch shows `WithdrawConfirm` in place, under its group. It names what stops (the
  purpose plus every granted purpose its cascade takes down, the same set `withdraw()` flips) and
  that the change is immediate. For a consent this reuses `consent.detail.withdrawNote` ("Geri
  çekmek hemen geçerli olur."). Then one confirm and one cancel. It is announced
  (`AnnouncedRegion`, SC 4.1.3);
- asking changes nothing. Only the confirmed withdrawal reaches `onWithdraw`, which both screens
  route through `withdrawLocal`. That queues the one op `POST /v1/consents/withdraw` records and
  audits (consents.py, invariant 4). No server file changes.

Withdrawal stays as easy as grant (files/06 §2): two taps from the list either way (switch +
confirm; row + "Okudum, kabul ediyorum"). The detail screen's labelled "İzni geri çekin" button,
which already sits beside the immediacy note, is unchanged. Adding a confirmation there would make
withdrawal harder than grant. The audit itself proposed "withdrawal stays one tap"; the issue's
acceptance asks for one confirmation, and the acceptance is followed. The legal-reviewer should see
this.

**K3 (item 3).** On `(auth)/consent.tsx`, "Devam edin" moves out of the `ScrollView` onto a
bottom-pinned `GlassBar` (absolute, bottom 0). The list pads itself by the bar's measured height
(`useGlassBarClearance`, INT-284), and the bar owns the bottom safe edge. overflow.spec.ts's
"auth screens keep the bottom edge" rule lists consent.tsx as now owning its edge through the bar,
as that rule asks a revisit to do.

**Item 4.** Every string comes from the catalogue, tr first with an en mirror. No docs/legal file,
fixed string, consent text, purpose, basis or route changes.

| key | tr | en |
|---|---|---|
| `consent.confirm.withdrawTitle` | Bu izni geri çekmek istiyor musunuz? | Do you want to withdraw this consent? |
| `consent.confirm.optoutTitle` | Bu seçeneği kapatmak istiyor musunuz? | Do you want to turn this option off? |
| `consent.confirm.stops` | Şunlar durur: | This stops: |
| `consent.confirm.optoutNote` | Kapatmak hemen geçerli olur. | Turning it off takes effect immediately. |
| `consent.confirm.optoutAction` | Kapatın | Turn off |
| `consent.confirm.cancel` | Vazgeçin | Cancel |
| `a11y.consent.optoutHint` | Bu seçeneği açar ya da kapatır. | Turns this option on or off. |

The following are reused unchanged: `consent.detail.withdraw`, `consent.detail.withdrawNote`, the
purpose labels, `consent.on`, `consent.off`, `consent.state.*` and `consent.group.learning.hint`.
The new hint is descriptive (iOS HIG), not an imperative, so the recorded `-iniz` register set in
tests/release/test_i18n_complete.py does not grow.
