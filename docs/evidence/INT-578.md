## What was built

**The pepper (row 7).** `intake_api.otp_pepper` is new. The phone tier keeps a code only as
`HMAC-SHA-256(pepper, domain ‖ len‖pseudonym ‖ len‖request_id ‖ len‖code)`; the device binding
is an HMAC under the same key in its own domain. The pepper lives in OpenBao at
`secret/api/otp`, field `pepper`, 32 to 128 bytes of lower-case hex. Where it comes from:

| deployment | source | without it |
|---|---|---|
| prod, staging (every strict environment) | OpenBao `secret/api/otp`, read after the delivery adapter is built, so a tier that cannot send pulls no key | `_auth_from_settings` returns `None`: every `/v1/auth` route answers 503; the log line names `secret/api/otp` and the field, never a value |
| dev on the OpenBao dev server (`make dev`, transit KEKs) | the same path; `scripts/security/openbao_dev_setup.sh` writes `openssl rand -hex 32` to it on stdin, once, and keeps it across re-runs | 503, as above |
| dev under `INTAKE_API_KEK_MODE=file-dev` (the no-OpenBao escape, refused at boot outside dev by INT-325) | a process-local random pepper, as that mode takes process-local KEKs | — |
| a test harness that builds `AuthWiring` itself | the field's default: a process-local random pepper | — |

No environment variable is a pepper source (a test sets three plausible names and the tier stays
at 503). The synthetic host makes it in `infra/staging/lib.sh`, `ensure_otp_pepper`: from the
kernel CSPRNG (`gen_secret`, 256 bits), into `bao kv put -mount=secret api/otp -` on stdin,
never argv, a file or a log line. A good pepper is kept — rotating it on every deploy would void
every code in flight — and a missing or malformed one, which the API refuses, is replaced.
`init.sh` runs it in `configure_openbao` after the policy; **every `deploy.sh` runs
`ensure_api_openbao`**, which re-applies the committed policy and then ensures the pepper,
because `init.sh` never runs again on a host that already exists. The API policy gains
`path "secret/data/api/otp" { capabilities = ["read"] }`: read only, no metadata, no list.

**The code record and the store (rows 3, 4, 6).** `AuthStore.store_code` keeps
`{digest, binding, expires}` and resets a separate attempt counter; `check_code` is now:

1. read the record; if there is none or it has expired, compare the candidate digest and
   binding against stand-ins (two constant-time comparisons, the same work a live record costs)
   and answer `missing`;
2. take the attempt with `INCR` **before** comparing — the atomic step, so racers that all read
   the record buy at most 5 comparisons between them;
3. compare the digest and the binding with `hmac.compare_digest`, both always;
4. over the budget → `exhausted`; a match → `DEL` the record, and only the caller whose `DEL`
   removed it is `ok` (the other is `missing`); the miss that spends the fifth attempt →
   `exhausted`; otherwise `unbound` when the binding is wrong, else `invalid`.

The Doctor Link tier shares the store (its own `dlink` prefix), so it gains the atomic budget and
the atomic single use; it keeps its unkeyed INT-131 digest (`code_digest`, now documented as the
Doctor Link's only) and no lockout, because neither is in this issue's scope and its codes never
leave the patient's own session today (no Doctor Link delivery channel exists).

**The lockout (row 5).** The miss that answers `exhausted` locks the number:
`AuthStore.engage_lockout` stores the instant the lockout ends, `lockout_wait` reads it (never the
key's TTL; the injected clock decides). While it runs, `request_code` mints nothing (429
`otp_limited`, retry-after the true remaining time; asking costs no budget) and `verify_code`
compares nothing (the generic 401, counted as `locked`). `OTP_LOCKOUT_S` is **one request window,
3600 s**, and the length is the control, proved on the route: a lockout shorter than the window
lets the 3-per-hour budget hand out three codes an hour, which is the 15 guesses an hour INT-131
allowed; at a window it is 5. It adds no denial-of-service lever: the same caller could already
hold a number for an hour by spending its request budget, and a lockout cannot be extended by
guessing during it.

**The binding (rows 8, 9).** Each admitted request mints `request_id = secrets.token_hex(16)` and
returns it in the 202 beside `delivery_id` and `resend_after_s`; the digest covers it. The device
binding is the App Attest **key id** when the call proved one (`mode: app-attest`), and the
install id only for `dev-unattested`, which only the dev tier accepts; in a real mode the install
id is the client's own claim, and binding to it would let any key that claims it spend the code.
`POST /v1/auth/otp/verify` now requires `request_id` (32 lower-case hex; a body without it is a
422 by shape). A code tried from another device, or under another request id, is one more miss:
the same generic 401, counted.

**The app.** `apps/mobile/src/lib/auth/pendingOtp.ts` (new, pure, vitest-covered) keeps the id
from the request's 202 in module memory — never SecureStore, never a log line — and `api.ts`
sends it on verify and drops it once the code is spent. A resend replaces it; a malformed id
clears it; without one (the app restarted in between) `verifyOtp` refuses locally with the
existing `code` error kind, so the patient asks for a new code. No copy changed.

**The signal.** `otp_verify_total{outcome}`, `outcome` ∈ {ok, invalid, unbound, exhausted,
missing, locked} (`VERIFY_OUTCOMES`, pinned), catalogued live. `unbound` is codes tried from a
device that did not ask for them: the interception signal.

## Engineering defaults (not clinical values)

- `OTP_LOCKOUT_S = OTP_WINDOW_S` (3600 s), for the reason above. The owner may lengthen it; the
  test that pins it asserts only that it is at least one window.
- The pepper's shape: 32 to 128 bytes, lower-case hex, matching what `gen_secret` and
  `openssl rand -hex 32` produce.
- The request id: 128 random bits as hex.

The binding is to the App Attest key rather than the DPoP key: the OTP request carries no DPoP
proof today, the App Attest key is hardware-backed and proven on both calls, and the DPoP key the
verify proves is the one the session tokens are then bound to (INT-131), so the chain request →
verify → session runs through two proven keys. Requiring a DPoP proof on the request as well is
a mobile change with no security gain over the App Attest key on iOS; on Android every OTP call
is refused today (HB-A3), so there is no unproven path to bind.

## What this does not stop

- **A patient who reads the code to a caller.** If the attacker asked for the code on their own
  device, the code is bound to the attacker's device, and the patient reading it out completes
  the attacker's sign-in. That is INT-580's (the SMS copy, the new-device notice, the passkey
  step-up).
- **The Doctor Link digest** stays unkeyed (above); it is not on the SMS path.
- **Enumeration through the lockout's 429.** A locked number answers 429 to a request where an
  unlocked one answers 202. INT-579 makes those answers identical; this PR does not widen what was
  already visible (the per-number budget's 429 says the same thing).
