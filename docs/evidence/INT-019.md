## What each finding actually was

**licenses — the offending dependency was us.** Every one of the seven
violations is a workspace member. `FIRST_PARTY_PYTHON` was a hand-written
three-name set; seven members landed after INT-019 was written, so each
arrived as a third-party dependency with no licence metadata. Fixed by
*deriving* the set from `[tool.uv.workspace]` — and by requiring PEP 610
`direct_url.json` to prove the distribution was installed from this checkout,
because skipping on a name alone is a dependency-confusion hole. Not a
blocker, not an allow-list entry: a staleness bug, plus a hole closed.

**sast — two true positives, verified before being believed.**
`ehrbase.py` parsed the CDR's status document with stdlib ElementTree, which
expands internally declared entities. Measured on this interpreter: one
declaration expanded 10×, i.e. billion-laughs against a hostile or compromised
CDR. Now `defusedxml` (PSF-2.0, read from the raw LICENSE blob in
`.venv/.../defusedxml-*.dist-info/LICENSE`, invariant 19), with `DTDForbidden`
converted into the same typed `EhrbaseRefusedError`; a test plants the
expansion document. `runtime_sim.py` used `urlopen`, which honours `file:` and
any other scheme the URL carries — now `httpx`, which speaks http/https only,
so the class of risk is removed at the call rather than annotated away.

**iac — a false positive on an environment-variable NAME, exempted narrowly.**
`target_secret_key_env: INTAKE_DR_S3_SECRET_KEY` is the name of a variable
OpenBao populates; checkov's entropy plugin reads it as a base64 token. Two
renames were measured (`INTAKE_DR_OBJECT_STORE_SECRET_KEY`,
`INTAKE_DR_S3_SECRET_ACCESS_KEY`) and both still fire, so renaming is
cargo-cult rather than a fix. The exemption is one line-scoped
`checkov:skip=CKV_SECRET_6`, and the control on it is a self-test: a real
base64 secret appended elsewhere in that same file still fails
(`Failed checks: 1`), and removing only the skip comment brings the original
finding straight back — both measured.

**check-py — the SBOM was undeclared.** `artefact_paths: []` in
`infra/ci/no-phi-policy.yaml` meant the artefact the gate set exists to
publish had nowhere to be declared. Declared with what was actually checked,
not with a hand-wave: the generated SBOM (1487 packages, 751 files) names
**zero** paths under `tests/fixtures` or `docs/`. Read honestly, running the
repo's own PHI scanner over the SBOM does report one checksum-valid TCKN — and
it is an 11-digit decimal substring of a package's SHA1 checksum, which is what
a coincidence looks like across 1487 packages, not an identifier.

**phi-scan — already fixed on main, verified rather than assumed.** The gate
flagged two TR mobile shapes in `docs/evidence/INT-206.md` and a
checksum-valid TCKN in `docs/evidence/INT-230.md`. Checked against the
committed blobs at both tips rather than by re-running a script that scans
whichever checkout it lives in:

```
$ git show 9c58cef:docs/evidence/INT-206.md | grep -cE '<phone shape>'   # 2
$ git show HEAD:docs/evidence/INT-206.md    | grep -cE '<phone shape>'   # 0
$ git show 9c58cef:docs/evidence/INT-230.md | grep -cE '<tckn candidate>' # 1
$ git show HEAD:docs/evidence/INT-230.md    | grep -cE '<tckn candidate>' # 0
$ git diff 9c58cef HEAD -- scripts/ci/phi_scan_allow.txt                  # empty
```

Main fixed both in `b6a99c0` by eliding the examples, with the allow-list
untouched. The merge alone clears this check.

## The trivy ignore row that never worked

`trivy fs` reports **CVE-2026-33310 HIGH** against `intake@0.1.0` from
`uv.lock`. That advisory is a `shell()` expansion command injection in the
PyData `intake` data-catalog project on PyPI, and what trivy matched is not
that project and not a package: `uv.lock` records
`source = { virtual = "." }`, this repository's own workspace root, declared
`[tool.uv] package = false` with no `[build-system]`. It is never built, never
published, never resolved from PyPI, ships zero source files, and `shell()`
appears nowhere in the tree.

A PURL-scoped `.trivyignore.yaml` for exactly this had been drafted in the
INT-019 worktree and never committed — **and it would not have worked**:

```
$ trivy fs --scanners vuln --severity CRITICAL,HIGH ... .      # rc=1, CVE reported
$ trivy fs --ignorefile .trivyignore.yaml ... .                # rc=0
```

trivy 0.74 auto-detects the plain-text `.trivyignore` and not the YAML form.
The file is now committed with that evidence in its own `statement`, the
Makefile passes `--ignorefile`, and two tests hold the shape: every row must
carry `purls` (a bare `id:` is a tree-wide mute) with a statement long enough
to disagree with, and `make security` must actually pass the flag — the second
test was checked by removing the flag and watching it go red.

**Recorded and deliberately not done:** the durable fix is renaming the
workspace root so it stops declaring the name of a real PyPI project. A
suppression does not remove that dependency-confusion surface. It churns
`uv.lock`, which every open branch is also editing, so it is the owner's call.

## Three defects inside the protected workflow file (HB-O5)

`.github/workflows/security.yml` is hook-protected, so these were diagnosed
and proven but not patched. Each is one line.
