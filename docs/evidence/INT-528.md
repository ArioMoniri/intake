# INT-528: Netgsm OTP SMS adapter behind the INT-329 SMS port (recorded fixtures only, fail-closed)

**Date:** 16 October 2026 · **Branch:** `int-528-netgsm-otp` · **Issue:** #895 · **Sec-Row:** files/10 §9 `onboarding` · **ADR:** ADR-042

On 16 Oct 2026 the owner decided, on INT-358 (#576), that the SMS vendor is **Netgsm's OTP SMS
product**. That decision records Netgsm as BTK-licensed and processing the data in Türkiye. The
signed DPA is what confirms both.

Scope addition on #895 (App Attest "keychain", HB-A3): the Apple team id is read at deploy time
from the owner's Apple Development certificate. It never goes into git, logs or chat.

Owner orders relayed the same day:

1. The credentials live in SSM Parameter Store as SecureStrings
   (`/intake/staging/netgsm_usercode`, `_password` and `_msgheader`, for a dedicated API sub-user).
   A sync step copies them into OpenBao on the host.
2. The sender header comes from SSM and never from code. It may contain spaces.
3. A read-only credential check is the go-live's first step.
4. The host's egress address is its Elastic IP, **3.211.2.143**, which the owner whitelists in
   Netgsm.
5. The official SDK is to be evaluated.
6. **SMS is real now.** On the synthetic host the API sends a code, and starts a login, only for a
   number on `/intake/staging/sms_test_allowlist`, and fails closed without the list.
7. One real OTP to that allow-listed number is authorised. It runs after INT-528, the egress patch
   and the deploy are live, and only when the owner or orchestrator runs it. This work never runs

**Route decision (orchestrator, ADR-042).** The synthetic API gets a dedicated SMS-only egress

**Owner's own verification, reported and not observed by this work.** From the host, Netgsm

## The vendor contract, and where it comes from

Source: Netgsm's public API documentation, <https://www.netgsm.com.tr/dokuman/>, sections **"OTP
SMS"** (REST v2) and **"Gönderici Adı Sorgulama"**, **retrieved 16 Oct 2026**. The page is a
single-page app, so the sections were read from its bundle,
`https://www.netgsm.com.tr/dokuman/bundle.js`, the same day.

Nothing was captured from a live call, and no test or CI job may call the vendor.
`tests/fixtures/netgsm/otp_rest_v2.json` and `msgheader_rest_v2.json` both carry
`"provenance": "built-from-documentation"`, the URL and the date.

| documented | used here |
|---|---|
| `POST https://api.netgsm.com.tr/sms/rest/v2/otp`, HTTP Basic auth (subscriber number : API sub-user password) | `NETGSM_OTP_URL`, with `auth=(usercode, password)`. The module names no other Netgsm endpoint: no bulk send and no İYS filter field. A test pins that, so OTP-type transactional messages are the only kind it can send |
| body `{"msgheader", "msg", "no"}` | `NetgsmOtpRequest.as_wire()`, enumerated by hand. A test holds its keys equal to the documented sample's |
| `no`: the 10-digit national mobile; OTP SMS cannot go abroad or to a landline | `+905xxxxxxxxx` → `5xxxxxxxxx`. Anything else is refused before the wire (`not_a_tr_mobile`) |
| `msg`: one segment, **no Turkish characters**; at most 155 characters with an alphanumeric sender | `SMS_TEMPLATE`: `Dogrulama kodunuz: {code}. Bu kodu kimseyle paylasmayiniz.` It is pinned as a literal and as INT-329's wording folded to ASCII |
| success `{"jobid", "code": "00", "description"}` | receipt `delivery_id` = `jobid` (digits only, otherwise `malformed_response`) |
| error `{"code": "XX", "description"}`; codes 20, 30, 40-41, 50-52, 60, 70, 100 | the typed refusals below. The body's code decides, whatever the HTTP status; the tests replay every error at 406 and at 200 |
| `GET /sms/rest/v2/msgheader` lists the approved sender names; codes 30, 70, 100-101 | the host's read-only credential check (`netgsm_secrets.sh --check`) |

| Netgsm code | `NetgsmRefusal` | `OtpDeliveryFailure` |
|---|---|---|
| 20 | `message_refused` | `rejected` |
| **30**: wrong usercode or password, no API permission, or an address outside the IP restriction | **`credentials_refused`** | `auth_failed` |
| 40, 41 | `sender_refused` | `rejected` |
| 50, 51, 52 | `number_refused` | `rejected` |
| 60 (no OTP SMS package) | `otp_package_missing` | `rejected` |
| 70 | `parameters_refused` | `rejected` |
| 100 (and 101 in the listing) | `vendor_system_error` | `vendor_unavailable` |
| any other code | `unknown_vendor_code` | `rejected` |
| refused before the wire | `not_a_tr_mobile`, `code_not_sendable`, **`not_on_test_allowlist`** | `rejected` |

Transport faults keep INT-329's mapping:

| fault | reason |
|---|---|
| 401, 403 | `auth_failed` |
| 429 | `rate_limited` |
| 5xx | `vendor_unavailable` |
| timeout | `timeout` |
| connect failure | `unreachable` |
| unfollowed redirect | `rejected` |
| a 2xx without a digit job id | `malformed_response` |

Every failure answers one generic `503 otp_delivery_unavailable` at the route.

## The official SDK, evaluated and not used

`netgsm-sms` 1.1.2 (PyPI; <https://github.com/netgsm/netgsm-sms-python>):

- **Licence: MIT, verified from the raw LICENSE blob.**
  - URL: `https://raw.githubusercontent.com/netgsm/netgsm-sms-python/1405f885fdf87fd2f132343c7cd1f836040ef452/LICENSE`
  - commit `1405f885…` (`main`); git blob `92c727ac97d979d9dd1eb2ee9254d27ac0b036a8`
  - file sha256 `d4b1a2d46d9a6e42c0ee5b08de11e2d3fb66928df403123b198d726b25e531bb`
  - `licence_verified_at: 2026-10-16T09:28:02Z`
- Its sources were read at that commit and never installed. Nothing is added to `uv.lock`.

It is not used, and the plain httpx adapter is used instead, for five reasons:

1. **There is no OTP endpoint.** `SmsService` offers `/sms/rest/v2/send` (the queued, İYS-filtered
   bulk product), `cancel`, `report`, `msgheader` and `inbox`, but not `/sms/rest/v2/otp`.
2. **It is synchronous.** Every call is a blocking `requests.post(..., timeout=30)`, which holds
   the async route's event loop: the INT-329 / audit F13 defect.
3. **It bypasses INT-018's egress guard.** It skips the allow-list, the purpose and data class,
   the resolve-and-pin and the transfer record (invariant 14, ADR-025).
4. **Its errors carry vendor text.** `create_api_exception` copies `str(e)` and the vendor's
   `message` into the exception.
5. **It is thin and unmaintained.** The last push was 2025-03-04, it has 2 stars, and the adapter
   needs one POST.

## The test allow-list (owner order: SMS is real now)

`intake_api.sms_recipients.SmsTestAllowlist` parses the field `test_allowlist`, which
`netgsm_secrets.sh` syncs from `/intake/staging/sms_test_allowlist` into OpenBao `secret/api/netgsm`.
The field holds Turkish mobiles in E.164, separated by commas, semicolons, spaces or newlines.

**It fails closed.** An absent, non-string, empty or blank list admits nobody. So does a list with
**one** malformed entry, so a typo never narrows it silently.

On the synthetic deployment (`INTAKE_ENV=staging`) the gate is enforced twice:

- `OtpAuthService.request_code` refuses an unlisted number with `422 phone_invalid` after the rate
  gate, in the same place and with the same answer as the carrier check. No code is minted and no
  SMS leaves.
- `NetgsmSmsDeliveryAdapter.send` refuses it again before the wire (`not_on_test_allowlist`).

Elsewhere the gate is `ADMIT_ALL`. The numbers never reach a `repr`, a log line, a metric label or
the route's answer; only their count is logged.

Every number in the tests is synthetic. The near miss differs from the listed number by one digit.

## The route out (ADR-042)

The staging API's networks are all `internal: true`, and INT-203 (ADR-032) refuses personal data
on a proxy. `docs/adr/ADR-042-the-sms-vendor-rides-its-own-egress-proxy.md` records the decision
and why it does not fall to INT-203's reasons:

- `intake_platform.egress.DEDICATED_PERSONAL_PROXIES` admits exactly the SMS purpose through
  exactly `http://sms-egress:3128`. Every other personal-data proxy arrangement is still refused at
  construction: the shared proxy, another port, scheme or lookalike host, another purpose, a
  pseudonymous call. The in-process allow-list, purpose, data-class and runtime-gate checks still
  decide first.
- `scripts/security/render_sms_egress_conf.py` renders `infra/staging/sms-egress/squid.conf` from
  the allow-list's `phi_path` `sms_otp_delivery` rows only, which must be exact hosts on 443.
  - With the owner's row it admits CONNECT to `api.netgsm.com.tr:443` and nothing else; without
    the row it admits nothing.
  - No cache, and one-second TTLs: the rebinding window is closed at the proxy.
  - `DENIED_RANGES` are refused at connect.
  - The log line is `host:port`, a status and byte counts only; TLS runs end to end.
- The `sms-egress` service in `infra/staging/compose.yaml`:
  - runs the digest-pinned `ubuntu/squid` image the shared proxy pins;
  - runs read-only as uid 13, with every capability dropped and no published port;
  - sits on `sms-out` (internal, shared with the API alone) and `sms-wan` (its only way off the
    host).
- The API joins `sms-out` and sets `INTAKE_SMS_EGRESS_PROXY_URL`. Only the Netgsm wiring reads
  that variable, and it refuses any other value.

**Did INT-203 or an invariant forbid this shape?** No. INT-203 is a construction-time refusal
decided in ADR-032, on two stated grounds:

1. neither enforcement point resolves;
2. the proxy's list carries no personal-data row.

The dedicated proxy answers both, as ADR-032 itself prescribes: it resolves at connect with no
cache and refuses the denied ranges, and it renders exactly the one row it carries. No CLAUDE.md
invariant names a proxy. ADR-042 amends ADR-032 for this one pair only.

   ```bash
   cd ~/Downloads/previsit && uv run python scripts/staging/app_attest_golive.py
   ```

4. **The authorised real OTP: the trigger.** It sends to the single allow-listed number and prints
   only `accepted: code 00, job id <id>` or the refusal. **Never run by this work.**

   ```bash
   aws ssm start-session --region us-east-1 --target i-0e489e48739f5de98 --document-name AWS-StartInteractiveCommand --parameters 'command=["sudo /opt/intake/infra/staging/netgsm_test_otp.sh"]'
   ```

5. **The check, also after a sign-in through the app.** It prints the API's Netgsm outcome lines:
   job id or refusal only.

   ```bash
   aws ssm start-session --region us-east-1 --target i-0e489e48739f5de98 --document-name AWS-StartInteractiveCommand --parameters 'command=["sudo /opt/intake/infra/staging/netgsm_test_otp.sh --last"]'
   ```

The real sign-in flow itself (`POST /v1/auth/otp/request`) needs an App Attest assertion from a
build signed by the team. A command line cannot produce one without weakening attestation, so
there are two routes:

- From the phone, the trigger is the app's own sign-in, with the allow-listed number.
- From the host, the trigger is the command in step 4. It runs the API's own wiring (egress row,
  runtime gate, SMS proxy, OpenBao, test list) without the attestation step.

Either way, the check is the command in step 5.
