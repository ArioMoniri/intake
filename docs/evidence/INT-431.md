# Evidence: INT-431 · The embed sample's JWT fixture is built at runtime

**Epic:** E10-connectors · **Phase:** P1 · **Sec-Row:** connectors · **GitHub:** #733 ·
**Depends on:** INT-320

## Problem

`apps/embed-sample-partner/src/partnerBackend.test.ts` (INT-320 follow-up) kept its synthetic
launch ticket as a JWT-shaped string literal on lines 39 and 41: the `ticket` field, and the
same token again inside `launch_url`. The token is not a credential. Its payload is
`{"tenant":"dev"}` and its "signature" is the text `signature-sample`. Even so, gitleaks' `jwt`
rule matches the shape. The pre-commit hook scans the whole staged diff, so it refuses any
commit that stages the file. That happens to every merge of `main` into a branch cut before
INT-320, and it blocked #481.

## Change

- The test builds the token at runtime. `TICKET_PARTS` holds the header (`{"alg":"HS256"}`),
  the payload (`{"tenant":"dev"}`) and the signature label. Each part is base64url-encoded
  (unpadded) by a local `base64url` helper, and the parts are joined with `.`. `launch_url`
  interpolates the same value. The token at runtime is byte-identical to the old literal, so
  every existing assertion checks the same behaviour as before.
- A new test, `the synthetic ticket fixture (INT-431)`, pins the fixture's shape. The ticket
  has exactly three base64url parts. Each part decodes back to its source, and `launch_url`
  ends in `#ticket=<ticket>`. A fixture that drifted into a non-token would fail there rather
  than quietly weaken the handshake tests.
- No allowlist, no `gitleaks:allow` comment and no `.gitleaksignore` entry was added. The
  scanner configuration is unchanged.
