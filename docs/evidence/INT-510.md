# INT-510 — the patient's send reaches the clinic

GitHub #872 · Sec-Row `review-send` · phase P1 · 16 Oct 2026 · from the INT-498
feature audit (#850, PR #870, findings F07, F08 and F11)

## What was wrong

"Gönder" on the review screen dispatched `{ type: "send" }`, and the reducer set
`status: "sent"`. Nothing left the phone. `offline/sync.ts` said so itself: no
note-sync client shipped. The share centre and the Doctor Link screen then put
the route param into `/v1/visits/{id}/note/…`. That param is the phone's own id
(`v-local-N` from `buildLocalVisit`, or a hospital-feed id), which the server
never issued, so every call was refused (422 for a non-UUID, 404 for an unknown
one). The patient saw "Gönderildi" for a note no clinician could open.

## What reaches the server now

1. **Gönder starts a send; it no longer marks anything sent.** The reducer moves
   `delivery` to `sending` (`src/lib/intake/noteDelivery.ts`). The send CTA is
   unchanged: one dispatch, no `disabled`, no `await`, and the review screen
   still reaches no network (INT-137's `review_send.spec.ts` §5 holds as written).
2. **The session's outbox sends it** (`src/lib/intake/useNoteOutbox.ts`; the
   transport `noteSendClient.ts` is a lazy `import()`, so `session.tsx` stays
   node-importable):
   - it resolves the server visit with `ensureServerVisit(visit, { create: true })`,
     the same resolver the records screen uses, so an upload and a send land on
     one server row;
   - it sends `PUT /v1/visits/{server id}/note` with `status: "sent"`. The body
     carries **exactly the scoped-on sections**; a section the patient turned
     off never leaves the phone. `scopes` names every section the note built
     (`true` shared, `false` withheld), so the withholding is still recorded;
   - the PUT is bounded at 30 s. The note is frozen while a send is in flight,
     so a request that never answers must become a queued send.
3. **"Sent" only on the server's word.** `classifyPut` treats only a 200 whose
   body says `status: "sent"` as delivered. A 200 that comes back as a draft is
   a failure.
4. **The local→server id map lives in the session** (`serverVisits`, ids only,
   memory only, forgotten on every sign-in, sign-out, wipe and kiosk entry), behind one
   resolver, `resolveServerVisit(visitId, { create })`. Every `/v1/visits/*`
   caller goes through it:
   - the Doctor Link: `issueDoctorLinkForVisit`. A visit the server has no row
     for gets "not shared" without a request; an unreachable lookup gets
     "unreachable";
   - the share centre: `loadShareCentre(visit, resolver)`. Revoke uses the
     server id the load resolved, and never the local one;
   - records: the refresh and the upload.
5. **Failure is worded, never swallowed.** Each state has its own line on the
   review screen (`deliveryLine`, catalogue keys `review.delivery.*`, tr + en,
   siz, no imperative, PolicyGuard-clean):

   | outcome | line (tr) |
   |---|---|
   | in flight | Notunuz gönderiliyor. |
   | unreachable, 408/425/429/5xx | Notunuz henüz gönderilmedi. Bağlantı gelince kendiliğinden gönderilecek. |
   | 403 `consent_required` (on the PUT, or on creating the visit) | Notunuz gönderilmedi. Paylaşım için izniniz kayıtlı değil. |
   | 403 age gate (INT-223's three codes) | Notunuz gönderilmedi. Bu hesaptan şu anda paylaşım yapılamıyor. |
   | 401 / no session | `records.err.session` (existing key) |
   | every section scoped off | Notunuz gönderilmedi. Paylaşılacak bölüm seçili değil. |
   | synthetic dev session (no network at all) | Deneme hesabındasınız; not bir hekime gönderilmez. |
   | anything else | Notunuz gönderilmedi. Bir sorun oluştu; yeniden gönderebilirsiniz. |

6. **Offline sends wait in the INT-142 sealed store.** `delivery` is part of
   `NoteState`, so the existing sealed draft mirror persists a queued send with
   the note, and no second store exists. `restoreNote` brings it back queued
   after a restart, and the outbox retries it after `SEND_RETRY_MS` (30 s). A
   send the server *refused* is not retried behind the patient's back. A
   `sent` stored by a pre-INT-510 build has no `delivery`. No such build could
   send anything, so that note is restored as a draft and can now really be
   sent.
7. **The note is frozen while its send is in flight. An edit to a queued or
   refused send cancels it**, so Gönder is pressed again over the note as it
   now stands. This is the "confirm step" control of the `review-send` row.
8. **Server, one line** (`services/api/src/intake_api/schemas.py`):
   `NoteBody.withheld_section_ids` now reads `scopes` rather than `sections`.
   Without this, the smaller body would have recorded the patient's
   withholding as nothing, which would undo INT-304's affirmative record. The
   INT-304 body shape (content sent with its scope off) is withheld exactly as
   before. `test_note_scopes.py` and `test_notes.py` pass unchanged. What
   the clinic reads is still `section_ids` only (fail-closed).

## Invariant 4: verified, not re-implemented

The server already checks the consent scope and audits the share
(`notes.py::write_note`: `ensure_consent(share:previsit_note)`, then
`create_share`, then `api.note.share`). `tests/api/test_note_send.py` drives
that path with the app's own body. These tests passed on the red run, before
any code changed, which shows the server side was already correct and that
this issue does not weaken it:

- with consent: exactly one share, scoped to exactly the body's sections, one
  `api.note.share` entry with `scope:share:previsit_note`;
- a re-send (a queued send retried after a lost response) leaves exactly one
  **live** share;
- without consent: a 403 `{"error":"consent_required","scope":"share:previsit_note"}`,
  no share, no audit entry, no note row (the transaction rolled back), and the
  patient's own GET is 404;
- a Doctor Link after the send: 201 against the server id. Before any send: 404;
- **the near miss**: PUT / issue / list on `v-local-1` give 422 and create
  nothing; a well-formed UUID the server never issued gives 404.

`e2e/sendReachesClinic.spec.ts` §5 pins the order in `notes.py`: the consent
check comes before the share row, and the audit action is present.

## The contract across the boundary

`tests/fixtures/note_send/app_note_put.json` is the one body both sides test.
`noteSend.test.ts` asserts that the app's `notePutBody(...)` **equals** it.
`test_note_send.py` PUTs it. The note answers the complaint and the duration,
answers past surgery, then scopes `pmh` off. The fixture carries
`chief_complaint` and `hpi` and `scopes.pmh = false`, and the word *ameliyat*
appears nowhere in it.

## Out of scope, and what stays blocked

- **Real (OTP) patients are refused today, and the refusal is now worded.**
  HB-L27 (the twenty-one Turkish legal documents, including the `share` and
  `core` consent texts) is open, so no new consent can be granted. Only the
  dev tier's seeded grants exist (`dev_fixture.DEV_CONSENT_SCOPES`). An OTP
  patient's send is therefore refused with the consent line, at the visit
  (`core`) or at the PUT (`share:previsit_note`). That is the fail-closed
  state, not a gap in this issue. The mechanism is built; the content is
  HB-L27's.
- **So no app session completes a send end to end today, and each one says
  why.** The synthetic dev session has no server identity (the app holds no
  dev bearer) and sends nothing. An OTP patient is refused as above. The
  server half is proved with the dev tier's seeded patient, who holds `core`
  and `share:previsit_note`, in `tests/api/test_note_send.py`. The phone half
  is proved over the real records resolver and a mocked `authedFetch` in
  `noteSendClient.test.ts`.
- The draft-reconcile transport in `offline/sync.ts` (pull/push with
  revisions) still has no server home: the server note carries no version.
  That is INT-142's recorded state, and its comment now says the send ships.
- A device-side screenshot of the new states needs a device and a dev
  server with the seeded patient. Nothing in this change alters layout beyond
  one status line under the consent summary.

## Invariants

- **4**: consent is checked and every share audited on the server, verified by
  tests and pinned by the spec. Nothing on the phone gates on consent; the
  phone only words the server's answer.
- **5**: every new string is in `tr` first, mirrored to `en`.
- **6**: ids only, as path segments. No section text, answer or id is logged.
  The id map is memory-only.
- **14**: the note travels only over the DPoP-bound `authedFetch`. At rest it is
  the server's existing envelope.
- **17**: no placeholder, no skipped test, and no mock outside tests. The
  synthetic session sends nothing, rather than faking a send.
- **2**: the new lines are statements. They contain no instruction, no `sen`,
  and pass PolicyGuard.
