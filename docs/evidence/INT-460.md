# Evidence: INT-460 · A second admin approver for synthetic staging

**Epic:** E12-admin · **Phase:** P1 · **Sec-Row:** admin-console · **GitHub:** #785 ·
**Depends on:** INT-180, INT-325, INT-365

## Problem

Owner request, 3 Oct 2026. The four-eyes rule needs a second person, and the synthetic AWS host
has no way to add a real second approver for model-lane switches. The brief proposed a second
INT-197 dev-bearer admin account behind a new `INTAKE_DEV_TOKEN_ADMIN_2`. It also said to
investigate first, and to write only owner steps if an existing path already works.

## Investigation (main `7c6facb7`, open PRs #643, #723 and #751, the deploy branch `int-443-deploy`)

1. **The console never sees a dev bearer.** Every `/admin` route, the model-lane ceremonies
   included, resolves its caller in `services/api/src/intake_api/admin/deps.py::resolve_caller`.
   That function calls `wiring.claims.verify`, the `KeycloakClaimsVerifier` that
   `app.py::_admin_from_env` wires. The dev tier's `auth.py::require_admin` is used only by `/v1`
   routes (`embed/router.py`, `experience.py`, `previsit_output.py`). A dev account has no `sub`,
   WebAuthn credential or session, so it could never stand in a four-eyes actor block.
2. **A dev token stops a staging boot.** `settings.py::refuse_dev_config_outside_dev` (INT-325)
   refuses any non-empty variable with the dev prefix when `INTAKE_ENV` is not dev. The staging
   compose sets `INTAKE_ENV: staging`. Adding the proposed variable to the staging env would
   therefore stop the API, not add an approver.
3. **What runs on the host.** INT-421 (PR #723, `docs/evidence/INT-421.md` §2 on its branch) put the
   console behind Caddy → oauth2-proxy → admin-web → the INT-180 gate, with staff in the Keycloak
   realm `intake`. The realm ships with no users. INT-428 (PR #751) added the model-lane ceremonies.
   Requesters are `platform_owner` and `platform_admin`. Approvers are `platform_owner`,
   `qms_owner` and `compliance_officer`. `approver_must_differ_org` is `False`. The host runs a
   local merge of the two.
4. **What four eyes compares.** `four_eyes.py::_check_distinct` refuses the same `sub`, the same
   WebAuthn credential, the same session, and an approver outside the action's approver roles. It
   checks the organisation only when `approver_must_differ_org` is set (tier 3). A second Keycloak
   user in the owner's org therefore satisfies every model-lane ceremony with no code change.
5. **The prerequisite.** `principal_from_claims` requires `aaguid` and `credential_id`. Stock
   Keycloak writes neither session note (`docs/runbooks/keycloak-realm.md` §3). The provider that
   writes them is INT-378, PR #643. It is open and conflicting, and absent from the deploy branch.
   Until it is live, the console refuses every staff token, the owner's included. A TOTP sign-in
   carries no AAGUID either, which is #644 (INT-389, awaiting the owner).
6. **A wiring gap between two open PRs.** #643 mounts the provider into the dev observability
   Keycloak. #723's staging Keycloak mounts no provider directory. It also imports its realm once
   (`start --import-realm` skips a realm that already exists), so the live realm's second-factor
   execution must also be switched on the running server. Whichever of #643 and #723 merges second
   has to carry both changes. That work is outside this issue's acceptance, and this PR does not
   build it.

## Decision

The existing path is a second Keycloak user, so no product code changes. The brief's
dev-bearer design is rejected, not deferred:

- it would not reach `/admin`;
- it would stop the staging boot.

Making it work would need two changes:

- relaxing INT-325's boot refusal;
- admitting a static bearer at the INT-180 gate, which bypasses the INT-365 second factor.

Both weaken a security gate, and CLAUDE.md sends that to the human.

The brief named the Sec-Row `auth`. `docs/security/threat-model.md` has no such row, and the
linkage gate would refuse it. `admin-console` is the row that INT-180, INT-365, INT-378 and
INT-389 carry.

## Change

- `docs/runbooks/second-admin.md` (14 lines): the owner's exact steps.
  - **Prerequisite:** #643 live, and a WebAuthn second factor for both people.
  - **The account:** a Keycloak user created with `kcadm.sh` over SSM, in the owner's `org`. It
    holds `qms_owner`, the model-lane approver that reaches no patient content and cannot request.
    It holds `platform_owner` only if the person must also request.
  - **The one-time password:** created on the laptop as an SSM SecureString from
    `$(openssl rand -hex 32)`, never printed. The host reads it into a shell variable and pipes it
    to `kcadm.sh update …/reset-password -f -`, so it never appears in an argv or on screen. It is
    marked temporary, handed over once through `aws ssm get-parameter --with-decryption` on a
    private channel, and then deleted.
  - **The approval:** the second person approves on their own key, device and session.
- `tests/admin/test_second_admin_runbook.py`, 15 tests:
  - **The dev tier is not the route.** A dev bearer at `/admin/whoami` gets 401. A second dev admin
    token refuses a staging or production boot, and the error names the variable, never its value.
    The near-miss: the same staging environment without it boots.
  - **Four eyes with two staff in one org.** Two `platform_owner` principals that differ in `sub`,
    credential and session approve each other's request in both directions. A `qms_owner`
    approves the owner's request. Neither person approves their own (`SelfApproval`). The
    ceremony used is the deploy-freeze lift. It is on main and has the model-lane ceremonies'
    shape: the same requesters, and same-org approval allowed.
  - **The runbook.** At most 15 lines. It names INT-378 and #643, and names no dev variable (the
    prefix is read from `settings.DEV_FLAG_PREFIX`, not written into the test). Every
    `--rolename` it grants stands as a second key on a tier-2 action. One parameter name is put,
    read and deleted. The put is a SecureString from `$(openssl rand -hex 32)`.
- The backlog row INT-460, the three pinned counts (330 → 331, with the reason), and a regenerated
  `files/11_ISSUE_BACKLOG.md`.

The `kcadm.sh` and `aws` commands follow their documented syntax and the staff-account steps of
INT-421's production checklist. They were not executed here. No container runtime exists on this
machine, and a change to the live realm is the owner's to make.
