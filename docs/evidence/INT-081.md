# Evidence — INT-081 · IntakeEngine FSM

## Acceptance (verbatim from docs/backlog/issues.yaml)

- [x] "no LLM inside; answered_pending + follow_up_tr semantics; delta mode driven by
  PatientOverlay; must_ask coverage computed"

Tests: `tests/engine/test_fsm.py`. sec_row: `intake-typed`
(docs/security/threat-model.md "## `intake-typed` — the typed parity path"). That row's asset is
*"typed session content, the same clinical state machine minus audio"* — this issue **is** that
state machine, and its threat *"[S/T] prompt injection by typed text"* is answered here by the
one structural fact the module can offer: patient text never reaches the engine at all. The
engine's inputs are a resolved protocol, the session clock and confirmed overlay facts; a
transcript is turned into `slot_updates` by INT-083, one layer out and behind the data boundary.

## What this issue is, and what it deliberately is not

**No clinical content was authored.** No threshold, age boundary, dose, red-flag level or Turkish
patient copy. Every id, slot and Turkish string in `tests/engine/test_fsm.py` is synthetic
(files/04 §7). The authored base pack is INT-043 (`awaiting-human`, HB-C1) and the eight patient
overlays are INT-056; neither is needed, because all four acceptance clauses are mechanisms.

The engine also authors no text at runtime. Every string it hands the Talker comes verbatim from
the resolved slot — `ask_tr`, `confirm_tr`, `follow_up_tr` — and where the author wrote none, the
engine records a gap rather than improvising (CLAUDE.md invariant 10).

## The four clauses, one at a time

### 1. "no LLM inside"

files/03 §5 names the engine *"deterministic protocol FSM — no LLM inside"*. Two assertions, both
structural rather than behavioural:

- `TestNoLlmInside::test_the_package_imports_no_model_or_vendor_client` AST-scans every module
  under `services/voice-runtime/src/intake_voice_runtime/clinical_agent/` for the same twenty
  forbidden import roots `tests/safety/test_triage_engine.py` uses on `packages/protocols`.
- `test_the_engine_has_no_seam_a_model_could_be_handed_through` pins `IntakeEngine.__init__`'s
  parameter set to `{protocol, reference_time, overlay_facts}` and `apply_extraction`'s to
  `{step_id, slot_updates, clarification_needed}` — files/03 §5's own signature. A port parameter
  is how a model gets into a class; there is none, and adding one fails the test.

The engine cannot produce a triage level at all: it holds no rule, imports nothing from
`protocols.triage.engine`, and CLAUDE.md invariant 1 therefore has nothing to reach here.

### 2. "answered_pending + follow_up_tr semantics"

**answered_pending.** `mark_asked` puts a step into `ASKED_PENDING` (files/13 §9.3, *"ask-ahead
bookkeeping"*) and publishes a new `EngineSnapshot`; the next `next_step()` already returns the
step after it. Nothing waits: every method returns immediately, which is the Layer-B half of
ADR-009.

Reconciling behind, three rules that are each a test:

- **Nothing binds to a question that was not asked.** An update whose step is in any state other
  than `ASKED_PENDING` is ignored. Absorbing a neighbouring answer would make the note read as
  *elicited* when it was *inferred* — the failure mode files/13 §9.6 refuses runtime selection
  over — so the engine under-binds by construction.
- **A boolean `false` binds `ASKED_ABSENT`**, the only state files/13 §9.3 lets into
  `ros_pertinent`; every other bound value binds `ASKED_PRESENT`.
- **The ask-ahead race is closed by discarding, never by storing** (files/13 §11.3). When an
  extraction retires a step that is still `ASKED_PENDING`, the step moves to
  `EngineSnapshot.invalidated`, its value is dropped, its queued follow-ups are dropped, and any
  answer arriving for it afterwards is dropped too.

**follow_up_tr.** A clarification becomes a class-3 re-entry (files/13 §9.1, §11.1) whose
`text_tr` is the origin slot's `follow_up_tr`, byte for byte, so it is a clip hit rather than a
TTS miss. It outranks an unasked `must_ask`. Bounded at two attempts; the third clarification
sets the slot `UNCLEAR` and records it in `data_gaps` — *"There is no third attempt."*

Two refusals sit behind this, both at plan build:

- a **required** slot without `follow_up_tr` is refused (files/04 §1; files/13 §11.1 — *"already
  mandatory on every required slot"*). Without it the re-entry would have nothing verbatim to say.
- a slot without `ask_tr` is refused: there is no path to an improvised question.

And one fail-closed at runtime: a **non-required** slot with no `follow_up_tr` that needs
clarification goes straight to `UNCLEAR` and into `data_gaps`. The engine does not invent a
clarification (invariant 10); it records that it could not get the answer.

### 3. "delta mode driven by PatientOverlay"

files/09 §3 lists what Loop 1 changes deterministically: *"confirm-don't-reask; **delta mode** for
follow-ups … full HPI only on change; skip resolved sections; pre-fill with `confirm` steps;
activate patient overlays …"*. Delta mode and overlay-pack activation are **siblings** in that
sentence, both driven by the same object — delta mode is not downstream of activation. So
`decide_delta` reads the `PatientOverlay` directly and does not wait for an overlay pack to exist.

`DeltaMode.ON` iff at least one confirmed, in-date fact whose key names a step in this session's
plan pre-filled that step's slot. The effect, and nothing beyond it:

- the pre-filled step is offered as a `confirm` step spoken from the slot's own `confirm_tr`
  instead of a full ask — files/03 §5 verbatim, *"Prior-record facts pre-fill slots as
  unconfirmed → `confirm` steps instead of re-asking"*;
- the value stays **unconfirmed**: the slot is `NOT_ASKED` with no bound value until the patient
  answers, so it never counts toward coverage and never reaches a rule;
- a confirmation that **contradicts** the pre-fill re-opens the full ask and **binds nothing** —
  files/09 §3's *"full HPI only on change"*. A `confirm_tr` question is not the slot's own
  question, so an answer to it may not be recorded as an answer to the slot;
- **delta mode never removes a step.** It changes a step's *kind*, never the frontier's
  membership, which is how files/04 §2.3's *"they never remove questions clinicians marked
  `must_ask`"* holds without a special case for `must_ask`. A test compares the frontier with and
  without an active overlay and asserts they are identical.

Two fail-closed edges, both toward **asking**:

- a fact past its twelve-month re-confirmation window is **withheld** and does not pre-fill,
  through the same `fact_needs_reconfirmation` predicate INT-258's `activate_overlays` uses, so
  the two cannot drift on what "in date" means. Reported in `withheld_fact_keys`.
- a fact for a slot the author gave **no `confirm_tr`** does not pre-fill: there is no improvised
  confirmation. Reported in `unconfirmable_fact_keys`, and the question is asked in full.

**With no overlay at all** — `overlay_facts=None`, or an overlay whose facts name no step in this
protocol — the decision is `DeltaMode.OFF` with empty pre-fills, and every step is a full ask
from `ask_tr`. There is no default-on path and no way for delta mode to arise from anything other
than a confirmed fact.

`overlay.frequent_attender` (files/04 §2.3, *"delta mode by default"*) is the **content** that
will one day switch a patient into delta mode unconditionally. It is INT-056 and it is not here.
That switch is additive: it turns delta mode on for a patient, and every rule above still holds.

### 4. "must_ask coverage computed" — the definition, stated plainly

`observability/metrics_catalog.yaml` carries `protocol.must_ask_coverage` (gauge, ratio,
`>= 95 %`, `status: planned`) and files/09 §2 makes it one of four conditions for L2. Neither says
what "covered" means. This is the definition, and later issues inherit it:

> **coverage = |covered| / |obliged|**, where
> **obliged** = the `must_ask` steps whose gate is **TRUE or UNKNOWN**, and
> **covered** = the obliged steps whose answer state is one of
> `ASKED_PRESENT`, `ASKED_ABSENT`, `DECLINED`, `CONTESTED`.

Why each half:

- **The obligation set is not invented.** files/13 §9.4 already writes it down for the budget
  governor: `R = |{must_ask steps still unasked whose gate is TRUE or UNKNOWN}|`. A gate that is
  definitively FALSE never obliged anything, so counting it would make coverage fall when a
  protocol correctly skips a branch. UNKNOWN counts, because an undecidable gate is exactly the
  case where the question still has to be put — the same Kleene reading that stops a `NOT_ASKED`
  slot being read as a negative (files/12 §1.1).
- **`DECLINED` is covered.** A refusal is an elicited answer; making coverage penalise a decline
  would put the metric in tension with consent.
- **`CONTESTED` is covered.** Both values reach the note (files/13 §11.2): the question was asked
  and answered twice, which is a coverage success and a reconciliation failure. Conflating the
  two would hide one behind the other.
- **`ASKED_PENDING` is *not* covered, and this is the load-bearing exclusion.** Under ask-ahead a
  step is asked long before anything binds, and files/13 §11.3 permits that answer to be
  *discarded*. Counting a pending step would let ask-ahead inflate coverage with data the engine
  may be about to throw away — and the harm this metric exists to catch is precisely files/13
  §9.4's *"an 18-turn cap that can silently drop a must-ask … the mechanism by which this product
  would generate a note asserting an unelicited negative"*.
- **`UNCLEAR` is not covered.** It is a recorded gap (files/13 §11.1 `data_gaps[]`), which is the
  opposite of coverage.
- **The ratio is a `Decimal`**, four places, rounded **down** — files/13 §9.5, *"no floats
  anywhere"*, and a coverage figure that rounds up overstates the one set the turn budget may not
  silently drop.
- **An empty obligation set yields `None`, not 1.** A session that owed nothing and a session
  that answered everything are different facts, and an L2 gate that averages across sessions has
  to be able to tell them apart.

`must_ask_coverage(states=..., gates=...)` is a pure function of two maps, so it is exercised over
every one of the seven answer states directly, including states the engine cannot yet reach on its
own. `IntakeEngine.must_ask_coverage()` supplies the two maps for its own `must_ask` steps.

The value is **computed and returned**; nothing is emitted. The catalogue row stays `planned`
until the issue that owns metric wiring emits it (CLAUDE.md invariant 13).

## Three places the blueprint disagrees with itself, and how each was resolved

1. **files/13 §9.2 admits `UNCLEAR` back into the frontier; files/13 §11.1 and §9.5 forbid it.**
   §9.2's candidate filter is `S.state_of(s) in (NOT_ASKED, UNCLEAR)`. §11.1 says a slot goes
   `UNCLEAR` after two clarifications and *"there is no third attempt"*, and §9.5's termination
   check requires every turn to strictly decrease `|NOT_ASKED| + |queued re-entries|` — a
   re-offered `UNCLEAR` step decreases neither and nothing in the state changes to make the next
   turn different, so §9.2 as written is a non-terminating loop. **Resolved in favour of §11.1 and
   §9.5:** `UNCLEAR` steps leave the frontier and are reported in `data_gaps`. Asserted by
   `test_an_unclear_step_does_not_return_to_the_frontier` on an *ungated* step, so it cannot pass
   by accident.
2. **files/13 §9.2 spells the retire field `retire_if`; files/03 §5-6 and the DSL spell it
   `skip_if`.** Same field, one name exists. `skip_if` wins — it is the one `protocols.dsl.Slot`
   carries.
3. **files/13 §9.2 reads `s.priority`, `s.order` and `s.gate` off a step, and the DSL has none of
   those fields on a slot.** They are *derived*, not authored: `priority` from `must_ask`
   (class 5) versus everything else (class 7), `order` from the resolved section/slot order which
   files/13 §4 requires to be frozen and versioned, `gate` from `ask_if`. The nine classes of
   §9.1 are declared at their blueprint integers so the issues that own the remaining content —
   the RED action script, the open narrative turn, the armed probe, the instrument block, wrap-up
   — slot in without renumbering an order that is already frozen.

## One capability deliberately not built, and why it is a refusal rather than a gap

files/13 §9.5 gives `GuardExpr` a function whitelist (`age_years`, `sex_at_birth`, `overlay`,
`section_done`, `any`, `count`, `days_since`, `turns_used`, `turns_remaining`, `mode`). It is not
implemented. Gates are read with the **closed `when` grammar** of files/03 §6 —
`protocols.triage.expr.parse_when`, the same parser and the same Kleene evaluator the triage
engine uses, so a step gate and a red-flag predicate can never disagree about what `Unknown`
means. A gate that reaches for the wider whitelist is **refused at build** (`PlanError`), which
fails closed: an unreadable gate stops the pack, it never silently opens. The fixture case is
files/03 §6's own `ask_if: "meds.any(class == DMARD)"`, and the test asserts the refusal.

The turn-budget governor of files/13 §9.4 is likewise not here: the acceptance does not name it,
and `SessionBudget` already exists in `clinical_schemas.session` for the issue that does.
