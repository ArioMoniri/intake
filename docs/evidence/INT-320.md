# INT-320 — Embeddable white-label integration: partner "Start pre-visit" button + tenant handshake (ADR-028)

## 1. What this is, and what it deliberately is not

Vizite becomes embeddable as a service: a partner drops a "Start pre-visit"
button into its own app, the branded Vizite intake runs for that partner's
patient, and the note flows back. The chosen surface is a **signed, single-use,
short-lived launch-ticket handshake** (ADR-028), *not* an embedded Vizite UI in
the partner's origin — the embedded-UI shape would put a PHI surface inside a
third-party origin and make the partner page an injection surface.

This PR is the ADR + a minimal, secure, fail-closed scaffold for ONE dev-tier
synthetic partner tenant. It is **not** a production build:

- no real partner secrets or branding — one synthetic `dev-partner-alpha` tenant;
- no new database table, migration or personal-data field;
- a partner-supplied patient identifier / note-back correlation is **out of
  scope** — linking it is a new personal-data category and a new recipient that
  need human sign-off (§7; docs/backlog/blockers.md INT-320). Built as the
  mechanism only, fail-closed, content empty (invariant 17).

## 3. Design, decided rather than assumed (ADR-028)

- **Trust boundary = the ticket, not the page.** HS256 over the stdlib `hmac`
  primitive `room_tokens` already uses, closed claim set
  `{tenant_id, nonce, iat, exp≤120s, purpose}`, no clinical or personal value.
- **Isolation.** The tenant is bound INSIDE the signature and the signing key is
  the tenant's own (from OpenBao). A ticket minted for tenant A cannot verify
  under tenant B's key, and the verifier also checks the claimed tenant against
  the tenant whose key verified it — there is no free-text tenant field to forge
  (invariant 37).
- **Single-use.** The nonce is consumed **last**, only after signature,
  structure, purpose, clock and tenant all pass — a tampered replay fails the
  signature long before `consume`, so it can never burn a genuine nonce.
- **Branding is data, not markup.** The registry validates six-digit hex
  colours, a bounded display name and id-shaped asset/consent refs; URLs,
  schemes and markup are refused at load — no injection surface.
- **Registry is a second list, fail-closed, zero prod rows** (the ADR-026
  shape). A `prod` row is refused without `dpa_ref` + `brand_permission_ref`.
- **`device_functions` off** for every embed tenant (ADR-020: no CE certificate).
- **Consent** renders from Vizite's own docs/legal flow (fail closed until
  authored), never from the partner. The **note flows back** only through the
  existing connector path (ADR-026) — the embed adds no new outbound PHI path.

## 5. What the tests pin

- Ticket: round-trip; cross-tenant refusal; tamper/expiry/skew/purpose/ttl/replay
  fail-closed; a tampered replay does not burn a genuine nonce; the closed claim
  set (no PHI in the token); the TTL ceiling bounded at mint and at verify.
- Registry: constrained branding (hex colours, bounded name, id-shaped refs;
  markup/URLs/schemes refused); `device_functions` cannot be enabled; a `prod`
  row without recorded DPA + brand permission is refused; the committed file is
  dev-only with no real partner.
- Router/service: admin-only mint; unknown tenant → 404; no signing key → 503;
  unconfigured surface → 503; replay/tamper/malformed → id-shaped 400; audit
  entries `embed.ticket_minted` / `embed.launched` (ids only, `basis:embed-handshake`).
- SDK: only opens an `https` launch URL; never holds a Vizite secret; refuses a
  non-https partner endpoint or launch URL; button renders and starts a handshake.

## 7. What is NOT met — flagged for a human (build fail-closed, content empty)

These are recorded in docs/backlog/blockers.md under INT-320. None is invented;
each mechanism ships wired and fail-closed.

1. **Real partner onboarding + data-processing basis (DPA).** A `prod` embed
   tenant requires an executed DPA and the controller/processor determination.
   The registry refuses a prod row without `dpa_ref`; no engineer may supply it.
2. **Partner branding permission.** Using a real company's name/logo needs
   recorded brand-use permission (`brand_permission_ref`). Only a synthetic dev
   tenant ships.
3. **New personal-data category + recipient (note-back correlation).** Linking a
   partner-supplied patient identifier to a Vizite patient, and disclosing the
   note back to the partner, are a new personal-data field and a new recipient —
   they need the {category,purpose,basis,retention,recipients} inventory and a
   lawful basis. Out of scope here; not invented.
4. **Consent texts for the embed context** must be authored by counsel and hash-
   bound under the tenant's dev legal root (they are unauthored, so the consent
   step fails closed, exactly like INT-038/INT-210).
5. **Production key custody + shared nonce store.** The dev signing key must be
   seeded in OpenBao (dev server); production needs per-tenant key custody /
   rotation and a shared (Redis) nonce store so single-use holds across API
   replicas. The dev path fails closed until seeded.

## Follow-up (INT-320 continuation) — dev consent step made to render end-to-end

Scope: resolve the fail-closed-empty state INT-320 shipped so the dev-tier
partner embed flow (`dev-partner-alpha`) works END-TO-END in LOCAL dev —
mint → launch → **consent render** — without inventing counsel-vetted content.
This references INT-320 (it completes its mechanism); no new INT id was minted
(INT-320 is the highest id on main and the fail-closed state is exactly what it
left).

### What was built
- **Consent render (the missing step).** `POST /embed/v1/consent` (marker
  `partner_embed`, caged to `/embed`) turns a launch's `consent_doc_set_id` into
  the hash-bound documents the branded intake must show. The set is two docs:
  `core` — the standard service consent, loaded from the SAME global consent
  catalogue a later `POST /v1/consents/grant` binds against (so what the patient
  reads and what is recorded can never drift) — and `partner_processor`, the
  per-tenant partner-processor disclosure (aydınlatma, shown never granted),
  loaded from the tenant's own `legal_root`. DB-free core:
  `packages/intake_platform/embed/consent.py`; hash-binding helper
  `intake_platform.consent.texts.bind_legal_document` (same whole-file SHA-256 as
  INT-038, without the closed-registry `resolve_scope`, for a disclosure).
- **Fail-closed.** Either document unauthored → empty set → `503
  embed_consent_unavailable`. A doc-set id that is not the one bound to the
  tenant's row is refused (no cross-tenant peek). Mint still `503`s without the
  OpenBao signing key.
- **Dev signing key.** `scripts/dev/seed_embed_dev_key.py` seeds the dev
  tenant's key into the local dev OpenBao at the ref the registry records
  (`embed/dev-partner-alpha/signing-key`, i.e. KV `secret/data/embed/
  dev-partner-alpha/signing-key`). Dev-tier only (refuses `INTAKE_ENV=prod` and
  any non-dev row); the key is generated locally, written to OpenBao, and never
  printed or committed. Idempotent.
- **Dev consent texts (NOT in the repo).** Authored under the dev-legal tree
  (outside the repo, never committed), clearly marked dev, not counsel-vetted:
  `~/.config/intake/dev-legal/embed/dev-partner-alpha/partner_processor.tr.md`
  (B1 Turkish, register `siz`) plus a `README.dev.md`; the `core` consent reuses
  the existing global dev text `~/.config/intake/dev-legal/consents/core.tr.md`.
  The committed counsel tree `docs/legal/embed/dev-partner-alpha/` stays empty
  (HB-L27).
- **Prod/dev parity.** The render always reads the tenant's `legal_root`;
  `embed_disclosure_root` swaps the `docs/legal/` prefix for the dev-legal base
  (derived from `settings.legal_root.parent`), so the same code reads the
  committed tree in prod and the dev tree locally.
