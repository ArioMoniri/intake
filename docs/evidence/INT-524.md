# INT-524 — CI cancels a pull request's superseded runs

GitHub #890 · Sec-Row `cicd` · phase P1 · 16 Oct 2026

ci.yml and security.yml had no concurrency group. Each push to a PR branch
queued a full new run of both workflows, and the superseded run stayed queued.
That includes every merge-from-main sync that the backlog count pins force. The
three ephemeral `intake-aws-ci` runners (INT-467) spent hours on heads nobody
would merge, and the deploy chain waited behind them.

`.github/**` is owner-only, and `.github/workflows/security.yml` is
hook-protected (07 §3.8, §F rule 2). The workflow change is therefore an owner
patch with a commit-message file. This branch commits the test, this evidence
and the backlog row.

## GitHub's semantics

Source: "Control the concurrency of workflows and jobs",
<https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency>.
It was read on 16 Oct 2026 (`curl -sSL`, HTTP 200). The fetched HTML has
sha256 `977e754bcb85d00b1b15ac1414709517434798ad970e4c52b798e3f5ebbff9a5`.
The page says, in summary:

1. A concurrency group holds at most one run in progress.
2. With the default `queue: single`, at most one run of a group waits. A newly
   queued run cancels the waiting one and takes its place, whatever
   `cancel-in-progress` says. In the page's words, "any existing pending job
   or workflow in the same concurrency group will be canceled".
3. `cancel-in-progress: true` also cancels the run in progress. It may be an
   expression over the allowed contexts.
4. Group names are case-insensitive and shared by every workflow in the
   repository. The page recommends building the group from `github.workflow`
   so that one workflow cannot cancel another.
5. `queue: max` lets up to 100 runs wait, and it cannot be combined with
   `cancel-in-progress: true`.

Point 2 decides the design. A `cancel-in-progress` that is false on push is
not enough to keep a push to main from being cancelled. While main's run waits
for a runner, any other run that joins its group replaces it. A push run must
therefore have a group that no other run can join.

## The block

Both workflows get the same workflow-level block, after `permissions:`:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.sha }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

| run | group (ci.yml) | cancel-in-progress |
|---|---|---|
| PR 7, first push | `ci-7-refs/pull/7/merge` | true |
| PR 7, next push | `ci-7-refs/pull/7/merge`, which cancels the first | true |
| PR 8 | `ci-8-refs/pull/8/merge` | true |
| push to main at A | `ci-<A>-refs/heads/main` | false |
| push to main at B | `ci-<B>-refs/heads/main` | false |
| v* tag on A (security.yml) | `security-<A>-refs/tags/v1.0.0` | false |

**Why the ref, beyond the issue's key.** The issue keys the group by workflow
plus PR number, falling back to the sha. That is exact for ci.yml, but
security.yml also runs on `push: tags: ["v*"]`. Release signing (the `sign`
job, read back by `services/probes/src/intake_probes/ops_cicd.py`) runs from
that tag push. Without the ref, a tag on the commit main just pushed shares
main's group (`security-<A>`):

- If main's run is still waiting for a runner, which is the usual case with
  three runners and a backlog, the tag run replaces it. The push to main is
  cancelled.
- If main's run is in progress, the tag run waits. A second tag on the same
  commit then replaces the first tag's waiting run, and that release is never
  signed.

The ref gives each tag, and main, its own group. Inside a PR, the ref
(`refs/pull/N/merge`) is constant, so the PR's runs still share one group.

## What the test pins

`tests/ci/test_workflow_concurrency.py` (new; the neighbouring files sit near
the 500-line limit):

- In both workflows, the workflow-level block is exactly that group and that
  `cancel-in-progress`, with no `queue` key and no job-level `concurrency`.
- A small model evaluates the block's expressions for seven runs that GitHub's
  `github` context would describe:
  - two pushes to PR 7;
  - PR 8;
  - pushes to main at A and B;
  - two v* tags on A.

  It asserts the following:
  - a PR's runs share one group and cancel in progress;
  - two PRs do not share a group;
  - a push to main never cancels in progress;
  - no other run joins main's group;
  - two tags on one commit do not share a group;
  - ci.yml and security.yml never share a group.

  The model implements only property paths, `||` and `==` with a literal,
  which are the shapes the block uses. Anything else raises. Strings compare
  without case, and groups compare casefolded, as GitHub does.
- Each workflow may fire only on `pull_request` and `push`. Any other trigger
  fails the test until a scenario covers it.
- Near misses, each caught with a named finding:
  - the issue's ref-less group (security.yml: main shares its group with the
    tag);
  - `cancel-in-progress: true`;
  - an inverted condition;
  - a ref-only group (main pushes share a group);
  - a sha-for-PRs group (a PR's runs never meet);
  - a workflow-only group;
  - no workflow prefix (ci and security collide);
  - a missing block;
  - a `queue: max` key;
  - an unmodelled `workflow_dispatch` trigger;
  - an expression outside the model.

## Effect on the runner pool and the consoles

- **A cancelled job leaves nothing behind.** Cancelling an in-progress job on
  an ephemeral runner ends the runner process. `infra/ci/aws-runner/cycle.sh`
  calls `cleanup` after every `systemctl start --wait` returns, whatever the
  job's result. `cleanup` removes the runner daemon's containers, volumes,
  networks and build cache, plus stray processes and the runner tree. The
  runner then registers again. A cancelled check-integration cannot leak
  ports or containers into the next job.
- **The consoles read only runs that are never cancelled.** `ops_ci.py` and
  `ops_cicd.py` read main-branch and tag runs only. `cancelled` was already a
  known conclusion there.
- **Required checks are per head sha.** A cancelled run on a superseded head
  does not gate the current head.
- **Known behaviour.** Re-running a superseded PR run puts it back in the PR's
  group, and with `cancel-in-progress` it cancels the current head's run in
  progress. Re-run the newest run instead.
