# INT-521 — the live voice and typed session evaluates triage on every bound answer, so a RED fires from the conversation

GitHub #887 · Sec-Row `clinical-core` · phase P0 · 16 Oct 2026 · Stacked on
INT-518 (#884, local head `d7f8bf3b`), itself stacked on INT-441 (#750)

**Acceptance, verbatim from GitHub #887:**
- "Every completed Work that binds a slot read by a served red-flag rule
  triggers a rules-engine evaluation (packages/protocols/triage only;
  invariant 1); a RED result reaches the existing RED path (pre-positioned
  script over the data channel, priority preempt only from the rules engine;
  invariants 9, 21)." — **met.** The Work queue evaluates after every
  state-lane Work that bound or changed an answer a served rule reads, through
  `protocols.triage.evaluate_triage` alone. The RED it returns goes through the
  queue's existing derivation (`preempt` only from a rules-engine RED), the
  preempt gate, the clinician route and the seal. The Talker drains it on its
  next turn, hands it to the existing `RedPreemption` path (cancel, then the
  rule's pre-positioned script over the data channel) and asks nothing more.
- "The Talker never awaits the evaluation (fake-clock test)." — **met.**
  `test_the_talker_never_awaits_the_evaluation`: with Layer B stalled 30
  virtual seconds before it evaluates, the turn costs exactly what it costs
  with Layer B instant, and the evaluation has not run when the turn returns.
  The Talker holds no evaluator (structural test) and keeps exactly six tools.
- "End-to-end test over the committed base.intake + base.life_threat on both
  profiles: a chest-pain character or radiation answer alone yields RED at the
  rule's register and location; near misses do not." — **met**, widened by
  the orchestrator from the INT-518 clinical review: all six cardiac literals
  of `rf.chest_pain_cardiac_features` (`baskı`, `sıkışma`, `ağırlık`, `kol`,
  `çene`, `sırt`), each alone, under all three locations (REMOTE, ON_SITE,
  UNKNOWN) on both profiles, 36 cases, each asserting the rule's own action
  for that location. Under ON_SITE the 112 affordance is absent
  (`show_112: false`, no "112" in any of its strings) and the action carries
  `notify_staff_immediate: true` (the server-side staff entry is #855, INT-475);
  under UNKNOWN the one question with the rule's own branch targets. The near
  misses are every other pair of committed choices (8 pairs, both profiles).
- "make safety, runtime-sim (both profiles, PARITY=1) green." — **met**, see
  *Gates*.

Every answer bound. The rules engine, run over the same answer state, says
RED for the character answer alone and for the radiation answer alone. Nothing
in the session ran it: no Work carried a determination, nothing preempted, the
queue did not seal, and the Talker's next turn asked the next question. Two
further joints were open behind that one:

1. `TalkerSession.accept_result` recorded a preempt in `preempts` and nothing
   delivered it; only tests called `deliver_preempt`.
2. Composition never bound `TalkerSession.preemption`, and handed the queue the
   caller's `rule_ids` (empty by default), so a RED from the session's own
   rules would have been refused by the preempt gate and the Work failed.

| Change | Where |

## Round 2 — runtime review

The runtime review (16 Oct 2026) blocked round 1 (`fc3289f4`) on one defect and
named three ways a RED could still be lost. All four are fixed here.

**The blocker: the RED fired only on a turn with no transcript.** `take_turn`
called `submit_utterance` before `drain_results`. The Work that produced the
RED had sealed the queue, so the patient's next answer made `submit` raise
`QueueSealed` before the drain ran: no trigger on the data channel,
`red_stopped` false, the RED left in the queue. Round 1's tests missed it
because every delivery turn was `take_turn(None)`. The reviewer's probe on
`fc3289f4`, both profiles:

```
raised: QueueSealed published: [] red_stopped: False preempts: 0
2 failed
```

**The three RED-loss paths:**

1. A handler that returned any `triage_update`, GREEN included, skipped the
   evaluation, so the engine's RED was masked.
2. An evaluation that raised became an ordinary failed Work (only
   `work_failed_total`). The answer stayed bound and nothing evaluated it
   again, so the RED was lost quietly.
3. A `DEFERRED_CLINICIAN` RED sealed the queue while the intake ran on, so
   every later answer raised `QueueSealed`.

### What changed in round 2

| Change | Where |
|---|---|
| `take_turn` drains Layer B and delivers every RED before it submits, and returns `INTAKE_STOPPED` before the submit once the intake has stopped. If `submit` still raises `QueueSealed` (a RED sealed the queue between the drain and the submit; `_settle` puts it in the results before `_seal`), the turn drains and delivers again; a seal with no RED behind it is raised. | `talker/session.py` (`_drain_and_deliver`) |

## Residuals (no id minted; for the orchestrator)

1. **The Talker drains Layer B only when it takes a turn.** A RED evaluated
   between turns is delivered at the next one. The budgets are measured from
   the evaluation, so a late drain is a loud `RedPathViolation` after delivery
   (pinned), not a silent pass, but nothing yet pushes a RED from Layer B to
   Layer A between turns. files/02 §8.2's 300 ms from rule evaluation is only
   held when a turn follows the evaluation promptly.
2. **No production `RedDataChannel` or `RedScriptIndex` exists in the runtime.**
   Composition takes both from the caller, and no in-tree caller composes a
   session over a served set (none exists while HB-C1 is open). The API
   (#766) mints script ids as `<rule_id>.<location lower-case>`; a shared
   function in `packages/protocols` for that id, used by the API catalogue and
   the runtime's index alike, would stop the two drifting.
3. **The location is fixed for the session.** A patient who checks in
   mid-session, or answers the UNKNOWN question, does not move the runtime's
   axis; #766 and #855 handle that answer on the API side for the app hop.
4. `chest_pain.onset_at` choice-to-date resolution (CD-05) is INT-522 (#888).
5. Named by the runtime review as follow-ups the orchestrator files:
   `live_triage` leaves a read it cannot resolve to a step reading Unknown with
   no signal; `IntakeEngine.answered()` drops `CONTESTED`; the RED path's
   cancel has no timeout (INT-520); a served-rule refusal has no signal of its
   own; a result accepted mid-drain can be lost when an earlier one raises.
6. In the race the round-2 catch covers (a RED seals between the drain and the
   submit), the transcript was deposited in the session's vault before
   `submit` raised; it stays there, in memory and unreferenced, until the
   session ends.
