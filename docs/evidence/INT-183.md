# Evidence — INT-183 · Models & self-hosting registry module + release gate surface

- **Epic/phase:** E12-admin · P0 · `sec_row: self-hosting` · `legal: G2019-12`
- **Depends on:** INT-022 (self-hosting registry + release gate), INT-180 (admin shell)
- **Acceptance, verbatim:** "registry rendered; benchmark trigger; red cell blocks release visibly"
- **Named test:** `apps/admin-web/e2e/models.spec.ts` (+ `tests/admin/test_models_module.py`)

## What was built, and the one decision that shapes it

`apps/admin-web` did not exist. This issue creates it as the second TS
workspace package, holding one module: the files/08 §148 *Models &
self-hosting registry*. It is built inside the INT-180 shell rather than
beside it — the two routes are `AdminRoute` descriptors in `ADMIN_ROUTES`, so
they inherit that issue's structural properties whole: a route cannot exist
without an audit action, the audited-route list stays derived from FastAPI's
own table, and the mutating route resolves to a registered `DangerousAction`.

The decision everything else follows from: **the console renders the registry,
it does not keep one.** `GET /admin/models` is a projection of
`observability/registry.yaml` through `intake_probes` — the same package that
runs the 60-second sweep and evaluates the release gate. `intake-probes`
became a declared dependency of `intake-api` for exactly the reason INT-241
declared `intake-metrics`: a second implementation of a gate is a gate that
disagrees with itself on the day it matters (invariant 13).

## "red cell blocks release visibly" — how it is held

This is the clause that is easy to fake, so it is worth being precise about
what is asserted and what would have to break for it to pass falsely.

**Red is not a colour, it is the gate's verdict.** A cell is
`CellSeverity.BLOCKING` **iff**
`intake_probes.gate.evaluate_release_gate` names its component — the INT-022
function, called, not a second implementation. `test_the_decision_is_the_
int_022_gate_not_a_second_implementation` asserts the two lists are equal
element for element, so a divergence is a failure rather than a drift.
files/08 §6's rule has two arms — *"`self_hostable=false` or no healthy
fallback"* — and the first is honoured by being **unreachable**:
`RegistryEntry` already refuses a `phi_path` row that is not `self_hostable`,
so that state cannot be written down in the first place.

**The block is visible.** Each blocking component contributes a `BlockReason`
carrying the gate's own sentence, the row gains a `release_blocked` finding
with the same text, and the console's release tile lists them. The spec
asserts every reason line names its component and is longer than a label.

**The block is load-bearing, not decorative.** `releaseControl.enabled` is
`false` while any cell is blocking, and `renderModelsModule` **throws**
`InconsistentReleaseState` when handed a payload claiming an unblocked release
over a blocking cell. A stale tab, a cached body or a tampered response cannot
buy a green console: the block is only "visible" if it cannot be rendered away.

**The near-miss negative control.** `tests/fixtures/registry/amber_only.yaml`
is a registry in which every enabled PHI-path row *has* a healthy self-hosted
fallback, so the gate returns nothing — while one row's licence has never been
read from a raw LICENSE blob and another is a declared-but-not-running
PHI-path row. Both render amber, both are loud, **neither blocks**. On the TS
side the same control runs by demoting the live payload's blocking rows to
`attention` and asserting the release control comes back to life.
`test_amber_fixture_is_genuinely_amber_and_not_merely_unprobed` guards the
control itself: if the fixture ever went all-green the near-miss would pass
vacuously and prove nothing.

Without that pair, an implementation that blocked the release on *any*
imperfection would satisfy "red cell blocks release" — and would be useless,
because nothing would ever ship and nobody would learn anything from the
colour.

## "benchmark trigger" — what it does, and what it refuses

`POST /admin/models/{component}/benchmark` resolves a benchmark **plan**:
which component, which probe, which `budget_ms`, and the *named basis* any
resulting measurement would carry. It answers `state: "planned"`,
`executes: false`, and it runs nothing.

Two lanes, kept apart on purpose:

- **`latency`** plans. It is an operational measurement of our own deployment
  against a declared budget over a synthetic probe payload — no patient data
  (invariant 6), and not one of the figures invariant 20 governs
  (sensitivity, specificity, AUROC, WER, accuracy).
- **`quality`** refuses, always, with `no_named_corpus`.
  `intake_probes.console.BENCHMARK_CORPORA` ships **EMPTY**, the same
  fail-closed shape INT-180 gave its `ip_allowlist` and tenant `deployments`.
  **HB-C10** (*"a 3–5 h Turkish spontaneous clinical-speech eval set … highest-
  value open task in the project"*) and **HB-A13** (*"name a records eval
  corpus, and say where it may live"*) are both open. A corpus id invented here
  to make the lane light up would be the invented value invariant 17 forbids,
  and a WER produced over an unnamed set is precisely the accuracy claim
  invariant 20 exists to prevent.

Both lanes are rendered on every row, the disabled one carrying its reason. A
control that is simply absent reads as "not applicable here"; a control that
is present, dead, and says why reads as "somebody decided this" — which is
true, and the decision is HB-C10's to reverse.

The action is registered as `admin.models.benchmark.run`, **tier 2,
DANGEROUS**, with `docs/runbooks/model-benchmark.md` and a catalogued alert.
Tier 2 rather than tier 1 because nothing about running a benchmark moves the
system toward the *less* capable state, and §8.2's asymmetry exists to stop a
tier being chosen to fit the surface rather than the risk. The two keys guard
**execution**, and no benchmark runner exists in this repository for them to
guard — so the approve half lands with the runner rather than as a ceremony
over a no-op, which is the same reasoning `actions.py` already gives for the
eighteen §8.2 rows it does not carry.

### Invariant 20 has teeth on both sides of the wire

`Measurement` — Python and TypeScript — cannot be constructed or rendered
without a non-empty `corpus` and a date. `renderMeasurement` throws
`UnlabelledMeasurement` rather than returning text. There is no second path
from a number to this page, which is the only way an unlabelled figure is
actually prevented rather than merely discouraged.

## The fixture is a recording, not a mock

`apps/admin-web/e2e/fixtures/models.payload.json` is the body the API serves,
emitted by `make admin-fixtures`. A hand-written mock would have been the
second, hand-kept copy of the self-hosting registry that invariant 13 forbids
— it would keep passing on the day the registry changed and the console
stopped matching it. `TestFixtureIsRecordedFromTheApi::
test_committed_fixture_matches_the_served_payload` holds the committed file
against the live response, so the fixture cannot silently rot: change the
registry without re-recording and the Python lane goes red.

## Findings

**F1 — `whisper-tr-medical` has no verified licence, and the console now says
so on every load.** `observability/registry.yaml` records
`license: "UNVERIFIED (card tag apache-2.0, no blob)"` for
`turkmedstt/whisper-large-v3-turkish-medical@0e74ec8`, a `phi_path: true`,
`self_hosted_now: true` row. It is the only row in the registry whose licence
rests on a model-card tag rather than a raw LICENSE blob, which is exactly
what files/03 §4.9.0 rule 3 and invariant 19 refuse. This issue does not fix
it — reading a blob is not an agent's call to make against a repo it cannot
verify provenance for — it **surfaces** it as a standing
`licence_not_verified_from_blob` finding. Reported, not repaired.

**F2 — the model rows that predate INT-243 carry no machine-readable pin.**
`qwen3.5-9b`, `whisper-tr-medical` and `freya-tts` record their
`model_id@revision` as prose inside `host`; only `voxcpm2-tts` fills the
`model_id` / `revision` / `weights_sha256` block. The console therefore renders
`pin: null` for three PHI-path model rows. `registry.py`'s own docstring names
this and says backfilling is its own issue; the console makes the gap visible
per row instead of hiding it behind a host string.

**F3 — no surviving `cascade_fast` / `s2s_cloud` defect.** Swept every tracked
file. Every hit is either `files/` (the blueprint's historical record,
allow-listed), an ADR or evidence file recording the deletion, or a test
asserting the identifiers do **not** resolve. Nothing in shipped code
references either.

## What this issue deliberately does not do

- **No benchmark runner.** Building one would mean dialling the team GPU
  server from the API. The trigger plans; execution arrives with the runner
  and the ceremony that guards it.
- **No `enable/disable`, `set fallback order` or `pin version` controls.**
  files/08 §148 lists them beside "run benchmark". Each writes to the registry,
  which is a signed, committed artefact and a release-gate input; a console
  that edits it needs its own tier-2/3 ceremony and its own issue. A button
  wired to nothing is a control in name only (invariant 17).
- **No live telemetry.** ADR-015: *"the console is mock-data in P0 and
  real-telemetry from INT-181 on."* The sweep is read from
  `INTAKE_PROBE_RESULTS_PATH` when one exists and is **empty** in a dev
  checkout — which makes every enabled row's own probe read *"no probe result
  in this sweep"* and makes the gate block on any fallback whose health is
  unobserved. That is the fail-closed direction: an unobserved fallback is not
  a healthy one.
