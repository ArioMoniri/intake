## The Doctor Link QR decision

**Nothing was built, deliberately.** The QR is in the issue title and in none of the acceptance
clauses, and the honest reason not to build it is a dependency, not a preference:

- **INT-150** — *"Doctor Link: 128-bit token + OTP + expiry + view limit + revoke + watermark +
  access log + no-index"* — is `status: todo` in `docs/backlog/issues.yaml`. INT-137 does not
  depend on it.
- There is **no redemption route to point a code at**. `services/api/src/intake_api/app.py`
  registers visits, notes, documents, otp, consents, profile, taxonomy, dsar, satisfaction,
  notification-prefs and experience. `GET /share/{token}` (files/03 §6) does not exist, and neither
  does any token issuer.
- files/ specifies the *link* (`intake://doctor-link/{token}`, files/02 §4; the connector, files/03
  §12) but **not the redemption flow** — who mints the reference, what the clinician presents, and
  where the consent scope is evaluated on redemption.

So building a QR now would mean inventing the payload, and the payload is exactly the thing that
becomes load-bearing the moment it ships. The rule it would have to satisfy is stated in the screen
and enforced by the spec: a QR must carry an **opaque, short-lived reference the clinician redeems
against the API under their own auth, with the consent scope checked AT REDEMPTION** — never
clinical data, never a bearer token, never the scope encoded in the code itself.

What was built instead is the negative control (`spec §7`): the review surface and the CSAT prompt
must construct no URL, no `intake://` link, no token and no QR payload, and must not
`JSON.stringify`, base64 or URI-encode the note. That control already fired once during the red
runs, so it is not decorative.

**Consequence, stated so it is not read as delivered:** the *"Doctor Link QR"* half of the issue
title is **not delivered by this PR**, and the issue's acceptance — which does not name it — is.
Whoever lands INT-150 owns the QR, and this file is the record of the constraint it inherits.

## CSAT and KVKK-5 — no blocker, and no new data field

**The purpose already exists and was not invented.** files/06 §2's closed list names `satisfaction`
outright. INT-132 mirrors it in `src/lib/consent/purposes.ts` (açık rıza, `ui: "toggle"`,
`defaultGranted: false`, no cascade children, unbundled), and INT-240 declares it on both
satisfaction routes as `require_scopes(SATISFACTION_SCOPE)`. HUMAN_BLOCKERS Rule 2 does **not**
apply: nothing here is waiting on a human to name a purpose.

**Invariant 18 needs no new inventory annotation, because no new data field is created.** The shape
the prompt collects is INT-240's landed `csat.v1` — `score` (1–5) and `reason` (the five-value
enum), nothing else. `CSAT_REASONS` is pinned against
`packages/clinical-schemas/src/generated/models.ts` `CsatReason` by the spec, so the app cannot
drift a sixth reason into existence. No free text is offered at all on this surface, which keeps the
`csat_texts` path (redaction baseline + envelope) entirely on the server side where INT-240 put it.

**The gate is the render, and it fails closed.** `csatCollectable(ledger)` asks the INT-132 ledger
for an *allowed* `satisfaction` grant; without one `CsatPrompt` returns `null` and there is no
question, no tap and no state. Pinned three ways: a fresh ledger is refused, a ledger with the text
loaded but ungranted is refused, and granting a *different* purpose (`voice`) does not open it —
that last one is the anti-bundling control.

**Standing consequence, and it is the correct one:** `satisfaction` cannot actually be granted in
the shipped shell today, because the consent **texts** do not exist — `docs/legal/consents` is
**INT-210** (owner + counsel), and the ledger refuses a grant with no loaded, hash-bound text. So
the CSAT surface is built, wired and unreachable until INT-210 lands. That is the mechanism built,
the gate wired, failing closed, with the content left empty — not a defect of this issue and not a
reason to widen anything.

**Invariant 20** is held by absence and by a test: no score, average, rate or target is rendered
back to the patient, and the spec scans every `csat.*` catalogue key for a figure.

## Findings — reported, not worked around

### F1 · `csat.v1` requires a reason, so "one-tap" cannot form an event on one tap

02 §5.4 calls this *"one-tap"*. INT-240's landed schema makes `reason` **required**
(`CsatIn.reason: CsatReason`, no default; `CsatV1.reason` likewise). A score on its own is therefore
not a submittable `csat.v1`.

Resolved the only honest way: the one tap **is** honoured in the UI (the score is recorded and the
reason chips appear), and `csatResponse()` returns `null` until both parts exist. No reason is
defaulted or inferred from the score — a defaulted reason would be an invented data point sitting in
an analytics table that nobody could later tell apart from a real one. Pinned in spec §5.

Whoever owns the divergence (02 §5.4 vs INT-240) should decide whether `reason` becomes optional or
the spec stops calling it one-tap. Not decided here.

### F2 · The app holds no intake-session id, so the CSAT cannot be posted

`POST /v1/sessions/{id}/csat` is keyed on an intake session. The mobile app has no such id and no
way to obtain one: `/v1/visits/{id}/sessions` (files/03 §6) is not implemented on
`services/api`, and `lib/livekit/token.ts` reaches `/v1/visits/{id}/voice-token`, a route that also
does not exist server-side. The answer is therefore held device-locally, which is the same posture
the whole INT-179 note pipeline already has (in-memory, `src/lib/session.tsx`).

Not fixed here: adding a session route is `services/**` work and outside this issue's fence and
acceptance. `CsatPrompt` deliberately contains no client seam for it — a submit path that could
never be called would be a placeholder with a nice docstring, and invariant 17 forbids exactly that.

### F3 · Invariant 4 — the mobile send is device-local, so the app's UI is currently the only place scope is applied

`updateNote(visitId, { type: "send" })` reaches no API; nothing leaves the device. The enforcement of
record is untouched and unweakened, and it is server-side:
`services/api/src/intake_api/notes.py` checks `ensure_consent(… SHARE_SCOPE …)` before creating a
share, writes only the scoped-on section ids into `shares.scope_sections`, filters a clinic-side read
through `_shared_ids`, and hash-chain audits `api.note.read` / `api.note.write` / `api.note.share`.

So invariant 4 is satisfied by the system, and **not** by the app in isolation — which is exactly the
thing the issue asked to be reported rather than assumed. Wiring the app to
`PUT /v1/visits/{id}/note` is not in INT-137's acceptance and was not done; it belongs with whoever
takes the mobile↔API note transport.

### F4 · The share ledger cannot express every scope the UI offers

`intake_api.schemas.SectionId` is `chief_complaint | hpi | medications`. `buildNote` emits those
plus `allergies`, `pmh`, `family_social`, `device_health` and `deferred` — every one of which the
patient can scope off in the UI. Spec §8 measures this from the app side and pins it: for the
fixture note, `allergies` is a scope the patient can set and the ledger has no literal to carry.

This is the drift INT-084's evidence flagged from the engine side (*"`buildNote` emits two section
ids that are not files/04 §5 note keys"*), now with a third case and a patient-visible consequence.
It is a schema question — files/04 §5 and INT-197 — and **was not widened from the app**, as the
issue brief required. A test holds the current set so the gap cannot grow silently.

### F5 · The Doctor Link expiry is stated, not enforced

`review.consent.untilValue` states 02 §2's rule — sharing ends 72 hours after the **appointment**,
which is the whole point of that section (*"pinned to `visit_datetime + 72 h`, never
`issue_time + 72 h` … the single most likely cause of 'the doctor couldn't see it' at P1"*). The
device computes no timestamp at all: it holds a visit **date**, not a datetime, so anchoring
arithmetic here would have meant inventing a time of day. `src/lib/intake/share.ts` reaches no
`Date`, and the spec pins that by absence.

The mechanism that actually expires anything is INT-150's, and it has not landed. The copy is a
statement of the product rule, and it is written down here so nobody later reads it as a promise the
app enforces.

## Two disclosed design choices

**1. `e2e/consent.spec.ts` pins that the review flow does not import the consent ledger.** It still
does not: the `satisfaction` gate lives inside `src/components/CsatPrompt.tsx`, which owns it
end-to-end, and `review.tsx` imports only the component. That is better design than threading a
ledger read through a note screen — one module owns one gate — but it is disclosed rather than left
for a reviewer to notice, because the pin's original intent (INT-132's rollout did not disturb the
existing flows) is now narrower than it reads: the review flow *does* contain a consent-gated
element, one component down.

**2. Sending no longer navigates away.** 02 §5.4 puts the status timeline and then the CSAT question
*after* send; with `router.replace()` in the handler there was no after-send surface on this screen
to put them on. The patient now stays on the review screen, sees the ladder move to *Gönderildi*, and
leaves by the top bar's back affordance when they choose to (design pass 6 guarantees every pushed
flow carries one). The visit detail still renders the same ladder; nothing was removed from it.

## What could not be verified, and why

- **Nothing was seen rendered.** No simulator, no emulator, no Docker, Expo cannot run in this
  container. Every claim about the screen in this file is a claim about what the source *declares* —
  the layout, the colours, the tap behaviour and the VoiceOver rendering of the new card and the two
  radiogroups are **unverified** and are named as such.
- **The vitest lane has no renderer**, so no test here mounts a component, fires a press or observes
  a re-render. `CsatPrompt`'s consent gate is proved on the pure predicate it calls and on the source
  fact that it calls it; that it returns `null` *on a device* is not proved.
- **The CSAT round trip is unexercised end to end** (F2): no test posts to
  `POST /v1/sessions/{id}/csat` from the app, because the app cannot address a session.
- **`make check` / `make safety` / `make security` were not run.** They are outside this iteration's
  fence and the container has no Docker; the gates that touch what this change wrote were run
  individually and are recorded above.
- **The 2.0-rung reachability of the new cards is modelled, not measured.** `scroll-containers.test.ts`
  and `e2e/large-text-overflow.spec.ts` both stay green with the new copy in `review.tsx`, and both
  files say plainly that their layout is a model and a floor rather than a device measurement.
