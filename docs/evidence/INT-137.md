| Acceptance clause | Where | Held by |

| status timeline | `StatusLadder` in the sent branch; the route replace removed | spec §3 |
| never blocks send | no `disabled`, no branch, no await, no network on the whole surface | spec §5 + three mutants |

Three details worth naming, because each is a decision rather than a default:

- **The expiry is an anchor, not a countdown.** 02 §2 pins the Doctor Link to
  `visit_datetime + 72 h` and calls `issue_time + 72 h` the single most likely cause of *"the
  doctor couldn't see it"*. The device holds a visit **date**, not a datetime, and the clock
  belongs to whatever issues the link — so `share.ts` reaches no `Date` at all and the string
  carries no numeral. A test pins the absence.
- **The consent summary reads `sentSections`, the same function the send path reads.** A
  second traversal of `scopes` would be a second source of truth, and the summary that lies
  is worse than no summary.
- **The scale is spoken in words.** Invariant 22 keeps numerals off the patient surface; the
  score that would reach `csat.v1` is still 1–5, and the option ids are words too, so no
  numeral exists on this path even as an identifier.

## 7. What is not met, and who owns it

**The CSAT clause is delivered as a mechanism that is shut.** Three separate reasons, none of
which is worked around:

1. **No consent record can exist yet.** `satisfaction` is açık rıza and default OFF
   (files/06 §2). `docs/legal/consents/` does not exist — `COUNSEL_BRIEF.md` §4.2 shows the
   loader refusing all eleven purposes — so `grant()` refuses, `csatCollectable()` returns
   false, and `CsatPrompt` returns `null` for every patient today. **Owner: INT-210.**
2. **One tap cannot form an event.** §5.4 calls the prompt one-tap; `csat.v1` requires
   `reason`. No reason is defaulted or inferred. **Owner: INT-305 (filed here).**
3. **The answer has no transport.** INT-240's route is `POST /v1/sessions/{id}/csat`, keyed on
   the `IntakeSession` id. The device holds a `visitId` and the note itself never goes over
   the network. No id is fabricated and no seam is invented for a value that does not exist.
   **Owner: INT-142 (offline drafts + sync).**

**And the share scope cannot record what the patient chose.** `services/api/schemas.py` has
`SectionId = Literal["chief_complaint", "hpi", "medications"]` — three names. `buildNote`
emits eight scope-toggleable sections. A patient who withholds **allergies** makes a choice
the consent scope and the hash-chained audit entry have no value to express. That is an
invariant 4 gap in the layer this screen feeds. **Owner: INT-304 (filed here).**

INT-137 therefore stays `todo`.

## 8. What was refused, and why the refusal still holds

**The Doctor Link QR.** `63d093e` refused it and gave a reason. The reason was re-tested
against today's main and it holds, in fact more strongly than when it was written:

- **INT-150 is still `todo`.** The 128-bit token, OTP, expiry, view limit, revoke, watermark
  and access log are its acceptance. There is no token to encode.
- **There is still no redemption route.** A QR has to point somewhere.
- **Either payload would be a defect.** Clinical data in the code is a share with no consent
  check and no audit entry — invariant 4 in both halves. A bearer token in the code is a
  credential rendered to a camera, readable off a shoulder and recoverable from any photo of
  the screen — invariant 6.
- **A QR library would need a licence audit nobody has run.** Invariant 19 reaches
  dependencies, and invariant 17 forbids hand-rolling the thing instead. `apps/mobile` carries
  no QR or barcode dependency and the spec asserts it stays that way.

So the QR is absent, `review.tsx` says why at the top so the next reader does not add one, and
spec §6 is four negative controls: no URL or scheme, no token, no serialised note, no QR
dependency in the manifest or the tree. The URL control was proved non-vacuous (§4).

**The İYS question, answered rather than assumed.** Invariant 18 makes reminders
transactional-only absent an İYS record, and a satisfaction question is not transactional. It
is also **not a *ticari elektronik ileti***: 6563 and the Yönetmelik reach messages **sent** to
a recipient over a channel, and this is a card on a screen the patient is already looking at,
one scroll below the button they pressed. Nothing is dispatched — neither `csat.ts` nor
`CsatPrompt.tsx` imports a notification port, a channel or a scheduler, and a test holds that
the whole surface reaches no network. INT-242's own cadence agrees and was read before this
was written: `surveys/cadence.py` excludes `csat` from `SurveyKind` because CSAT is
*"triggered by the session ending rather than by a clock, so it has no cadence to own"*. **No
second cadence gate was written.** The record that governs the prompt is the KVKK m.6 açık
rıza for `satisfaction`, and it fails closed today (§7).

One inconsistency is flagged, not resolved, because it is counsel's: `COUNSEL_BRIEF.md` §2.9
records that the registry makes `satisfaction` açık rıza while the storage annotations and
`retention_policy.yaml` give it the m.5/2-c contract basis. This issue takes the **stricter**
of the two — açık rıza, fail closed — so no reading of that contradiction makes the code
collect more than it may.
