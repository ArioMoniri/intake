# Evidence: INT-550 · A new staff user enrols a passkey after the password step

**Epic:** E12-admin · **Phase:** P0 · **Sec-Row:** platform · **GitHub:** #930 ·
**Depends on:** INT-378, INT-421, INT-538 · **Branch:** `int-550-kc-passkey-enrol` from
`origin/main` `ab9b8819`

## Problem

The issue was found read-only on the synthetic host on 17 Oct 2026, and it blocks all admin use.
Realm `intake` refused every new staff user after the password with "Invalid username or
password". Keycloak logged `LOGIN_ERROR invalid_user_credentials` with `userId=null`, and the
`webauthn-register` required action, which INT-538 sets on every new user, never ran.

The live `staff second factor` subflow had two ALTERNATIVE steps:
`intake-webauthn-session-notes` and `auth-otp-form`. A new user holds neither credential.

## Investigation: the provider was not the cause

The issue blamed the INT-378 provider for not allowing user setup. Keycloak 26.7.4's source shows
otherwise. Every path below is under `keycloak/keycloak` at tag `26.7.4`, read through the GitHub
contents API.

| fact | source |
|---|---|
| The stock factory returns `isUserSetupAllowed() == true`. `WebAuthnSessionNotesAuthenticatorFactory extends` it and does not override the method, so the provider has always allowed setup. INT-378's test `everythingButTheIdAndTheLabelsIsTheStockFactorys` already held the two values equal. | `services/.../authenticators/browser/WebAuthnAuthenticatorFactory.java:56-59` |
| The stock authenticator, which ours extends unchanged, has `requiresUser() == true` and `configuredFor` returns `isConfiguredFor("webauthn")`. Its `setRequiredActions` adds `webauthn-register` once, and `getRequiredActions` names `WebAuthnRegisterFactory`. | `WebAuthnAuthenticator.java:281-302` |
| **The switch is the requirement.** For an identified user who is not `configuredFor` the step, the engine marks it `SETUP_REQUIRED` and calls `setRequiredActions` only if `factory.isUserSetupAllowed() && model.isRequired() && authenticator.areRequiredActionsEnabled(...)`. Otherwise it throws `CREDENTIAL_SETUP_REQUIRED`. | `services/.../authentication/DefaultAuthenticationFlow.java:471-481` |
| In a level of ALTERNATIVEs that exception is only collected. With both steps unusable, the subflow, and so the whole browser flow, ends unsuccessful and returns no page. | `DefaultAuthenticationFlow.java:309-330` |
| `authenticateOnly` then throws an exception built from the top flow's (empty) list. `handleBrowserException` answers `invalid_user_credentials` and `Messages.INVALID_USER`, which is "Invalid username or password". | `AuthenticationProcessor.java:1132-1133, 906-908` |
| `areRequiredActionsEnabled` is false when the realm lacks the action or has it disabled. | `server-spi-private/.../Authenticator.java:102-113` |
| A realm imported with no `requiredActions` list gets Keycloak's defaults, and those include `webauthn-register`, enabled. Neither committed realm carries a list. | `model/storage-private/.../DefaultExportImportManager.java:362-373`; `server-spi-private/.../DefaultRequiredActions.java:316-333` |
| The per-execution `userSetupAllowed: false` in the realm JSON is an export field. The import never reads it, so it is not the switch either. | `DefaultExportImportManager.java:1576-1600` (`toModel`) |
| An execution counts as completed (the `amr` mapper's input) only on `SUCCESS`. | `services/.../authenticators/util/AuthenticatorUtils.java:112-130`, called from `DefaultAuthenticationFlow.processResult` |
| The admin API's `updateExecutions` copies the body's `priority` whenever it differs, so a body without one sets it to 0. | `services/.../resources/admin/AuthenticationManagementResource.java:804-806` |

**So the fix is in the realms, not the jar.** The WebAuthn step becomes REQUIRED. OTP becomes
DISABLED: it stays in place, with its `amr otp` reference, until the owner decides INT-389
(#644). Keeping OTP as an ALTERNATIVE was ruled out for two reasons:
- an ALTERNATIVE beside a REQUIRED step is ignored with a warning (`DefaultAuthenticationFlow.java:354-361`);
- in the host's shape it was a way around the passkey for anyone who held a TOTP credential.

The console already refuses a TOTP token (INT-378's `aaguid` rule), so disabling OTP takes away
nothing that worked. files/08 §2.3 asks for MFA on every console role, and WebAuthn meets that
for every role.

The provider's own semantics are now held outright, not only as "equal to stock":
`isUserSetupAllowed`, `requiresUser`, `configuredFor` (only a passkey counts), `setRequiredActions`
(adds `webauthn-register` once), and `areRequiredActionsEnabled`, with its near misses.

## The deploy step (coordinator, after merge)

Keycloak imports a realm once, so the realm JSON change does not reach the host by itself.
`deploy.sh` switches the live realm. Run the staging runbook's deploy, `docs/runbooks/staging.md`
§2–3: archive `origin/main`, upload it, then on the host:

```bash
sudo -i
curl -fsSL '<presigned URL>' -o /tmp/intake-staging.tgz
rm -rf /opt/intake && tar -xzf /tmp/intake-staging.tgz -C /opt && cd /opt/intake/infra/staging
./deploy.sh
./smoke.sh
```

`init.sh` has already run and is not needed again.

**What `./deploy.sh` does for this change.** `build_keycloak_image` rebuilds the jar, which
must match the unchanged pin. Then `compose up keycloak`, then `ensure_staff_webauthn_notes`,
which is `staff_flow.py apply`. Expected output:

```
staff flow: set_required <id of the intake-webauthn-session-notes execution>
staff flow: disable_otp <id of the auth-otp-form execution>
staff flow: realm intake runs intake-webauthn-session-notes REQUIRED with the hwk reference, OTP disabled, and webauthn-register enabled
```

From the host's state, the provider ALTERNATIVE at priority 0 (INT-421's sync) and OTP
ALTERNATIVE at priority 20, it takes exactly two steps. Both keep the priorities.

Then `smoke.sh` check 7 passes: "realm intake runs the WebAuthn session-notes provider REQUIRED
with the hwk reference, and a new staff user can enrol".

**What would stop it.** If `webauthn-register` were absent or disabled in the live realm, the
script refuses before any change ("staff flow: refused: …"), and the deploy stops at
`ensure_staff_webauthn_notes`. The realm was imported with Keycloak's defaults, so it is
expected to be enabled.

**Verification on the host (the owner, once):**
1. Open the console and sign in with the username and the temporary password.
2. Set a new password (`UPDATE_PASSWORD`).
3. Register a passkey or security key on the `webauthn-register` page.
4. The console refuses this first session (step 5 below explains why). Sign out of Keycloak at
   `https://auth.<host>/realms/intake/protocol/openid-connect/logout` and confirm.
5. Sign out of the console's proxy at `https://admin.<host>/oauth2/sign_out`.
6. Open the console again and sign in with the new password and the passkey: admitted.

Step 4's session asserted no passkey. Its token's `amr` is `["pwd"]`, with no
`aaguid`/`credential_id`, and an SSO resume would keep that.

  - `start-dev --import-realm` on loopback;

  The engine test runs Keycloak's own flow classes instead, and the host deploy is the live

## Findings for the coordinator

1. **The issue's root cause was wrong**, as shown above. Nothing in the jar changes. The pin and
   INT-378's recording stay valid.
2. **INT-421's sync left the provider at priority 0.** `set_alternative` sent no priority, and
   Keycloak copies the body's. INT-421's evidence shows the effect: "provider ALTERNATIVE
   (priority 0)". It was harmless there, and the new steps always send the current priority.
3. **The first session after enrolment is refused by the console**, and the staff member must
   sign out of Keycloak and the proxy before a passkey sign-in. The runbooks now say so.
   - A console-side improvement would remove the manual step: on
     `insufficient_user_authentication`, end the Keycloak session and restart the login, or
     have the proxy request `prompt=login`.
   - It is outside this issue, and no id was minted for it.
4. **INT-389 (#644).** If the owner chooses (b), TOTP for roles outside patient content, OTP
   cannot come back as an ALTERNATIVE beside WebAuthn. That is exactly the shape that refused
   every new user. It would need its own subflow design, and its own enrolment test.
