## Clause 1 — "facts commit only with patient/clinician confirmation (type-level)"

The mechanism is an **absence**, following the posture INT-172 took for `CandidateRedFlag`
(no `level` field, so `RED` is a `TypeError` at the call site rather than a rejection three
layers later). Four absences, each of which a test names:

1. **`FactCandidate` has no `source` field and no `confirmed_at` field.** It carries
   `{key, value, origin_ref, observed_at, confidence}` and nothing else, so the unconfirmed
   form cannot be spelled as the confirmed one by filling a value in. `origin_ref` is
   deliberately not a provenance: it says which artefact the proposal came from, not that
   any human agreed with it. `observed_at` is deliberately not `confirmed_at`: the
   twelve-month window runs from a human act, and an observation is not one.
2. **There is no inheritance between `FactCandidate` and `LearnedFact`** in either
   direction, so neither can stand in for the other.
3. **`confirm(candidate, confirmation)` is the only function in the module returning a
   `LearnedFact`** — asserted by an AST scan of `clinical_schemas/overlay.py`, so a second
   producer cannot appear quietly. Its `Confirmation.source` is a `LearnedFactSource`, whose
   three members are all confirmations; there is no unconfirmed value to pass. `ConfirmingActor`
   has exactly `PATIENT` and `CLINICIAN` (invariant 12's own two words) and
   `CONFIRMING_ACTOR` is **total** over `LearnedFactSource` — checked as a set equality, so
   the map cannot grow a hole when the enum changes.
4. **`OverlayStore` has no public method with a `LearnedFact` parameter.** You cannot hand
   the store a fact you minted yourself; `confirm_fact(candidate=…, confirmation=…)` mints
   it. A signature scan over every public method asserts this, so adding such a door is a
   test failure rather than a review miss.

And the reason all four bind: **`PatientOverlay.facts` is typed `tuple[LearnedFact, ...]`**,
and `PatientOverlay` is the only object INT-081's `decide_delta` and INT-258's
`activate_overlays` accept. A `FactCandidate` placed there is a mypy error under the
`--strict` lane `make check` already runs, and a `ValidationError` at runtime. So an
unconfirmed fact does not reach a rule or a triage input because **there is no value of the
type a rule reads that represents one** — not because a guard rejects it.

**There is no candidates table.** That is the same design decision at the storage layer: one
table with a nullable `source` column is exactly the runtime check invariant 12 refuses to
depend on. See "Device-local vs server-side" below for the second reason.

## Clause 2 — "12-month reconfirm", and where the window is *not* re-derived

`fact_needs_reconfirmation` (INT-031) is the window. INT-258's `activate_overlays` and
INT-081's `decide_delta` already share it; a third copy would drift on what "in date" means,
so this issue adds none. Two consequences, both deliberate:

- **The store does not withhold stale facts.** `list_facts` and `load_overlay` return every
  confirmed fact. A store that dropped them would also hide them from *Me → Hakkımda
  öğrendikleri*, where the patient has to **see** a fact in order to re-confirm it — and it
  would give the tree a second, silent definition of the window. The withholding stays where
  INT-081 put it: `decide_delta` reports the key in `withheld_fact_keys` and asks the
  question in full.
- **`/v1/me/learned` calls the same predicate** to fill each fact's `needs_reconfirmation`
  flag. That is the only place a duration appears in this feature.

`tests/learning/test_overlay_provenance.py::TestTwelveMonthReconfirmation::
test_no_module_added_by_this_issue_re_derives_the_window` scans every line of
`intake_platform/overlay/` and `intake_api/learned.py` for `timedelta(`, `365` or
`RECONFIRM_AFTER` and asserts the list is empty. The one end-to-end test stores a
400-day-old fact, reads it back through the store (present, so the patient can act on it)
and runs `decide_delta` over it (mode OFF, `withheld_fact_keys == ("oyku.belirti_var",)`).

Re-confirmation itself is an upsert: the row is replaced in place and `confirmed_at` becomes
the instant of the **human act**, not the instant the proposal was observed — so a year-old
draft confirmed today is in date, and a fact confirmed a year ago is not.

## Clause 3 — "provenance shown"

Every stored fact round-trips its `source`, its `source_ref` (the confirming artefact — the
"where from" files/09 §3 promises), its `confirmed_at` and its `confidence`, parameterised
over all three `LearnedFactSource` members. `/v1/me/learned` renders those plus the derived
`confirmed_by` (patient or clinician) and `needs_reconfirmation`, and gives the patient the
two verbs files/09 §3 names: `PATCH` for the per-field share scope and `DELETE` to remove a
fact. A deletion **removes the row**; there is no tombstone, because a tombstone that keeps
the key keeps the health fact.

The overlay is versioned, and the version is a **column** rather than a derivation: a
version taken as `max()` over the surviving facts would go *backwards* when the patient
deletes the newest one. Version 1 is the empty overlay every patient starts with, the header
row appears at the first mutation, and a deletion is a mutation like any other.

## Clause 4 — "delta-mode works in simulator"

`TestDeltaModeOverTheStore` runs one headless session end to end against the real objects:
seed the store → `load_overlay` → `build_plan` over a synthetic resolved protocol →
`decide_delta`. Four cases, and the negative controls are the point:

- a stored confirmed fact turns delta mode **ON** with a `confirm` step spoken from the
  slot's own `confirm_tr` and carrying the fact's `source_ref`;
- an empty store leaves it **OFF**;
- a fact whose slot has no `confirm_tr` does **not** pre-fill and is reported in
  `unconfirmable_fact_keys` — the question is asked in full (invariant 10: no improvised
  confirmation);
- **a candidate that was never confirmed changes nothing.** The test builds one and then
  asserts the decision is byte-identical to the decision with `overlay_facts=None`, because
  there is nowhere for it to go.

## Invariants 4, 6 and 14 on the route

- **4** — `/v1/me/learned` is a read of clinical data, so all four routes declare `core` and
  are enforced by the single `ensure_consent` path. No marker, no exemption: unlike the DSAR
  routes (legal obligation) or the notification register (a refusal a withdrawal must not
  lock), nothing here becomes unreachable when a consent is withdrawn that should not.
  A withdrawn `core` answers `{"error": "consent_required", "scope": "core"}` and **audits
  nothing** — a refused read is not a read. Every read, confirm, re-scope and delete that
  *does* happen appends to the hash chain (`api.learned.read` / `.confirm` / `.rescope` /
  `.forget`) with `resource_ref = patient:<id>` and a scope ref, and nothing else.
- **6** — the audit sweep plants INT-175's Turkish symptom sentence (borrowed verbatim, as
  INT-172 and INT-205 borrow it) as a fact value and sweeps the audit entries **decoded**:
  JSON escaping means a raw sweep passes on an escaped Turkish sentence, so `_blob` round-
  trips through `ensure_ascii=False` before looking. The store-side sweep does the same over
  the persisted rows and the Prometheus exposition.
- **14** — the value and its confidence are one EncryptedField envelope; there is no
  plaintext-value column to fall back to, which is why `confidence` lives inside the payload
  rather than beside it. `fact_key` is in the clear exactly as `slots.slot_id` is: it is an
  authored protocol reference, which is what lets delta mode match it against a step id at
  all. The `source` column is a CHECK-constrained closed vocabulary of the three
  `LearnedFactSource` members, so a fourth provenance cannot arrive by SQL either.

**Invariant 12 on the route, restated as an absence:** the request body carries **no
`source` field**. `FactOrigin` has two members — `intake_extraction` and `imported_record` —
which are the two provenances a *patient* can establish; `clinician_accepted_note` is
unspellable over this endpoint rather than filtered out of it, and it is established by note
acceptance against the same store. `extra="forbid"` on the body model makes a smuggled
`source` a 422 rather than an ignored field, and both are tested.

## Device-local vs server-side: the choice this store actually met

The owner's standing preference is that data live on the patient's device as far as
possible. This store met the question once, at the candidate lane, and the answer went
device-local. Recorded here so the ADR that decision needs can be written from real options.

| | server-side candidates table | device-local candidates (**chosen**) |
|---|---|---|
| invariant 12 | an unconfirmed fact exists in a row; "confirmed" is a column state to check | an unconfirmed fact has **nowhere to be written**; nothing can read one back |
| new personal-data category | yes — persisting unconfirmed inferences about a patient is a new category, which CLAUDE.md makes a **stop-and-ask** | no new category: only the patient's own confirmation is stored |
| retention | needs a files/06 §3 row that does not exist; inventing a clock is forbidden | rides `clinical_record`, the row 06 §3 already writes for transcript-derived structured data |
| pending confirmation cards | survive a reinstall; readable by the server | held by the app (INT-247 already owns the client-side "carried-forward facts must be confirmable" surface); lost if the patient wipes the app before answering |
| clinician confirmation | same table | unchanged — note acceptance calls `confirm_fact` directly with a `CLINICIAN_ACCEPTED_NOTE` confirmation |

**Chosen: device-local.** The deciding argument is not the preference but the blocker rule —
the server-side option requires persisting a new category of personal data, which is
stop-and-ask territory, and the device-local option needs no human decision at all. It also
makes invariant 12 strictly stronger: the forbidden state has no storage, not merely no
type. The cost is honest and stated: **a confirmation card that is never answered is not
durable**, and if a later issue needs it to be, that is the ADR — server-side pending
candidates with their own retention row and their own consent purpose — and it should be
written against this table rather than assumed into it.

Two smaller choices went the same way and for the same reason: the fact **value** is
envelope-encrypted server-side rather than held only on device, because `decide_delta` and
`activate_overlays` run in the voice runtime and need it; and the fact **key** is in the
clear, because a store that could not match a key to a step id could not do delta mode at
all.

- **4** (consent + audit) — the four routes go through the one `ensure_consent` path under
  `core`; every disclosed read and every change is on the hash chain; a refusal is not.
- **6** (no PHI in logs/metrics) — the value never leaves the envelope except in the
  patient's own response body. Audit entries and both metric label sets carry closed
  vocabularies and ids; the sweeps are decoded.
- **7** (monotonic overlays) — untouched. This issue stores overlay *facts*; overlay rule
  composition stays entirely in INT-258's `compose_overlay_rules` and no second path to a
  rule set was added.

  existing `packages/intake_platform` + `services/api` lane at its ≥ 85 % floor.

  No new service, so the health/SLO/probe contract is unchanged.
- **14** (envelope encryption for learned facts) — `overlay_facts.payload` is always an
  EncryptedField; the erasure crypto-shreds it before the row goes.
- **17** (zero placeholders) — the gate is green; nothing here is deferred behind a marker.
- **18** (inventory annotation) — every column of both tables carries
