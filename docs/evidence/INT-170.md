## Clause 1 — "(type-level)" is a different type, not a flag

`LearnedFactSource` (INT-031) already had no unconfirmed member, but a source enum is not enough: the
thing extraction produces and the thing a person confirmed were still the *same type*, so any caller
could assemble a `LearnedFact` from output nobody looked at. INT-170 splits them:

- `UnconfirmedObservation` — `{key, value, observed_ref, observed_at}`. No field names a confirmer, a
  confirmation time or a confirmed provenance, so "an observation that says it was confirmed" cannot
  be written down.
- `ConfirmedFact` — `{key, value, confirmation, confidence}`, where `Confirmation` is
  `{by, actor_ref, at, source, source_ref}` and every one is required.
- `Confirmer` has exactly two members, `PATIENT` and `CLINICIAN`. There is no model member.
- `PatientOverlayStore.commit(*, fact: ConfirmedFact, …)` is the only entry to the store.

**These four are frozen dataclasses, not `FrozenModel`, and that is the load-bearing detail.** This
repository does not enable pydantic's mypy plugin — `pyproject.toml` declares no `plugins` — so
`BaseModel.__init__` type-checks as `**data: Any`: a missing `confirmation=` and a stray
`confirmed=True` both pass `mypy --strict` and fail only at runtime. Building the confirmation
vocabulary on `FrozenModel` would have made "(type-level)" a runtime claim wearing a type's clothes.
A frozen dataclass gives the checker a synthesised `__init__` and a read-only field, which is what
produces the five diagnostics below.

## Clause 2 — the 12-month rule: a decided expiry semantics, on an injected clock

**The question.** At twelve months and a day: does the fact stop being *used*, or stop being
*asserted* while staying visible as history?

**The decision: it stops being asserted and stays visible.** `FactStatus` has four members —
`ASSERTED`, `STALE`, `SUPERSEDED`, `WITHDRAWN` — and a fact past the window becomes `STALE`, which
means precisely three things:

1. **It is never put in front of anyone as current.** The ledger and `/me/learned` show it as `stale`,
   beside the `reconfirm_due_at` it passed, and INT-081's `decide_delta` withholds it from the session
   so the question is asked in full rather than confirmed from a year-old answer.
2. **It is still in the ledger, with its full provenance.** A silently dropped allergy is not the same
   artefact as one marked stale. Dropping it destroys the record of what the system was told, and it
   takes the patient's KVKK m.11 correction right with it: you cannot correct a fact you can no longer
   see. This is the same reasoning files/06 §2.2 gives for tombstoning lane signals rather than
   deleting them.
3. **Re-confirmation appends.** The older record becomes `SUPERSEDED` and stays; nothing is edited in
   place, so the history of what was believed when survives.

**Where the rule is applied, and why only once.** `PatientOverlayStore.overlay()` excludes `WITHDRAWN`
and `SUPERSEDED` facts and **includes `STALE` ones**. That is deliberate: INT-081's `decide_delta` is
already the component that applies the twelve-month rule to a session, and it *records* the
withholding in `DeltaDecision.withheld_fact_keys`. Filtering at the store as well would (a) give the
repository two implementations of "in date" that can drift, with the drift invisible from either side,
and (b) delete the session's own record that a stale fact existed. So the store calls
`clinical_schemas.overlay.fact_needs_reconfirmation` — the same predicate `decide_delta` calls — and
a test pins the two answers equal across the boundary rather than pinning a constant.

**No wall clock.** `PatientOverlayStore.__init__` takes `clock` as a required keyword with **no
default**, asserted by `test_the_store_has_no_default_clock`; an AST scan
(`test_no_overlay_module_reads_a_wall_clock`) proves no branch of either new module can reach
`datetime.now`, `utcnow`, `today` or `time`. The tests use a `ManualClock` they advance. A wall-clock
test for a twelve-month rule takes a year to go red, which is the flake docs/TDD.md rule 6 forbids and
the one INT-264 cost this repo a gate for.

Boundary asserted from both sides: at `confirmed_at + 365 days` exactly the fact is still `ASSERTED`;
at `+ 365 days + 1 day` it is `STALE`. That matches `fact_needs_reconfirmation`'s strict `>`.

## Clause 3 — provenance shown, and unconstructable if absent

`LedgerEntry` carries every axis as a required field: **where from** (`source`, `source_ref`), **when**
(`confirmed_at`, plus `reconfirm_due_at`) and **by whom** (`confirmed_by`, `confirmed_by_ref`). The
only optional member is `withdrawn_at`, because "not withdrawn" is a real state and a missing
provenance is not; a test asserts that no other field's annotation admits `None`.

Because a `LedgerEntry` is only ever built from a `ConfirmedFact`, and a `ConfirmedFact` cannot be
built without a `Confirmation` whose five fields are all required (and whose reference fields refuse
empty strings), **a fact with no provenance is unconstructable rather than merely unrendered**.

Patient and clinician are not interchangeable and stay apart to the wire: `Confirmer` is carried
through commit → ledger → the `/me/learned` body.

**One honest narrowing, recorded rather than hidden.** `clinical_schemas.overlay.LearnedFact` — the
INT-031 transport the IntakeEngine reads — has no carrier for *who* confirmed. Its shape is pinned by
the committed OpenAPI/TS codegen (`packages/clinical-schemas/schemas/`, `src/generated/models.ts`),
which this issue does not own and cannot regenerate. So `ConfirmedFact.as_learned_fact()` drops
`Confirmer` on the way to the engine and the ledger is where "by whom" is shown. That is a narrowing,
never a widening: nothing the engine sees was unconfirmed. Adding `confirmed_by` to `LearnedFact` is a
codegen change and belongs to whoever owns that regeneration — see **Wires still needed**, item 3.

## Clause 4 — delta mode works in the simulator

Three tests drive INT-082's headless simulator (`tests/sim/driver.py`, unmodified) over scenario
**IM-07** with persona `P12-frequent-attender-delta`, replacing only the persona's overlay with one
**materialised out of this store**, so what the simulator consumes went through `commit()` rather than
being written into a persona by hand:

- a fact confirmed at the simulator's reference time → `delta_mode == "on"`, a `StepKind.CONFIRM` turn
  is played, and `ilac.ilac_kullanimi` is asked as a confirmation instead of a full ask;
- the same fact confirmed 366 days earlier → the store still hands it over (`overlay.facts` is
  non-empty), `IntakeEngine(...).delta.withheld_fact_keys == ("ilac.ilac_kullanimi",)`,
  `prefills == ()`, `delta_mode == "off"`, and the step is asked with a non-`CONFIRM` kind;
- a withdrawn fact → not in `overlay.facts` at all, `delta_mode == "off"`.

`tests/sim/**` was read and not edited.

## Invariants 4, 6, 14, 18 and KVKK-11

**Invariant 4 — consent scope on every read, audit on every touch.** `GET /v1/me/learned` declares
`require_scopes("learning:personal")`, the files/06 §2 purpose (quoted from
`intake_platform.consent.registry`, never invented). `unguarded_data_routes()` returns `[]` for a
router-mounted app, so the route-table scan will pass the moment the router is wired. The store audits
**write-ahead** — files/10 §2's ordering — with `overlay.learned.read`, `overlay.fact.commit`,
`overlay.learned.materialise`, `overlay.fact.withdraw`; an audit failure propagates and the read does
not answer (`test_a_read_that_cannot_be_audited_does_not_answer`).

**KVKK-11 — withdrawal is reachable and audited.** `DELETE /v1/me/learned/{fact_id}` declares `core`
and deliberately **not** `learning:personal`. The reason is the one `DataSubjectRightDeclaration` and
`NotificationPreferenceDeclaration` already state in `intake_api.consent_guard`: a purpose whose
withdrawal locks the correction of the facts it produced is not a purpose, it is a cage — the request
a withdrawal provokes is exactly the request a `learning:personal`-gated route would refuse. The audit
entry names `basis:KVKK-11` rather than a scope. A withdrawal tombstones the row; it never deletes it,
because deleting one would break the audit hash chain. Erasure proper remains INT-037's
`/v1/me/dsar/delete`; nothing in `dsar/` was touched.

**Invariant 1 — an overlay fact is not a triage input.** Nothing in these modules names a triage level,
a rule id or `packages/protocols`. The overlay reaches triage only the way it already did: through
`decide_delta` changing a step's *kind*, never the frontier's membership (`delta.py`'s own invariant),
so a learned fact cannot raise or lower a level.

**Invariant 6 — no PHI in logs.** The store logs nothing. Every refusal is a code with no narrative
(`overlay_store_unconfigured`, `not_found`, `consent_required`). The learned value travels only in the
`/me/learned` response body, which is the data subject reading their own record over an authenticated
channel — the whole purpose of the surface.

**Invariant 14 — field-level envelope encryption for learned facts.** The store seals the whole fact
(key, value, confirmation, confidence) with `EnvelopeCipher.encrypt_field` **before** the repository
sees anything, so the repository — and the table behind it — cannot hold plaintext; a test asserts the
sealed blob contains neither the key, the source ref nor the source name. The AAD binds the ciphertext
to `{tenant, patient, fact_id}`, so a ciphertext moved between rows fails authentication instead of
re-attributing a fact (also tested).

**Invariant 18 — inventory annotation.** `OVERLAY_INVENTORY` in `overlay_store.py` declares
`{category, purpose, basis, retention, recipients}` for all six persisted fields, built with
`intake_platform.db.inventory.inv` so a half-filled annotation cannot be written. A test asserts the
key set equals `SealedFactRow`'s field set and every row is complete; `sealed` is
`special_category_health`. The retention quoted is files/06 §3's record clock (`RET_RECORD`).

**No consent purpose was invented, and no new blocker is raised on that axis.** files/06 §2 names
`learning:personal` for exactly this data and states its basis: *"performance of the very service the
patient configured"*. That wording is quoted into `_BASIS_LEARNING_PERSONAL` rather than mapped onto
an existing constant that would misstate it (`BASIS_HEALTH_CONSENT` says *açık rıza*, which this
purpose is not — it is on by default and opt-out). Whether m.5/2-c alone carries a special-category
value is a reading files/06 §2 has already made; if counsel disagrees, that is an HB-L row against
files/06 §2, not against this issue, and the store's purpose id would not change.

**Invariant 12 — the learning loop cannot write a learned fact.** The store is a *writer*, so it lives
in `services/api`, which `tests/learning/test_proposal_scope.py` already names among the forbidden
import roots for `services/learning`. That makes "the loop cannot write a patient fact" a property of
the existing gate rather than a new rule; a test pins the placement so a later move into
`services/learning` cannot happen quietly. `proposal_scope` is untouched and green: **14 tests**.

## Blocked: the `learned_facts` table

`PatientOverlayStore` is complete and fully tested against its repository `Protocol`; the concrete
SQLAlchemy repository is **not written**, because it needs a table that does not exist and every file
it would need is outside this issue's ownership:

- `packages/intake_platform/src/intake_platform/db/models.py` — a `LearnedFact` model with the six
  columns of `SealedFactRow`, carrying `OVERLAY_INVENTORY`'s annotations **verbatim** on
  `Column.info` (they are written to be copied, not re-derived);
- `migrations/versions/` — the migration, with RLS forced on `tenant_id` like every other table;
- `tests/data/test_inventory.py` — add `"learned_facts"` to `EXPECTED_TABLES`, which is an exact-set
  assertion and will fail the moment the table lands without it.

This is a scope boundary, not a missing decision: no value was invented and nothing was faked. Per
HUMAN_BLOCKERS Rule 2 the mechanism is built, the gate is wired and it fails closed — the route
answers 503 rather than an empty ledger, and invariant 18 is already enforced against the declaration.
**No new HUMAN_BLOCKERS row is needed**: this waits on an engineering change in another agent's files,
not on a named human's answer.
