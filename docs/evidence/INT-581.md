## What was built

**The canary, end to end** (`tests/security/test_sms_data_protection.py`). One number nothing else
in the suite uses, written seven ways — E.164 (`+90` and the ten national digits), with `90` and
no plus, with the national `0`, the bare ten digits, and grouped 3-3-2-2 behind `+90 `, behind
`0` and with no prefix — and every code it is sent, go through every path:

- a sent request, a withheld one, a wrong code, the right code, a refresh;
- a 500 inside verify (the patient write fails);
- a vendor that refuses;
- a vendor client that crashes with the number and the code in its exception message.

They are then searched for in every sink:

- every log record the API emitted: message, arguments, formatted traceback, and the JSON line
  `JsonLogFormatter` writes;
- the whole metrics exposition (`generate_latest`);
- every span the tracer provider finished;
- the error-report event for the crash after `intake_platform.errors.scrub_event`;
- every HTTP answer, headers included;
- every audit row;
- every Redis key and value, except the dev tier's peek slot;
- every row of every database table.

Codes are matched as whole digit runs, so a timestamp that happens to hold the six digits is not
counted as a leak, while a stored code is. The scanner has its own near miss: a log line that does
carry the number is found.

One scoping decision. The **test's** HTTP client (httpx) logs the URLs it calls, and the dev-only
peek route takes the number as a query parameter. Those records are the test's, not the API's, and
are left out of the scan. The route itself is recorded below as a residual.

**What the canary found, and the fixes:**

1. **The redactor missed the canonical form.** `redact_text` masked a mobile written with the
   national `0` or as the bare ten digits (`\b0?5[0-9]{9}\b`), but not the E.164 form
   `normalise_tr_phone` gives every number (`+90` and the ten digits), nor any grouped form. The `+90` glued the digits to a word character, so
   `\b` never fired. The pattern
   (`packages/intake_platform/src/intake_platform/redaction.py`) now takes the `+90`, `0090`, `90`
   and `0` prefixes or none, the number whole or grouped 3-3-2-2 by single spaces, NBSPs or
   hyphens, bounded by non-digits. Near misses that stay as written: a landline (`+90 212 …`), a
   ten-digit run outside the 5XX range, `5 mg … 532 ml`, a blood pressure, a timestamp. A grouped
   run that starts with 5 is masked even when it is something else. In a log line that is the
   right side to err on, and `redact_text` runs only on logs, spans and error reports.
2. **The collector had the same hole.** Its five phone statements
   (`infra/observability/otel-collector.yaml`) now read `(\+90|\b90|\b0|\b)5[0-9]{9}\b`; RE2 has
   no lookbehind, so the prefixes are an alternation. A test runs the committed patterns on the
   canonical forms.
3. **A crashing vendor reached the logs.** INT-579's background delivery caught only the typed
   `OtpDeliveryError`. Any other exception stayed in the task, and asyncio logs an unretrieved
   task exception with its text: on the red run, `ERROR asyncio … Task exception was never
   retrieved` carried the number and the code. `_deliver` now contains every exception. It logs
   the type (`otp delivery crashed (RuntimeError)`) and never the words, and records
   `auth.otp.delivery_failed`.

**The SMS proxy is required on the synthetic host (row 40).** `otp_delivery_from_settings`
already refused any proxy but `http://sms-egress:3128`. It now also refuses **no** proxy where
`environment ∈ SYNTHETIC_ENVIRONMENTS`: ADR-042 makes the dedicated proxy the only route out
there. The tier stays at 503 and the vault is never read, and the log line names ADR-042.
Production keeps its own route (in-country, in-process resolve-and-pin), which ADR-042 leaves to
its own decision. A test pins that it still wires without the synthetic host's proxy. The staging
compose already sets `INTAKE_SMS_EGRESS_PROXY_URL=http://sms-egress:3128`, so the live host is
unaffected.

**Every send and verify on the chain, ids only (row 41).** With INT-579 the send side writes
`auth.otp.requested` or `auth.otp.withheld` on the route and `auth.otp.sent` (job id) or
`auth.otp.delivery_failed` after it. Verify now also writes `auth.otp.verify_refused` for every
refusal, with the number's 8-character log ref as the actor and the closed outcome as the
resource (`otp_verify:invalid|unbound|exhausted|missing|locked`). Every kind of refusal writes one
row, so INT-579's same-work property holds. A test walks a flow and asserts every `auth.*` row's
actor and resource against id grammars, and that the chain verifies.

**Credentials (row 39) and tokenisation (row 38)** were already enforced. The canary scan of every
Redis value and database row is the at-rest proof. A test pins that INT-528's
environment-is-not-a-secrets-path test still exists.

## What this does not stop (residuals)

- **The phone-tokenization key is not in OpenBao.** It is read from `INTAKE_TOKENIZATION_KEY`
  (`settings.py`), which the synthetic host keeps in its root-only env file. With the key, the
  10⁹ Turkish mobiles can be enumerated back from their pseudonyms. Moving the key into OpenBao is
  a migration that has to carry the existing key across: a new key would change every pseudonym on
  the host and orphan every account. That is a key-management design change, so it goes to the
  owner (CLAUDE.md "when to stop and ask") rather than into this PR.
- **The dev-only peek route takes the number as a query parameter** (`GET /v1/auth/dev/otp-peek?phone=`,
  `apps/mobile` `devPeekOtp`), so a dev access log carries a (synthetic) number. The route is 404
  everywhere but dev, which every other environment refuses at boot (INT-325).
- **A bare 6-digit code cannot be redacted generically** without shredding every 6-digit value in a
  log. Codes are kept out by construction: no OTP path logs one, the typed delivery errors carry
  none, and an untyped one is contained (above). The canary scan is what holds that.
