# Evidence: INT-377 · /admin/models and /admin/ops fail closed on a malformed probe-results file

Found by INT-181 (PR #612, evidence "Finding reported, not fixed"). **Sec-Row:** `admin-console`
(files/10 §9; `docs/security/threat-model.md` § `admin-console`). The logging half also answers
the files/10 §9 "Observability pipeline" row: PHI in `ValidationError` messages.
**Branch:** `int-377-probe-file-fail-closed`.

## 1. The defect

`INTAKE_PROBE_RESULTS_PATH` names the file the probe runner writes. Two console routes read it
through `services/api/src/intake_api/admin/models_source.py`:

- `GET /admin/models` (INT-183): the release gate and every row's own-probe finding;
- `GET /admin/ops` (INT-351): the models tile.

`_results()` checked that the variable was set and that the path was a file, then called
`intake_probes.gate.load_results` with no guard. A file that exists but is not a sweep raised
`JSONDecodeError`, `UnicodeDecodeError` or pydantic's `ValidationError` straight through both
routes. The red run below reproduces it: every malformation answered **500** on both routes.

`/admin/ops` had a second, quieter fault on the same path. `load_ops_console` wrapped
`load_models_module()` in `except (OSError, ValueError)`, and every one of those parser errors is a
`ValueError`. So the first read of the bad file was caught and labelled `registry_unreadable`,
which blamed the wrong file, and the unguarded second read then crashed the route anyway.

## 2. The change

- **`models_source.py`:**
  - `load_probe_sweep() -> ProbeSweep` never raises. It reads the file once and returns the records
    or the reason there are none. The three reason codes are INT-181's own vocabulary
    (`probe_results_unconfigured` / `_missing` / `_unreadable`), so one file reads the same way on
    every console page.
  - A present file that fails to parse or validate (`OSError`, `ValueError`: which covers JSON,
    UTF-8 and pydantic errors) is refused as `probe_results_unreadable` with an empty record set.
    The release gate then blocks on every fallback it cannot see, which is the direction the module
    docstring already required.
  - One `WARNING` on `intake_api.admin.models_source` names the reason, the exception class and the
    environment variable. It never names the path, the content or `str(exc)`, because pydantic's
    message echoes the offending `input_value` and a results file carries free-text `detail`
    fields (invariant 6).
  - `load_models_module(sweep=None)` takes the sweep a caller already read, so each request reads
    the file once. The raising `load_probe_results()` is removed; `ops_console` was its only
    caller.
- **`GET /admin/models`** (`routes.py`, `views.py`): the body gains
  `probe_results: {state, reason}`. `state` is `ok` when a sweep was read, otherwise `unknown` with
  its code. The rows and the release decision are unchanged in shape.
- **`GET /admin/ops`** (`ops_console.py`): a refused sweep turns the models tile
  `{"state": "unknown", "reason": "probe_results_unreadable", "release_blocked": null, "rows": []}`.
  That is the same empty shape as `registry_unreadable`: a refused sweep drawn as per-row
  `no_result` would claim a sweep ran. `sources.registry` stays `ok`, because the registry was
  read. An unset or absent file keeps its INT-351 rendering (`state: ok`, every row `no_result`).
  Nothing was there to refuse, and changing that rendering is outside this issue.
- **`apps/admin-web`:**
  - The `ModelsPayload` wire type carries `probe_results`, and `renderModelsModule` passes it
    through as `probeResults`.
  - `ops/copy.ts` gains the `probe_results_unreadable` reason in `tr` and `en`, with INT-181's text
    for the same key.
  - `e2e/fixtures/models.payload.json` was re-recorded from the API with
    `scripts/dev/record_models_fixture.py`. The only change is the new block, which reads
    `unknown / probe_results_unconfigured` because the recording checkout sets no runner file.

`GET /admin/reliability` (INT-181, PR #612) is not on `main`. Its composite reads the file through
its own `load_sweep`, which already never raises and uses the same three codes. Nothing here
touches it.

## 3. Tests

**`tests/admin/test_probe_results_fail_closed.py`** (new, 45 tests).

- **Ten malformations, each its own test id:**
  - `malformed_json`
  - `truncated` (a valid sweep cut in half)
  - `empty_file` (0 bytes)
  - `whitespace_only`
  - `not_utf8`
  - `shape_object_not_list`
  - `shape_list_of_scalars`
  - `shape_status_outside_vocabulary`
  - `shape_record_missing_status`
  - `shape_record_unexpected_key`
- **Four tests per malformation:**
  - The loader refuses the file without raising: reason `probe_results_unreadable`, no records.
  - `/admin/models` answers 200 with `probe_results = unknown / probe_results_unreadable`, the
    release stays blocked, and no byte of the file appears in the body.
  - `/admin/ops` answers 200. Its models tile is `unknown / probe_results_unreadable` with no rows
    and no verdict, and `sources.registry` is still `ok`.
  - Exactly one log record names the reason and the environment variable. A sentinel planted in
    the file, the file's path and pydantic's `input_value` never appear in the captured log.
- **Near-miss controls:**
  - **A valid sweep** (one healthy record per registry component) reads `ok` / `None` through the
    loader and both routes, and the tile's statuses are the file's `healthy` rather than the
    no-sweep `no_result`.
  - **A valid sweep logs nothing.**
  - **An empty *sweep* (`[]`)** is a readable file, unlike an empty *file*: `ok`, every row
    `no_result`.
  - **An unset or absent file** gives `probe_results_unconfigured` / `_missing` on `/admin/models`,
    logs no refusal, and leaves the INT-351 ops rendering unchanged.

**`apps/admin-web/e2e/models.spec.ts`** (+3):

- the recorded fixture renders `probeResults` as `unknown / probe_results_unconfigured` with the
  release blocked;
- a refused file's code passes through and the release control stays dead;
- near miss: a read sweep renders `ok` / `null`.

**`apps/admin-web/e2e/ops.spec.ts`** (+1): a refused file renders the models tile
`data-tile-state="unknown"`, `data-reason="probe_results_unreadable"`, and the copy rather than the
bare code.

## 7. Not proven here, and for the owner

- **The deployed file.** The owner still has to set `INTAKE_PROBE_RESULTS_PATH` on the API host
  once the runner's 60 s loop is deployed (INT-181's note). Until then `/admin/models` reads
  `probe_results_unconfigured`, which is the truth.
- **No new metric.** The refusal is a log line, not a counter. A catalogued
  `admin.probe_results_refused_total` would need a `metrics_catalog.yaml` row and an alert owner,
  and this issue asks for neither.
