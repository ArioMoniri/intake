# INT-367 — Scheduled quarterly key rotation that emits sec_secret_rotation_due_days

**Epic:** E02-data · **Phase:** P1 · **Sec-Row:** data-at-rest · **GitHub:** #594 ·
**Legal:** 2018-10 (measure 3b, gap `rotation-schedule` in
docs/legal/special-category-measures.yaml) · **Depends on:** INT-215 (merged, PR #585)

## Acceptance (verbatim)
- "a scheduled job runs the existing re-wrap rotation quarterly (files/10 §3) and emits sec_secret_rotation_due_days, catalogued as live; an overdue rotation raises an alert"

## Problem
files/10 §3 keeps each tenant's key-encryption key (KEK) in OpenBao Transit
and states "key rotation quarterly". INT-014 built the rotation:
`TransitKekProvider.rotate` adds a Transit key version, and
`EnvelopeCipher.rewrap_field` moves a wrapped DEK to the newest version
without touching the data bytes. Nothing called either on a schedule, and
`sec_secret_rotation_due_days` was catalogued `planned`. The INT-215 mapping
recorded this as the `rotation-schedule` gap under KVKK 2018/10 measure 3b.

## Change
- **`packages/intake_platform/src/intake_platform/key_rotation/`** (new):
  - `schedule.py`: `ROTATION_PERIOD_MONTHS = 3`, sourced to files/10 §3.
    `next_rotation_due` adds three calendar months in UTC, clamped to the
    month's length (30 Nov → 28/29 Feb). `rotation_due_days` is the countdown:
    zero when due, negative when overdue. It is pure, and a naive instant is
    refused.
  - `transit.py`: `TransitKekInventory` lists the Transit keys named
    `tenant-<tenant_id>` and reads each key's `latest_version` and that
    version's creation time from Transit's own key metadata. There is no new
    store and no new persisted field, so invariant 18's inventory annotation is
    not engaged. Metadata without an integer creation time for the latest
    version raises `KeyMetadataError`. It is reported, never guessed.
  - `job.py`: `run_rotation(inventory, rotator, now=…)` is one idempotent
    tick:
    - a key whose countdown is above zero is left alone;
    - otherwise the tick calls the existing `TransitKekProvider.rotate`, then
      re-reads the key to confirm Transit recorded a newer version.
    It sets `sec_secret_rotation_due_days{key}` from what Transit says after
    the tick. Each outcome is one of:
    - `current`: not yet due;
    - `rotated`: the countdown restarts from the new version's creation time;
    - `failed`: the rotate errored or recorded nothing, and the key keeps its
      negative countdown;
    - `unreadable`: the key gets no series and is not rotated blind.
    Series for keys that no longer exist are dropped.
  - `cli.py` / `__main__.py`: `python -m intake_platform.key_rotation` is the
    entry point the scheduler calls. It fails closed through
    `SecretsProvider.from_env()`, prints Transit key names, outcomes and
    countdowns only (invariant 6), and exits 0 (all current or rotated), 2 (a
    key is still overdue) or 4 (refused).
- **`envelope.py`**: the Transit key prefix becomes the named constant
  `KEK_KEY_PREFIX`, which `TransitKekProvider` and the rotation now share.
- **`observability/metrics_catalog.yaml`**: `sec_secret_rotation_due_days` is
  now `live` with the label `[key]` (the Transit key name, an id).
- **`infra/observability/security-rules.yaml`** (new): the alert
  `SecretRotationOverdue`, `expr: sec_secret_rotation_due_days < 0`, severity
  `ticket`, runbook `docs/runbooks/key-rotation.md#overdue`. It is loaded by
  `prometheus.yml` and mounted by `docker-compose.obs.yml`.
- **`Makefile`**: `make key-rotation` runs one tick.
- **`docs/runbooks/key-rotation.md`** (new) covers:
  - what runs where;
  - the OpenBao capabilities the job's token needs (list, read, rotate, and
    nothing else);
  - what the job never does;
  - the exit codes;
  - the `#overdue` procedure.

## Re-wrap only: why a failed rotation cannot orphan data
The job's only write is Transit `rotate`, reached through a `KeyRotator`
protocol whose one method is `rotate`. It never sets `min_decryption_version`,
never enables deletion, never deletes or trims a key. Every wrapped DEK written
under an older version still unwraps, whether the rotate succeeded, failed, or
failed for one tenant and succeeded for the next. The fake Transit honours
`min_decryption_version` on decrypt, so a job that retired old versions would
fail these tests. Mutation M2 below proves it.

## Scope boundary (stated, not hidden)
- **Stored rows are not swept.** Nothing re-wraps existing rows onto the new
  version. None of the six envelope-bearing tables has such a sweep, and this
  acceptance does not ask for one. Old versions are kept, so nothing is
  orphaned. A sweep would be needed only before an old version could be
  retired, and retiring one is a separate, destructive change.
- **Production wiring is not in this change.** The production host
  (`infra/staging/compose.yaml`) runs no worker or scheduler. The API's
  OpenBao policy deliberately grants no `rotate`. The LOOP guardrails forbid
  touching OpenBao policies. The gauge lives in the process that ran the tick,
  and no Prometheus scrapes a one-shot process; today the obs profile scrapes
  only the OTel collector. Before the alert can fire in production, three
  things must exist: a daily trigger, a scraped host process and a
  rotation-scoped token. The runbook states all three. Deploying a job that
  rotates production keys is a key-management decision for the owner
  (CLAUDE.md "When to stop and ask").
- **files/08 §8.2 lists key rotation as a T2 (two-person) console action.**
  That row governs a human triggering rotation from the admin console
  (INT-191). This job is the routine quarterly cadence of files/10 §3. It can
  only add a version, never remove one.
- **The `rotation-schedule` gap stays open in the measures file.** Its header
  makes closing a gap a human act recorded in that file's diff. This change
  gives the security owner the answer to the gap's question.

## Tests — `tests/security/test_rotation_schedule.py` (26)
They run on the INT-014 `FakeTransit`, extended in the test file with:
- LIST and read of key metadata;
- a creation time per version from a fake clock;
- `min_decryption_version` honoured on decrypt;
- a rotate-failure switch;
- a call log.

- Cadence:
  - the files/10 §3 phrase is asserted from the spec text;
  - `next_rotation_due` over the plain case, the year crossing, two clamps
    (2027 and leap 2028) and an offset instant (months counted in UTC);
  - countdown 10 / 0 / −2.5 days;
  - naive instants are refused.
- Due-ness from Transit metadata:
  - a current key sees reads only;
  - **near-miss control:** one second short of the quarter, the key is not
    rotated and the countdown is 1/86400 d. At the quarter it is rotated;
  - an overdue key is rotated, the countdown restarts from Transit's timestamp
    for the new version, and the next day's tick leaves it alone;
  - only `tenant-*` keys are rotated and labelled (the identity vault's
    `tokenization` key is untouched);
  - the only label is the Transit key name;
  - a vanished key's series is dropped.
- Re-wrap only:
  - one tenant's rotate fails and the next tenant's succeeds. The failed key
    stays at −2.0 d, and both tenants' pre-run ciphertexts decrypt;
  - after two rotations `min_decryption_version` is still 1, the January
    ciphertext decrypts, and `rewrap_field` moves it to v3 with identical data
    bytes;
  - the job's only writes are `…/rotate`, and deletion is never enabled;
  - unreadable metadata is reported, has no series and is not rotated;
  - a rotate that Transit did not record counts as a failure.
- Signal and alert:
  - the catalogue entry is live, a gauge, `[key]`, in days;
  - the alert expression, catalogue-clean, has a runbook anchor that resolves
    to a heading;
  - Prometheus loads the file and compose mounts it.
- Entry point:
  - `make key-rotation` runs the module;
  - the CLI rotates the due keys and prints ids only (no patient text or its
    base64);
  - exit 2 when a rotate fails;
  - exit 4 with no OpenBao pointer;
  - exit 4 when the key list cannot be read.
