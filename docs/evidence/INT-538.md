# Evidence: INT-538 · One laptop command creates a staff user on the synthetic host

**Epic:** E13-infra · **Phase:** P1 · **Sec-Row:** platform · **GitHub:** #906 ·
**Depends on:** INT-460

## Problem

Owner order, 16 Oct 2026, after the staging deploy (main `f7f6b6ee`, smoke 1–7 pass). The realm
`intake` on the synthetic host has no users. Agents never create accounts. So the owner needs one
command to run from the laptop: first for themselves (`platform_owner`), then for the second
approver (`qms_owner`). It replaces the manual steps of `docs/runbooks/second-admin.md` (INT-460).

## Investigation (main `f7f6b6ee`)

1. **The org for the first user is defined nowhere.**
   - `infra/staging/keycloak/intake-realm.json` declares the `org` user-profile attribute (admin-only, pattern `^[A-Za-z0-9][A-Za-z0-9._:/@-]{0,127}$`) and maps it into the token. It gives no value.
   - `docs/runbooks/second-admin.md` step 3 reads "your own org", so it assumes a first user already exists.
   - `docs/release/production-checklist.md` §3 step 2 names no org.
   - files/ and the ADRs name none either.
   - The `org:intake` strings under `tests/` are fixtures, not a decision.

   So the owner types it, once. Round 1 read it from a realm-config attribute and refused while that was empty. On review this was replaced by a read-only probe and one prompt. See "Round 2" below.
2. **Same-org approval is what INT-460 established.** Model-lane approval allows the same org (`approver_must_differ_org` is `False`, `docs/evidence/INT-460.md` §4). So the second approver joins the owner's org.
3. **How kcadm gets the bootstrap password without an argv.**
   - Keycloak's `BaseConfigCredentialsCmd` reads `KC_CLI_PASSWORD` when `--password` is absent. Checked in the source at tag `26.0.0` and on `main`. The admin-CLI guide says the same. The host image is 26.7.4.
   - An SSM command has no TTY, so the interactive prompt fails, and `--password` would show the password in `ps`.
   - So the host script pipes the password into `docker exec -i … bash -c '<fixed text>'`. Inside the container, the `read` builtin sets `KC_CLI_PASSWORD` and `exec`s kcadm.
   - The value is never an argv. It is never in the docker CLI's environment either, which matches `lib.sh`'s rule for this password.
4. **Why the request goes through a file, not a pipe.** This was measured on the laptop against an unreachable local endpoint (`AWS_ENDPOINT_URL=http://127.0.0.1:9`, dummy credentials, so AWS was never contacted). aws-cli 2.37.0 was given the same request two ways:
   - piped as `--cli-input-json file:///dev/stdin`, it stopped at `Error parsing parameter 'cli-input-json': Invalid JSON received`, because the CLI reads a parameter file twice;
   - as a regular file, it got past parsing to `Could not connect to the endpoint URL`.

   This matches the note in `scripts/ci/aws_runner.sh::hand_over`. So the request is a 0600 file in a fresh 0700 `mktemp -d` directory, written by the `printf` builtin, read once and removed at once, with a trap as a backstop.

   `shred` is not used:
   - macOS has no `shred`;
   - on APFS an overwrite writes new blocks and leaves the old ones, so it would erase nothing.

   The value is a one-time password. Keycloak makes the first sign-in replace it (`temporary=true` plus `UPDATE_PASSWORD`), and the reveal command deletes the parameter.
5. **Reaching the host without a deploy.** The host script is 10,152 bytes, or 13,536 characters of base64. It travels inside each AWS-RunShellScript command as `bash -c "$(printf %s '<b64>' | base64 -d)" staff_user_host '<arg>' …`. It reads nothing from the release directory.
6. **The instance role may read `/intake/staging/staff_tmp/*`: verified 16 Oct 2026.** The orchestrator checked this from the host, read-only: a lookup of a parameter that does not exist answered `ParameterNotFound`, not `AccessDenied`. I did not run that lookup myself. The host script still refuses cleanly on another host whose role may not read there (see "Change").

## Change

- `scripts/ops/staff_user.sh` (laptop, bash 3.2-compatible, shellcheck-clean, `LC_ALL=C` so `[a-z]` is ASCII). It works in this order:
  1. **Prompts.** It asks for the username, email and role. It accepts only `platform_owner` or `qms_owner`, and validates every answer before any call. It lower-cases the email.
  2. **Probe.** A read-only `probe` command asks the host whether a `platform_owner` exists.
     - If one does, it never prompts for an org, and sends `-`, so the user inherits that owner's org.
     - If none does, the user must be the `platform_owner`; a `qms_owner` is refused here, before anything is made. It then prompts once for the organisation id. The id must be a slug: 2–40 of `a-z`, `0-9` and `-`. It must also start and end with a letter or digit, because the realm's user-profile rule requires an alphanumeric first character and a slug does not end in a hyphen. Anything else is refused before anything is made.
  3. **The password.** `openssl rand -hex 32` writes the temporary password into the SecureString `/intake/staging/staff_tmp/<username>` through the 0600 request. A waiting parameter is never overwritten: the command refuses and prints the reveal command.
  4. **Create.** It sends the `create` command. Its arguments are the username, email, role, parameter name, region, and the slug or `-`. No secret travels in it.
  5. **Output.**
     - On success: `created`, then the reveal command. That command is `aws ssm get-parameter … --with-decryption --query Parameter.Value --output text && aws ssm delete-parameter …`.
     - On a refusal: `refused: <reason>`. The unused parameter is deleted.
     - When no result line comes back from create: `unknown: …` and the reveal command. The parameter is kept, because the user may exist.
     - When no result line comes back from the probe: `unknown: …; nothing was created`.
- `infra/staging/staff_user_host.sh` (host, two modes).
  - **Both modes** re-check every argument with the shapes the laptop uses. Then they check that the instance role may read `/intake/staging/staff_tmp/*`. That check is a lookup without decryption, so its answer is a name or an error, never a secret, and a missing parameter still proves the permission.
  - **On `AccessDenied`** it refuses in one line. The line names the role and the statement to add, for example `{"Effect":"Allow","Action":"ssm:GetParameter","Resource":"arn:aws:ssm:<region>:<account>:parameter/intake/staging/staff_tmp/*"}`, with the region and account taken from the denial.
  - **Both modes** then read `KEYCLOAK_ADMIN_PASSWORD` from `/etc/intake-staging/.env`, requiring the generated 64-hex shape. They log kcadm in as above, with `--config` in a fresh 0700 directory inside the container that is removed on every exit path.
  - **`probe`** lists the `platform_owner`s and prints `owner-org <org>` or `no-owner`. It refuses if they disagree, or if one has no org. It only reads.
  - **`create`** does the following, in order:
    1. Refuses an existing username or email.
    2. Applies the org rule:
       - with a `platform_owner`, their org; an org argument that differs is refused;
       - with none, the user must be the `platform_owner` and the slug must be given;
       - no org is ever invented.
    3. Reads the temporary password from SSM.
    4. Creates the user: enabled, `emailVerified`, required actions `webauthn-register` and `UPDATE_PASSWORD`.
    5. Grants the role.
    6. Sets the password from stdin with `temporary: true`.
    7. If step 5 or 6 fails, deletes the user again.
- `docs/runbooks/second-admin.md`: one line, which keeps INT-460's 15-line limit. It points to the one command, says the organisation id is asked once on the owner's first run only, and keeps steps 1–7 as the manual fallback.
- Tests, 96 in total.
  - `tests/infra/test_staff_user.py` (63) holds the laptop flows end to end. `tests/infra/test_staff_user_host.py` (33) holds the host half alone and both scripts as files.
  - `tests/infra/staff_user_world.py` holds the test world, and `tests/infra/staff_user_fakes.py` the fake `aws`, `docker` and `openssl`.
  - **The fakes.**
    - `aws` keeps a parameter store and runs the send-command text with `sh`, so the decoded host script runs against the same fakes. Each send-command can be told to run, hang or fail.
    - `docker` plays the Keycloak container: kcadm, the container's file system, and a login that checks the bootstrap password on stdin.
    - `openssl` returns a known value.
    - An IAM denial can be simulated, using AWS's documentation account id.
  - **The laptop half** runs under `/bin/bash`, which is 3.2.57 on macOS.
  - **What the tests cover:**
    - the prompt order, with the org prompt only when no `platform_owner` exists and never once one does;
    - 20 input near misses and 12 org-slug near misses: empty, 1 or 41 characters, capitals, colon, underscore, dot, space, a leading or trailing hyphen, non-ASCII, a quote. Each is refused before anything is generated;
    - slugs at the edges (2 and 40 characters, mixed) accepted;
    - the host re-check of every probe and create argument, and the laptop's refusal of an `AWS_REGION` or instance id that would break the command;
    - the org rule:
      - the second approver inherits the owner's org, and no org travels;
      - a differing org is refused, and the same org is accepted;
      - with no org given and no owner, the host refuses;
      - the first user must be the `platform_owner`, on both the laptop and the host;
    - the IAM refusal line, from the probe (before Keycloak is touched) and from create;
    - neither secret in any argv, the command parameters or any output, and each on stdin only;
    - each command equals the committed host script;
    - the reveal command, which shows the password once and deletes the parameter;
    - refusals: an existing username or email, owners in two orgs, an owner without an org, a waiting parameter;
    - rollback after a failed role grant or password set;
    - a wrong or unreadable bootstrap password, and a stopped container;
    - an unanswered probe, and an unanswered create;
    - the kcadm config deleted on every path that made one;
    - shellcheck, the same shapes in both scripts, a line filter on the secret variables, and the realm-config route gone.
- `docs/security/threat-model.md` `platform` row: the threat, the control and the tests.
- Backlog row INT-538, the three pinned counts (355 → 356, with the reason), and a regenerated `files/11_ISSUE_BACKLOG.md`.

Nothing here was run against AWS or the host. No user was created and no real secret was read.
