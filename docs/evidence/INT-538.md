# Evidence: INT-538 · One laptop command creates a staff user on the synthetic host

**Epic:** E13-infra · **Phase:** P1 · **Sec-Row:** platform · **GitHub:** #906 ·
**Depends on:** INT-460

## Problem

Owner order, 16 Oct 2026, after the staging deploy (main `f7f6b6ee`, smoke 1–7 pass). The realm
`intake` on the synthetic host has no users. Agents never create accounts. So the owner needs one
command to run from the laptop: first for themselves (`platform_owner`), then for the second
approver (`qms_owner`). It replaces the manual steps of `docs/runbooks/second-admin.md` (INT-460).

## Investigation (main `f7f6b6ee`)

1. **The org for the first user is defined nowhere.**
   - `infra/staging/keycloak/intake-realm.json` declares the `org` user-profile attribute (admin-only, pattern `^[A-Za-z0-9][A-Za-z0-9._:/@-]{0,127}$`) and maps it into the token. It gives no value.
   - `docs/runbooks/second-admin.md` step 3 reads "your own org", so it assumes a first user already exists.
   - `docs/release/production-checklist.md` §3 step 2 names no org.
   - files/ and the ADRs name none either.
   - The `org:intake` strings under `tests/` are fixtures, not a decision.

   So the host script reads the org from one named place: the realm config's `attributes."intake.first_staff_org"`. That place is empty today, so the script refuses with a message that says where to set it. No value is invented. After the first `platform_owner` exists, every later user gets that owner's org (runbook steps 3–4).
2. **Same-org approval is what INT-460 established.** Model-lane approval allows the same org (`approver_must_differ_org` is `False`, `docs/evidence/INT-460.md` §4). So the second approver joins the owner's org.
3. **How kcadm gets the bootstrap password without an argv.**
   - Keycloak's `BaseConfigCredentialsCmd` reads `KC_CLI_PASSWORD` when `--password` is absent. Checked in the source at tag `26.0.0` and on `main`. The admin-CLI guide says the same. The host image is 26.7.4.
   - An SSM command has no TTY, so the interactive prompt fails, and `--password` would show the password in `ps`.
   - So the host script pipes the password into `docker exec -i … bash -c '<fixed text>'`. Inside the container, the `read` builtin sets `KC_CLI_PASSWORD` and `exec`s kcadm.
   - The value is never an argv. It is never in the docker CLI's environment either, which matches `lib.sh`'s rule for this password.
4. **Why the request goes through a file, not a pipe.** This was measured on the laptop against an unreachable local endpoint (`AWS_ENDPOINT_URL=http://127.0.0.1:9`, dummy credentials, so AWS was never contacted). aws-cli 2.37.0 was given the same request two ways:
   - piped as `--cli-input-json file:///dev/stdin`, it stopped at `Error parsing parameter 'cli-input-json': Invalid JSON received`, because the CLI reads a parameter file twice;
   - as a regular file, it got past parsing to `Could not connect to the endpoint URL`.

   This matches the note in `scripts/ci/aws_runner.sh::hand_over`. So the request is a 0600 file in a fresh 0700 `mktemp -d` directory, written by the `printf` builtin, read once and removed at once, with a trap as a backstop.

   `shred` is not used:
   - macOS has no `shred`;
   - on APFS an overwrite writes new blocks and leaves the old ones, so it would erase nothing.

   The value is a one-time password. Keycloak makes the first sign-in replace it (`temporary=true` plus `UPDATE_PASSWORD`), and the reveal command deletes the parameter.
5. **Reaching the host without a deploy.** The host script is 7,834 bytes, or 10,448 characters of base64. It travels inside the AWS-RunShellScript command as `bash -c "$(printf %s '<b64>' | base64 -d)" staff_user_host '<username>' '<email>' '<role>' '<parameter>' '<region>'`. It sources nothing from the release directory.
6. **Assumption, not verified here.** The instance role reads `/intake/staging/*`, as INT-428's `load_provider_key.sh` and INT-460 step 6 assume. The repo holds no IAM policy to check this against. If the role cannot read `/intake/staging/staff_tmp/<username>`, the host refuses with "the temporary password is not in SSM, or is not a generated one". In that case it creates nothing.

## Change

- `scripts/ops/staff_user.sh` (laptop, bash 3.2-compatible, shellcheck-clean). It works in this order:
  - **Prompts.** It asks for the username, email and role. It accepts only `platform_owner` or `qms_owner`, and validates every answer before any call. It lower-cases the email.
  - **The password.** `openssl rand -hex 32` writes the temporary password into the SecureString `/intake/staging/staff_tmp/<username>` through the 0600 request. A waiting parameter is never overwritten: the command refuses and prints the reveal command.
  - **The host command.** It sends the host script base64-wrapped. The command carries no secret.
  - **The wait.** It waits up to 2 minutes for the host's single result line.
  - **Output.**
    - On success: `created`, then the reveal command. That command is `aws ssm get-parameter … --with-decryption --query Parameter.Value --output text && aws ssm delete-parameter …`.
    - On a refusal: `refused: <reason>`. The unused parameter is deleted.
    - When no result line comes back: `unknown: …` and the reveal command. The parameter is kept, because the user may exist.
- `infra/staging/staff_user_host.sh` (host). Steps, in order:
  1. Re-checks all five arguments with the same shapes as the laptop.
  2. Reads `KEYCLOAK_ADMIN_PASSWORD` from `/etc/intake-staging/.env` and requires the generated 64-hex shape.
  3. Logs kcadm in, as above, with `--config` in a fresh 0700 directory inside the container. The directory is removed on every exit path.
  4. Refuses an existing username or email.
  5. Resolves the org: the one org shared by the `platform_owner`s, or for the first user the realm config's. It refuses if `platform_owner`s disagree, if one has no org, or if no org is defined. The org must match the user-profile pattern.
  6. Reads the temporary password from SSM.
  7. Creates the user: enabled, `emailVerified`, required actions `webauthn-register` and `UPDATE_PASSWORD`, in the org.
  8. Grants the role.
  9. Sets the password from stdin with `temporary: true`.
  10. If step 8 or 9 fails, deletes the user again.
- `docs/runbooks/second-admin.md`: one line, which keeps INT-460's 15-line limit. It points to the one command, says where the first org is set, and keeps steps 1–7 as the manual fallback.
- `tests/infra/test_staff_user.py`, 71 tests. `tests/infra/staff_user_world.py` holds the test world, and `tests/infra/staff_user_fakes.py` the fake `aws`, `docker` and `openssl`.
  - **The fakes.** `aws` keeps a parameter store and runs the send-command text with `sh`, so the decoded host script runs against the same fakes. `docker` plays the Keycloak container: kcadm, the container's file system, and a login that checks the bootstrap password on stdin. `openssl` returns a known value.
  - **The laptop half** runs under `/bin/bash`, which is 3.2.57 on macOS.
  - **What the tests cover:**
    - the prompt order;
    - 20 near misses: role typos, bad emails, empty or unsafe usernames, all refused before any call;
    - the host re-check of each of the five arguments, and the laptop's refusal of an `AWS_REGION` or instance id that would break the command;
    - neither secret in any argv, the command parameters or any output, and each on stdin exactly once;
    - the decoded command equals the committed host script;
    - the reveal command, which shows the password once and deletes the parameter;
    - refusals: existing username or email, no org defined, an unreadable realm config, owners in two orgs, an owner without an org, a waiting parameter;
    - rollback after a failed role grant or password set;
    - a wrong or unreadable bootstrap password, and a stopped container;
    - an unanswered host;
    - the kcadm config deleted on every path that made one;
    - shellcheck, the same shapes in both scripts, and a line filter on the secret variables.
- `docs/security/threat-model.md` `platform` row: the threat, the control and the test.
- Backlog row INT-538, the three pinned counts (355 → 356, with the reason), and a regenerated `files/11_ISSUE_BACKLOG.md`.

Nothing here was run against AWS or the host. No user was created and no real secret was read.
