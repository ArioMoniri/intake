# INT-236 — Adaptive answer-dependent flow + Hızlı/Detaylı modes (dev tier)

Owner directive: "each question for each department should be updated and
next qs should be with regard to answer of previous question and these
should be with regard to guidelines and in 2 modes of fast and complete as
in before coming and after coming to hospital".

## What this is, honestly (mechanism, not clinical content)

The guideline-sourced content itself is the physician-gated protocol chain
(packages/protocols, INT-040/041/096) — nothing clinical is invented here.
This iteration ships the MECHANISM in the dev-tier packs:

- **Answer-dependent flow**: `IntakeQuestion.askIf` — a serializable DATA
  predicate `{questionId, includesAny}` MIRRORING the DSL's `ask_if` on
  `packages/protocols/src/protocols/dsl.py::Slot` (data, not functions, so
  compiled packs slot in without UX change; stated in the code headers).
  `applicableQuestions` / `nextApplicableQuestion` / `missingQuestions`
  are exported from the pack layer (`apps/mobile/src/lib/intake/
  questions.ts`) so StepFlow, the voice-first prefill AND the dialogue
  engine (int-235's surface, consuming `packForDepartment`) all inherit
  the same gating. Progress is dynamic: "n of applicable".
- **Hızlı/Detaylı modes (02 §2 table, dev tier)**: mode context on the
  note state — Hızlı default (pre-hospital, the existing voice-first
  flow); a quiet "Hastanedeyim" switch sets Detaylı, which (a) runs the
  02 §33 environment self-check ("Yanınızda başkası var mı?", one calm
  question) and, when privacy is not established, DEFERS sensitive
  sections — not asked quieter, not asked in text — carrying the
  clinician-visible marker `eksik: ortam uygun değildi` into the note as
  a `deferred` section in `buildNote`; and (b) keeps a persistent
  "Sıranız geldi" affordance that checkpoints INSTANTLY (no dialog) into
  the v2-partial review (existing answers + an "eksik" section list +
  resume), with zero lost turns pinned at the reducer level.
- Stated plainly: the dev packs carry no sensitive-flagged questions
  (wellbeing instruments are a separate, licence-BLOCKED surface —
  HB-L2/HB-L3), so the deferral mechanism is LIVE with the wellbeing
  entry point as its only consumer (`WELLBEING_DEFERRAL` in note.ts).

## askIf gates added (structurally obvious, zero clinical judgment)

| question | gate |
|---|---|
| `pain_character` | complaint includesAny [pain] — the question literally asks how the pain feels |
| `radiation` | complaint includesAny [pain] — where the pain spreads |
| `gastro_meal` | complaint includesAny [stomach] — meal relation of the stomach complaint |
| `gastro_bowel` | complaint includesAny [stomach] — bowel habit of the stomach complaint |

An edit that unmets a gate KEEPS the committed answer and marks its HPI
line "(koşul değişti)" in the review — patient words are never silently
discarded (test-pinned).

## Gates considered and REFUSED — clinical judgment, for the pack owners

- `gastro_character` ("Ağrının niteliği" in the gastro pack) on
  complaint [pain|stomach]: whether epigastric burning without the "pain"
  chip still warrants a character question is a clinical call.
- Whether `gastro_meal`/`gastro_bowel` should ALSO open on complaint
  [pain] (abdominal pain without the stomach chip): clinical call; the
  directive named [stomach] only, and that is what shipped.
- `neuro_character`/`neuro_trigger`/`neuro_course` on complaint
  [headache]: the neuro pack serves non-headache presentations too;
  deciding which dimensions still apply is clinical.
- `eye_vision` on complaint set, `uro_urination` on complaint set,
  `gyn_cycle` on complaint set: all pack-defining dimensions a specialist
  may want asked regardless of the chief-complaint chips — clinical.
- Any severity/associated gating: never structural.
