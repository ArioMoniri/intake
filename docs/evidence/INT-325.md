# INT-325 — production refuses dev bypasses and dev default credentials

**Date:** 26 September 2026 · **Branch:** `int-325-prod-refuses-dev` · **Sec-Row:** files/10 §9 `secrets`

Source: production audit 2026-09-26 (`docs/audit/2026-09-26-production-audit.md`), findings
**F04** (dev bypass flags have no production refusal), **F14** (in-code default credentials)
and the **F13** silent fallback (the OTP tier wired to a delivery adapter that sends nothing).

## What was wrong

Only three places in the platform looked at `INTAKE_ENV` (DevNullScanner, the OpenBao
provider, LiveKit room tokens). Under `INTAKE_ENV=prod` nothing refused:

- `INTAKE_DEV_OTP_PEEK` (anyone can read any phone's pending code: account takeover),
  `INTAKE_DEV_ALLOW_UNATTESTED`, `INTAKE_DEV_TOKEN_PATIENT` / `INTAKE_DEV_TOKEN_ADMIN`
  (static bearers onto the synthetic accounts), `INTAKE_DEV_GEORGE_TTS`;
- `INTAKE_API_KEK_MODE=file-dev` (process-local KEKs: notes unreadable after a restart);
- a missing `INTAKE_API_DB_URL` / `INTAKE_API_AUDIT_DB_URL` / `INTAKE_API_BOOTSTRAP_DB_URL` /
  `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`, each of which silently fell back to the compose
  dev role's in-code credential;
- the OTP tier, hard-wired to `DevLogDeliveryAdapter`, which answers 202 and sends no SMS.

## What was built

- `services/api/src/intake_api/settings.py`
  - `is_prod_env(environ)`: `INTAKE_ENV` stripped, lower-cased, `startswith("prod")`. This is
    the rule `intake_platform.documents` and `room_tokens` already use and the audit's F04
    remedy names. It is a superset of `secrets.py`'s exact `== "prod"`, so every environment
    the OpenBao gate treats as prod is refused here too.
  - `refuse_dev_config_in_prod(environ)`: a no-op outside prod. In prod it collects every
    offence and raises one `ProdConfigRefusedError` naming all of them: any non-empty
    `INTAKE_DEV_*` variable (by prefix, so a dev gate added later is covered without being
    listed), `INTAKE_API_KEK_MODE=file-dev`, and each missing or empty credential variable.
    The message carries variable **names only**, never values (invariant 6).
  - `ApiSettings.from_env` calls it first, before any dev default can apply, and sets the new
    `production` field.
- `services/api/src/intake_api/app.py`
  - `_auth_from_settings`: under `production` the OTP tier is never wired to the dev logger.
    No contracted SMS adapter exists on main, so the tier stays unconfigured and every
    `/v1/auth` route answers `503 otp_auth_unconfigured`. It never answers a fake "sent".
  - `_documents_from_env` reads the MinIO pair through the same constants the guard checks,
    so the list that is required and the variables that are read cannot drift.

The boot path is `create_app()` → `wiring_from_env()` → `ApiSettings.from_env()`, so the
refusal happens before any engine, cipher, OpenBao client or MinIO client is built. Dev
behaviour is unchanged: outside prod the guard returns immediately and every default and
opt-in phrase behaves as before.

## Follow-up in the same PR: prod readiness no longer waits on the dev bearers

The first commit made prod refuse `INTAKE_DEV_TOKEN_*` at boot. `/readyz`, however, still
carried the INT-197 `dev_auth` check, which is ready only when both dev bearers are set. A prod
API therefore answered 503 on `/readyz` forever, even with every real dependency healthy. The
fix is in `create_app` (`app.py`): the `dev_auth` readiness check is mounted only when
`settings.production` is false. In prod, readiness is `db` + `audit_store`. Dev is unchanged.

Three tests were added to `tests/api/test_prod_refuses_dev_config.py`. Each uses the harness's
healthy sqlite db and audit store, with neither dev bearer set:

- `test_prod_is_ready_with_every_real_dependency_healthy`: prod → 200,
  `checks == {db: ok, audit_store: ok}`.
- `test_prod_readiness_still_fails_on_a_real_dependency`: near-miss control. Prod with a dead
  audit store → 503, `audit_store: error`, so readiness did not become vacuous.
- `test_dev_readiness_still_requires_the_dev_bearers`: dev control → 503,
  `{db: ok, audit_store: ok, dev_auth: error}`, exactly as before.

## Follow-up 2 in the same PR: only the dev environment waits on the dev bearers

Follow-up 1 mounted the `dev_auth` readiness check everywhere except prod. Staging
(`INTAKE_ENV=staging`, no `INTAKE_DEV_*`; PR #549's infra/staging) is neither prod nor dev, so
it still carried the check and reported `/readyz` 503 forever. The dev bearers belong to the
dev environment only, so the condition now says exactly that.

- `settings.py`: `ApiSettings.environment` is the normalised `INTAKE_ENV`: stripped,
  lower-cased, and unset or empty means `dev`, the same default `secrets.py` uses. It replaces
  the boolean `production` field and is now the single source of truth. `production` is a
  property (`environment` starts with `prod`, the rule is unchanged). The new property
  `dev_tier_expected` is `environment == "dev"`. `from_env` sets `environment` from
  `environment_name(os.environ)`, and `is_prod_env` is re-expressed through that same function.
- `app.py`: the `dev_auth` readiness check is mounted only when `settings.dev_tier_expected`.
- The two DevLog tests build their settings with `environment="prod"` / `"dev"` instead of the
  removed `production=` field. This follows the API change; their assertions are unchanged.

The readiness tests now build their settings exactly as the service does (`ApiSettings.from_env`
under a given `INTAKE_ENV`, with every `INTAKE_DEV_*` removed) over the harness's healthy db
and audit store:

- `test_non_dev_environment_is_ready_with_every_real_dependency_healthy[prod|staging]`: 200,
  `checks == {db: ok, audit_store: ok}`.
- `test_non_dev_readiness_still_fails_on_a_real_dependency[prod|staging]`: near-miss control.
  A dead audit store → 503, `audit_store: error`.
- `test_dev_readiness_still_requires_the_dev_bearers[unset|dev]`: 503,
  `{db: ok, audit_store: ok, dev_auth: error}`, exactly as before.

## Follow-up 3 in the same PR: every non-dev environment is as strict as prod

Decision: a public staging host must be as strict as prod on configuration. The
dev-default-credential refusal, the `INTAKE_DEV_*` refusal, the `file-dev` KEK refusal and the
OTP dev-logger refusal now apply whenever `INTAKE_ENV` is not dev.

**Dev is defined once.** `settings.is_dev_env(environ)` returns true when `INTAKE_ENV`,
stripped and lower-cased, is unset, empty or `dev`. `ApiSettings.dev_tier_expected` uses the
same `_is_dev_name`. I checked what the repository actually sets before choosing the set:

- tests: `prod`, `dev` or unset (`tests/security/test_openbao_wiring.py`,
  `tests/security/test_document_store*.py`, `tests/voice/test_room_tokens.py`);
- CI (`.github/`), the Makefile, compose files and `env.example`: no `INTAKE_ENV` at all;
- PR #549 (`infra/staging/compose.yaml`): `staging`.

No `test`, `ci` or `local` value exists anywhere, so the dev set is only {unset, empty,
`dev`}. `test` is strict, and a test asserts that on purpose.

**Changes**

- `settings.py`:
  - `is_prod_env` and `_is_prod_name` are removed; `is_dev_env` and `_is_dev_name` replace them.
  - `refuse_dev_config_in_prod` is now `refuse_dev_config_outside_dev`, and is a no-op only
    in dev.
  - `ProdConfigRefusedError` is now `DevConfigRefusedError`.
  - `PROD_REQUIRED_CREDENTIALS` is now `NON_DEV_REQUIRED_CREDENTIALS`.
  - The `production` property is removed; `dev_tier_expected` is the only derived flag.
  - The refusal message names the environment: `INTAKE_ENV=<name> is not dev ...`.
- `app.py`: `_auth_from_settings` refuses the dev delivery logger whenever the dev tier is not
  expected. PR #549's own compose comment gives the reason: wiring the OTP tier in staging
  "would wire the dev delivery logger".

The renames were made first, as a pure refactor, and confirmed green (35/35) before the new
tests were written. That makes the red run below purely behavioural. The first two sections of
this file record the red output under the old names, which were the names at that time.

**Tests.** The refusal suite runs on a parametrised `strict_env` fixture, once for `prod` and

- each dev flag, a non-phrase flag value and a future flag by prefix;
- `file-dev` KEK;
- each of the 5 credential variables, unset and empty;

**Cross-PR consequence (PR #549).** The staging api service in `infra/staging/compose.yaml`
sets the three DB URLs, but it does not set `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`, and that
tier runs no MinIO at all. Once both PRs are on main, the staging API is refused at boot with
`credential variable(s) missing: MINIO_ROOT_USER, MINIO_ROOT_PASSWORD`. This is the refusal
working as designed. Staging needs either an object store with real credentials, or a
deliberate documents-off mode; neither is built here. Staging never sets any `INTAKE_DEV_*`,
uses KEK mode `transit` and sets no tokenization key, so none of the other refusals affect it.
