# INT-325 — production refuses dev bypasses and dev default credentials

**Date:** 26 September 2026 · **Branch:** `int-325-prod-refuses-dev` · **Sec-Row:** files/10 §9 `secrets`

Source: production audit 2026-09-26 (`docs/audit/2026-09-26-production-audit.md`), findings
**F04** (dev bypass flags have no production refusal), **F14** (in-code default credentials)
and the **F13** silent fallback (the OTP tier wired to a delivery adapter that sends nothing).

## What was wrong

Only three places in the platform looked at `INTAKE_ENV` (DevNullScanner, the OpenBao
provider, LiveKit room tokens). Under `INTAKE_ENV=prod` nothing refused:

- `INTAKE_DEV_OTP_PEEK` (anyone can read any phone's pending code: account takeover),
  `INTAKE_DEV_ALLOW_UNATTESTED`, `INTAKE_DEV_TOKEN_PATIENT` / `INTAKE_DEV_TOKEN_ADMIN`
  (static bearers onto the synthetic accounts), `INTAKE_DEV_GEORGE_TTS`;
- `INTAKE_API_KEK_MODE=file-dev` (process-local KEKs: notes unreadable after a restart);
- a missing `INTAKE_API_DB_URL` / `INTAKE_API_AUDIT_DB_URL` / `INTAKE_API_BOOTSTRAP_DB_URL` /
  `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`, each of which silently fell back to the compose
  dev role's in-code credential;
- the OTP tier, hard-wired to `DevLogDeliveryAdapter`, which answers 202 and sends no SMS.

## What was built

- `services/api/src/intake_api/settings.py`
  - `is_prod_env(environ)`: `INTAKE_ENV` stripped, lower-cased, `startswith("prod")`. This is
    the rule `intake_platform.documents` and `room_tokens` already use and the audit's F04
    remedy names. It is a superset of `secrets.py`'s exact `== "prod"`, so every environment
    the OpenBao gate treats as prod is refused here too.
  - `refuse_dev_config_in_prod(environ)`: a no-op outside prod. In prod it collects every
    offence and raises one `ProdConfigRefusedError` naming all of them: any non-empty
    `INTAKE_DEV_*` variable (by prefix, so a dev gate added later is covered without being
    listed), `INTAKE_API_KEK_MODE=file-dev`, and each missing or empty credential variable.
    The message carries variable **names only**, never values (invariant 6).
  - `ApiSettings.from_env` calls it first, before any dev default can apply, and sets the new
    `production` field.
- `services/api/src/intake_api/app.py`
  - `_auth_from_settings`: under `production` the OTP tier is never wired to the dev logger.
    No contracted SMS adapter exists on main, so the tier stays unconfigured and every
    `/v1/auth` route answers `503 otp_auth_unconfigured`. It never answers a fake "sent".
  - `_documents_from_env` reads the MinIO pair through the same constants the guard checks,
    so the list that is required and the variables that are read cannot drift.

The boot path is `create_app()` → `wiring_from_env()` → `ApiSettings.from_env()`, so the
refusal happens before any engine, cipher, OpenBao client or MinIO client is built. Dev
behaviour is unchanged: outside prod the guard returns immediately and every default and
opt-in phrase behaves as before.

## Follow-up in the same PR: prod readiness no longer waits on the dev bearers

The first commit made prod refuse `INTAKE_DEV_TOKEN_*` at boot. `/readyz`, however, still
carried the INT-197 `dev_auth` check, which is ready only when both dev bearers are set. A prod
API therefore answered 503 on `/readyz` forever, even with every real dependency healthy. The
fix is in `create_app` (`app.py`): the `dev_auth` readiness check is mounted only when
`settings.production` is false. In prod, readiness is `db` + `audit_store`. Dev is unchanged.

Three tests were added to `tests/api/test_prod_refuses_dev_config.py`. Each uses the harness's
healthy sqlite db and audit store, with neither dev bearer set:

- `test_prod_is_ready_with_every_real_dependency_healthy`: prod → 200,
  `checks == {db: ok, audit_store: ok}`.
- `test_prod_readiness_still_fails_on_a_real_dependency`: near-miss control. Prod with a dead
  audit store → 503, `audit_store: error`, so readiness did not become vacuous.
- `test_dev_readiness_still_requires_the_dev_bearers`: dev control → 503,
  `{db: ok, audit_store: ok, dev_auth: error}`, exactly as before.

In prod there is no auth-tier readiness check. The OTP tier is unconfigured until an SMS
adapter is contracted, and the OIDC tier belongs to INT-131/180. A prod API with healthy
dependencies is therefore ready and answers 503 per route (`dev_auth_unconfigured` /
`otp_auth_unconfigured`), rather than being not-ready as a whole. An auth-tier readiness check
belongs with the real tier when it lands.
