# INT-400: The on-device MHRS SMS parser refuses an ambiguous date, as the server does

**Epic:** E08-mobile · **Phase:** P1 · **Sec-Row:** mobile · **GitHub:** #666
**Found by:** INT-122 (PR #663), docs/evidence/INT-122.md §10.4. This branch is cut from
`origin/int-122-enabiz-mhrs`, because #663 files this row and had not merged when the branch
was cut.

## Acceptance (verbatim from docs/backlog/issues.yaml)
> the device parser applies the server's ambiguity rule: an ambiguous day/month is refused
> with a prompt to confirm the date, never guessed; one shared fixture drives both parsers

GitHub #666 adds a second line: *"when INT-399 fixes the MHRS order from a real sample, both
parsers switch together, pinned by that fixture"*.

## Problem
INT-134's `parseMhrsSms` (`apps/mobile/src/lib/taxonomy/mhrsSms.ts`) read every
`d.m.yyyy` date day-first. Its own fixture, `03.09.2026`, became 3 September. The server's
guard (`intake_platform/records/turkish_dates.py`, INT-122) refuses the same string as
`PrintedDateAmbiguous`: day-first and month-first are both real days, a month apart, and no
committed source states the order an MHRS SMS prints (docs/backlog/blockers.md INT-122
Ask 2). So one pasted message gave a date on the device and a refusal on the server. A visit
date read the wrong way round books the wrong day, and nothing on the screen makes the wrong
reading look wrong (CLAUDE.md invariant 22).

The red run below shows the device's old reading differed from the server's on 13 of the 21
shared messages. On 8 of them the device **guessed a date where the server refuses**. On 5
it found no date where the server reads one.

## Change

**The rule is ported, not rewritten.** `apps/mobile/src/lib/taxonomy/turkishDates.ts`
follows `turkish_dates.py` line for line:
- `parsePrintedDate` is `parse_printed_date`, and `findPrintedDate` is `find_printed_date`;
- `order` is the same seam, with no default. `parseMhrsSms` passes none, as `parse_mhrs_sms`
  passes none;
- the refusal names are the server's `VisitFieldRefusal`: `ambiguous`, `not_found`,
  `unreadable`;
- evaluation order matches the server's. Month-name forms are scanned before numeric ones,
  and the first date-shaped token that will not read refuses the whole message;
- `TURKISH_MONTHS` and `fold_tr` are ported with it.

Python's regex classes are Unicode-aware, and JavaScript's shorthand classes are not. A
straight transliteration would have read different characters as digits, letters and
spaces. So each class is spelled out, and each was compared with CPython 3.12, one code
point at a time, over every code point Unicode 15.0 assigns (scratch scripts, not
committed):

| Python | device | code points that differ |
|---|---|---|
| `\d` | `\p{Nd}` | 0 |
| `\w` | `[\p{L}\p{N}_]` | 0 |
| `[^\W\d_]` | `[\p{L}\p{Nl}\p{No}]` | 0 |
| `\s` | the explicit class in the module | 0 |
| `int()` of each of the 680 `Nd` digits | `digitValue` | 0 |
| `fold_tr` → month-name lookup | `foldTr` | 0 |

On the last row: 297 code points fold differently under `toLowerCase` and `casefold`. Only
five of them (ß, ẞ, ſ, ﬅ, ﬆ) fold to letters a month name uses, and those five are mapped.
Each of the other 292 folds, on both sides, to a string holding a letter no month name has.
So a word is a month on the device exactly when it is one on the server.

All six patterns in the module are regex literals. The app's own Hermes compiler
(`hermes-compiler@250829098.0.17`) compiled all six, lookbehinds, `\p{…}` classes and
backreference included. A negative control with an invalid property name was rejected at
build time, so the check is real.

**The parser** (`mhrsSms.ts`): `ParsedMhrsSms` gains `dateRefusal`, which is null exactly
when `dateIso` is set. The old `DATE` regex and its day-first `isoDate` are gone. Hospital,
branch and time are unchanged.

**The screen** (`visits.ts`, `(tabs)/visits/new.tsx`): a new notice, `ambiguous_date`.
- The date field is left **empty**, with neither reading filled in. A date already in the
  field is cleared too, because it is not known to be this message's date. An empty field is
  the one state that cannot pass for an answer.
- The notice renders through the existing `AnnouncedText` error slot above the fields. It
  asks the patient to write the date in the existing date field. No new component was added.
- It outranks the unknown-clinic notice. Saving already refuses a visit with no branch
  (`missing_fields`). A visit with no date saves, so this notice is the only thing that asks
  for the date.
- A message whose only reading is an ambiguous date is no longer called "unreadable".
- Two explicit options were considered and not built. The server's `ambiguous` also covers
  "two different dates printed". In that case the two readings are not the choice. And
  showing the device's own readings as options would put a guess back on screen.

**One new string** (tr is the source of truth; en mirrors it):

| key | tr | en |
|---|---|---|
| `visits.new.smsAmbiguousDate` | Mesajdaki tarihten randevunuzun hangi gün olduğunu kesin anlayamadık. Tarihi aşağıya siz yazın. | We could not tell for sure which day the message's date means. Please write the date below yourself. |

The copy covers both `ambiguous` cases: a date that reads two ways, and two dates printed.
It does not say which. Register findings:
- `siz` throughout, and B1 (8 and 4 words).
- It uses the short imperative `yazın` in a notice, the same form as its siblings
  `smsNoDate` ("ekleyin") and `smsUnknownBranch` ("seçin").
- The INT-253 prose-register gate does not flag it. Its key does not end in
  `body|hint|intro|info|footer|sub|why`. So it cannot be entered in `PROSE_REGISTER_FINDINGS`,
  which is asserted by exact equality. It is recorded here instead, for the same copy-owner
  decision as the 41 recorded keys.
- **Flagged for clinical-reviewer sign-off**: new patient-facing copy on a `risk:clinical`
  row.
- The sentence is not clinical or legal, so it takes no `[REVIEW]` mark. `REVIEW_FLAGGED_KEYS`
  is exact.

**The shared fixture**, `tests/fixtures/records/mhrs_dates.json`, has 30 `printed` rows and 21
`messages` rows:
- `tests/records/test_mhrs.py` holds the server to it;
- `turkishDates.test.ts` (printed rows) and `mhrsSms.test.ts` (message rows) hold the device
  to it;
- the pytest also requires that the table keep its guard rows: INT-134's `03.09.2026` as
  ambiguous in both kinds of row, the near-miss controls `13.09.2026` and `05.05.2026` read,
  and every refusal class;
- the pytest requires that only the `seam_*` rows carry an order, and that the two app tests
  keep reading this file.

When INT-399 fixes the order, the message rows change, and both sides stay red until both
change. That is how the table meets the issue's second line. The rows are synthetic, with
masked names. The six INT-134 message shapes are carried over verbatim.

**Gate change, one line, recorded:** `tests/release/test_i18n_complete.py`
`HARDCODED_EXEMPT` gains `lib/taxonomy/turkishDates.ts`. The entry states why. The twelve
month names and the I/İ fold are matched against printed text and never rendered. The server
creates no tr key for the same table, for the same reason (`turkish_dates.py`). Its
`test_every_hardcoded_exemption_is_still_load_bearing` case passes.

## Tests (TDD)
- `tests/fixtures/records/mhrs_dates.json` — the table.
- `tests/records/test_mhrs.py` — the server against every row, plus the table's own pins.
- `apps/mobile/src/lib/taxonomy/turkishDates.test.ts` — the device against every `printed`

- `apps/mobile/src/lib/taxonomy/mhrsSms.test.ts` — the device against every `messages` row,
  on two counts: the same date or none, and the same refusal. INT-134's own tests are updated
  where they encoded the guess (`03.09.2026` and `07.09.2026` are now ambiguous).
- `apps/mobile/src/lib/visits.test.ts` — the reducer. The date is asked for and left empty. A
  stale date is cleared. The notice outranks the clinic notice. An ambiguous-only message is
  not "unreadable". The patient's own date then saves.
- `apps/mobile/e2e/visits.spec.ts` — source pins. `turkishDates.ts` is pure, the parser
  imports the port, and the screen maps the notice. tr and en both carry the key.

## Acceptance, line by line
- **"the device parser applies the server's ambiguity rule"** — the rule is ported line for
  line in `turkishDates.ts`, and the character classes were matched to Python's code point by
  code point. Every shared row agrees on both sides. The ten mutants show that a device that
  departs from the rule fails a row.
- **"an ambiguous day/month is refused with a prompt to confirm the date, never guessed"** —
  `dateIso` is null and `dateRefusal: "ambiguous"`. The screen shows
  `visits.new.smsAmbiguousDate` and leaves the date field empty. No reading reaches the form,
  and none is shown as a choice.
- **"one shared fixture drives both parsers"** — `tests/fixtures/records/mhrs_dates.json`
  drives `test_mhrs.py`, `turkishDates.test.ts` and `mhrsSms.test.ts`, and the pytest pins
  that the app tests keep reading it.
- **#666, second line: "both parsers switch together"** — neither parser has a default order.
  The day INT-399 states one, the message rows change, and both sides fail until both pass
  the same order.

## Not in scope, recorded
- **The time field still differs.** The device reads `saat HH:MM` or `saat HH.MM`, and does
  not range-check the time. The server reads any colon clock, refuses `HH.MM`, refuses
  out-of-range times, and refuses a second distinct time. `apply_sms` never reads
  `parsed.time`, so no time reaches the form today. The divergence matters the day a time is
  used, and aligning it belongs with that change.
- **An `unreadable` or `not_found` date keeps a date already in the field**, and the notice is
  still `no_date`, as INT-134 shipped it. Only `ambiguous` clears the field. That was this
  issue's case. Whether `unreadable` should clear the field too is a product call on INT-134's
  screen.
- **Unicode version drift.** The classes match CPython's Unicode 15.0. Hermes and Node carry
  their own tables. A character assigned after 15.0 could class differently on the two sides.
  Such a character is not a Turkish digit, letter or space.
- **The order itself** stays open as INT-399 (awaiting-human; Ask 2). Nothing here chooses
  it.
