# INT-032 — EHRbase export tier: OPT templates + client + roundtrip (P3 export per D8)

## Scope

The two acceptance lines, verbatim from `docs/backlog/issues.yaml`, each with the artefact that satisfies it:

- **"intake composition template (OPT) uploaded on boot; write/read composition per session; contribution audit"**
  → `packages/intake_platform/src/intake_platform/ehrbase.py`: `EhrbaseClient.ensure_template`
  (idempotent, byte-for-byte, 409 = already present), `.write_composition` / `.read_composition`,
  `.contribution` (CONTRIBUTION uid + `change_type` + committer + `time_committed` + the version uids
  it covers). `packages/clinical-schemas/src/clinical_schemas/mappers/openehr.py` builds the composition.
- **"integration test writes and reads a composition against EHRbase container"**
  → `tests/integration/test_ehrbase_roundtrip.py`, 8 tests, green against `ehrbase/ehrbase:2.35.1`
  running from the new `export` profile in `infra/docker-compose.dev.yml`.

`legal: KSVY-5`, `sec_row: clinical-core`.

**What the export carries, and what it does not.** The roundtrip is real in both directions —
internal value → canonical openEHR → EHRbase → read back → internal value → identity — for the
**operational template** and for the **composition envelope**. It carries **no clinical content**,
and that is the finding rather than a shortcut. See "What was refused rather than invented".

## The gap this issue reports rather than patches

**The committed operational template cannot be uploaded to EHRbase.**

`packages/protocols/openehr/previsit_intake.v1.opt` (sha256 `c72247ab…`) declares
`<occurrences>` on the COMPOSITION root and on **none** of its nine `C_ARCHETYPE_ROOT` content
children. AOM 1.4 makes `C_OBJECT.occurrences` optional in `Template.xsd`, but EHRbase's parser
dereferences it without a default:

```
HTTP 500
java.lang.NullPointerException: Cannot invoke
  "org.openehr.schemas.v1.IntervalOfInteger.getLowerUnbounded()" because "occurrences" is null
  at o.e.c.exception.DefaultExceptionHandler
```

Adding one `<occurrences>` block per child — `0..*`, the least-constraining interval AOM can
express, which asserts nothing the RM does not already — makes the same file upload with HTTP 201.
That was verified, and the verified bytes are committed as
`tests/fixtures/openehr/previsit_intake.v1.aom-occurrences.opt` (sha256 `631b80c5…`), whose header
says at length what it is.

**It was not applied to `packages/protocols`**, because this issue's scope is to consume that
package, not to edit it — and touching it would move the OPT pin, forcing a new
`questionnaire_definition` version and a CODEOWNER review that belongs with the archetype work in
HB-C12, not with a client library. `tests/integration/test_ehrbase_roundtrip.py::test_the_committed_template_is_rejected_today`
pins the current refusal; `test_the_fixture_is_root_identical_to_the_committed_template` pins that
the fixture differs by exactly nine `<occurrences>` elements and by nothing else (comments stripped,
occurrences stripped back out, byte comparison). When `packages/protocols` adopts the element, the
first test flips and the fixture is deleted.

Handed on as: **INT-032a**, one edit to
`packages/protocols/openehr/previsit_intake.v1.opt` plus the `OPT_SHA256` bump in
`packages/protocols/src/protocols/bindings/openehr.py`.

## What was refused rather than invented

Every at-code and every path this issue declined to make up, with the ask:

| refused | why | the ask |
|---|---|---|
| any leaf path `/content[<archetype>]/data[atNNNN]/items[atNNNN]/value`, for all nine roots | a root path addresses an ENTRY, not a datum. The committed template carries no node below the root and no committed source in this repository states one. A fabricated at-code produces a binding table that resolves against a fiction, and there is no diff that makes that look wrong | **HB-C12(a)** — for each root, which CKM revision and which leaf path carries which intake slot |
| at-codes for `openEHR-EHR-COMPOSITION.intake_previsit.v1` and `openEHR-EHR-EVALUATION.triage_outcome.v1` | both are LOCAL archetypes. files/03 §7 marks the latter "custom" and names no CKM composition archetype at all, so there is no upstream to copy from — they have to be authored | **HB-C12(a)** — author the two local archetypes and have the physician of record sign the triage one |
| a placement for `CLUSTER.provenance` (files/03 §7) | a CLUSTER is not a CONTENT_ITEM, so it cannot sit under `content`, and no committed source states which structure hosts it. INT-041 left it out of the template for the same reason | **HB-C12(a)** — which ENTRY's `protocol`/`other_participations` structure hosts it |
| a `.vN` bump on any of the nine archetype ids | INT-041's header records that the ids were transcribed from files/03 §7 and have **not** been reconciled against a CKM revision. Guessing `.v2` because CKM moved would be inventing a version | **HB-C12(a)** — reconcile the nine ids against a named CKM revision and date it |
| an `<occurrences>` cardinality in the committed template | see the gap above. `0..*` is verified to work, but choosing a *tighter* cardinality (how many symptoms may an intake carry?) is a modelling decision nobody has taken | **INT-251** — apply `0..*` verbatim from the fixture, or state a tighter interval. Filed, because the consequence is that the committed template cannot be uploaded to a live CDR at all |
| a default `context.setting` | which care setting a pre-visit intake happens in is a modelling decision. `IntakeEnvelope.setting` is required with **no default** — CLAUDE.md forbids "a default that would be chosen once by an engineer for all future cases" | the caller states it; the enum offers the whole published group and nothing else |
| a `session_id` anywhere in the composition | there is no RM-level home for it. `context.other_context` needs an ITEM_STRUCTURE (an at-code), and `LINK.target` is a `DV_EHR_URI` constrained to the `ehr:` scheme. The linkage stays on our side: EHR id + composition version uid | none — recorded so nobody adds it to `COMPOSITION.name` |
| a "leaf present" branch in the mapper | the binding table (`openehr_bindings.json`) has no leaf column to branch on. Writing placement machinery against a shape nobody has authored is building around the blocker, and it would need `rm_type` for the *leaf*, which the compiler cannot supply | **HB-C12** — the mapper grows placement in the same change that grows the bindings |

`tests/schemas/test_openehr_export.py::test_no_at_code_is_invented_anywhere_in_the_export` greps the

whole design rests on cannot rot silently.

## Egress (DoD: enumerate every outbound call the change adds)

The change adds exactly one outbound destination: the EHRbase container, reached over loopback
(`127.0.0.1:8092`) inside the deployment boundary. It is not a vendor, not an internet host, and an
IP literal that `infra/security/egress-allowlist.yaml` would refuse by design.
**No entry was added to the allow-list, and no PHI egress path was created.** The client accepts an
injectable `httpx.BaseTransport`, which is the seam
`intake_platform.egress.guarded_transport` plugs into when a deployment needs it.

The two image pulls (`ehrbase/ehrbase:2.35.1`, `ehrbase/ehrbase-v2-postgres:16.2`) and the two
one-off documentation fetches (the LICENSE blob, the openEHR terminology XML) were developer/CI
traffic, not runtime traffic.

## What was NOT exercised

Stated plainly, because a green suite is not a claim about everything:

1. **Clinical content never crossed the boundary.** Nothing in this issue proves that a symptom, a
   medication or a triage outcome roundtrips through openEHR — because none can be placed until
   HB-C12 is answered. The roundtrip identity assertions cover the template's nine archetype roots
   and the composition envelope (template id, archetype id, RM version, language, territory,
   category, composer, `context.start_time`, `context.setting`) and the EHR subject.
2. **The committed OPT was never accepted by a CDR.** Only the root-identical fixture was. The
   committed file's live behaviour that *is* proven is its refusal.
3. **AQL was not exercised at all.** No feature issues a query (files/05 §2.1), so the client speaks
   none and the tier is write/read-by-uid only.
4. **No CKM reconciliation.** The nine archetype ids are still the transcription INT-041 made from
   files/03 §7. Whether each exists at `.v1` in a current CKM revision is unverified, and the
   template upload does not check it — EHRbase accepts an archetype id it has never seen, because
   an OPT is self-contained.
5. **Versioning, modification and deletion were not exercised.** Every composition written is
   version 1. `PUT` (new version), `DELETE` and the `versioned_composition/revision_history`
   surface are untouched, as is EHRbase's admin API.
6. **No multi-tenant, RLS or consent-scope integration.** The client takes an `ehr_id` and writes.
   Wiring the export behind `consent_guard` and a `share:*` scope belongs to the issue that calls
   it, not to the tier.
7. **Nothing runs the tier.** `self_hosted_now: false`, the compose profile is opt-in, and no
   service, worker or endpoint imports `intake_platform.ehrbase` yet. DSAR `/export` still bundles
   FHIR+PDF (INT-037), unchanged.
8. **Not tested at scale, under concurrency, or against a cold cache.** A single-writer,
   single-container dev tier on one machine is what was measured, and no timing figure is recorded
   from it (invariant 20).
9. **The 2.35.1 pin was not evaluated against older or newer EHRbase.** The `occurrences` NPE is a
   fact about 2.35.1; whether earlier releases tolerate the omission is unknown and was not probed.
