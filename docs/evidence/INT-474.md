# Evidence — INT-474 · Deployment-role gate for relatives', household and partner data categories

GitHub #811. Sec-Row: `consent`. Legal: KVKK m.6, m.10.

## 1. Scope

The INT-471 legal lane (branch `int-471-legal-lane`, PR #809) proposed LD-03 and
LD-04 under owner decision D25 (synthetic and test use only; a licensed Turkish
lawyer countersigns before any real patient). Both are still in legal review.
Their finding, as this issue uses it:

- Relatives' family health history and consanguinity (`relatives_health`, LD-03),
  a household member's tuberculosis diagnosis (`household`, LD-04) and the
  partner's fertility (`partner_fertility`, D3's other-subject category) are
  about a person who is not the patient. That person gives no açık rıza, and
  the patient cannot give it for them.
- The ground for that person's data is KVKK m.6(3)(e), which belongs to persons
  under a duty of secrecy or authorised institutions: the health service
  provider. It holds in the hospital deployment, where the hospital is veri
  sorumlusu and INTAKE processes on its behalf (files/06 §0.1(1)(b)).
- In the consumer deployment the company is veri sorumlusu (files/06 §0.1(1)(a)).
  Whether any ground exists there is not decided, so those items are not served
  there.

Nothing enforced that split. The INT-349 register row records whether counsel
has placed a category, not in which deployment, so the day counsel filled the
`relatives_health` row both deployments would have opened. The red run below
shows exactly that: a filled register row compiled a `relatives_health` slot with
no deployment named at all.

Acceptance (issue #811, restated in the backlog row):

1. *The compiler/runtime refuses the categories household, relatives_health and
   partner_fertility unless the deployment role is the hospital-controller role,
   independent of the register row.* Delivered for the compiler and for the one
   runtime path that admits an answer by category (`intake_api.store.write_slot_answer`).
2. *Tests: consumer deployment with a filled row is refused; near-miss: hospital
   deployment with a filled row is served (synthetic).* Delivered, plus a
   missing role refused, for both halves.
3. *Cross-reference LD-03, LD-04 and D25; no consent text changes.* Done here
   and in the module docstrings. No file under `docs/legal/` changed, no
   `strings.yaml` string, no register row.

## 2. Where the deployment role is declared

There already is a typed deployment-role field, so none was added:
`intake_platform.db.models.Tenant.kvkk_role` (`KvkkRole`, INT-030), a
non-nullable column with no default and the inventory annotation *"controller/
processor flag per deployment (files/06 §1)"*. It names INTAKE's own KVKK role,
so the hospital deployment (the hospital is controller) is `processor` and the
consumer app is `controller`. It is written when a tenant is provisioned and is
never a request value.

What this PR adds around it:

- `protocols.deployment_role.DeploymentRole`, a closed `StrEnum`
  (`hospital_controller`, `consumer_controller`) with no default member, for
  the compiler, which has no tenant. `HOSPITAL_CONTROLLER_ONLY` is the
  register's own `OTHER_SUBJECT_CATEGORIES` (the exact ids `household`,
  `relatives_health`, `partner_fertility`, pinned by a test), so a category D3
  adds there is gated too. `admits()` is true for a gated category only when
  the role is the parsed enum member `HOSPITAL_CONTROLLER`; `None` and a raw
  unparsed string are refused.
- Compile time: `protocols compile --deployment-role
  {hospital_controller,consumer_controller}`, parsed to the enum by argparse,
  default unset (no role, so the gated categories refuse);
  `make protocols-compile ... DEPLOYMENT_ROLE=<role>` passes it through. The
  compiled `manifest.json` records `deployment_role`, so a bundle built for the
  hospital deployment says so. `resolved_protocol_hash` is unchanged.
- Runtime: `intake_api.deployment_role` reads `tenants.kvkk_role` for the
  writing tenant and maps it (`processor` → `hospital_controller`,
  `controller` → `consumer_controller`; the mapping is pinned over every
  `KvkkRole` member). A tenant with no visible row has no role.

## 3. What was built

- **Compiler.** New refusal `DATA_CATEGORY_DEPLOYMENT_ROLE` from
  `protocols.compile.data_categories.slot_category_refusals`, on every resolved
  slot, alongside and independent of `DATA_CATEGORY_REGISTER_INCOMPLETE`: the
  role gate does not read the row, and the role does not open an incomplete row.
  When both apply both are reported. The message names INT-474, the category,
  the role given (or that none was declared), KVKK m.6(3)(e), files/06 §0.1(1)(b)
  and LD-03/LD-04. `resolve_protocol` and `compile_bundle` take
  `deployment_role: DeploymentRole | None = None`; the `None` default refuses.
- **Store.** `write_slot_answer` raises `DeploymentRoleRefused` before anything
  is written when the category is gated and the tenant row does not make the
  tenant a hospital-controller deployment. The writer has no parameter that can
  carry a role (asserted), so neither a caller nor a patient can state one. The
  exception carries ids only (invariant 6).
- **INT-349 storage test.** `tests/data/test_sensitive_slot_categories.py` wrote
  all eight categories for a tenant with no row. Its fixture now provisions that
  tenant as a hospital-controller deployment, the one deployment where all eight
  are admitted, so the at-rest encryption property is still proven for every
  category. No assertion changed.
- **Threat model.** The `consent` row names the control and the two test files.

## 4. Tests

- `tests/protocols/test_deployment_role_gate.py` (new). The gated set is exactly
  the three register ids; the two roles; only `hospital_controller` admits; a
  bare string does not; patient-only categories and `general_health` are never
  touched by the gate. Compiler, each of the three categories with every register
  row filled: **consumer deployment refused**, **no role refused**, **near miss:
  hospital-controller compiles** and its manifest says `hospital_controller`. The
  hospital role does not open an empty row; a consumer compile with an empty row
  reports both reasons; a child pack adding `household` is refused for the
  consumer; patient-only categories still compile for the consumer. CLI: absent
  and `consumer_controller` exit 1 and write nothing; `hospital_controller` exits
  0; an out-of-set role is an argparse error.
- `tests/data/test_deployment_role_store_gate.py` (new, SQLite, synthetic
  tenants). The mapping over every `KvkkRole`; the role is read from the tenant
  row; the writer takes no role. Each of the three categories: **consumer tenant
  refused** with nothing at rest, **unprovisioned tenant refused**, **near miss:
  hospital-controller tenant writes it** (sensitive envelope). Control: a
  consumer tenant still writes `general_health`, `sexual_health` and `literacy`.
- `tests/protocols/test_data_category_gate.py` and
  `tests/protocols/test_data_register.py` (INT-349) are unchanged and pass.

## 7. What stays open

- The consumer deployment's ground for the other person's data is LD-03/LD-04's
  open question for counsel (a Kurul decision or counsel's opinion would settle
  it). If counsel finds one, opening the consumer deployment is a change to
  `HOSPITAL_CONTROLLER_ONLY` with its own decision record, never a register row.
- LD-03 and LD-04 themselves are `proposed` and in legal review on #809; this
  gate narrows what is served and does not rely on their approval.
- The register's counsel fields stay empty, so today nothing in these categories
  is served in either deployment; this PR only removes the path by which filling
  a row would have opened the consumer deployment.
