# INT-478: capture protection held until the last protected screen closes

GitHub #820. Sec-Row: `mobile`. This is a security defect in INT-131's clinical screen privacy. It was found on 4 Oct 2026 while building INT-477 (#817, PR #819).

This branch is cut from `main` and is not stacked: `useClinicalScreenPrivacy` has been on `main` since INT-131.

## The defect

Every protected screen passed expo-screen-capture the same key, `intake-clinical`. The library keeps a set of keys (`node_modules/expo-screen-capture/build/ScreenCapture.js`):
- `preventScreenCaptureAsync(key)` adds the key, and protects only if the key was not already in the set;
- `allowScreenCaptureAsync(key)` deletes the key, and releases when the set is empty.

With one shared key, the set holds one entry however many screens are mounted. So the first protected screen to unmount released OS-level protection for all of them. For example, closing the doctor-link issue screen left the share centre under it capturable while it was still on screen. The same happened under any protected screen: review over the intake, or a visit screen closed while Records stays mounted as a tab.

`captureLock.test.ts` reproduces this rather than describing it. It models the OS with the library's own key-set rules and shows the old per-screen calls releasing the share centre.

## The fix

- **`apps/mobile/src/lib/auth/captureLock.ts`** (new, pure). It is a reference-counted lock over the OS guard:
  - it asks the OS once, when the first screen acquires it, and releases once, after the last;
  - each screen's release counts only once;
  - a runtime without the module refuses, by rejection or by a synchronous throw; that is a no-op that changes nothing in the count, never a crash.
- **`apps/mobile/src/lib/auth/screenPrivacy.ts`.** The hook acquires the app's one lock on mount and gives back only its own hold on unmount. The OS calls and the key are unchanged, so expo's set only ever sees one prevent per protected period and one allow at its end.
- **`docs/security/threat-model.md`**, `mobile` row: one control line and its tests.

The protected screens are unchanged: records, wellbeing, intake, review, shares, issue-link and the kiosk PIN screen. `captureLock.spec.ts` pins that list.

## The app-switcher snapshot

- **Android.** The recents thumbnail is blacked out by the same FLAG_SECURE call, so the lock covers it.
- **iOS.** expo-screen-capture's app-switcher blur (`enableAppSwitcherProtectionAsync`) is not used anywhere in the app, and it takes no key. There is no second path to fix. `captureLock.spec.ts` fails if the blur, or the library's own `usePreventScreenCapture` hook, appears without going through the lock. Turning the blur on would change which surfaces are protected, which this issue excludes.

## Decided: protection follows the mount, not the focus

A tab screen stays mounted after its first visit, and its guard runs on mount. So Records or Wellbeing stays protected after the patient moves to another tab, until it unmounts, for example at sign-out. The acceptance asks to fail closed when unsure. This PR keeps that behaviour and records it as decided: protection stays on while a protected screen is mounted, not only while it is focused.

`captureLock.spec.ts` pins the guard as a mount effect and never a focus effect. If protection is ever meant to follow focus, that is a decision for the owner and security, with its own issue.

### Tests and near misses

- `captureLock.test.ts`:
  - open A and B, close A: still protected. **Near miss:** close both, and protection is released, once.
  - the OS is asked once per protected period;
  - a second release cannot drop another screen's hold;
  - a reopen asks again, in order;
  - React's development double effect leaves the screen protected;
  - refusals are swallowed.
  - **Near miss (the old guard):** the shared key releases the share centre.
- `captureLock.spec.ts`:
  - every OS call goes through the one lock, and only the guard imports expo-screen-capture;
  - there is no app-switcher blur and no library hook;
  - the guard is a mount effect;
  - the protected screens are unchanged.
  - **Near miss:** the old per-screen call is caught.
- `e2e/auth.spec.ts` (INT-131) is unchanged and green.

## Interaction with INT-477 (PR #819, stacked)

INT-477 also rewrites `screenPrivacy.ts`: it routes the guard through `protectScreen` and its window store. When #819 is rebased onto a `main` that has this fix, its guard should acquire this lock inside `protectScreen` rather than calling the OS per screen. That keeps both the count and INT-477's solid chrome.
