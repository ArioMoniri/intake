# INT-599 — the admin-web runtime image carries no build/dev npm tooling

GitHub #1019. Sec-Row: cicd. Branch int-599-admin-web-runtime-prune, from main 5d6984a7.
Part (a) is in this PR. Part (b), the corrected zod and deepmerge exception reasons, is the
owner's to apply: `owner-599-exception-reasons.patch` (below).

## What main shipped

`infra/staging/Dockerfile.admin-web` on main:

- its builder ran `pnpm install --frozen-lockfile --filter "@intake/admin-web..." --filter intake`;
- its runtime stage ran `COPY --from=builder /app /app` and `next start`.

The walk over pnpm-lock.yaml in `tests/infra/test_admin_web_runtime_image.py` puts 384
packages in that install, devDependencies included. Among them are eslint 9.39.5,
typescript 5.9.3, vitest, prettier, commitlint, jsdom, and minimatch 3.1.5 and 10.2.6. All
of it reached the image the staging host runs.

The node base image adds its own package managers: npm, npx, corepack and Yarn 1.

The issue says the Expo tooling shipped in that image too. The same walk shows otherwise.
Neither the root importer nor admin-web reaches @expo/cli, zod 3.25.76 or deepmerge 4.3.1.
apps/mobile is the only importer that does. One clause of the INT-573 reasons is false:
"no server runtime image installs npm packages". The other clause, that no admin-web
importer reaches these packages, is true.

## Change

- `apps/admin-web/next.config.ts` sets `output: "standalone"`.
- `infra/staging/Dockerfile.admin-web` has a builder and a runtime stage, both on the same
  pinned base.
- The builder installs and runs `next build` as before. It then lists admin-web's
  production closure with `pnpm --filter "@intake/admin-web..." list --prod --parseable
  --depth Infinity`. Then it runs `infra/staging/admin_web_trace_guard.sh`. All of this is
  one `&&` chain, so a failing guard fails the build.
- The runtime stage runs one command. It removes the base image's `/usr/local/lib/node_modules`
  (npm and corepack), `/opt/yarn-v${YARN_VERSION}`, and the npm, npx, corepack, yarn and
  yarnpkg links. It uses `rm -r` without `-f`, so a base image that moves one of these
  paths fails the build.
- The runtime stage then copies two things from the builder: `.next/standalone` into
  `/app`, and `.next/static`. It runs `node server.js` from `/app/apps/admin-web` as
  10001:10001, with the same health check.
- `PORT` and `HOSTNAME` were already set, and the standalone server reads both. The
  compose tmpfs `/app/apps/admin-web/.next/cache` is still inside the server's directory.
- The guard is a POSIX sh script. It fails the build unless every package file under a
  `node_modules` in the trace sits in a pnpm store entry that the production list names,
  by exact entry name. It also refuses an empty list, a trace with no store, and a regular
  file in the store's hoist directory, where pnpm keeps only links. It prints entry names
  and paths, never file contents.
- `Dockerfile.admin-web.dockerignore` re-includes the guard. Nothing else is added to the
  build context.
- Backlog row INT-599. The three count pins go from 386 to 387 (the real count), and
  files/11 is regenerated.

### The base image's package managers, read from the upstream artefacts it installs

These facts come from the upstream artefacts the pinned image installs, not from the image
itself. The pinned base is node 24.21.0. The docker-node trixie-slim Dockerfile installs the
official Node tarball into `/usr/local` and Yarn 1.22.22 into `/opt/yarn-v1.22.22`.

- **npm 11.19.0** (nodejs.org/dist/index.json for v24.21.0). The registry tarball holds 184
  `package.json` files, minimatch 10.2.5 among them. None is zod, deepmerge, @expo,
  node-forge or braces.
- **corepack 0.36.0** (nodejs/node v24.21.0 `deps/corepack`). It is one bundled `.cjs` file
  that inlines its dependencies (tar, semver, minipass, clipanion and others). There is no
  zod, deepmerge or braces in it.
- **Yarn 1.22.22**. It is one bundled `lib/cli.js` that inlines an old braces module
  (header "Copyright (c) 2014-2015"). There is no zod or deepmerge in it.

The runtime stage removes all three. After INT-599 its only npm packages are the
standalone trace's.

## Part (b): the owner patch

`~/.claude/projects/-Users-ario-Downloads-previsit/issue-drafts/owner-599-exception-reasons.patch`
comes with its commit message, `owner-599-exception-reasons.msg`.

The patch touches only the owner-only files: `osv-scanner.toml`, `.trivyignore.yaml` and
`tests/ci/test_security_gates.py`. The osv zod and deepmerge reasons and the trivy zod
statement now state four things:

- apps/mobile is the only importer that reaches the package;
- where the package is installed: a developer checkout, the CI jobs that run pnpm install,
  and the EAS build;
- that it is in neither `expo export` bundle;
- why no server runtime image carries it. Dockerfile.api is Python only. The admin-web
  builder's closure does not reach it. The runtime stage holds node, the guarded
  standalone trace and the static assets, with npm, corepack and Yarn removed.

No id, purl, expiry or MAX_* pin moves, so no exception is widened. The pins in the
patched test require those facts and refuse the old false clause. The near miss is the
INT-573 wording itself, and a reason that keeps the false clause beside the new facts.

- Red run of the pins: the patched test against the current reasons gives 2 failed, 65
  passed (the zod and deepmerge tests).
- Green run with the patch: `tests/ci/test_security_gates.py` gives 67 passed.
- `git apply --check` is clean on this branch's head. The owner files on the branch are
  byte-identical to main.

Ordering: owner-597's patch (INT-597, #1018) appends its minimatch entry directly after the
deepmerge reason that this patch rewrites. Whichever of the two the owner applies second
needs a rebase of that hunk.

owner-597's minimatch reason also says the admin-web runtime stage carries the root
devDependencies. After INT-599 that holds for the builder only.
