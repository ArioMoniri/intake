one, so a submitted build cannot be reviewed (INT-482, #825). D39 approves one way in for the
reviewer, as specified. Every clause is built and pinned by a test with a near miss. A security
review and a legal-lane review ran on the branch on 30 Oct 2026. Both asked for changes, the
changes are below, and on re-review **both returned APPROVE**; their remaining minors are fixed
too. Both lanes see the PR again before merge. The PR is opened once the SMS stack has
merged; until then this branch is pushed only to `backup/int-488-review-signin`.

**The typed 503.** With the window open on the synthetic host and no well-formed code in the
document (absent, empty, five or seven digits, not digits, not a string), the reserved number
answers `503 review_signin_unconfigured` on both steps, and nothing is sent:
`test_a_code_absent_from_openbao_answers_a_typed_503_and_sends_nothing` × 6, near miss
`test_near_miss_the_same_document_with_its_code_signs_in`. A malformed number wires no reviewer
and names no value (`test_a_malformed_number_wires_no_reviewer_and_names_no_value` × 6), and no
document wires none (`test_no_document_wires_no_reviewer`). The security review suggested a
withheld answer instead, because the 503 picks the number out while it has no code. The 503 stays
because the orchestrator's acceptance for this issue names it ("Code absent from OpenBao → 503
typed"). It is reachable only on the synthetic host with the window open.

**The canary (as in INT-581).** One reviewer is drawn at run time and pushed through:

- an admitted request, a wrong code, the right code and a refresh;
- the owner's `off`, then a request and a verify on the closed window;
- `on` and `status`;
- an unconfigured document, and a real-patient tenant.

Its code, the wrong code and five spellings of its number are then searched for in every sink:
log records (with tracebacks, as the API's JSON lines), the metrics exposition, every span, every
HTTP answer, and every Redis key and value, database row and audit row. None is found:
`test_no_code_or_number_reaches_a_log_metric_trace_answer_or_store`. The scanner's own near miss
is `test_the_scan_finds_a_leak_when_one_is_there`.

## What the reviews of 30 Oct 2026 changed

**Security review (CHANGES REQUESTED), all findings addressed:**

1. *An operator's row forked the API's chain.* The API's `AuditWriter` held the chain head in
   memory, so a row the owner's command appended from another process collided with the API's
   next seq. The collision was on the primary key, and every audited route failed until a
   restart. INT-577's `sms_spend` CLI and `access_hygiene` had the same defect. Now
   `AuditChain.catch_up()` adopts rows another writer appended, but only if they chain from the
   head held in memory: consecutive seqs, each `prev_hash` linking, each hash recomputing.
   Otherwise it raises `AuditChainForked` and appends nothing. `AuditWriter` calls it before every
   locked operation, which costs one tail read when nothing is new. The held head stays the check a
   truncate-and-re-append forgery cannot pass. Tests: `…_reset.py::test_the_api_adopts_rows_an_operator_appended_beside_it`,
   near miss `::test_near_miss_a_row_that_does_not_chain_is_refused`.
2. *One reviewer patient for every real reviewer, and hosted lanes.* There is now a patient per
   window, sessions are bound to the window, and the tenant is erased on `on` and `off` (rows 5
   and 6). The synthetic data class lets the model-lane router send a tenant's traffic to a
   hosted provider as non-personal, so the reviewer tenant's INT-182 kill switch must read
   engaged. The router honours that switch per tenant. If it is off, or the store is unreadable
   or absent, every reviewer step refuses (`hosted_lanes_open`), and so does `on`. The owner
   engages it once from the console's voice controls (runbook).
3. *First use did not alert.* Every label pair is now created at zero at import.
4. *The declared, not the bound, data class.* `ReviewGuards` now reads the bound class.
5. *Closing paused sessions.* Sessions are bound to the window id, so a token from one review is
   dead in every later one.
6. *No window expiry.* Built after the re-review, on the orchestrator's instruction: the window
   closes itself 14 days after `--on` (below, "The window closes itself after 14 days").
7. *A row for an opening that never happened.* The store is read first, and a failed opening
   after its row is compensated.
8. *Telling the number apart.* The branch now sits after the SMS spend kill switch. The 503 is
   kept (above).
9. *Guesses add up against a fixed code.* `REVIEW_MISS_CAP = 15` counted misses per generated
   code close the window, audited as `auth.review.window.closed` by `system:review-guard`. That is
   three INT-578 lockouts. It is an engineering default, not D39's, and a reviewed diff changes it.
10. *The helper could load modules from root's working directory.* It now runs `python3 -I`.
    `--generate` sets `max-versions=1` on the path, so a rotated code leaves no KV history.
11. *A limited request was not audited.* It is now. The number stays host-generated: no source
    in this repository can say which prefix BTK has left unallocated, and the
    `infra/security/msisdn_allocation.yaml` header forbids claiming one from memory.

**Legal-lane review (CHANGES REQUESTED), all findings addressed:**

1. *(blocker) The reviewer is a real person; their input stayed under one patient across

## The window closes itself after 14 days (orchestrator, 30 Oct 2026)

The orchestrator replaced the window-expiry owner ask with a fail-closed engineering default:
`REVIEW_WINDOW_S = 14 days` (`services/api/src/intake_api/review_window.py`). It is not a D39
value and not a clinical one, and the owner may change it in a reviewed diff. The runbook says so.

- **Expired means closed, at once.** `ReviewWindow.current()` reads an expired window as closed,
  so every reviewer step and every reviewer session is refused from the instant the 14 days are
  up, before anything records it.
- **The close is audited like `--off`.** `ReviewSignInFlow.expire_if_due` runs on every reviewer
  step and on the API's own sweep, once a minute (`review_expiry_forever` in the lifespan). It
  removes the window document first, by id in one transaction, so it can never close a fresh
  window opened a moment before. Then it appends `auth.review.window.closed` with the actor
  `system:review-expiry`. The erasure follows on the API's sweep only, never on a reviewer's
  request (round two, below). Of several callers racing, exactly one
  closes it and writes the row.
- **Nothing reopens it** but a fresh `--on`. An `--on` that finds an expired window still stored
  closes it the way `--off` does first.
- **`--status` shows the time left:** "closes itself at <UTC>, in 13d 23h 0m". An expired window
  reads "expired at …".
- The `docs/backlog/blockers.md` ask is removed.

## Design decisions, and why

- **The number is drawn on the host too, and kept in OpenBao beside the code.** D39 names a
  reserved number and says where the code lives. The INT-482 review notes (PR #828, legal lane)
  say the sign-in details are never written into the repository, an issue, a PR or a chat. A
  committed number would also be an agent-invented value, and it could be a real subscriber's
  line. So `--generate` draws it once and keeps it across rotations, and the App Store Connect
  user name never changes.
  - The drawn number may match a subscriber's real line. It is never contacted, never in
    `identity_vault`, and is used only as a credential label.
  - A deployment with no document has no reviewer number to reserve. Only the synthetic host's
    policy grants the path, and every deployment that can read the document reserves the number
    whatever its gate says.
- **The reviewer goes through INT-578's own code record.** The request mints the ordinary record:
  an HMAC over (pseudonym, request id, the reviewer code's HMAC), bound to the requesting device.
  The verify spends the number's attempt budget through `check_code`. So the reviewer's code is
  single use, device-bound, request-bound, compared in constant time and locked out exactly as a
  patient's is. There is no second comparison path to drift. The reviewer must enter the code
  within the 5-minute TTL of the request, which the app's flow does.
- **No SMS spend budget.** The reviewer path sends nothing, so it does not spend the tenant and
  global SMS caps. It stays under the number, device and address budgets and the resend backoff,
  and the spend kill switch is read before it. Its requests are not counted in
  `sec_otp_requests_total`, so they cannot trip `OtpRequestSpike`; they have their own series.
- **Withholding.** Withholding is INT-579's answer to every refusal that is a fact about a
  number, and the reviewer's refusals follow it.
- **The reviewer's own tenant, and a patient per window.** The consumer tenant on the synthetic
  host holds simulated patients only (D18). A separate tenant still makes "never real data"
  structural rather than a property of the host: RLS keeps every other tenant out.
- **No new category of personal data.** The reviewer is a real person. What they enter goes
  into the existing annotated columns of their window's patient, and it is erased per window.
  The reviewer document is a credential label and a code; the drawn number may match a
  subscriber's line, but it is never contacted and never in `identity_vault`. The window
  document holds a state, an instant and a random id. The session-binding keys hold a window id
  under a token hash, the same class of datum as the token records beside them. So no inventory
  annotation is owed (invariant 18); the legal lane agreed.
- **The reviewer erasures are ours, not the reviewer's application.** `review_reset` files
  `dsar_requests` rows, whose annotations describe a data subject exercising a KVKK m.11 right.
  These erasures are started by INTAKE as controller under m.7, at the end of the purpose: they
  are not a reviewer's application. Nothing in this repository counts the reviewer tenant toward
  an m.13 application count or SLA report. The requests complete in the same run, so
  `overdue_requests` never lists them, and any future m.13 report must leave `REVIEW_TENANT_ID`
  out. The `dsar_requests` rows and the `dsar.delete.*` chain rows double as the record of
  deletions that the Deletion Regulation (RG 30224) requires. Every reviewer window is reset
  before the next opens, so a run erases one subject, and `admin_dsar_delete_total` keeps
  `subject_count="1"` (a multi-subject run pages, files/08 §4 group O).

## Round three: the pre-PR guards (R1, R3, R2, R6), 30 Oct 2026

Both re-reviews approved at `3aa2c3e7`. The security reviewer then suggested two cheap guards
(R1, R3) and two optional ones (R2, R6). All four are built, test-first, in
`tests/security/test_review_signin_guards.py`.

**R1: the erasure role is checked.** `intake_api.review_reset` refuses a role that is the
bootstrap role, or that holds `rolsuper` or `rolbypassrls`. Any of these would erase past the
reviewer tenant's row-level security, so a scoping fault in the erasure would reach real tenants.

- *Same role as bootstrap.* This compares the user names in the two URLs
  (`bootstrap_role_problem`), never echoing a URL.
- *Role attributes.* They come from `pg_roles` for `current_user` (`pg_role_attributes`).
  - Off PostgreSQL there are no roles, so the check passes. That is the tests' SQLite.
  - A role the catalogue does not list reads as holding both attributes.
  - A check that raises refuses.
- *Who asks.* `ErasureRoleGuard` asks at the API's start, logging
  `review erasure role refused at start`. It asks again before every erasure run, ahead of
  INT-395's preflight, so an `ALTER ROLE` after start is caught on the next run.
- *A refused run.* It appends `auth.review.reset_blocked` on `review_signin:erasure_role` and
  raises `ReviewResetBlocked` naming the attribute and INT-394. `--on` therefore refuses.
- *The owner's command.* It refuses the bootstrap role before building any engine.
- *Near miss.* The app role, holding neither attribute, passes and erases.

**R3: fixed close actors, isolated sweep stages.**

- `ReviewWindow.note_unrecorded_close` takes only the three `CLOSE_ACTORS`:
  `operator:host`, `system:review-expiry` and `system:review-guard`.
- `first_unrecorded_close` reads any other entry as `UNATTRIBUTED_CLOSE`. That covers an unknown
  actor, one that is not id-shaped, a non-string, a missing actor or garbled JSON. The sweep
  records such an entry as `auth.review.window.closed_unattributed` under `system:review-guard`,
  never in its own words.
- Before this change, an actor that was not id-shaped made `_record_closes` raise in the audit
  layer's `_require_ref_shaped`. That stopped the expiry and the erasure behind it on every sweep.
- `ReviewSignInFlow.sweep` now runs its three stages (`record_closes`, `expire`, `erase`) each in
  its own `try`. A failed stage is logged by type, and the next stage still runs.

**R2: one refusal episode, one set of rows.**

- `ReviewReset` is now a protocol with `record_blocked`.
- The sweep passes `record_blocked=False` while `auth:review:reset_failing` is set. That is the
  same flag that already kept `auth.review.reset_failed` to one row per episode.
- A blocked erasure that retries every minute therefore writes its `reset_blocked` rows once,
  while the counter and the page still count every attempt.
- The owner's `--on` and `--off` still write them every time, because each is a deliberate act.

**R6: `opened` only for a window that opened.**

- `ReviewWindow.open()` returns the new window's id, or None when the SET NX lost.
- `--on` now opens first and writes `auth.review.window.opened` only for a window it opened.
- A lost race writes nothing and exits 1. So does a store that refuses the SET.
- If the `opened` row fails, `--on` closes that window again at once, by id, so it never closes
  someone else's. The close is noted first, so the sweep records it if the audit store still
  refuses.
- The old `auth.review.window.open_failed` compensation row is gone, because there is nothing to
  compensate.
