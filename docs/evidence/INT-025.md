## Path supersession (honest reconciliation)

The acceptance names `packages/clinical-schemas/metrics_catalog.yaml`, a path
written before INT-021 landed the catalogue at
`observability/metrics_catalog.yaml` — where every consumer already binds it:
the `intake_platform.slo` loader, `scripts/observability/slo_report.py`,
`tests/observability/test_slo_files.py` (the runtime emit-without-catalogue
gate), and the Prometheus rules derivation. Creating a second file at the
acceptance's path would split the single source of truth that CLAUDE.md
inv. 13 depends on, so the `observability/` path supersedes the acceptance's
path; this entry is the record of that supersession. files/08 §4 group O
carries the same stale pointer ("must land in
packages/clinical-schemas/metrics_catalog.yaml") — same resolution.

## What the catalogue now holds

files/08 §4 names 135 distinct metric ids (138 mentions; `triage.events_total`,
`sec.break_glass_total` and `sec.admin_actions_total` are restated in group O).
Before this issue the catalogue held only the 12 platform families
(2 × `http_*` + 10 prometheus_client default-collector families): 0 of the 135
were present. All 135 were added as `status: planned` — nothing emits them yet;
the emitting services have not landed — each with `id` (the spec's OTel dotted
id), a Prometheus `name` (dots → underscores), `type`, `labels` (08 §4's stated
label sets, incl. group B's per-turn profile/tenant/branch/vendor), `owner`,
`unit`, and `target` wherever 08 §4 states one (26 targets). The 12 pre-existing
entries gained the now-required `unit` and stay `status: live` (the default).

08 §4 rows that carry no metric id (prose KPIs in groups H, K, L and most of
I and J) cannot be catalogued as entries without inventing ids the spec never
named; they are recorded verbatim in the catalogue's footer comment so nothing
is silently dropped, and they become entries the moment the spec names them.
`document_upload_pipeline_total` (unmerged branch int-120) was deliberately not
included; that merge is resolved by the coordinator.

## Reverse direction (catalogued-but-never-emitted)

`status` is held honest in both directions by
`test_live_entries_are_emitted_and_planned_entries_are_not`: a `live` entry
must be observably emitted (statically constructed or served on `/metrics`;
the prometheus_client default-collector families are exempt because the
process collector is platform-dependent), and a `planned` entry must not be —
promotion to `live` is forced the moment real code emits it. Planned entries
are by design, never a failure.
