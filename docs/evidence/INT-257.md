## 2. The schema, read rather than recalled

INT-032's evidence (§ "The gap") said that *AOM 1.4 makes `C_OBJECT.occurrences` optional in
`Template.xsd`*. That is wrong, and this issue starts by correcting it from the source.

**Source.** openEHR `specifications-ITS-XML`, tag **`Release-1.0.2`** (commit
`f7a937778bf9ea43b01b0f9d8a616e47f35017c1`, 25 Feb 2021), directory `components/ALL/`. Retrieved
27 Sep 2026 from
`https://raw.githubusercontent.com/openEHR/specifications-ITS-XML/Release-1.0.2/components/ALL/<file>`

The include chain (`Template → OpenehrProfile → Archetype → Resource → BaseTypes`) resolves inside
that directory, so `lxml.etree.XMLSchema` compiles it with no network access. The digests are pinned
in `XSD_PINS` and asserted by `test_the_schema_set_is_the_pinned_upstream_release`, so a changed
schema file is a failing test and a visible diff.

**What the schema requires.** In `Archetype.xsd`, `C_OBJECT` is the sequence
`rm_type_name, occurrences, node_id`, and none of the three carries `minOccurs`. All three are
mandatory, and `test_the_schema_makes_occurrences_and_node_id_mandatory_on_c_object` reads this from
the vendored file. `C_ATTRIBUTE` requires `existence`. `C_MULTIPLE_ATTRIBUTE` appends a mandatory
`cardinality` after `children`. In `Template.xsd`, `C_ARCHETYPE_ROOT` extends `C_COMPLEX_OBJECT`,
so its `archetype_id` comes after `attributes`.

The normative model agrees. AOM 1.4 §4.3.6 lists `occurrences` and `node_id` on `C_OBJECT` as
`1..1`, and §4.3.2 and §4.3.4 do the same for `existence` and `cardinality`. Source:
`https://specifications.openehr.org/releases/AM/Release-2.0.6/AOM1.4.html`, retrieved 27 Sep 2026,
241 867 bytes, sha256 `0c696d0ac12e6b8a199bab1405b003df28c2f08aba5439cb63fe9ff38b6b7d80`.

**What the committed file violated.** There were four breaches:

1. `occurrences` was missing on all nine content roots.
2. `node_id` was missing on all ten C_OBJECTs.
3. `existence` and `cardinality` were missing on `content`.
4. `archetype_id`/`template_id` came before `attributes` on the definition.

libxml2 stops at the first out-of-sequence element, so the red run reports only line 83. The
mutation controls in §5 show that each missing element is caught on its own.

**An earlier, unmerged attempt.** The production audit
(`docs/audit/2026-09-26-production-audit.md` rows for INT-257 and F23) points at commit `35195d7c`
on `merge-305`. That commit added `occurrences` only, in a multi-issue commit with no evidence. Run
against the same schema, it is still invalid (`line 83: Element 'archetype_id': This element is not
expected. Expected is ( node_id )`), so this change supersedes it and cherry-picks nothing.

## 3. Every value, and where it comes from

Nothing in the template was chosen. Each value was read off one of these sources.

| element | value | source |
|---|---|---|
| root `occurrences` | 1..1, both ends included | Unchanged from INT-041, because a template has exactly one root. `upper_included` is now explicit. Without it, an openEHR `Interval` with `lower=1` included and `upper=1` not included is the empty set [1,1). |
| `content` `existence` | 0..1 | RM 1.0.2 `COMPOSITION.content : List<CONTENT_ITEM>` is `0..1`. RM §5.3 adds that content "may be empty". Source: `https://specifications.openehr.org/releases/RM/Release-1.0.2/ehr.html`, retrieved 27 Sep 2026, 301 696 bytes, sha256 `2bd9e66d42a2b1031d6582c3484c5271c9fe29d0ea883eafbda30885bc1e74f6`. AOM 1.4 `Existence_set` bounds existence to at most 1. |
| `content` `cardinality` | `is_ordered` true, `is_unique` false, interval 0..* | The RM container is a `List`. ADL 1.4 §5.3.4.1 defines a logical list as ordered with non-unique membership, and says a cardinality constraint may not be stronger than the RM container. Source: `https://specifications.openehr.org/releases/AM/Release-2.0.6/ADL1.4.html`, retrieved 27 Sep 2026, 585 118 bytes, sha256 `f568a7f28d53e8a66de0067f878301c60b36dec501f91e461891672a451703ab`. |
| each content root `occurrences` | 0..*, `upper_included` absent | See the derivation below. `upper_included` is omitted because an unbounded upper has no inclusion (openEHR `Interval`: `upper_unbounded` implies not `upper_included`). |
| every `node_id` | present, empty | See the derivation below. |

### 3.1 Content-root occurrences: 0..*, derived rather than chosen

The caller's rule was to copy whatever the archetypes say. So the question is which archetype says
how often an entry may sit in `COMPOSITION.content`.

- **The parent says it.** An archetype root's occurrences under `content` is stated by the
  COMPOSITION archetype's content constraint, for example `allow_archetype … occurrences matches
  {…}`. It is not stated by the entry archetype. The parent here is
  `openEHR-EHR-COMPOSITION.intake_previsit.v1`. It is local and unauthored: files/03 §7 names no
  CKM composition archetype, and authoring it is **HB-C12(a)**. No archetype in the chain states the
  value.
- **The entry archetypes state nothing about their own placement.** The four ids that exist at the
  transcribed version in the openEHR CKM mirror (`openEHR/CKM-mirror`, commit
  `5cb099fa17ee760c8501a9bddc85ade7ce57d63b`, 25 Sep 2026) each open their definition with a root
  that carries no occurrences:

  | archetype (path under `local/archetypes/`) | bytes | sha256 | root line |
  |---|---|---|---|
  | `entry/evaluation/openEHR-EHR-EVALUATION.reason_for_encounter.v1.adl` | 34 344 | `8ba361a1e709dfb63f30b75a3510a05d0911f8418070b44c1c56a12a3734161b` | 195: `EVALUATION[…] matches {` |
  | `entry/observation/openEHR-EHR-OBSERVATION.story.v1.adl` | 51 578 | `9df52e706fa96eaa87c8c6326c45a83feb0a199acb385c1736da86530a9df8f6` | 327: `OBSERVATION[…] matches {` |
  | `entry/evaluation/openEHR-EHR-EVALUATION.problem_diagnosis.v1.adl` | 262 313 | `8462a3b811a440c2b01451f0da48c7d297d53b5dc4d45c4722b13321e645ce1f` | 787: `EVALUATION[…] matches {` |
  | `entry/action/openEHR-EHR-ACTION.medication.v1.adl` | 267 202 | `7e2484d4aec5ad8c5ceb5edb466a82b43b45396fbe3abaa4ee4a298b8e6437bc` | 480: `ACTION[…] matches {` |

- **CKM's own practice leaves the composition's `content` unconstrained.** The generic
  `composition/openEHR-EHR-COMPOSITION.encounter.v1.adl` (45 002 bytes, sha256
  `f334e2d3b7238c634cf753d19ab6e7900e8ffc4baa4b0c9614be4d55168d866c`) constrains `category` and
  `context` and has no `content` attribute at all. It leaves placement cardinality to the template.
- **What is left is the RM.** `content` is an unbounded list that may be empty, and 0..* is exactly
  that bound. It is what INT-032 verified EHRbase accepts, and it adds no constraint the RM does not
  already impose. A tighter interval, such as how many symptom entries an intake may carry, is a
  modelling decision that belongs to HB-C12. Nobody has taken it.

Two readings were considered and rejected:

- **ADL 1.4's default `occurrences {1..1}`.** This default applies to an object constraint inside an
  archetype definition that states no interval. Applied here, it would make all nine entries
  mandatory, so every composition would need a reason for encounter, a PHQ-9, a GAD-7 and a triage
  outcome at once. That is an invented constraint. It would also make the envelope-only export that
  HB-C12 leaves us with invalid.
- **AOM 1.4 `C_MULTIPLE_ATTRIBUTE.Members_valid`.** It requires every member's
  `occurrences.upper <= 1`. This contradicts AOM 1.4's own `C_OBJECT.occurrences` text, which allows
  an upper limit above 1 when the owning attribute's cardinality exceeds 1. It also contradicts ADL
  1.4's worked example (`use_node ADDRESS[at0009] occurrences ∈ {0..*}` inside a container) and
  every CKM archetype. `encounter.v1` itself declares `allow_archetype CLUSTER[at0002] occurrences
  matches {0..*}` inside `items cardinality matches {0..*; unordered}`. This contradiction in the
  published spec is recorded here, not resolved. No validator in reach, including the XSD, EHRbase
  and Archie, enforces it.

### 3.2 Node ids: present and empty

The schema makes `node_id` mandatory but types it `xs:string`, so any value validates, including an
empty one. The value was decided by two sources:

- **The model.** AOM 1.4 §4.2.3.1 says each `node_id` is a term code in the archetype ontology.
  A node that needs no path of its own can have no node id. In an OPT, each root is addressed by its
  `archetype_id`, which is what `/content[<archetype_id>]` names and what
  `protocols.bindings.openehr.resolve` reads. This template carries no archetype terminology (no
  `term_definitions`, no `ontology`), because HB-C12 has not authored it. A non-empty node id would
  therefore name a term the file does not define.
- **The CDR.** A non-empty node id is also an upload failure in EHRbase, not a cosmetic gap. Read at
  `openEHR_SDK` tag `v2.35.0`, which is the SDK EHRbase 2.35.1 reports on `/rest/status` per INT-032,
  file `web-template/src/main/java/org/ehrbase/openehr/sdk/webtemplate/parser/OPTParser.java`
  (61 469 bytes, sha256 `329f92d43fdb3990df2cc20624944403e1ebc7040a5da3baa181a1b52af3fef8`):
  - `buildNode` (lines 1249–1313) reads `occurrences.getLowerUnbounded()` with no null check at line
    1257. This is INT-032's `NullPointerException` site.
  - For any non-blank node id, the same method evaluates
    `termDefinitionMap.get(nodeId).get(defaultLanguage)` at line 1266. The archetype root code
    without its term definition would reproduce that 500 one line further down.
  - A blank id takes the `else` branch at line 1306, which names the node from the RM type, the same
    branch an absent id took. `parseCOBJECT` (lines 902–910) addresses a `C_ARCHETYPE_ROOT` by
    `archetype_id`, not by node id.
  - EHRbase `service/src/main/java/org/ehrbase/service/TemplateServiceImp.java` at tag `v2.35.1`
    (18 001 bytes, sha256 `c74f56381d3765fad3d290f99606b43d522357acb3a0cda1d463d98bdf85ae51`) runs
    `validateTemplate` → `buildWebTemplate` → `new OPTParser(template).parse()` on every upload
    (lines 168, 225–236, 325–354). Its catch list has no `NullPointerException`, which is why the
    defect surfaced as HTTP 500 rather than 400.

`test_the_schema_admits_an_uncatalogued_node_id_so_the_catalogue_guard_is_needed` proves that the
XSD alone would let the root code through. `test_no_node_id_names_a_term_the_template_does_not_carry`
carries the check the schema cannot make. Once HB-C12 authors the terminology, a node id with a
matching `term_definitions` entry passes that guard unchanged.

## 4. Why EHRbase 2.35.1 now answers 201, and where that is proven

INT-032 saw EHRbase accept its fixture: the committed file plus nine `occurrences` blocks, placed out
of schema order. The table compares every element the committed file now adds against what
`OPTParser` v2.35.0 does with it:

| added element | what the parser does with it | vs the accepted fixture |
|---|---|---|
| `occurrences` on the 9 roots | read at 1256–1258 | identical intervals (0..*) |
| empty `node_id` on all 10 nodes | `StringUtils.isNotBlank` is false (1261, 416, 913–919), so it takes the same branch as absent | same path |
| `existence` on `content` | read only for `C_SINGLE_ATTRIBUTE` (457–461); `content` is multiple | not read |
| `cardinality` on `content` | `buildCardinality` (777–796) gives min 0, max −1, which is trivial and not added (579–594) | no effect |
| `upper_included` on the root and on `existence` | never read | none |
| schema element order | XMLBeans accepted the fixture's out-of-order `occurrences` | the new file is in schema order |

`validateTemplate`'s other checks (concept, language, definition, `description.validate()`) see the
same `description` element INT-032's fixture passed.

**Where this is proven.** Only CI's `check-integration` job proves it, against the pinned
`ehrbase/ehrbase:2.35.1` container. It was **not** run here. There is no container runtime on this
machine: Docker is banned on the laptop, and the team server has neither Docker nor Podman
(`check-integration` is CI-only). So the 201 is **argued from the source above and asserted by the
test**. It is not yet observed. The first CI run on the PR is the observation.

What was run locally is the test's mechanics, against a loopback stub. The stub answered 201 to the
first template POST and 409 after that, the same as EHRbase. It ran as a scratch script, not a
committed test:

```
first upload: TemplateState(template_id='previsit_intake.v1', uploaded=True) [('POST', '/ehrbase/rest/openehr/v1/definition/template/adl1.4', 201)]
201 assertion: passed
second upload: TemplateState(template_id='previsit_intake.v1', uploaded=False)
```

This confirms that the `_StatusRecorder` transport survives the production client's per-request
`httpx.Client`, and that the assertion reads the status on the wire. `TemplateState` folds 200 and
201 into `uploaded=True`, and the acceptance names 201.

## 5. Tests

**New: `tests/protocols/test_opt_schema.py`** (12 tests).

Tests of the committed template:

- pinned schema set
- the schema's own `C_OBJECT` declaration
- Template.xsd validity
- occurrences and node id on every C_OBJECT
- root 1..1
- each content root 0..* in file order, with the nine ids and RM types unchanged
- `content` existence and cardinality
- no uncatalogued node id and no at-code anywhere in the file
- `load_opt` still reads the same nine roots

Near-miss negative controls. Each mutates one node of the **committed** bytes in memory:

- one content root without `occurrences`: the **schema** rejects it
- `content` without `cardinality`: the schema rejects it
- a content root whose `node_id` is the archetype root code: the schema **accepts** it and the
  catalogue guard flags it. The same test then adds a synthetic `term_definitions` entry for that
  code, and the guard accepts it. The guard checks the catalogue; it does not ban at-codes, so
  HB-C12's terminology will pass it without a test change.

**`tests/integration/test_ehrbase_roundtrip.py`** (8 → 7 tests):

- `test_the_committed_template_is_rejected_today` is flipped to
  `test_the_committed_template_uploads_with_201`. This is the flip INT-032's evidence prescribed:
  "When `packages/protocols` adopts the element, the first test flips and the fixture is deleted".
- `test_the_fixture_is_root_identical_to_the_committed_template` is **removed** along with the
  fixture it compared. That is a deliberate exception to LOOP.md's "never delete tests". The property
