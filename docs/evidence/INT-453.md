# Evidence: INT-453 · The RED path triggers the winning rule's own script

**Epic:** E05-voice · **Phase:** P0 · **Sec-Row:** triage · **GitHub:** #767 ·
**Depends on:** INT-080 (the triage engine), INT-093 (the RED preemption path) ·
**Found by:** INT-446 (#766)

## Acceptance (verbatim)

- *"The RED script is chosen by the highest-severity firing rule, deterministically, using that
  rule's own register, location and text_tr. A multi-rule test with a near-miss control is
  included."*
- *"`make safety` passes, with triage at 100% branch coverage."*

## Problem

`services/voice-runtime/src/intake_voice_runtime/talker/red_path.py`, `RedPreemption.trigger`, had
two lines that addressed a different rule:

- `script_id_for(rule_ids[0], location)`
- `RedTriggerMessage(rule_id=rule_ids[0], register=triage.register, …)`

The cause is that the two values follow different orders:

- `RulesTriageResult.rules` is ordered by severity and then id.
- The engine's winner is ordered by severity, then register restrictiveness, then id (files/02 §5.3).
  The winner's register is the `register` the result carries.

Take two RED rules of equal acuity, `rf.a` (ALERT) and `rf.b` (SILENT). The wire carried SILENT
beside `rf.a`'s ALERT script. An alarm script under the register whose whole point is "no audio,
ever" is the mechanism-of-harm case §5.3 exists to prevent.


## Review round 1 (CHANGES-REQUESTED on #773)

The first fix asked the engine for the winner over the pack's rules, and every fired rule had to be
in the pack. That had two problems:

- **A YELLOW rule firing beside a RED dropped the RED.**
- **An unaddressable RED published nothing.** The device renders a RED only on a received
  `red_trigger`, so the patient saw no RED at all.

Both are fixed below.

## Change

**(a) The engine names its RED, so the path never re-derives it.**

- `RulesTriageResult.red_rule_id` (clinical-schemas) is the fired rule whose register and action
  script the RED delivers. It is validated as a RED axis only, and it must name a fired rule.
- The engine sets it on every RED (`protocols.triage.winning_red_rule`, one implementation that
  `evaluate_triage` uses).
- OpenAPI and the TS models are regenerated (`make schemas-codegen`).
- `red_path._red_rule` reads `red_rule_id`. When the result names no RED (a hand-built or imported
  result), a lone fired rule is its own RED. It **never** reads a position among several.
- Only that one RED rule has to be addressable, so a YELLOW rule beside it is irrelevant.
- The pack-rules index of the first round (`MappingRedScriptIndex.rules`) is removed.

**(b) An unaddressable RED is still a RED on the device.** This covers pack drift (no script for the
named RED at this location) and a result with several fired rules and no name.

- The path publishes the **generic escalation** trigger: register ALERT (`GENERIC_RED_REGISTER`, the
  most conservative), the result's own location, and
  `scriptId = GENERIC_RED_SCRIPT_IDS[location]` (`base.generic_red.{remote,on_site,unknown}`).
- It still fails loudly with SCRIPT_UNADDRESSABLE, after the intake is stopped and the clinician is
  told.
- **Replay.** A replay of an unaddressable outcome re-sends the device trigger. It resolves the real
  script if the pack now holds it, and the intake is not re-cancelled and the clinician not
  re-notified. A replay of a delivered RED stays a no-op.
- **Device** (`apps/mobile/src/lib/livekit/red.ts`): `genericRed(trigger, catalog)`, and the session
  emits `{type:"red"}` with it whenever `resolveRed` finds no script. The `red_unrenderable` event,
  which nothing rendered, is removed. The generic RED is ALERT, at the trigger's location, with
  `show112` clamped false under ON_SITE.
- **Generic UNKNOWN.** It asks the one location question before any 112. This follows
  files/04 §8.1 rule 7 and the motion contract's `redAffordances`, which gives `askLocation` and
  `call112:false` until the answer.

**The generic copy is `draft_needs_source`.**

- No generic or base life-threat script text exists. The only scripts in
  `files/protocols/base.life_threat.yaml` are rule-specific exemplars.
- Until a signed generic script is compiled under those ids, the device shows the RED with the
  location-correct affordance and **no words**. Nothing is invented.
- The copy went to the INT-432 clinical-decisions process (agent author plus independent verifier,
  D18). It is **open** as **CD-24**, whose register row is
  [`docs/clinical/decisions/CD-24.md`](../clinical/decisions/CD-24.md); that register is INT-432,
  GitHub #735, and is not yet on `main`. The CD lead noted that the UNKNOWN question
  ("Şu anda hastanede misiniz?") already exists as `ask_one_tr` in the active exemplars and is fixed
  by files/04 §8.1 rule 7; that is why the generic UNKNOWN asks before showing any 112.
- The generic's **register** is part of CD-24 and is also **open**. It stays ALERT until CD-24
  lands; see review round 3.

## Review round 3: a fail-closed serve precondition, and the register hook

- **The generic RED document.** `protocols.generic_red` defines the `kind: generic_red` document:
  its decision (`CD-24`), status, register, source or `source_gap`, and per-location copy. ON_SITE
  never offers 112, because the DSL's `RedFlagAction` refuses it.
  - The committed `packages/protocols/generic/generic_red.yaml` is **`draft_needs_source`**. It
    carries no copy, because **CD-24 is open**.
  - `generic_red_refusals` returns `generic_red_absent` or `generic_red_draft_needs_source`. An
    empty result means servable.
- **Serve precondition.** `/v1/triage` (`load_served_red_rules`) serves nothing, and answers 503,
  while the generic document is absent or a draft. The shipped default
  (`ApiSettings.triage_generic_red_path`, env `INTAKE_API_TRIAGE_GENERIC_RED`) is the committed
  draft, so a blank generic can never reach a live tenant. When the document is servable, the
  catalog pre-positions `base.generic_red.{remote,on_site,unknown}`.
- **The `device_functions` precondition.** `FlagGovernor` refuses to open, or to flip, an enable of
  `device_functions` while the generic is unservable (`DeviceFunctionsPreconditionUnmet`, code
  `flag_device_functions_generic_red_unservable`).
  - Nothing wired means refused.
  - The precondition is re-checked at the second key, so copy withdrawn between the two keys
    refuses the flip.
  - Other safety flags are unaffected.
- **The register hook** (CD-24, open).
  - `protocols.generic_red.generic_red_register` gives a servable document's register, and ALERT
    (`DEFAULT_GENERIC_RED_REGISTER`) otherwise.
  - `RedPreemption.generic_register` is a value, not a port: the constructor pin admits it as a
    `RedRegister` defaulting to ALERT. It is set from that function.
  - The device honours the register a server-sent generic trigger carries, and uses ALERT for a
    RED it could not resolve itself.

## Round 4: CD-24 applied (supersedes the ALERT register of rounds 1 to 3)

CD-24 is the generic RED escalation decision in the INT-432 register. Its source of truth is
`packages/protocols/decisions/CD-24.yaml` on #757. An EM/IM-cardiology physician agent authored it,
and an independent verifier agreed (int-432-cd24 2e6bbf26). Its scope is D18: simulated-patient
testing only, with a licensed physician's review required before any real patient.

- **Register.** CD-24 sets `register_policy: carry_engine_register`. Its finding G2 rejects
  always-ALERT under invariant 21: that would be a default register, and the base.life_threat schema
  refuses ALERT for `distress_sensitive`, `subject_is_child` and consent-independent crisis rules.
  - The generic trigger now carries the engine result's own register.
  - `GENERIC_RED_REGISTER`, `DEFAULT_GENERIC_RED_REGISTER`, `RedPreemption.generic_register` and
    `generic_red_register` are removed. The constructor pin is back to five ports.
  - The document's `register_policy` is the literal `carry_engine_register`, and `always_alert` is
    refused at load.
- **On the device.** `genericRed` uses the trigger's register:
  - ALERT and CALM paint the root layer, with CALM amber-neutral;
  - SILENT renders in the flow with no headline;
  - DEFERRED_CLINICIAN never reaches the device.
- **SILENT and mixed registers stay draft in CD-24.** The delivery floor still applies: intake stops
  (`REGISTER_DELIVERY` `stops_intake`), and the clinic notification carries `silent_generic: true`
  whenever the generic is delivered SILENT. The result carries no per-rule register, so this flag is
  set for every SILENT generic, a superset of CD-24's "SILENT chosen over a co-fired ALERT or CALM".
- **UNKNOWN** asks "Şu anda hastanede misiniz?" before any 112, as CD-24's verdict `ask_first`
  requires.
- **Copy.** `packages/protocols/generic/generic_red.yaml` now carries CD-24's
  `value.scripts.base.generic_red` verbatim, for REMOTE, ON_SITE and UNKNOWN.
  - It **stays `draft_needs_source`** until the CD-24 row is on main (#757), so the serve
    precondition still holds: `/v1/triage` serves nothing and `device_functions` stays off.
  - To become active it also needs the compiler's tr expansion of the ON_SITE line, which has bold
    markers and an optional `tenant.acil_location_tr` segment.
  - Still draft in CD-24: the SILENT copy, mixed registers, the no-answer wait, and generic
    driving, accompaniment and nil-by-mouth do-nots.
