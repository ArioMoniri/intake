# INT-304 — Share scope covers every note section (no withheld section can leak)

**Branch** `int-304-share-scope` · **Date** 6 Sep 2026 · **sec_row** `review-send` · **legal** KVKK-5

Acceptance (`docs/backlog/issues.yaml`):

1. `SectionId` in `services/api` (`schemas.py`) is widened from the three names it carries
   today — `chief_complaint`, `hpi`, `medications` — to the full set the note actually emits,
   derived from ONE declaration shared by the note builder and the schema rather than restated,
   because two lists is how they drifted.
2. A patient who scopes a section off has that choice recorded in the share consent scope and in
   the hash-chained audit entry for the share (invariant 4): a test scopes off `allergies`,
   sends, and asserts the recorded scope names it.
3. The mobile consent summary and the server-side scope check read the same section ids, so the
   summary a patient reads before Gönder is the set the audit records afterwards.

## The count: the note emits NINE section ids, not eight

The issue prose says "eight" but its own acceptance enumerates nine names (the three it carries
today plus `allergies`, `pmh`, `family_social`, `measurements`, `device_health` **and the
deferral marker**). `apps/mobile/src/lib/intake/note.ts::buildNote` in fact emits nine distinct
`id:` values — `chief_complaint`, `hpi`, `pmh`, `medications`, `allergies`, `family_social`,
`measurements`, `device_health`, `deferred` — each of which the review screen gives its own
share switch (`note.scopes[section.id] !== false`). The fix covers **all nine**: covering only
eight would leave one buildNote section unrepresentable in the scope, which is precisely the leak
the issue exists to close. "The full set the note actually emits" is the operative requirement,
so the number is nine.

## The bug

`SectionId = Literal["chief_complaint", "hpi", "medications"]` and `NoteBody.sections` capped at
`max_length=3`. A note carrying an `allergies` section, or a `scopes` map naming `allergies`,
cannot even be represented at the boundary — so a patient's choice to withhold allergies has no
field to be recorded in. Acceptance clause 2's assertion "cannot even be written" today.

## What ONE declaration means across the TS/Python boundary

`buildNote` (TS) and `SectionId` (Python) cannot literally share a symbol. The single source is
enforced by test-lock instead:

- `apps/mobile/src/lib/intake/note.ts` exports `NOTE_SECTION_IDS`, the ordered vocabulary, and
  `review_send.spec.ts` scans `note.ts` so `buildNote`'s emitted `id:` set must equal it — the
  declaration cannot drift from the builder.
- `services/api/.../schemas.py` declares `SectionId` (the `Literal`) once and derives
  `SECTION_IDS = get_args(SectionId)` — the runtime tuple is never restated.
- `review_send.spec.ts` parses `schemas.py` and asserts the server `SectionId` set equals the
  mobile `NOTE_SECTION_IDS` — clause 3 parity, so the summary the patient reads is the set the
  server scope check enforces.

## Fail-closed recording

`create_share` now records both halves: `scope_sections = {"section_ids": [...granted],
"withheld_section_ids": [...scoped-off]}`. The clinic read path and Doctor Link redemption still
read `section_ids` only, so a section absent from the grant is never served (unchanged
fail-closed read). The withheld list makes the patient's choice an affirmative record, not an
absence, and the `api.note.share` hash-chained entry references that share (invariant 4).

Default-on send semantics (02 §5.1: a section absent from `scopes` is shared, and scope choices
never block send) are preserved — a scoped-**off** section is what "absent from the grant" means,
and it is excluded from `section_ids` and named in `withheld_section_ids`.

## What is not met

Nothing in the acceptance is deferred. The wire that would carry this note from the phone to the
server is still INT-142's (mobile sync) — the review screen sends offline, so the parity between
the mobile consent summary and the server scope check is enforced structurally (the spec above)
rather than over a live request. That transport was out of scope here and remains INT-142's.
