## 7. Staff sign-in on the host: the WebAuthn session-notes provider, 2026-10-03

**Why.** The API's admin gate refuses a staff token that lacks `aaguid` and `credential_id`
(INT-180, INT-391). Only INT-378's provider writes them, and INT-378 merged to main as
`d3abd45a` on 3 Oct 2026. Before this change, the host's Keycloak ran the stock image and the
stock `webauthn-authenticator`, so every staff sign-in was refused, the owner's included.

**The merge.** Main (`d3abd45a`) was merged into this branch. There were seven conflicts, all
taken from git's own list, and a sweep found no leftover markers.

- **Backlog:** main's file plus this branch's only row, INT-421. The pins go 335 → 336, and
  `files/11` is regenerated.
- **`00_STATE.md`:** main's D18 (INT-432, the clinical decisions register) landed first. This
  branch's admin-access decision is now **D19**, and every reference this branch added
  follows: compose, tests, the checklist, HB-A16, this file, the backlog row and PROGRESS.
- **PROGRESS:** both sides kept.

**What changed.**

- **`infra/staging/Dockerfile.keycloak`.** The runtime stage is INT-390's pin plus one file,
  the provider jar (`--chmod=0444`, `USER 1000`, a readiness `HEALTHCHECK`). The build stage:
  - runs on `eclipse-temurin:21.0.11_10-jdk-noble`, pinned by index digest `8a79c84c…`
    (recomputed from the manifest bytes). JDK 21.0.11+10 is GPL-2.0 with the Classpath
    Exception, per the raw LICENSE at `jdk-21.0.11+10` (sha256 `4b9abebc…`). It is a build
    stage only;
  - fetches Maven and checks it against the `distributionSha256Sum` in the module's
    `maven-wrapper.properties`;
  - runs `mvn -B clean verify` under the module's trusted checksums;
  - refuses any jar that is not `infra/keycloak/providers/webauthn-session-notes.sha256`,
    which is **`91da12328b158bdf7195bd62e510b7aaf47b35b2deb200ff4ec5ffb1b201b694`**.

  The wrapper itself is not used. The image has no `unzip`, and without it the wrapper switches
  to the `.tar.gz`, which the zip's sum cannot match.

  `Dockerfile.keycloak.dockerignore` denies everything, then admits the module and its pin.
  It excludes `target/`.
- **`compose.yaml`.** The keycloak service is now `intake-staging/keycloak:${INTAKE_GIT_SHA}`,
  built from that Dockerfile. It still runs `start` and never `--optimized`, so start-up
  re-augments and loads the jar. `deploy.sh` builds it (`build_keycloak_image`) beside the
  other two images, before anything restarts.
- **The live realm.** The realm was imported before the provider existed, and
  `start --import-realm` skips a realm that exists. So `deploy.sh` runs
  `ensure_staff_webauthn_notes` after Keycloak starts and before the key-set mirror.
  - It runs `infra/staging/keycloak/staff_flow.py` in a one-off api container (stdlib only),
    with the bootstrap admin password on stdin.
  - The script makes the live `staff second factor` subflow match the committed realm:
    - the WebAuthn alternative is `intake-webauthn-session-notes`, ALTERNATIVE, with the
      `amr hwk` reference, and placed before OTP;
    - the stock execution is removed;
    - the OTP alternative is not touched, because that is INT-389, the owner's decision.
  - It refuses to edit a state it does not expect, such as two providers or a foreign
    reference. It fails unless the flow settles. It prints ids only.
  - `smoke.sh` check 7 re-reads the flow with `--check`.
- **`intake-realm.json`.** Its flows now equal the dev realm's (provider in place of stock), as
  `test_the_two_factor_browser_flow_is_kept` requires.
- **The checklist** (§3, staff accounts): the required action is `webauthn-register`, a security
  key or passkey. A TOTP sign-in stays refused until INT-389.

**Proof against a real Keycloak 26.7.4.** The official distribution ran on the JVM with no
container, loopback only. It started with the host's flags: `start`, a fixed `https`
hostname, `hostname-backchannel-dynamic`, `proxy-headers=xforwarded`.

1. **The host's state.** A copy of this branch's staging realm as it was (stock WebAuthn step)
   was imported. `staff_flow.py --check` refused it: `next: add_provider`, exit 3.
2. **The sync.** It took four steps: `add_provider`, `set_alternative`, `remove_stock`,
   `add_hwk_reference`.
   - Then `--check` passed, and a second run changed nothing.
   - The flow read back as provider ALTERNATIVE (priority 0) with `amr hwk`, and OTP
     ALTERNATIVE (priority 20) with `amr otp`.
   - The admin API answered over the backchannel with the fixed hostname, which is the
     condition the host runs under.
3. **A real login.** The server restarted in `start-dev` on the same database, so the login
   pages are loopback. A WebAuthn login (software authenticator) went through the synced realm.
   Its token carried `amr ["pwd","hwk"]`, an `aaguid` equal to the authenticator's, and a
   `credential_id`. The console admitted it (`tenant_clinical_responsible`).
4. **The near-miss.** The same login through an unsynced copy carried neither id. The console
   refused it with `MalformedClaims: claim 'aaguid' is absent`. That is the host's state today.
5. **The build-stage recipe.** It was replayed outside Docker (no container runtime here): curl,
