**Added** this iteration, because the inherited slice left the acceptance's
first line open and — more importantly — left the allow-list bypassable four
ways that files/10 §4 names in a single sentence:

1. **DNS resolve-and-pin.** `EgressPolicy.authorize()` resolves an authorised
   host once through an injectable resolver, refuses any answer inside
   `DENIED_RANGES`, and the transport connects to the pinned address with
   `Host` and `sni_hostname` still naming the hostname.
2. **Purpose and data-class binding.** `purpose_id` on every allow-list row
   (closed `EgressPurpose`), `EgressContext(purpose, data_class)` required at
   transport construction, `DataClass.PSEUDONYMOUS` treated as personal data.
3. **Redirect proof.** The per-hop re-authorisation was true by construction
   and untested; it is now tested, and `guarded_client()` ships with
   `follow_redirects=False` per files/10 §4.
4. **The transfer log.** `TransferRecord` / `TransferLog` /
   `InMemoryTransferLog` / `LoggingTransferLog` — one record per decision with
   `{ts, host, port, purpose, data_class, bytes_out, decision, reason, tier}`.
5. **`sec_egress_denied_total`**, promoted from `planned` to `live` in
   observability/metrics_catalog.yaml and emitted on every refusal.
6. **The forward proxy in dev compose**: `infra/docker-compose.egress.yml`
   (profile `egress`), `infra/security/squid/squid.conf` **generated** from the
   allow-list by `scripts/security/render_egress_proxy_conf.py`, `make egress`
   / `egress-down` / `egress-conf` / `egress-conf-check`, and the
   `egress-proxy` row in observability/registry.yaml with the licence blob
   read and hashed.
7. `tests/security/test_egress_allowlist.py` (36) and
   `tests/infra/test_egress_proxy.py` (30).

## The four bypasses, and whether each is genuinely blocked

| bypass | blocked? | how | test |
|---|---|---|---|
| IP literal in the URL (`169.254.169.254`, `127.0.0.1`, `10.x`, `[2001:db8::1]`) | **yes**, before any lookup | `EgressPolicy.check` refuses any host that parses as an address; the allow-list also refuses IP-literal *entries* | `test_ip_literal_url_is_refused_before_any_lookup`, `test_literal_ip_hosts_denied_even_if_someone_lists_them`, `test_allowlist_refuses_ip_literal_entries` |
| allow-listed hostname resolving into a private / loopback / link-local / metadata range | **yes** | `authorize()` resolves and refuses on `DENIED_RANGES`; a split answer fails closed on the denied member rather than picking the good one | `test_allowlisted_host_resolving_into_a_denied_range_is_refused` (10 addresses), `test_a_split_answer_fails_closed_on_the_denied_member`, `test_an_empty_answer_is_a_denial_not_a_pass` |
| DNS rebinding between check and connect | **yes** | resolve once, pin, connect to the pinned address; there is no second lookup to win. `Host` and `sni_hostname` still name the hostname, so certificate verification is unchanged | `test_the_connection_goes_to_the_pinned_address_with_the_hostname_intact`, `test_rebinding_cannot_move_the_destination_between_check_and_connect`, `test_each_request_is_authorised_and_pinned_independently`, `test_ipv6_answers_are_pinned_as_bracketed_url_hosts` |
| redirect to a non-allow-listed host | **yes** | every hop re-enters the transport and is checked, resolved and pinned independently; `guarded_client` also ships with redirects off | `test_a_redirect_to_an_unlisted_host_is_refused_on_the_hop`, `test_a_redirect_to_a_denied_ip_literal_is_refused_on_the_hop`, `test_guarded_client_does_not_follow_redirects_by_default`, `test_a_relative_redirect_resolves_against_the_hostname_not_the_pin` |
| PHI bound for an allow-listed but wrong-purpose destination | **yes** | `purpose_id` per row plus a required `EgressContext`; personal data (pseudonymous included) needs `phi_allowed`, which additionally needs the runtime env var | `test_personal_data_bound_for_a_non_personal_destination_is_refused`, `test_pseudonymous_data_is_personal_data_and_is_refused_too`, `test_a_purpose_the_row_does_not_serve_is_refused`, `test_the_transport_refuses_a_wrong_purpose_before_resolving` |

Two properties worth naming because they are easy to get wrong and are pinned:

- **Order.** The allow-list check runs *before* resolution
  (`test_a_host_that_is_not_allow_listed_is_never_resolved`). Resolving first
  would turn every refused destination into a DNS query carrying an
  attacker-chosen name to a resolver we do not own — a working exfiltration
  channel out of a request we correctly denied.
- **The pin is a copy, not a mutation**
  (`test_a_relative_redirect_resolves_against_the_hostname_not_the_pin`).
  httpx assigns `response.request` from the object it built, so rewriting the
  URL in place would make a relative `Location` resolve against the pinned
  address on the next hop.

## Is invariant 19 now a fact?

CLAUDE.md states as fact: "the `anthropic|openai|google` LLM adapters exist as
the mock/dev path only and are blocked on the PHI path by the egress
allow-list." After this issue that is true by three independent constructions,
and each is tested:

1. **The PHI tier is empty** and a test holds it empty
   (`test_shipped_allowlist_validates_and_phi_path_is_empty`). A policy built
   for `phi_path` denies everything, vendor or not
   (`test_phi_path_tier_is_default_deny_everything`).
2. **`assert_dev_only_vendors` refuses the three families outright** on the
   PHI tier, and refuses them anywhere with `phi_allowed: true` — matched by
   domain family (`anthropic.com`, `openai.com`, `googleapis.com` as suffixes,
   plus a glob wider than the family), with a lookalike domain as the
   near-miss negative control.
3. **Topology.** `infra/docker-compose.egress.yml` puts PHI-path services on
   an `internal: true` network the proxy is not attached to, so an empty tier
   is a Docker-enforced fact rather than a YAML promise
   (`test_the_phi_network_is_internal_and_the_proxy_is_not_on_it`).

The honest boundary of that claim: (1) and (2) are enforced wherever the
allow-list is loaded and `guarded_transport` is used, which today is the
library itself — no service on the PHI path has an outbound HTTP client yet,
so there is no adoption to point at. (3) is enforced by Docker for any service
placed on the `phi` network, and no service is placed there yet either,
because the PHI-path services (`services/api`, `services/voice-runtime`) are
not in a compose file at all (registry rows say `self_hosted_now: false`,
"code landed … not yet wired into compose/systemd"). The mechanism is
complete, tested and fails closed; wiring each service to it is that service's
deployment issue. This is stated rather than papered over: an issue that
claimed adoption it does not have would be the placeholder invariant 17
forbids.

## Invariant 6 at both enforcement points

The in-process record is a frozen dataclass with a closed field list, so there
is no key a URL, a query string or a body could occupy — asserted directly
(`test_transfer_records_have_no_field_a_payload_could_occupy`) rather than by
filtering. Denial messages carry no path or query
(`test_the_denial_message_carries_no_path_or_query`), and neither does the
resolution-denial reason echo the attacker-supplied address.

The proxy's own access log was the sharper hazard and is a real finding:
squid's `%ru` is `host:port` for a CONNECT — exactly what the transfer
register wants — but the **full URL** for any other method, which is where a
token or an identifier would land. So the format carrying `%ru` is attached to
a `CONNECT`-scoped `access_log` line and the non-CONNECT format does not carry
it at all, with `strip_query_terms on` set explicitly rather than relied on as
a default. `test_no_access_log_line_can_write_a_url_path_or_query` reads every
`access_log` line and its format and fails if `%ru` appears in one that is not
CONNECT-scoped.

## The two enforcers had to be made to compose

Writing both revealed a trap that neither would have shown alone. The
in-process guard rewrites the request's URL host to the pinned address; squid
matches the **hostname** on the CONNECT line against `vendor_exact` /
`vendor_glob`, and an IP literal matches neither — so a process using
`guarded_transport()` *behind* the proxy would have had every request refused
by the control that was supposed to allow it. Two correct controls, composed,
denying everything.

Resolved by making the composition explicit rather than documenting the trap:
`guarded_transport(..., proxy=...)` keeps the hostname and delegates
resolve-and-pin to the proxy tier, which is where files/10 §4 puts it
("resolves once and pins, re-validating on connect") and where `denied_nets
dst` refuses the private/metadata ranges. The allow-list, purpose and
data-class checks run in process either way. Three tests pin it:
`test_behind_the_proxy_the_hostname_survives_to_the_connect_line` (hostname
intact, no `sni_hostname`, resolver never called),
`test_the_allow_list_still_refuses_behind_the_proxy` and
`test_a_wrong_purpose_is_still_refused_behind_the_proxy` — delegating the pin
must not delegate the policy.

One related property, stated because it is easy to assume the other way:
`httpx` ignores `HTTP_PROXY`/`HTTPS_PROXY` when an explicit transport is
supplied, so the guard cannot be routed around by an environment variable. The
proxy is only ever the one named in the call.

## One list, two enforcers

`infra/security/egress-allowlist.yaml` is the only file anyone edits.
`scripts/security/render_egress_proxy_conf.py` generates the squid config from
it; `--check` fails when the committed render is stale
(`test_the_committed_config_is_not_stale`), and an eleven-host table is decided
through *both* the library's `AllowlistEntry.matches` and the rendered ACLs
(`test_the_proxy_acls_and_the_library_agree_host_for_host`). That table caught
the one place the two would otherwise have disagreed: squid's `dstdomain
.hf.co` matches the bare apex and `AllowlistEntry.matches` does not, so globs
render as an anchored `dstdom_regex` instead. `DENIED_RANGES` is likewise one
list rendered into both, asserted equal.

## What was refused rather than invented

- **No vendor host was added to the PHI tier, and none was asked for.**
  HB-L5 is closed by D-self-hosting ("there is no vendor socket at all"), so
  the empty tier is the answer, not a gap. Asking again would violate the
  HUMAN_BLOCKERS rule.
- **The proxy is not booted.** HB-I1 (free 80–100 GB of disk) and HB-I2 (the
  security + observability tiers need 22 GB) are open; INT-205 set the
  precedent of validating such a tier statically rather than shrinking it
  until it ran. `docker compose config` was not run either — that would need
  the daemon. Everything asserted about the tier is asserted about the files.
- **`make security` does not exist.** CLAUDE.md names it and INT-019 builds
  it; it is `status: todo`. No stand-in was written: a `security` target that
  ran a subset would make the gate look green for gates that do not exist yet.
- **No connector-endpoint allow-list.** files/10 §9 invariant 46 wants a
  registered *per-tenant* destination list bound to the signed DPA. The
  primitives it needs (denied ranges, resolve-and-pin, redirect refusal,
  no-free-text) are all here and reusable, but the per-tenant registration and
  the DPA binding belong to the connector issues, and no tenant, endpoint or
  DPA term was invented to fill them in.

## Decisions and collisions surfaced while proving it

- **The deferral in the previous evidence was wrong.** It sent the compose
  proxy to "INT-203 infra". INT-203 is the *production* edge tier and it
  `depends_on: [INT-018]`, so deferring INT-018's dev proxy to it made the
  acceptance unreachable in both directions. Corrected: the dev proxy lands
  here, INT-203 keeps Traefik/Coraza/CrowdSec/cert-manager and the prod egress
  proxy.
- **The hook-protected allow-list.** `infra/security/egress-allowlist.yaml` is
  on the guard list (07 §3.8) and the guard's own message names the escape
  hatch: `ALLOW_PROTECTED=1` "only with an ADR". ADR-025 is that ADR, written
  before the change and recording it explicitly; the schema addition
  (`purpose_id`) was applied under it and the file returns to guard-only
  change. The inherited commit created the file by the same route.
- **Vendor literals vs the INT-001 gate** (carried forward, unchanged):
  `scripts/ci/assert_no_vendor_calls.sh` refuses literal vendor endpoint
  strings outside `files/`, so the vendor pin matches domain *families*, which
  is strictly broader than three exact hosts and leaves the gate untouched.
- **Event name** (carried forward): the acceptance says `sec.egress_denied`
  (implemented, and the metric is `sec.egress_denied_total` per files/08 §4);
  files/07 §6 spells it `security.egress_denied` in one spot. The acceptance
  and the metrics catalogue agree with each other, so the odd spelling is the
  defect — flagged for a docs-consistency pass, not changed here.
- **Test-file name reconciled.** The backlog `tests:` field named
  `tests/security/test_egress_allowlist.py`, which did not exist; it does now
  (the bypass lane), and the field lists all three files.
- **Documentation addresses in tests.** Python's `ipaddress` marks the RFC
  5737 / RFC 3849 documentation ranges `is_private`, so `DENIED_RANGES` is an
  explicit list rather than `not ip.is_global` — which is also what makes it
  renderable into squid's `dst` ACL, and lets `203.0.113.10` be the stand-in
  public answer it was reserved to be.
