## Acceptance, clause by clause

### "forward proxy in dev compose"

**Delivered this iteration.** `infra/docker-compose.dev.yml` gains a
`forward-proxy` service (squid), in the **default** tier so `make dev` —
`docker compose --profile clamav up -d --wait` with no service list — starts
it. Its entire configuration is `infra/security/squid/squid.conf`, which is
**generated** from `infra/security/egress-allowlist.yaml` by the new
`intake_platform.egress_proxy`. The allow-list header already promised this
("the deployed proxy tier will consume the same file"); this is that
consumption, so the proxy and the in-process policy are one source of truth
rendered twice, with a byte-identity test that makes drift a build failure.

> ⚠️ **This service has never been started.** There is no Docker daemon in the
> session that wrote it, so nothing here is a claim that squid boots, that the
> healthcheck passes, or that a real CONNECT is tunnelled or refused. The
> service and its config are validated **statically**, the way INT-202 landed
> the backup tier (`tests/infra/test_restore_drill.py`): the compose YAML
> parses and has the required shape, the image is pinned, the ACL order is
> default-deny, the log format carries no path or query, and the committed
> conf is byte-identical to the render. A first boot on a host with a daemon
> is still owed, and is the one thing that would move this from "written and
> statically validated" to "demonstrated". The same caveat is written into the
> compose comment and into the generated conf's header, so a reader who never
> opens this file still sees it.

Design notes that are decisions, not incidentals:

- **`forward-proxy`, not `egress-proxy`.** `tests/voice/test_audio_retention_guard.py`
  refuses any dev-compose service whose name or image contains
  `egress`/`ingress`/`recorder` — those are LiveKit's *recording* components
  and the guard exists for invariant 3. That guard is correct; the name works
  around it rather than weakening it.
- **Pinned by exact tag *and* manifest-list digest**
  (`ubuntu/squid:6.6-24.04_edge@sha256:8a3baed4…`). Invariant 14 pins images,
  and a floating tag on the host that terminates every outbound connection is
  a supply-chain hole. Tag and digest were verified to exist, multi-arch
  (amd64/arm64/ppc64le/s390x), against the Docker Hub registry API on
  31 Aug 2026. The image *config blob* could not be fetched — this session's
  own egress proxy 403s `production.cloudfront.docker.com` — so the compose
  entry deliberately depends on nothing about the image's internals beyond
  the `squid` binary and the documented `/etc/squid/squid.conf` path.
- **CONNECT to port 443 only.** Every allow-list row is `protocol: https`, so
  the proxy tunnels and never sees a request line. That is a security property
  *and* the reason the access log structurally cannot contain a path or query.
- **No credential anywhere.** The proxy authenticates nobody — access control
  is the ACL plus network placement — so there is no secret for `docker
  inspect` or the compose file to leak (invariant 14). `env.example` is
  untouched; the OpenBao-pointer-only assertion in
  `tests/security/test_openbao_wiring.py` still holds.
- **The proxy stores nothing**: `cache deny all`, no `cache_dir`, no cache
  volume. A caching egress proxy is a store of response bodies.
- **`forwarded_for delete` / `via off`**: the register records a transfer to a
  vendor, not who inside asked for it.

### "only allow-listed vendor hosts reachable from PHI-path services"

**This was the real gap and it is now closed.** Before this iteration the
policy library was correct and *nothing in a committed service called it* —
`intake_platform/llm/gateway.py` (INT-083) was the only consumer, and
`ehrbase.py` merely named `guarded_transport` in a docstring as something "a
deployment can pass". A library that is correct and uncalled is exactly the
failure mode this clause exists to catch.

Three PHI-path clients now compose the guard **by construction**, with a
refusal proved through each service's own client:

| service | client | wired at | proof |
|---|---|---|---|
| EHRbase (openEHR CDR, carries compositions) | `EhrbaseClient` | `ehrbase.py` `__init__` | `TestEhrbaseClient` — `status()` against an unlisted host raises `EgressDenied` and emits one `sec.egress_denied` record |
| OpenBao (every credential + the transit KEKs) | `SecretsProvider` | `secrets.py` `__init__` | `TestSecretsProvider` — `check_ready()` / `get_kv()` refused; also covers `TransitKekProvider`, which shares this client |
| Unleash (feature flags: kill switch, lane enablement) | `UnleashProvider` | `flags.py` `__init__` | `TestUnleashProvider` — `get_bool()` refused |

What guard, and why it is **not** the vendor allow-list. All three run inside
the deployment boundary (files/10 §2 "Services"; `ehrbase.py`'s own header:
"inside the deployment boundary … no PHI egress path"), and `phi_path: []` is
not an empty list awaiting entries — it is the design (invariant 19 /
00_STATE D11). So the guard a PHI-path client carries is the new
`intake_platform.egress_boundary.BoundaryPolicy`: **its own configured
in-boundary destination and nothing else**. That is strictly narrower than the
vendor allow-list, which is what "the PHI path reaches no vendor" means when
written as code rather than as prose.

`BoundaryPolicy` satisfies the new `EgressCheck` protocol in `egress.py`, so
it is enforced by the *same* `guarded_transport()` and emits the *same*
structured record. One enforcement point, two allow sets.

The in-boundary rule — a destination that **cannot exist in the public DNS**,
or is the machine itself:

- a bare service label with no dot (`ehrbase`, `openbao`) — a compose or k8s
  service name, with no public TLD to resolve against;
- a suffix reserved by a standard so it is never delegated: `.test`,
  `.invalid`, `.localhost` (RFC 6761), `.local` (RFC 6762 mDNS, which covers
  `.svc.cluster.local`), `.internal` (ICANN private-use, 2024);
- a loopback literal (`127.0.0.0/8`, `::1`) — the dev tier's form.

Everything else is refused, including **every routable IP literal**: RFC 1918
space and link-local as well as public. "Inside a private network" is not
"inside our boundary", and `169.254.169.254` — the payoff files/10 §4 names
for a server-side fetch made from within the PHI network — is refused by the
same clause.

It fails **at request time, never at construction**: a client with an
out-of-boundary base URL builds fine and then refuses every request. That is
deliberate — the acceptance is "refused *and logged*", and a client that
raised at import would produce no transfer record at all.

`transport=` on `EhrbaseClient` and `UnleashProvider` is now the transport
*underneath* the guard, not a way around it (`test_an_injected_transport_does_not_bypass_the_guard`).
A guard that every exercised path bypasses is a guard nobody exercises.

An anti-regression gate closes the loop:
`TestNoUnguardedClient::test_every_httpx_client_in_intake_platform_composes_a_guard`
walks every module under `intake_platform/` and fails if one constructs an
`httpx.Client`/`AsyncClient` without composing `guarded_transport` or
`boundary_transport`. Adding an unguarded client is now a red build, not a
review miss.

### "every egress logged {host,purpose,bytes,ts} feeding the vendor-transfer register"

Two feeds, same field set, both asserted to carry no payload, path or query:

- **In-process** (already delivered, unchanged): `sec.egress_allowed` /
  `sec.egress_denied` with `{host, port, decision, purpose, bytes_out,
  reason}` plus the log record's own timestamp.
- **At the proxy** (new): the generated `logformat intake_transfer` is
  `ts=%ts.%03tu host=%>rd port=%>rP decision=%Ss bytes_out=%>st reason=%err_code`.
  `%>rd`/`%>rP` are the destination host and port. The path-bearing codes
  (`%ru`, `%rp` and every `>`/`<` variant) and every client-identity code
  (`%>a`, `%>A`, `%[un`, `%ul`, `%>eui`) are asserted absent — invariant 6,
  and a query string is exactly where an identifier would leak.

`purpose` and `basis` are not repeated per line. They are joined per host from
the allow-list row, which is where a human already reviews them; the rendered
conf carries each row's purpose and basis as a comment above its ACL, so the
join is readable in the artefact itself.

### "denial emits sec.egress_denied"

Unchanged and still pinned (`test_denial_emits_structured_record_and_allow_logs_purpose`),
now additionally asserted through each of the three service clients.

  covers a vendor LLM **domain family** with `phi_allowed: true`, or puts one
  on the PHI-path tier at all; a lookalike domain is the near-miss negative
  control.

  `httpx.MockTransport` (CI stays vendor-free) passes an allow-listed call
  through and raises `EgressDenied` for an unlisted host; `http://` infers
  port 80 and is refused by the 443-only list.
- **The log is transfer evidence, not a leak**: denial emits a WARNING record
  with message `sec.egress_denied` and `{host, port, decision, purpose,
  bytes_out, reason}`; allowed calls emit `sec.egress_allowed` with the
  header-declared `bytes_out`; URL paths, query strings and bodies are
  asserted absent from every record (invariant 6 — a query string is exactly
  where an identifier would leak). `bytes` and `ts` of the acceptance map to
  `bytes_out` + the record timestamp.
