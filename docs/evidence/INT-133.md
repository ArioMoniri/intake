# Evidence — INT-133 · Profiles, companions, guardian flows (minors), proxy acknowledgement

Acceptance (docs/backlog/issues.yaml, verbatim): *"under-18 only via guardian
account with guardian consent; adolescent private-section policy implemented
per 06 §6; proxy-reported flag on every record"*. Legal: TMK-339, HHY-24.
Depends on: INT-131, INT-223.

INT-223 built the **rules engine** — age bands from a verified DOB, the
required consent actor, the adolescent-private visibility decision, and the
shut `guardian_link` gate. INT-133 is the **profile and flow layer on top of
it**, and it consumes those decisions rather than repeating or relaxing them:
`resolve_consent_actor` is the only thing in this repo that turns a date of
birth into a band, and this layer calls it.

What landed:

- `intake_platform.profiles.attribution` — the three files/02 §3 attribution
  values (`self_report`, `proxy_report`, `assisted_self_report`) **derived**
  from a declared role + speaker. files/06 §6's "companion/proxy answers are
  always flagged `proxy_reported` on the record" is a consequence here, never
  a caller's assertion; files/13 §13's third-party rule rides the same
  derivation (sensitive sections to text, safeguarding not asked at all).
- `intake_platform.profiles.flow` — the next step for a session, with the
  HB-L20 policy rows that block it. Age axis FIRST, companion rules second,
  so an acknowledgement can never look like proof of representation.
- `intake_platform.profiles.sections` — the adolescent-private section per
  files/06 §6, delegating the release decision to INT-223 and adding the
  render rule (a guardian entitled by a recorded policy still does not get
  the section painted onto a screen the adolescent can see).
- `sessions.attribution` / `.third_party_present` / `.proxy_ack_at` +
  migration `0005_int133`, projected onto **every** record the API emits
  from a session — visit create, visit read, visit list, note read, note
  write. Documents are deliberately out: files/06 §6 flags companion/proxy
  *answers*, an uploaded lab report is not one, and `documents` rows hang
  off the patient rather than a session, so stamping them would assert a
  provenance nobody observed.
- `GET /v1/me/profile` (`intake_api.profile_routes`) — SYSTEM facts only,
  declaring the `core` scope so `unguarded_data_routes()` stays empty.
- Mobile: `src/lib/profile/{attribution,refusals,api,store}.ts`, the
  `(tabs)/me/companion.tsx` screen, and the tr/en copy for the four refusals.

## Which flows fail closed, and on which HB-L20 question

`blocked_on` is a **server-side** fact. It never travels in a response body
and never appears in the app's copy: a body or a screen saying
`adolescent_self_consent` would disclose that this subject is a minor
(invariant 6). Both are pinned by tests.

| flow | refusal (typed 403/422) | HB-L20 question(s) that gate it |
|---|---|---|
| under-12 subject | `guardian_consent_required` | `guardian_link_basis`, `guardian_relationship_proof` |
| 12–17 subject | `guardian_consent_required` | `adolescent_self_consent`, `emancipation`, `guardian_link_basis`, `guardian_relationship_proof` |
| self-declared DOB | `dob_unverified` | `unverified_dob` |
| non-TR subject | `jurisdiction_unsupported` | `jurisdiction_tr_only` |
| guardian sees adolescent-private, no recorded clinic policy | withheld | `adolescent_private_guardian_default` |
| companion with no acknowledgement | `proxy_acknowledgement_required` | *none* — a product rule; recoverable in-app |
| no DOB recorded at all | *service continues* | `dob_collection_mandatory` — the minor regime is simply not asserted (INT-223's `no_dob_recorded`), recorded on the outcome as `minor_regime_asserted: False` |

Every relaxation INT-223 refused stays refused, and each is *unreachable*
rather than merely unimplemented:

- **no adolescent self-consent** — the required actor comes from the engine,
  and no argument to `resolve_profile_flow` can change it (test iterates
  every role × speaker × acknowledgement combination for a 14-year-old);
- **no emancipation** — there is no emancipation parameter to pass (test
  inspects the signature), and no `ergin kıl`/`emancipat` affordance exists
  anywhere in the mobile tree (test walks every `.ts`/`.tsx`);
- **no guardian-disclosure default** — no recorded clinic policy means the
  guardian sees nothing, and the decision names the row;
- **`guardian_link` stays shut** — the flow never consults the linkage store,
  and `GET /v1/me/profile` reports `guardian_flow_available: false` read
  straight off the safety flag. The mobile screen renders a closed door with
  the reason on it instead of a form that would end in a refusal.

## New persisted personal-data category

**None was created, and that is the deliberate answer.** The three new
`sessions` columns are the same provenance facts the clinician note already
carries and already exports to FHIR
(`clinical_schemas.note.ScreeningProvenance`: `proxy_reported`,
`third_party_present`), lifted to the session so every derived record reads
one flag instead of holding a settable copy that can drift.
`proxy_ack_at` is a timestamp on the patient's own session row. Nothing
identifies the companion: no name, no account ref, no relationship, no free
text (invariant 14/6).

The thing that *would* be a new category — a persisted person↔person link —
is exactly `guardian_links` (INT-223, migration `0003_int223`), and it stays
behind its shut gate with `awaiting-human` on basis and retention. INT-133
adds no second linkage table: the companion declaration is **session-scoped
and in memory on the device** (`src/lib/profile/store.ts`, pinned as writing
to no storage API), so "a companion is answering for this patient" is a fact
about one sitting rather than a stored fact about a second person.

**The ask that stands** (no new HUMAN_BLOCKERS row needed — it is HB-L20's
own `guardian_link_basis` and `guardian_relationship_proof`): until Turkish
counsel names a KVKK m.5/m.6 ground and a retention period for a persisted
guardian↔minor record, and states what evidence of velâyet is required and
who verifies it, **no under-18 can be served at all** — not through a
guardian account, not through an acknowledged companion, not through any
path this issue could build. The mechanism is complete and the door is shut.

## What this issue did NOT do

- No consent or legal text was authored; `docs/legal/` is untouched. The
  in-session proxy acknowledgement is a **protocol** question that already
  exists (`identity_check.proxy_reported` in the base pack) — not a legal
  text, and `packages/protocols/**` is untouched.
- No date of birth is collected or persisted. `NoAgeRecordSource` still
  truthfully reports that none exists, so in the shipped configuration the
  age gate asserts nothing and the consent ledger alone answers — which is
  why the guardian door is closed rather than merely unused.
- No metric was emitted (see the sec-row note above) and
  `observability/metrics_catalog.yaml` is unchanged.
- `docs/backlog/`, `docs/PROGRESS.md`, `files/HUMAN_BLOCKERS.md` and
  `.github/**` are untouched by this iteration, per the iteration brief.
