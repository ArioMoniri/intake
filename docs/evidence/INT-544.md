## 2. Sharded check-py, every floor on the combined data

`scripts/ci/py_shards.py` (Makefile `check-py-shard SHARD=n`, `check-py-combine`):

- **The split.** Every tracked file pytest collects (pyproject's `testpaths`
  and `python_files`, read rather than copied) goes to exactly one of three
  shards. The packing is greedy longest-first over
  `scripts/ci/py_shard_durations.json`. Ties go to the lower shard, then the
  lower path. A file with no record weighs the median. Shard 1 carries
  ruff+mypy (82 s, CI) and shard 2 the triage lane (34 s, CI) as reserved
  load. The recorded seconds come from one local whole-suite run, scaled to
  CI's 1826 s (the file says so). On f7f6b6ee the plan was 96 / 98 / 140
  files, about 10.2 min each in CI seconds. On 2ccd07ee it is 144 / 102 /
  102 files, because 14 newer test files weigh the median until the next
  `py_shards.py record`. That command reads the junit reports each shard
  uploads.
- **How a shard runs pytest.** It passes no path. pytest walks the testpaths
  exactly as the whole-suite run does and `--ignore`s the other shards'
  files. The first design passed each shard its own files. That loads every
  directory's `conftest.py` up front, and `tests/research`'s
  `from conftest import ...` then imported `tests/voice`'s conftest
  (ImportError, measured). The `--ignore` form also fails safe: a file the
  split does not know about, such as one pytest collects but git does not
  track, runs in every shard rather than in none.
- **Coverage.** Every floored source is measured in every shard
  (`--cov` x 9, `--cov-branch`). `relative_files = true` lets the data from
  three checkouts combine. `combine` refuses a missing shard's data, a
  missing junit report, or a report with failures. It then enforces every
  floor of `make check-py` on the combined data with coverage's own
  `should_fail_under`, the function pytest-cov uses.
  `tests/ci/test_py_shards.py` reads the floors back from the Makefile's
  check-py lines, so the two cannot drift.
- **What changes in the measurement, and what does not.** The api floor is
  measured exactly as before: every test, default addopts. The triage floor
  keeps its own run on tests/safety alone, word for word as in `make check-py`
  and `make safety`. It is the one floor that proves the safety goldens, and
  not just any test, reach every triage branch. The other seven floors were
  measured on their own directories' tests only. On the combined data, any
  test's execution counts toward them. Same tree (f7f6b6ee), same laptop:

## 3. Path-scoped lanes

`scripts/ci/lanes.py` runs first in each lane job, on the bare runner's
python3. It writes `python=`, `ts=` and `integration=` to `$GITHUB_OUTPUT`.
Every later step runs unless its lane is exactly `false`. So a missing,
empty or misspelled output runs the lane, and a skipped lane's job still
succeeds and reports success to its required check.

- **python (check-py and its shards): runs on every diff.** 73 tracked Python
  files name paths under apps/. Examples are session.tsx source slicing, the
  i18n catalogues and the admin fixtures recorded from the API. The rest of
  the suite reads docs/, files/ and infra/. A filter that skipped check-py
  would let a mobile change that breaks a Python test land green. This is the
  conservative mapping's answer to "vice versa", stated rather than hidden.
- **ts (check-ts):** runs for a pnpm workspace that holds a package.json, the
  root TypeScript and pnpm configuration, or CI itself. No TypeScript source
  reads tests/, docs/, files/, infra/, migrations/ or a Python package. The
  `git grep` behind that claim is a test.
- **integration (check-integration):** runs for anything outside the
  TypeScript workspaces and that root configuration.
- **Every lane** runs on a push, an empty diff, a checkout that is not a
  two-parent merge commit, or a git error. It also runs on any change under
  .github/, scripts/ci/, infra/ci/ or to the Makefile.
- **Never filtered:** gates (no_placeholders, assert_no_vendor_calls,
  evidence_check, sec_row linkage) and every security.yml job: gitleaks,
  sast (semgrep, bandit), vulnerabilities (trivy, osv), iac (trivy config,
  checkov), licenses, sbom, phi-scan, claims-scan. Tests assert none of them
  reads the decision or carries a condition.
- **Replayed on the last 60 merged pull requests** with the real classifier:
  23 would skip check-ts, none would skip check-integration (every one touched
  docs/backlog or another non-workspace path), and none skips check-py. The
  filter saves about 0.7 runner-minutes per pull request on average. It is in
  place for the TypeScript-only work to come.
- `tests/ci/test_lanes.py` runs the decision on real git repositories (a
  base, a pull request head, their merge commit). A move out of a workspace
  still runs check-ts, because the diff uses `--no-renames`. It also checks
  every lane job's conditions, with near misses (`== 'true'`, a missing
  condition, a shallow checkout, a conditional decision, a job-level `if`).

## 4. The cache seed

**Why not actions/cache with a local backend.** A local cache server
accepts writes from jobs, so any pull request's job could poison an entry
that a later main run restores. That breaks "read-only to jobs". Pointing
setup-uv or setup-node at it changes nothing about eviction or trust. The
measured problem is a 10 GB Actions cache that is over its limit and evicting
entries, and a deid restore that `make deid-model` never re-checks: a present
`config.json` reads as "present".

**What a seed is.** Each runner keeps `$CI_ROOT/seed` (seed.sh):

```
current -> gen-<16 hex of the inputs bundle's sha256>
gen-*/uv/                uv cache: `uv sync --frozen --all-packages --no-install-workspace`
gen-*/pnpm-store/        pnpm store: `pnpm fetch` (lockfile only, runs no install script)
gen-*/deid/deid-tr-ner-v1.tar.gz   the release asset, sha256 = the Makefile's pin
gen-*/MANIFEST.sha256    sha256 of every file
gen-*/SEED               inputs=<bundle sha256> manifest=<sha256 of MANIFEST> built=<UTC>
```

- **Per runner, read-only to jobs.** The seed sits in the runner's own CI
  root, which is `root:ghrunnerN 0750` and ACL-denied to every other runner
  (guard.sh peer paths). It is root-owned with no group or other write bit.
  The job unit binds it read-only (`BindReadOnlyPaths=-…/seed`). The isolation
  probe adds a check that a job cannot write it.
- **Refreshed by the registrar between jobs.** cycle.sh `prepare`, after the
  guards and the namespace proof and before the runner tree and
  registration, runs `seed.sh N refresh`. If the staged inputs changed, it
  rebuilds; otherwise it checks that every entry is still root-owned and the
  manifest is the one recorded. Then it wipes the workspace again, because
  the build ran there. A failed refresh removes the seed and the runner
  registers anyway. Its jobs fall back to the network.
- **Built where a job runs.** The build runs as the runner's user, in the job
  unit's own sandbox (the probe's `job_props`, moved to guard.sh and shared),
  in its network namespace, with `RuntimeMaxSec`. Package code that runs
  while uv builds a wheel runs exactly where a job's would. Root then copies
  the output and owns it. It refuses a device, pipe, socket, setuid or setgid
  bit, or a link that is absolute or climbs out of the tree (uv's own links
  are relative, `../../archive-v0/…`, so the cache is relocatable). Only then
  does root write the manifest.
- **The inputs come from the owner, not from a job.** `aws_runner.sh seed
  [--ref]` cuts a bundle on the laptop. It holds the 24 lockfiles and
  manifests (uv.lock, .python-version, every pyproject.toml and package.json,
  pnpm-lock.yaml, pnpm-workspace.yaml) and the deid release asset, checked
  against the Makefile's pin. It contains no source file, credential or PHI.
  The bundle goes to the host as one sha256-pinned S3 object behind a
  presigned URL, the same path as `install`. `seed.sh stage` refuses a bundle
  that holds anything else. No runner user can read the staged inputs.
- **Integrity pinned by hash, end to end.** The bundle's sha256 is pinned in
  transit. Every package's hash is pinned in the lockfiles, and uv and pnpm
  check each package. The tools are pinned in runner.conf by sha256: uv
  0.13.1, `eadd9d27…0220`, from its .sha256 file and the GitHub API digest;
  pnpm 9.15.9, `9b861b35…9760`, the sha256 of the @pnpm/linux-x64 tarball
  whose sha512 matches the npm registry's published integrity. The deid
  asset is checked against `SEED_DEID_SHA256`, which a test holds equal to the
  Makefile pin. Every file is listed in the manifest, and the manifest's own
  sha256 is recorded in SEED.
- **The job side.** `scripts/ci/ci_seed.sh restore uv|pnpm|deid` checks the
  manifest against SEED, then each part's files against the manifest, and
  that no file was added. It copies the part into the job's temp:
  `UV_CACHE_DIR`, `npm_config_store_dir` (written to `$GITHUB_ENV`), and
  `.cache/deid-tr-ner-v1` only when the asset matches this commit's pin. It
  writes `<part>=true` only then. The workflow enables setup-uv's and
  setup-node's Actions cache, and the deid `actions/cache` step, only where a
  part was not restored. A part that fails a check is never used, and the job
  log carries a warning.
- **What it buys, honestly.** About the same seconds per job as a warm
  Actions cache hit. Copying and checking the parts is a local disk operation
  where the Actions cache downloads and unpacks. What it removes is the
  dependence on a cache that evicts at 10 GB, which costs a full download on
  a miss. It also gives a restore that is checked against a pinned manifest.
  The job-started hook prints each job's seed and manifest digest, so the
  after-measurement reads both.

## 5. Queued main runs collapse

The group becomes `${{ github.workflow }}-${{ github.ref }}` in both workflows.
cancel-in-progress stays true for pull_request events only.

- A pull request's runs share `refs/pull/N/merge`. A new push cancels the
  older run, queued or in progress, as INT-524 delivered.
- Every push to main shares `refs/heads/main`. With cancel-in-progress false,
  the run in progress always finishes. GitHub keeps at most one run pending
  per group, and a newer push replaces it (the semantics INT-524 quoted).
  On 16 Oct, the burst of three main pushes at 11:23-11:24 would have run two
  ci runs instead of three. The third would have replaced the second while it
  waited. That saves about 54 runner-minutes in that burst alone.
- A v* tag has a ref, and so a group, of its own. It never replaces main's run
  or main its run, so a release is always signed.
- **Trade-off, for the owner.** An intermediate main commit whose queued run
  was replaced gets no CI run of its own. Its status shows a cancelled run.
  The next main run tests a tree that contains it. A regression is still
  caught, but it is attributed to a batch of merges rather than to one commit.
  Every such commit was green as a pull request first. The owner's
  alternative is to keep one run per main commit. That means restoring
  INT-524's group, which the test keeps as the near miss `PER_SHA_GROUP`
  (`int-524-every-main-commit-keeps-its-own-run`), a one-line change in each
  file.

**Known numbers.** These are from INT-467's evidence, read on the host on

**What decides headroom.** Run the read-only command below on a busy
afternoon, while at least three pull requests are in CI. Add runners 4-6
under the present ceiling only if all of these hold:

- the slice's `memory.peak` stays below about 12 GiB (MemoryHigh is 14G);
- the host's `available` memory stays above 8 GiB;
- `/proc/pressure/cpu` some avg60 stays below about 25 %, and memory and IO
  `full` stay near 0;
- the NVMe volume keeps 150 GiB free. Each runner holds a workspace, an image
  store and a seed of about 2-3 GiB.

If memory is the limit, raising MemoryMax is a separate owner decision,
because the host serves staging. Six runners under the same 16G would add
parallelism for the many short jobs and queue more memory-heavy ones behind
the ceiling.

| runner work per pull request | about 54 runner-min (44 work, 9 turnover) | about 55 runner-min (35 shards, 2 combine, 7 others, 12 turnover); about 53 when check-ts is skipped |
| main runs in a burst of n pushes | n | 2 at most (one running, one pending) |
| Actions cache dependence | uv, pnpm and deid on every job, cache over its 10 GB limit | only where a runner has no verified seed part |

How "after" is computed: CI's whole-suite pytest took 1826 s. Split three
ways, that is 609 s per shard. Each shard adds its collection, the cost of
measuring all nine sources instead of two (about 7 %, from the local runs),
and its reserved work (82 s static on shard 1, 34 s triage on shard 2;
the plan balances it). Setup is about 20 s and turnover about 0.8 min. The
after numbers are measured on this pull request's own runs once the owner's
patch is on it. They are added to this file with that commit, which changes
nothing else.

**The gain, in one line:** the required check's critical path goes from
about 37-51 min to about 13-14 min when runners are free. Queued main runs
collapse to the newest. Under the 16 Oct load, staying under 20 min still
needs runners 4-6 or fewer jobs.
