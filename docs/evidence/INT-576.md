# INT-576: Netgsm OTP adapter parses the live success shape; an unreadable 200 is never retried

**Date:** 28 October 2026 · **Branch:** `int-576-netgsm-otp-response` · **Issue:** #971 ·
**Sec-Row:** files/10 §9 `onboarding` · **Depends on:** INT-528

## What happened

The owner's real OTP send on the synthetic host logged:

```
otp delivery failed (netgsm) refusal=- reason=malformed_response http_status=200 vendor_code=-
```

The SMS from the approved sender "VIVAX AS" arrived on the allow-listed phone after both
tries anyway. So the request, the credentials, the header, Netgsm's IP allow-list and the
sms-egress proxy (ADR-042) all work. Only INT-528's response parsing and success detection
in `services/api/src/intake_api/otp_netgsm.py` was wrong. Its fixtures had been built from
the documentation's sample alone.

**Endpoint.** The adapter calls `POST https://api.netgsm.com.tr/sms/rest/v2/otp` with a JSON
body and HTTP Basic auth. The JS SDK's `sendOtpSms` calls the same endpoint the same way.

- **The Python SDK 1.1.2 has no OTP method.** Its five endpoints are REST v2 `send`,
  `cancel`, `report`, `msgheader` and `inbox`. INT-528 recorded the same finding.
- The documentation's other OTP endpoint is `POST /sms/send/otp`. It takes XML with the
  credentials in the body, and the PHP package sends it as `Content-Type: text/xml`.
- The adapter stays on REST v2. **The wire request is unchanged** (`msgheader`, `msg`, `no`)
  and so is the sms-egress allow-list.

**Content types.**

- Request: `application/json` for REST v2, XML for `/sms/send/otp`.
- Response: neither endpoint documents a content type. The JS SDK parses the body as JSON
  whatever the header says.
- So the adapter decides on the body, never on the header.

**The success shape.**

| who says it | where the job id is |
|---|---|
| the documentation's REST v2 sample | `{"jobid": "17377215342605050417149344", "code": "00", "description": "success"}` |
| the JS SDK, `OtpSmsResponse` | `{code, description, jobId?: string}`, camelCase. The same SDK's REST send type, `RestSmsResponse`, uses `jobid` |
| the JS SDK's integration test against `/sms/rest/v2/otp` | asserts `smsResponse.code === "00"` and `smsResponse.jobId` truthy |
| the documentation, XML OTP endpoint | `<xml><main><code>0</code><jobID>…</jobID></main></xml>`, and the PHP package reads `$donen->main->jobID` |
| plain text `00 <id>` | documented only for the bulk `/sms/send/xml` endpoint, never for OTP |

INT-528 read the job id from `body["jobid"]` alone.

- **Replaying the JS SDK's shape against the INT-528 parser reproduces the owner's log line
  exactly**: `refusal=- reason=malformed_response http_status=200 vendor_code=-` (in the red
  run below).
- That is strong evidence for `jobId`, but it is not proof. A non-JSON body would have logged
  the same line.

**The decision.** The adapter accepts the two shapes Netgsm documents for this endpoint: code
`00` and exactly one digit-string job id under `jobid` or `jobId` (`JOB_ID_KEYS`). It does not
accept these, each a near miss in the tests:

- the XML endpoint's `jobID`;
- a job id given as a JSON number (the 2025 announcement says it is a "string ifade");
- both spellings at once;
- an empty job id.

**Code 00 with no job id is a refusal, `accepted_without_job_id`, and not a success.**

- Every documented success carries a job id: the documentation's sample does, and the JS
  SDK's integration test asserts one.
- The receipt and the audit row (`resource_ref=delivery:<jobid>`) must name the vendor job.
- Code 00 says Netgsm accepted the job, so it is **not retryable**.

**Was the owner's diagnostic needed?** Yes. The documentation (`jobid`) and the SDK
(`jobId`) disagree, and no source is a live capture. So the brief's step 3 applies, and
`netgsm_test_otp.sh --shape` was added (below). The fix does not depend on it: both REST v2
shapes are accepted. If the live answer is a third shape, the same single send now prints
its structure.

- **The body's code decides at any HTTP status.** Every documented code is replayed at 406
  and at 200. The JS SDK's integration test expects 406 for codes 20 and 50.
- **"JSON deeper than the decoder"** used to escape `send()` as a `RecursionError`, which
  would have been a 500 at the route. It is now `unparseable_response`.
- **Transport faults keep INT-528's mapping.**

Every refusal is a closed `StrEnum` value and appears in the metric's outcome label. The
`metrics_catalog.yaml` description now names the three new outcomes.

## No retry: how it is enforced and tested

An answer after which Netgsm may already have sent the code is never sent again. A second
send would put a second code on the patient's phone.

- **The port (`otp.py`).**
  - `DELIVERY_MAY_HAVE_SENT` = {`malformed_response`, `timeout`, `vendor_unavailable`}.
  - `OtpDeliveryError.retryable` is `False` for exactly those reasons. A test pins the truth
    table over every `OtpDeliveryFailure`.
  - A timeout and a vendor-side failure are in the set for the same reason as an unreadable
    200: neither says whether the message left.
- **`OtpAuthService.request_code`** calls `delivery.send` once and has no loop. On any
  `OtpDeliveryError` it answers the generic `503 otp_delivery_unavailable`.
  - `otp_request_gate` starts the 60 s cooldown before the send, so an immediate resend gets
    `429 otp_limited`.
  - Route test, for plain text `00 <id>` and for `00` without a job id: the first request
    answers 503, the second answers 429, and the vendor saw **one** request.
- **The adapter.**
  - One `post` per send and no loop anywhere in its class. An AST test checks it: no
    `while`/`for`, exactly one `.post(` call.
  - Each of the 17 unreadable-2xx scenarios reaches the vendor exactly once and raises an
    error with `retryable is False`. So does a timeout.
- **The transport.** No layer below the adapter retries either:
  - `guarded_async_client` builds a plain `httpx.AsyncHTTPTransport()`, with httpx's default
    `retries=0`, and redirects off.
  - httpcore's retries, when configured, apply only to a failed connection, before any byte
    of the request is written.
- **The owner's check (`otp_send_check`).** It prints `unconfirmed:` (exit 3), never
  `not sent:`, for a non-retryable failure, and says
  `Netgsm may have sent the code, so check the phone before running this again`.
  - On 28 Oct it printed "not sent" while the SMS arrived.
  - A documented refusal (for example code 30) still prints `not sent:` (exit 1).
- **The app.** Read, not changed: `apps/mobile/src/lib/auth/api.ts` (`attestedPost`) repeats
  a request only after an attestation refusal, never on a 503.

## The owner's diagnostic (opt-in, structure only)

`sudo /opt/intake/infra/staging/netgsm_test_otp.sh --shape` is the same one send through the
API's own wiring. After the outcome line it prints one more line, for example:

```
answer shape: content_type=application/json kind=json-object keys=code:string,description:string,jobId:string code=00 length=74
```

- **What it prints** (`intake_api.otp_netgsm_shape.answer_shape`):
  - the `Content-Type` media type without parameters, or `-` / `?`;
  - the kind: `empty`, `json-object`, `json-other`, `markup` or `text`;
  - the top-level JSON keys, each with its value's JSON type, or the markup's tag names, at
    most 12;
  - the vendor's code, only when it is one to three digits;
  - the body length.
- **What it never prints:** the number, the code, the job id or the body.
  - It prints no value at all, only JSON types.
  - A key or tag is printed only when it is letters and underscores, otherwise `?`, so no
    digit string can ride a name.
  - The code is capped at three digits, so it cannot be a six-digit OTP or a phone number.
- **Who runs it:** only the owner. No agent sends. The script was not run by this work, and
  nothing here sent an SMS.
- **Arguments:** anything but no argument, `--last` or `--shape` is refused before anything
  runs.

## Invariant 6 on the new paths

- The PHI tests now also run every unreadable-2xx scenario through the error, its `args`,
  its `vars` and every log record. The INT-528 suite covers the transfer log.
- New hostile answers echo the phone and the code in JSON values, in JSON keys, as the
  `code`, as the job id, in plain text, in an HTML page and in XML tags. Each is checked
  against the error, the log records and the rendered shape.
- The failure log line keeps INT-528's shape exactly (`refusal`, `reason`, `http_status`,
  `vendor_code`), and a test pins it for an unreadable answer.
