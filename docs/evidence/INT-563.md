# INT-563: console four-eyes approval through a WebAuthn step-up the script-free console can complete

**Date:** 28 October 2026 · **Branch:** `int-563-console-step-up` (stacked on #963) · **Issue:** #952 ·
**Sec-Row:** files/10 §9 `admin-console` · **ADR:** ADR-043 · **Depends on:** INT-459, INT-378

## Acceptance (verbatim, GitHub #952)

> From the admin audit, 18 Oct 2026. Every approve button is disabled ('the console cannot mint a WebAuthn assertion yet'): voice controls, CI/CD freeze lift, model lanes. Design the step-up (Keycloak re-auth with max_age=0 / acr, or one nonce'd ceremony script within the CSP), approver must differ in subject/key/session, self-approval refused and counted; ADR if the CSP changes.

The orchestrator approved the design and set five constraints. Each is met below:

1. The staging host gets the new public client `admin-web-stepup` and its mappers through the
   deploy path, idempotently, the way `staff_flow.py` works. No flow or execution is ever `PUT`.
2. Confirm from the Keycloak source which mapper emits `amr` for the INT-378 provider, and say in
   the ADR what is verified.
3. Fail closed: an unreachable JWKS, a reused code, an unknown state, an expired ceremony or a
   sub/sid mismatch is refused with no fallback. The old `assertion_id` path is deleted, with a
   near-miss test that the old unused-string approval is now refused.
4. Every new metric is catalogued. The grant and its use are audited in the hash-chained log by
   ids only.
5. The threat/control mapping is in this file, for the security-reviewer pass.

## What was wrong (the red run)

Before this change, on the base commit 3533999d, an approval carrying a string nobody had ever
issued was accepted. The probe opened a break-glass request as `clinical_lead` and approved it as
`qms_owner` with `{"assertion_id": "assert-fresh-1"}`:

```
open: 200
approve with an unused string: 200 approved
POST /admin/step-up: 404
```

`FourEyesService.approve` checked only that the string was non-empty and unspent. The approver
block carried the console session's login credential, so four-eyes' "different credential"

## The design (ADR-043)

**The API runs the ceremony.**

- `POST /admin/step-up {action_id}`:
  - refuses an approval that could never pass:
    - unknown action (404);
    - decided or expired action (409);
    - no approver role for this action (409 `four_eyes_approver_role`);
    - the requester, in any tab (409 `four_eyes_self_approval`, counted on
      `admin_four_eyes_self_approval_attempt_total`);
  - otherwise opens a two-minute ceremony bound to the caller's `sub`, Keycloak `sid` and that
    one action;
  - answers the authorization URL for `admin-web-stepup`, with `state`, `nonce`, PKCE S256,
    `prompt=login` and `max_age=0`. The verifier never leaves the API.
- `POST /admin/step-up/complete {state, code}`:
  - pops the ceremony, so a state is never tried twice;
  - checks it belongs to this caller;
  - redeems the code with the verifier at the internal token endpoint;
  - verifies the ID token;
  - issues a one-time grant `sug_<128-bit hex>` for that caller and action, valid two minutes.
- Every approve and countersign route — break-glass, the three voice approvals, the freeze lift,
  the three model-lane approvals, the access-review countersign — calls one function,
  `stepped_up_approver`:
  - it spends the grant named by `step_up_grant` and writes `admin.four_eyes.step_up.redeemed`
    ahead of the approval;
  - it returns the caller's actor block carrying the **credential and AAGUID just asserted**;
  - four-eyes spends `stepup:<sha256(jti)[:32]>`;
  - there is no other path.

**The console has no script.**

- **Onayla** on each pending row (voice, CI/CD, model lanes) posts `{action_id, from}` to
  `/step-up/start`. That route:
  - refuses a cross-site post;
  - asks the API;
  - follows the answer only if it is the configured Keycloak origin's
    `/realms/<realm>/protocol/openid-connect/auth` for `admin-web-stepup`, with `prompt=login`,
    `max_age=0`, S256 and a state-shaped `state`.
- `/step-up/callback` relays `{state, code}`, then presents the grant on the action's own approve
  route from a closed table keyed by the `DangerousAction` id. It lands on the action's page with
  `?step_up=<code>`.
- `/step-up?action_id=` serves break-glass and the access-review countersign, which have no
  module page.

**What `amr` proves — constraint 2, from Keycloak source** (26.1.4, the dev pin, and 26.7.4, the
staging pin; both read on 28 Oct 2026):

- `AmrProtocolMapper.getAmr` parses the user session's `AUTHENTICATORS_COMPLETED` note.
  `AmrUtils.getAuthenticationExecutionReferences` then emits each execution's
  `default.reference.value` while `authTime + default.reference.maxAge >= now` (`isAmrValid`).
  The realm's `amr hwk` config (maxAge 28800) is on the REQUIRED
  `intake-webauthn-session-notes` execution, so `oidc-amr-mapper` reliably emits `hwk`. It
  emits it for eight hours, so it is **not** freshness evidence.
- `AuthenticationManager` (26.7.4 line 982ff) sets the session's `AUTH_TIME` to now on every
  authentication where `isSSOAuthentication` is false. `prompt=login` makes the step-up one.
- `TokenManager.generateIDToken` (26.7.4 line 1316ff) sets `typ=ID`, `aud` = the client,
  `azp`, `nonce` and `sid`.
- **Chosen and stated in the ADR:** verify `hwk` in `amr` **and** `auth_time` no earlier than
  the ceremony's start less 30 s. The `credential_id`/`aaguid` notes identify the key; they are
  not the freshness evidence.
- The residual risk is stated in the ADR. Freshness of the WebAuthn step itself depends on the
  staff flow keeping it REQUIRED, which `staff_flow check` holds on every deploy and smoke.

**The realm client — constraint 1.**

- Both realm files declare `admin-web-stepup`:
  - public, standard flow only, PKCE S256;
  - the console callback as the one redirect URI, no web origins;
  - mappers `aaguid` and `credential_id` (user-session note) and `amr` (`oidc-amr-mapper`), all
    in the ID token only, never the access token.
- `infra/staging/keycloak/step_up_client.py`:
  - adds the client with one `POST /clients` when it is absent;
  - verifies it field by field and mapper by mapper when it is present;
  - refuses a drifted client by naming the field, and changes nothing;
  - never reads or writes a flow or an execution. Its only verbs are `GET` and `POST`, and a
    test holds that.
- `deploy.sh` runs `ensure_step_up_client` after `ensure_staff_webauthn_notes` and before
  `mirror_keycloak_jwks`. `smoke.sh` runs `step_up_client check`. The password travels on stdin,
  as for `staff_flow`.
- The API gets `INTAKE_ADMIN_STEP_UP_REDIRECT_URI` and `INTAKE_ADMIN_STEP_UP_EXCHANGE_URL`. The
  console gets `INTAKE_ADMIN_STEP_UP_ORIGIN`.

**The CSP — the ADR the issue asks for.** `form-action` becomes `'self' https://auth.<host>`.
Browsers hold a form's redirects to `form-action`, and the **Onayla** form continues to Keycloak.
Nothing else changes: still nonce-based, no `unsafe-*`. With no origin configured it stays
`'self'`. `buildCsp` refuses anything that is not a bare origin.

## Threat × control mapping (files/10 §9 `admin-console`, for the security review)

The row names **"forgeable four-eyes"** among the console's threats. Its controls include
"four-eyes as a server-side pending-action protocol with distinct AAGUID/credential id" and
"nonce CSP with no `unsafe-*`". Its signals include "**self-approval attempts**".

| threat | control (where) | signal | test |
|---|---|---|---|
| Approval with a string nobody issued (the pre-INT-563 hole) | only a live grant redeems (`stepped_up_approver`); closed bodies refuse `assertion_id` (422) | `admin_step_up_total{stage="redeem",outcome="step_up_unknown"}` | `TestTheOldPathIsGone` (old field 422, same string in new field 403, both fields 422; action stays pending); `test_an_unused_string_is_not_a_grant` |
| Stolen console bearer approves | the grant needs a fresh password + passkey login at Keycloak; the code is useless without the API-held PKCE verifier | `step_up_exchange_failed`, `step_up_token_refused` | `test_a_refused_code_exchange_refuses_the_step_up`; `RecordedKeycloak.exchange` checks S256 |
| Remembered login / "remember this device" passes as a second key | `prompt=login`, `max_age=0`; `auth_time` ≥ ceremony start − 30 s | `step_up_not_fresh` | near misses at −3600 s, −31 s and a missing `auth_time`; −30 s passes |
| Re-authentication without the WebAuthn step | `hwk` required in `amr`; the staff flow's WebAuthn REQUIRED (`staff_flow check` on deploy and smoke) | `step_up_without_webauthn` | `amr` = `pwd`, `pwd otp` and empty, each refused |
| Token substitution: another account, session or ceremony; an access token; another client | `sub` and `sid` = the ceremony's; `nonce`; `typ=ID`; `azp`/`aud` = `admin-web-stepup`; issuer; RS256 over the mirrored key set | `step_up_token_refused` | one near miss per claim; a tampered signature; an expired token |
| Replay of an ID token, code, state or grant | `jti` spent until the token's expiry; state popped on first try; grant single use; ceremony and grant TTL 2 min | `step_up_replayed`, `step_up_unknown` | `test_one_id_token_is_spent_once`, `test_the_state_is_spent_on_the_first_try_whatever_follows`, `TestAGrantIsBound::test_it_is_spent_once`, the TTL tests |
| A grant used for another action, or by another caller (CSRF, leak) | grant bound to `sub` + `sid` + `action_id`; a foreign presentation is refused and does not burn it | `step_up_unknown` | `TestAGrantIsBound::test_to_its_action`, `test_to_its_caller`; `test_a_foreign_presentation_is_refused_and_burns_nothing` |
| Login CSRF on the callback (the attacker's code in the victim's browser) | `/complete` matches the ceremony's `sub`/`sid` to the caller's bearer | `step_up_unknown` | `TestComplete::test_another_callers_ceremony_is_unknown_to_them` |
| Self-approval, including a second tab | refused at `/admin/step-up` (and again at approve) | `admin_four_eyes_self_approval_attempt_total` | `test_the_requester_is_refused_and_counted`, `test_the_requester_in_a_second_tab_is_the_requester` |
| Same key or session as the requester | the approver block carries the credential just asserted, so `_check_distinct` compares the key used *now* | `four_eyes_shared_credential` / `_session` | `test_the_second_key_is_the_one_just_asserted`; existing `test_four_eyes.py` |
| Open redirect via the start route | the authorization URL is followed only on the configured origin and endpoint, with the ADR-043 parameters | `api_refused` (console) | `e2e/step-up.spec.ts` "does not follow an authorization URL…" (10 near misses) |
| Approval POSTed to an attacker-chosen API path | the approve route comes from a closed table keyed by the `DangerousAction` id; ids and grants are shape-checked | `action_unknown` (console) | `e2e/step-up.spec.ts` "…is refused before anything is approved"; `__proto__`/`constructor` |
| CSP weakened | one origin added to `form-action` only, validated as a bare origin; no `unsafe-*` | smoke: CSP with no `unsafe-*` | `e2e/step-up.spec.ts` CSP tests; `e2e/ops.spec.ts` |
| A deploy breaks the staff flow (e19640d2) | `step_up_client.py` never names a flow or an execution; `GET`/`POST` only | deploy stops on drift | `TestItNeverTouchesAFlow`, `TestRun`, `TestNearMisses` |
| A drifted or widened live client (wildcard redirect, web origins, mapper in the access token) | verified on every deploy and smoke; drift refused, never edited | smoke fail | `TestNearMisses` (14 cases + an extra mapper) |
| PHI or credential in logs or audit (invariant 6) | audit rows name `four_eyes:<action>:stepup:<hash>`; no grant id, no credential id; refusals are codes | — | `test_grant_and_use_are_on_the_chain_by_ids_only` (both credentials and the grant absent; chain verifies) |
| Restart drops state | process-local, like `FourEyesService`: a restart refuses rather than grants | — | by construction |

## Audit and metrics (constraint 4)

- `admin.four_eyes.step_up.granted` is written when a grant is issued.
- `admin.four_eyes.step_up.redeemed` is written ahead of the approval it enables. The test
  asserts its `seq` is below the approve route's `.success` row.
- Both are `actor` = subject and `resource_ref` = `four_eyes:<action_id>:stepup:<32 hex>`, with
  consent scope `basis:KVKK-12`. The `AdminActionRecord` intent/outcome rows wrap both routes, as
  for every console route.
- `admin_step_up_total{stage,outcome}` (`admin.step_up_total`) is catalogued in
  `observability/metrics_catalog.yaml`.
  - Stages: `begin`, `complete`, `redeem`.
  - Outcomes: `ok`, or a closed refusal code.
  - It is the alert metric of the new tier-1 SAFE action `admin.four_eyes.step_up`, whose
    runbook is `docs/runbooks/four-eyes-step-up.md`.
  - Its actors are exactly the roles that reach an approve or countersign route, derived from the
    route table in the test.
