The orchestrator's brief adds: reuse the voice runtime's RedNotification / Safety-inbox path rather
than a parallel mechanism; new metrics catalogued; and the RED path touches no media transport and
never waits on the network before the RED shows (invariant 21; MOTION-4 "RED paints first"), so the
location POST is fire-and-forget with retry and the screen never depends on its response.

## Why

The ON_SITE RED copy says "Görevlilere haber verildi.". files/02 §5.3 Axis 3 and files/04 §8.1
rule 7 make the clinic notification the **primary** channel under ON_SITE, fired automatically,
regardless of connector presence. Before this issue only the voice runtime's RED reached the clinic
Safety inbox (INT-406). The API triage hop answered the trigger and told nobody, its request named
no session or visit, and the patient's answer to "Şu anda hastanede misiniz?" never left the
device on any lane.

## Change

**One path, not two.** Everything goes through INT-406's Safety inbox: an `InboxEntry` put in a
process `SafetyInboxOutbox` (an append under a lock, nothing awaited) and pumped into the shared
Redis store the console reads. The voice runtime reaches that path through its
`RedNotification` port (`SafetyInboxNotifier`); the API does not import that class, because it
lives in the Talker package (`intake_voice_runtime.talker.red_path`) the API does not depend on.
The API writes the same entries the port writes, with the same constructors, into the same kind
of outbox and the same store.

- `intake_platform.safety_inbox`
  - `EntryKind.RED_ON_SITE` (`red_on_site`) and `InboxEntry.for_on_site`: the staff notification.
    It names the RED by its `work_id`, so there is one per RED; it has its own clock; it carries
    no register; it does not index the visit (files/02 §2b reads a visit's REDs, and this is not
    one). `ID_SHAPE` and `RULE_ID_SHAPE` are public so a route refuses what the entry would.
  - `clinic_red_notification_unaudited_total` (new, catalogued): an audit row the API owed for a
    RED's clinic route that could not be appended.
- `intake_voice_runtime.safety_inbox.SafetyInboxNotifier`: a RED determined at ON_SITE also puts
  the `red_on_site` entry, in the same put, for every register. The DSL requires
  `notify_staff_immediate: true` on every KIRMIZI rule's ON_SITE action (`protocols.dsl`), so no
  RED's on-site action spares staff.
- `services/api`
  - `POST /v1/triage/evaluate` takes `session_id` and `visit_id` (id-shaped). On the device a
    visit is a session row (INT-197), so the app sends the visit id for both; the voice lane's
    session id is already the visit's uuid. They are optional only so an app build from before
    INT-475 still gets its RED (a 422 would read as "unevaluated" and lose it): with no ids the
    route cannot name the RED, which is counted and audited as unrouted.
  - **How an id is kept** (`red_notify.stored_ref`, invariant 14). A canonical UUID is one the
    server minted (a visit row, a voice session), so it is kept as it is and files/02 §2b still
    finds the visit's REDs by it. Any other id is kept only as its keyed pseudonym
    (`px:` + `Tokenizer.pseudonym` of the id's hex): a synced hospital visit's id
    (`acb-<patient number>-<date>-<time>`, INT-318) carries the hospital's patient number. With no
    tokenization key, a non-UUID id is not kept at all: the RED is unrouted, never stored raw.
  - `red_notify.raise_red` (the RED branch): the `red` entry (tenant from the principal, session,
    visit, work id, the fired rule ids, the register) and at ON_SITE the `red_on_site` entry, put
    **before** the answer is returned and never waited on. The work id is
    `w_` + sha256("red", tenant, session, visit, winning rule)[:32] over the kept ids, so a
    re-sent request, a re-derived RED (more answers, another location) and the later location
    answer all land on one entry. GREEN and YELLOW raise nothing. A route that cannot put (no inbox
    wired, a refusal, or no id it may keep) is counted on `clinic_red_inbox_route_failures_total`
    (`RedInboxRouteFailed` pages) and owes an `api.triage.red_unrouted` audit row naming
    `visit:<kept id>/red:<work id>` (or `visit:unidentified/red:<rule id>`), so the on-call can
    find it; it never costs the RED.
  - The hop's audit rows (`api.triage.red_notified`, `api.triage.red_on_site_notified`,
    `api.triage.red_unrouted`) are written in a background task **after** the answer is sent; a
    failed append is counted, never raised.
  - `POST /v1/triage/red-location` (new): `{session_id, visit_id, rule_id, location}` with
    `location` ON_SITE or REMOTE only, `extra="forbid"`, patient-only (`require_patient`), under
    the core consent scope. `rule_id` must be a KIRMIZI rule of the served set (an in-memory check;
    otherwise 422 `rule_not_served`, and with no served set 503 `triage_unconfigured`), so only a
    RED the device could have been shown can be answered. ON_SITE puts the `red_on_site` entry
    (same id policy, same work id derivation)
    and audits `api.triage.red_location.on_site` by `safety_inbox:<tenant>:<entry id>`; REMOTE
    puts nothing and audits `api.triage.red_location.remote` by `visit:<id>/red:<work id>`.
    Answer `202 {"kind": "red_location", "staffNotified": bool}`. An unwired inbox or an id it may
    not keep under ON_SITE (`safety_inbox_unconfigured`, `safety_inbox_unidentified`), or an audit
    append that fails, is a 503 the device retries; the retry lands on the same entry.
  - `SafetyInboxOutbox` (INT-406's, hardened here): an entry a flush has taken but not yet written
    still counts in `pending`, in the age that pages and in `wait_until_empty`; and a store fault
    other than `SafetyInboxUnavailable` now keeps the entry and the pump alive (it used to end the
    pump thread and drop the batch it had taken, with nothing paging).
  - `ApiState.red_outbox`, wired exactly when the inbox is, and a pump thread in the app lifespan
    (`_RedPump`), stopped after one last pass; what is still unwritten at stop is counted, never
    named.
- `apps/mobile`
  - `lib/red/hop.ts`: `RedOrigin {sessionId, visitId}`; `triageRequest(…, origin)` sends
    `session_id`/`visit_id`.
  - `lib/red/store.ts`: `RedState.origin`; `present(trigger, catalog, origin, elapsedMs?)`. The hop
    passes `{sessionId: visitId, visitId}`; the voice session passes its `sessionId` for both.
  - `lib/red/locationReport.ts` (new): `locationReportFor(state)` is the patient's own answer only
    ("evet" → ON_SITE, "hayır" → REMOTE; the no-answer wait's expiry is not posted);
    `createLocationReporter` posts it once, fire-and-forget, retrying with the reconnect policy's
    capped full-jitter backoff on a network error, a request that hangs past
    `LOCATION_REPORT_TIMEOUT_MS` (10 s), a 5xx, 408 or 429, at most
    `LOCATION_REPORT_MAX_ATTEMPTS` (20); both are engineering bounds, not clinical values. A 2xx
    or any other 4xx stops it.
  - `components/RedLayer.tsx`: `useLocationReports()` subscribes the reporter to the one RED store,
    once. Nothing the layer renders reads the report's result.
- Ops and docs: `infra/staging/compose.yaml` hands the API `INTAKE_SAFETY_INBOX_REDIS_URL` (the
  Redis it already uses), so the synthetic host's hop REDs reach the inbox after the next deploy
  (no deploy in this PR); the alert description, the runbook (`docs/runbooks/red-acknowledgement.md`)
  and the metrics catalogue name the API's route; `docs/security/threat-model.md` clinical-core
  row records the new records, the controls and one residual.
- Retired (acceptance 3): `requires_bool`, `test_the_tripwire_reads_the_grammar` and
  `test_tripwire_no_served_red_rule_can_fire_through_the_hop`. They existed only so that the
  ON_SITE copy could stand while the hop told nobody; the hop now tells the clinic, so they guard
  nothing. `test_tripwire_the_hop_refuses_a_json_boolean_answer` is not deleted: the 422 is still
  the hop's real contract and still the evidence for INT-465 **finding 1** (the hop carries
  strings, so the served cardiac rule cannot fire through it yet), which stays open. It is renamed
  `test_the_hop_carries_strings_only_so_the_served_cardiac_rule_cannot_fire_yet`, its docstring no

## Findings, reported and not built around

1. **The location answer is checked against the served set, not against a raised RED.** The
   route refuses a rule that is not a KIRMIZI rule of the served set, but it does not read the
   store to prove this RED was raised, because the hop's own entry may still be in an outbox (or
   another replica's) when the answer arrives. A patient can therefore file an on-site entry for a
   served RED rule against a session or visit id of their choosing, in their own tenant, under
   their own audited account — the same reach the hop already gives anyone who answers its
   questions. The outcome is an extra alert, never a missing one. Recorded in the threat model;
   a per-patient bound is not set here, because how many REDs one patient may legitimately raise
   is a clinical question.
2. **A voice-lane RED and its answer carry different work ids.** The runtime keys its RED entry by
   its Work-queue id, which the device never sees, so an on-site answer to a voice-lane RED names
   the same session, visit and rule under the derived id. Still one notification per RED; the
   console pairs them by visit and rule. This lane is not yet wired in the app
   (`createLiveVoiceSession` has no caller), and its pack rules outside the API's served set are
   refused by the answer route (`rule_not_served`): when the voice lane is wired, its on-site
   answer for such a rule is not notified, though its RED entry is. The issue that wires the lane
   owns that.
3. **Reports do not survive an app restart.** The reporter's de-duplication and retry live in
   memory; an answer whose delivery is still retrying when the app is killed is lost. The screen
   and the patient's action are unaffected.
4. **A synced hospital visit's notification names a pseudonym.** The console shows the keyed
   pseudonym of an `acb-…` visit id, never the patient number in it (invariant 14), and nothing
   in the console resolves it back to an appointment yet. Staff still see an on-site RED in their
   tenant, with its rule and its clock. A resolver belongs to the console (INT-406's surface).
5. **The device reports no give-up.** When the location answer's delivery gives up, or meets a
   401/403, nothing is counted on the device; the server-side counters see only what arrives.
6. **No deploy in this PR.** The synthetic host gets `INTAKE_SAFETY_INBOX_REDIS_URL` on its next
   deploy. Until then its hop REDs page `RedInboxRouteFailed` and are on the chain as
   `api.triage.red_unrouted`.
