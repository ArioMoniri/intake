# Evidence: INT-515 · Voice runtime and a LiveKit SFU on the synthetic host

GitHub #877, from the INT-498 feature audit (docs/evidence/INT-498.md §5 P7).
Branch `int-515-voice-runtime-on-host`, from `origin/main` at `be6c09c1`.
Sec-Row: `voice-runtime`. Nothing was deployed: the merge queue deploys.

## Problem

`services/voice-runtime` was built and deployed nowhere, so no voice turn,
extraction job or RED data-channel trigger could happen on the synthetic host
(F04, F06, F10, F27). The issue asks for the runtime and a pinned LiveKit SFU,
with TURN on 443/TLS, in the staging compose. It also asks for a room-token
route behind the patient's DPoP session, catalogued metrics, the four health
endpoints, an SLO file and a synthetic probe (invariant 15), and for raw audio
never to be written (invariant 3). Its tests are the compose services set, a
probe that completes a scripted synthetic turn, and a RED trigger that arrives
over the data channel with the media track torn down.

## Decisions

1. **TURN over TLS on 443 through the existing Caddy.** The security group
   admits TCP 80/443 only (docs/runbooks/staging.md step 1), and only Caddy
   publishes ports. Caddy gets the layer-4 module (caddy-l4 v0.1.2, whose
   go.mod requires exactly Caddy v2.11.4) as a listener wrapper on `:443`:
   - SNI `turn.<host>` has its TLS terminated with that name's own certificate
     (HTTP-01; TLS-ALPN disabled for it). The plain TURN stream goes to the
     SFU's `tls_port` with a PROXY v2 header, which only Caddy's fixed address
     may send.
   - Every other name falls through to the HTTP server's TLS unchanged.
   - LiveKit advertises `turns:<domain>:443?transport=tcp` itself (read in
     `pkg/service/roommanager.go` at v1.13.10).
   - UDP TURN, ICE-over-TCP and any published media port are off.
2. **LiveKit v1.13.10**, not the dev tier's v1.13.6, for #4992: "turn: refuse
   TCP relays and limit relays to this host to media ports". A public TURN
   needs that relay policy. The SFU's private address is the one restricted
   peer allowed, so the media network has a fixed subnet (`10.47.115.0/24`;
   SFU `.10`, Caddy `.20`).
3. **The RED trigger goes through the SFU's server API.** `RoomService.SendData`
   sends one RELIABLE packet to the patient's identity. Neither participant
   token gains `canPublishData`: INT-090's grant is unchanged. The agent's
   peer connection is not on the RED path, so the trigger still arrives when
   the agent's media is gone. `RoomMediaTeardown` mutes every audio track the
   agent publishes before the trigger is sent. The server credential is a new
   `mint_room_admin_token`: `roomAdmin` on one room, 60 s, never leaves the
   process.
4. **The ack is the device's.** `RedDataChannel.publish` resolves when the
   script has started on the device (INT-093's contract). The adapter takes a
   `RedStartAcks` port for that stamp and never invents one. Nothing in
   production feeds that port yet. The RED path stays unwired in the
   composition root (HB-C1), so this changes nothing a session can reach.
   The device-to-server ack route belongs with the RED in the app (INT-446).
   Its implementation of the port owns the bound on how long a stamp may
   take; the clinic has already been told by then (INT-093's ordering).
5. **Process hardening is reported, not assumed.** `serve.app_from_env` sets
   `RLIMIT_CORE=(0,0)`, `PR_SET_DUMPABLE=0` and `mlockall(MCL_CURRENT|MCL_FUTURE)`
   before it binds anything. Compose gives the container `memlock: -1` and no
   capability. `core_dumps_off` and `memory_locked` are readiness checks; a
   typed worker holds no audio, so only the first binds it.
6. **The synthetic turn is a real loop on whatever lanes are bound.** It runs
   agent speech, the synthetic patient's speech, transcription, then extraction
   of one synthetic boolean slot, through the production boundary, schema and
   parser. In CI it runs against recorded fixtures; on the host, against the
   deployment's lanes, at most one turn per 30 s. The report is ids and timings.
7. **The SFU logs at `warn`.** Its info-level join lines carry the client's
   network details (invariant 6).
8. **`turn-detector`.** The registry's voice-runtime row said "livekit/
   turn-detector … knowingly adopted"; files/00_STATE.md §3 records it as OUT,
   and 00 wins. The row now states what the image carries: no LiveKit Agents
   SDK and no turn-detector weights.

## Not done here, and why

- **No deploy.** The merge queue deploys. On the first deploy the operator
  re-runs `./init.sh` once, which generates `LIVEKIT_API_KEY` and
  `LIVEKIT_API_SECRET`. `deploy.sh` stops at `load_env` until that is done.
- **The hosted lanes.** After #751 merges, the lane checks report the
  registry's own reasons. The runtime then needs three more things:
  - the synthetic data class baked into its image;
  - the `intake_hosted_lanes` package in its image;
  - a read-only OpenBao token for the provider keys.

  These follow #751's API image change and are a follow-up to it. Until then
  the registry reports `hosted_not_in_deployment` or
  `hosted_key_store_unconfigured`, never a guessed route.
- **The egress route.** `owner-515-egress.patch` puts the runtime on #774's
  `outbound` leg with `INTAKE_EGRESS_PROXY_URL`. It also updates the tests
  that pin who reaches the proxy. It was checked with `git apply --check`
  against this branch, and with `patch --dry-run` against #774's
  `tests/infra/test_staging_egress.py`.
- **The device's RED start stamp** (`RedStartAcks`) has no production
  implementation, and the RED path stays unwired (HB-C1).
