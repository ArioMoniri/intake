# Evidence — INT-355 · Gated questions are never asked: resolve bare `ask_if` slot names

Branch: `int-355-bare-gate-resolution`, cut from `origin/main` at `6dd1f2a4`.
Sec-Row: `triage`.

## 1. The defect

The engine keys every step `<section>.<slot>` and `_lookup` reads a gate atom
exactly as written. A pack may name a gate slot bare —
`protocols.types.SLOT_REF_PATTERN` documents both forms as legal — and the
packs do: `base.intake` writes `subject_role != 'kendim'` (on
`identity_check.proxy_reported`) and `pregnancy_status != 'hayir'` (on
`pmh_fh_sh.lmp_date`), and every specialty/cluster candidate on the review
branch writes `<slot> == true`. A bare atom looked up a key no step carries,
so it evaluated `UNKNOWN` for the whole session. files/13 §9.5 opens a gate
only on `TRUE`, so the dependent question was dropped without any error.

A verifier reproduced it with a real `IntakeEngine`. After "yes" to the gate
slot, the gated question never appeared. With `sorular.<slot>` it did.

The FHIR emitter had a second, quieter form of the same fault. It mapped bare
keys to linkIds with a dict `update`. When two sections held the same key, the
last one written won, and `enableWhen` pointed at whichever slot that was.

## 2. The rule (one module, applied everywhere a gate is read)

`packages/protocols/src/protocols/gates.py` — `SlotNamespace` + `qualify_gate`:

- a qualified name resolves to itself when that slot exists;
- a bare name resolves to the one slot of that name across every section of
  the resolved chain (base + cluster + specialty + overlays);
- a bare name that two or more sections hold is `AMBIGUOUS`, and a name that no
  section holds is `UNKNOWN`. Both are refused.

The rewrite runs on the parsed tree, so a string literal that spells a slot
name is never renamed. Triage is untouched: red-flag `when` predicates and
`tense_anchor` are read by the rules engine through its own reference set,
and no triage module changed (invariant 1).

Where it is applied:

| Reader | Change |
|---|---|
| Compiler — `compile/resolve.py` `_gate_ref_refusals` | new refusals `GATE_REF_AMBIGUOUS`, `GATE_REF_UNKNOWN` (subject = the gated slot's linkId; the message names every candidate) |
| FHIR emitter — `compile/emit_fhir.py` | `enableWhen.question` is the resolved qualified linkId; an ambiguous or unknown atom is `GATE_NOT_PROJECTABLE` and never picks the last holder |
| Voice runtime — `clinical_agent/plan.py` `build_plan` | every gate is rewritten to step ids at build; ambiguous or unknown raises `PlanError`. `fsm.py` `_lookup` therefore only ever sees step ids (docstring updated) |
| Typed lane — `typed/affordance.py` | no change needed: it renders the engine's frontier and cannot reach `ask_if` (its own docstring) |
| Mobile — `apps/mobile/src/lib/intake/questions.ts` `askIfMet` | no change needed: it does not read DSL gate strings. Its `AskIf {questionId, includesAny}` gates on a flat question-id namespace. Existing vitest pins that namespace as unique (`allQuestions … contains every pack question exactly once`) and requires every gate to name a real question (`every gate names a real question, a real option of it, and never itself`). The ambiguity and unknown cases cannot be represented there |

The engine applies the rule a second time at plan build, for any document
that did not come through the compiler (hand-built, or an older bundle). That
is how the verifier's reproduction reached the defect.

## 5. Tests and their near-miss controls

- Specialty-style bare gate, spelled `belirti_var == true` and as the bare
  atom `belirti_var`: opens on `true`, stays closed on `false` and while
  unanswered. The qualified spelling runs through the same three cases as
  the control.
- Cross-section: a bare gate in `sorular` reads a slot `ziyaret` owns (the
  specialty-gates-on-base shape).
- A bare `skip_if` retires its step. A bare `skip_if` closing behind an
  asked-ahead step invalidates it and discards the late answer (files/13
  §11.3).
- A closed bare gate discharges a must-ask obligation. Before the fix it
  stayed `obliged` forever (files/13 §9.4).
- `base.intake`: `proxy_reported` opens when `subject_role` is anything but
  `kendim` and stays closed on `kendim` and while unanswered. `lmp_date` opens
  on `evet` and `emin_degilim` and stays closed on `hayir` and while
  unanswered. The engine runs over the authored sections directly, because
  the compiler refuses this L0 pack by design (HB-C1). Nothing is promoted or
  stripped to get round that.
- Ambiguous bare name: refused at compile (`GATE_REF_AMBIGUOUS`, for both
  `ask_if` and `skip_if`) and at plan build. **Near-miss control:** the same
  chain with the same duplicated key compiles and runs once the gate is
  qualified.
- Unknown name (bare, wrong section, missing key, three-part): refused at
  compile (`GATE_REF_UNKNOWN`) and at plan build. Every bad gate is reported,
  not only the first.
- FHIR: a bare gate on a parent-pack slot projects the qualified linkId, for
  `ask_if` and for `skip_if` (inverted). An emitter given a hand-built
  document with an ambiguous name refuses it, whether the name stands alone
  or sits in a conjunction.

## 6. The review-branch candidates under the new rule

This is a measurement, not a gate. Every gate on `origin/merge-305` was
resolved over its merged chain. That covers `packages/protocols/base` and
`packages/protocols/review/{cluster,specialty}`: 100 packs and 183 gates. All
183 resolve to exactly one slot, with none ambiguous and none unknown. On
`main` every one of them was a gate that could never open.
