## The word this change refuses

The issue title says "anonymisation (KSVY-16)". KSVY m.16 was read rather than assumed, and
it has **two limbs**:

| limb | text | what it permits |
|---|---|---|
| m.16(1) | *"Kanunun 28 inci maddesinin birinci fıkrasının (b) bendi kapsamında veri sorumlusu tarafından **anonim hâle getirilen** kişisel sağlık verileri ile bilimsel çalışma yapılabilir."* | scientific work on data the controller has **anonymised** |
| m.16(2) | *"…(c) bendi kapsamında kişisel sağlık verileri, ilgili kişilerin özel hayatın gizliliğini veya kişilik haklarını ihlâl etmemek ya da suç teşkil etmemek kaydıyla alınacak teknik ve idari tedbirler çerçevesinde, bilimsel amaçlarla işlenebilir."* | scientific-purpose processing under the KVKK m.28/1(c) exemption |

Also checked, because files/06 §78 warns that anything resting on the 2019 wording needs
re-reading: **the RG 33096 amendment of 03.12.2025 does not touch m.16.** Its thirteen
maddes reach articles 1, 3, 4, 5, 6, 7, 8, 9, 10 (repealed outright), 11, 13 and 21. m.16 is
named in none of them, so the 2019 text stands.

**What this pipeline produces is not m.16(1)'s artefact.** The subject key is
`Tokenizer.pseudonym("research:<study_id>:<patient_id>")` — a keyed HMAC. Whoever holds the
tokenization key can re-derive it from a patient id, which makes it personal data under KVKK
and makes "anonymised" false. So:

- the type is `PseudonymisedExtract`, the row is `PseudonymisedRow`, and
  `test_the_package_never_names_anything_anonymised` asserts no name in `__all__` contains
  `anonym` and that the package docstring carries the denial in words;
- `PseudonymisedExtract.provenance` — the sentence a methods section would copy — ends
  *"Pseudonymised, NOT anonymised: the subject key is a keyed derivation and remains personal
  data under KVKK"*, pinned by a test;
- the lawful route taken is the **other** one files/06 §75 states in the same sentence:
  *"All research consented (`research`) or anonymised per KSVY-16; ethics IDs recorded on
  every export"*. Consent **and** a recorded ethics id, both enforced.

Whether that consent route is available at all under m.16, or whether m.28 displaces açık
rıza here, is a counsel question and is asserted nowhere in the code — **HB-L21**.

## What "validated on corpus" means, stated narrowly

The INT-015 corpus validates an **exclusion rule**, not a scrubber. Three tests drive it:

| test | what it proves |
|---|---|
| `test_no_corpus_sentence_can_become_an_export_value` | every sentence in both corpora (authored + vendored) is refused as an export value: the *carrier* is refused, before any question of content |
| `test_no_bare_corpus_identifier_can_become_an_export_value` | **the sharp one.** Every TCKN, mobile number, IBAN, email and date in the corpora is refused — and a TCKN like `TCKN-XXXXXXXXXXX` is *id-shaped*, so a shape rule on its own would have admitted every one of them |
| `test_a_scrubbed_corpus_sentence_is_still_refused` | scrubbing is not a route in: `[PERSON] ile 0532…` is still a sentence, and this pipeline admits declared vocabulary members only |

The order of the two checks in `check_export_value` is the point: **the de-identifier adds
refusals, it never licenses an acceptance.** Acceptance comes from the spec's closed
per-dimension vocabulary. That matters because the pattern tier alone leaves a hole a test
demonstrates directly — `test_a_value_outside_the_declared_vocabulary_is_refused` feeds
`"Ahmet"`, which is ASCII, short, id-shaped and carries no pattern identifier, and it is
refused because it is not a declared member of `profile`. Without the vocabulary that value
would have shipped.

Narrative is **excluded, not scrubbed**, for the reason INT-171 already recorded: files/10 §3
on realistic Turkish NER recall, and HB-L6 on the claim itself ("one Turkish NLP cannot
support"). No transcript, note, slot value or document is reachable from this package —
`test_the_research_package_reads_no_narrative_relation` asserts the sources import no
narrative model and build no query at all.

## The six gates, and why each one is where it is

1. **`k` below the floor** → `ThresholdBelowFloor`, raised before anything is read: an
   under-floor request is a programming error, not a statement about this cohort.
2. **The study resolves on the date being asked about.** `resolve(study_id, *, on=...)` has
   no default for `on` — an approval window is only meaningful against a date, and a default
   would let a caller ask without saying when.
   `test_an_approval_that_has_lapsed_refuses_with_no_grace` serves on the last valid day and
   refuses the next.
3. **The recipient is on the study's closed list.**
4. **`research_extracts` carries a stated retention.** Creating data whose destruction date
   nobody can state is the KVKK m.7 / DEST-2017 failure, so the gate refuses.
   `test_the_shipped_retention_policy_refuses_a_research_extract` runs against the real
   committed policy.
5. **Row shape, vocabulary and measures** — checked over **every** candidate, before the
   consent filter. Deliberate: a free-text value must not be quietly carried away by the same
   pass that drops a non-consenting patient.
6. **Consent, then the k cross-tab.**

## Consent: dropped, never flagged

There is one consent evaluator and this is not a second one. `_consented` calls
`intake_platform.consent.consent_state` — the same function `intake_api.consent_guard`'s
`ensure_consent` calls — with `scope="research"`, and keeps only the rows it allows. Four
tests cover the four ways a patient is not in:

| case | test |
|---|---|
| never answered (the scope is off by default) | `test_a_patient_who_never_answered_is_dropped` |
| withdrew | `test_a_patient_who_withdrew_is_dropped_and_not_flagged` |
| grant bound to a superseded text (`stale`) | `test_a_stale_grant_is_dropped` |
| granted everything **except** research | `test_the_export_consults_the_research_scope_and_not_a_neighbouring_one` |

The last one is the important one: a patient who granted `core`, `voice`, `documents` and
`learning:service_improvement` is not in a research export. Care consent is not research
consent.

The converse — withdrawing `core` must also remove a patient from research — is not re-tested
here on purpose: `dependents_of("core")` returns every other purpose, so a `core` withdrawal
revokes `research` in the same evaluation pass, and that cascade is INT-038's property with
its own tests in `tests/legal`. It composes with this suite's rule (not allowed → dropped)
without a second implementation to keep in step, which is the same reason the consent check
here calls `consent_state` rather than reading the `consents` table.

"Dropped, not flagged" is asserted rather than asserted-in-prose: the withdrawal test
serialises the extract, the register and every audit entry the export wrote, then fails if
the refuser's id appears, or if any of `refus`, `withdraw`, `declin`, `opt_out` or `excluded`
appears anywhere in it. The export records the served cohort and nothing about who said no —
a count of refusals would itself be the disclosure.

`_consented` asks the ledger **once per patient**, not once per row, which is also what makes
the cohort a count of people: `test_one_patient_wearing_many_rows_is_still_one_subject`
inflates three patients into thirty rows and the extract still refuses.

## Small cohorts: the INT-240/INT-171 pattern reused, not re-derived

- The floor is `K_ANONYMITY_FLOOR`, imported. `intake_metrics.rollups.MIN_COHORT` is already
  an alias of it; a third copy here would be a third chance to drift down.
- The gate is `intake_platform.analytics.materialise`, called on the extract's own
  quasi-identifier cross-tab. A "cell" is one combination of the declared dimensions and its
  `subjects` is the distinct-patient count.
- **The whole artefact refuses; no cell is suppressed.**
  `test_one_thin_quasi_identifier_cell_refuses_the_whole_extract` puts eleven patients on
  `profile=residency_tr` and one alone on `typed`, and the export refuses entirely — a reader
  given every cell but one recovers it by subtraction. The same test asserts the refused
  export left **no** register row.
- **No min/max at any cohort size.** `_ORDER_STATISTIC` refuses a measure whose name reads as
  an order statistic (`age_min`, `max_duration`, `earliest_visit`, `latest_note`,
  `first_seen` are all in the test), because each is one real patient's value however large
  the cohort.
- **Nothing observed goes into a histogram.** Both new series are counters:
  `research_extract_refused_total{spec,reason}` and `research_extract_served_total{spec}`.
  A histogram of an observed value leaks it through `_sum` over `_count` after a single
  observation, and the served counter counts *extracts*, never subjects.
- **The refusal is not an oracle.**
  `test_an_empty_cohort_and_a_thin_cohort_refuse_identically` asserts the two messages are
  string-equal: otherwise "refused" would mean "someone was there, but fewer than k".

## The register

One row per **served** extract, and only served: a refused request produced no extract, so
it goes to the hash chain instead (`research.extract.refused.<reason_class>`). The split is
deliberate — the register answers "what left, under what authority", the chain answers "what
was asked".

A row carries `content_sha256`, `study_id`, `ethics_approval_id`, `protocol_version`,
`recipient`, `requested_by`, `spec_name`, the window, `subjects`, `k` and `recorded_at`. It
carries **no patient id, no pseudonym and no copy of the extract**, and both halves are
tested. The reasons are binding rather than tidy: keeping the extract would create a second
persisted store of personal data, which CLAUDE.md makes a stop-and-ask rather than a design
an agent may choose; and keeping pseudonyms would make the register a linkage table, the
exact artefact the study-scoped pseudonym exists to prevent.

`ExtractRecord.__post_init__` refuses a row whose `subjects` is below its own `k` — a record
of something the gate cannot have served.

Every served extract is also audited in the hash chain
(`test_a_served_extract_is_audited_in_the_hash_chain`, which re-verifies the chain), which is
invariant 4's "every share is audited".

## A real hole found and closed: pydantic echoes what it refuses

`test_a_registry_field_that_is_not_id_shaped_is_refused_without_echo` failed on first run —
not because the validator echoed the value (it is written not to) but because pydantic v2's
`ValidationError.__str__` appends `input_value=<the refused value>`. A registry paste error —
a consent sentence typed into `site`, an identifier into `study_id` — would have reached a
traceback and a log verbatim, defeating invariant 6 through the wrapper rather than the
validator. Fixed with `hide_input_in_errors=True` on both registry models, with the reason at
the config line. The test now pins it, in Turkish, with the diacritics that make it obvious.

## Design decisions worth stating

**The vocabulary is the acceptance rule.** A shape check bounds the carrier and the pattern
tier bounds the known identifier classes; neither can stop a bare given name. Only a declared
closed value set can, and the spec requires one per dimension (an empty vocabulary is refused
as "not a declaration").

**Study-scoped pseudonyms.** `research:<study_id>:<patient_id>` rather than the patient's
platform pseudonym, so an investigator holding two studies' extracts cannot join them.
`test_the_pseudonym_is_study_scoped_and_stable` asserts both halves: stable within a study
(so longitudinal analysis works) and disjoint across studies.

**`tenants=1` is a count, not a label.** One study sits at one qualifying site (TCKAY m.5/6),
so unlike Loop 2 there is no "at least two clinics" criterion to satisfy — but the field
stays a count for the same reason it is one in INT-171: a clinic label re-identifies a small
clinic.

**No new service** (invariant 15 untouched) and **no migration**: this is a library in
`packages/intake_platform/research`, and the register's SQLAlchemy store belongs to the
integration slice the way the audit chain's does. Nothing new is persisted by this change.

**Five modules, none over CLAUDE.md's 500-line rule** (442 / 221 / 200 / 119 / 112 / 100),
and the seams are real rather than arithmetic. `values` answers "may this value appear in an
export at all", which a spec author asks before any patient row exists — no session, no
study, no ledger. `artefact` holds the three types and the canonicaliser, kept apart because
the artefact's *name* is a legal claim and should be readable without the permission logic
around it. `extract` is the gate. `studies` is the registry. `register` is the record.

## What a determined reader could still do

Recorded because it is the honest answer, not because it is comfortable:

1. **The pipeline is pseudonymisation, so the controller can always re-identify.** That is
   not a defect — it is the definition of the route taken, and it is why the consent and the
   ethics approval carry the weight. It does mean the extract must be treated as personal
   data wherever it lands, and the register exists so that "wherever it lands" is answerable.
2. **k ≥ 10 on the declared quasi-identifiers does not bound an *undeclared* one.** If a
   study's spec omits a dimension the recipient can obtain elsewhere (a site roster, an
   appointment list), the cross-tab is gated on the wrong set. The vocabulary makes the
   declared set explicit and reviewable; it cannot know what the recipient already holds.
   That is a study-design judgement for the ethics committee, which is another reason the
   registry is human-authored.
3. **Repeated extracts over overlapping windows are a differencing attack.** The gate holds
   for one extract; it does not compare an extract against the ones already in the register.
   The register makes the attack *visible* (same study, same spec, shifted window) and does
   not prevent it. Closing it means a query-history bound, which is a policy decision with a
   parameter nobody has stated — so it is named here rather than guessed at.
4. **Measures are summed counts and are not themselves floored.** A cell of ten subjects
   whose `sessions` sums to 10 tells the reader every one of them had exactly one session.
   For count-of-people-shaped measures that is harmless; for a measure that is really a
   per-patient quantity it is not, which is part of why `_ORDER_STATISTIC` exists and why
   measures must be integers a spec declares.
5. **The `built_at` timestamp and the window bounds are in the register, not the extract
   rows** — but a recipient who receives two extracts can still order them in time. Nothing
   in the rows is time-resolved beyond the declared `week_start`-style dimension, which the
   k gate crosses.
