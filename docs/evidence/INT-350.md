## 1. G1 — the edge suite needs the pinned plugin, and CI has to fetch it

### 1.1 First red run: no step at all

CI run 36250080198 (PR #554, INT-347, job `check-integration`, 2026-09-26
14:57 UTC). INT-347 fixed the `minio/minio` pull, so this was the first run in
which the dev tier came up and the suite actually ran. The fixture fails
instead of skipping, by design:

```
ERROR at setup of test_the_waf_decides_the_corpus_the_way_the_corpus_says[sqli_in_query_string]
E  Failed: the pinned Coraza plugin is not on disk at /home/runner/work/intake/intake/.cache/edge/plugins-local/src/github.com/corazawaf/coraza-http-wasm/coraza-http-wasm.wasm.
   Run `make edge-plugin` — it downloads the artefact named in infra/security/edge/edge-policy.yaml
   and verifies its sha256 before unpacking. This test fails rather than skips: a WAF suite that
   silently does not run is worse than no suite
…
49 passed, 6317 deselected, 1 warning, 17 errors in 31.39s
##[error]Process completed with exit code 2.
```

All 17 errors are `tests/infra/test_edge_stack_integration.py`, and each has
this setup error. The other 49 integration tests passed.

`.github/workflows/ci.yml`'s `check-integration` job ran `uv sync` and then
`make check-integration`. It never ran `make edge-plugin`, the target that
fetches the Coraza http-wasm artefact from the URL in
`infra/security/edge/edge-policy.yaml`, checks the archive's sha256, unpacks it,
and checks the module's sha256. `make edge-check` depends on that target.
`make check-integration` selects the same suite through `-m integration`, but
it has no such dependency.

### 1.2 The fix is the owner's edit to the workflow

The owner added the step on GitHub, in `2ff595ef`: `make edge-plugin` after
`uv sync --all-packages` and before `make check-integration`. This PR edits no
workflow file. The workflow does not contain the URL or either hash: the
script reads them from the policy, so the workflow cannot drift from the pin.

- **Not cached, on purpose.** The archive is 1,014,369 bytes (the release asset's
  `content-length`). `infra/ci/no-phi-policy.yaml` declares `cache_paths` as a
  closed list, and the INT-206 gate fails any `actions/cache` path missing from
  it, so a cache would mean growing that list. A 1 MB download does not justify
  growing it. On a cache hit, `fetch_edge_plugin.sh` would re-verify only the
  `.wasm` and not the plugin manifest next to it. A fresh, verified download on
  every run avoids that gap.
- The suite itself (`tests/infra/test_edge_stack_integration.py`) is unchanged.

The job exits before `make check-integration`, so the suite does not run. No

### 1.4 Test first (TDD)

`tests/infra/test_waf_rules.py`, group 9. The helper `_fetch_precedes_suite`
compares whole `run:` strings, so the step has to be exactly `make edge-plugin`.

- `test_the_ci_integration_job_fetches_the_pinned_plugin_before_the_suite`
  parses `ci.yml`. It asserts that `make edge-plugin` runs before `make
  check-integration` in the `check-integration` job, and that none of the
  policy's `plugin_url`, `plugin_sha256` or `wasm_sha256` appears in the
  workflow.
- `test_a_fetch_that_runs_after_the_suite_does_not_count` is a near-miss
  negative control: the right step in the wrong order, and a job with no fetch
  step, are both rejected.
- `test_a_fetch_step_with_a_stray_argument_does_not_count` is the near miss that
  happened: `make edge-plugin a` is rejected, and the exact `make edge-plugin`
  is accepted.

### 2.3 Fix

| Package | From → to | File | How |
|---|---|---|---|
| urllib3 | 2.7.0 → 2.8.0 | `uv.lock` | `uv lock --upgrade-package urllib3` |
| virtualenv | 21.7.5 → 21.14.5 (and its dependency python-discovery 1.5.3 → 1.6.1) | `uv.lock` | `uv lock --upgrade-package virtualenv` |
| brace-expansion | 1.1.18 → 1.1.21, 5.0.9 → 5.0.12 | `pnpm-lock.yaml` | two `pnpm.overrides` rows in `package.json`, in the style of the existing `vite`, `uuid` and `decode-uri-component` rows |
| fast-uri | 3.1.6 → 3.1.8 | `pnpm-lock.yaml` | one `pnpm.overrides` row |

`pnpm update --depth Infinity` was tried first and rejected: it moved rollup,
babel and others, 555 lines of lockfile. `pnpm install --lockfile-only` with
the overrides moved only the five packages above, plus peer-suffix churn on the
eslint resolver and two `transitivePeerDependencies` lines. Only the hunks that
name brace-expansion or fast-uri were kept (15 insertions, 12 deletions).

No suppression and no ignore entry was added. `osv-scanner.toml` does not
exist, and `.trivyignore.yaml` is unchanged.

### 2.4 Green run

Same scanner, same command, this branch:

```
Total 1 package affected by 1 known vulnerability (0 Critical, 1 High, 0 Medium, 0 Low, 0 Unknown) from 1 ecosystem.
0 vulnerabilities can be fixed.
| https://osv.dev/GHSA-86w9-cpqp-85rv | 8.7 | npm | node-forge | 1.4.0 | -- | pnpm-lock.yaml |
```

`trivy fs --scanners vuln --severity CRITICAL,HIGH --ignorefile .trivyignore.yaml`
(local 0.74.0; CI pins v0.70.0, and its log on `main` lists the same node-forge
row) reports `uv.lock` clean and `pnpm-lock.yaml` with the same one row, node-forge.

The acceptance clause reads "zero fixable vulnerabilities … reached by upgrading
the affected dependencies, never by adding a suppression or ignore entry". It
holds: 16 fixable findings are gone, and the scanner's own count of fixable ones
is 0.

**What remains, and why it is not fixed here.** node-forge 1.4.0 (RSA PKCS#1
v1.5 verification, GHSA-86w9-cpqp-85rv, CVE-2026-85393). The advisory is
`last_affected: 1.4.0`, and 1.4.0 is the latest release, so there is no version
to upgrade to. The dependents are `@expo/cli@57.0.19` and
`@expo/code-signing-certificates@0.0.6`, both from the Expo toolchain in
`apps/mobile`. Until that is resolved, the `vulnerabilities` job stays red on
this one row (osv exits non-zero on any finding, and trivy on any HIGH). The
two ways out are an ignore row, or a different dependency. `.trivyignore.yaml`
only takes rows that are provably inapplicable, and an ignore is a gate change,
so it is the owner's decision (CLAUDE.md, "when to stop and ask the human").
