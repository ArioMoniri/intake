## 1. The three sources are three different trust problems

The acceptance runs them together in one line. They are not the same, and the design is
mostly the consequence of separating them.

| source | what it is | what the parser does when unsure |
|---|---|---|
| **e-Nabız export** | structured data the patient obtained from the state system — the most trustworthy of the three, and still patient-supplied and therefore still untrusted input | refuses the **document** when the mandated header is absent; refuses the **row** when the geometry does not resolve, and reports the row's ordinal |
| **PDF** | a *rendering*, whose text layer may not exist at all (HB-A1) | never opens one. The input is `TextRegion[]`, so which seam produced it is not this module's business, and both seams are fail-closed today |
| **MHRS SMS screenshot** | an OCR of a photograph of a text message | leaves the field **unset** and names it with one of three reasons. Every reading is a candidate at the type level |

The asymmetry that decides every close call: **a missing appointment is visible to the
patient the moment they open the app; a wrong one is not visible until they arrive at the
hospital on the wrong day.** So there is no nearest-match, no fuzzy distance, no default
date order and no ordinal column fallback anywhere in this change.

## 2. What the e-Nabız parser actually reads, and what it refuses to claim

`intake_platform/records/enabiz.py`.

**It parses a shape a committed source states; it does not claim to recognise a
provenance.** files/03 §10: *"Expect the mandated six-column *Akılcı Laboratuvar* shape
(`Tetkik Adı ∣ Sonuç ∣ Durum ∣ Birim ∣ Referans Aralığı ∣ Önceki Sonuçlar`) in any
post-2018 Turkish report — **`Birim` is a named, mandated column whose contents nothing
constrains**, so expect free text inside it."* That is the whole content of the parser's
table knowledge, transcribed. A header-block signature that said "this is an e-Nabız
export" would be invented: HB-A1 records that nobody on this project has seen one, and an
e-Devlet citizen login is the only way to.

**It feeds INT-121 rather than replacing it.** The output is the closed-key-set completion
`extract_record_items` already consumes, carrying `printed_value` and `printed_unit`
**exactly as printed**. There is no path in this module that resolves a separator,
normalises a unit or touches an analyte name — a parser that helpfully normalises a unit
before the invariant-22 guard sees it defeats the guard, and the tests prove the guard
still fires *through* the new parser rather than beside it:

- ALT printed `30 U/mL` against an authored expectation of `U/L` → `unit_conflict=True`
  with `value_magnitude == Decimal("30")` — and the **near-miss negative control**, the
  same row printed `30 U/L`, → `unit_conflict=False`.
- `Sonuç` of `1.500` → `PrintedMagnitudeAmbiguous` through this parser.
- `Üremi` in `Tetkik Adı` → `AnalyteAmbiguous` through this parser, and `Üre Nitrojeni`
  arrives at the guard spelled as the document printed it.

**Columns are decided by geometry, never by position in the row.** This is the failure the
module exists to stop: a row missing one cell shifts every later cell one column left under
an ordinal read, so `Referans Aralığı` becomes the unit and `Durum` becomes the value — a
wrong unit on a lab number, with nothing in the output that looks wrong. Each cell is
assigned to the one column whose header it horizontally overlaps. A cell overlapping two
columns, a cell overlapping none, and two cells landing in one column each make the **row**
unreadable rather than guessed; there is deliberately no nearest-column fallback, because
the nearest column is exactly where a wrong unit comes from. Rows are grouped by page and
vertical overlap, which is what a row *is* on a rendered page and needs no tuned tolerance.

**Three of the six columns are located and then dropped, each for its own reason.**

- `Durum` is an abnormality flag. A document is not a rules engine (invariant 1), and
  carrying a status forward is a document asserting something about the patient.
- `Referans Aralığı` is the two-number cell files/03 §4.9.6 calls *"a signal to stop, not
  to average"*.
- `Önceki Sonuçlar` is a **different observation with a different date**. Folding it into
  this row attributes a value to the wrong day.

They are still *located*, because locating them is what keeps the columns aligned. The
closed key set refuses them a second time on the way out.

**A document with no recognisable table is refused whole**, not returned as an extraction
with no items: *"this document contains no labs"* is a clinical statement, and this parser
is not entitled to make it. An empty region set — the `NoLayout`/`NoOcr` answer — is
refused by INT-121's existing control before any of this runs.

## 3. Invariant 22 for the other numeral: the printed date

`intake_platform/records/turkish_dates.py` is `numbers.py` for temporal values, and it
obeys the same three rules for the same reason.

`03.04.2026` is 3 April under Turkish `gg.aa.yyyy` and 4 March under `mm.dd.yyyy`. The two
readings are a month apart and **there is no diff that makes the wrong one look wrong** —
which is HUMAN_BLOCKERS.md rule 1's argument about invented numbers, arriving at the
records path through a different door.

- **Resolved per value, never per document.** Nothing picks a locale and applies it onward.
- **A form that reads two ways is refused.** `13.09.2026` has exactly one valid reading (13
  is not a month) and is taken; `09/13/2026` likewise, in the other direction — taking the
  only valid reading chooses nothing. `03.04.2026`, `01/02/2026` and `12-11-2026` each have
  two and are `PrintedDateAmbiguous`.
- **A missing century is not inferred.** `03.09.26` is refused; the twentieth century is as
  available to that string as the twenty-first.
- A Turkish **month name** cannot be read as a day, so `3 Eylül 2026` is unambiguous by
  construction and needs no order at all.

`order=` is the seam for the day a human states the format a source prints. **It has no
default and no `TURKISH` member**, and `parse_mhrs_sms` passes nothing, because no
committed source in this repository states the order an MHRS SMS uses. A default here would
be one engineer choosing once, for every future patient — the shape rule 1 forbids.

Scanning a message adds one rule of its own: **more than one distinct date refuses the
read.** A booking confirmation plausibly prints both the date it was booked and the date of
the appointment, and picking between them without knowing the message's shape is the
wrong-day error with extra steps. A date-shaped token the guard *cannot* read refuses the
whole scan rather than being skipped — the unreadable token may be the appointment. A word
that is not a Turkish month is a different case and is skipped, not refused: `3 Foo 2026`
is not a date-shaped token at all.

Outbound, the crossing happens once: `VisitFields.date` is `date.isoformat()` — plain
positional digits, `useGrouping:false`, one atom, and the exact form the API's own
`_validated_date` accepts.

## 4. The MHRS screenshot: the `üre` rule, applied to a branch name

`intake_platform/records/mhrs.py` and `intake_platform/records/visit_candidate.py`.

**A branch is never substring-matched.** `Göğüs Hastalıkları` is a whole-token subsequence
of `Çocuk Göğüs Hastalıkları`, and reading the child appointment as the adult branch runs
an adult protocol pack on a child. So matching is over **adjacent whole tokens** against
the committed taxonomy, and where one match's token span sits strictly inside another's,
the shorter reading is **the same printed characters counted twice** rather than a second
occurrence — the maximal span is what the document printed.

- **The control:** `Kardiyoloji` → `kardiyoloji`; `Göğüs Hastalıkları` → `gogus_hastaliklari`.
- **The near-miss negative control:** `Çocuk Göğüs Hastalıkları` → `cocuk_gogus_hastaliklari`,
  and the adult reading is asserted *not* to win. This is `Üre Nitrojeni`'s exact shape.
- **A second near miss:** `Kardiyoloji` is a *character* substring of `Çocuk Kardiyolojisi`
  and not a token of it — the Turkish suffix is doing the work, which is why matching is
  whole-token rather than prefix.
- **Two different branches in one message are refused**, because two branches can serve two
  different protocol packs.
- **Turkish folding is load-bearing and is tested:** `İç Hastalıkları` under Python's
  default `casefold` grows a combining dot and stops matching its own committed name. The
  fold is INT-121's `fold_tr`, imported rather than copied.
- **`Acil Tıp` resolves, and the taxonomy still refuses it.** The excluded-cluster rule
  stays where INT-042 put it — one enforcement point, not two.

The vocabulary is supplied by the caller because `intake_platform` does not depend on
`intake-protocols` (`services/api` depends on both), and a second copy of the branch list
here would be a second thing to keep in step with files/09 §1. A vocabulary whose names
collide when folded is refused at construction, and an empty one fails closed.

**Every reading is a candidate at the type level** (invariant 12), in INT-170's shape and
with INT-170's vocabulary rather than a second one: `CandidateVisitFields` has no field a
confirmation could occupy, `ConfirmedVisitFields` cannot be built without a `Confirmation`,
`confirm_visit_candidate` is the only bridge, and it takes no `by=` — the actor is read off
`CONFIRMED_IMPORTED_RECORD → PATIENT` in a closed total table. `source_ref` is derived from
the candidate, so a confirmation naming another document is not a case to reject: the
bridge cannot mint one. **No enum member was added to `LearnedFactSource`**; a screenshot
is a patient-supplied record import, which is what that member already means.

**Two fields are missing from the candidate on purpose, and their absence is the design.**

- No `hospital`. No hospital list is committed, so a screenshot's hospital name cannot be
  resolved against anything, and a field that is always `None` is a claim the parser tried.
- No `visit_type`. files/09 §1's ten visit types are ids, and **no committed source maps a
  printed Turkish word to one of them**; inventing that table would be authoring clinical
  vocabulary. The picker already narrows the type per branch (INT-134).

Both are supplied by the person at confirmation, so the confirmed form carries three things
a patient *agreed to* and two things a patient *typed*, and neither set can be mistaken for
the other. Confirming is agreeing, never restating (INT-121's rule): the candidate crosses
unchanged, and a patient who disagrees types the visit themselves.

**When it is unsure it says which field and why**, in three distinct kinds —
`not_found` (the message did not state it), `ambiguous` (it stated more than one) and
`unreadable` (it stated one this guard will not resolve). Collapsing those into "missing"
would send whoever reads the refusal looking for the wrong bug. A refusal names the field
and the reason and never the message (invariant 6, asserted).

**The appointment *time* has nowhere to go yet, and that is reported rather than papered
over.** `VisitCreate.date` is an ISO **date** string; the store has no time column. The
candidate and the confirmed form both carry `time` because dropping it silently would leave
a patient unable to check the one field they remember, and `as_visit_fields()` — the shape
the API takes — carries only what the API has a field for. Giving the visit a time is a
schema change and an issue of its own; it is not minted here.

## 5. "No scraping" is enforced, not noted

files/03 §12 and 00_STATE §2: there is no e-Nabız **read** path and no category for one —
KSVY m.6(2), as amended by RG 33096 (03.12.2025), is a **closed list of physician access
tiers**. files/06 §1 states the operative sentence: *"e-Nabız remains the state channel —
no scraping, patient-exported documents only — m.6"*.

A note nothing enforces is a comment, so the clause is carried by three mechanical checks
and one structural one:

1. **The egress allow-list names no Ministry host**, so INT-018's default-deny already
   refuses one — the allow-list is the enforcement point and the test pins its contents.
2. **No file under `packages/`·`services/`·`apps/`·`infra/`·`scripts/` names one.** `files/`
   is the historical record and `docs/` is prose about it; the *build* is what may not reach
   one. (The hostnames are assembled from parts in the test so the gate does not find
   itself — the `assert_no_vendor_calls.sh` shape, one level in.)
3. **No module on this path can represent a read.** An AST walk asserts that none of the
   four new modules imports `httpx`, `requests`, `urllib`, `aiohttp`, `socket` or `http`,
   and that no public entry point takes a `url`, `host`, `endpoint`, `client`, `transport`,
   `base_url` or `api` parameter. `parse_lab_table` takes `regions` and nothing else;
   `parse_mhrs_sms` takes `text`, `document_ref` and `vocabulary` and nothing else. A read
   path is not merely absent — it is unrepresentable, which is INT-121's move applied to a
   different property.
4. The control and the test are recorded in the `records` row of
   `docs/security/threat-model.md`, which is what invariant 16 asks a feature PR to link.

**And the legal citation itself was wrong.** See §7.

## 6. Acceptance, line by line

### "patient-exported e-Nabiz documents parsed"

**The parser is complete and is bounded by HB-A1, which names this issue.** The table
parser reads the six-column shape files/03 §10 states, feeds INT-121's extraction layer
with every value still spelled as printed, refuses a document without the header and
reports every row it could not resolve. What it cannot do is turn a PDF into regions:

> **HB-A1** — *"An authenticated e-Devlet login to answer the e-Nabız PDF question. Two
> things are UNVERIFIED and neither is obtainable any other way: does the e-Nabız PDF have
> a **text layer** or is it a scanned image, and does it **normalise units**? … **Do not
> assume a text layer.**"* Blocks: *"INT-122's acceptance; the OCR-vs-text-extraction fork
> in `03 §10`"*. Owner only — it is a citizen login.

So the design is the fail-closed reading of that row: the parser takes `TextRegion[]` and
is agnostic to which seam produced them, both seams (`NoLayout`, `NoOcr`) are wired
fail-closed behind the open engine-and-sandbox ADR (files/10 §4), and the second half of
the row — *"does it normalise units? Lean: **no normalisation**"* — is why nothing here
normalises one either. Rule 2's shape exactly: build the mechanism, wire the gate, make it
fail closed, leave the content empty.

**No PDF library was added, and that is deliberate.** `NoLayout` and `NoOcr` are wired in
production because the engine-and-sandbox decision is an open ADR, not because nobody got
round to it. Adding a PDF parser here would decide that ADR in a records issue, put an
untrusted-byte parser in-process where files/10 §4 requires a seccomp sandbox, and add a
dependency needing an invariant-19 licence verification from the raw LICENSE blob. It is
reported as a finding, not taken as a dependency.

### "MHRS SMS screenshot -> visit fields"

**It produces the fields it can defend and refuses the rest by name.** Branch, date and
time are attempted and each has its own refusal; hospital and visit type are not attempted
and have no field, for the stated reasons. What is *not* here:

- **No committed MHRS SMS exists.** Nobody on this project has seen one, so **the message's
  shape is not encoded anywhere in this change** — no label vocabulary, no field order, no
  regex over a body layout. Values are recognised by their own shape and against committed
  vocabularies, which is the only kind of recognition that does not require having seen the
  message. This is the same refusal INT-121 made about the corpus and INT-102 made about
  its own gap.
- **The pixel→text step does not run in production.** INT-120's `NoOcr` is wired, for the
  same open ADR.

So the clause is met with the mechanism and not with an end-to-end demonstration, and the
ask that would change that is in `docs/backlog/blockers.md`.

### "no scraping of e-Nabiz (no third-party API exists; legal note enforced)"

**Met.** §5. Three mechanical checks, one structural property, a threat-model row, and the
legal citation corrected to the article that is actually in force.

## 7. A repealed article, cited in the backlog

`00_STATE.md §2` carries this as a 🔴 row: *"`06 §1` cites the WRONG KSVY articles, twice —
and one of them is repealed. … **Fix before any legal review.** These are the kind of
citation errors that cost credibility with counsel on first read."*

INT-122's row carried `legal: "KSVY-9,KSVY-10"`. Both are wrong:

- **m.10** was `Sağlık verilerine avukatların erişimi` — **lawyers'** access, not the
  patient's — and it was **repealed outright** by RG 33096 (03.12.2025) MADDE 9.
- **m.9** is `hasta yakınlarının erişimi` — **relatives'** access.
- The e-Nabız regime is **m.6**; patient rectification is **m.13**.

`files/06 §1` corrected its own row on 25 Aug 2026 and already lists INT-122 under
`KSVY-5/6/7/13/16`. This backlog row was the last place in the repository that still cited
the repealed article. It is corrected here to **`KSVY-5,KSVY-6`** — m.5 minimisation, which
any ingestion path is under, and m.6, which is the clause this issue's third acceptance
clause *is*. This applies a correction already recorded in two committed files; it decides
nothing new, and a test pins it so it cannot drift back.

**Still outstanding and not this issue's to fix:** `files/02 §3`'s *"Hekiminize ne
iletildi"* bullet repeats the same m.10 error. `files/06 §1` flags it in terms — *"Flagged
rather than edited, because `02` is not this file's to change"* — and it is reported here

## 9. What is deliberately absent

- **No PDF or OCR engine.** §6. The seams stay fail-closed behind the files/10 §4 ADR, and
  a new dependency would need an invariant-19 licence verification from the raw LICENSE
  blob rather than a badge.
- **No REST endpoint and no migration.** INT-121 deferred `POST /records/items/{id}/confirm`
  for the same reason — it needs a table for extracted items, which is INT-030 schema
  territory reaching INT-123's pgvector index. This issue delivers what such an endpoint
  would enforce.
- **No mobile screen.** The MHRS-screenshot flow's UI is INT-138's *"Visits: create (manual
  + MHRS SMS OCR)"*; this issue delivers the reading and the confirm gate it would drive.
- **No new `LearnedFactSource` member**, no new visit-type vocabulary, no hospital table, no
  e-Nabız branding signature, and no accuracy figure.
