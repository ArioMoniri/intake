# INT-254 — the DSL and the life-threat exemplars, reconciled

INT-041 built the compiler and, while pointing its life-threat loader at the
blueprint exemplar, found that the document does not load. It did not fix the
gaps: they are INT-040 semantics. This issue fixes four of them and the one
real defect found in the same pass, and pins the rest open.

## The reproduction

```
uv run protocols compile --pack specialty.kardiyoloji --voice x \
  --life-threat files/protocols/base.life_threat.yaml
```

**Before: 21 validation errors. After: 13.** The eight error locations
belonging to the four named gaps are gone; nothing else was absorbed.

## Gap 1 — `tense_anchor` is a reference, not a bare key

This was the one with a wrong answer available. The tempting reading is
"`tense_anchor` names a slot, and slots are `SlotKey`, so strip the section" —
and it is wrong, because two sections may both declare `onset_at`.

The evidence that settles it is in the code, not in a preference:

- `protocols/triage/expr.py` tokenises a `when` predicate's `ident` as
  `[a-z][a-z0-9_]*(?:\.[a-z][a-z0-9_]*)*` — **dotted references are
  first-class in the grammar**, and `referenced_slots()` returns them dotted.
- `protocols/triage/engine.py:141` computes
  `refs = referenced_slots(node) | {rule.tense_anchor}` — the anchor is
  unioned into the predicate's reference set.
- `protocols/triage/context.py` documents `TriageContext.answers` as keyed
  "by the dotted slot reference exactly as the rule's `when` predicate spells
  it".

So the anchor and the predicate's references were already one namespace at
runtime and two namespaces in the type. The fix gives them one pattern:
`SLOT_REF_PATTERN` lives in `protocols/types.py` (the leaf module both sides
already import), the DSL builds `SlotRef` from it, and the tokenizer builds
its `ident` group from it. `SlotKey` keeps the bare form and keeps its job —
naming a slot *inside* its section, where a dot is meaningless.

`SLOT_REF_PATTERN` is strictly `SLOT_KEY_PATTERN(?:\.SLOT_KEY_PATTERN)*`, so
the widening admits exactly what the grammar admits and nothing more:
`Chest_pain.onset_at`, `chest_pain.Onset_at`, `chest_pain.`, `.onset_at`,
`chest_pain..onset_at`, `_onset_at`, `9onset`, a space, a trailing space and
the empty string are all still rejected, each with its own parametrised case.

**No existing pack changed.** `base.intake`, all 79 specialty packs and every
fixture write bare anchors (`sikayet_suresi`, `time_last_known_well`,
`olay_zamani`, `sure_dakika`), which remain valid.

### The workaround this removed

`tests/safety/triage_goldens_corpus.py` (INT-059) had already hit this and
worked around it: `payload["tense_anchor"] = str(raw["tense_anchor"]).replace(".", "__")`,
with the golden fixtures keying answers on `chest_pain__onset_at`. That meant
the safety golden suite evaluated the anchor under a name the document never
writes, while its own mutation test claimed edits flow through verbatim. Both
the rewrite and the constants are gone; the anchors are now carried like every
other field, and `make safety` is green on the dotted names.

## Gap 2 — `status` stays required; the exemplars carry the value

Two options were on the table: default `status` to `active`, or write it in
the two sourced exemplars. Defaulting loses, for the reason the file already
gives about `register` two fields away — *"a default would be chosen once, by
an engineer, for every future rule"*. Here the specific harm is sharper: with
a default of `active`, a **forgotten** `status` reads active, which is the
unsafe direction, and ~30 more rules are still to be pasted against this file.

So `RedFlagRule.status` remains required with no default (a test asserts
`is_required()`, so the option cannot be quietly taken later), and
`rf.chest_pain_cardiac_features` and `rf.chest_pain_no_cardiac_history` now
carry `status: active` with a comment saying why it is written rather than
defaulted.

`active` is not a new judgement about those two rules. Both carry complete
`evidence` blocks sourced to binding Turkish law; the file itself says of the
first *"the one rule here whose evidence block is complete"*; exemplars 3 and
4 write `status: draft_needs_source` explicitly; and INT-059's translator has
been reading these two as `active` in the merged safety suite since it landed.
This makes the repo's operative reading explicit. It also cannot cause
anything to be served: `served: false` and `maturity: L0` at pack level are
untouched, and rule status is not pack status.

That translator's `raw.get("status", "active")` default is also gone — it now
reads `raw["status"]`, so a future rule that omits status fails loudly in the
safety suite instead of being silently defaulted there too.

## Gaps 3 and 4 — `SourceBlock.note`, `LocationAction.secondary`

Both are added as optional fields rather than folded away.

- `note` is provenance commentary *about the citation* — exemplar 1's records
  the EK-4 three-way chest-pain split and names the gate that asserts the third
  arm exists. Moving it out of the source block would separate it from the
  quote it qualifies. It is not a new hole in invariant 17: `_signoff_findings`
  walks `rule.model_dump()`, so the pending-value scan reaches it like every
  other rule string.
- `secondary` is a second action code carried **alongside** `primary`
  (exemplar 1: `CALL_112` + `NEAREST_ACIL_ADDRESS_AS_TEXT`). Folding it into
  `primary` would make one field mean two actions and put their ordering
  beyond the schema's reach. It takes the same `ActionCode` shape as `primary`
  (a lowercase value is rejected, with a test).

**What `secondary` deliberately does not do:** it adds no second carrier for
the ON_SITE 112 affordance. `RedFlagAction._on_site_never_offers_112` still
refuses `show_112: true` under ON_SITE with a `secondary` set, tested
directly. **Residual, stated rather than closed:** `primary` and `secondary`
are open SCREAMING_SNAKE strings, so a 112-*bearing* action code under ON_SITE
is not structurally excluded — for `primary` either, and that predates this
issue. Closing it needs an enumerated action-code set, which no blueprint
writes down, so it is recorded in the file's `schema_reconciliation` block
rather than guessed at here.

## The validator defect

`validator.py:351` dereferenced `rule.action.unknown.ask_one_tr` with no None
check. Reproduced before the fix:

```
>               texts.append((rule.id, rule.action.unknown.ask_one_tr))
E               AttributeError: 'NoneType' object has no attribute 'ask_one_tr'
packages/protocols/src/protocols/validator.py:351: AttributeError
```

The three location keys are required on `RedFlagAction`, so this is reachable
only on an object that got past validation — which is precisely the case
`compile/resolve.py:229` already guards, with all three branches checked:
`action is None or action.remote is None or action.on_site is None or
action.unknown is None`. The compiler had the guard; the validator did not.
The same defect sat on `remote` and `on_site` two lines above, so all three
are fixed, not just the one named.

Why it mattered more than a crash: `validate_packs` iterates every pack in the
registry, so an `AttributeError` in the middle **took every remaining finding
with it** — a broken action masked the numeral and `follow_up_tr` checks on
its own pack rather than adding to them. `_tr_texts` now skips an unresolved
branch, and a new `_red_action_findings` emits
`FindingCode.RED_ACTION_UNRESOLVED` naming the rule, the DSL-layer twin of
`RefusalCode.RED_ACTION_UNRESOLVED` in the compiler slice.

INT-041 routed around this by ordering — its own RED-axis check runs first —
because another agent was live in the file. Ordering is not a fix: it holds
only for callers that happen to run the compiler's check first.
