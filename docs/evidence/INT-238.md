# Evidence — INT-238 · Kaynaklar: document ingest could never produce a scan verdict

## Acceptance (working label; the coordinator files the backlog entry)

Owner bug report, verbatim: *"kaynaklar cant be added and that part is not
completed with regard to roadmap"*.

INT-229 (mobile client + screen) and INT-034/INT-120/INT-197 (store, ClamAV
client, endpoints) had all merged, yet no document could be added on the
documented dev stack. This iteration finds and fixes the wiring defect that
made every upload fail, makes a no-verdict scan a typed refusal instead of a
500, and records the roadmap gap map for the rest of the slice.

## Reproduction — the real local stack, driven exactly as the app drives it

Compose (postgres/redis/minio/openbao/clamav/hapi) up; API booted from this
worktree on `127.0.0.1:8010` with the dev-tier env. A probe replicating the
INT-131 `authedFetch` sequence (attested OTP → DPoP-bound access token →
consents → visit → records declare → content PUT → list) with a synthetic
phone and a synthetic 1×1 PNG — no PHI at any point.

```
--- POST /v1/consents/grant documents: 201
--- POST /v1/visits: 201   {"id": "fde4b02a-…"}
--- POST declare: 201
    {"id": "c9e91568-…", "state": "quarantined", "content_type": "image/png",
     "upload_url": "http://127.0.0.1:9000/intake-docs/quarantine/…"}
--- PUT content: 503
    {"error": "scan_not_configured"}
--- GET documents: 200
    [{"id": "c9e91568-…", "state": "quarantined", …}]
```

The declare leg succeeds and writes a `quarantined` row; the byte ingest
refuses; the row stays quarantined forever. In the app that surfaces as
`records.err.scanUnavailable` with a document stuck on "Taranıyor" that never
resolves — the owner's "kaynaklar cant be added".

### Root cause

`intake_api.app._documents_from_env()` built its `Scanner` slot from
`DevNullScanner()` alone. That stub is unconstructible without
`INTAKE_DEV_ALLOW_UNSCANNED=explicit-yes`, so on any normal stack the slot was
`None`, `DocumentStore` fell back to `_NoScanConfigured`, and every
`PUT …/content` answered 503 — while a healthy ClamAV sat on 127.0.0.1:3310
and INT-120's fully-tested `ClamAvScanner` (INSTREAM, TCP or unix socket,
`from_env()`) sat unreferenced in `intake_platform.uploads`. The production
wiring was never covered: `tests/api/api_harness.py` injects a `CleanScanner`
into every harness, so no test ever exercised the slot the service actually
builds at boot.

Second, narrower defect found in the same path: a scanner that *is* wired but
cannot produce a verdict raises `ScanFailedError`, which no handler caught —
an unreachable clamd answered **500** with a stack trace rather than a typed
refusal the client can word.

## The fix

- `services/api/src/intake_api/app.py` — scanner precedence, strongest first:
  `ClamAvScanner.from_env()` whenever a clamd endpoint is configured, then the
  dev stub behind its opt-in phrase, then `None`. The real scanner is checked
  **first** so the dev stub can never shadow a live clamd and quietly turn a
  verdict into an assumption. No default endpoint is invented — a guessed
  scanner is a scan that did not happen.
- `services/api/src/intake_api/documents.py` — `ScanFailedError` → typed
  `503 {"error": "scan_failed"}`. The row stays quarantined, never promoted
  and never fetchable.
- `apps/mobile/src/lib/records/api.ts` — `scan_failed` maps to the existing
  `scan_unavailable` kind. Both no-verdict causes read to the patient as the
  same honest "we could not check this file yet"; the distinction is the
  operator's, not theirs.
- `Makefile` — `make dev` (and `dev-down`) carry the `clamav` profile. Ingest
  fails closed without a scanner, so a dev stack without clamd cannot add a
  record at all.
- `env.example` — documents `INTAKE_CLAMD_HOST` (+ port/socket/timeout) as
  required for document upload, and corrects the stale "until INT-120's
  ClamAV lands" note; INT-120 has landed. Left commented, like every other
  optional knob in that file: `tests/security/test_openbao_wiring.py`
  ::`test_env_file_carries_only_address_and_token` holds the template to the
  OpenBao pointer alone (invariant 13), and that gate is not mine to relax.
  The endpoint therefore still has to be exported deliberately — which is
  also INT-120's own posture, since it refuses to guess one.

## End-to-end verification against the live stack

Same probe, API restarted with `INTAKE_CLAMD_HOST=127.0.0.1`:

```
--- POST declare: 201     {"state": "quarantined"}
--- PUT content: 200      {"state": "clean", "sha256": "c414cd0e…"}
--- GET documents: 200    [{"state": "clean", …}]
```

The verdict is a real one, not a stub. Pushing the 68-byte EICAR test vector
through the same path:

```
--- declare eicar(raw): 201
--- PUT eicar(raw): 422   {"error": "document_rejected"}
--- list: 200             [{"state": "rejected", …}]
--- download url: 409     {"error": "document_not_scanned"}
```

Infected bytes are rejected, retained out of reach, and never served. (An
EICAR wrapped in a PDF envelope returns clean — confirmed to be clamd's own
behaviour, `clamdscan` agreeing on both payloads, not a gap in this path.)

## Roadmap gap map (Phase 3 — reported, not built)

`02 §5.5`/`§7`/`§8.1` and `03 §10` (the ingestion pipeline; `03 §4.6` is
*Runtime invariants*, not ingestion) promise substantially more than the slice
delivers. Covered by existing issues: extraction to `ExtractedRecordItem[]`
and provenance rendering (INT-121, INT-138), LOINC/ATC/ICD coding (INT-121,
INT-124), e-Nabız/MHRS import (INT-122), pgvector retrieval (INT-123), DSAR
export (INT-037), consent texts (INT-210). Wearable import is done, device-
local by design (INT-208).

Gaps with **no backlog issue at all**, highest-stakes first:

1. **EXIF/GPS strip on ingest** — `03 §10` calls this a KVKK m.4 minimisation
   failure by name. Camera-roll JPEGs reach MinIO with GPS and device ids
   intact today, and nothing in the backlog will ever remove them.
2. **`services/workers` does not exist** — `03 §10` is "MinIO → Celery", and
   `uploads.py` was written around the absence (`process_quarantined_document`
   is a bare callable whose docstring points at a workers issue never filed).
   INT-121/122/123/124 all assume a runtime nobody is scheduled to build.
3. **OCR engine + seccomp sandbox** — INT-120 is `done` while its own evidence
   file defers both pending an ADR. `NoOcr` is still the fail-closed default
   and no successor issue exists; INT-121 consumes text it cannot produce.
4. **"Never upload while a voice turn is in flight"** — `02 §8.1` calls it a
   binding product rule, `03 §4.9.4` a hard rule. Nothing serialises the two.
5. **HEIC** — first image input named in `03 §10`, the iPhone default in
   Türkiye; the sniffer recognises it, the allow-list refuses it, no issue
   widens it. Photographing a lab report on an iPhone yields `records.err.type`.
6. **JSON/FHIR/HL7 v2 ingest** — promised in `02 §5.5` and `03 §10` with a
   "bypass OCR" fast path; the one input class needing no OCR at all.
7. **Per-document delete** — `02 §3` requires every timeline item to be
   individually deletable; `ObjectRemover` exists and no route reaches it.
8. **Hikâyem (longitudinal timeline) and "Ne değişti" (pre-visit diff)** —
   both P2 in `02 §3`, explicitly promoted from P3; neither has an issue.
9. **In-context `documents` consent on the upload sheet** — `02 §7` makes
   in-context asking the whole defensibility argument; the screen routes to a
   cold consents list instead.
10. **ClamAV/tesseract/docling absent from `observability/registry.yaml`** —
    invariants 13/19 want `self_hostable` + a probe for anything on the PHI
    path, and ClamAV reads document bytes.
11. Offline upload queueing (`02 §8.3`), resumable upload, thumbnails, FHIR
    `DocumentReference`.

Also flagged: **INT-124 is mis-phased.** The unit-resolution guard is
CLAUDE.md invariant 22 and `03 §10`'s reserved invariant 53 — a safety
invariant — and it sits in a P2 `gpu`-labelled issue behind INT-121. A
`üre`/BUN substring match is a 2.14× error on a value that can fire a
red-flag rule.

## Known, not fixed here

- A fresh OTP account starts with every consent false, `core` included, while
  the records screen gates on `documents` alone. Granting documents without
  core reaches the upload affordance and then gets an honest
  `records.err.consent` from the visits call. A UX wart in consent-UI
  territory (INT-132), not this defect.
- `docs/legal/` does not exist, so the consent catalog is empty and no scope
  can be granted through the app at all — the reproduction had to point
  `INTAKE_LEGAL_ROOT` at the test fixture tree to get past it. That is
  **INT-210** (`approval:human-legal`), and inventing consent text is
  forbidden by invariant 18 and the stop-and-ask list.
