### How the acceptance's three terms were read

- **"axe/a11y CI checks"** — there is no axe for React Native, because there
  is no DOM: the accessibility tree only exists at runtime on a device. What
  was built instead is `apps/mobile/e2e/a11y.spec.ts`, a source-scanning suite
  that reads each `.tsx` with a brace-, string- and comment-aware JSX reader
  and asserts on individual elements' accessibility props. It runs in
  `pnpm vitest run`, therefore in `make check-ts`, therefore in `make check`.
  A test named `axe` that could not run axe would be a claim, not a check.
- **"VoiceOver/TalkBack scripts"** — delivered as the per-criterion
  **cannot verify** rows of the conformance report, each naming the exact
  runtime behaviour a device session must decide (§2 BK6, BK10, BK11, BK17,
  BK18, BK25, BK26; §3 for 1.3.4, 1.4.4 layout survival, 1.4.10, 2.4.7,
  2.4.11, 3.1.2). That list IS the device script, and it is written where the
  auditor reads it rather than in a separate file that could drift.
- **"docs/legal/accessibility-statement.md (EN 301 549 mapping)"** — written,
  and explicitly marked **not for publication**: publication is INT-226 and is
  gated on HB-L9 plus counsel. Nothing renders it (invariant 18 — legal texts
  render only from `docs/legal/` **with hash binding**, and this file carries
  no version or hash because no loader may read it yet).

The parent instruction additionally named
`docs/compliance/accessibility-conformance.md`, mapped 1:1 to BK numbering.
That is the substantive deliverable; the statement points at it.

## What changed, and why each change is a criterion

Three new pure modules carry the policy so it is testable without a device:
`src/lib/a11y/labels.ts` (accessible-name composition — one separator, visible
words first), `motion.ts` (what the app does with the OS reduce-motion answer),
`target.ts` (the 44 pt floor and the computed vertical slop that reaches it).
`prefs.ts` is the thin `AccessibilityInfo` adapter, kept separate so the policy
modules stay importable in a node test environment.

| finding | criterion | fix |
|---|---|---|
| The **speaking bubble's accessible name was the barge-in copy**, which replaced the agent's question — the words were unreachable to a screen reader | SC 4.1.2, 1.1.1 | The name is the spoken turn; the affordance moved to `accessibilityHint` |
| **Nothing attributed a transcript turn to its speaker** — left/right alignment is the only sighted cue and no reader conveys alignment | SC 1.3.1 | `spoken(speaker, …)` on every bubble; `a11y.speaker.agent` / `a11y.speaker.patient` |
| Listening / speaking / transcribing / settling were **animation only** | SC 4.1.2 | `useLiveAnnouncement` + `accessibilityLiveRegion="polite"` on each state |
| The listening pulse is an **infinite 700 ms loop** running for the whole open-mic turn | SC 2.2.2 (BK14) | Rests static under OS reduce-motion; scroll, screen transitions and the sheet collapse too |
| **No heading semantics anywhere** — `accessibilityRole="header"` appeared zero times | SC 1.3.1 (BK5) | `AppText heading` prop; every screen title and every guidance-block title |
| **13 controls under 44 pt, 5 under 24** — bare caption links | SC 2.5.8 | `minHeight: MIN_TAP` where the box owns its space, computed `verticalSlop()` where the measured design must not move |
| **Error lines were amber text with no announcement** on four screens | SC 3.3.1 (BK28) | `live="assertive"`, prefixed "Hata"; a test forbids a new amber line that is not announced |
| **Single-answer turns announced as checkboxes** while the handler enforced single choice | SC 4.1.2 | `radio` on intake single-select, dialogue confirm chips, branch rows, visit-type chips |
| **Three identical "Paylaşılıyor" switches** on review; a consent row and its switch sharing one name | SC 4.1.2, 2.5.3 (BK22) | `withContext(visibleWord, subject)` — visible words first so Voice Control still reaches them |
| **Five `TextInput`s double-scaled** (OS multiplier × app multiplier: 200 % rendered at 400 %) | SC 1.4.4 | `allowFontScaling={false}` where `scaledSize` is applied |
| **Progress dots and ladder rungs carried state as a hue only** | SC 1.4.1 (BK8) | Dots hidden as decoration; each rung says "tamamlandı" / "henüz tamamlanmadı" |
| **The section sheet did not declare itself modal** | SC 2.4.3 (BK18) | `accessibilityViewIsModal` |

## Review round — seven defects the green suite did not catch

An independent read of the diff found seven real defects **after** the suite
was green, which is worth recording because it is the honest measure of what
a source-scanning suite can and cannot prove. Each is fixed, and each fix
brought its own assertion so the class cannot come back.

1. **`accessibilityViewIsModal` on `<Modal>` is silently dropped.** React
   Native's `Modal` enumerates the props it forwards to the native host view
   (`Libraries/Modal/Modal.js`) — there is no spread — so the prop
   type-checks (`ModalProps extends ViewProps`) and never reaches a view. The
   SC 2.4.3 fix did not exist at runtime, and the suite was certifying a
   no-op. Moved onto the sheet container; a test now **forbids** it on
   `<Modal>` as well as requiring it on the sheet.
2. **`live="assertive"` is silent on iOS.** `accessibilityLiveRegion` is
   declared `@platform android`, and `accessibilityRole="alert"` does not
   substitute — iOS has no alert trait and RN posts no announcement for it.
   All four error lines were mute under VoiceOver. Each screen now also calls
   `useLiveAnnouncement`, and the test requires both halves.
3. **The visible copy changed.** `labelled(t("a11y.error"), …)` was applied to
   `AppText`'s *children*, not to an accessible name, so the word "Hata" was
   printed on screen — and on the records screen it labelled
   `records.scanningInfo` ("Belge güvenlik taramasında…"), a progress
   message, as an error. Visible copy reverted; the prefix now exists only in
   what is spoken, and the records notice is announced politely without it.
4. **The consent switch was unreachable.** A pressable `ListRow` is
   `accessible` by default, so RN merges the subtree and the `StatePill` in
   the trailing slot is not a focusable element at all on iOS — the row's new
   hint, state and slop were inert, and there was **no way to withdraw a KVKK
   consent with a screen reader**. Worse, the slop stole 7 pt of the parent
   row's tap area above and below the pill, turning "open the text" into
   "withdraw the consent" for a sighted user. Fixed with a custom
   accessibility action on the row (VoiceOver's actions rotor, TalkBack's
   context menu) plus a visible 44 pt pill; a test forbids `hitSlop` in that
   file.
5. **Double-speak in the dialogue.** Three bubbles carried
   `accessibilityLiveRegion="polite"` *and* the state went through
   `useLiveAnnouncement`. TalkBack re-reads a polite region when its content
   changes, and those labels contain the whole question — so every playback
   flip re-read the question. One mechanism now; a test forbids the other.
6. **SC 2.5.3 regression, introduced by this pass.** The listening bubble
   reads "Sizi dinliyoruz." and its new name said "Siz: Sizi dinliyor" — the
   visible string was no longer contained in the name, so voice control could
   no longer activate it, where the pre-diff label had matched exactly. Bubble
   names now use the visible strings; the a11y catalog's paraphrases are for
   announcements only, and a test pins that.
7. **`useLiveAnnouncement` ate a repeat.** It returned early on `null` without
   clearing the remembered value, so A → null → A announced A once — and that
   sequence is the ordinary dialogue path (speaking → confirming → speaking).
   The rule is now a pure function, `lib/a11y/announce.ts`, with the A → null
   → A case as a named test.

Two smaller ones from the same read, also fixed: the suggested single-select
option announced `checked: true` for a suggestion the patient had not
committed (contradicting invariant 1 in the one modality where "Önerilen"
cannot be told apart from a state), and an `accessibilityRole="list"` wrapper
on the status ladder that was a no-op on iOS and repeated the Kicker above it.

One more finding was **already fixed before the review landed** and is
recorded because the reasoning is worth keeping: the ask-ahead engine makes
"agent speaking" and "ASR transcribing" concurrent, so a ternary that treated
them as exclusive reported the quieter one and never announced the louder.
The turn phase now wins.

## How a RED renders for a screen-reader user

**It does not render at all — for anyone.**

`src/lib/livekit/red.ts` decodes the data-channel trigger and resolves it
against the pre-positioned script catalog (refusing anything under-specified,
clamping the 112 affordance off under `ON_SITE`); `session.ts` emits it as a
`{ type: "red", presentation }` event; `events.ts` types it. And then nothing
consumes it:

```
$ grep -rn "lib/livekit" apps/mobile/src/app apps/mobile/src/components
(no matches)
```

No screen and no component in the mobile app imports the voice-session module.
The RED delivery route (`visits/[visitId]/emergency`, files/02 §5.3 — one
route, four registers, three locations) is a later issue, and building it here
would put two issues in one PR.

So the honest statement, and the one the conformance report makes in §4: a
screen-reader user perceives a RED exactly as a sighted user does, which is
not at all. This is a **product** gap, not an accessibility one, and it must
not be read as an accessibility defect this pass declined to fix.

What the issue that builds it must carry is written out in the report §4 as
seven requirements — text first and never audio-only; assertive focus on
arrival; action before do-nots before explanation; the 112 affordance as a
labelled control that is **absent from the accessibility tree** under
`ON_SITE` rather than dimmed; `SILENT` perceivable without audio or vibration
being the only channel; the screen modal to the accessibility tree; and no
load-bearing emphasis carried by an animation, because reduce-motion would
stop it.

## Found and NOT fixed

The palette was measured in full (WCAG relative luminance, both schemes, every
pair the app renders). Hexes were out of scope for this issue by instruction,
so these are reported. The measured floors are now pinned in
`src/lib/theme.test.ts` so they cannot silently worsen.

1. **SC 1.4.3 — `inkFaint` on light grounds: 3.43 / 3.64 / 3.11 : 1** against
   4.5. It carries 13 pt caption text, which is not "large text", so 3:1 does
   not apply. Widely used: dates, the progress counter, provenance lines, form
   hints, inactive rail labels. Dark mode also fails on `surfaceRaised`
   (4.03). Fixing it needs a palette-hex change.
2. **SC 1.4.3 — `success` on `successSoft` (light): 4.35 : 1.** The "Dosyaya
   eklendi" chip. Independently confirms what design pass 5 recorded.
3. **SC 1.4.11 — light-mode component boundaries: `border` at 1.25 : 1**
   against 3. Cosmetic for cards; a real failure for **unselected interactive
   chips**, whose `surface` fill sits on `background` at ≈1.04:1, leaving the
   hairline as the only boundary. Dark mode is unaffected (filled, borderless).
4. **SC 3.1.1 on Android.** `accessibilityLanguage` is iOS-only in React
   Native; there is no per-node equivalent. Unclosable without a native module.
5. **Heading rank.** RN's `header` role has no level, so screen titles and
   section titles are indistinguishable in the rotor. Platform limitation.
6. **Sheet focus management (SC 2.4.3).** The sheet declares itself modal but
   does not move focus in or restore it out. Deliberately left: doing it blind
   with `setAccessibilityFocus` is as likely to make focus worse as better, and
   it is only meaningfully verifiable on a device.
7. **OTP auto-advance (SC 3.2.2).** Focus moves on every keystroke without
   advising the patient. Conventional, and mitigated by
   `textContentType="oneTimeCode"` autofill; not changed blind, and **not
   claimed conformant**.

## Deviations

- **No axe.** Explained above; a source-scanning suite replaces it because
  React Native has no DOM. No dependency was added — `eslint-plugin-jsx-a11y`
  and `eslint-plugin-react-native-a11y` were considered and rejected: both
  would need a lockfile change under a `--frozen-lockfile` install and a
  licence verification, and neither covers what actually failed here (names,
  state, live regions, reduced motion, target size on `Pressable`).
- **The statement is not published.** The acceptance names the file; it was
  written, and marked not-for-publication. Publishing a conformance statement
  before a device run and before HB-L9 would be exactly the overclaim
  invariant 20's posture forbids, and INT-226 owns publication.
- **`docs/compliance/` is a new directory.** The parent instruction named the
  path. Nothing loads from it.
- **No simulator, no Metro.** Every claim in this evidence file and in the
  report is from code inspection or from a test, and every claim that would
  have needed a device is marked as unverified instead.
