## The one fact to read first: the consent TEXTS do not exist

`docs/legal/consents` is absent — the texts are INT-210's human deliverable
(owner + counsel), and this iteration does not author a word of them. What
ships is the COMPLETE UI mechanism against the INT-038 loader contract, and
it fails closed honestly, exactly like the server:

- a purpose whose text is missing renders the calm "Metin hazırlanıyor"
  state and CANNOT be granted — no grant action exists on the detail screen,
  and the reducer refuses (`grant` is a no-op without a loaded text);
- fixture texts live ONLY inside test files (inline constants in
  `ledger.test.ts` / `consent.spec.ts`) — never in `docs/legal`, never in the
  app bundle (the e2e spec walks `src/` and pins that no consent text or
  front-matter marker is compiled in, and pins `docs/legal/consents` absent);
- the moment INT-210 lands texts, every dev-seeded/unbound grant goes stale
  and the UI re-prompts — adding the text IS the version bump (mirrors
  `intake_platform.consent.service.consent_state`).

## What was built

Layered İzinleriniz (02 §7's permanent one-tap-away record), purpose by
purpose in the 06 §2 closed list and order (`share` deliberately absent —
parameterised per visit in Review & send; `lane:acoustic` refused by name —
06 §2.4 made it an ICF, not a toggle):

| Purpose | Rendering | Basis shown |
|---|---|---|
| `core` | information row + "Hizmetin temeli" pill — never a switch | service itself |
| `voice` | toggle, off | açık rıza |
| `lane:affect` | inset sub-toggle under voice; grantable only while voice stands; falls with voice | açık rıza |
| `lane:linguistic` | inset sub-toggle under voice (UI nesting only); survives voice withdrawal | açık rıza |
| `wellbeing` | toggle, off | açık rıza |

| `learning:service_improvement` | default-ON opt-out switch, honest basis sublabel ("kapatmak hiçbir özelliği kısıtlamaz") | de-identified opt-out |
| `satisfaction` | toggle, off | açık rıza |
| `research` | toggle, off | açık rıza |

Layer 2 (`me/consents/[purpose]`): the versioned text rendered from the
loader payload (`entry.text.body` — legal copy NEVER enters the i18n
catalogs, pinned), version + hash-binding indicator, who-sees-what and basis
copy, grant ("Okudum, kabul ediyorum") only when a text is loaded, withdrawal
with the "hemen geçerli" note. Stale grants render "Yeniden onay gerekli"
with the re-prompt path; a version bump can never silently re-grant (pinned:
`applyTexts` touches no record; only an explicit grant rebinds).

Entry points: Profilim → İzinleriniz row (replaces the four inline demo
pills), and the first-run at `/(auth)/consent` right after OTP verify — a
consent needs a subject, so it comes after account creation, grants nothing
by itself, and "Devam edin" never blocks (optional purposes never gate core
flows; `visibleTabs` with everything off still yields today/visits/records/me,
pinned).

Withdrawal is instant: the ledger flips synchronously and the legacy session
consents flip in the same handler, so the existing wellbeing tab gate reacts
immediately; voice withdrawal cascades `lane:affect` in the same pass with
ONE queued op for the root (the server re-derives cascades itself).

## Queueing semantics (stated, not implied)

The server ledger is the source of truth (invariant 4). Local changes apply
instantly and enqueue ops in order, in memory only — persisting consent
state on-device would be a new category of personal data, which is a
stop-and-ask decision, so it was not taken. Each queued grant carries the
version + SHA-256 hash of the text that was actually shown; the flush pushes
strictly in order and stops at the first failure. The İzinleriniz screen
shows an honest notice while ops are queued ("bu cihazda uygulandı;
bağlantı kurulunca iletilecek"). After an app restart the queue is gone and
the next server snapshot reconciles — local state yields to the server
wherever it speaks. services/api exposes no patient-facing consent routes
yet (INT-038 shipped the service layer + guard); the client seam targets
`GET /v1/consents`, `POST /v1/consents/grant|withdraw` via the DPoP-bound
`authedFetch`, and treats non-OK/unreachable as "route absent": local state
stands, nothing fakes a success. Needed server work is reported, not built
here (hard boundary: no services/api changes).
