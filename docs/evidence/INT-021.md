  machinery every later service reuses: pydantic models for
  `observability/metrics_catalog.yaml` (types counter|gauge|histogram, unique
  names, PHI-risk label denylist — `name`/`phone`/`tckn`/`text`/`transcript`

  file; SLIs are error ratios over a `[5m]` base rate, re-ranged per window.

  `mount_http_metrics(app, service)`: `http_requests_total` +

  reaches a label — tested), unhandled exceptions counted as 500, unmatched
  requests collapsed to one label value.

  two http_* families from the shared middleware plus the prometheus_client
  default collector families behind `/metrics`. Nothing invented.

## Honest scope (why `doing`)

- **services/api has not landed on main** (no `services/` directory exists
  yet), so `http_requests_total`/`http_request_duration_seconds` had no
  emitter anywhere. Rather than catalogue series nothing serves, the shared
  middleware `mount_http_metrics` now emits them from
  `packages/intake_platform` — the same place `mount_health` lives — and the
  api mounts both when it lands. The every-service-dir-has-an-SLO-file gate
  binds the moment the first directory under `services/` appears.
- `docs/slo/voice-runtime.yaml` and `docs/slo/workers.yaml` are NOT written:
  those services do not exist, no metric they would reference is emitted by
  any code, and an SLI over series nobody serves would be an invented value.
  They follow with their services, through the same schema and generator.
- "golden-signal dashboards provisioned" — the dashboard exists as code and
  is test-bound, but nothing provisions it into a running Grafana: no live
  Prometheus/Grafana exists in CI, and alerting is untested against a live
  stack until the INT-023 observability deploy.
- sec_row `monitoring-contract` (files/10 §6): endpoints unchanged
  (INT-010), SLOs + burn-rate alerts + runbook + dashboard are this issue;
  probes remain INT-022.
