**So the provider** (`infra/keycloak/providers/webauthn-session-notes`) is
`WebAuthnSessionNotesAuthenticator extends WebAuthnAuthenticator`, with `action` overridden
as `super.action(context)` and then `WebAuthnSessionNotes.recordAfterAction(context,
getCredentialType())`. That method writes both notes only when all of these hold:

- the status is `SUCCESS`;
- there is an authenticated user;
- one of that user's stored credentials of the authenticator's own type has the asserted id,
  decoded exactly as the stock code decodes both sides;
- that credential has an AAGUID.

The two notes are `intake.webauthn.aaguid` (the stored UUID text) and
`intake.webauthn.credential_id` (`Base64Url.encode` of the asserted bytes). In every other case
it writes nothing, so the token lacks both claims and is refused. Nothing is logged.

`WebAuthnSessionNotesAuthenticatorFactory extends WebAuthnAuthenticatorFactory` and changes
only the id (`intake-webauthn-session-notes`), the display name and the help text. It is
registered in `META-INF/services/org.keycloak.authentication.AuthenticatorFactory`.

**The recording.** Run `KC_ADMIN_PASSWORD=… uv run python scripts/keycloak/record_webauthn_login.py
--base-url http://127.0.0.1:18085 --jar-sha256 <jar> --dist-sha256 <dist>`. For each realm it:

1. creates the synthetic `int378-staff` account through the admin API. The account has
   `tenant_clinical_responsible`, which reaches patient content and so needs `hwk`, plus `org`,
   a `tenant` UUID, a password, and a WebAuthn credential. That credential is a fresh P-256 key
   with a random credential id and a random AAGUID, stored as `RepresentationToModel.createCredentials`
   stores any value-less credential;
2. runs the PKCE authorisation-code flow for `admin-web` through the real login pages: the
   password form, then the WebAuthn page, whose challenge, `rpId` and `userVerification` come
   from the page;
3. answers with an assertion built as WebAuthn §7.2 specifies (the RP id hash, UP and UV flags,
   a counter, and ES256 over `authenticatorData || SHA-256(clientDataJSON)`), and exchanges the
   code;
4. verifies the access token live with the console's `KeycloakClaimsVerifier` (JWKS, issuer,
   `aud=api`, expiry), and runs `principal_from_claims`.

| realm (WebAuthn execution) | `aaguid` / `credential_id` in the token | `amr` | console |
|---|---|---|---|
| `intake-dev` (`intake-webauthn-session-notes`) | equal to the software authenticator's AAGUID and base64url credential id | `["pwd","hwk"]` | **admitted**, `tenant_clinical_responsible`, tenant = the account's |
| `intake-dev-stock` (`webauthn-authenticator`) | absent | `["pwd","hwk"]` | **refused**: `MalformedClaims: claim 'aaguid' is absent or not id-shaped` |

The two tokens' claim sets differ by exactly `{aaguid, credential_id}`. The same run also shows
INT-365's `amr` and INT-373's `aud`, `org` and `tenant` coming from a real Keycloak.

The recording holds the decoded claims and the console outcome, not the compact JWT. Its values
are synthetic ids: the account name, a `.invalid` mail address, and random UUIDs. The test
re-signs the recorded claims with its own key, so no Keycloak key is committed.

**Why not in CI's check-integration.** That lane boots `infra/docker-compose.dev.yml`, which has
no Keycloak. The obs compose has one, and CI never boots it (Makefile, INT-023). The software
authenticator needs no browser, so a CI lane could run this same script against the 26.1.4
distribution. That is a new CI surface, a download of about 148 MB per run, and is not added
here. The recording is clause 2's "recorded output". It must be redone whenever the jar pin
changes, and the test enforces that through `provider_jar_sha256`.

## Findings for the owner

1. **Decide clause 3**, (a) or (b). Until then a TOTP sign-in is refused, and so is a WebAuthn
   one on any Keycloak without the provider.
2. **Deploy the provider** (runbook §3):
   - `make keycloak-provider` on the deployed commit;
   - the jar in `/opt/keycloak/providers/`;
   - `kc.sh build`;
   - swap the realm's WebAuthn execution, keeping `amr hwk`;
   - one real sign-in to confirm.
3. **Some credential ids are refused by the console's id shape.** An unpadded base64url id
   starts with `-` or `_` for 2 in 64 random ids, and an id longer than 96 bytes encodes to more
   than 128 characters. `_ID_SHAPE` (`[A-Za-z0-9][A-Za-z0-9._:/@-]{0,127}`) refuses both, so
   that staff member is refused until the key is re-registered. The recorder draws ids until
   one is id-shaped, and says so. This is outside this issue; the verifier is unchanged.
4. **PR #598's realm does not import on a real Keycloak** (the 271-character description). This
   PR fixes it. #598 on its own still carries the defect.
