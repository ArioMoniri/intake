## What was built

**`src/lib/dsar/requests.ts`** — the request model. Closed sets for `kind` and
`status`; the grace instant is read, never re-derived from a duration on the
phone; `overdue` is the server's verdict and an unreadable flag is a refusal
to parse rather than a quiet `false`, because "we are not late" is exactly the
claim a reader must not invent.

**`src/lib/dsar/api.ts`** — `POST /export`, `POST /delete`,
`DELETE /delete/{id}`, `GET /requests`. A refusal or an unreachable server
resolves to `null`; no server narrative reaches the patient (02 §8.2).

**`src/lib/dsar/store.ts`** — the working copy, in memory only, with **no
optimistic writes**. Everywhere else in this app optimism is the kinder
choice; here it is the dangerous one — a patient told their erasure is
scheduled stops asking, so a filing that never left the phone would produce
exactly that silence. A write either lands or the state is unchanged and
`unsent` says so.

**`src/lib/learned/facts.ts`** — the ledger view. Two boundaries live in the
type: `source` is the closed three-member CONFIRMED vocabulary shared with
`clinical_schemas.overlay.LearnedFactSource`, so a row arriving with an
unconfirmed provenance is dropped rather than hedged (invariant 12); and a
held value becomes patient copy only when it already is a phrase the patient
said, so a bare `true` or `12` takes a catalogue label instead of being
printed as a sentence (invariant 22).

**`src/lib/learned/api.ts` / `store.ts`** — `GET`, per-field `PATCH`,
`DELETE`. A record fact is not removed from the screen until the record has
removed it, and a scope is not shown turned until the record has turned it. A
device-held fact — one this device carried out of an earlier visit (INT-247) —
exists in one place, so removing it removes it and no server is asked.

**`(tabs)/me/data.tsx`** ("Verileriniz") and **`components/LearnedLedger.tsx`**
— design pass 5's Oura settings anatomy, unchanged: group headers outside the
groups, 56 pt rows with hairlines between, tonal state pills, the honest
explanation as the group's footer. No new primitive, no new colour, no new
type role. Erasure and per-fact deletion are both two-step: the first tap
changes the word, the second acts.

## What is not met, and who owns it

**The export ANSWER is not delivered in the app, and the client deliberately
never calls `GET /v1/me/dsar/export/{id}`.** `e2e/me.spec.ts` asserts the
absence over the whole tree, because the absence is the control.

Three facts make the call wrong today rather than merely unimplemented:

1. That route MARKS the KVKK m.13 obligation completed at the moment of
   delivery (`row.status = COMPLETED` in `dsar/router.py`). Calling it without
   handing the patient anything would record an answer nobody received —
   worse than a visibly open request.
2. It cannot succeed anyway: the document renders only from the fixed strings
   in `docs/legal/strings.yaml` with hash binding (invariant 18), the file
   does not exist, and the route answers `503 legal_strings_missing`.
   **Owner: INT-210** (`status: todo`, `approval:human-legal`).
3. The app has no path that hands a file to a patient. Building one is a
   security decision — writing an export of the whole record to device storage
   and out through a share sheet needs its own files/10 §9 row and its own
   threat review — and a dependency (`expo-sharing`) that needs the
   licence-auditor. Neither belongs inside this issue.

So the screen files the request, shows it in the tracker with the date the
answer is due, and says plainly that the copy cannot be downloaded in the app
yet. It states no right, no period and no obligation of its own: the m.11
notice is INT-210's, rendered from the legal tree.

`INT-140` therefore stays `status: todo`. The erasure half and the learned-fact
half are complete; the export half is filed-and-tracked but not answered, and
the remaining step is one unit of work that cannot exist before INT-210.

## Two things refused, with the reason

**Re-confirmation is shown and not answered here.** files/09 §3's twelve-month
rule is surfaced per fact, and the footer says the question is asked during
visit preparation. Answering it from the ledger would mean posting a
confirmation, and `POST /v1/me/learned` needs the `origin`, `origin_ref` and
`observed_at` of the candidate behind the fact — none of which `GET` returns.
Inventing any of them would be minting a provenance, which is precisely what
invariant 12 exists to prevent. `e2e/me.spec.ts` asserts the client has no
`POST`.

**A learned fact's VALUE is not rewritten.** KVKK m.11(d) rectification exists
on the server as an addendum (`POST /v1/me/dsar/rectify`), and its
`target_ref` admits `note`, `visit` and `document` — not an overlay key. A
patient correcting a learned fact deletes it and states the current fact in
the visit that asks; that is the path files/09 §3 describes, and widening the
server's target vocabulary is INT-037's decision, not a mobile one. The
tracker still renders a rectification row if one exists, so a correction filed
elsewhere is visible here.

## One product finding, flagged not fixed

**Overlay keys have no patient-readable label anywhere in the repo.** A record
fact is identified by a slot ref (`chronic.hipertansiyon`), and nothing maps
that ref to Turkish. The ledger therefore renders the fact's own recorded
phrase where the value is one, and a catalogue label
(`learned.value.unreadable`) where it is not — never the ref itself, which is
machine text and not B1 Turkish. Every other promise of files/09 §3 is kept
for those rows: provenance, where it is held, the share scope and the delete
control. Authoring the label vocabulary is clinical copy against the protocol
packs' slot definitions, so it belongs with the pack owners rather than in a
mobile issue. Recorded here for the clinical copy owner.
