## Bottom line

- The test measured the runner, not the property. One cold `POST
  /v1/triage/evaluate` through the in-process TestClient read 620 ms on
  main's own run and 350 ms on #963's, 40 ms on a laptop, and 200 ms on the
  same laptop with one competing CPU-bound thread in the process. None of
  those numbers says whether the RED waited on the Safety-inbox store, which
  is what invariants 9 and 21 forbid and what the test exists to prove.
- The test now holds the store instead of timing the request: every write
  waits at a gate only the test opens. The RED coming back while the gate is
  closed is a fact of ordering — nothing had been written, so nothing was
  waited on — and holds whatever the runner's load. A near-miss test sends
  the same RED through an outbox that writes the store itself: it reaches
  the store and is held there, and comes back only once the test opens the
  gate.
- Three other wall-clock budgets are asserted in tests/api and tests/voice
  (§4). They are listed with a recommendation each and left as they are:
  one issue per PR.

## 2. The fix (test only)

`tests/api/test_red_notify.py`:

- `_HeldStore` — a `RedisSafetyInboxStore` over fakeredis whose `add` sets
  `entered` and then waits on `opened`, an event only the test sets.
  `open()` lets the held writes through; `open(refusing=True)` has them
  refused the way a down store refuses (`SafetyInboxUnavailable`, so the
  pump keeps the entry pending). A write held for `HELD_S` (30 s) gives up,
  counted in `gave_up`: that is a hang guard so that a RED which *did* wait
  comes back and fails the test instead of hanging the shard; no assertion
  reads a clock.
- `test_the_red_never_waits_on_the_inbox_store` — the RED is evaluated with
  the gate closed. Back, the test asserts the kind, `gave_up == 0`, the gate
  still closed and the store empty: the write could not have completed, so
  the response did not wait on it. The entry is pending in the outbox with
  the RED's own instant (`T0`); the pump brings it to the store
  (`entered`, a liveness wait on an event, 10 s); the gate is then opened
  refusing, and at shutdown the unwritten entry is counted, never named —
  the original test's shutdown property, unchanged.
- `test_near_miss_a_red_that_writes_the_store_itself_is_held_with_the_write`
  — after a GREEN warm-up, the state's outbox is replaced by
  `_WaitingOutbox(store)` and the RED is sent on a thread. It reaches the
  store (`entered`) and is not back while the gate is closed; the gate
  opens, it comes back as `red_trigger`, and the entry is in the store. The
  observation the main test makes is impossible for a RED that waits.
- Removed: `RED_BUDGET_MS` (the 300 ms RED budget is measured on the
  runtime's fake clock, INT-531), `_down_store`, `_pending_eventually` (a
  poll with sleeps; the entry is pending deterministically at response
  time) and the `time` import. The file has no wall-clock threshold left.

Against d5f1907b (#963): that rewrite kept a ratio (`elapsed < STALL_S / 2`,
i.e. 750 ms) measured on the wall clock after a warm GREEN. It is lifted in
spirit (a store that does not answer; the warm GREEN in the near miss) and
replaced by the ordering, so nothing is timed.

## 4. Sweep: wall-clock budgets asserted in tests/api and tests/voice

Method: `grep -rn "perf_counter\|time\.monotonic\|time\.time()\|process_time"`
over both trees, then every `budget`, `elapsed`, `_MS` and `deadline`
assertion checked for which clock it reads. Only this test is changed in this
PR.

| test | what it asserts, on the real clock | recommendation |
|---|---|---|
| `tests/api/test_red_notify.py::test_the_red_never_waits_on_the_inbox_store` | one cold request `< 300 ms` | fixed here (§2) |
| `tests/api/test_triage_hop.py::test_answer_to_trigger_is_inside_the_red_budget` (line 305) | p95 of 50 warm `/v1/triage/evaluate` round trips `< RED_BUDGET_MS` (300 ms) | Same hazard, softer: it needs 3 of 50 warm requests over 300 ms, and §1.2 shows one competing thread quintuples a request. The 300 ms answer-to-trigger budget (files/02 §8.2) is already measured on the runtime's fake clock (INT-531, `tests/voice/test_red_between_turns.py`) and belongs in the latency harness (`make runtime-sim`). Keep the test as a structural guard of the hop (no store, audit or network await before the answer — this PR proves the store half) and record the 50-request measurement in docs/evidence with a named machine; if a bound must stay, assert it on `time.thread_time()` (the request's CPU time), which a loaded runner cannot inflate. |
| `tests/voice/test_policyguard_latency.py::test_every_sentence_is_inspected_inside_the_budget` (line 58) | hard maximum over 320 `inspect_sentence` calls `<= POLICY_GUARD_BUDGET_MS` (20 ms); reported at 22.8 ms on a loaded runner (#967) | A maximum over 320 samples on a shared runner reads the scheduler: one preemption of 20 ms fails it with the guard's own work untouched. Measure the guard's work with `time.thread_time()` for the `<= 20 ms` assertion (CPU time of the thread, not inflated by preemption) and keep the wall-clock maximum as a recorded measurement in docs/evidence with a named machine; or assert a high quantile (p99 of 320) rather than the maximum. The 20 ms line itself (files/03 §4.2) is kept. |
| `tests/voice/test_policyguard_latency.py::test_the_filter_reports_the_time_it_spent` (line 84) | one `filter` call's `verdict.elapsed_ms <= 40 ms` (`POLICY_GUARD_BUDGET_MS * MAX_SENTENCES_PER_TURN`), measured by `policy_guard.py` with `perf_counter` | One sample on the wall clock.
