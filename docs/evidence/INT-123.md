## 1. The model: files/03 §4.9.1 names none, so nothing is pinned

§4.9 is canonical: *"a model that is not in §4.9.1 is not pinned"*. The table has 21 rows.
None is a record or text embedder. Row 18 (`speechbrain/spkrec-ecapa-voxceleb`) is an
embedding model, but a **speaker** embedding. Invariant 15 makes it ephemeral, in-memory
and never persisted, so it is the one row this index must never use.

Choosing a model is not an agent's call. Invariant 19 defines a pin: open weights,
commercially usable, the licence read from the raw LICENSE blob and recorded with
`licence_verified_at`, and weights pinned by `model_id@revision + sha256`. §4.9.0 says
which licences pass. So nothing was added to `observability/registry.yaml`, and no model
ran anywhere, on the laptop or elsewhere.

What ships instead:

- `intake_platform.records.embedding.RECORD_EMBEDDING_ROW = None`.
- `default_record_embedder()` returns `NoEmbeddingModel`. Every member of it
  (`embed`, `model_ref`, `dimensions`) raises `EmbeddingModelUnregistered`, whose message
  names the ask and none of the text it was given.
- `pinned_model_ref()` refuses any embedder that does not name `org/model@<commit>` and a
  positive dimension.
- `embed_checked()` refuses a wrong count, a wrong dimension or a non-finite value.
- `test_the_canonical_table_is_read_and_names_no_record_embedder` parses the §4.9.1 table.
  It fails the day a record-embedding row appears, so the fail-closed default cannot
  outlive the decision.
  - A near-miss control plants such a row and checks it is detected.
  - Row 18 is asserted to be *seen* and excluded, so the scan cannot pass by reading
    nothing.
- There is no fallback to another model or a vendor endpoint. On the PHI path that would
  be the invariant-19 defect, so the absence of one is the control.

## 2. The table and its RLS (migration `0014_int123`, one head)

`uv run alembic heads` → `0014_int123 (head)`, revising `0013_previsit_output`. No open PR
adds a migration.

`record_embeddings` holds:

- a vector;
- the source box: `document_ref`, `page`, `bbox`, `char_start`, `char_end`;
- `kind`, the derived `item_ref`, `model_ref` and `dimensions`;
- `consent_scope_ref`.

It never holds the item's text. The confirmed item is the source of truth, and the note
cites it from there. A second copy of the line would be one more place to erase, and one
more plaintext column that only RLS would protect.

- **Two policies, and the second is RESTRICTIVE.**
  - `record_embeddings_tenant_isolation` is the PERMISSIVE `app.tenant_id` policy that every
    tenant-scoped table carries.
  - `record_embeddings_patient_namespace` is **AS RESTRICTIVE** on `app.patient_id`, in
    USING and WITH CHECK.
  - Postgres ORs permissive policies together. A second permissive policy would therefore
    let every patient in a tenant read every other patient's vectors. As a restrictive
    policy it is ANDed instead.
  - An unset GUC reads as NULL through `NULLIF` and selects nothing.
- **Enabled and FORCED.** The owner gets no bypass.
- **Least privilege.**
  - `app_rw` gets SELECT, INSERT and DELETE. There is no UPDATE: a vector is replaced by a
    delete and an insert, never edited in place.
  - `clinician_ro` gets nothing, and nor does PUBLIC.
- **Dimension per row.** `embedding` is `vector` with no typmod, since no model declares a
  dimension. `CHECK (vector_dims(embedding) = dimensions)` binds each row to its own
  model's declaration.
  - Reads are an exact cosine scan of one patient's rows, and there is no ANN index. A
    namespace holds a few hundred rows, and approximate recall is a defect in a clinical
    citation.
- **The policy is asserted from metadata.**
  - `RecordEmbedding.__table__.info["rls_namespace"]` declares
    `(("tenant_id", "app.tenant_id"), ("patient_id", "app.patient_id"))`.
  - `namespace_breaches()` renders each predicate from it and checks that the migration
    spells it both ways, with RLS enabled and forced.
  - Near-miss controls, each named exactly:
    - a PERMISSIVE patient policy;
    - a patient policy without WITH CHECK;
    - an unforced table;
    - a widened namespace the migration does not scope.
- The column type is `intake_platform.db.vector.Vector`, about 40 lines, with no new
  dependency. The pgvector Python package would have added a licence review for a text
  codec.
- Invariant 18: every column carries `{category, purpose, basis, retention, recipients}`.
  - The vector and `kind` are `special_category_health`.
  - The retention is `RET_RECORD`.
  - The recipients are internal only.
  - The basis is the `documents` consent.
  - This is the files/03 §10 index the blueprint already names, derived from data the
    record clock already covers. It is not a new category of personal data.

## 3. Consent scope (invariant 4)

- The purpose is files/06 §2's `documents`, the scope an uploaded document is processed
  under.
- `records_consent()` reads the decision with `consent_state`, the same question the API's
  consent guard asks. A stale, withdrawn or absent grant does not stand.
- `RecordsConsent` refuses a decision for any other scope, so a `core` grant cannot open
  the index.
- `RecordIndexQueue.enqueue` records a `REFUSED` receipt and holds nothing when the
  decision does not stand.
- `RecordRetriever.retrieve` raises `RecordsConsentRefused` before the query reaches any
  model. The message names the scope and nothing else.
- One patient's consent opens only that patient's namespace. The store is always asked
  for the consent's own namespace.

## 4. Confirmed items only, through the queue

- `ConfirmedRecordStore(on_admit=…)` calls the hook *after* admission, with the confirmed
  type it has just checked. The index binds its queue there, with the patient's consent, so
  that is the only door into the index.
  - An unconfirmed item still raises at `admit` and never reaches the hook.
  - A declined card is never confirmed, so it is never admitted or embedded.
- `RecordIndexQueue` takes the queue's shape from the Backend Work queue.
  - `enqueue` returns at once.
  - `run_pending` is the pump that the (not yet existing) workers service wraps, on the
    `process_quarantined_document` precedent.
  - Each item leaves a receipt: an id, a closed state and an error class name. A refusal
    is a receipt, not a crash.
- What is embedded is exactly the confirmed `summary`, verbatim.
- The item id `ri_<sha256[:32]>` is derived from the box and the kind, never minted. A
  re-confirmation is therefore one row (the files/12 §7.5 reasoning for `work_id`).
- A source box that is not `doc:<documents.id>` is refused (`UnaddressableDocumentRef`).
  Such a row would be out of the retention executor's reach.

## 5. The retrieval Work and the citations

- `WorkType.RETRIEVE_RECORDS` is files/03 §4.3's `retrieve_records(query)`. It runs in the
  **background** lane (files/12 §7.4).
  - It takes a `ReadOnlyContext` and returns a `BackgroundEffect`, which cannot express a
    slot write or a triage level.
  - It speaks nothing.
  - The rail shows the existing `reading_document` label, so no new patient-visible string
    was added.
- `RetrieveRecordsHandler` follows `extract_slots`' shape.
  1. It takes the query from the session vault by `input_hash`, so the queue holds no text.
  2. It retrieves.
  3. It keeps the citations, once per item id.
  4. It returns an empty effect.
  - A refusal becomes a failed receipt naming the class: `RecordsConsentRefused`,
    `EmbeddingModelUnregistered` or `TranscriptNotHeld`.
  - A cancelled Work keeps nothing.
- The composition root does **not** register it. With no model there is no retriever to
  build, so `UnregisteredWorkType` at submit is the fail-closed state, on the
  `parse_document` precedent. `register_retrieve_records()` is the one call a root makes
  once the row exists.
- `RecordRetriever` resolves every hit against `ConfirmedRecordStore.admitted`.
  - A hit whose item is no longer confirmed goes into `Retrieval.uncited` by id. It is
    never cited from the vector alone.
  - A hit whose stored box disagrees with the item raises `IndexProvenanceMismatch`.
- `cite_records()` turns each citation into `Sourced[ImportedObjectiveItem]`.
  - The attribution is `RECORD`.
  - The span is `SourceSpan.document(document_ref, page, bbox, item_ref)`. `item_ref` is
    a new optional field, id-shaped by regex, and appended to the locator only when set,
    so every existing locator is unchanged.
  - A citation of a kind with no `imported_objective` shape (medication, diagnosis,
    allergy) is returned in `not_filed` with its id and kind. Filling another section's
    fields would be the composer inventing a clinical claim (the INT-084 blockers).
- The INT-385 guard forbids any `services/voice-runtime/src` module to import
  `intake_platform.records`, which keeps the screen number renderer off the speech path.
  It is kept, not weakened. The voice side states what it consumes as protocols over
  `clinical_schemas` types (`RecordCitationLike`, `RecordRetrievalLike`), and the platform
  objects satisfy them structurally.

## 6. Erasure removes vectors

- **DSAR erasure** (`intake_api.dsar.shred._erase_subject`) calls
  `erase_record_index()`, which deletes the subject's rows. On postgres it first sets
  `app.patient_id` for the transaction.
  - Without that step the RESTRICTIVE policy turns the DELETE into a silent no-op under a
    non-owner role.
  - `test_an_erasure_that_forgets_the_patient_guc_deletes_nothing` shows that on postgres:
    `(0, 1)`.
- **Retention executor** (`clinical_record`, per session tree): it deletes the rows whose
  `document_ref` names a document it destroys, before the document rows go.
- **The contract, SQLite with foreign keys ON** (the INT-392 lane):
  - the DSAR erasure leaves only the other patient's vector;
  - the executor leaves the vectors of kept documents;
  - `record_embeddings.patient_id` keeps NO ACTION, so a path that forgot the vectors
    fails, and a test deletes the patient row first to prove it.
- **The INT-392/393 erasure contract, extended.** Both #648 and #653 merged into `main`
  during this iteration, and `main` was merged into this branch twice.
  `tests/data/test_session_delete_contract.py` walks every table reachable from `patients`
  and now declares:
  - `record_embeddings` → `ERASED`;
  - `record_embeddings.patient_id` → `PARENT_KEPT`.

  Its seed carries a vector on the destroyed session's document. The DSAR behaviour test
  checks the vector is erased with every other `ERASED` table. The vector table has no key
  to `sessions`, so the retention test names it explicitly. The `executors.py` conflict
  with #648 was resolved by keeping both sides in dependency order: previsit output, then
  vectors, then documents, then Doctor Links and shares.

## 9. What is not done, and who owns it

- **An embedding model** (clause 1): the owner, via a files/03 §4.9.1 row. The ask is in
  docs/backlog/blockers.md, and the HB id is for the coordinator to allocate. Until it
  lands, every index receipt is `failed: EmbeddingModelUnregistered` and
  `retrieve_records` is unregistered.
- **Withdrawal of `documents`** does not yet purge the index. The retriever and the queue
  both refuse on a withdrawn decision, so nothing is read or written, but the rows stay
  until the DSAR erasure or the record clock removes them. Purging on withdrawal changes
  the withdrawal-cascade contract (files/06 §2.2), which belongs to a consent issue, not
  this one.
- **The DSAR export** does not include vectors. It exports the confirmed record the
  vectors are derived from, and a vector is not intelligible to its subject.
