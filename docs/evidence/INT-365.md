## What Keycloak actually emits (the claim this rests on)

| fact | source |
|---|---|
| `amr` comes only from the `oidc-amr-mapper` protocol mapper. It lists the reference value configured on each authenticator execution the user completed. | Server Administration Guide, "Authentication flows" → "Creating a flow": https://www.keycloak.org/docs/latest/server_admin/index.html#_authentication-flows. keycloak.org publishes no per-patch copy, so the pinned text is https://github.com/keycloak/keycloak/blob/26.1.4/docs/documentation/server_admin/topics/authentication/flows.adoc, lines 114–115. See also `services/.../oidc/mappers/AmrProtocolMapper.java` |
| **No authenticator has a default value.** An execution without `default.reference.value` in its config contributes nothing. | `services/.../oidc/utils/AmrUtils.java` (`getAuthenticationExecutionReferences`), key names in `server-spi-private/.../models/Constants.java` |
| `default.reference.maxAge` defaults to `"0"`. A value is dropped once `authTime + maxAge` is in the past, so with no max age the claim is empty a second after login. | `AmrUtils.isAmrValid` |
| No default client scope in 26.1.4 carries the AMR mapper. The `acr` scope carries `acr loa level`, and `basic` carries `sub` and `auth_time`. The mapper must be added to the client. | `services/.../oidc/OIDCLoginProtocolFactory.java` |
| An execution is recorded as completed only on `SUCCESS`. A `SETUP_REQUIRED` enrolment pass therefore does not put its factor in `amr`. | `services/.../authentication/DefaultAuthenticationFlow.java` (`processResult`) |
| An ALTERNATIVE execution without a registered credential throws `CREDENTIAL_SETUP_REQUIRED`. Only a REQUIRED one can trigger in-flow enrolment. | `DefaultAuthenticationFlow.processSingleFlowExecutionModel` |
| Importing a realm with custom `authenticationFlows` still creates every built-in flow (`migrateFlows`), so naming only `browserFlow` leaves direct grant, reset credentials, client auth and the rest intact. | `model/storage-private/.../DefaultExportImportManager.java` (`importAuthenticationFlows`), `server-spi-private/.../DefaultAuthenticationFlows.java` |
| Without the step-up LoA flow, `acr` is `"1"` for a fresh login and `"0"` for an SSO-cookie one. It records when the login happened, not how. | `AcrProtocolMapper`; Server Administration Guide, "Creating a browser login flow with step-up mechanism": https://www.keycloak.org/docs/latest/server_admin/index.html#_step-up-flow |
| The value names are RFC 8176's. `pwd` is a password. `otp` is a one-time password. `hwk` is proof of possession of a hardware-secured key. | https://www.rfc-editor.org/rfc/rfc8176.html |
| RFC 9470's answer to a token without enough authentication is 401 with `error="insufficient_user_authentication"` in the `WWW-Authenticate` challenge. | https://www.rfc-editor.org/rfc/rfc9470.html |

Consequences for the design:

- the realm must tag its executions and add the mapper, or `amr` never appears;
- the tags need a max age;
- `acr` cannot be the evidence.

### The rule

A token reaches the console only if its `amr` is a JSON array of strings containing `pwd` and one
of the accepted second factors. Values are compared exactly and case-sensitively. A bare string
is refused, not split. A list with a non-string member is refused, not filtered. `acr` is never
read. A refusal is the 401 above. It has one body for "no second factor" and "not WebAuthn", so
the answer does not reveal whether the account reaches patient content.

### The realm

- **Browser flow** `staff browser`:
  - `auth-cookie` ALTERNATIVE, or the subflow `staff browser forms` ALTERNATIVE.
  - `staff browser forms` is `auth-username-password-form` REQUIRED (`amr pwd`), then the subflow
    `staff second factor` REQUIRED.
  - `staff second factor` is `webauthn-authenticator` ALTERNATIVE (`amr hwk`) or `auth-otp-form`
    ALTERNATIVE (`amr otp`).
- **OTP policy:** TOTP, HmacSHA1, 6 digits, 30 s, look-ahead 1, code not reusable. SHA-1 is
  RFC 6238's default and the only algorithm every common authenticator app implements. HMAC-SHA-1
  is not weakened by SHA-1 collisions.
- **WebAuthn policy:** ES256 and RS256, user verification `required`, relying-party name `intake`.
  The relying-party id is empty, which means the realm's host. Attestation, attachment, resident
  key and acceptable AAGUIDs are left unspecified. They choose which authenticator models staff
  may use, and that is the owner's decision.
- **Mapper:** `oidc-amr-mapper` on `admin-web`, emitted into the access, ID and introspection
  tokens.
- **Session bounds** (files/08 §2.3):

  | setting | value |
  |---|---|
  | `ssoSessionMaxLifespan` | 28800 |
  | `ssoSessionIdleTimeout` | 1800 |
  | `clientSessionMaxLifespan` | 28800 |
  | `clientSessionIdleTimeout` | 1800 |
  | `offlineSessionMaxLifespanEnabled` | true |
  | `offlineSessionMaxLifespan` | 28800 |
  | `offlineSessionIdleTimeout` | 1800 |
  | `rememberMe` | false |

  The bounds are realm-wide, so every session that can reach patient data has the 30-minute idle
  timeout. The `offline_access` role would otherwise grant sessions of 30 days.
- **`amr` max age** is 28800, equal to the session bound. The references therefore stay valid for
  the whole session and lapse with it, and a token refreshed after 8 h reaches the API with no
  `pwd`/`hwk` and is refused there too.

## For the owner

1. **The live realm.** The committed realm is the laptop fixture ("never seed any deployed
   environment from this file"). A deployed Keycloak needs the same four things: the two
   policies, the three-flow browser binding, the AMR mapper on the console client, and the
   session values. Until it has them, its tokens carry no `amr` and the console refuses every
   one of them. That is the fail-closed direction, and it is intended.
2. **Staff enrolment.** The second factor is an ALTERNATIVE, and Keycloak refuses an ALTERNATIVE
   for an account with no credential. So every staff account needs a registered factor before its
   first console login:
   - a **WebAuthn authenticator** for the six patient-content roles;
   - TOTP or WebAuthn for the rest.

   The path is an admin-sent required action (`webauthn-register` or `CONFIGURE_TOTP`, via
   "execute actions" e-mail, which needs realm SMTP). Which authenticator models are acceptable
   (attestation and AAGUID list) is the owner's call.
3. **Seen, not fixed, and outside this issue.** The console also reads `aud=api`, `org`, `tenant`,
   `aaguid` and `credential_id`. The committed realm has no mapper for any of them, so a real
   dev-realm token would be refused as malformed even with a good `amr`.
4. files/08 §2.3 also requires WebAuthn for anything touching a protocol pack, the device flag,
   the study assertion, connector endpoints or audit configuration. Those are actions, which
   §2.3's step-up rule governs with a fresh assertion at the moment of the action. The acceptance
   scopes this token check to the roles that reach patient content, so `qms_owner`,
   `platform_admin`, `tenant_admin` and `sre_oncall` may enter with TOTP.
5. **Backlog.** PR #590 is not on main, so `docs/backlog/issues.yaml` and files/11 are untouched.
