## What was built

**Withheld, not refused.** A refusal is now one of three kinds, decided by
`AuthStore.otp_request_decision`:

| kind | budgets | answer |
|---|---|---|
| the platform's | tenant, global hour, global day (INT-577), the kill switch | 429 `otp_limited` / 503 `otp_delivery_unavailable`, as before: the same for every number |
| the caller's | address, device | 429 `otp_limited` with the caller's true wait: the same for every number |
| **the number's** (`NUMBER_DIMENSIONS`: its resend wait, its hourly budget) and the number facts the service passes as `withhold` (the INT-578 lockout, the synthetic host's test list) | — | **withheld**: the 202 an admission gets, and nothing minted or sent |

A withheld request:

- spends the caller's address and device budgets exactly as an admission does, so the caller's
  next answer cannot tell the two apart either;
- runs the same Redis commands as an admission, the number's, tenant and global writes going to a
  key that expires in a second (`auth:otp:decoy:*`), and the code store's writes too
  (`AuthStore.withhold_code`);
- mints an id, a code and its HMAC digest, and appends one audit row (`auth.otp.withheld`, beside
  an admission's `auth.otp.requested`), so its work and its time are an admission's;
- answers `{request_id, resend_after_s}`, with a fresh random request id and a wait read from the
  caller's own **device** history (`resend_wait(device admissions + 1)`). For a patient asking for
  their own number, the device history and the number's history are the same, so the app shows
  the true doubled wait. For anyone else, the wait says nothing about the number.

**The vendor left the response path.** `OtpAuthService._dispatch` starts the send as a tracked
task after the code is stored and the request audited. The route answers before the vendor does.
The 202 therefore carries no vendor job id (`delivery_id` is gone; the app never read it). The task
appends `auth.otp.sent` with the job id, or `auth.otp.delivery_failed`. The adapters still log and
count their own outcome (`otp_sms_delivery_total`). `settle()` waits for the tasks in flight: the
test harnesses call it, and the API's lifespan calls it at shutdown with a 10 s bound, so a code a
patient was answered 202 for is still sent. A vendor refusal can no longer be read off the route.
That mattered: Netgsm refuses an unreachable number with its own codes (50-52), so the old 503
told a stranger which numbers were live.

**Verify does the same work.** `check_code` runs both constant-time comparisons and takes one
attempt whether or not a code exists, has expired, is bound to another device or the number is
locked; an expired record is no longer deleted on the spot (its key's own expiry does that).
`verify_code` runs `check_code` under a lockout too, then refuses as `locked`. A wrong guess, a
number that never had a code, an expired code and a locked number all cost `GET` (lock), `GET`
(code), `ZREMRANGEBYSCORE`, `ZADD`, `EXPIRE`, `ZCARD`, and all answer `401 otp_invalid`.

As first built the attempt was an `INCR` on a per-code counter. INT-578's review fix (B1, 28 Oct
2026) made the budget the number's, over a rolling hour, spent only by the bound device, and this
branch took it on in the merge: only the bound device's guess on a live code, and not under a
lockout (`check_code(charge=False)`), joins the number's window (`auth:otp:miss:<pseudonym>`).
Every other attempt runs the same four commands against `auth:otp:stray:<binding>`, a window that
decides nothing, so the work stays identical. The lockout half matters on its own: guesses during
a lockout used to land in a counter that the next code reset; in the number's window they would
outlive the lockout and refuse the right code after it ended.
`test_guesses_under_the_lockout_do_not_outlive_it` pins that, and fails (`401 == 200`) with
`charge=True`.

**What still differs, and why it is no oracle.** A malformed number (422: the shape is public); the
carrier check's unallocated prefix (422: a fact of the numbering plan, the same for every
subscriber in it; it still sits after the gate, so probing costs budget); the caller's own address
or device budget (429: the same whatever number it asks for, pinned for two numbers); the
platform's caps and switch (429/503: the same for everyone).

**What it costs a patient.** A resend asked for inside the number's wait, or past its 3-an-hour
budget, is answered as sent and sends nothing, and the app takes the decoy's request id as the
live one. A patient who follows the countdown the app shows never meets this: the countdown is the
number's wait for them. The previous 429 told such a patient to wait; that message is exactly what
told a stranger the number was in use.

## The timing test, and why it can be trusted on a shared runner

No duration is asserted against a budget. With a vendor that takes 50 ms, 25 sent and 25 withheld
requests are timed alternately (so drift in the runner's load falls on both). The medians are
compared with a ratio bound of 3. The old path fails it at about 15. Two samples of the same work
do not approach it: the test passed alone, three times in a row, and twice under six
CPU-burning processes. The deterministic half (`CommandTrace`) does not depend on any clock at
all. It holds that a withheld request runs the same Redis commands, in the same counts, as a sent
one, and that each writes one audit row; for verify, that a wrong, missing, locked and expired
code cost the same commands.

## Security review fix (28 Oct 2026): a failed send is not silent

The orchestrator's review found one blocker here (B3). With the vendor called after the 202, a
send that Netgsm refused or that never reached it showed nowhere a person would look: the patient
was told the code was sent, the route was green, and only the `auth.otp.delivery_failed` audit row
and the adapter's counter recorded it.

**The alert.** `OtpSmsDeliveryFailing` in `infra/observability/security-rules.yaml` (group
`sms-abuse`, severity page): over half the last 30 minutes' `otp_sms_delivery_total` not
`accepted`, and at least 3 refused, held 5 minutes. The floor keeps one number Netgsm will not
reach from paging at night. The 50 %, 30 minutes and 3 are engineering defaults. Runbook:
`docs/runbooks/sms-abuse.md`, "OTP SMS is not being delivered", which splits the refusal by
`outcome` and says who acts on each (the Netgsm account, the egress path, a changed answer
shape, unreachable numbers).

**Why a rule and not an SLO in `docs/slo/`.** The review asked for the alert in
`infra/observability` and `docs/slo`. An SLO was built first and taken out. In `docs/slo/api.yaml`
it makes the api's SLO file no longer HTTP-only, and the generated api dashboard loses its golden
signals (`tests/observability/test_slo_generator.py::test_http_services_get_all_four_golden_signals`
failed). In a file of its own it adds reliability-console queries, whose recorded answers and the
three `apps/admin-web/e2e/fixtures/reliability*.payload.json` files would have to be re-recorded:
the admin console's files, which this stack touches only through the API. The rule gives the same
page and the same runbook. If an error budget is wanted on top, it is a follow-up for after the
admin console lands.

**The catalog.** `sec_otp_requests_total` now describes `withheld` and `not_listed` (and that
`locked` answers 202 since this issue), and `otp_sms_delivery_total` says it is the only place a
failed send shows and names the alert.

## Legal review fixes (30 Oct 2026)

**B1: a stranger's number ref kept ten years.** A request for a number off the synthetic
host's test list is withheld and appends `auth.otp.withheld`. It was written under
`phone:<log ref>`. The number is a stranger's, typed by a caller, and the audit chain is kept
ten years in WORM storage, which contradicts INT-308 (nothing kept of a number nobody admitted).

exactly one row, so the work stays an admission's. A listed number withheld in its resend wait
is the owner's own and keeps its ref.

containment is carried down verbatim: `_deliver` catches every exception and logs its type only,
appends the audit row outside the handler (so a failed append chains nothing), and every
delivery task has the `_retrieve_by_type` done-callback. The forward merge into INT-581 is a
no-op for this code.
