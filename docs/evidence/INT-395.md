## 1. The defects

INT-393's evidence §11 found two:

- **No path erased `notification_preferences`.** `RET_NOTIFICATION_PREFERENCE` puts the row on
  the files/06 §3 record clock ("patient-deletable, 30-day grace, then crypto-shred"). The DSAR
  erasure did not touch it, and the retention `clinical_record` executor is keyed by session, so
  it cannot reach it. INT-393's contract declared it `kept` with that reason.
- **The DSAR export did not list Doctor Links.** `dsar.store.subject_record` promises one answer
  for export and erasure, and the erasure destroyed Doctor Link rows the export never showed.

The completeness contract below, run against main's declarations (INT-393's `ROWS_ON_ERASURE`
and the tables main's export rendered), names both, plus six more tables the export did not
list. INT-393 §11 had already noticed two of them (previsit outputs, learned facts):

```
notification_preferences is annotated subject-erasable but the erasure keeps it
csat_texts holds the subject's data but the DSAR export does not list it
doctor_links holds the subject's data but the DSAR export does not list it
guardian_links holds the subject's data but the DSAR export does not list it
notification_preferences holds the subject's data but the DSAR export does not list it
overlay_facts holds the subject's data but the DSAR export does not list it
patient_overlays holds the subject's data but the DSAR export does not list it
previsit_outputs holds the subject's data but the DSAR export does not list it
```

The acceptance is "every table holding the patient's personal data appears in the DSAR export",
so all eight are closed here, not only the two the title names.

## 2. The completeness contract, read from the inventory annotations

Invariant 18 already requires every column to carry `{category, purpose, basis, retention,
recipients}`. The contract reads two of those fields; it keeps no hand-kept table list.

**The two readings** (`packages/intake_platform/src/intake_platform/db/inventory.py`, next to the
constants they read):

- `grants_subject_erasure(retention)`: the clock carries `patient-deletable` (the files/06 §3
  record clock) or `DSAR-erasable` (the satisfaction row). Today that is exactly `RET_RECORD`,
  `RET_NOTIFICATION_PREFERENCE`, `RET_PREVISIT_OUTPUT` and `RET_SATISFACTION`, and a test pins
  that set. Rewording a clock out of the marker, or adding a new erasable clock, fails there, so
  a table cannot leave the erasure because of how a string was phrased.
- `holds_subject_data(annotation)`: the category describes the subject (`pseudonymised_identity`,
  `special_category_health`, `consent_record`, `guardianship_link`), or the clock is
  subject-erasable. The second clause exists because a row the subject may destroy is a row the
  subject may also see. The two categories left out, `operational_metadata` and `audit_trail`,
  describe how the platform runs.

**The rules** (`tests/data/test_session_delete_contract.py`, `completeness_breaches`), over the
erasure graph INT-393 already derives from the foreign keys (17 tables):

1. A table with a subject-erasable column must be declared `ERASED` in `ROWS_ON_ERASURE`. There
   is one pinned exception, `ANCHORED = {"patients"}`: the pseudonym row that the retained
   consent (10 y) and DEST-2017 destruction records name. That is INT-037's decision. The
   annotation still says `RET_RECORD`; see §11.
2. A table with a subject-data column must be declared in `EXPORTED_IN`, which gives the export
   section and the `<ref>:` its line leads with.
3. Every `EXPORTED_IN` table is in the graph, and every section is one the export renders.
4. Every anchor is a subject-erasable table that the erasure keeps.

Today the rules require erasure of 11 tables and export of 15. The only graph tables left out
are `events` (operational, on its own telemetry clock) and `dsar_requests` (operational, on the
consent & audit tier), and the export lists the tracker anyway.

**Near-miss controls** (each asserts the exact breach list):

- a planted `ghost_facts` table, keyed to `patients`, annotated `RET_RECORD` and declared kept, is
  named: "annotated subject-erasable but the erasure keeps it";
- a planted health-category table on a non-erasable clock, missing from `EXPORTED_IN`, is named:
  "holds the subject's data but the DSAR export does not list it". The access right does not
  depend on the erasure right;
- undoing either INT-395 fix (`notification_preferences` back to kept, `doctor_links` out of the
  export) names both;
- a stale export declaration (`tenants`) and an unrendered section (`links`) are named;
- an anchor the annotations do not support (`consents`) is named.

**Behaviour over the full seed.** INT-393's seed already puts a row in every graph table. It now
carries a real envelope wherever the export decrypts: note sections, the rectification's
correction, the learned fact's `{value, confidence}`, and the CSAT comment. The export view built
from it must list every seeded row of every `EXPORTED_IN` table, as `<ref>:<id>` in the declared
section. The two exceptions are the subject, which is the export's header, and a slot, which is
an answer inside its visit's QuestionnaireResponse. Both the FHIR bundle and the PDF are rendered
from that one view.

## 3. The erasure: the notification preference, and one sweep

- **`notification_preferences` is erased.** The row holds a flag and two clock times, with no
  envelope, so there is nothing to shred and deleting the row is the erasure. It is deleted by
  the ids the sweep read, after the learned facts' header and before the slots. It is audited as
  `dsar.delete.notification_preference` against `notification_preference:<id>`, with
  `actor=patient:<id>` and `consent_scope=basis:KVKK-11/13` like every other row the erasure
  names. The access log classifies it as `DATA_REQUEST`, not as a preference change.
- **One sweep for both.** The erasure had its own queries for learned facts (INT-170), previsit
  outputs (INT-392) and Doctor Links (INT-393), so it destroyed rows the export never read. Those
  queries now live in `dsar.store.subject_record`, with the CSAT comments, the preference and the
  guardian links. `shred._erase_subject` reads the same `SubjectRecord` the export reads, so the
  erasure destroys exactly what the export showed, row for row.
- **Unchanged:** the order, the crypto-shred of every envelope, the NO ACTION backstops, the
  `csat_texts` cascade and `guardian_links` kept (awaiting-human retention).

## 4. The grant preflight (INT-394, recorded, not decided)

Migration 0007 grants `app_rw` `SELECT, INSERT, UPDATE` on `notification_preferences`, and
INT-394 (#650) leaves the role that runs erasure to the owner. So the new DELETE cannot run as
`app_rw`, and granting it here would take the owner's decision.

What is built instead (`services/api/src/intake_api/dsar/grants.py`):

- **`ERASURE_PRIVILEGES`**: every privilege the run exercises, statement by statement. It covers
  SELECT on the 16 tables the due-request read and the sweep touch. It covers UPDATE per column
  for the 6 envelope shreds, the request close and the telemetry de-link: column grants are the
  narrowest that work, and `has_column_privilege` accepts a table-level grant too, so the check
  holds under either INT-394 option. It covers DELETE on the 11 tables removed. It declares no
  DELETE on `csat_texts`, because postgres runs a cascade as the table owner.
- **The probe** asks postgres once, before step 1 of the run, with `has_table_privilege` /
  `has_column_privilege` and every argument cast to text. SQLite has no privilege system, so the
  probe reports nothing missing in the unit lane.
- **The refusal.** If the role lacks anything, the run touches neither the object store nor a
  row. It returns `ShredReport(0, 0, 0, blocked=ErasureBlocked(request_ids, missing))`, and each
  `Privilege.describe()` reads, for example, `role lacks DELETE on notification_preferences
  (INT-394)`. It audits `dsar.delete.blocked` against each due `dsar-request:<id>`, followed by
  one `dsar.delete.blocked.missing_grant` per privilege against `db-grant:<table>[.<column>]/<PRIV>`.
  It leaves every request `scheduled`, so the next run tries again.
- **Why before, not on failure:** a run that failed on the first `permission denied` would already
  have removed the subject's object bytes (step 1 runs outside the row transaction on purpose). It
  would also report only the first missing grant.

**The declared grant need.** `tests/legal/test_dsar_flows.py` parses every `GRANT … TO app_rw`
in `migrations/`. The parser must account for every GRANT line that names the role. It compares
the grants against `ERASURE_PRIVILEGES` and pins the gap to exactly three:

| privilege | migration | why `app_rw` lacks it |
|---|---|---|
| DELETE on `notification_preferences` | 0007 | "a preference is set and changed, never erased here" |
| DELETE on `patient_overlays` | 0010 | "the header is bumped, never erased on its own" |
| UPDATE on `events.session_id` | 0001 | events are append-only for the app (INT-392 §8) |

The second and third were already true before this change: the erasure deleted the overlay
header and de-linked telemetry, so it could never complete as `app_rw`. It failed half-way
instead of refusing. The CI integration lane runs the erasure as `app_rw` against the real grants
and asserts the refusal names exactly these three.

## 5. The export

**Doctor Links** are listed in the `shares` section, under the share they reach. A link is one
addressed, expiring way of reaching a share (INT-150). Each line reads:

```
doctor_link:<id> · share:<share_id> · recipient:clinician · created:<ts> · expires:<ts> · revoked:<ts>
```

The recipient is a **role**, never the label. The label is a third party's name, typed by the
patient into an envelope. files/06's DSAR row (KVKK-11/13: "access/rectify/delete/port") has no
clause asking for it. files/10 §3 is the rule the access log already applies to the same grant:
"the patient sees a role, never a name". The patient can still read the label on the link list
(`GET /v1/visits/{id}/note/doctor-links`). A test issues a link through the real route and checks
that the recipient's surname reaches neither the FHIR bundle nor the PDF bytes.

**The other six tables**, each listed by id in the section that fits it:

| table | section | the line carries |
|---|---|---|
| `previsit_outputs` | notes | id, visit, schema version, payload SHA-256, completion instant. The content is the note's, which the section already carries |
| `overlay_facts` | learned_facts (new) | id, fact key, value, confidence, source, source ref, confirmation instant, share flag |
| `patient_overlays` | learned_facts (new) | id, version, last update |
| `csat_texts` | feedback (new) | id, visit, instant, and the comment as stored (after the redaction baseline) |
| `notification_preferences` | preferences (new) | id, opt-out, quiet window `HH:MM-HH:MM` or `none`, last change |
| `guardian_links` | guardians (new) | id, relationship ref, verified/revoked/created instants. Not the guardian's account ref, for the Doctor Link reason |

The **consent** and **rectification** lines now lead with `consent:<id>` / `rectification:<id>`,
as every other line leads with its row's ref. That is what lets the contract check them, and it
lets the patient name the row back to us.

**Numbers (invariant 22).** A learned value is decoded from its INT-309 wire form, so a Decimal
never reaches a line as `~d38.5`. It is written for the export's reader, `tr`, through
`records.numbers.render_quantity`: a comma, no grouping, no exponent. The confidence `0.9` reads
`0,9`.

**Four new counsel headings.** No existing heading fits a learned fact, a satisfaction comment,
the opt-out register or a guardian link. The opt-out register is a refusal under row 6563-İYS
and deliberately not a consent (`consent_guard.NotificationPreferenceDeclaration`). The guardian
link has its own inventory category so that it is never filed as a consent. So
`dsar_export.section.{learned_facts,feedback,preferences,guardians}` join the key set, with **no
wording drafted**. `docs/legal/strings.yaml` does not exist yet (INT-210), so the export refuses
(503) today for all thirteen keys as it did for nine. Nothing that worked stops working.
`docs/legal/COUNSEL_BRIEF.md` §3.4 lists the four new keys with a dated note.
