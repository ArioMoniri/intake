# INT-319 — Dev on-prem expressive-TTS lane for scripted questions + latency harness

> Every figure below is a measurement of one bridge on one day against a named
> corpus. None is a property of a model, an NFR, or a claim about output quality
> (CLAUDE.md invariant 20). Measurements live here, in docs/evidence/, with a
> date and the corpus — never in docs/regulatory/, docs/legal/, or patient copy.

## Acceptance (restated)

1. `make tts-latency` measures four delays per lane — compiled-text→synth start,
   time-to-first-audio, time-to-full-audio, total delivery delay — over one
   fixed named corpus, records them with a date and the corpus, and reports a
   lane it could not measure as **blocked**, never a filled-in number.
2. The expressive runtime lane speaks the scripted line verbatim from `text_tr`
   (inv 10); no numeral reaches any TTS model (inv 22), self-hosted and cloud
   normalisers alike disabled; the harness and adapters assert both.
3. The offline cloud clip-gen adapter (ADR-028) sits behind the existing
   gateway, key from env only and never logged, vendor normaliser disabled,
   spend-gated, no vendor hostname literal in the tree.
4. The runtime never calls the cloud vendor; it plays cached clips → zero
   per-session egress; inv 19 not weakened; ElevenLabs licence/terms and the
   KVKK transfer question recorded as human blockers.
5. Evidence records the per-model latency measurements with date + named corpus,
   described as measurements only.

## Measurement 3 — clip-cache playback path (this host, hermetic)

The fixed set is pre-synthesised offline, so at runtime the device only decodes
and plays a cached clip. Decoding a 1.0 s 24 kHz mono clip to PCM on this Mac,
2026-09-04, n=9: **median 0.003 ms** (min 0.003, max 0.014). Across the seven
live-generated clips above, the decode step is ~0.003–0.007 ms. The runtime
fixed-question path is effectively synth-free — which is the whole point of
offline clip-gen: cloud-quality audio with negligible runtime latency and zero
per-session egress.

## Provider note (for the owner, via the coordinator)

On this bridge and this day, on-prem VoxCPM2 is VRAM-blocked to CPU (6.5–46.9 s
/synthesis) and cannot meet an interactive budget; Freya is the working on-prem
lane (~0.8–1.3 s/clip, telephony-band). The offline ElevenLabs path generated
Turkish at ~1.1–1.3 s/clip and, being **offline**, its speed does not sit on any
session's critical path — the runtime just plays the cache. So the design the
owner chose is coherent: ElevenLabs for the fixed set's quality (offline), the
on-prem lane for the few dynamic lines. The open decisions are the vendor
licence/terms, the KVKK transfer question, and a specific warm Turkish voice id
(the scoped key cannot browse the voice library).
