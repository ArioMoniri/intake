# Runbook: a second admin approver on the synthetic staging host (INT-460)

The console at `https://admin.3-211-2-143.sslip.io` signs staff in through Keycloak (realm `intake`). A dev bearer never opens it, and a staging API with a dev token set refuses to boot (INT-325). So the second approver is a second Keycloak user. Four eyes holds because the two of you differ in subject, security key and session.

**Prerequisite (engineering, not you):** PR #643 (INT-378) is merged and its provider is live in the host's Keycloak. Until then the console refuses every staff token, yours included. TOTP sign-ins stay refused until #644 (INT-389) is decided, so both of you use a security key or a passkey.

**One command (INT-538):** on your laptop, run `scripts/ops/staff_user.sh`, first for yourself (`platform_owner`), then for them (`qms_owner`). It asks for the username, email and role. On your own first run only, while no `platform_owner` exists, it also asks once for your organisation id: 2–40 lowercase letters, digits and hyphens. The second approver then joins your org without being asked. It prints `created` and the one command that shows the temporary password once and deletes it. Hand that over as in step 7. Steps 1–7 are the manual fallback.
1. On your laptop, create their first password without printing it: `aws ssm put-parameter --name /intake/staging/admin2_initial_password --type SecureString --value "$(openssl rand -hex 32)" --region us-east-1`.
2. In a root shell on the host (SSM), log in as the bootstrap admin. Its password is `KEYCLOAK_ADMIN_PASSWORD` in `/etc/intake-staging/.env`; read it there, never in chat. Run `docker exec -it intake-staging-keycloak-1 /opt/keycloak/bin/kcadm.sh config credentials --server http://localhost:8080 --realm master --user intake-bootstrap`, then define `kc() { docker exec -i intake-staging-keycloak-1 /opt/keycloak/bin/kcadm.sh "$@"; }`.
3. Read your own org: `kc get users -r intake -q username=<you> -q exact=true --fields attributes`.
4. Create them in that org: `kc create users -r intake -s username=<them> -s enabled=true -s email=<their mail> -s emailVerified=true -s 'attributes.org=["<your org>"]' -s 'requiredActions=["webauthn-register"]'`.
5. Grant the approver role: `kc add-roles -r intake --uusername <them> --rolename qms_owner`. It approves model-lane switches and cannot request them. Grant `--rolename platform_owner` instead only if they must also request.
6. Set the password from SSM, never on screen: `ID=$(kc get users -r intake -q username=<them> -q exact=true --fields id --format csv --noquotes) && P=$(aws ssm get-parameter --name /intake/staging/admin2_initial_password --with-decryption --query Parameter.Value --output text --region us-east-1) && printf '{"type":"password","temporary":true,"value":"%s"}' "$P" | kc update users/$ID/reset-password -r intake -n -f -; unset P`.
7. Hand it over once. On your laptop run `aws ssm get-parameter --name /intake/staging/admin2_initial_password --with-decryption --query Parameter.Value --output text --region us-east-1` and send the value privately (Signal or in person; never chat, mail or a ticket). After their first sign-in, run `aws ssm delete-parameter --name /intake/staging/admin2_initial_password --region us-east-1`.
8. They sign in at the console, set a new password and register their own security key. They approve on their own device, in their own session. A shared key, a shared session, or approving your own request is refused.
