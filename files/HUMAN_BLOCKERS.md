# HUMAN_BLOCKERS — the things no agent can do

> **What this file is for.** Two audiences, one list.
>
> - **An agent** reads this *before* claiming something is blocked, and *before* inventing a value to get past it. If the thing you are stuck on is here, the answer is already known: it is waiting on a named human. Mark the issue `awaiting-human`, write the ask into `docs/backlog/blockers.md`, and move to the next unblocked issue.
> - **The owner** reads this to see what only he can do — and, for each row, what it is holding up. Rows are sorted by group, not by urgency; the `blocks` column is the urgency.
>
> **Update discipline is the same as `00_STATE.md`.** Add a row; never delete one. A blocker that has been resolved or made moot is marked `closed` **with the reason**, and it stays in the table — a deleted blocker is a blocker that gets re-raised in three weeks by someone who never saw it. Update this file in the same commit as the fact that changed it.
>
> Last updated: **27 Aug 2026**. Source of record for every row: `00_STATE.md` §2, §4, §5, §7 and the decisions in §3.

## The two rules

**Rule 1 — never invent a value to unblock yourself.**
Not a clinical threshold. Not a cut-off, a dose, an age band, a licence number, a reviewer name, a study id, an endpoint, a repo id, a WER, a sensitivity. If a value is needed and no human has supplied it, the correct artefact is the literal string `TODO: <what> requires <who>` plus an `awaiting-human` mark — never a plausible number. A plausible invented number is worse than a missing one, because **there is no diff that makes it look wrong**: it reads as authoritative to every subsequent reader, including the clinician who was supposed to catch it. `files/protocols/base.life_threat.yaml` is the worked example — it carries `TODO: threshold requires clinical sign-off` in four places and not one guessed figure.

**Rule 2 — a blocker being open is not permission to build around it.**
Most rows here gate whether something may be **served**, not whether it may be **written**. The compiler can be built while `base.life_threat` is unsigned; the pack cannot be served. The instrument engine can be built while C-SSRS is licence-blocked; the instrument cannot be compiled into a pack. The `acoustic` lane's plumbing can be built; the lane is unreachable without a registered investigation. So: build the mechanism, wire the gate, make the gate **fail closed**, and leave the content empty. Do not add a bypass, a `dev_only` flag, a "demo mode", a placeholder rule set, or a default that would be chosen once by an engineer for all future cases. If you find yourself designing a way for the product to work without the missing thing, you have converted a blocker into a defect.

**Corollary for the agent's own reporting.** "Blocked" is a status with an owner and an ask, not an excuse. A row that says `awaiting-human` must name **who** and **what one sentence they need to answer**. If you cannot write that sentence, you are not blocked — you have not finished thinking.

## 5 · How a row gets closed

A row moves to `closed` when **one** of these is true, and the reason is written into the row:

1. **The human did the thing.** Record what they supplied and where it now lives — the signed commit, the licence letter, the contract, the credential's OpenBao path (never the credential).
2. **A decision made it moot.** HB-L5 is the worked example: the self-hosting constraint deleted the vendor socket, so the DPA question has no subject. Cite the decision id from `00 §3`.
3. **The scope that needed it was dropped.** Cite the issue and the decision. This is the only closure that is allowed to leave work undone, and it must say so.

A row does **not** get closed because it has been open a long time, because a workaround was found, or because the agent stopped needing it. If an agent finds a way to proceed without a blocker, that is a fact worth recording in the row — and it is still not a closure, because Rule 2 says the mechanism being buildable was never the question.
